## 2. 크롤링에서 걸린 함정 ⚠️

> [!warning] 다른 아사달 보드 사이트에도 그대로 적용되는 교훈
> 페이징 파라미터를 **번호만 보고 검증하면 안 된다.**

### 2-1. `thisPage`는 표시용, `startTextId`가 진짜 offset

```
list.htm?bn=cause04&thisPage=3     → No 컬럼만 182,181,180 으로 바뀜. 내용은 동일
list.htm?bn=cause04&startTextId=24 → 실제로 다른 12건
```

처음에 `No` 컬럼만 비교하고 "페이지마다 다르네" 하고 넘어갔다가, **18페이지 전부 같은 12건**을 받았다. 사업명까지 비교해야 잡힌다.

- `startTextId` = 0-based offset, 페이지당 12
- `buffer` = (전체건수 − offset), 서버가 재계산하므로 불필요
- 초과 offset은 빈 결과

### 2-2. 페이저가 들어온 쿼리스트링을 그대로 되뱉는다

```
요청:  ?bn=cause04&startTextId=24
링크:  ?bn=cause04&startTextId=24&categoryValue=0&bn=cause04&thisPage=3&startTextId=24&buffer=182
                  ^^^^^^^^^^^^^^ 그대로 붙어서 나옴
```

한 홉마다 파라미터가 누적 → URL 무한 증식 → **3만 건 요청**하고 멈췄다.

**해결**: PHP가 같은 이름이면 마지막 값을 쓰므로, 정규화에서도 **이름당 마지막 값만** 남긴다. 그러면 서버가 실제로 보는 값과 정규형이 일치한다.

### 2-3. 안전장치

`config.crawl.max_requests`로 상한을 둔다. 사이트 전체가 800건 내외인데 그걸 넘으면 URL 증식 버그를 의심해야 한다.

## 4. 온톨로지 — 라벨 15개

### 결정 규칙

> [!note] 규칙 1 — 노드인가 속성인가 (셋 다 만족하면 노드)
> ① 값이 여러 노드에서 반복 참조되는가
> ② 그 값에 다른 것이 매달리는가
> ③ N:M 인가
>
> `Domain` ✅ (206건이 3종 참조, 51건 다중) → 노드
> `contract_date` ❌ (아무도 참조 안 함) → 속성

> [!note] 규칙 2 — 라벨을 나누는가 (셋이 전부 같으면 같은 라벨)
> ① 같은 키로 식별되는가
> ② 같은 속성 집합·제약을 갖는가
> ③ 같은 간선이 같은 방향으로 붙는가
>
> `BusinessArea` + `Technology` → 셋 다 같음(둘 다 `OFFERS`를 받음) → **`:Offering {kind}` 로 병합**
> `Page` + `Asset` → 셋 다 같음 → **`:Resource {kind}` 로 병합**
> `Domain` / `OrgType` → 간선이 다름(`IN_DOMAIN` vs `FOR_ORG_TYPE`) → 분리 유지

> [!note] 규칙 3 — 두 번째 라벨은 제약이 달라질 때만
> 상태는 라벨이 아니라 속성이다. 규모가 작으면 규칙 2가 나누라고 해도 안 나눈다.
>
> 절단 발주처 23건 → `name_truncated: true` 속성
> 주요실적 12건 → 속성 집합은 다르지만 12건뿐 → `is_highlight` 속성

> [!note] 규칙 4 — 서브그래프를 섞지 않는다
> 웹사이트 산물(`:Resource`, `:Notice`, `:Photo`)은 도메인 개념이 아니다.
> 같은 DB에 넣되 `SOURCE_OF`로만 잇는다. 안 그러면 "회사의 지식그래프"가 아니라
> "홈페이지를 그래프로 옮긴 것"이 된다.

### 라벨 목록

**도메인 그래프 (11)**
`:Company` `:Project` `:Organization` `:Domain` `:OrgType` `:Department` `:Team` `:Office` `:HistoryEvent` `:Certificate` `:Offering`

**웹 아카이브 (4)**
`:Resource` `:Notice` `:Photo` `:ExternalSite`

### 핵심 관계

| 관계 | 카디널리티 | 건수 |
|---|---|---|
| `(Company)-[:PERFORMED]->(Project)` | 1:N | 206 |
| `(Project)-[:ORDERED_BY]->(Organization)` | N:1 | 206 |
| `(Project)-[:IN_DOMAIN]->(Domain)` | **N:M** | 201 (다중 51) |
| `(Project)-[:FOR_ORG_TYPE]->(OrgType)` | N:1 | 206 |
| `(Organization)-[:HOMEPAGE]->(ExternalSite)` | 1:1 | 12 |
| `(*)-[:SOURCE_OF]->(Resource)` | N:1 | 전량 |

### 식별자 정책

**자연키가 없다.** 목록의 `No`는 표시용이라 키로 쓰면 데이터가 뒤섞인다.

```

Organization org:{slug(name_normalized)}
Resource     {정규형 URL}
```

## 5. 계층 — 온톨로지가 실제로 값을 내는 지점

평평한 분류만 있으면 추론할 게 없어서 "온톨로지"라 부를 근거가 약하다. 계층 두 개를 선언한다.

```
:OrgType                                :Domain
  public_sector ← 선언(observed:false)     Homepage
    ├ Government of the ROK    34          System
    ├ a local government       88            └ IntegratedInformationSystem
    ├ a public institution     58                (근거 18/18)
    ├ education    ← 고객페이지에만
    └ legislature  ← 고객페이지에만
  nonprofit ← 선언
    └ Foundations and assoc.   26
```

관계 타입 하나 추가: `(:OrgType)-[:BROADER]->(:OrgType)`

```cypher
MATCH (p:Project)-[:FOR_ORG_TYPE]->(:OrgType)-[:BROADER*0..]->(:OrgType {code:'public_sector'})
RETURN count(DISTINCT p)
// 180   ← 88+58+34. 어디에도 저장하지 않은 숫자
```

속성 2개 추가
- `observed: bool` — 데이터에서 관측 vs 우리가 선언. **섞으면 안 된다**
- `scheme_codes: map` — 게시판 4종 / 고객페이지 6종 두 체계 코드를 한 노드에

> [!tip] 정직하게
> **실제로 새 질의를 벌어주는 건 OrgType 계층 하나뿐.**
> Domain 계층은 IIS에 이미 System이 붙어 있어 질의 이득이 없고, "IIS인데 System 없음 = 0건" 무결성 검사용이다.

**라벨은 안 늘어난다.** `public_sector`도 `:OrgType`이다 (규칙 2).

## 6. 파이프라인 — 5단계, 4개의 파일 경계

```
fetch → nara1data/ → parse → graph/ → resolve → resolved/ → validate ⛔ → load → Neo4j
```

한 명령으로 끝까지 돌지만 **단계마다 파일로 떨어진다.** 묶지 않는 이유는 성능이 아니라 진단 가능성 — 크롤이 틀렸다는 건 파싱해 봐야 안다.

| 단계 | 재실행 | 실패하면 |
|---|---|---|
| fetch | 증분 (sha256 / 304) | 이어받기 |
| parse | 전량 (수 초) | 해당 추출기만 실패 |
| resolve | 전량 (결정은 누적) | 미해결은 플래그 달고 통과 |
| validate | 전량 | **적재 중단** |
| load | 전량 MERGE (멱등) | 트랜잭션 롤백 |

### load 순서

1. 제약 DDL 생성·실행 (`IS UNIQUE`, `IS NOT NULL`)
2. **노드 전부** MERGE
3. **그 다음 간선** MERGE (노드가 다 있어야 참조됨)
4. `_crawl_run` 태깅
5. 이전 run에만 있는 노드 정리

## 7. 전처리 — 6층으로 분리

한 덩어리 함수로 쓰면 어느 층에서 값이 뭉개졌는지 못 찾는다.

| 층 | 하는 일 | 실측 근거 |
|---|---|---|
| **clean** | `&nbsp;` 제거 → 공백 축약 → strip | 사업명 206건 **전부** 앞에 `&nbsp;`. 안 벗기면 대리키가 통째로 어긋남 |
| **cast** | 날짜·정수 변환 | `%Y-%m-%d` 파싱 실패 0건 |
| **dedup** | 행 중복 제거 | 탭 4개가 같은 게시판 렌더 → **618행 → 206** |
| **normalize** | 기관명 정규화 | NFC, `㈜→(주)`, 괄호 공백, 절단 판정 `endswith('..')` |
| **transform** | 코드 훅 | 조직도 세로쓰기 재조립 / 연혁 날짜 2종 |
| **derive** | 파생값 | `year` ← 계약일, `is_highlight` ← 주요실적 12/12 일치, `id` ← sha1 |

## 8. 증분은 데이터가 아니라 **결정**에 건다

206건 규모에서 파싱·적재를 증분화하면 얻는 건 몇 초고, 잃는 건 "언제 돌려도 같은 결과"라는 성질이다.

```
데이터    → 매번 전량 재구축   (멱등, 원본이 진실)
사람 결정 → 증분 누적          (파일로 버전관리)
```

```yaml
# resolutions/organizations.yaml — 사람이 채우는 유일한 파일
- raw: "(재)예술경영지원센.."
  resolved: "(재)예술경영지원센터"
  method: manual          # manual / llm-suggested / external-source
  approved_by: kyeung     # llm-suggested 인데 이게 비면 load 가 안 씀
```

적재기가 파싱 결과 **위에 덧씌운다**. 결정이 없어도 파이프라인은 안 멈추고, 미해결만 `review-queue.yaml`로 떨어져 **검토 대상이 자연히 증분**이 된다.

## 9. LLM의 위치 — 파이프라인 **옆**

> [!important] 런타임에 LLM은 없다
> 행을 뽑는 건 CSS 셀렉터, 전처리 6층은 전부 결정적 코드다.
> 정형 테이블을 LLM으로 파싱하면 비결정적이고, 그럴듯하게 **틀린 값**을 낸다.

```
parse → resolve → validate → load     ← 전부 결정적 코드
          ↑
       resolutions/*.yaml  ← 동결된 결정
          ↑  사람 승인
       LLM 제안 (review-queue.yaml)
```

LLM은 **제안자**다. 승인되면 파일로 동결되고 다음 실행부터는 부르지 않는다.

| LLM이 값을 내는 곳 | 규모 | 위험 |
|---|---|---|
| 연혁 텍스트 구조화 | 27건 | 낮음 |
| 기관유형 충돌 대표값 | 14곳 | 낮음 |
| 기관명 동일성 판정 | 소수 | 중간 |
| **절단 이름 복원** | 23개 | **높음** — 데이터가 아니라 사전지식에서 나온 답 |
| **산문 페이지 사실 추출** | 17페이지 | 중간 — §10 참조 |

**개발 시점**엔 LLM이 `ontology.yaml`을 쓴다. **런타임**엔 그 yaml이 파이프라인을 돌린다.

## 10. 온톨로지 주도 수준 — Level 0 ~ 3

> [!question] 판별 기준 하나
> **새 엔티티를 추가할 때 코드를 고쳐야 하나?**
> 고쳐야 하면 온톨로지가 아니라 config다.

> [!caution] 이 Level 0~3 사다리는 표준 용어가 아니라 이 프로젝트에서 만든 프레임이다.
> 설명 도구로는 쓰되 외부에 그대로 인용하지 말 것.

| | 내용 | 비용(감) |
|---|---|---|
| **Level 0** | 코드가 흐름을 알고 YAML에서 값만 받음 = 설정 파일 | — |
| **Level 1** | 코드에 도메인 지식 0. 추출 primitive만 구현 → 새 엔티티 = YAML만 | 1~2일 |
| **Level 2** | `domain`/`range`/`cardinality`/계층 선언에서 **검사가 자동 생성** | 반나절 |
| **Level 3** | `coverage_target` + `gap_action` → 격차 계산해 **할 일을 자동 도출** | 반나절 |

비용은 근거 있는 추정이 아니라 감이다.

### 페이지 모양 실측 — primitive 7개

콘텐츠 페이지 43개를 실제로 분류한 결과. (처음엔 6개라고 썼는데 **틀렸다.**
가장 큰 덩어리인 `prose`가 빠져 있었다.)

```
17  prose            ← 산문+이미지. 보유기술 12, 사업분야 4, 인재채용, CI, 사가
 7  card/image-list  ← 주요실적, 주요인증, 주요고객, 회사사진
 5  table            ← 사업실적, 공지 목록
 2  table + span-pair
 2  image-only       ← 오시는 길, 번역 데모
 1  year-block       ← 연혁
 1  tree             ← 조직도
 1  table + year-block
```

- `definition-list` 라고 적었던 회사개요는 `<dl>` 이 아니라
  `<ul><li><span>법 인 명</span><span>㈜나라원시스템</span></li>` → 이름은 **`span-pair`** 가 맞다.

> [!warning] Level 1 의 효용은 정형 페이지에 한정된다
> `prose` 17페이지에서 뽑을 수 있는 건 `{제목, 본문, 이미지}` 뿐이다.
> 여기서 나오는 `:Offering` 16개는 **구조화 추출이 아니라 페이지 하나 = 노드 하나**다.
> 산문에서 의미 있는 사실을 뽑으려면 LLM이나 손으로 쓴 규칙이 필요하다.
>
> **"새 엔티티 = YAML만" 은 43개 중 26개(정형)에만 참이다.**

### Level 2 — 선언에서 검사가 나온다

```yaml
edges:
  ORDERED_BY: {domain: Project, range: Organization, cardinality: N:1}
```

이 한 줄에서 검사 3개가 자동 생성 → `validate.py` 는 무엇을 검사하는지 모른다.

```python
for name, e in ontology["edges"].items():
    check_domain(name, e["domain"])
    check_range(name, e["range"])
    check_cardinality(name, e["cardinality"])
```

계층도 같다. `hierarchy: {Domain: {System: [IntegratedInformationSystem]}}` 두 줄에서
**BROADER 간선 생성 + 무결성 검사 + 상위 집계 질의** 세 가지가 나온다.

이건 SHACL·OWL이 하는 일과 같은 것이라 표준적이다.

### Level 3 — 격차가 할 일이 된다

```yaml
Organization.homepage_url:
  coverage_target: 81/81
  source: highlight.client_url
  gap_action: needs_external
```

→ 돌리면 `12/81, 격차 69건, 사이트 내 출처 없음` 이 **자동으로** 나온다.
§12 "채울 수 없는 칸" 표를 손으로 안 적어도 매번 계산된다.

> [!warning] 크롤 시드를 온톨로지로 대체하면 안 된다
> "온톨로지가 필요한 페이지를 알고 있으니 시드가 필요 없다"고 썼는데, **반대급부를 빠뜨렸다.**
> 선언하지 않은 페이지는 영영 발견하지 못한다.
>
> 이번 BFS가 내비게이션에 없는 페이지 둘을 실제로 찾아냈다:
> `/art/homepage_trans.htm`, `/class/aiservicedevelopment.htm`
>
> 올바른 설계: **BFS 는 발견용으로 유지하고, 온톨로지는 표적 갱신용으로 쓴다.**

### 결론

**Level 2 까지 간다.** 비용이 적고 여기까지 안 가면 온톨로지라 부를 근거가 없다.
**Level 1 은 선택** — `prose` 17페이지 때문에 효용이 반감했다.
**Level 3 은 `coverage_target` 만** 취한다. 크롤 역방향은 안 한다.
