# 온톨로지 자동화 정도

> 관리자가 프론트에서 **개발자 없이** 온톨로지를 어디까지 바꿀 수 있나 — 2026-09-29 논의 정리.
> 결론: **추가 · 삭제 · 그 둘을 조합한 변경(옮기는 규칙이 기계적일 때)** 까지가 최대치. 의미 판단 · 업무 규칙 · 키는 사람(개발자).

---

## 1. 원칙 — LLM 은 제안, 사람은 승인, 코드는 적용·검증

```
① 계기      업로드 파일에 온톨로지에 없는 값·칸이 나옴
② 제안      LLM(또는 관리자)이 **정해진 양식의 변경 명령**을 냄
            { 명령: "어휘에 값 추가", 어휘: "rank", 값: "수석연구원", 근거: "명단 260928.xlsx 12행" }
③ 검토      관리자가 변경 전후 비교를 보고 승인 (필요하면 칸을 직접 고침)
④ 적용      코드가 승인된 명령만 적용 — LLM 없음
⑤ 검증      규칙 기반 자동 검사 → 섀도우 시험 → 운영 전환
```

- LLM 은 **온톨로지 JSON 을 받지도 쓰지도 않는다.** 변경 명령만 낸다 → 기존 정의를 빠뜨리거나 바꿀 방법이 없다.
- 허용 명령 종류를 정해 둔다(어휘 추가 · 동의어 추가 · 속성 추가 · 라벨 추가 · 관계 추가 …). "기존 항목 수정·삭제" 는 관리자 경로에 없음(단계 이전은 §4).
- 할루시네이션이 들어갈 수 있는 곳은 **② 제안뿐** → ③ 사람 검토 + ⑤ 기계 검증으로 거른다.

## 2. 규칙 기반 검증 (⑤)

| 검사 | 내용 |
|---|---|
| 기존 보존 | 옛 버전의 모든 라벨·관계·속성·어휘 값 ⊆ 새 버전 (하나라도 빠지거나 바뀌면 거부) |
| 차이 일치 | 새 버전 − 옛 버전 = 승인한 명령과 정확히 일치 (명령에 없는 추가도 거부) |
| 온톨로지 규칙 | 없는 라벨을 가리키는 관계, 중복 이름 등 — 지금 `build.py` 검사 |
| 데이터 재검증 | 기존 운영 데이터 전체가 새 버전으로 통과 (섀도우). 추가형이면 전부 통과해야 정상 |
| 예시 질문 | 관리자가 적은 예시 질문 + 누적 회귀 질문을 섀도우에서 실행 |

- 버전은 **덮어쓰지 않는다.** 버전마다 새로 저장 + sha256 고정(지금도 `ontology/versions/nara1-0.6.x.json`). 롤백 = 이전 버전으로.

## 3. 변경 종류별 가능 범위

| 변경 | 예 | 지금 구조 | 바뀐 구조¹ |
|---|---|---|---|
| 어휘 값 추가 | 직급 `수석연구원` | 관리자 가능² | 관리자 |
| 동의어 · 예시 질문 추가 | `AI 개발1팀` | 관리자 가능² | 관리자 |
| 선택 속성 추가 | 직원 `내선번호` | 관리자 가능² (LLM 공개 여부는 권한자) | 관리자 |
| 새 라벨 · 새 관계 | `Certification` · `HAS_CERT` | 관리자 가능², 조회 품질 보장 못함 | 관리자 |
| 이름 변경 · 안 쓰는 속성 삭제 | `rank` → `grade` | 개발자 | **관리자** (확장→이전→축소) |
| 명확한 타입 변환 | 문자 날짜 → 날짜 | 개발자 | 관리자 (변환 실패 시 멈춤) |
| 의미가 바뀌는 변경 | 칸 나누기 · 합치기 | 개발자 | **개발자** (옮기는 방법이 판단) |
| 업무 규칙이 닿는 변경 | 겸직 허용(카디널리티) | 개발자 | **개발자** (퇴사 판정·속성 합치기 로직) |
| 키 변경 | 직원 키 규칙 | 개발자 | **개발자** (노드 정체성) |

¹ 적재·조회가 이름을 코드에 박지 않고 온톨로지에서 읽는 구조
² 온톨로지 저장소를 DB 로 옮기고 조회가 버전을 실행 중에 따라가게 바꾼 뒤

- 실제 이력: 0.6.2 의 `SUBSIDIARY_OF` 추가 · 어휘 추가(`초급직원`, `AI개발자` …)는 관리자 영역. **`MEMBER_OF` 겸직 허용만** 구조 변경이었고 적재 로직을 같이 고쳐야 했다.

## 4. 기존 것 변경 = 추가 + 삭제로 쪼개기 (확장 → 이전 → 축소)

```
rank → grade
① 확장  grade 속성 추가                  (추가형)
② 이전  모든 노드 grade = rank 복사        (개수·값 일치 기계 검증)
③ 전환  적재·조회가 grade 를 쓰게          (이름을 온톨로지에서 읽으면 설정 변경)
④ 대기  둘 다 둔 채 회귀 시험 통과 확인
⑤ 축소  rank 삭제                          (아무도 안 쓰는 걸 확인한 뒤)
```

- 조건: **옮기는 규칙이 기계적**이어야 한다(값 복사, 명확한 타입 변환, 어휘 대응표).
- 구조와 상관없이 남는 것: 의미 판단(나누기·합치기) · 적재 업무 규칙(퇴사·겸직·대량 퇴사 멈춤) · 키(정체성).

## 5. 바로 반영(승인 즉시)하려면 바뀌어야 할 것

지금 막히는 곳:

| 막히는 곳 | 지금 | 결과 |
|---|---|---|
| 온톨로지 보관 | git 파일(`declaration.py` → `versions/*.json`) | 커밋·배포 필요 |
| 현재 버전 | 코드 상수 `ONTOLOGY_VERSION` | 코드 수정 필요 |
| 조회 버전 검사 | 코드 버전 = DB 버전이어야 답함 | 온톨로지만 바뀌면 조회 멈춤 |
| 조회 스키마 로드 | 서버 시작 시 한 번 | 재시작 필요 |

바뀐 흐름:

```
승인 → 규칙 검사 → 섀도우 시험 → 온톨로지 저장소(DB 표)에 새 버전
     → 운영 Neo4j 한 트랜잭션: 새 제약·인덱스 + ReleaseHead 온톨로지 버전 교체
     → 조회는 요청마다 ReleaseHead 버전을 보고 그 버전 스키마 사용(버전별 캐시)
```

- **온톨로지 저장소** = 온톨로지 정의를 보관하는 곳. 지금은 git 파일, 바꾸면 DB 표(버전 · 내용 JSON · 상태 · 승인자 · 시각). 내용·칸 구성은 지금 JSON 과 같다.
- 한 트랜잭션 전환 → 적재·릴리즈 사이 조회 공백도 사라짐.
- 전환 중 돌던 적재는 쓰기 직전 지문 확인에서 멈춤 → 다시 돌리면 됨(섞이지 않음).

## 6. 조회 품질을 위해 온톨로지에 더 담을 것

지금 조회 품질을 좌우하는 정보 일부가 **조회 코드**(`graph_rag/guided_schema.py`)에 박혀 있다. 새 라벨이 들어오면:

1. 안 보임 — LLM 에 넘기는 라벨이 코드 목록 `SEARCH_LABELS`(9개)뿐
2. 결과 0건 — "살아 있음" 조건이 직원 외 전부 `site_status=present` 고정
3. 이름으로 못 찾음 — 1단계 찾기가 `name` 속성 고정
4. 관계 방향 실수 — 방향 뜻이 코드 `RELATION_MEANINGS` 에만
5. 전용 로직 없음 — 소속·연락처·조직 계층은 전용 코드가 받쳐 줌(온톨로지로 대체 불가)

온톨로지 양식(`ontology/model.py`)에 추가할 칸 (예):

```python
class NodeSpec:        # 기존: ko, key, properties, synonyms, note, read_by …
    searchable: bool                    # 조회 공개 (← SEARCH_LABELS)
    name_property: str | None           # 이름으로 찾을 속성
    alive: dict[str, str] | None        # 살아 있는 노드 조건
    examples: list[str]                 # 예시 질문 = 자동 시험

class RelationSpec:
    meaning: str | None                 # 정방향 뜻 (← RELATION_MEANINGS)
    meaning_reverse: str | None         # 역방향 뜻
    examples: list[str]

class PropertySpec:
    exposure: 'llm' | 'lookup' | 'hidden'   # LLM 공개 / 코드 조회만(전화번호) / 숨김 (← HIDDEN_PROPERTIES)
```

- 값은 `ontology/definition/declaration.py` 에 채우고, 승격하면 `versions/` 에 새 JSON. 칸만 느니 패치 버전. **그래프 데이터는 안 바뀜**(설명서).
- 조회 쪽은 상수를 지우고 이 칸을 읽게 — 조회 담당.
- 나중에 DB 저장소로 옮겨도 칸 구성은 그대로, **관리자 화면 입력 칸 = 이 칸들**.

## 7. 개발자 개입 — "변경마다 승인" 이 아니라 "운영하며 품질 개선"

- 추가형: 관리자 + 자동 시험으로 충분.
- 구조 변경: 개발자 필수. 관리자 프론트는 **요청만** 받는다.
- 품질 유지: 라벨별 실패 지표(`no_match` · `ambiguous` · `query_generation_failed`)를 보고 **주기적으로** 전용 로직·예시 보강.
- 예시 질문 회귀 시험 모음이 개발자 리뷰를 대신하는 핵심.

## 8. 관련 — 정형 파일에서의 LLM 역할

- 양식이 다르거나 처음 보는 파일 → LLM 은 **"이 파일이 뭔지 · 칸 → 속성 연결표"만 제안**, 사람 확인 후 양식으로 저장.
- 실제 값 읽기는 **파서(코드)** — 정확·재현·개인정보(LLM 엔 머리행 + 가린 샘플만).
- 한 번 승인한 양식은 다음부터 LLM 없이. 지금 명단 파서의 칸 이름 목록이 곧 연결표이고, 모르는 칸에서 멈추는 자리가 LLM 제안이 들어갈 자리.
- 온톨로지에 없는 대상이면 넣지 않고 멈춤 → 온톨로지 변경 **요청**.

## 한 줄 요약

**LLM 이 제안 → 사람이 승인 → 코드가 적용하고 "기존은 그대로 · 차이는 승인한 것뿐" 을 규칙으로 증명.** 관리자가 할 수 있는 최대치는 추가 · 삭제 · 기계적으로 옮길 수 있는 조합 변경. 의미 · 업무 규칙 · 키는 개발자.

## 9. 새 버전은 누가 쓰나 — 제안서가 곧 변경 내용

- 프론트는 **"제안서 #N 승인"** 신호만 보낸다(관리자가 고친 칸이 있으면 그 값 포함).
- 제안서에는 **넣을 내용 전체**가 들어 있다 — 라벨 추가면 라벨 정의 전체(한국어 이름 · 키 · 이름 속성 · 속성과 공개 여부 · 동의어 · 예시 질문 · 관계와 양방향 뜻). LLM 이 초안, 관리자가 화면 칸에서 확인·수정.
- **승인 순간 화면에 보인 내용 = 적용될 내용.** 승인 뒤 새로 생성되는 것 없음.

```
서버 적용 코드
① 저장소에서 현재 승인 버전 JSON 읽기
② 제안서의 명령 꺼내기
③ 명령 종류별 고정 함수로 적용
     라벨 추가    → nodes["Certification"] = 내용
     어휘 값 추가 → vocabulary["rank"]["values"].append("수석연구원")
④ 버전 번호 올리기
⑤ 모양 검사(ontology/model.py) → 규칙 검사 → 차이 검사
⑥ 정규화해 새 행으로 저장 (해시 · 승인자 · 제안서 번호)
```

- 지금도 같은 방식: `versions/*.json` 은 사람이 아니라 `build.py` 가 선언(`declaration.py`)에서 만든다. 바뀌는 건 입력(개발자 선언 → 승인된 명령)뿐.

### 차이 검사 방법

- 옛·새 JSON 을 정규화(키 정렬) 후 **"경로 = 값" 목록으로 펼쳐 집합 비교** → 차이 목록(`+` 추가 · `−` 삭제 · `~` 변경).
- 명령마다 기대 차이가 정해져 있다(어휘 값 추가 → `+ vocabulary.rank.values "수석연구원"`).
- 통과 조건: 차이마다 짝이 되는 명령이 있고 · 명령마다 짝이 되는 차이가 있고 · 추가형 명령뿐이면 `−` `~` 가 0개.
- 적용(명령 실행)과 검사(결과만 보고 차이 계산)가 **서로 다른 방식**이라 의미가 있다 — 적용 코드 버그 · 저장 중 변질 · 명령 없는 직접 수정 · 그사이 다른 변경(옛 버전 해시 확인)을 잡는다.

## 10. 라벨 의미 중복 위험

관리자가 라벨을 쉽게 추가하면 가장 먼저 생길 문제:

- `Certification`(자격증) · `License`(면허) · `Qualification`(자격) 이 따로 생김
- `Client` 가 있는데 `Customer` · `Partner` 가 또 생김
- 관계도 `HAS_CERT` · `HOLDS_CERT` · `CERTIFIED_IN`

→ 같은 사실이 흩어지고 조회 LLM 이 어느 라벨로 찾을지 헷갈려 **조회 품질 직접 하락.** 나중에 합치기는 의미 판단 + 키 변경 = **개발자 구조 변경.** 그래서 **추가 시점에 막는 게** 핵심.

| 방법 | 내용 | 막는 것 |
|---|---|---|
| 재사용 먼저 | 제안서 필수 칸 "비슷한 기존 항목 · 재사용 안 되는 이유". LLM 에 "라벨 추가는 마지막 수단" | 불필요한 라벨 |
| 규칙 충돌 검사 | 이름 · 한국어 이름 · 동의어가 기존과 겹치면 거부(정규화 비교). 같은 출발·도착 쌍에 관계가 있으면 경고 | 이름 겹침 (확실) |
| 의미 유사도 경고 | 설명 · 동의어 · 예시 질문을 임베딩(BGE-M3)해 기존 라벨과 비교, 기준 초과 시 상위 권한 승인 | 뜻 겹침 (애매) |
| 작은 추가 권장 | 새 라벨 대신 속성 · 어휘 값으로 (예: `Certification` 에 `종류` = 자격증 · 면허) | 라벨 난립 |
| 권한 · 정기 점검 | 어휘 · 동의어는 일반 관리자, 라벨 · 관계는 온톨로지 담당 권한. 분기마다 유사도로 겹침 후보 추출 → 합치기는 개발자 | 누적 중복 |

- 규칙은 **이름 겹침**만 확실히 잡는다. **뜻 겹침**은 유사도 경고 + 사람 판단 — 완전 자동으로는 못 막는다.
- 라벨 수가 빠르게 늘면 그 자체가 경고 신호.

## 11. 결론 — 개발자만 온톨로지를 만지게 하는 선택지

위 위험(의미 중복 · 조회 품질 · 합치기 비용)을 보면 **온톨로지는 개발자만 수정하는 것**도 충분히 합리적인 선택이다.

| 선택 | 장점 | 단점 |
|---|---|---|
| **A. 개발자만** (지금 방식) | 온톨로지 일관성 · 조회 품질 · 보안 판단을 코드 리뷰로 보장. 새 구조(DB 저장소 · 동적 버전 전환 · 제안 화면) 불필요 | 어휘 값 하나에도 개발자 · 배포 필요 → 느림 |
| **B. 관리자에게 추가형만** | 일상 변경(어휘 · 동의어 · 선택 속성)은 빠름 | 저장소 DB 이전 · 조회 동적 전환 · 제안/검증 구현 필요 |
| **C. 관리자에게 라벨 · 관계까지** | 새 대상도 개발자 없이 | B 비용 + 의미 중복 방지 장치 + 조회 품질 운영 필요. 위험 가장 큼 |

현실적인 절충:

- **온톨로지 수정은 개발자만(A).** 대신 프론트에는 **"온톨로지 변경 요청"** 만 둔다 — LLM 이 업로드에서 빠진 값 · 칸을 찾아 **요청서 초안**(무엇을 · 왜 · 근거 파일)을 만들고, 관리자는 요청만 낸다.
- 개발자는 요청을 보고 선언 수정 → 승격 → 조회와 같이 배포. 요청서가 제안서 양식과 같으면 반영이 빠르다(초안 PR 자동 생성까지 가능).
- 나중에 요청 대부분이 **어휘 · 동의어 추가**로 반복되면, 그 종류만 B 로 여는 걸 검토.

**한 줄:** 라벨 · 관계는 뜻이 겹치면 되돌리기 비싼 구조 변경이 된다 — 온톨로지는 개발자가 지키고, 관리자는 요청으로 참여하는 게 지금 규모에선 가장 안전하다.
