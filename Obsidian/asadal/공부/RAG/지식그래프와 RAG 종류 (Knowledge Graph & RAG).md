## 개념

**지식 그래프**는 개념 간의 관계를 그래프 구조로 표현한 데이터베이스이며,
**RAG(Retrieval-Augmented Generation)** 는 외부 지식을 검색해 LLM 답변 품질을 높이는 기법입니다.
두 기술을 결합하면 단순 유사도 검색을 넘어 관계 기반 추론이 가능해집니다.

# 지식그래프 기초

## 노드 & 엣지

**노드 (Node)** — 그래프 안의 개체(Entity)
```
[서울], [이순신], [대한민국] 각각이 노드
```

**엣지 (Edge)** — 노드와 노드를 잇는 관계(Relation)
```
[이순신] ──소속──→ [조선]
          ↑
         엣지
```

- 노드에는 **속성(properties)** 을 붙일 수 있음 — 이름, 타입, 임베딩 벡터, 중요도 점수 등
- 엣지에는 **가중치(weight)** 를 줄 수 있음 — "얼마나 강한 관계인가"를 수치로 표현

> 노드 = 점, 엣지 = 점과 점을 잇는 선

## 온톨로지 (Ontology)

**타입, 속성, 관계의 규칙을 정의하는 설계 공간**

- 어떤 **타입**이 존재하는가 → `사람`, `도시`, `나라`
- 타입이 가질 수 있는 **속성**은 뭔가 → `사람`은 `이름`, `생년월일`, `직업`을 가짐
- 타입 간 **관계 규칙**은 뭔가 → `사람`은 `나라`에 `소속될 수 있다`

```
온톨로지
├── 타입 정의:    사람 / 도시 / 나라
├── 속성 정의:    사람.이름, 사람.직업, 도시.인구
└── 관계 규칙:    사람 → [소속] → 나라
                 도시 → [수도이다] → 나라
```

### 엣지 속성 — 필수 vs 선택

온톨로지에서 엣지 속성을 정의해도 **반드시 채워야 하는 건 아닙니다.**
속성은 "가질 수 있다"는 허용이지, "반드시 채워야 한다"는 강제가 아닙니다.

```
온톨로지 정의:
출연 관계 → {기간, 배역, confidence} 가질 수 있음

실제 데이터:
(아이유) -[출연 {기간: "2018", 배역: "지안"}]-> (나의아저씨)  ← 채움
(아이유) -[출연]-> (드림하이)                                  ← 생략해도 OK
```

단, 온톨로지 설계 시 **required**로 지정한 속성은 반드시 채워야 합니다:
```
소속 관계 → valid_from (필수), valid_to (선택)
```

## 지식 그래프 (Knowledge Graph)

**온톨로지 설계도대로 노드를 만들고 엣지로 연결한 실제 데이터**

```
지식 그래프
├── 노드 생성:  이순신 (타입: 사람, 이름: "이순신", 직업: "장군")
├── 노드 생성:  조선   (타입: 나라)
└── 엣지 연결:  [이순신] ──소속──→ [조선]
```

| | 온톨로지 | 지식 그래프 |
|--|---------|------------|
| 역할 | 설계도 | 실제 데이터 |
| 내용 | 타입/속성/관계 규칙 정의 | 규칙에 맞게 노드 생성 + 엣지 연결 |
| 비유 | 건축 설계도 | 설계도대로 지은 건물 |

## 트리플 (Triple)

지식그래프의 **최소 저장 단위**입니다. 모든 지식을 `(주어) -[관계]-> (목적어)` 형태로 표현합니다.

```
(아이유) -[출연]-> (나의 아저씨)
```

벡터DB는 "텍스트 덩어리"를 저장하지만, 지식그래프는 "사실(fact) 하나하나"를 저장합니다.
덕분에 "A와 B가 어떻게 연결되는가"에 답할 수 있습니다.

### 트리플 확장 형태

기본형은 주어-관계-목적어 3개짜리가 맞지만, 실무에서는 확장해서 씁니다.

#### 1) 속성이 붙은 트리플 — 가장 흔한 형태

엣지에 시간, 출처, 신뢰도 같은 메타데이터를 답니다:
```
(아이유) -[출연 {기간: "2018", 배역: "지안", confidence: 0.9}]-> (나의아저씨)
```
Neo4j 같은 **Property Graph** 모델이 이를 기본 지원합니다.
RDF 방식은 `reification`이라는 별도 우회 기법이 필요합니다.

#### 2) N-ary 관계 — 참여자가 3명 이상일 때

주어-관계-목적어 하나로 못 담는 경우, **이벤트 노드를 만들어 우회**합니다:
```
(협업이벤트_001) -[참여자]-> (아이유)
(협업이벤트_001) -[참여자]-> (네이버)
(협업이벤트_001) -[참여자]-> (삼성전자)
(협업이벤트_001) -[시점]-> (2023)
```

#### 3) 시간에 따라 변하는 관계 — Temporal

사실이 시간에 따라 바뀌면 유효기간을 속성으로 붙입니다:
```
(아이유) -[소속 {valid_from: "2020", valid_to: "2022"}]-> (LOEN)
(아이유) -[소속 {valid_from: "2023"}]-> (EDAM)
```

# 지식그래프 심화

## 엔티티 정규화 (Entity Resolution)

"아이유", "IU", "이지은"은 같은 사람인데 텍스트마다 다르게 표기됩니다.
이를 **하나의 노드로 합치는 작업**이며, 합치지 않으면 노드가 무한 증식해 그래프 품질이 급격히 떨어집니다.
**지식그래프 프로젝트에서 품질을 좌우하는 가장 큰 요인**입니다.

실무에서는 **alias(별칭)** 속성으로 처리합니다:
```
노드: 이지은
alias: ["아이유", "IU", "Lee Ji-eun"]
```

## 서브그래프 (Subgraph) 추출

전체 그래프가 10만 개 노드짜리라도, 특정 질문/목적에 대해선 그중 일부(예: 20~200개)만 필요합니다.
**"전체 그래프에서 지금 필요한 부분만 잘라내는 것"** 이 서브그래프 추출입니다.

```
전체 그래프 (10만 노드)
        ↓ 특정 시작점(seed node) 기준으로 자르기
서브그래프 (예: 아이유 중심 2홉 이내 40개 노드)
```

### 추출 방법

| 방법          | 설명                                    |
| ----------- | ------------------------------------- |
| **홉 기반**    | 시작 노드에서 N홉 이내 모든 노드                   |
| **중요도 기반**  | PageRank/가중치 상위 K개만 (홉 수 무시하고 중요한 것만) |
| **커뮤니티 기반** | 커뮤니티 탐지로 찾아낸 그룹 자체를 서브그래프로 추출         |

보통 셋을 섞어서 씁니다:
```
"2홉 이내 + 그중에서도 중요도 상위 50개만"
"드라마 커뮤니티 그룹 전체를 잘라내서 검색에 활용"
```

> **커뮤니티 탐지 vs 홉 기반 차이**
> - 홉 기반: "아이유에서 2단계 떨어진 노드는?" → 특정 시작점 기준 탐색
> - 커뮤니티 기반: "전체 그래프에서 자연스럽게 묶인 그룹이 뭐야?" → 전체 분석 후 클러스터 발견

- **시각화**: 노드가 수천 개라 전체를 보여줄 수 없을 때 필수
- **검색**: 관련 없는 노드까지 가져오면 LLM 컨텍스트가 오염되므로 동일하게 중요

### 실제 처리 순서

**사전 처리 — 그래프 구축 시 1회 (오프라인)** - 스냅샷 형태
그래프가 계속 바뀌면 주기적 재계산(변경량 임계치)

```
① 커뮤니티 탐지 실행
   → 전체 그래프 분석해서 각 노드에 그룹 ID 부여
   → 노드: 아이유 { community_id: "드라마그룹" }

② PageRank 점수 계산
   → 각 노드에 중요도 점수 부여
   → 노드: 아이유 { pagerank: 0.87 }
```

커뮤니티 탐지랑 PageRank는 **미리 계산해서 노드 속성으로 저장**해둡니다.

**실시간 처리 — 질문이 들어올 때마다**

```
질문: "아이유 출연작 알려줘"

① seed 노드 탐색    → 임베딩 유사도로 "아이유" 노드 찾기
② 홉 기반 확장     → 아이유에서 2홉 이내 노드 수집 (수백 개 가능)
③ 중요도 필터링    → PageRank 상위 50개만 남기기
④ 커뮤니티 보완    → "드라마그룹" 커뮤니티의 핵심 노드 추가 (선택)
⑤ 최종 서브그래프  → LLM 컨텍스트로 전달
```

```
커뮤니티 탐지 / PageRank  →  사전 계산 후 노드 속성으로 저장 (오프라인)
홉 기반 확장             →  질문마다 실시간 실행
중요도 필터링            →  홉 확장 결과를 줄일 때 사용 (실시간)
```

## 중심 노드 (Seed Node) 탐색

서브그래프 추출의 시작점이 되는 노드를 찾는 과정입니다.
유스케이스에 따라 방식이 달라집니다.

### 검색 / RAG — 질문에서 찾기

```
① 엔티티 추출 (NER)
   질문 → LLM or spaCy → "아이유" 추출

② 그래프 노드 매핑
   exact match → alias 확인 → 임베딩 유사도 순으로 시도

③ 엔티티명 없을 때 (모호한 질문)
   질문 전체를 임베딩 → 노드 임베딩과 유사도 비교 → 가장 가까운 노드
```

### 동명이인 처리 (Disambiguation)

```
"김민수" 노드가 여러 개
→ 질문 문맥으로 타입 좁히기 (배우/가수 등)
→ 그래도 애매하면 PageRank 높은 쪽 (가장 유명한 쪽)
→ 최후엔 LLM 재판단
```

### Multi-seed — 중심 노드가 여러 개일 때

```
"아이유랑 삼성전자 협업한 적 있어?"
→ 각각 N홉 확장 후 합치기
→ 또는 두 노드 간 최단 경로 탐색 (shortestPath)
```

### 유스케이스별 차이

| 유스케이스 | 중심 노드 결정 방식 |
|----------|-----------------|
| **검색/RAG** | NER → 노드 매핑 → 임베딩 보완 |
| **추천** | 사용자가 방금 본 아이템 or 행동 이력 임베딩 |
| **시각화** | 사용자가 직접 클릭 (초기값은 PageRank 상위) |

## N-홉 (N-hop) 탐색

```
1홉: 바로 연결된 이웃 노드
2홉: 이웃의 이웃
```

"A와 B 사이에 몇 단계 관계가 있는가"를 묻는 것이 그래프의 핵심 능력입니다.

- **검색(RAG)**: 질문과 관련된 노드에서 1~2홉 확장해 컨텍스트를 풍부하게 만듦
- **추천**: "2홉 이내에서 자주 같이 나타나는 노드"를 추천 후보로 사용

## 중요도 점수 (PageRank)

연결이 많이 되는 노드일수록 중요하다는 개념으로, 구글 검색이 웹페이지에 쓰던 알고리즘을 노드에 적용한 것입니다.

| 활용 | 설명 |
|------|------|
| 시각화 | "중요한 노드만 보여주기" 필터 |
| 추천 | "인기 있는 관련 노드" 우선순위 |
| 검색 | 여러 후보 중 랭킹 결정 |

## 커뮤니티 탐지 (Community Detection)

서로 밀접하게 연결된 노드 묶음(클러스터)을 **자동으로 찾아내는 것**입니다.
"이 노드들은 하나의 주제/그룹에 속한다"를 자동으로 분류합니다.

- **추천**: 같은 커뮤니티 안의 다른 아이템 추천
- **시각화**: 색깔별로 그룹 구분

# 그래프 모델 종류

## RDF (Resource Description Framework)

**순수한 트리플만 저장**하는 방식입니다. W3C 표준이며 엣지에 속성을 직접 붙일 수 없습니다.
속성을 표현하려면 **reification(재귀 트리플화)** 으로 우회해야 합니다:

```
# 트리플 하나를 표현하는데 트리플 4개가 필요
_:stmt1 rdf:subject   아이유
_:stmt1 rdf:predicate 출연
_:stmt1 rdf:object    나의아저씨
_:stmt1 :기간         "2018"
```

- 쿼리 언어: **SPARQL**
- 대표 DB: Apache Jena, Virtuoso

## Property Graph

**노드와 엣지 둘 다에 속성을 자유롭게 붙이는** 방식입니다. 실무에서 압도적으로 많이 씁니다.

```
(아이유 {이름: "이지은", alias: ["IU"]})
    -[출연 {기간: "2018", 배역: "지안"}]->
(나의아저씨 {장르: "드라마"})
```

- 쿼리 언어: **Cypher**
- 대표 DB: **Neo4j**

## RDF vs Property Graph 비교

| | RDF | Property Graph |
|--|-----|----------------|
| **엣지 속성** | 불가 (reification 우회) | 가능 |
| **표준** | W3C 공식 표준 | 비표준 (Neo4j 주도) |
| **쿼리 언어** | SPARQL | Cypher |
| **장점** | 상호운용성, 추론 가능 | 직관적, 빠름, 실무 친화 |
| **단점** | 복잡하고 무거움 | DB마다 구현 다름 |

## pgvector 사용 시 한계

PostgreSQL + pgvector로도 그래프 구조를 만들 수 있지만, **N-홉 탐색 시 성능이 급격히 떨어집니다.**

```sql
-- 2홉 탐색만 해도 WITH RECURSIVE 필요
WITH RECURSIVE graph AS (
  SELECT to_id FROM edges WHERE from_id = 'A'
  UNION
  SELECT e.to_id FROM edges e JOIN graph g ON e.from_id = g.to_id
)
```

홉이 늘수록 JOIN이 기하급수적으로 증가합니다.

### Neo4j가 빠른 이유 — Index-free Adjacency

```
PostgreSQL: A → 전체 edges 테이블 스캔 → B 찾기 (테이블 클수록 느림)
Neo4j:      A → 포인터 따라가면 바로 B  (그래프 크기와 무관하게 O(1))
```

# RAG 종류 및 비교

## 나이브 RAG (Naive RAG / 벡터 RAG)

**가장 기본적인 방식. 문서를 청킹 후 임베딩 벡터로 저장하고 유사도 검색으로 문맥을 가져옵니다.**

```
[문서] → 청킹 → 임베딩 → 벡터DB 저장

[질문] → 임베딩 → 유사도 검색 → 관련 청크 추출 → LLM → 답변
```

### 한계
- 청크 단위로 잘려 **문서 간 관계 파악 불가**
- "A의 상관의 출신지는?" 같은 **다중 홉 질문에 취약**
- 유사한 단어가 없으면 **검색 자체가 실패**

## 그래프 RAG (Graph RAG)

**지식 그래프를 검색 소스로 활용. 관계를 따라가며 다중 홉 추론이 가능합니다.**

```
[문서] → 개체/관계 추출 → 지식 그래프 구성

[질문] → 그래프 탐색 → 연결된 노드/엣지 수집 → LLM → 답변
```

### 다중 홉 예시
```
질문: "이순신의 상관이 태어난 도시는?"

나이브 RAG: 관련 청크 없으면 답 못 함
그래프 RAG: [이순신] → [상관: 원균] → [출생지: 충주] → 답변 가능
```

### 한계
- 그래프 구축 비용이 높음
- 그래프에 없는 정보는 답 못 함
- 구축/관리 복잡도 높음

## 하이브리드 RAG (Hybrid RAG)

**벡터 검색(나이브 RAG) + 그래프 검색(그래프 RAG) 을 함께 사용하는 방식**

```
[질문]
   ↓
┌─────────────────────────────┐
│  벡터 검색    그래프 탐색   │
│  (유사 청크)  (관계 추론)   │
└──────────┬──────────┬───────┘
           ↓          ↓
        결과 통합 (Re-ranking)
           ↓
          LLM
           ↓
          답변
```

| 역할 | 담당 |
|------|------|
| 넓은 문맥, 유사 내용 검색 | 벡터 검색 |
| 개체 간 관계 추론 | 그래프 탐색 |
| 최종 답변 생성 | LLM |

## 세 가지 RAG 비교

| | 나이브 RAG | 그래프 RAG | 하이브리드 RAG |
|--|-----------|-----------|--------------|
| **검색 방식** | 벡터 유사도 | 그래프 탐색 | 둘 다 |
| **관계 추론** | 불가 | 가능 | 가능 |
| **구축 난이도** | 낮음 | 높음 | 높음 |
| **비용** | 낮음 | 높음 | 높음 |
| **적합한 질문** | 단순 유사 검색 | 다중 홉 추론 | 복합 질문 |

## 한 눈에 요약

```
노드            →  그래프 안의 개체 (점)
엣지            →  노드 간 관계 (선), 가중치 부여 가능
트리플          →  주어-관계-목적어, 지식그래프의 최소 단위
  └ 확장 형태   →  속성 부착 / N-ary 이벤트 노드 / Temporal 유효기간

온톨로지        →  타입·속성·관계 규칙 정의 (설계도)
  └ 엣지 속성   →  required면 필수, 아니면 생략 가능
지식 그래프     →  설계도대로 노드 생성 + 엣지 연결 (실제 데이터)
엔티티 정규화   →  다른 표기 → 하나의 노드로 합치기 (alias 처리)

N-홉 탐색       →  연결된 이웃을 몇 단계까지 따라갈지
서브그래프      →  홉/중요도/커뮤니티 기반으로 필요한 부분만 잘라내기
PageRank        →  연결 많은 노드 = 중요한 노드
커뮤니티 탐지   →  밀접한 노드 묶음 자동 분류

그래프 모델     →  RDF (순수 트리플, 엣지 속성 불가) vs Property Graph (속성 자유)
pgvector        →  그래프 구현 가능, 관계 많아질수록 JOIN 폭발로 느려짐
Neo4j           →  Index-free Adjacency로 홉이 늘어나도 O(1) 속도 유지

나이브 RAG      →  벡터 유사도로 청크 검색, 관계 추론 불가
그래프 RAG      →  지식 그래프 탐색, 관계 추론 가능
하이브리드 RAG  →  벡터 + 그래프 병행, 가장 강력하지만 구축 비용 높음
```
