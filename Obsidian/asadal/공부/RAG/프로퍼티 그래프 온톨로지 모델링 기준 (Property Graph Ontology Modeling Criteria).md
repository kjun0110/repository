## 개념

온톨로지(TBox/ABox) 설계에서 자주 헷갈리는 두 가지 결정 기준을 정리합니다. **① 어떤 규칙을 TBox(클래스 계층)에 넣고 어떤 걸 ABox(인스턴스 관계)에 넣을지**, **② 어떤 정보를 노드(Class+Instance)로 만들고 어떤 걸 속성(property)으로 둘지**.

---

# TBox vs ABox — 규칙을 어느 층위에 넣을 것인가

## 원칙

**타입 전체에 일관되게 성립하지 않는 관계는 TBox의 클래스-대-클래스 규칙(`SUBCLASS_OF` 등)으로 넣지 않는다. 실제 사실은 ABox의 인스턴스-대-인스턴스 관계로 넣는다.**

핵심은 "규칙을 아예 안 만든다"가 아니라 **"어느 층위에 넣느냐"**의 문제입니다. TBox는 "무엇이 가능한가(스키마/규칙)", ABox는 "실제로 무엇이 그러한가(사실/데이터)"를 나눠서 담당합니다.

## 판별 질문

> **"이 관계가 그 타입에 속하는 모든 인스턴스에 대해 항상 참인가?"**

- **Yes (항상 참)** → TBox에 넣어도 됨
  - 예: `직원 -[SUBCLASS_OF]-> 구성원` — 모든 직원 인스턴스는 예외 없이 "구성원" 카테고리에 속함
- **No (인스턴스마다 다름)** → ABox 관계로 내려야 함
  - 실패 예: `과 -[SUBCLASS_OF]-> 국` 같은 TBox 규칙은 성립 안 함 — 어떤 "과"는 국 밑에, 어떤 "과"는 부시장 바로 밑에 있어서 타입 수준의 고정 규칙이 될 수 없음
  - 정답: 조직 소속은 각 인스턴스의 개별 사실이므로 **ABox 관계(`PART_OF`)**로 표현
    ```
    (회계과) -[PART_OF]-> (경제정책국) -[PART_OF]-> (제1부시장) -[PART_OF]-> (시장)
    ```

## 오늘 실제 사례

suwon_ontology의 `SUBCLASS_OF`(TBox, 과/팀/동 등 16개 조직 타입 → "조직")는 의도적으로 **평평(flat)**합니다 — "관이 과보다 위다" 같은 타입 수준 규칙이 성립하지 않기 때문. 대신 실제 보고체계는 `PART_OF`(ABox)가 이미 다단계로 정확히 담당하고 있음. **TBox가 평평한 건 결함이 아니라, 애초에 이 정보가 TBox에 속할 정보가 아니었기 때문.**

# 노드(Node) vs 속성(Property) — 무엇을 타입화할 것인가

## 판별 기준 6가지

### 1. 정체성(Identity)이 있는가
"이게 다시 등장해도 같은 것으로 취급돼야 하나?"
- 노드감: "영통구"는 어느 조직에서 참조되든 항상 같은 영통구를 가리켜야 함
- 속성감: "031-5191-2170" 같은 전화번호는 그 자체로 재참조될 일 없음

### 2. 다른 개체들과 관계를 맺어야 하는가
"이걸 기준으로 뭔가를 탐색해야 하나?"
- 노드감: "영통구에 속한 부서 전부"처럼 관계(`PART_OF`)를 타고 탐색해야 함
- 속성감: "직위가 주무관인 사람"은 `WHERE e.position = '주무관'` 필터 한 줄로 충분

### 3. 여러 개체가 그 값을 공유하는가 (N:1, N:N)
"이 값이 여러 곳에서 재사용되나?"
- 노드감: "영통구"는 수십 개 부서가 공유. 나중에 지역 자체 정보(인구, 면적)를 고치면 참조하는 모든 부서에 한 번에 반영돼야 함 → 정규화 관점에서 노드
- 속성감: 전화번호는 사람 한 명에게만 종속, 공유될 일 없음

### 4. 그 개념 자체가 추가 속성/정보를 가져야 하는가
- 노드감: "직위"에 급수, 결재권한, 연봉 밴드 같은 부가 정보를 나중에 붙여야 한다면 → 노드
- 속성감: 지금 "주무관"이라는 값 자체엔 더 기록할 정보가 없음

### 5. 계층/분류 체계가 필요한가
- 노드감: "팀장 > 부팀장 > 주무관" 같은 순서/계급 체계를 비교·정렬해야 한다면 → 노드 + 관계(`RANKS_ABOVE` 등)
- 속성감: 지금은 "주무관이냐 아니냐" 이분법 판단만 필요 → 문자열 비교로 충분

### 6. 독립적인 생명주기(lifecycle)를 가지는가
"이게 그 자체로 생성/삭제/개편되나?"
- 노드감: "과"는 조직개편으로 신설·폐지·이름 변경되는 등 그 자체가 하나의 사건 단위
- 속성감: 전화번호가 바뀌는 건 그 사람의 한 속성이 바뀌는 것일 뿐, "전화번호"라는 개체가 별도로 생성/소멸하는 게 아님

## 비교표

| 기준 | 노드로 만들 신호 | 속성으로 충분한 신호 |
|---|---|---|
| 정체성 | 다시 등장해도 같은 것이어야 함 | 그 자체로 재참조될 일 없음 |
| 관계/탐색 | "이걸 기준으로 찾아줘" 질의 필요 | 단순 필터(`WHERE`)로 충분 |
| 공유 여부 | 여러 개체가 같은 값을 참조·공유 | 개체 하나에만 종속된 값 |
| 추가 속성 | 그 개념 자체에 부가 정보 필요 | 부가 정보 없음, 값 자체가 끝 |
| 계층/분류 | 상위-하위 비교/정렬 필요 | 단순 나열이면 충분 |
| 생명주기 | 독립적으로 생성/폐지/개편됨 | 상위 개체의 한 속성일 뿐 |

## 실제 적용 예시

- **지역(구/동)**: 6개 기준 대부분 해당 → 노드가 맞음 (실제로 `:구`, `:동` Instance로 존재)
- **직위(시장/과장/팀장/주무관)**: 6개 기준 어디에도 안 걸림 → 속성으로 충분 (지금 `e.position` 문자열 속성)
  - 단, 나중에 직급 순서/권한 범위를 비교·추론해야 하는 요구사항이 생기면 그때 기준 5번(계층/분류)에 걸리기 시작 → **그때가 노드로 승격시킬 타이밍**. 모든 걸 미리 노드로 만드는 게 "더 온톨로지답다"는 뜻이 아니라, 필요해지는 시점에 승격하는 게 맞음.

## 한 눈에 요약

```
TBox vs ABox — 규칙을 어느 층위에 넣을 것인가
├── 판별 질문: "그 타입의 모든 인스턴스에 항상 참인가?"
├── Yes → TBox 클래스 규칙(SUBCLASS_OF)으로 OK
└── No(인스턴스마다 다름) → ABox 인스턴스 관계(PART_OF)로 내림
    └── "규칙을 안 만든다"가 아니라 "어느 층위냐"의 문제

노드 vs 속성 — 무엇을 타입화할 것인가 (6가지 기준, 하나라도 해당하면 노드)
├── 정체성          → 다시 등장해도 같은 것이어야 하나?
├── 관계/탐색        → 이걸 기준으로 탐색해야 하나?
├── 공유 여부        → 여러 개체가 같은 값을 참조하나?
├── 추가 속성        → 그 개념 자체에 부가 정보가 필요한가?
├── 계층/분류        → 상위-하위 비교/정렬이 필요한가?
└── 생명주기         → 독립적으로 생성/폐지/개편되나?

예시: 지역(구/동) → 노드 / 직위(주무관 등) → 속성 (필요해지면 나중에 승격)
```
