## 개념

- **호출처 세기** — 선언이 살아 있는지 보는 방법. 내용을 읽으면 "잘 들어갔다"로 보이고, **누가 읽는지**를 세야 죽은 절이 보인다
- **죽은 선언** — 파일에 있는데 아무도 안 읽는 절·필드·검사기. 고쳐도 아무 일이 안 일어나는데 고친 사람은 바꿨다고 믿는다
- **definition / observed** — `required` 두 종류. "없으면 그 라벨이 아니다"와 "지금 다 차 있을 뿐"
- **선행조건(needs)** — 단계가 돌기 전에 그래프에 있어야 하는 라벨·관계. 순서 제약을 주석이 아니라 데이터로
- **domain union** — 한 관계가 여러 라벨에서 나갈 수 있다(`from: [Article, CivilService]`). RDFS 의 `rdfs:domain` 유니온
- **방아쇠 대기** — 판단은 끝났고 조건이 오면 즉시 실행하는 상태. "미결"과 다르다

## 1. Gruber 5원칙으로 온톨로지를 대조했다

##### 문제

선언을 계속 늘리고 있는데 기준이 없었다. 무엇이 온톨로지에 있어야 하고 무엇이 코드에 남아야 하는지가 그때그때 판단이었다.

##### 방법 — 내용이 아니라 호출처를 셌다

다섯 기준(명료성·정합성·확장성·최소 부호화 편향·최소 존재론적 개입)으로 훑되, 각 절이 **실제로 코드에서 읽히는지**를 셌다. 09-07 에는 선언 내용만 읽고 "잘 들어갔다"고 판정했었다.

##### 결과 — 죽은 절 둘이 바로 나왔다

```
schema.classes()        호출처 0    요건 판정은 validate/01 에 Cypher 로 두 벌
schema.entity_labels()  호출처 0    :Entity 부착은 embedding/01~04 가 각자 한다
```

`classes` 는 `Procedure: { requires: [HANDLED_BY], exempt_if: external_org }` 를 선언해 놓고 **아무도 안 읽는다.** 09-07 에 같은 부류를 셋 고쳤는데(제약·키 두 벌 · `UNIT_LEVELS` 17개 두 벌 · `_SCHED_LABEL` 어휘 키 중복) 이것만 남아 있었다.

`entity_labels()` 는 다르다 — 접근자는 죽었지만 `labels[].entity` 절은 `validate/06` 이 읽는다. **선언이 구동은 안 하지만 검증은 되는** 중간 상태다.

## 2. `classes` 절을 살렸다 — 선언이 거짓말하는 유일한 자리였다

##### 택한 안 — 살린다 (지우는 것도 정당했다)

선택지는 "살린다 vs 그냥 둔다"가 아니라 **"살린다 vs 지운다"** 였다. 살리기로 한 이유 둘: `classes` 는 온톨로지의 핵심 개념(클래스 요건)이라 지우면 그 층이 비고, 곧 `range:` 가 생기면 소비자가 2가 된다.

##### 구현 — 표현식 파서를 만들지 않았다

`if: "content_type == 'procedure'"` 를 **`if: { content_type: procedure }`** 로 바꿨다. 표현식 파서를 새로 만들면 검증할 방법이 없다. `inference.via[].where` 가 이미 `{속성: 값}` 모양이고 `infer.py:_hop()` 이 그것을 읽는 코드를 갖고 있어서, **만드는 것이 아니라 쓰는 것**이 됐다.

**대상 라벨은 선언에 안 적었다.** `if` 의 속성이 `properties` 의 어느 라벨에 있는지로 정해진다(`content_type` → CivilService). 적으면 이미 있는 사실이 두 벌이 되고, 그것이 이 절을 죽게 만든 바로 그 병이다.

##### 검증 — 선언을 바꾸면 숫자가 달라지나

```
선언 그대로              NO_DEPT 7건
Reference.requires 제거   NO_DEPT 0건
```

**그전에는 무엇을 고쳐도 7이었다.**

##### 갈라 놓자 안 보이던 질문이 보였다

`NO_DEPT` 위반 7건이 **전부 reference** 였고 procedure 는 0건이었다. 규칙이 코드에 한 덩어리로 있을 때는 둘을 나누는 조건이 규칙 안에 없어 물어볼 수조차 없었다.

7건을 열어 보니 전부 `dept_raw` 가 NULL — 원천에 담당부서 칸이 아예 없는 링크 모음·계획서 안내였다(관련사이트 · 구역별홈페이지링크 · 현수막 · 2020/2030도시.주거환경정비기본계획). **`Reference` 에서 `requires` 를 뺐다.** 원천에 칸이 없는 것을 error 로 부르면 진짜 새 위반이 그 안에 묻힌다.

##### 결과

error 등급 민원 14 → 7. `schema.py` 가 로드 시점에 요건을 검산한다 — `requires` 가 없는 관계를 가리키나 · 그 관계가 그 라벨에서 나가나 · `exempt_if` 가 실재 속성인가 · `if` 의 값이 닫힌 어휘 안인가.

## 3. `slots.default` 도 죽은 필드였다 — 세는 단위가 셋이다

`slots` 에 `default` 가 둘 있고(`Article.article_type` · `CivilService.page_kind`) **둘 다 읽는 코드가 0곳**이었다. 값은 `nodes/16:166` 과 `schema.page_kind()` 에 `'unknown'` 으로 박혀 있었다.

**아침에 이걸 못 본 이유가 중요하다.** `schema.slots()` 는 `validate/06` 이 부르고 있어서 **산 절로 보였다.** 죽어 있던 것은 그 안의 필드 하나였다.

```
세는 단위 셋   절 · 필드 · 접근자
```

`schema.slot_default()` 를 만들어 두 자리를 배선했고, 로드 시점에 **기본값이 그 슬롯의 어휘 안인지**도 본다.

검증은 반쪽만 됐다 — `page_kind()` 는 default 를 '목록'으로 바꾸니 반환값이 바뀌는 것을 확인했지만, `nodes/16` 쪽은 `default_type` 없는 Board 가 0개라 분기가 안 돈다. 주석에 못 박아 뒀다.

## 4. `required` 55개를 definition / observed 로 갈랐다

##### 문제

`required` 를 붙인 기준이 **"2026-09-07 기준 그 라벨의 모든 노드가 갖고 있음"** 이라는 실측이었다. 관측을 정의로 승격시킨 것이고, `validate/06` 은 그것을 정의로 취급해 FAIL 한다. 조회수를 안 싣는 게시판 하나가 열리면 **게시글 하나 때문에 적재 전체가 멈춘다.**

##### 근거를 굳힌 실측 — `required` 는 이미 아무것도 보장하지 못하고 있었다

`IS NULL` 만 보므로 빈 문자열·빈 리스트·0 은 통과한다.

```
Board.path             20 / 20     전부 빈 문자열
OrgUnit.aliases       896 / 940    적재기가 항상 [] 를 넣는다 -- 항진명제다
CivilService.aliases  643 / 644    같음
Employee.phone        421 / 5,136  빈 문자열
Article.views         728 / 6,285  0
```

##### 결과 — 18개가 아니라 23개였다

앞 목록의 `Domain.path` 는 **Domain 의 라벨 키**라 빼면 안 됐다(유일성 제약이 거기 걸려 있다). 대신 여섯을 더 찾았다: `CivilService.domain` · `Employee.assigned_task` · `phone` · `position` · `Place.operator` · `place_type`. 최종 **definition 32 · observed 23.**

`validate/06` 이 definition 위반은 FAIL, observed 위반은 WARN 으로 다룬다. `schema.py` 가 로드 시점에 (a) `required` 값이 그 둘 중 하나인지 (b) **라벨 키는 definition 인지** 를 본다.

##### 검증 — 양쪽 분기를 다 밟았다

지금은 NULL 인 속성이 하나도 없어 새 코드가 안 걸린다. `Employee.name`(5,130명 NULL)을 잠깐 required 로 선언해 확인했다.

```
observed    → [주의] … 빈 노드 5130개    통과 (exit 0)
definition  → [위반] … 빈 노드 5130개    중단 (exit 1)
```

**미해결 28번(`observed` 구분 없음)이 이것으로 닫혔다.** 그리고 이 작업은 같은 날 세 번 값을 했다 — `Attachment.size_text` · `Article.no` · 서브도메인 적재가 전부 이것 덕에 FAIL 이 아니라 WARN 이 됐다.

## 5. 관계에 뜻과 치역을 붙였다

##### 문제

관계 18종에 `from`/`to`/`cardinality` 는 있는데 **뜻이 없었다.** 라벨 14종에는 전부 `ko`+`desc` 가 있어 대칭이 안 맞았다.

실제로 못 읽는 자리가 있었다 — `LISTED_IN { Place → CivilService }` 가 "그 장소가 이 민원 페이지 표에 실려 있다"인지 "그 민원을 그 장소에서 처리한다"인지 가리지 못한다(답은 전자, 알려면 `nodes/11` 을 읽어야 했다).

##### `range:` — `to:` 가 못 하는 말

`to:` 는 "어느 라벨인가"까지만 말한다. 실제 규칙이 더 좁으면 나머지가 코드로 흐른다.

```yaml
HANDLED_BY:
  to: OrgUnit
  range: { unit_level: 실무조직 }     # 국·실은 결재 라인이지 창구가 아니다
```

`validate/01` 의 `DEPT_NOT_BODY` 가 이제 `infer.build_range()` 로 선언에서 나온다.

##### 검증

```
range 를 총괄기관 으로 뒤집음   DEPT_NOT_BODY  0 → 631건
되돌림                       631 → 0
오타 unit_leve               [중단] properties.OrgUnit 에 없다   로드 시점에 막힘
```

##### 정정

아침에 "`range:` 가 32번의 3건 중 2건을 지운다"고 했는데 **1건이다.** `PART_OF_DIRECTION`("총괄기관은 실무조직 밑에 안 온다")은 `range` 로 못 적는다 — 한쪽 끝의 필터가 아니라 **두 끝의 부류 사이 관계**다. 소비자 하나뿐인 문법을 새로 만들지 않고 `check_org_tree` 에 남겼다.

## 6. 답변을 읽다 진짜 오답 하나 (36번)

##### 방법

gold 48문항 중 답변 축이 없는 42개에서 다섯을 골라 실제로 돌리고 눈으로 읽었다. 검증 가능한 사실(금액·기한·벌칙)이 답에 들어가는 것들로.

##### 찾은 것

`난임부부 지원금액` 답변이 **"장안구보건소 소관 · 장안구보건소에 문의하시기 바랍니다"** 로 한 곳을 찍는다. **권선구 시민에게는 틀린 안내다.**

```
난임부부 시술비 지원  HANDLED_BY → 건강관리과 x4 (장안·권선·팔달·영통 보건소)
                     IN_CHARGE_BUREAU → 장안구보건소 하나
건강관리과            peer_count = 4   ← 신호는 이미 노드에 있었다
```

원인 둘이 겹쳤다. `IN_CHARGE_BUREAU` 의 `tie_break: org_id` 가 가장 작은 id(장안구)를 고르고, `synthesize.py:184` 의 `peer_count` 가드가 **OrgUnit 후보에만** 걸려 CivilService 의 담당부서 줄에는 안 걸렸다.

**이것은 거주지 관할 문제가 절반만 풀려 있었다는 뜻이다.** `OrgUnit.peer_count` 로 해결했다고 적어 뒀는데, 푼 것은 OrgUnit 경로 하나뿐이었다. 축이 없어서 여태 안 보였다.

##### 고침과 전후

`context.py` 가 `dept_peer_count`/`dept_peer_scope` 를 같이 내고 `synthesize` 가 **소관과 주소를 감춘다**. 소관을 감추는 것이 요점이다 — 그 값이 특정 구를 찍는 값이다.

```
전  담당 부서: 건강관리과 (장안구보건소 소관) / 전화 031-5191-0181
    ... 자세한 사항은 장안구보건소에 문의하시기 바랍니다
후  담당 부서: 건강관리과 / 상위 소속: 보건소
    연락처: 장안구 0181, 권선구 0381, 팔달구 0580, 영통구 0778
```

##### 축을 두 번 잡았다 — 처방을 축에 적으면 다른 정답을 막는다

처음에 `answer_must: ["거주지|관할|4개 구|구보건소 각각"]` 로 뒀는데, 고친 뒤 답변은 그 문구 대신 **네 곳 연락처를 전부** 냈다. 시민에게는 그쪽이 더 낫다. 축이 재려던 것은 "거주지 관할이라고 말했나"가 아니라 **"한 구만 찍지 않았나"** 였다.

##### 결과

답변 적중 **7/7**(기존 6 유지 + 새 축 통과). 후보 지표는 기준선과 동일(1위 17/17 · 정밀도 83/227 · 첨부 4/4 · 장소 3/3). 같은 모양의 민원이 **18건** 더 있다.

덤으로 `validate/04` 의 `report()` 에 **답변 요약 줄이 없던 것**을 찾아 넣었다. 1위·첨부·장소는 있는데 답변만 빠져서 24번의 진척이 매 실행에 안 보였다.

## 7. 민원 본문 파일 402간선 (14번)

##### 틀린 진단

"원본 href 가 `/webcontent/ckeditor/…` 이고 페이지 JS 가 실행 중에 `ND_fileDownload.do` 로 바꾼다"

**실측: JS 변환이 없다.** ckeditor 경로가 최종 URL 이고 HEAD 로 찔러 셋 다 `200 OK` + `Content-Length`. `ND_fileDownload.do?id=` 는 **647개 파일에 정확히 1번씩** 있는 템플릿 stub 이라 그걸 찾으면 0건이 나오는 것이 맞다. 수집기가 게시판 첨부 패턴을 민원 페이지에 적용하고 있었을 뿐이다.

##### 축을 하나도 안 만들었다

구멍이 있다는 것은 그래프가 직접 답했다.

```
Attachment 7,647개  전부 게시판(ND_fileDownload) 출신
ckeditor            0개
```

gold 축은 "검색이 그것을 찾아 주는가"를 재는 도구지 데이터가 있는지 없는지를 재는 도구가 아니다.

##### 관계 이름 — `HAS_FILE` 을 확장했다

새 이름을 만들지 않고 `from: [Article, CivilService]` 로 넓혔다. 게시글 첨부와 민원 본문 파일은 **같은 관계**다 — 그 노드가 그 파일을 내놓는다는 뜻이고, 첨부 영역이냐 본문이냐는 파일의 성질이 아니라 위치다. 새 이름을 만들면 소비자를 안 고쳤을 때 아무도 안 읽는 관계가 하나 더 생긴다. RDFS 의 `rdfs:domain` 유니온과 같은 개념이고 `schema.sides()` 가 읽는다.

##### 이름 규칙은 세 번 고쳤다 — 오탐 검증이 절반이었다

서버가 `Content-Disposition` 을 안 주고 URL 은 UUID 다. 앵커 텍스트는 절반 이상이 이름이 아니다('다운로드' 106 · 'pdf 파일다운로드' 39 · 빈 문자열 14).

```
1차  'x"> 법, 시행령…'      300자를 자를 때 태그 한가운데서 잘려 속성값이 남았다
2차  '…계획 다운로드'         가장자리 일반어가 남았다
3차  '…신청서 다운로드 건설기계등록증 재교부신청서'
                           앞 링크의 이름이 딸려 왔다. '다운로드'를 구분자로 쓰되
                           **마지막 비지 않은 조각**을 취해 한 규칙으로 갈랐다
```

##### 결과

본문 파일 413건 / 민원 83건(앞문맥 247 · 앵커 166), 이름 못 정해 건너뜀 10건, 적재 **402간선**. 외부 요청 0회 — `scraping/01:1049` 가 매 수집마다 저장하는 `html/<civil_id>.html` 만 읽는다.

**소비자도 같이 고쳤다.** `context.py` 의 첨부 질의 세 갈래가 전부 조직·게시글을 경유해서 민원 본문 파일에 못 닿았다. 네 번째 갈래를 넣고 두 질의의 RETURN 이 출처가 게시글이 아닐 수도 있게 고쳤다. 동작 확인: `과태료 의견진술서 양식 받고 싶어` → "의견진술서 예시서식 (hwp)" + 정확한 URL. 첨부 적중 4/4 그대로.

## 10. 파이프라인 순서를 주석에서 선언으로

##### 물음 — 적재가 35단계나 되나

재보니 **개수는 문제가 아니었다.**

```
코드 4,068줄 / 35단계 = 평균 116줄     가장 작은 것 38줄 · 큰 것 298줄
병합 후보 셋(07+08 · 02+rel02 · 13+14) → 32. 별 차이 없고
합치면 리포트 해상도와 실패 지점의 명확성을 잃는다
```

단계 수는 온톨로지 크기를 따라간다 — **라벨 15 + 관계 18 = 33, 단계 35.** 거의 1:1이다.

진짜 낭비는 원천 재파싱이다(`civil_service.json` 2.8MB × 11단계 등, 매 실행 74MB). 전체 20분 중 몇 초라 **지금은 안 아프다.**

##### 대신 고친 것

`main.py` 에 "CivilService 가 있어야 …" 같은 순서 제약이 **열세 곳 주석**으로만 있었다. 입력 가드 9곳은 **파일 존재**만 보고 **그래프 선행조건을 보는 단계는 0개**였다. 순서를 바꾸면 멈추지 않고 **조용히 덜 적재된다** — `nodes/17` 을 `nodes/04` 앞에 두면 `MATCH (c:CivilService)` 가 0건 매치해서 본문 파일 0개를 넣고 통과한다.

```python
("nodes/17_body_files.py",       ["CivilService"]),
("nodes/09_org_address.py",      ["PART_OF"]),
("relationships/05_inferred.py", ["HANDLED_BY", "REQUIRES", "PART_OF"]),
```

`run_step` 이 실행 **전에** 그래프에서 센다(대문자면 관계, 아니면 라벨). STEPS 35개 중 23개 · CHECK 7개 중 4개. 음성 테스트: 없는 라벨·없는 관계를 요구하니 둘 다 `[중단] … 그래프에 0건이다 — 앞 단계가 안 돌았거나 순서가 틀렸다`.

**이것이 곧 의존 그래프라 29번(부분 실행 불가)의 기초가 된다.**

## 재사용 가능한 판단

- **선언은 내용이 아니라 호출처를 세야 죽은 절이 보인다.** 09-07 에 내용만 읽고 "잘 들어갔다"고 판정했다가 죽은 절 넷을 못 봤다
- **절이 살아 있어도 필드는 죽어 있을 수 있다.** 세는 단위가 셋이다 — 절 · 필드 · 접근자
- **정적 호출처 세기는 별칭에 속는다.** `import X as Y` 하나에 내 측정이 틀렸다
- **갈라 놓아야 물어볼 수 있다.** `required` 를 definition/observed 로, 23번을 23-a/23-b 로, 단계 검사를 입력가드/불변식으로. 묶음의 이름이 판단을 가둔다
- **처방을 검증 축에 적으면 다른 정답을 막는다.** 축은 결함을 재야 한다
- **가짜 경보를 남기면 진짜가 묻힌다.** `PROC_EMPTY` 7건 · `DATE` 1,917건이 전부 정상이었다
- **0이 나오면 도구부터 의심한다.** "JS 라 못 읽는다"가 사실은 파일 쓰기 실패였다
- **크기가 아니라 소비자를 센다.** 서식 507건은 그래프에서 가장 큰 단일 구멍인데 첨부 축이 이미 4/4다
- **결론을 반영할 자리가 있는지부터 센다.** 13번은 측정이 맞았는데 바꿀 기본값이 없었다
- **기각된 항목이 새 데이터로 되살아날 수 있다.** 12번은 www 에 대해서는 맞고 서브도메인에 대해서는 틀렸다
- **선언의 키를 바꾸는 것은 이름 바꾸기가 아니라 새 노드를 만드는 것이다**
- **같은 관계면 같은 이름을 쓴다.** 새 이름은 소비자를 안 고쳤을 때 죽은 관계를 하나 더 만든다
