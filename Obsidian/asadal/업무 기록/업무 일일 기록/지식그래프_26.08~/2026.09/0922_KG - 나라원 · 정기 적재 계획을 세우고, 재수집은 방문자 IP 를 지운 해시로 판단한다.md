## 개념

- **U · D 동기화** — 주기적으로 원천(사이트 · 명단)을 다시 읽어 바뀐 것은 갱신(U), 필요 없어진 것은 삭제(D)하는 적재. 브랜치 `feat-load_auto_sync`
- **러너 `aisearch`** — 운영 서버에 설치된 Gitea Actions 실행기. Gitea 가 시키는 워크플로를 그 서버에서 실행한다. 배포가 이미 이걸로 돈다
- **정규화 해시** — 받을 때마다 바뀌는 조각(방문자 IP, 캐시 번호 `?v=`)을 지운 뒤 낸 해시. "같은 내용인가"의 기준. 원문 파일은 받은 그대로 저장한다
- **새로 고침 모드** — 수집기 `collector.py refresh`. 지금까지 받은 주소를 전부 다시 받는다
- **`run.json`** — 수집 회차 하나의 요약(시작 · 끝 · 받을 목록 · 받은 수 · 실패 · 완주 여부). 끝까지 돌았을 때만 생긴다
- **`NARA1_DATA_DIR`** — 서버가 수집 · 업로드 파일을 쓰는 저장소 밖 데이터 폴더

## 요약

9/18 0.6.0 을 main 에 병합 · 릴리즈한 뒤 main 을 받아 새 브랜치 `feat-load_auto_sync` 를 땄다. **사람 손 없이 주기적으로 수집 → 갱신 · 삭제 → 확인하는 계획**을 세웠다. 실행은 Gitea Actions 예약(러너 `aisearch`)이고, Redis · 워커는 쓰지 않는다. 스케줄은 맨 마지막에 붙인다. 계획을 한 번 검토해 **파일이 쌓이는 구멍**을 찾았다. 수집본을 저장소 밖 서버 폴더에 내용 해시로 한 번만 저장하고, 완주 4회차만 남기도록 고쳤다.

1단계(수집기 무인화, D60)를 구현했다. 먼저 잰 바이트 안정성에서 **9/2 저장본과 오늘 받은 페이지가 20개 중 0개 같았다.** 채팅 위젯이 방문자 IP 를, 일부 페이지가 캐시 번호를 HTML 에 넣기 때문이다. 해시를 낼 때 두 조각을 지우게 했다. 기존 수집기는 새 페이지 찾기용이라 **이미 받은 주소를 다시 받는 기능이 없어** 새로 고침 모드를 더했다. 실제 사이트로 돌린 결과 359개 완주, 9/2 대비 358페이지 중 357 같음, **그래프 도메인 노드 변화 0** 이다. 운영 DB 는 건드리지 않았다.

## 1. 정기 적재 계획 (U · D)

##### 지금 있는 것과 없는 것

| | 상태 |
|---|---|
| 증분 갱신 · 임베딩 증분 · `unchanged` | 있음 |
| 이전 상태를 DB 기록으로 이어 적재 | 있음(D55) |
| 사라짐 표시(`removed` · `left`) | 있음, 지우지는 않음 |
| 수집 무인화 · 실행 기록 · 노드 삭제 · 서버 실행 경로 · 예약 | **없음** |

정기 적재는 입력이 바뀌어야 의미가 있어 **수집 → 적재 → 확인이 한 묶음**이다.

##### 실행 수단 — Gitea Actions 예약

| 안 | 판단 |
|---|---|
| **Gitea Actions `schedule`** | **채택.** 러너가 이미 있고, 실행 기록 · 로그가 웹에 남고, `workflow_dispatch` 로 버튼 실행도 된다. Gitea 1.22.0 이라 지원(1.21~)을 확인했다 |
| 서버 cron · systemd timer | 기각. 서버에 들어갈 경로가 없다 |
| 상주 컨테이너 + 스케줄러 | 기각. 과함 |
| Celery + Redis 워커 | 기각. 요청이 쌓이는 비동기 작업용이다. 하루 한 번 순서대로 도는 배치에는 큐가 할 일이 없다. Chatty 의 Celery 에 얹으면 Chatty 배포에 묶인다 |

적재는 API 앱 밖(러너)에서 돌아 API 재시작과 무관하다. DB 쓰기는 트랜잭션 하나라 중간에 죽어도 어중간한 상태로 남지 않는다.

##### "마지막 성공 시각" — 매일 확인, 7일 넘으면 실행
사용자 제안대로 **매일 확인하고 마지막 성공이 7일 넘었으면 돌린다.** 러너가 며칠 꺼져도 켜지는 날 따라잡는다. 다만 `ReleaseHead` 로는 판단할 수 없다. 시각이 없고, `unchanged` 면 갱신되지 않아 매일 다시 돈다. 그래서 `ReleaseHead` 에 **릴리즈 밖 칸** `last_success_at` · `last_outcome` 을 둔다(`unchanged` 여도 갱신, 실패 · 멈춤이면 갱신 안 함). 새 라벨(`LoadStatus`)은 적재기가 "릴리즈에 없는 노드"로 보고 멈춰서 기각했다.

##### 삭제 — 명시된 것만
릴리즈 매니페스트에 `deletions: [{label, key, reason}]` 을 두고 적재기는 그것만 지운다. 예상 밖 노드는 지금처럼 멈춘다. 이번 범위는 **아무 노드도 가리키지 않는 고아 `Capture`** 만이다. 사라진 사이트 노드 · 퇴사자 삭제는 보관 기간이 정해진 뒤로 미뤘다.

##### 서버 실행 — 이미지에 굽지 않고 체크아웃을 연결

| | A. 이미지에 복사 | B. 체크아웃 연결 |
|---|---|---|
| 준비 | `Dockerfile` 수정 · 다시 빌드 | compose 설정만 |
| 코드 · 데이터가 바뀌면 | 다시 빌드 | 그대로 반영 |
| 장점 | 버전 고정 · 서버 폴더 상태와 무관 | 워크플로가 정해진 커밋을 받으면 버전 고정도 됨 |

**B 채택.** 처음에는 확인 없이 A 를 권했다. 적재가 쓰는 라이브러리(표준 + `neo4j` + `dotenv`)가 API 이미지에 이미 있고, 데이터는 매번 바뀐다는 걸 확인하고 바꿨다.

##### 검토에서 고친 것 — 파일이 쌓이는 구멍
- **변경 감지를 "직전 회차 파일 그대로"로 적으면 옛 회차 폴더를 영영 못 지운다.** → 원문을 `blobs/<내용 해시>` 에 한 번만 저장하고, 회차 폴더(`runs/<날짜>/`)는 목록과 `run.json` 만 갖는다
- **수집본을 깃에 두면 서버가 매주 커밋해야 하고 저장소가 계속 커진다.** → 저장소 밖 서버 폴더. 첫 수집본(41MB)은 기준점으로 깃에 둔다. 적재기는 두 곳을 함께 읽는다
- **`carry_provenance()` 가 직전 `Capture` 를 전부 옮겨 와서 고아 삭제와 부딪힌다.** → 가리키는 것만 옮긴다
- 러너 체크아웃은 배포 폴더와 달라 compose 프로젝트 · `.env` 가 어긋날 수 있다. → 배포 폴더의 compose · `.env` 를 명시한다
- `--collect` 를 적재기에 넣지 않는다. 워크플로에서 단계를 나눠야 어디서 실패했는지 로그가 갈린다

##### 보관 규칙

| 대상 | 남김 |
|---|---|
| 회차 폴더 | 완주 **4회차**(주 1회면 약 한 달). 8회차에서 사용자가 줄였다 |
| 끊긴 회차 | 7일 |
| 원문 파일 | 남은 회차나 그래프 `Capture` 가 가리키는 것 |
| 첫 수집본 | 계속 |

최악(매번 전 페이지가 바뀜)이어도 4 × 약 41MB 에서 멈춘다. 오래 남는 건 사라진 노드 · 퇴사자의 근거 원문뿐이다. 퇴사자의 명단 파일은 폴더째 지워도 적재는 안 깨진다(옮겨 온 `Capture` 는 직전 릴리즈 기록으로 검증). 다만 개인정보는 DB 노드에 남아 파일만 지워서는 해결되지 않는다. 연락처 비우기 규칙은 인사 쪽 보관 기간이 정해진 뒤로 미뤘다.

##### 단계

| 단계 | 내용 | 주요 파일 |
|---|---|---|
| 0 | 결정 — 데이터 폴더 · 보관 규칙 | 확정 |

| 4 | 서버에서 버튼 실행 — 드라이런 → `--write` → 수집 · 적재 · 확인 · 정리 | `docker-compose.yml` · `scheduled-load.yml`(신규, `workflow_dispatch` 만) |

## 2. 1단계 — 바이트 안정성 측정

```
짧은 간격으로 두 번 받기     전부 같음
9/2 저장본과 비교           20개 중 0개 같음
그중 방문자 IP 줄만 다름     17개
```

- 채팅 위젯이 접속한 사람의 IP 를 `mb_id` · `user_id` · `user_name` 에 넣는다. 사무실 외부 IP 가 바뀌면 전 페이지가 달라진다. 서버에서 수집해도 같다
- 일부 페이지는 `style.css?v=<요청 시각>` 캐시 번호를 붙인다

그대로 두면 **사이트가 그대로여도 매 수집마다 전 페이지가 바뀐 것**이 된다. 원문이 매번 새로 저장되고, `Capture` 97개가 매번 새로 생기고, `unchanged` 가 영영 안 나온다.

##### 택한 안
해시를 낼 때 두 조각의 **값만 비우고 이름표는 남긴다**(`ingestion/parsers/volatile.py`). HTML 같은 텍스트에만 적용한다(엑셀은 압축 파일이라 제외). 수집기와 적재기가 같은 규칙을 써야 해서 한 파일에 둔다. 매니페스트에는 `sha256`(정규화 = 파일 이름)과 `raw_sha256`(받은 바이트)을 함께 적는다.

## 3. 1단계 — 새로 고침 수집과 적재 읽기 (D60)

##### 발견 — 수집기가 재수집을 못 했다
기존 수집기는 한 번에 최대 100개, 옛 회차를 참고로 주면 **거기 있는 주소는 건너뛰고 새 주소만** 받는다. 9/2 수집이 `full` + `delta-01·02·03` 으로 나뉜 이유다. 예약으로 돌려도 기존 페이지는 다시 받지 않는다.

##### 구현

| 파일 | 변경 |
|---|---|
| `ingestion/parsers/volatile.py`(신규) | 정규화 규칙(IP · `?v=`) |
| `collector.py` | `refresh` 명령 — 알던 주소 전부 + 새로 보이는 링크, `robots.txt` 먼저, 실패 시 1회 재시도. 원문은 `blobs/<정규화 해시>` 에 없을 때만 임시 이름으로 쓴 뒤 이름 변경. 끝까지 돌면 `run.json`, 못 받은 주소가 있거나 개수 제한(1000)에 걸리면 `exit 1` |
| `ingestion/parsers/snapshots.py` | 저장소 `snapshot-full*`(첫 수집)과 데이터 폴더 `runs/*`(완주한 것만)를 `Row` 하나로 읽음. 첫 수집은 받은 바이트 해시로 파일 손상을 확인한 뒤 정규화 해시를 새로 냄. 주소 선택은 D57 규칙 그대로 |
| `ingestion/parsers/uploads.py` | 저장소 + 데이터 폴더 |
| `ingestion/candidates/__init__.py` | 건너뛴 회차를 notes 에 남김 |

404 는 "받은 것"으로 센다. 사이트가 없다고 답했기 때문이다. `NARA1_DATA_DIR` 이 없으면(PC · 섀도우) 지금과 똑같이 저장소만 읽는다.

##### 바꾼 판단 — 끊긴 회차는 멈춤이 아니라 건너뜀
계획은 "끊긴 회차가 있으면 적재 멈춤"이었다. 그러면 그 회차를 지울 때까지(7일) 적재가 계속 막힌다. 끊긴 회차는 적재가 절대 믿지 않고 다음 완주 회차가 이어받는다. 대신 **수집기가 실패 코드로 끝나** 워크플로가 그 단계에서 실패하고 알림이 간다.

## 재사용 가능한 판단

- **예약은 이미 손으로 잘 도는 것을 시계에 맡기는 것이다.** 스케줄은 맨 마지막, 그 앞은 버튼 실행으로 검증한다
- **하루 한 번 순서대로 도는 배치에는 큐가 필요 없다.** 러너면 충분하다
- **"마지막 성공" 판단 칸은 결과가 같아도 갱신돼야 한다.** 멱등 적재 + 매일 확인 + N일 기준이면 꺼졌다 켜져도 따라잡는다
- **삭제는 릴리즈에 명시된 것만 한다.** 조용히 지우는 경로를 만들지 않는다
- **증분 저장은 "직전 파일 참조"가 아니라 내용 해시로 한다.** 참조하면 옛 폴더를 못 지운다
- **데이터는 저장소 밖에 둔다.** 배포 · `git reset` 에 휩쓸리지 않는다
- **해시로 변경을 판단하기 전에 같은 페이지를 시간 차를 두고 받아 본다.** 방문자 IP 한 줄이 전 페이지를 "바뀜"으로 만들었다
- **근거 파일은 원본 그대로, 비교는 정규화 값으로.** 두 해시를 같이 적는다
- **실패를 멈춤으로 막을지 건너뜀 + 알림으로 막을지는 막힘이 얼마나 오래가는지로 정한다**

## 한계

- **운영 적재 때 `Capture` 97개가 한 번 전부 바뀐다.** 해시 기준이 정규화로 바뀌어서다. 도메인 · 임베딩 영향은 없다. 운영 DB 는 아직 그대로다
- **2~5단계는 계획만 있다.** 서버에서 한 번도 적재를 돌린 적이 없다. 컨테이너 사용자와 서버 사용자 권한, 배포 폴더 compose 문제는 4단계에서 드러난다
- **알림 방법이 정해지지 않았다**(5단계 전)
- **정규화 규칙은 오늘 본 두 조각뿐이다.** 새 변동 조각이 생기면 매번 새 원문이 생기는 것으로 드러나고, 그때 목록에 더한다
- **사라진 노드 · 퇴사자 삭제와 개인정보 보관 기간은 미정이다.** 퇴사자 연락처는 DB 에 남는다
- **1단계 변경은 커밋 전이다**(깃은 사용자가 한다)
