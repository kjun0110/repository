## 개념

- **선언 구동 크롤링** — 접속 주소·셀렉터·수집 정책·게시판 목록을 코드가 아니라 `sites/*.yaml` 에 두고 코드가 그것을 읽는 것. 사이트가 늘어도 코드는 안 늘어난다
- **게시판 단위 라우팅** — 어휘 검색 결과가 어느 게시판에 몰렸는지 세어서, 그 게시판이 `공고` 유형이면 최신 글을 자리 보장하는 것. **신호를 지어내지 않고 이미 계산된 것을 센다**
- **`article_type`** — 게시글이 무엇인가(공고·결과발표·안내·자료실·현황공개·소식·홍보·unknown). `content_type`(민원의 절차/참고)과는 다른 축이다
- **`unknown` 을 어휘 "안" 에 둔다** — 어휘 밖이면 새 유형이 하나만 들어와도 `validate/00` 이 파이프라인을 멈춘다. 격리는 검사가 아니라 적재에서 정한다
- **`content_hash`** — 본문의 sha256 앞 16자. 사이트가 ETag·Last-Modified 를 안 주므로 **받아 봐야만 바뀐 걸 안다**
- **확신 있게 틀린 답** — 근거를 붙이고 출처를 달았는데 소관이 다른 답. 무응답보다 나쁘다

## 요약

어제 만든 도구(RRF·품질 게이트·정답 라벨) 위에서 **다섯 가지를 붙이고 다섯
가지를 기각했다.**

가장 값진 것은 **`sites/suwon.yaml` 이 실제로 크롤링을 지시하게 만든 것** 이다.
어제까지 그 파일은 "기록" 이었다. 지금은 접속 주소·셀렉터 9개·수집 정책 5개·
게시판 128개를 코드가 읽는다. 목표 문장의 앞 절 — *사이트 선언이 크롤링을
지시하고* — 가 처음으로 참이 됐다.

그리고 **어제 세 번 실패한 문제를 오늘 풀었다.** '공고가 지난 것부터 나온다'
를 시간 감쇠·풀 확대·자리 보장으로 세 번 고치려다 전부 실패했는데, 원인이
순서가 아니라 **관련성** 이었다. 게시판 단위로 라우팅하니 정밀도 81 → 86,
최신성 2/15 → 6/15, 오발동 0건.

**그리고 오늘 가장 중요한 교훈은 지표 밖에서 나왔다.** 게이트를 통과한
상태에서 실제 답변을 눈으로 보니 **브리지 게시글 URL 이 전부 틀려 있었고**,
`출생신고 서류 뭐 필요해` 가 **확신 있게 틀린 답** 을 내고 있었다. 둘 다
gold 로는 안 잡힌다.

## 1. 게시판 라우팅 — 세 번 실패하고 네 번째에 풀렸다

##### 문제

`수원시 공무원 채용 공고` 를 물으면 **지난 공고** 가 최신보다 위에 왔다.
게시글에 시간 감쇠가 없기 때문이라고 봤다.

##### 실패한 세 처방

```
① NOTICE_POOL 5 -> 25    날짜 경쟁 창을 넓힌다      변화 0건 · 정밀도 -2   기각
② 어휘 게시글을 풀에 주입   후보에 넣어 준다          변화 0건               기각
③ 어휘 1위를 자리 보장     확실한 것부터 고정한다     어휘 1위도 오답        기각
```

세 번 다 **원인 진단이 틀렸다.** 어휘 검색은 정답을 이미 찾고 있었다
(1048 게시판 글 25건 중 14건). 그런데 어휘 **1위부터가 '공무원 사칭' 보도자료**
였다. '공무원' 이라는 낱말이 그 기사에 물려서 벡터·어휘가 둘 다 그것을 위로
낸다. **관련성 단계에서 이미 진 것을 순위 조정으로 되살릴 수 없다.**

##### 네 번째 — 게시판을 신호로 쓴다

```python
BOARD_ROUTE_TYPES = {"공고"}
BOARD_ROUTE_MIN   = 0.4
BOARD_ROUTE_KEEP  = 2

# 어휘 게시글 결과가 어느 게시판에서 왔는지 센다
# 한 게시판이 40% 이상이고 그 게시판이 공고 유형이면 -> 최신 2건 자리 보장
```

**신호를 지어내지 않았다.** 어휘 검색은 이미 돌고 있고 게시판 소속도 이미
그래프에 있다. 세는 것만 추가했다.

##### 결과

```
정밀도       81/222  ->  86/222
최신성(3문항)  2/15  ->  6/15
좋아짐 3 · 나빠짐 0 · 오발동 0 (47문항 전수)
```

발동한 5개 질문의 게시판 비중은 56·56·100·100·100% 였다. **`0.4` 문턱이
현재 데이터에서는 한 번도 갈라내지 않는다** — 지금은 사실상 비활성이고,
게시판이 늘었을 때를 위한 안전장치다. 그렇게 적어 뒀다.

##### 지표의 함정을 하나 발견했다

`BOARD_ROUTE_KEEP` 을 4로 늘리니 `91/224` 가 나와 더 좋아 보였다.

```
KEEP 2   86/222
KEEP 4   91/224   <- 착시
```

자리 보장이 `top`(=5)을 넘어서면 `hits` 가 6개가 되어 **분자와 분모가 같이
는다.** 지표가 "후보를 더 보여주는 것" 에 보상을 준다. **후보 수를 고정하고
비교해야 한다.**

## 2. 선언이 실제로 크롤링을 지시한다

##### 어제까지

`sites/suwon.yaml` 은 robots 예외를 적어 둔 메모였다. 접속 주소·셀렉터·
게시판 목록은 전부 `scraping/12_fetch_articles.py` 안에 상수로 박혀 있었다.

##### 지금

```yaml
endpoints:   board_list · board_view
selectors:   9종   body · body_fallback_rows · meta_th · file_href ·
                   file_size · file_icon_prefix · list_head · list_body · list_row_link
crawl:       5종   user_agent · delay_sec · default_days · refetch_days · seen_stop_pages
robots:      deny 6경로 + allow_despite_robots(사유 포함)
boards:      128개  (take:true 20 / take:false 108 — 108개 전부 why 있다)
```

`scraping/12` 가 이걸 읽는다. 상수가 코드에서 사라졌다.

**`take:false` 에 전부 `why` 를 적게 한 것이 핵심이다.** "안 긁는다" 만 남으면
나중에 누구도 다시 판단할 수 없다. 108개 중 가장 큰 덩어리는 업무추진비
4종(11,032건)이고 사유는 "행정 공개 의무 자료 — 시민 질문의 답이 아니다" 다.

##### 유형도 선언이 정한다

```yaml
"1048": { name: "수원시 공무원/임기제 채용", take: true, type: 공고 }
"1042": { name: "시정소식",                take: true, type: 소식 }
```

`nodes/16` 이 `Board.default_type` 을 만들고 게시글에 물려준다. 선언에 없으면
`unknown` 이다.

```
소식 3,528 · 안내 636 · 자료실 510 · 공고 168 · 현황공개 146 · unknown 0
```

**`unknown` 이 0 인 것은 아직 격리 장치가 한 번도 안 돌았다는 뜻이다.**
20개 게시판을 사람이 미리 분류해 놨기 때문이다. 게시판을 더 열어야 그
장치가 처음으로 일한다.

##### 어휘 안에 `unknown` 을 둔 이유

```yaml
article_type: [공고, 결과발표, 안내, 자료실, 현황공개, 소식, 홍보, unknown]
```

어휘 밖에 두면 새 유형이 하나 들어올 때마다 `validate/00` 이 **파이프라인
전체를 멈춘다.** 격리는 검사가 아니라 적재의 일이다.

## 3. 수집 증분 — 바뀐 글을 잡는다

##### 문제 (어제의 "남은 것")

캐시가 새 글만 걸렀다. **바뀐 글은 못 잡는다.** 사이트가 ETag·Last-Modified 를
안 주므로 받아 봐야만 안다.

##### 만든 것

```
content_hash      본문 sha256 앞 16자
REFETCH_DAYS 30   최근 30일 글은 캐시가 있어도 다시 받아 해시를 비교
SEEN_STOP_PAGES 2 이미 본 글만 나오는 목록 페이지가 2번 연속이면 그 게시판 종료
```

##### 사흘째에 진짜 수정 3건을 잡았다

```
장애인 특별공급 안내      "○ 수정내용 : 84F 삭제, 84D 배정세대 변경" 이 추가됨
청소년 음악 경연대회      행사명 "2026 음악" -> "2026 전국 청소년 음악" 정정
새빛시민 도시정비학교     문자 몇 개 정정
```

**첫 번째가 정확히 우리가 잡아야 하는 것이다** — 배정세대가 바뀐 공고를
옛날 본문으로 답하면 시민이 헛걸음한다.

##### 목록 조기 종료

```
18분  ->  11분      데이터 손실 0
```

목록 페이지를 끝까지 넘기지 않고 "이미 본 글만 2페이지 연속" 에서 멈춘다.
어제 "주기 분할이 2단계의 강제 조건" 이라고 적었는데, **조기 종료가 그
긴급도를 낮췄다.**

##### 병합에서 창(window)이 깨질 뻔했다

조기 종료를 넣으니 이전 `articles.json` 을 병합하게 되는데, 그 병합이
**1년 창을 벗어난 글까지 되살렸다.** 3,747 → 3,736 으로 11건이 줄어드는 걸
보고 알았다(전부 2025-09-03 자). 게시판별 `in_window()` 를 붙여 고쳤다.

## 4. `--scope=type` — 유형으로 검색 대상을 정한다

어제는 `news`(= NOT timeless) 로 갈랐다. 유형 축이 생겼으니 그것으로 바꿨다.

```python
SEARCHABLE_TYPES = ["공고", "결과발표", "안내", "소식"]
# 제외: 자료실 · 현황공개 · 홍보
```

`timeless` 는 "오래돼도 유효한가" 이고 `article_type` 은 "무엇인가" 다.
**서식 자료실을 빼야 하는 이유는 오래돼서가 아니라 첨부 블록이 이미 그
자리를 담당하기 때문** 이므로 유형이 맞는 축이다.

범위 밖 게시글은 **`:Entity` 만 떼고 벡터는 남긴다.** 그래서 범위를 다시
바꿔 보는 실험이 공짜다(임베딩을 다시 안 만든다).

## 5. `places_for` — 죽어 있던 관계를 하나 살렸다

어제 "관계 18종 중 4종이 죽어 있다" 고 적었다. 그중 `LISTED_IN`(2,509개)이
오늘 처음 일했다.

##### 문제

`권선동 공중화장실 어디 있어` 를 물으면 민원 페이지 전체가 나온다. 그 안에
수원시 **전역** 의 화장실 표가 들어 있어서 답이 안 좁혀진다.

##### 만든 것

```python
def places_for(graph, civil_id, region):
    # 질문에서 잡힌 구·행정동·법정동 이름으로 Place.address 를 거른다
    MATCH (p:Place)-[:LISTED_IN]->(c:CivilService {civil_id: $civil_id})
    WHERE any(w IN $names WHERE p.address CONTAINS w)
```

결과가 컨텍스트 블록에 이름·주소·전화로 실린다. `권선동` 이면 8건이 나온다.

정답 라벨에 `places` 축(3문항)을 새로 만들고 게이트에 넣었다. **3/3.**

##### 기각 — Place 를 `:Entity` 로 올리기

"장소도 검색되게 하면 되지 않나" 를 실측했다. 안 된다.

```
Place 노드가 후보 자리를 먹고 관련 민원을 밀어낸다
장소는 "무엇을 하는 곳인가" 없이 이름·주소뿐이라 질문과 안 맞는다
```

**장소는 검색 대상이 아니라 답을 좁히는 재료다.** 앵커(CivilService)를 먼저
찾고 그 안에서 거르는 지금 구조가 맞다.

##### 기각 — 죽은 관계 4종 되살리기

`VISIT_FOR`(266개)를 검색에 붙여 봤다. **88건 중 88건이 이미 `visit_stops()`
가 내는 것과 같았다.** 관계는 있는데 정보가 중복이다. 지운 건 아니고 검색에
안 쓰기로 했다.

## 6. 지표를 통과해도 답이 깨질 수 있다

**오늘 가장 중요한 발견이다.** 게이트가 `1위 17/17 · 정밀도 86/222 · 첨부
4/4 · 장소 3/3` 으로 전부 통과한 상태에서, 실제 답변을 브리지까지 태워
눈으로 봤다. 둘이 나왔다.

##### (1) 브리지의 게시글 URL 이 전부 틀렸다

```python
def _hit_url(hit):
    url = hit.get("source_url")   # 민원
    org_id = hit.get("org_id")    # 조직
    # article_url 을 모른다  -> 전부 부서 홈 루트로 떨어진다
```

거기에 `_dedup_url` 이 `#3`·`#4` 를 붙여서, 시민이 출처를 눌러도 그 공고로
안 갔다. 09-03 에 Article 을 `:Entity` 로 올리면서 생긴 구멍이다.

**gold 로는 절대 안 잡힌다** — gold 는 후보 이름만 세고 브리지를 안 탄다.

##### (2) `출생신고 서류 뭐 필요해` 가 확신 있게 틀린 답을 낸다

답변이 출생신고가 아니라 **출산 지원금** 서류를 답한다("관할 보건소",
"분만일로부터 6개월", "여성정책과"). 그리고 첨부 `출생신고서(1).hwp` 를
**찾아 놓고 3/3 회 답변에 안 쓴다**(효도수당 3/3 · 지방소득세 3/3 은 잘 쓴다).

원인은 프롬프트가 아니다. **출생신고는 대법원 소관이라 수원시 CivilService 에
아예 없다.** 그래서 후보 5개가 전부 출산 지원이고 LLM 이 그것으로 답을 만든다.

```
gold 는 이 문제를 절반만 본다
  후보 정밀도 0/5   O   잡는다
  첨부를 찾고도 안 쓴다  X   못 잡는다
```

고치려면 **"수원시 소관이 아니다" 를 말할 수 있어야** 한다(`external_org` 축).
표본 하나로 프롬프트를 만지는 건 09-03~04 에 세 번 걸린 함정이라 안 했다.

##### 교훈

```
지표는 "어제보다 나빠졌는가" 를 본다
지표는 "애초에 맞는가" 를 못 본다
주기적으로 실제 답변을 눈으로 보는 것이 지표만 보는 것보다 값지다
```

**질문이 좁으면 라벨도 좁아야 한다.**

## 9. 클린 실행

30단계를 처음부터 다시 돌렸다.

```
exit 0 · 게이트 통과

1위 적중 17/17   정밀도 86/222   첨부 4/4   장소 3/3
PART_OF   937 요청 -> 938        WORKS_AT  5,089 -> 5,137
REQUIRES  890 요청 -> 890        고아 노드 없음 · 폐지 대상 없음
```

**증분으로 쌓아 온 상태와 처음부터 돌린 결과가 같다.** 이틀 동안 세 번
나왔던 "전체를 돌려야만 드러나는 버그" 부류는 지금은 없다.

실행 로그에 이런 게 찍힌다.

```
[참고] 담당 OrgUnit 을 안 붙인 13건 — 고용노동부·경기도 등 수원시 소관이 아니라 정상
[참고] 법령명을 특정할 수 없어 연결하지 않은 3건 — '영 제6조' 처럼 본법 없이 적힌 경우
```

**이게 출생신고 문제와 같은 부류다.** 적재는 "수원시 소관이 아니다" 를 이미
알아보고 안 붙이는데, **검색·답변 쪽에는 그 축이 없다.**
