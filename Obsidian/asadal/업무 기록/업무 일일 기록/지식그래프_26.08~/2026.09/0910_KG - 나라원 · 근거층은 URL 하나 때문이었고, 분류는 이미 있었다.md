## 개념

- **도메인층 / 근거층** — 나라원에 대한 사실(회사·조직·사업) / 그 사실이 어디서 왔는지(원문 파일·조각·진술). 후자가 지금 전체의 89%
- **두 게이트** — 라벨이 살려면 **원천**(원문에서 결정적으로 뽑히나)과 **소비자**(어떤 질문이 쓰나)를 모두 통과해야 한다. 지금까지 세 구현 모두 첫 게이트만 있었다
- **사물화(reification)** — 트리플 `(주어, 술어, 목적어)` 자체를 노드로 만들어 그 진술에 대해 말하는 것. 여러 출처가 같은 사실을 지지하거나 다툴 때 값어치가 난다
- **바이트 게이트** — 선언을 옮겨 적은 뒤 canonical JSON 바이트가 기존 동결 파일과 같은지 대조하는 것. 무회귀의 증명
- **`since` / `until`** — 라벨·관계가 어느 버전에 생겼나 / 사라졌나. 한 선언 파일에서 버전 여러 개를 파생시키는 장치
- **파악** — 배포 중인 저장소(`Ai_Pro_Neo4j_Search`). 운영 6060 포트와 Chatty 연동이 여기 물려 있다

## 6. 잘린 발주처는 사이트 안에서 복원되지 않는다

##### 문제

게시판 `발주처` 칸이 10자에서 잘린다. 23종 44건.

```
(재)예술경영지원센..  78건    대중소기업농어업협력..  76건
인천광역시 의회사무..  70건    과학기술정보통신부 ..   21건
```

##### 검증 — 코퍼스 전량 검색

HTML 전체 **421,816자**를 접두사로 훑었다.

```
대중소기업농어업협력..  →  대중소기업농어업협력재단   (company/history.htm 에 있음)

```

`guest.htm` 로고에 있을 수 있으나 이미지라 프로그램으로 못 읽는다.

##### 택한 안 — 노드로 만들고 사람에게 묻는다

지금 코드는 잘린 이름에 `continue` 를 걸어 노드도 간선도 안 만든다. **그러면 44건의 사업이 "발주처 없음"으로 보인다.** 원문에 그렇게 적혀 있다는 것은 참이므로 노드로 만들고 `name_truncated: true` · `identity_status: review_required` 를 붙인다.

사람이 확정하면 `name` 만 바뀌고 `merged_from` 에 원문이 남으며 **사업 노드와 간선은 그대로다** — 발주처를 속성이 아니라 노드로 둔 이유가 이것이다.

기계가 단서를 채워 준다 — 잘린 23종 **전부 기관유형을 이미 알고 있어** 로고 후보 범위가 5~35장으로 좁혀진다.

## 7. 근거층 — 세 번 재서 확정했다

##### 문제

릴리즈 2를 셰도우에 적재해 구성을 세니 **근거층이 89%** 였다.

```
전체 372   순수 도메인 40 · Assertion 282 · SourceRecord 41 · SourceAsset 6 · Release 2 · Head 1
도메인 노드 1개당 Assertion 약 7개 → 0.4.0 규모(도메인 371)면 6,053노드
```

##### 1차 — Assertion 은 원장의 중복 투영이다

사물화의 값어치는 `fact_key` 가 겹칠 때 난다. 실측했다.

```
릴리즈 1   Assertion 249 / 고유 fact_key 249   다중 출처 0건
릴리즈 2   Assertion 282 / 고유 fact_key 280   다중 출처 2건 (0.7%)
도메인 간선 121개의 support_count 분포   {1: 121}
```

겹친 2건도 같은 노드의 같은 속성(`Organization` 의 `name`·`identity_status`)이다. 그리고 **서빙 코드가 `Assertion` 을 한 번도 안 읽는다** — `read_by` 가 빈 선언이다. 원장(`fact_decisions`·`assertions`)은 이미 `release.json` 에 있고 `manifest_sha256` 으로 봉인돼 있다.

##### 2차 — 뒤집었다. 다중 출처가 372/389 였다

preview 전체로 다시 세니 다중 출처 노드가 **372/389** 였다. 조직도 슬라이스(40노드)만 보고 판단한 것이 틀렸다고 보고 근거층 유지로 돌아섰다.

##### 3차 — 다시 뒤집었다. 페이지네이션 중복이었다

URL 을 경로로 접어 다시 셌다.

```
BusinessProject 1건   SUPPORTED_BY 39개
                      고유 경로 3개 → /cause/cause02/list.htm · cause03 · cause04
고유 경로 수 분포      1개:17건 · 3개:372건
```

39번 관측은 **같은 게시판을 세 탭 × 페이지네이션으로 본 것**이지 39개 원문의 증언이 아니다. **진짜 독립 출처는 없다.**

##### 원인 — 실질 이유는 URL 하나였다

도메인 노드가 가진 속성 13개를 세어 봤다.

```
unit_id · name · unit_type · display_order · identity_status
source_record_id · source_asset_id · source_sha256          ← 전부 ID/해시
observed_at · parser_version · mapping_version · ontology_version · assertion_method

URL 을 담은 속성   없음
```

`source_asset_id` 는 자산 ID 지 URL 이 아니다. 그래서 `serving/neo4j_reader.py:15` 가 2홉을 걷는다.

```cypher
OPTIONAL MATCH (u)-[:SUPPORTED_BY]->(sr:SourceRecord)-[:PART_OF]->(sa:SourceAsset)
RETURN sa.canonical_uri AS source_url    ← URL 이 여기에만 있었다
```

##### 택한 안 — ProvenanceRef 에 필드 하나

```
제거   Assertion · SourceAsset · SourceRecord · Release
       PART_OF · SUPPORTED_BY · SUPPORTS · HAS_SUBJECT · HAS_OBJECT · DELIVERED_BY
       source_location(path) · parser_version · mapping_version · assertion_method

추가   ProvenanceRef.source_url
유지   ReleaseHead — release_writer.py:80 이 쓰기 락을 거는 대상이다
       ontology_version 을 여기로 이관 (한 트랜잭션 원자 적재라 노드마다 다를 수 없다)

6,053 노드 / 12,000 간선  →  372 노드 / 544 간선   서빙 2홉 → 0홉
```

**응답에 나가는 출처는 그대로다** — `source_url` · `source_sha256` · `observed_at`.

##### 남는 값들의 행선지

```
raw_location · content_type · byte_count   snapshots/manifest.jsonl (이미 있음)
payload_json · record_type · source_id     release.json
도메인이 안 된 레코드(주주총회·대표이사)     release.json
record_location                            제거 — 사업은 project-row:N(페이지 안 행 번호)이라
                                           재크롤 시 다른 사업을 가리킨다
```

##### `Release` 도 뺐다

적용 순서는 체인이 이미 강제한다(`expected_before_fingerprint`). 이력은 `release.json` 에 있다. 서빙도 `release_writer` 도 읽지 않고 간선이 0개다.

## 재사용 가능한 판단

- **파라미터를 하나만 보고 "원문에 없다"고 적으면 안 된다.** `categoryValue` 만 보고 재크롤이 필요하다고 썼는데 `k`/`v` 로 137페이지가 이미 수집돼 있었다. 수원의 "원천 한 장" 과 같은 부류다
- **"다중 출처" 를 세기 전에 URL 을 경로로 접는다.** 39개가 3개였다. 페이지네이션은 증언이 아니다
- **작은 슬라이스로 비율을 재고 전체를 판단하지 않는다.** 조직도 40노드로 "다중 출처 0.7%" 를 내고 근거층을 걷으려 했다. 전체로는 372/389 로 보였고, 경로로 접으니 다시 뒤집혔다 — 세 번 재서야 맞았다
- **라벨이 존재하는 실질 이유를 한 줄로 못 적으면 뺄 후보다.** `SourceAsset`·`SourceRecord` 는 "URL 을 둘 데" 하나였고, 필드 하나로 대체됐다
- **`read_by` 가 비어 있는 선언은 죽은 선언이다.** `Assertion` 2,400개를 서빙이 한 번도 안 읽었다
- **원장이 파일에 있으면 그래프에 또 넣지 않는다.** `fact_decisions` 는 `release.json` 에 manifest sha 로 봉인돼 있다
- **한 라벨이 두 가지를 뜻하면 반드시 걸린다.** `Organization` 이 회사 자신과 발주처를 함께 담고 있었다. DB 에 발주처가 0개인 지금이 분리 비용이 가장 낮다
- **노드 개수가 아니라 "주어가 될 수 있는 문장" 이 라벨을 가른다.** `Company` 는 싱글턴이지만 4개 관계의 출발점이라 `OrganizationalUnit` 과 별도다. 검증기가 라벨로 판정하므로 라벨이 강제의 손잡이다
- **집계 단위를 바꾸면 없던 충돌이 생긴다.** 기관유형 14종 충돌은 사업 단위 분류를 고객 단위로 합산한 결과였다. 데이터 오류가 아니다
- **어휘는 원문이 닫아 놓은 것만 만든다.** `event_kind`(수상/특허/사업)를 만들려다 뺐다 — 원문이 평면 목록이고 27건이 한 번에 읽히는 양이다
- **크롤 아티팩트를 도메인 속성으로 만들지 않는다.** `observation_count` 가 1~39로 요동하는 것은 페이지네이션 중복이지 사실이 아니다
- **파생 가능한 값을 저장하지 않는다.** 게시판 연도 분류와 `contract_date` 연도가 208/208 일치한다
- **표시용 일련번호를 식별자로 쓰지 않는다.** 게시판 `no` 가 208 중 204에서 게시판마다 다르다
- **"안 봤다" 와 "보고 뺐다" 는 다르다.** 제외한 페이지마다 사유를 남겨야 다음에 다시 묻지 않는다

## 한계

- **코드는 한 줄도 안 고쳤다.** 결정 15건이 문서에만 있다. `kjundocs/` 는 `.gitignore` 대상이라 저장소에 올라가지 않는다
- **운영 DB 상태를 직접 세지 못했다.** `10.20.20.12` 가 이 PC 에서 도달 불가라 "bootstrap 으로 73노드" 는 코드로 추정한 값이다
- **`until:` 이 없으면 0.4.0 을 선언할 수 없다.** `since` 는 "언제 생겼나" 만 표현하는데 0.4.0 에서 라벨 4종이 사라진다
- **`cardinality` 어휘에 `one_to_many` 가 없어 관계 4종을 `many_to_many` 로 잘못 적었다.** `HAS_EVENT`·`LOCATED_AT`·`OPERATES_IN`·`OFFERS` — 그대로 두면 "연혁 하나가 여러 회사에 속한다" 가 합법이 된다
- **`cardinality`·`inference_policy` 를 `validate_registry` 가 검사하지 않는다.** 오타나 미등록 값이 통과한다
- **어휘 값의 언어가 섞여 있다.** `unit_type`·`event_scope` 는 영문, `client_type` 은 한글(`guest.htm` 이 한글이라)
- **사람이 채워야 할 것이 4종 173건 남았다** — 잘린 발주처 23 · 영문 유형 매핑 4 · 인증서 21 · 고객 로고 125. 전부 이미지이거나 사이트에 없다
- **`generative-ai` 는 실적 0건이다.** 사업분야 탭에는 있는데 게시판 분류에 안 나온다 — `OPERATES_IN` 은 있고 `IN_AREA` 는 없는 노드가 된다
- **미결정 6건** — `Company` 키 값 · 런타임 YAML/JSON · 질문 20개 목록 · 매출 · 인증서 · 로고
