## 개념

- **RRF(Reciprocal Rank Fusion)** — 점수를 버리고 순위만 합치는 것. `1/(k+rank)` 를 검색기마다 더한다. 척도가 다른 검색을 섞을 때 쓴다
- **평활화 상수 `k`** — 1위와 2위의 차이를 줄이는 값. 크면 "한 검색기의 강한 1위" 보다 "여러 검색기의 합의" 가 이긴다
- **검색기 커버리지** — 한 검색기가 어떤 라벨을 볼 수 있는가. 라벨마다 다르면 융합이 편향된다
- **품질 게이트** — 답이 나빠지면 기준선을 갱신하지 않고 멈추는 장치. "기록" 과 "판정" 을 가른다
- **시간 감쇠(age decay)** — 같은 관련도면 최신을 우선하는 것. 게시글처럼 시점이 사실의 일부인 문서에 필요하다
- **`Board.timeless`** — 그 게시판 글이 오래돼도 유효한가. 서식은 참, 소식은 거짓
- **조용한 실패** — 예외도 안 나고 0건이 나오는 것. 측정 도구가 없으면 "효과 없음" 으로 잘못 결론난다

## 요약

검색에 **RRF** 를 넣고, 나빠지면 멈추는 **품질 게이트** 를 만들고, 게시글
3,743건의 **본문** 을 수집해 검색 대상에 넣었다. 셋 다 정답 라벨로 전후를
재고 결정했다.

가장 값진 것은 **정답 라벨을 26 → 35문항으로 늘린 것** 이다. 추가하자마자
회귀 2건과 내 라벨 오류 1건을 잡아냈고, 오후에 그 회귀 둘을 고쳐
**1위 적중 17/17** 이 됐다.

그리고 오늘 **전체 실행이라야 잡히는 버그가 두 번 나왔다** -- f-string 안의
중괄호(첨부가 4/4 → 0/4 로 조용히 죽음)와 `nodes/16` 의 낡은 가드(단독
실행은 통과, 30단계 실행은 중단). `EXPLAIN` 파싱이나 단독 실행으로는 절대
안 잡히는 부류다.

세 개의 가설이 기각됐다. **자리 보장을 RRF 로 대체하기**, **게시글은 서식이
유용할 것**, **발견이 커버리지를 늘릴 것** -- 셋 다 실측이 반대로 나왔다.

## 1. RRF — 척도가 안 섞이는 문제를 순위로 푼다

##### 문제

점수 척도가 셋인데 서로 안 섞였다.

```
코사인   0.6~0.9
BM25     1~90        질의어 수·희귀도·매칭 필드에 따라 절대값이 통째로 움직인다
구조     점수 없음
```

그래서 지금까지 "점수로 겨루게 하지 않고 자리만 보장한다" 로 피해 왔는데,
**자리 보장은 후보를 살려낼 뿐 자리 안의 순서를 정하지 못한다.** 후보 2~5위가
코사인 하나로만 줄을 서서, 어휘·업무 검색이 같이 가리킨 후보와 벡터만
가리킨 후보가 구별되지 않았다.

##### 만든 것

`search/steps/rrf.py`. 점수를 버리고 순위만 쓴다.

```
score(d) = SUM  w / (k + rank_L(d))        w=1.0, k=60
           L
```

`other_hits` 정렬만 바꿨다. 자리 보장·별칭·지역·이름 일치는 안 건드렸다 --
효과를 이 변경에만 귀속시키려면 한 번에 하나만 바꿔야 한다.

`k=60` 은 관례값이고 우리 데이터로 튜닝하지 않았다. 26문항에 맞춰 고르면
그 26문항에만 맞는 값이 된다.

##### 결과

```
                   1위      정밀도
코사인 정렬          16/16    41/118 = 35%
RRF                16/16    45/118 = 38%    채택
```

5개 좋아지고 1개 나빠졌다. 회귀 20/20 유지, 평균 0.30s.

##### 자리 보장은 RRF 가 대체하지 못한다 (기각)

없애도 되는지 실제로 빼 보고 쟀다.

```
자리보장 유지 + RRF     1위 16/16   정밀도 38%    채택
자리보장 제거 + RRF     1위 15/16   정밀도 35%    기각
```

이유는 `k=60` 의 성질 그 자체다. 어휘 1위와 벡터 1위가 둘 다 `1/61` 로
비기고, 어휘가 주입한 후보는 코사인이 0.0 이라 동점 처리에서 진다. 벡터
20위 밖의 정답을 어휘가 끌어올리는 경우(실측 1건)가 정확히 그 모양이다.

**평활화가 합의를 우대하는 대신 단독 강한 표를 누른다.** 단독 표가 유일한
근거인 경우에 손해가 난다. 둘은 하는 일이 다르다.

```
자리 보장    후보를 살려낸다        "이건 자르지 마라"
RRF         살아남은 것을 줄 세운다  "이 순서로 보여라"
```

##### 목표는 절반만 이뤘다

"손으로 맞춘 상수를 없앤다" 가 이 항목의 제목이었는데 **상수는 하나도 안
없어졌다.** `LEXICAL_MIN=14`·`LEXICAL_KEEP=1` 그대로고, 오히려 `K=60`·
`RRF_FETCH=20` 이 늘어 12개에서 14개가 됐다. 상수 제거는 데이터가 커져서
자리 보장 자체가 안 통할 때 다시 볼 문제다.

## 2. 품질 게이트 — 기록과 판정을 갈랐다

##### 문제

`validate/03` 은 대조 없이 기준선을 덮어썼다. 나빠진 채로 돌려도 그 결과가
새 기준이 되고, 다음부터는 "어제와 같다" 로 통과한다.

**실제로 오늘 그 사고를 냈다** -- RRF 를 붙이면서 대조 없이 `03` 을 돌려
이전 `search20.json` 을 날렸다. 그때는 `04` 를 손으로 전후에 찍어 둬서
정보가 안 날아갔지만, 자동으로 돌면 아무도 손으로 안 찍는다.

##### 만든 것 — `validate/05_gate.py`

```
1. 정답 라벨 35문항 실행
2. 그래프 상태 측정
3. 저장된 기준(quality.json)과 대조
4. 통과면 세 파일 갱신 / 실패면 아무것도 안 쓰고 exit 1
```

**실패했을 때 기준선을 그대로 두는 것이 핵심이다.** 다음 실행이 고쳐졌는지
비교할 대상이 남아야 한다.

##### 판정 기준과 문턱 근거

```
1위 적중 감소        FAIL   정답이 1위에서 밀렸다. 후보에 있어도 답이 안 나온다
첨부 적중 감소        FAIL   4문항뿐이라 1건만 빠져도 크다
정밀도 3건 초과 하락   FAIL
노드/관계 10% 감소    FAIL   수집 실패·적재 사고. 검색 지표보다 먼저 잡힌다
violations 50% 증가  WARN   규칙을 새로 넣어도 늘어서 막지 않는다
```

문턱을 감으로 안 정했다 -- 같은 코드로 3회 연속 돌려
`16/16 · 45/118 · 4/4` 가 세 번 다 똑같이 나왔다. 그래서 1위·첨부는
여유 0, 정밀도 여유 3은 지금 관측된 잡음이 아니라 앞으로 생길 잡음
(HNSW·데이터 증가) 몫이다.

##### 고장 주입으로 확인

어휘 자리 보장을 일부러 빼고 돌렸다.

```
[게이트 실패] 기준선을 갱신하지 않는다.
  - 1위 적중 16 -> 15  밀린 질문: ['육아휴직 급여 얼마']
  - 후보 정밀도 45/118 -> 41/118  (4건 하락, 허용 3)
-- exit: 1 --

md5sum -c   quality.json OK · search20.json OK      <- 안 덮어썼다
```

##### 곁들여 고친 것

- `validate/03` 을 기본 **보기 전용** 으로. 덮어쓰려면 `--write`
- `gold_sha` 를 quality.json 에 넣었다. 라벨이 바뀌면 비교를 건너뛴다 --
  질문을 9개 더하면 `45/118` 이 `52/159` 가 되는데 그건 개선이 아니다
- `main.py` STEPS 마지막에 편입. **여기서만 파이프라인이 검색 결과를
  근거로 멈춘다** (`validate/00` 은 원천, `01` 은 그래프의 모순을 본다)

## 3. 정답 라벨 26 → 35문항 — 추가하자마자 셋을 잡았다

뉴스 6 + 지역 3 을 추가했다. **없으면 게시글을 넣어도 "손해" 만 재고 "이득"
을 못 잰다.**

```
1  내 라벨이 틀렸다      '수원 발레축제 언제 해' 를 "기사에만 있다" 고 적었는데
                      CivilService '수원발레축제' 본문에 '기 간 : 2026. 9. 12.(토)'
                      가 있다. 검색이 그걸 1위로 냈고 맞았다

2  진짜 회귀 발견        '권선구 세무 관련 문의' 의 1위가 '권선구'(구 자체)다

3  라우터 결함           '중장년 1인가구 지원사업' 이 civil_filter 로 빠져
                      후보가 1건뿐
```

**원래 26문항은 relevant 도 top1 도 안 건드렸다.** 아침 상태와 대조하면
그대로 21 · 좋아짐 4 · 나빠짐 1, 1위 적중 16/16 유지.

##### 라벨은 "점수가 오르나" 가 아니라 "이것이 답인가" 로 정한다

두 건을 넓혔고 둘 다 오늘 내가 만든 질문이다.

```
수원 발레축제         CivilService '수원발레축제' 를 relevant 에 추가
새빛청년존 모집 결과   '당첨자 및 예비입주자 발표' 도 모집 결과의 답이다. 1 -> 4건
```

반대로 `드론 불꽃축제` 는 후보가 전부 오답이라 0/5 그대로 뒀다.

## 4. 게시글 본문 — 이미 받아놓고 버리고 있었다

##### 문제

`scraping/12` 가 상세 페이지 HTML 을 받으면서 `parse_meta`(부서·전화)와
`parse_files`(첨부)만 뽑고 **본문을 버렸다.** Article 3,771건 전부 본문이
없었고, 게시글은 벡터로 닿을 수 없어 "담당부서가 최근 올린 소식" 이라는
구조 경로로만 답에 실렸다.

##### 수집 결과

```
글 3,743건 · 본문 파싱 실패 0건 · 총 259만자
본문 길이  중앙 670 · 평균 692 · 최소 7 · 최대 5,722

게시판별            건수    본문 중앙   timeless
  보도자료          2,204     804      False
  시정소식          1,068     403      False
  민원서식자료실        469      33      True
  민원서식             26     257      True
  옥외광고물            12      22      True
  청렴자료실             3     689      False
  해명자료               1     561      False
```

**양의 87% 가 뉴스고 본문이 실한 것도 그쪽이다.** 서식 게시판은 "첨부 참조"
형식이라 본문이 제목 반복 수준이다. 50자 미만 350건 중 312건이
민원서식자료실이다.

길이로 거르지 않았다 -- 짧아도 쓸모 있는 게 섞여 있다
(`[38자] 여권발급 수수료 인상 안내(2026.3.1.)`).

셀렉터는 `.bbs__view td.p-table__content` 다. `.bbs__view` 전체를 긁으면
제목·작성자·부서·전화·첨부 목록·이전글/다음글이 다 딸려 온다(실측 788자 중
본문은 401자).

##### 범위 판정 — 세 후보가 전부 빗나가고 정반대가 답이었다

내가 세운 후보는 `all / timeless / recent` 였다. 후보로 들어온 게시글의
출처를 세어 보니:

```
민원서식자료실 timeless=True   후보 11자리 차지 · 정답 0건
시정소식      timeless=False   5자리 · 정답 1
보도자료      timeless=False   3자리 · 정답 1
```

**서식 게시글은 첨부 블록이 이미 담당하는 자리다.** 첨부 적중이 4/4 로
나가고 있는데 같은 것이 후보 자리를 또 먹으며 relevant 를 밀어냈다.

그래서 `news`(= NOT timeless) 를 새로 만들어 채택했다.

```
범위          정밀도 합계    1위      첨부
없음           55          17/18    4/4
전량 3,743     51 (-4)     17/18    4/4     기각
news + 최신    55 (동률)    17/18    4/4     채택
```

##### 동률인데 왜 넣나

손익이 상쇄된 것이지 아무 일도 안 일어난 게 아니다.

```
뉴스 질문 6개    +2
민원 질문 29개   -2
```

목표가 "수원시 전체를 답한다" 이므로 뉴스 질문도 답해야 하고, 민원 쪽 -2 는
후보 구성이 바뀐 것이지 답이 깨진 것이 아니다(1위·첨부 유지).

##### 새로 만든 장치 둘

**게시글 자리 상한 1** -- `REGION_GU_CAP`·`LEXICAL_KEEP` 과 같은 장치.
게시글은 주제가 좁고 시점이 있어 "이 주제 전체" 를 답하지 못하는데 벡터
유사도는 높게 나온다. 한 질문에 3건씩 몰렸다.

**그 한 자리는 최신 것에게 (시간 감쇠)** -- 같은 주제 게시글이 여러 건이다.
'일자리두드림 채용행사' 는 매달 열려 12건이 있고 "언제 열려" 의 답은 최신
것이다. RRF 는 시점을 안 봐서, 정답이 벡터 1위(2026년 8월)인데 **2025년
12월 글**이 자리를 가져갔다. 관련성 상위 3건으로 좁힌 뒤 날짜로 고른다
-- 순서를 바꾸면 무관한 어제 글이 이긴다.

## 5. RRF 의 커버리지 편향 — 오늘 가장 중요한 발견

게시글을 넣었는데 뉴스 질문이 거의 안 잡혔다. 그런데 벡터 검색은 완벽했다.

```
새빛청년존      기사 벡터 2위 (0.757)
일자리두드림     기사 벡터 1위 (0.803)
드론 불꽃축제    기사 벡터 1위 (0.761)
연화장         기사 벡터 1위 (0.817)
```

원인은 **어휘 인덱스가 Article 을 안 덮어서** 였다.

```
벡터 1위 게시글          {vector: 1}                0.01639  ->  RRF 8위
벡터 54위 CivilService   {vector: 54, lexical: 1}   0.02517  ->  RRF 2위
```

RRF 는 "여러 검색기가 함께 가리킨 것" 을 우대하는데, **한 검색기가 특정
라벨을 아예 못 보면 그 라벨은 영구히 불리하다.**

```
CivilService   벡터 + 어휘              2개
OrgUnit        벡터 + 직위어휘 + 업무어휘  3개
Article        벡터                    1개   <- 구조적으로 불리
```

`article_text_index`(title·content, cjk)를 만들고 `article_lexical_search`
를 추가해 2개로 맞췄다. 제목에 `^5` 를 준다 -- 게시글 제목은 고유명사인
경우가 많다('일자리두드림', '새빛청년존', '연화장').

**교훈: RRF 를 쓸 때는 검색기별 커버리지가 라벨마다 같은지 봐야 한다.**

## 6. 조용한 실패 셋

세 개 다 예외도 안 나고 0건이 나왔다. 측정 도구가 없었으면 전부 "게시글은
도움이 안 된다" 로 잘못 결론 났을 것이다.

##### (1) `name` vs `title`

Article 은 이름 자리가 `name` 이 아니라 `title` 이다. `RETURN_FIELDS` 가
`node.name` 을 읽어서 게시글이 후보에 들어와도 이름이 `None` 이었다.
정답 라벨과 대조 자체가 안 되고 컨텍스트 블록도 비었다 -- **첫 측정이 통째로
무효였다.** `coalesce(node.name, node.title)` 로 고쳤다.

##### (2) f-string 안의 중괄호

Cypher 주석에 중괄호를 그대로 썼는데 f-string 이라 파이썬이 그 안을 변수로
해석해 `NameError` 가 났다. 그게 `except Exception: return []` 에 삼켜져
**첨부 적중이 4/4 → 0/4 로 죽었다.** 09-02 의 `{{org_id}}` 버그와 같은
부류다.

##### (3) `status` 가 없으면 임베딩해도 안 보인다

`vector.search` 의 질의가 `WHERE node.status = 'active'` 다. Article 에 그
속성이 없어서, 임베딩만 했으면 **아무 일도 안 일어난 채로 "효과 없음" 이라는
결론이 났을 것이다.** `nodes/16` 에서 붙였다.

## 7. 회귀 2건 수정 (오후)

##### (1) '권선구 세무 관련 문의' 의 1위가 '권선구'

원인이 셋이었고 **전부 같은 뿌리** 였다 -- "시민이 구 이름을 댄 것은 그 구
안의 무언가를 묻는 것이지 구청 자체를 묻는 게 아니다" 를 세 장치가 각각
몰랐다. 지역은 `region_hit` 이 이미 담당하는 자리다.

```
① 이름 승격      $q CONTAINS o.name 에 '권선구'(3글자)가 걸려 무조건 1위로
② 어휘 자리보장   CivilService '권선구' 를 물었다 -- 공인중개사무소 목록 표 페이지
③ 직위 검색      직위 '권선구청장' 이 34.4점으로 걸려 OrgUnit '권선구' 를 주입
```

한 원칙을 세 곳에 적용했다 -- **이름이 지역명 "그 자체" 일 때만 뺀다.**
'장안구보건소' 는 이름이 '장안구' 와 달라서 안 걸린다(이 규칙이 실제로
순위를 바꾼 유일한 사례라 반드시 살아남아야 했다).

**기각한 대안**: "어휘 검색도 지역명 뺀 텍스트를 쓴다". 실측하니
`장안구보건소장이 누구야` 가 깨진다 -- 원문이라야 장안구보건소 86.7 로
1위인데 지역을 빼면 보건행정과만 남는다. `권선구청장이 누구야` 는
`detect_leader` 가 앞에서 이미 답하므로 제외해도 잃는 것이 없다(실측).

```
+ 권선구 세무 관련 문의   0/5 -> 3/5
+ 팔달구 반려동물 등록    2/5 -> 3/5     같은 원인이었다
```

**팔달구가 같이 고쳐진 것이 중요하다** -- 한 질문에만 맞춘 땜질이 아니라는
뜻이다.

**라벨도 고쳤다.** `top1='세무과'` 로 박았는데 근거가 약했다. 세무과는
임베딩 텍스트가 256자라 산하 팀들(더 긴 텍스트)에 밀려 벡터 60위 밖이고,
대신 권선구 세무과 산하 도세1팀·시세팀·재산세팀이 들어온다. 셋 다 답이라
`top1` 을 null 로 두고 relevant 를 넷으로 넓혔다. "과 단위로 답할 것인가
팀 단위로 답할 것인가" 는 별도 설계 문제로 남긴다.

##### (2) `civil_filter` 라우터가 절차 질문을 가로챈다

원인은 "'중장년' 이 무시됐다" 가 아니었다.

```
'중장년'    TARGET_ALIASES 에 아예 없다. 무시된 게 아니라 모르는 말
'지원사업'   TRIGGER_WORDS 에 있어서 목록 라우터가 발동
결과        target_group='1인가구' -> 1건
```

**목록 라우터의 값은 "전수를 보여주는 것" 인데 1건이면 그 값이 없다.**
게다가 그 경로는 `hits` 에 `civil_id` 를 안 실어서 절차·구비서류·담당부서·
첨부가 통째로 빠진다.

```python
CIVIL_FILTER_MIN = 2
if len(names) < CIVIL_FILTER_MIN:
    civil_filters = None      # 벡터 경로로 흘려보낸다
```

**트리거 어휘를 좁히는 방법("지원사업" 을 빼는 식)은 안 골랐다** -- 그러면
진짜 목록 질문을 잃는다. 결과 수로 판정하는 편이 어휘를 지어내지 않는다.

```
중장년 1인가구 지원사업 신청하려면   0/1 -> 2/5   정답 기사 + 1인가구지원팀 둘 다
청년 관련 정책 뭐가 있어          23건 목록 유지 (변화 없음)
```

## 9. 사이트 실측 — 규모가 생각과 달랐다

##### 게시판이 8개가 아니라 130개다

```

```


**130개 게시판이면 하루 단위다.** 주기 분할(변화율별)이 "있으면 좋은 것" 이
아니라 2단계의 강제 조건이다.

그리고 **중간 저장이 없어서 2시간치를 실제로 잃었다.** 90% 지점에서
중단시켰는데 캐시가 메모리에만 있었다. `_detail_cache.json` 에 50건마다
저장하도록 고쳤다.

##### robots.txt

`scraping/00` 이 긁는 `/web/organization/` 이 `Disallow` 경로다 -- 조직도
(OrgUnit 940 · Employee 5,134)가 전부 그 산물이다.

**결정: 지금 상태 유지, `sites/*.yaml` 에 기록만 남긴다.**

`allow_despite_robots` 라고 이름 붙이는 것이 핵심이다 -- 나중에 누가 봐도
"몰라서 긁은 게 아니라 알고 예외로 둔 것" 이라는 게 남는다.

## 10. 관계 18종 중 4종이 죽어 있다

검색 코드에서 한 번도 안 쓰이는 관계를 세어 봤다.

```
IN_DOMAIN     644개   CivilService -> Domain    분야 트리
LISTED_IN   2,509개   Place -> CivilService     표에 실린 장소
PARENT_OF      74개   Domain -> Domain          트리 계층
VISIT_FOR     266개   CivilService -> Issuer    추론으로 만든 것인데 안 쓴다
```

**적재는 쉽고 활용은 어려워서 22% 가 죽었다.** `VISIT_FOR` 는
`relationships/05` 가 합성한 것인데 아무도 안 물어본다. 이것이 "관계는
자동으로 늘릴 수 없다" 의 실물 증거다.

대응 방향은 **선언 기반 순회** 다 -- `schema.yaml` 의 `relations` 절을 읽어
1홉 이웃을 자동으로 나열하면 새 관계가 YAML 한 줄이 된다. 다만 첨부(날짜
정렬+임계+게이트)·집계·지역·추론은 일반 순회로 안 되므로 혼합이다.
검증은 죽은 4종을 선언에 넣었을 때 정밀도가 오르는지로 한다.

`schema.yaml` 에 `relations` 절이 아예 없다는 것도 오늘 확인했다 -- 관계
18종이 코드 다섯 개에 박혀 있고, 표류를 막는 것은 선언이 아니라 사람이다.
