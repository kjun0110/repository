## 개념

- **온톨로지 구동** — 선언이 파싱·검증·적재·추론·라우팅을 *만든다*. 선언 한 줄을 고치면 코드를 안 건드려도 검사 수·제약 수·질의 모양이 바뀐다
- **규칙 적용기** — 선언한 규칙을 한 바퀴 돌리는 것. 고정점까지 반복하는 추론기와 다르다
- **물질화(materialize)** — 파생 사실을 간선으로 저장할지, 질의 때 풀지
- **사람 결정(decisions)** — "이 건은 이렇게 본다"는 판정. 근거(`why`)와 승인자(`by`)가 붙는다. 값의 집합을 정하는 어휘와 다르다
- **답변 축** — gold 의 여섯 번째 축. 생성된 답변 문장을 보는 유일한 축. 나머지 다섯은 후보만 본다
- **`page_kind`** — 민원 페이지가 단일 절차인가, 여러 서비스를 모은 대문인가. 대문의 구조화 필드는 페이지 것이 아니다

가장 값진 것은 **선언이 검사를 만들게 한 것**이다. 제약 14개가 `labels[].key` 에서 생성되고 검사 139건이 선언에서 나온다. 라벨을 한 줄 추가하면 제약이 15개가 되고, 카디널리티를 고치면 검사가 138건이 된다.

그 구조가 서자마자 아무도 몰랐던 결함이 나왔다. `WORKS_AT` 식별자가 조직 *이름*을 써서 두 구의 세무과가 한 사람으로 접혔고, `IN_CHARGE_BUREAU` 는 동점 21건에서 답이 안 정해지는 상태였다. 둘 다 그래프는 멀쩡해서 기존 검사로는 영원히 안 잡힌다.

## 1. `출생신고` — 열한 번 만에, 원인은 프롬프트가 아니었다

##### 문제
`출생신고 서류 뭐 필요해` 가 출산 지원금 서류(진단서·진료비 영수증·입퇴원 확인서)를 출생신고 구비서류라고 답한다. 담당부서·전화·출처까지 붙어 확신 있게 틀린 답이다. gold 의 다섯 축을 전부 통과한다.

##### 기각한 안 여덟

```
1~4  기권 신호 4종      점수 임계 · 겹침 길이 · 바이그램 커버리지 · LLM 판정 호출
5    표 자르기 수리      이미 잘 되고 있었다 (gold note 가 옛 동작을 적어둔 것)
6    중복 후보 제거      본문 해시가 같은 무연분묘 알림 11건이 전부 정답이다
7    Issuer 앵커        '출생신고'와 '가족관계등록부' 사이에 다리가 없다
8    소관 밖 목록 하드코딩  틀린 사실이었다 — 접수는 동 행정복지센터에서 한다
```

기권 신호 넷은 전부 같은 이유로 실패했다. 검색은 언제나 주제상 가까운 것을 돌려준다 — `출생신고`→`저출생대응팀`, `부동산 등기`→`부동산관련사이트`. "가깝지만 그것이 아니다"는 표면 통계가 아니라 의미 판단이다.

실측(gold 47문항 + 그래프에 없는 6문항):

```
1위 점수      gold 중앙 0.745 · 없는 것 0.695     겹침 과다
              gold 8문항이 1위 점수 0.000 — 자리 보장 후보라 코사인이 없다
겹침 길이      gold 0~10 · 없는 것 2~4            없는 것이 gold 안에 들어앉는다
판정 호출      absent 5/5 잡음 · gold 오탐 12      컨텍스트를 더 주니 오탐이 늘었다
```

##### 원인 — 목록 페이지
`출산 후 지원` 은 하나의 민원이 아니라 여러 서비스를 모은 대문이다. 적재가 페이지를 노드 하나로 접으면서 표 첫 줄(`고위험 임산부 의료비 지원`)의 구비서류를 페이지 전체 것으로 붙였다. 그 민원은 별도 노드로도 존재한다.

LLM 은 거짓말을 한 게 아니라 틀린 노드를 충실히 읽었다. 노드가 "내 구비서류는 10종"이라고 주장하는 한 읽는 쪽을 단속해도 소용이 없다 — 프롬프트 가드가 실패한 이유(아홉 번째 기각)가 이것이다.

##### 택한 안 — `page_kind` 를 온톨로지에 두고 적재가 판정
마커 5개(`지원대상`·`신청대상`·`사업대상`·`지원내용`·`사업내용`)가 4회 이상이면 목록. 임계와 마커는 `schema.yaml page_kind_rule` 에 있다.

```
CivilService 644  ->  단일 618 · 목록 26
정상 페이지 0~2회   인감증명발급 0 · 여권 신청 0 · 효도수당 2 · 난임부부 2
목록 페이지 4회+    복지·문화 50 · 출산 전 지원 20 · 일자리 20 · 출산 후 지원 9
```

노드는 지우지 않는다. `맞춤형 기초생활보장제도`(9회)는 gold 문항 `기초생활수급자 지원` 의 정답이다. 본문은 쓸모가 있고 구조화 필드만 못 믿는다.

##### 구현 — 세 곳을 막았고, 두 번 샜다
구비서류만 막으니 처리 장소로 샜다(`주소지 관할 보건소`). 처리 장소를 막으니 절차로 샜다(`동 행정복지센터에 신청`). 결국 구조화 필드 전체를 한 덩어리로 가린다. 본문·담당부서·전화는 남긴다 — 페이지 전체의 것이 맞고 시민이 어디에 물어볼지는 알아야 한다.

점수 하한도 같이 뒀다. `page_kind` 는 "이 노드의 필드가 제 것이 아니다"라는 구조적 사실이고, `DOC_TRUST_MIN = 0.74` 는 "그래프에 그 절차가 아예 없다"는 통계적 추정이다. 후자는 벡터로 온 후보만 보고 구비서류 블록에만 건다.

```
구비서류 후보를 가진 질문의 벡터 최고 점수
  그래프에 없는 절차 6개   0.702 ~ 0.734
  ---------- 0.74 ----------
  gold 구비서류 질문       0.747 ~ 0.881
```

여유 0.013 으로 얇다. 답변 축이 이 값을 지키는 장치다.

##### 결과

```
"출생신고에 필요한 구비서류는 수원시 안내에서 찾지 못했습니다.
 하지만 출산 후 지원과 관련된 정보는 다음과 같습니다. …
 출생신고와 관련된 서식: 출생신고서 (hwp 66KB) 내려받기 …"
```

09-04에 "첨부를 찾고도 3/3 답변에 안 쓴다"고 적은 문제도 같이 풀렸다.

## 2. 답변 축 — 게이트가 처음으로 답변 문장을 본다

##### 문제
gold 의 축 다섯(`top1`·`relevant`·`attach`·`places`·`aggregate`)이 전부 후보만 본다. `validate/04` 가 `make_answer=False` 로 부르니 검증 중에는 답변이 생성조차 안 된다. 그래서 `출생신고` 가 정밀도 0/5 로 이미 잡히면서도 오답이 나갔다 — "후보가 나쁘다"는 말했고 "나쁜 후보로 답을 지어냈다"는 못 말했다.

##### 택한 안 — 표시된 문항만 답변을 생성한다
`answer_must` / `answer_not` 이 붙은 문항만 `make_answer=True` 로 한 번 더 돈다. 47문항 전부에 LLM 을 태우면 검증이 느려지고 비결정적이 된다.

판정은 문자열 포함으로만 한다. 의미 판정을 넣으면 판정기 자체가 흔들려 회귀 검사가 성립하지 않는다 — 같은 날 판정 호출을 관문으로 쓰려다 gold 오탐 12로 기각한 이유다.

```
"출생신고 서류 뭐 필요해":
  answer_not: [관할 보건소, 진료비 영수증, 입·퇴원 확인서, 진단서]
```

`answer_not` 의 값은 전부 실제로 나온 오답 문장에서 가져왔다.

##### 결과
축이 만들어지자마자 잡을 것을 잡고 오탐이 없었다.

```
전입신고 어떻게 해            X   빠짐 행정복지센터
출생신고 서류 뭐 필요해         X   관할 보건소 · 진료비 영수증 · 입·퇴원 확인서
대형폐기물 냉장고 버리는 비용     O
권선동 공중화장실 어디 있어      O
```

`전입신고` 는 내 라벨이 틀린 것이었다. 답변이 "거주지 관할 동에서 처리합니다"라고 옳게 말하는데 `행정복지센터` 라는 글자가 없어 실패로 잡혔다. `answer_must` 항목에 `|`(이 중 아무거나)를 넣어 고쳤다.

`출생신고 서류 뭐 필요해` 의 `answer_must` 도 틀렸다. 서류를 묻는 질문에 장소를 요구해 놓고, 그 장소를 담은 줄에서 금지어가 딸려 나왔다. 질문 종류에 맞게 라벨을 나누고 `출생신고 어떻게 해` 를 새 문항으로 추가했다.

최종 gold 48문항 · 답변 축 6문항 · 6/6 통과.

## 3. 선언이 검사를 만든다 — 제약·판정·규칙

##### 문제
라벨 14종과 관계 18종이 코드로 닫혀 있는데 **닫혔다는 것을 확인할 방법이 없었다.** `:Article` 이 있다는 사실은 `nodes/16_articles.py` 가 있다는 것으로만, `POSTED_BY` 는 그 안의 Cypher 문자열로만 표현됐다.

##### 구현 — `labels`·`relationships` 절과 `validate/06_schema.py`

```
labels 14        key · entity · ko · desc
relationships 18 from · to · cardinality · acyclic · transitive · materialize · read_by · derived

slots 6          어느 라벨의 어느 속성이 어느 어휘를 쓰는지
inference 2      chain · depth · where · nearest · tie_break

제약은 `labels[].key` 에서 생성한다. 기존 이름을 그대로 재현해야 `IF NOT EXISTS` 가 먹으므로 `LEGACY_NAMES` 로 14개를 매핑했다.

##### 검증 — 선언을 고치면 무엇이 따라 움직이나

## 4. 리팩토링이 결함 여섯을 찾아냈다

전부 **데이터는 멀쩡하고 답만 틀리는** 부류다. 그래프를 보는 검사로는 안 잡힌다.

##### `WORKS_AT` 식별자가 조직 이름을 쓴다
카디널리티 검사(`N:1`)가 잡았다. `new_id(gname[gid], …)` 가 조직 *이름*을 해시해서, 같은 팀 이름이 여러 구에 있으면 다른 사람이 한 노드로 접힌다.

```
live_3cbdc5ada343  행정관리팀   장안·권선·팔달·영통 7명 -> 1명
live_a7a8ff2211cf  도로정비팀   장안 4 + 팔달 4      -> 1명
                              원천 기준 7묶음 35명
```

`org_id` 를 쓰도록 고쳤다. 본체 5,089명은 `<부서코드>_<번호>` 라 이 문제가 없다. 그래프에 실제로 뜬 유령 1건(이름·업무 없음, 폐지 상태)은 지웠다.

##### `IN_CHARGE_BUREAU` 동점 21건이 미정의
추론 규칙을 선언으로 옮기니 손으로 쓴 Cypher 와 18건에서 다른 답이 나왔다. 원인은 구현이 아니라 규칙이었다 — 4개 구보건소가 전부 거리 0·직속기관이라 "가장 가까운 것 하나"로는 답이 안 정해진다. `tie_break: org_id` 를 명시했다.

##### 제약·키가 선언과 코드에 두 벌
레지스트리를 만들자마자 드러났다. `labels[].key` 와 `schema/01_constraints.py` 가 같은 사실을 갖고 있었다.

##### `UNIT_LEVELS` 17개가 선언과 코드에 두 벌
`org_classes` 와 완전히 같은 값이 `search/steps/structure.py` 에 있었다. 손으로 훑어 찾았고, 그 훑기를 `validate/08_declared.py` 로 만들었다.

##### `_SCHED_LABEL` 이 어휘 키와 중복
`validate/08` 이 만들어지자마자 잡았다. 키 4개가 `schedule_kind` 어휘와 정확히 같아서, 어휘에 종류를 추가하면 라벨이 없어 그 일정이 답변에 안 나갔다.

##### YAML 이 `no` 를 `false` 로 읽는다
속성 선언에 `no: { type: int }` 를 넣었더니 검사가 `Article.False 은 required 인데 빈 노드 6,285개` 라고 했다. **검사기가 자기를 만든 선언의 오류를 잡았다.**

## 5. 수집 — 유형과 창을 맞췄고, 두 규칙이 서로를 몰랐다

##### 문제
`sites/suwon.yaml` 의 게시판 20개 중 4개가 유형과 `days` 가 어긋나 있었다. 자료실·안내·현황공개인데 혼자 1년치였다.

##### 원인 — 두 규칙이 각자 맞는 일을 한다
창을 넓혀도 글이 안 들어왔다. 조기 종료(`seen_stop_pages: 2`)가 목록 1~2쪽이 전부 아는 글이면 멈추는데, 새로 받아야 할 옛 글은 12쪽 아래에 있다. 조기 종료는 매일 도는 증분 수집을 위한 것이고 창 확대는 한 번 하는 소급 수집이다 — 성격이 반대다.

##### 구현
`--only=<ids>` 를 추가해 지정 게시판만 `--full` 로 돈다. `--full` 만 쓰면 20개 전부의 조기 종료가 꺼져 보도자료 목록 1,987쪽을 걷는다.

`bcut`(게시판별 기준일)은 걸러진 목록이 아니라 `BOARDS` 전체로 계산한다. 걸러진 목록으로 만들면 안 훑은 게시판의 기준일이 전역 365일로 떨어져 `days: null` 게시판의 옛 글이 병합에서 통째로 탈락한다.

##### 결과

```
원천   4,937 -> 6,208건
그래프 Article 4,988 -> 6,282 · Attachment 5,985 -> 7,645
유형   안내 636->1,158 · 현황공개 146->854 · 자료실 510->557 · 소식 3,528->3,544
```

소식이 16건만 늘었다. 위험한 쪽(옛 보도자료가 후보를 미는 것)은 안 건드렸다.

##### 덤 — `--full` 이 죽던 버그
`limit = int(sys.argv[1])` 이 첫 인자를 무조건 숫자로 읽어서, `--full` 을 첫 인자로 주면 `ValueError` 로 죽었다. 주석에는 `--full` 로 적혀 있는데 실제로는 `0 --full` 로만 됐다. 아무도 안 써봐서 몰랐다.

## 6. 사람 결정을 파일로 — 약 250건

##### 문제
사람이 눈으로 보고 정한 값이 파이썬 딕셔너리로 아홉 파일에 흩어져 있었다. **누가 언제 왜 정했는지가 없다.** `external_org` 에 대법원을 넣을지 판단하려는데 기존 14개의 근거를 알 수 없어 처음부터 다시 확인해야 했다.

##### 택한 안 — 어휘와 결정을 가른다

```
그래프에 값으로 나타나면        ontology/schema.yaml vocabulary
사람이 개별 건을 판정한 것이면   decisions/*.yaml
값을 만들어 내는 방법이면        코드
```

##### 구현

```
어휘 46항목    CHANNELS 10 · GROUPS 12 · KINDS 4 · EXTERNAL_ORGS 14 · NO_ISSUE 3 · FACILITY 3
              -> vocabulary 4종 -> 11종

결정 250건     org_labels 29 · search_aliases 157 · places 35 · issuers 13 · aliases 7 · extraction 9
              -> decisions/*.yaml 6파일. why · decided · by 없으면 로드 중단
```

값을 손으로 안 옮겼다. 코드에서 AST 로 읽어 yaml 에 쓰고, 옮긴 뒤 다시 읽어 대조했다 — 백업이 있는 14건 전부 동일.

별칭은 **묶음마다** 근거를 달았다. 항목 하나하나가 아니라 범주 전체가 한 번의 판단이었기 때문이다.

##### 결과 — 검사 둘

```
형식 검사    why 를 빼고 로드 -> rc=1 "결정에는 근거(why)와 승인자(by)가 있어야 한다"
대상 존재    '장안구보건서' 오타 -> [주의] "조용히 아무 일도 안 한다"
```

`by: 미상` 으로 적었다. 누가 정했는지 실제로 모른다 — 그게 이 작업을 한 이유다.

## 7. 무회귀 확인 — `main.py --check`

##### 문제
리팩토링이 값을 안 바꿨는지 확인하려고 오늘 `main.py` 전체(20분)를 22번 돌렸다.

```

## 8. 목록 라우터 — 목차가 정책인 척한다

##### 문제
`청년 관련 정책 뭐가 있어` 가 23건을 내는데 가나다순이라 앞 5개가 분야 대문(`교육`·`복지·문화`·`일자리`·`주거`·`참여·권리`)이었다.

##### 기각 — `IN_DOMAIN` 집계 라우터
Domain 트리 76개를 적재해 놓고 검색이 안 타는 상태였다. 집계로 답하게 하려 했으나 실측에서 기각했다.

```
'청년' 도메인 8건   교육 · 복지·문화 · 일자리 · 주거 · 참여·권리 (목록 페이지 5)
                   관련사이트 · 청년지원센터 · 청누리
gold 정답          청년기본소득 · 청년 주거 패키지 지원 -> 복지 > 생애주기별에 있다
```

도메인 트리는 사이트 메뉴 구조지 정책 분류가 아니다. 집계로 답하면 지금보다 나빠진다.

##### 택한 안 — 열거에서 목록 페이지를 뺀다
목차 페이지는 목록의 항목이 아니다. 빼도 못 찾게 되지 않는다 — `CivilService` 는 `:Entity` 라 그 페이지를 직접 물으면 벡터 경로로 닿는다.

이름만으로 중복도 접었다. 전에는 `(name, content_type)` 이라 같은 이름이 `procedure`/`reference` 로 갈려 `청누리` 가 2건 나왔다.

##### 결과
23건 -> 16건, 전부 실제 민원. 답변 축(`answer_must: 청년기본소득` · `answer_not: 참여·권리`)이 판정한다.

## 9. 과설계 정리 — 아무도 안 지키는 숫자

##### 문제
`labels[].n`·`relationships[].n` 32개와 `properties[].coverage` 32개를 "규모 감각"으로 넣었는데, **같은 날 안에 32개 중 6개가 틀어졌다.**

```
Article    선언 6,282 · 실제 6,285
WORKS_AT   선언 5,137 · 실제 5,136   <- 유령 노드 지운 것이 반영 안 됨
```

##### 택한 안 — 지우되 지식은 남긴다
숫자 64개를 뺐다. `coverage` 는 "비어 있는 것이 정상인가"를 설명하는 값이라 `note` 7개로 바꿨다.

```
Employee.name             "사이트가 직원 이름을 안 싣는다. 기관장 6명만 있다"
CivilService.external_org "수원시 소관이면 비는 것이 맞다"
DocumentType.issued_at    "발급처를 판정 못 한 서류. 추측하지 않는다"
```

##### 순환 검사 깊이도 선언에서
`*1..12` 는 근거 없는 숫자였다. 추론 선언의 `depth` 를 읽어 `PART_OF` 6 · 나머지 8을 쓴다.

## 재사용 가능한 판단

- **선언이 검사를 만들면 선언을 고칠 때 검사 수가 변한다.** 그것이 온톨로지 구동의 증거다. 말이 아니라 숫자로 확인된다
- **판단을 코드에서 선언으로 옮기면 판단의 빈틈이 드러난다.** 동점 처리가 없다는 것을 옮기기 전에는 아무도 몰랐다
- **노드가 자기 것이 아닌 값을 주장하면 읽는 쪽을 아무리 단속해도 소용없다.** 프롬프트를 네 번 고쳐 네 번 실패한 이유다
- **하나만 막으면 옆으로 샌다.** 구비서류를 막으니 처리 장소로, 그것을 막으니 절차로 샜다
- **아무도 안 지키는 숫자는 감각이 아니라 오해다.** 넣은 지 몇 시간 만에 32개 중 6개가 틀어졌다
- **오탐이 쌓이면 검사가 무시당한다.** `max_requests` 를 넣자마자 산출물 순서 검사가 오탐을 냈고, mtime 대신 범위 지문을 비교하도록 고쳤다
- **기준선을 자동 갱신하면 그 검사가 무너진다.** `code_constants.json` 은 사람이 손으로 더한다. `quality.json` 과 반대 방침이다
- **쓸 데가 확인 안 된 규칙 종류는 만들지 않는다.** 만들어도 검증할 방법이 없다
- **`materialize: false` 는 "안 한다"가 아니라 "일부러 안 한다"는 선언이다.** 없으면 다음 사람이 다시 만든다
