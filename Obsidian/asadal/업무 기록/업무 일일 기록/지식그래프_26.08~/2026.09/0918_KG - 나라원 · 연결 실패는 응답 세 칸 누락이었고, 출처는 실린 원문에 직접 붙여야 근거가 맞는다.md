## 개념

- **`Capture`(수집원문)** — 한 번 받아 온 원문 파일 하나를 나타내는 노드. `capture_id` · `page_url` · `raw_url` · `sha256` · `saved_path` · `snapshot_id` · `fetched_at` 을 가진다. 원문 자체는 그래프에 넣지 않고 가리키기만 한다
- **`SOURCED_FROM`** — 도메인 노드(조직 · 사업 · 직원 …)에서 그 노드가 실려 있던 `Capture` 로 가는 출처 관계
- **`page_url`** — `raw_url` 에서 쿼리를 뗀 페이지 주소. "이 페이지에서 나온 것 전부"를 물을 때 쓴다(색인)
- **`uploads/`** — 사람이 넣는 입력(명단 등)을 모으는 폴더. 파일 뜻은 이름이 아니라 `manifest.jsonl` 의 `kind` · `as_of` 가 정한다
- **Chatty 필수 8칸** — Chatty `_validated_items` 가 근거 항목마다 요구하는 필드. `content` · `evidence_id` · `ontology_version` · `source_record_id` · `source_asset_id` · `source_location` · `source_sha256` · `source_url`

## 1. 개발 Chatty 연결 — 관문은 통과, 호출에서 실패

## 2. 연결 실패 원인 — 필수 3칸 누락과 버전 불일치

##### 실패로 처리되는 곳
Chatty `chat/nara1_graph.py` `search()` 는 예외를 로그 없이 삼키고 `graph_timeout` · `graph_response_unavailable` 두 가지로만 나눈다. 키는 양쪽이 같다고 확인했다. 그래서 남은 후보는 네트워크와 응답 형식 검사 탈락이었고, 코드 대조로 형식 쪽을 확정했다.

##### 원인 두 개

| | Chatty 가 보는 것 | Graph API 가 주는 것 |
|---|---|---|
| 필수 칸 | 8칸 모두 비어 있지 않음 | 3칸 없음(D15 에서 `SourceAsset` · `SourceRecord` · `Assertion` 층을 없애며 뺌, 계약 버전은 `"1"` 그대로) |
| 버전 | 응답 맨 위 `ontology_version` == 항목 버전 | 맨 위 = 서빙 코드 0.4.3, 항목 = DB `ReleaseHead` 0.4.2 |

조직 질문이 `outcome: ok` 로 오면 첫 번째에서 `incomplete evidence` 로, 고쳐도 두 번째에서 `invalid provenance` 로 떨어진다.

##### 검토한 안과 기각 사유
- Chatty `required` 에서 3칸 빼기 + 버전 비교 완화 — 기각. 남의 저장소 수정 요청이 필요하고, 우리에게도 "근거 원문을 지목하는 값"이 필요했다
- `evidence()` 에서 지금 있는 값(`unit_id` · `hashes[0]` · `source_url`)으로 임시로 채우기 — 기각. 뜻이 맞지 않는 값을 계약 칸에 넣게 된다
- **출처를 노드로 올려 세 칸을 실제 값으로 채우기 — 채택.** 버전 불일치는 재적재로 코드 · DB 가 같은 버전이 되면서 함께 풀린다

## 3. 출처 노드화 1차 — 0.5.0 (D56)

##### 설계 논의에서 정한 것
- **노드에서 출처 속성 3칸을 뺀다.** 노드로 옮기면서 속성을 남기면 이중 기록이다
- **관계의 출처는 속성으로 둔다.** 관계는 노드를 가리킬 수 없다. 노드로 올리려면 관계 761개를 옛 `Assertion` 구조로 승격해야 한다. 여러 출처는 이미 배열로 담긴다
- **`Snapshot` 라벨은 만들지 않는다.** 매니페스트에 완주 여부가 없다(delta-03 이 62줄인 이유를 알 수 없음). 노드로 둘 값이 없어 `Capture.snapshot_id` 속성으로 둔다
- **명단 파일도 수집원문으로 취급한다.** 예외를 두지 않는다
- 응답 세 칸 — `source_record_id` = Source id, `source_asset_id` = `Capture.sha256`, `source_location` = `saved_path`. 뜻이 옛것(페이지 안 행 번호)과 달라진 점은 D56 에 적었다

##### 구조와 결과

```
(도메인) ─SOURCED_FROM→ (:Source {source_url}) ─HAS_CAPTURE→ (:Capture {sha256, saved_path, snapshot_id, …})
```

라벨 · 관계 종류 10 · 8 → 12 · 10. 노드 · 관계 584 · 761 → 902 · 2,228(Source 27 · Capture 292 · `SOURCED_FROM` 1,175).

##### 검토에서 잡은 결함 2건
- **재수집하면 적재가 멈춤** — `plan.py:71` 은 릴리즈에 없는 노드가 DB 에 있으면 멈춘다(노드 삭제 미지원). 내용이 바뀐 재수집에서는 옛 `Capture` 가 후보에서 빠져 걸린다. 첫 게이트는 같은 수집본으로만 재적재해서 못 잡았다. → `carry_provenance()` 로 직전 릴리즈의 출처 노드를 빠짐없이 옮겨 온다
- **중복 검사가 넓게 풀림** — 출처 후보를 합치려 만든 `_unique` 가 도메인 노드까지 합쳐, 같은 노드를 두 번 만드는 버그를 조용히 넘겼다. → 합치는 대상을 출처 라벨 · 관계로 좁혔다

##### 곁가지 정리
- 내부 키 `SourceAsset.asset_id`(`nara1:asset:`) → `capture_id`(`nara1:capture:`) 이름 변경. 릴리즈 파일에 나가지 않는 이름이라 `unchanged: true`
- `Capture.byte_count` 제거 — 크기 대조는 매니페스트 파일 값으로 하고, 그래프 값은 읽는 곳이 없음(D48 기준)

## 4. 재수집 — 주소마다 가장 늦게 받은 원문 (D57)

##### 문제
`parsers/snapshots.py` `discover()` 는 회차 4개를 한 덩어리로 보고, 같은 주소가 다른 내용이면 멈춘다. 지금 회차들은 9/2 하루에 나눠 받은 조각이라 합쳐 보는 게 맞았다. 하지만 **재수집은 정의상 내용이 다르므로 새 회차를 넣는 순간 멈춘다.** 새 회차를 임시로 만들어 돌려 보고 확인했다.

##### 택한 안

```python
order = (item["fetched_at_utc"], snapshot.name)      # 받은 시각, 같으면 폴더 이름
if url not in latest or order > latest[url][0]:
    latest[url] = (order, snapshot, item)
found = {url: v for url, v in latest.items() if v[2]["http_status"] == 200}
```

- 새 회차에 없는 주소는 옛 회차 것을 그대로 쓴다(조각 수집 가능)
- 가장 늦은 응답이 404 면 고르지 않는다
- `answered_pages()` 신규 — 사라짐 판정 근거를 200 · 404 둘 다로 한다. **매니페스트에 줄조차 없는 페이지(수집이 끊김)만 멈춘다.** 수원에서 직원 22명이 폐지로 잡힌 사고(`last_seen != batch` → abolished)를 구조로 막는 형태다

## 5. 입력 폴더 통합 — `uploads/` (D58)

##### 문제
`parsers/roster.py` `latest_roster()` 는 폴더의 `*.xlsx` 중 **파일 이름의 날짜가 가장 늦은 것**을 명단으로 쓴다. 앞으로 프론트에서 파일이 올라와 같은 폴더에 섞이면 두 경우가 생긴다. 이름 규칙이 안 맞으면 적재 전체가 멈춘다. 날짜가 들어간 다른 엑셀이 오면 그걸 명단으로 읽는다.

##### 택한 안

```
snapshots/     사이트 수집 (크롤러)       깃 O
uploads/       사람이 넣는 것 전부        깃 O   ← 명단이 여기로
    2026-09-14-d161/
        manifest.jsonl   {"kind":"roster","as_of":"2026-09-14","sha256":…,"saved_path":"raw/…",…}
        raw/인원현황.xlsx
resolutions/   사람 결정                  깃 O
private/hr/    삭제
```

- 뜻은 `kind` 가, 기준일은 `as_of` 가 정한다. 명단은 `kind: roster` 중 `as_of` 가 가장 늦은 것
- 폴더 이름 = 날짜 + 해시 앞 4자. 한 번 넣은 파일은 고치지 않는다. 덮어쓰면 `Capture` 해시와 어긋나 멈추거나, 근거가 조용히 바뀐다
- `snapshots/` 와 섞지 않는다. `discover()` 가 그 안을 전부 사이트 페이지로 읽으려 한다
- 깃 제외는 하지 않았다. 명단도 이미 깃에 있고, 사내 Gitea 가 서버로 파일을 옮기는 유일한 길이다

##### 미룬 것
- **jsonl 파생물** — 표(엑셀 · CSV)에는 맞고 문서(PDF)에는 맞지 않는다. 만들더라도 원본은 그대로 두고 옆에 둔다. 표 종류가 둘 이상 들어올 때 만든다
- `kind: document` 처리 — 어느 노드로 만들지 기준이 없어 빈 껍데기를 만들지 않았다

## 6. 출처 노드화 2차 — `Capture` 에 직접 (0.6.0 · D59)

##### 문제 — 근거가 틀린 파일을 가리키고, `Source` 가 허브
0.5.0 을 운영에 넣은 뒤 캡처가 왜 이렇게 많은지 따졌다. 실적 게시판 3종(`cause02~04`)이 연도 탭 × 쪽으로 나뉘어 파일 268개(116 · 88 · 64)였다. 내용 중복은 0개다. 이어서 드러난 것:

- **사업 A 가 116개 파일 중 어디에 실렸는지 모른다.** 응답 세 칸은 정렬 첫 번째를 골라 엉뚱한 쪽일 수 있다. 조직도 페이지는 `Capture` 가 1개라 조직 조회에서만 안 드러났다
- **`Source` 가 허브가 된다.** `cause02` 하나에 사업 208 · 발주처 81 · 원문 116 이 달린다(차수 405). 운영 DB 실측으로 사업 하나의 2홉 이웃이 출처 포함 565, 제외 116 이다. "같은 게시판에 실렸다"는 관련성이 아니다

##### 검토한 안과 기각 사유
- 출처를 속성으로 되돌리고 `saved_path` 배열 추가 — 기각. 허브는 없어지지만 노드 ↔ 파일 짝이 끊기고 Chatty 칸이 여전히 대표값이다
- `(도메인) → Capture → Source` 로 화살표만 옮기기 — 기각. `Capture.raw_url` 에서 페이지 주소가 나오므로 `Source` 가 하는 일은 주소를 한 번 더 적는 것뿐이다
- `Capture` 라벨 이름을 `Source` 로 바꾸기 — 기각. 재수집하면 같은 페이지 노드가 더 생기고, 게시판은 지금도 한 페이지가 파일 여럿이다. `Source` 면 "출처 97개"로 읽히는데 실제 페이지는 27개다

##### 택한 안

```
0.5.0  (도메인) ─SOURCED_FROM→ (:Source) ─HAS_CAPTURE→ (:Capture) ×116
0.6.0  (도메인) ─SOURCED_FROM→ (:Capture {page_url, raw_url, sha256, saved_path, snapshot_id, fetched_at})
```

응답 세 칸: `source_record_id` = `capture_id`, `source_asset_id` = `sha256`, `source_location` = `saved_path`, `source_url` = `page_url`. 계약 `"1"` 그대로이고 Chatty 수정은 필요 없다.

##### 구현 중 조정
처음에는 노드마다 실린 파일을 전부 이어 관계가 5,894 로 늘었다. 같은 사업 행이 연도 · 쪽 파일 수십 개에 반복되기 때문이다. **노드마다 페이지당 원문 하나만** 가리키게 다듬어 `SOURCED_FROM` 1,175, `Capture` 97 이 됐다.

##### 결과

| | 0.5.0 | **0.6.0** |
|---|---|---|
| 라벨 · 관계 종류 | 12 · 10 | **11 · 9** |
| 노드 · 관계 | 902 · 2,228 | **680 · 1,936** |
| 근거 읽기 | 2홉 | **1홉** |
| 근거 정확도 | 어느 파일인지 모름 | **실린 파일 지목**(게이트에서 원문에 사업명이 있는지 확인) |
| 사업 2홉 이웃 | 565 | **138** |
| 게시판 원문 하나당 노드 | 405 | **최대 24** |

##### `Capture` 가 늘어나는 조건
키가 주소 + 내용 해시라 **안 바뀐 페이지는 다시 받아도 그대로**다. 1바이트라도 다르면 새 노드가 생긴다. 도메인 노드는 증분으로 덮어쓴다. 옛 `Capture` 를 주소 단위로 덮어쓰지 않는 이유는 추적 때문이다. 사라진 조직 · 퇴사자가 "마지막으로 본 원문"을 가리키는데, 덮어쓰면 그 근거가 조용히 거짓이 된다. `ReleaseHead` 매니페스트는 노드별 출처를 담지 않고 현재 릴리즈 하나만 기록해서 이 역할을 대신 못 한다.

## 7. Chatty 권한 방식 조사

나라원 허용 목록이 Chatty 안에서 이례적인지 확인하려고 다른 기능의 제한 방식을 조사했다. **권한 체계는 없다.**

| 방식 | 예 |
|---|---|
| 코드에 박힌 챗봇 UUID 목록 | `ai_search/vector/support.py:461,477` |

## 재사용 가능한 판단

- **연결 실패가 조용히 삼켜지면 양쪽 계약을 칸 단위로 대조한다.** 키 · 네트워크보다 "한쪽만 필드를 뺀 것"이 먼저다. 필드를 빼면 계약 버전도 올려야 한다
- **소비자 계약을 바꾸기 어려우면, 제공 쪽이 칸을 뜻 있는 값으로 채운다.** 억지 값으로 채우지 않는다
- **출처는 "실제로 실려 있던 원문"을 가리켜야 근거다.** 페이지 단위로 묶으면 한 층 미뤄질 뿐 짝이 끊긴다
- **공통 부모 노드는 허브가 된다.** 출처 관계는 근거를 읽을 때만 나가는 방향으로 한 번 탄다. 관련 탐색에서는 타지 않는다
- **라벨 이름은 재수집 뒤에도 참이어야 한다.** 여러 번 생기는 것을 "출처"라 부르면 개수가 거짓말을 한다
- **게이트는 입력이 바뀌는 상황도 시험한다.** 같은 수집본 재적재만으로는 재수집 결함을 못 잡는다
- **파일 뜻을 이름에서 추측하지 않는다.** 넣는 쪽이 아는 정보(`kind` · `as_of`)를 매니페스트로 받는다
- **읽는 곳이 없는 칸은 두지 않는다.** 필요해지면 그때 넣는다(`byte_count` · `Source` · `Snapshot`)

## 한계

- **API 릴리즈 배포 뒤 확인이 기록에 없다.** 운영 DB 는 0.6.0 이고, 옛 코드면 `/health/data` 가 503 이다. 배포 뒤 세 칸 · ready 를 확인해야 한다
- **프론트에서 그래프 모드가 실제로 붙는지는 아직 못 봤다.** 9000 → Graph API 서버 간 통신(방화벽)도 확인 전이다
- **재수집을 실제로 해 보지 않았다.** 임시 복사본으로 두 경우만 시험했다. 페이지가 바이트 단위로 안정적인지(방문자 수 · 날짜 박힘)도 모른다
- **수집기 쪽 3종을 미뤘다.** `run.json`(완주 여부) · 변경 감지 · 바이트 안정성 측정은 재수집을 시작할 때 같이 한다
- **`source_record_id` 는 `page_url` 과 사실상 중복이다.** Chatty 가 필수에서 뺄 때 정리한다
- **Chatty 버전 비교(맨 위 == 항목)는 그대로다.** 다음 필드 추가 버전에서 서빙을 먼저 배포하면 같은 불일치가 다시 난다
- **`Capture` 정리 규칙과 노드 삭제가 없다.** 아무도 안 가리키는 옛 원문도 옮겨 와 쌓인다
- **서버에서 적재하는 경로는 여전히 없다**
