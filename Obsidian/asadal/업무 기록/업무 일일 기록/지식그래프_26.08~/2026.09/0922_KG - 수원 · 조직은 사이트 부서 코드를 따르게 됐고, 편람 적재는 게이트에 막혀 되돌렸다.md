## 개념

- **`org_live.json`** — 조직도 크롤러(`scraping/00_fetch_org.py`)가 매번 사이트에서 새로 받아 만드는 조직·직원 명단. 오늘부터 그래프 조직 뼈대의 유일한 원천
- **부서 코드** — 수원시 조직도 HTML 이 국·과·팀·동마다 붙이는 고유 번호(`hyper_grp_<코드>`). 그래프가 원래 쓰던 조직 ID 와 같은 체계
- **민원사무편람** — 부서·동마다 "처리하는 민원 목록과 처리 기준"(담당팀 · 연락처 · 근거법령 · 구비서류 · 처리기한 · 수수료)을 적어 분기마다 게시판(`bbsCd=1027`)에 올리는 한글 파일. 수집기(`scraping/13`)는 있었지만 적재 단계가 없었다
- **관리번호** — 편람 항목 번호. "실국 순번 - 과 순번 - 민원 순번"이고 부서 편람 안의 목차 번호다
- **신뢰 계산** — 검색 후보 점수가 기준(0.74) 미만이면 옆 민원의 서류 · 처리 장소를 답변에서 감추는 안전장치(9/7 도입)

## 요약

**조직 · 직원이 8월에 멈춘 고정 파일(`org_chart.json` 8/18, `org_teams.json` 8/28)에 묶여 있던 것을, 매번 사이트에서 새로 받는 `org_live.json` 을 따르게 바꿨다.** 조직 ID 는 사이트 부서 코드를 그대로 쓴다. 그래프 조직 940개 중 938개가 이미 같은 코드여서 ID 를 바꾸지 않았다. 정책실(폐지 상태)과 부속실(없음)이 제자리에 들어갔고, 사이트에만 있던 직원 23명이 0명이 됐다. 조직도 HTML 캐시는 없앴다.

게이트에서 계속 떨어지던 "출생신고 어떻게 해"의 원인을 찾다가, **창구 민원 1,107종이 편람에 있는데 적재되지 않고 있었음**을 발견했다. 편람을 LLM 없이 규칙으로 읽어 `CivilService` 노드로 넣는 단계를 만들고, 파싱 품질을 네 차례 보정한 뒤 적재했다. 창구 민원 답은 크게 좋아졌다. 하지만 **기존 질문 5개가 나빠져 품질 게이트가 막았고, 그래프를 넣기 전 백업으로 되돌렸다.** 원인 중 신뢰 계산 결함은 오늘 고쳤다.

## 1. 조직도 수집 — 캐시 제거

##### 문제
`00_fetch_org` 는 받은 HTML 을 `data/raw/org/html/` 에 저장하고, **다음 실행에 날짜 확인 없이 재사용**했다. 재수집해도 옛 페이지를 다시 읽었다. 다른 수집기는 매번 새로 받거나(`01` 민원 · `13` 편람), 최근 1개월 글만 다시 받는다(`12` 게시판).

##### 검토한 안과 기각 사유
- 저장본에 6일 유효기간 — 기각. "6일이 적당한가", "스케줄이 밀리면" 을 계속 따져야 한다
- 매번 새로 받되 HTML 은 기록으로 저장 — 기각. `org/html/` 을 읽는 코드가 자기 자신뿐이고, 폐지된 부서 파일은 쌓인다

##### 택한 안과 결과
항상 사이트에서 받고 저장하지 않고 바로 파싱한다. 232페이지 · 2~5분 · LLM 없음이라 비용이 작다. 페이지를 3번 시도해도 못 받거나 결과가 직전보다 10% 넘게 줄면 파일을 쓰지 않고 멈춘다(오늘 수집 중 실제로 1페이지 네트워크 실패). `data/raw/org/` 는 103MB → 3.4MB 로 줄었다. 안 쓰는 게시글 `.bak` 4개(약 30MB)도 지웠다.

| | 어제(9/21) | 오늘 |
|---|---|---|
| 페이지 · 조직 · 직원 | 231 · 939 · 5,109 | 228 · 939 · 5,110 |
| 수원시 API 대조 | 99.9% | 99.8%(API 는 하루 전) |

사라진 페이지 3개는 다른 페이지에 이미 있는 팀 표만 다시 싣던 페이지였다(중복 행 757 → 742).

## 2. 조직 뼈대를 사이트 부서 코드로

##### 문제 — 뼈대는 고정 파일, 새 명단은 직원 동기화에만

| 상황 | 동작 | 실제 |
|---|---|---|
| 새 조직(고유한 이름) | `load_new_orgs()` 가 만든 뒤 다음 실행에 "이미 있음"으로 건너뜀 → 배치 날짜 없음 → `lifecycle/01` 이 폐지 | 정책실이 `…#정책실` ID 로 폐지 상태 |
| 새 조직(이미 있는 이름) | 새 조직으로 인식 안 됨 | 부속실 없음, 직원 누락(`validate/06` 경고 23명, 파이프라인은 통과) |
| 없어진 조직 | 고정 파일이 매번 다시 적재돼 모든 조직에 오늘 날짜가 찍힘 | 폐지되지 않음 |

크롤러 키(`페이지코드#팀이름`)가 그래프 ID 와 달라 `nodes/14` 가 이름 · 담당업무로 추측해 짝을 지었다.

##### ID 기준 — 검토한 안
- `페이지코드#이름` · API 전체 경로 — 기각. 조직 이름이 바뀌거나 개편되면 ID 가 바뀐다
- 임의 번호 — 기각. 사이트와 매번 다시 짝을 지어야 한다. 9/9 재직자 22명 퇴직 처리 사고가 이 짝짓기에서 났다
- **사이트 부서 코드 — 채택.** 수원시가 직접 매겨 동명 팀(행정민원팀 44곳, 비서실 3곳)도 구분된다. 조직에 걸린 관계 약 1만 2천 개(소속 5,267 · 게시글 담당 4,161 · 민원 담당 700 · 민원 소관 583 · 상하 938)가 그대로 산다

##### 상위 조직 읽기 — 코드 반영 전 측정
HTML 제목이 전부 같은 `<h4>` 라 순서로 읽는다. 과 블록(주요업무 · 위치 · 팩스 표) 뒤의 팀은 그 과 소속이고, 과의 상위는 페이지 주인이다. 45개는 조직도 트리(`<ul>/<li>`)에서 채웠다.

```
상위 관계 938개 대조   일치 932 · 불일치 0 · 못 정함 5
부서 페이지와 트리가 둘 다 알려주는 185개   전부 같은 답
```

못 정한 5개(구 4개 → 시장, 의회사무국 → 지방의회)는 사이트 어디에도 상위가 없어 `decisions/org_labels.yaml` 에 고정값으로 적었다.

## 3. 직원 식별 — 지금 방식 유지

직원 ID 는 두 형식(`조직코드_번호` 4,981명, `live_해시` 129명)이 섞여 있지만 이름표일 뿐이다. 매칭은 **같은 조직 안에서 전화번호, 없으면(약 9%) 담당업무**로 한다.

- **업무를 매칭 키에 넣지 않는다.** 업무 끝에 마침표 하나만 붙어도 5,052명이 물갈이되고, 전화번호만 쓰면 417명으로 92% 준다(주석 실측). 업무는 갱신 대상이다
- **전화번호는 사람이 아니라 자리를 따라간다.** 8/28과 오늘 둘 다 있는 번호 4,181개 중 같은 조직 4,172개(99.8%), 다른 조직 9개. 조직을 넘는 이동은 퇴직 + 입사로 처리되며, "지금 누가 하나"에는 영향이 없어 두었다
- 사이트는 5,110명 중 6명만 이름을 싣는다. 다른 곳에서 이름을 모으는 안은 개인정보 문제로 기각

첫 실행: 유지 5,075 · 신규 32 · 복귀 3 · 폐지 4 · 갱신 86, 임베딩 다시 만든 직원 118명.

## 4. 게이트 "출생신고 어떻게 해" — 원인과 편람 발견

##### 원인
수원시 사이트에 출생신고 페이지가 없다. 검색되는 옆 민원(출산 지원)의 처리 장소를 감추는 9/7 안전장치와, 답변에 "행정복지센터"를 기대하는 게이트 문항이 충돌했다. 8번 중 1번 통과였고, 기준값 7점은 그 1번에 찍힌 값이다. 오늘 작업과 무관하다(아침 백업 DB 로도 4번 중 0번).

##### 검토한 안
- 사람이 확인한 "수원시 밖 절차" 스텁 — 보류. 기한 · 접수처를 지어낼 위험이 있다
- 안전장치 완화 — 기각. 모든 민원 답변에 영향
- 게이트 기대값만 변경 — 기각. 시민은 여전히 답을 못 받는다
- 정부24 수집 — 보류. 수집 데이터 안에 이미 있는지부터 확인

##### 발견
`scraping/13` 이 매달 받는 편람(`manuals.json`)을 **그래프에 넣는 코드가 없었다.**

```
편람 속 민원 1,107종 · 그래프 민원 노드 644개 · 이름 겹침 11개
출생신고 77건 · 사망신고 77 · 전입신고 68 · 확정일자 68 · 혼인신고 9  → 그래프 0
```

8/27 에 "수원시 소관 밖이라 페이지가 없다"고 정리한 창구 민원이 편람에 다 있었다. 민원서식자료실(글 469 · 첨부 844)은 서식 이름과 링크뿐이고, 종합민원 안내 45쪽은 목록이 아니다. 전자민원은 첫 화면이 로그인이다. **수원시에서 민원 종류를 처리 기준과 함께 모아 둔 곳은 편람뿐이다.**

## 5. 편람 적재 설계

##### 규칙 추출 가능성 측정
편람 항목 7,909개 → 고유 민원 986종. 칸별 채움률 담당팀 99% · 근거법령 99% · 구비서류 97% · 연락처 96% · 처리기한 95%, 핵심 5칸 모두 93%. **LLM 없이 칸 제목으로 자른다.** 홈페이지 민원 644페이지는 자유 글이라 LLM 으로 추출하지만(`scraping/02·03·04·06·07`) 편람은 양식이다.

##### 민원 ID — 관리번호 기각, 민원명 채택

| | 관리번호 | 민원명 |
|---|---|---|
| 부서 간 | 2026-2분기 번호 954개 중 92개가 다른 민원에 겹침(부서마다 따로 매김) | — |
| 분기 간 | 같은 부서 · 같은 민원 1→2분기 97% 유지, 조직개편 때 실국 순번이 통째로 바뀜(`13-…` → `12-…`) | 38개 부서 738종 중 90% 그대로, 표기만 바뀐 것 0, 이름 변경 2 |

처음에는 관리번호를 "연도-분기-순번"으로 추측했다가 사용자 지적으로 다시 쟀다. 관리번호는 보조 단서로 남긴다. **같은 부서 · 같은 관리번호인데 이름만 바뀌면 같은 노드로 잇는다.**

##### 구조
- 라벨은 기존 `:CivilService`, `source_type = manual`. 검색 · 임베딩 · 답변 조립이 모두 이 라벨 기준이다
- 원천은 **부서별 최신 판**. "최신 분기만" 쓰면 이번 분기에 안 올린 부서 민원이 사라진다(2026-1분기 67건, 2분기 114건)
- 구청판과 동판은 역할이 다르다(구청 약 7일 · 제44조 / 동 경유 즉시 · 제21조 · 신분증 추가). 민원명이 같으면 한 노드로 두고, **창구마다 다른 값(처리기한 · 연락처 · 관리번호)은 `HANDLED_BY` 관계 속성**으로 둔다
- 담당부서는 연락처 → 그 번호를 쓰는 직원 → 그 조직(창구 3,112개 중 88%). 오늘 조직을 코드로 맞춰서 가능해졌다
- 홈페이지 민원과 이름이 같으면 새로 만들지 않고 빈 칸만 채운다

| 칸 경계 — "담당 공무원 확인사항" 변형 · 신청서 양식이 칸에 섞임 | 변형 2개(정확히 일치)만 추가, `(앞쪽)` · `(서명 또는 인)` · `210mm` 등이 나오면 다음 칸까지 버림 | 양식 섞임 116 → 0, 새로 빈 칸 0 |
| 처리기한 괄호가 무조건 떼어짐 | 전체가 괄호로 감싸진 경우만 뗌 | 짝 안 맞음 122 → 2(원문 자체) |

칸 경계 보정 중 기각한 안: "칸 제목으로 **시작하면** 제목" — "구비서류 확인 및 검토"(75) 같은 절차 문장 수백 줄에서 칸이 끊긴다. "업무개요" 변형 — 빈 개요 6건에 총괄표 내용이 들어갔다. `□ 구비서류` 기호 제목 — 520건 중 517건에 표준 제목이 따로 있다. "접수번호" 양식 표시 — 정상 문장에서 잘렸다. 전부 규칙을 임시로 적용해 전후를 비교한 뒤 정했다.

## 7. 적재 → 게이트 실패 → 되돌림

DB 백업(245MB) 후 `main.py` 로 적재했다. 편람 민원 877개 + 홈페이지 민원 10개 빈 칸 채움.

##### 좋아진 것

| 질문 | 전 | 후 |
|---|---|---|
| 사망신고 필요한 서류 | 서식 링크만 | 서류 · 동 행정복지센터 · 1개월 이내 · 수수료 없음 |
| 혼인신고 뭐 필요해 | "확실한 답을 찾을 수 없습니다" | 신분증 · 증인 2인 · 미성년 동의 · 약 7일 |
| 전입신고 어떻게 해 | "행정민원팀"까지 | 서류 · 14일 이내 · 즉시 처리 |
| 출생신고 어떻게 해 | "자료에서 찾을 수 없습니다" | 거주지 관할 동 + 담당 전화 |

서식 연결 1,144개(관련 없는 서식이 붙음), 규칙 위반 경고 121 → 1,001 도 나왔다. 개발 챗봇에 나빠진 답이 노출되지 않게 **넣기 직전 백업으로 되돌렸다.** `main.py` 의 편람 단계는 주석으로 빼 두었고 코드와 `manual_civil.json` 은 남아 있다. 오전의 조직 · 직원 작업은 그대로다.

## 8. 원인 분석과 신뢰 계산 수정

- **위반 1,001건** — 편람의 "업무처리 세부설명도"(접수 → 검토 → 결재 → 교부)를 정리 단계에서 버려 877개 대부분이 "절차 민원인데 절차 없음"
- **출생신고 답에 서류가 안 나옴** — 처음에는 "본문이 딱딱해 점수가 낮다"(0.52)고 판단했으나 틀렸다. 검색 코드는 코사인을 0~1로 바꾼 점수를 쓴다. 실제 점수 0.761로 기준을 넘는다. 진짜 원인은 **신뢰 계산이 글자 매칭 후보를 무조건 빼서**, 이름이 정확히 맞는 정답 노드가 빠지고 옆 후보 점수로 판정된 것이다(출생신고 옆 후보 최고 0.721 → 감춤, 전입신고는 운 좋게 0.799 → 보여줌)

`search/pipeline.py` 에서 표시(글자 매칭 등)가 아니라 **벡터 점수 유무로** 거르게 고쳤다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 운영 DB(홈페이지 민원만) 1위 적중 · 정밀도 · 첨부 · 장소 | 17/17 · 83/227 · 4/4 · 3/3 | 같음 |
| 임시 DB(편람 있음) 출생신고 어떻게 해 | 서류 감춤 | 서류 5종 표시 |
| 확정일자 어디서 받아 | 감춤 | 감춤(자기 점수 0.724 < 0.74) |

## 재사용 가능한 판단

- **싼 단계는 매번 전체, 비싼 단계만 증분.** 수집 2~5분을 캐시로 아끼다 옛 데이터가 조용히 들어갔다
- **ID 는 원천이 직접 매긴 코드를 쓴다.** 이름 · 업무 추측 짝짓기는 사고가 난 자리다
- **새 추출 규칙은 코드 반영 전에 현재 그래프와 전수 대조한다.** 불일치 0을 보고 옮겼다
- **"없다"고 결론 내기 전에 이미 받아 둔 데이터를 뒤진다.** 페이지가 없다던 창구 민원이 수집만 되고 적재 안 된 편람에 있었다
- **번호가 ID 인지 가정하지 말고 부서 간 · 분기 간으로 잰다.** 목차 번호는 개편 때 통째로 바뀐다
- **파싱 규칙을 넓힐 때는 임시 적용해 전후를 전부 비교한다.** "시작하면 제목"은 절차 문장 수백 줄을 끊었을 것이다
- **새 원천을 넣으면 기존 질문 순위부터 본다.** 좋아진 질문만 보면 밀려난 정답을 놓친다
- **점수 판단 전에 코드가 쓰는 점수 단위를 확인한다.** 코사인과 0~1 변환 값을 섞어 원인을 잘못 짚었다
- **안전장치의 제외 조건은 표시가 아니라 값으로 건다**

## 한계

- **편람은 그래프에 없다.** 다시 켜려면 이름만 다른 같은 민원 합치기, 편람 민원의 후보 독차지 제한, 서식 연결 강화, 절차 표 읽기가 필요하다
- **게이트 "출생신고 어떻게 해"는 여전히 대부분 실패한다.** 편람이 들어가야 풀린다. 그 전까지 매 실행 게이트가 빨간불이다
- **확정일자는 편람을 넣어도 기준 0.74에 못 미친다.** 기준은 홈페이지 민원 기준으로 잡혀 있다
- **팔달구 종합민원과 PDF 편람을 읽지 않는다.** 수집기는 한글 파일 없는 글을 기록하지도 않는다
- **주간 수집 경로(`--collect=weekly`) 전체는 돌려 보지 않았다.** 오늘 고친 `scraping/08` 실행 검증 전이다
- **주요업무 표가 사라진 조직 7곳은 옛 값이 남아 있다**
- **git 저장소가 아니다.** 고치기 전 파일과 DB 백업이 세션 임시 폴더에 있다
- **조직을 넘어 이동한 직원은 같은 사람으로 이어지지 않는다**
