## 개념

- **ingress** — 다른 담당이 오늘 넣은 관리자 승인 수집 경로(PR #19). URL 을 등록하면 본문을 받아 LLM 이 엔티티·관계를 뽑고, 관리자가 승인하면 **운영 Neo4j 에 바로 게시**한다. Graph API 서버 안에서 돌고, 검토 기록은 PostgreSQL 에 남는다
- **`validate(existing=...)`** — ingress 가 추가한 검증 인자. 직전 릴리즈와 **완전히 같은** 노드·관계는 개별 검증을 건너뛴다. 스냅샷 없이 적재하기 위한 것이고, 기본값이 비어 있어 우리 적재 동작은 그대로다
- **변경 명령** — 온톨로지 자동화에서 LLM 이 내는 제안의 형식. JSON 전체가 아니라 `{어휘에 값 추가, rank, 수석연구원}` 같은 한 건
- **추가형 변경** — 기존 정의를 건드리지 않고 옆에 붙이는 변경(어휘 값 · 동의어 · 선택 속성 · 새 라벨 · 새 관계). "옛 버전 ⊆ 새 버전"을 기계가 검증할 수 있다
- **확장 → 이전 → 축소** — 이름 변경 같은 구조 변경을 추가와 삭제로 쪼개는 방법

## 요약

**오늘 적재 쪽 코드는 한 줄도 바꾸지 않았다.** 새 브랜치를 main 에 맞춰 두고, 어제 이후 들어온 남의 PR 12개(#13~#25)를 읽고, 앞으로의 구조를 정하는 논의를 했다.

어제 조회 담당자에게 넘긴 5건 중 4건이 **조회 쪽에서 보강됐다.** 웹사업부 이름 겹침은 우리가 "구조적으로 자연스럽다"고 본 방식 그대로 **회사 조건을 관계로 확인**하는 식으로 풀렸다. 그래서 내가 제안했던 적재 쪽 0.6.3(`name_key` · `company` 속성)은 **필요 없어졌다.**

대신 **ingress(PR #19)가 운영 DB 에 쓰는 두 번째 경로**를 만들었다. 우리 적재기는 원천만으로 그래프 전체를 다시 만들기 때문에, ingress 가 넣은 것을 "사라진 것"으로 보거나 삭제 규칙에 걸려 멈춘다. **운영에서 둘을 섞어 돌리기 전에 영역을 나눠야 한다.**

오늘의 큰 줄기는 **온톨로지를 관리자가 프론트에서 어디까지 바꿀 수 있나**였다. 결론은 **추가형까지**다. LLM 은 변경 명령만 제안하고, 사람이 승인하고, 코드가 적용과 검증을 한다. 기존 정의가 변질되지 않는다는 것은 "옛 버전 ⊆ 새 버전"과 "차이 = 승인한 명령"을 집합 비교로 증명한다. 구조 변경은 적재·조회 코드가 이름을 직접 쓰고 있어 개발자가 필요하다. 논의는 `asadal/KG - 온톨로지 자동화 정도` 노트로 정리했다.

그 밖에 그래프 시각화 화면을 검토했고(**NVL 은 라이선스 때문에 탈락, Sigma.js**), KGreference 코드에서 가져올 것을 가렸다.

## 2. ingress — 운영 DB 에 쓰는 두 번째 경로

##### 무엇인가
URL 등록 → 본문 수집 → LLM(Qwen) 추출 → 관리자 검토 → 승인 → **운영 Neo4j 게시**. 게시할 때 **우리 적재기 부품을 그대로 쓴다**(이전 릴리즈 읽기 · 검증 · 쓰기 · 되읽기). 직전 릴리즈에 승인분을 **덧붙여** `release_seq` 를 +1 한다. Graph API 서버 안에 붙어 돌고 별도 워커는 없다.

##### 부딪히는 점

| | 내용 |
|---|---|
| **① 그래프를 만드는 방식이 다르다** | ingress 는 "직전 그래프 + 승인분", 우리는 **원천만으로 전체 재생성**. ingress 가 한 번이라도 게시한 뒤 우리 적재를 돌리면 그 노드들이 `removed` 가 되거나 삭제 규칙에 걸려 멈춘다. **나중에 쓴 쪽이 이긴다** |
| ② 공용 검증 함수가 바뀜 | `validate(existing=...)`. 기본값이 비어 있어 우리 동작은 그대로지만, 핵심 검증 코드를 다른 쪽이 고쳤다 |
| ③ 운영 이미지에 `ingestion/` 이 들어감 | Dockerfile `COPY` 추가. 어제 만든 서버 실행 명령은 그대로 동작한다 |
| ④ `.env` 에 PostgreSQL 계정이 커밋됨 | 이 저장소는 `.env` 를 일부러 커밋하는 정책이지만 비밀번호가 늘었다. 값은 열지 않았다 |

##### 검토한 안

| 안 | 내용 | 판단 |
|---|---|---|
| **A. 영역을 나눈다** | 우리 적재는 원천에서 온 것만 다시 만들고, `ingress:` 키 노드와 그 관계는 그대로 가져간다(carry) | **가장 현실적.** ingress 를 운영에서 켜기 전에 이게 돼야 한다 |
| B. 순서로 맞춘다 | 승인 기록을 `uploads/` 처럼 입력으로 받아 매번 다시 읽는다 | 구조 변경이 크다 |
| C. 당분간 하나만 쓴다 | 한쪽을 멈춘다 | 임시 |

지금 운영은 seq 3 그대로이고 ingress 노드는 없다. **정하기 전까지 둘을 섞어 돌리지 않는 것**이 가장 중요하다.

## 3. 두 갈래 적재 — 크롤링 증분과 승인 게시

사용자가 정리한 방향(파일·URL 은 LLM 제안 + 관리자 승인, 크롤링은 증분)에 동의했다. 크롤링 증분은 **이미 대부분 돼 있다** — 원문 해시로 바뀐 페이지만 파싱하고(추출 캐시) 달라진 것만 쓴다. 남은 건 스케줄뿐이다.

공존하려면 정해야 할 것:

- **영역 분리**(위 A안). 구분은 출처로 한다 — 크롤링·명단은 수집본 `Capture`, 승인분은 `ingress:` 키
- **겹칠 때 규칙.** 승인분이 기존 크롤링 노드에 **속성을 덮지 못하게** 하고 관계만 추가하는 게 깔끔하다. 크롤링 노드가 사라지면 거기 붙은 승인 관계를 어떻게 할지도 정해야 한다
- **승인분 삭제.** 잘못 승인한 것을 되돌리는 흐름이 필요하다
- **쓰는 곳 잠금.** 지문 확인으로 섞이지는 않지만 실패한 쪽은 다시 돌려야 한다

##### 정형 파일에는 LLM 을 어디에 쓰나
양식이 바뀌거나 전혀 다른 파일이 올 수 있으니 LLM 이 필요하다. 다만 **행마다 값을 읽게 하지 않고 양식을 해석하는 데만** 쓴다.

```
① 아는 양식인가(머리행 지문) → 알면 저장된 연결표로 바로 파싱, LLM 안 씀
② 모르면 LLM 에게 머리행 + 샘플 몇 줄만 → "직원 명단, 성명=name …" 제안
③ 관리자가 연결표 확인·수정·승인 → 양식으로 저장
④ 파서가 전 행을 읽음 → 미리보기 → 승인 → 적재
```

값은 원본 칸에서 그대로 오니 정확하고 재현된다. 명단 전체가 외부 모델로 가지 않는다. **지금 명단 파서가 사실 이 연결표를 코드에 적어 둔 것**이고, 9/28 에 옛 15칸과 새 12칸을 둘 다 읽게 만든 게 사람이 ②를 한 셈이다.

## 4. 온톨로지 자동화 — 어디까지 관리자에게 열 수 있나

##### 층을 나눠야 한다

| 층 | 예 | 누가 |
|---|---|---|
| 데이터 | 직원 추가 · 퇴사 · 관계 승인 | 관리자(프론트) |
| 양식 연결표 | "이 엑셀의 `휴대폰` = mobile_phone" | 관리자(LLM 제안) |
| **온톨로지** | 새 라벨 · 관계 · 속성 · 어휘 | **지금은 개발자(코드 → 승격 → 배포)** |

연결표는 **이미 있는 속성에만** 연결한다. 없는 대상을 만나면 멈추고 보고한다.

##### 지금 개발자가 필요한 이유
온톨로지가 코드 파일이고, 버전이 코드 상수이며, 조회 코드가 라벨·관계·숨길 속성을 직접 알고 있다(`SEARCH_LABELS` · `RELATION_MEANINGS` · `HIDDEN_PROPERTIES` · 살아 있음 조건). 즉 **온톨로지 밖에 흩어진 지식**이 개발자를 부른다.

##### 승인 즉시 반영하려면

```
관리자 승인
 → ① 규칙 검사  → ② 섀도우 시험 적재 + 예시 질문 → ③ 저장소에 새 버전 기록
 → ④ 한 트랜잭션으로 운영 전환(제약·인덱스 + ReleaseHead 의 온톨로지 버전)
 → ⑤ 조회는 요청마다 ReleaseHead 버전을 보고 그 버전 스키마를 읽음 (재배포 없음)
```

막고 있는 것은 넷이다 — 온톨로지가 git 파일, 버전이 코드 상수, 조회가 **코드 버전과 DB 버전의 일치**를 요구, 조회가 스키마를 **서버 시작 때 한 번만** 읽음. ④가 한 트랜잭션이면 **지금 겪는 "적재와 릴리즈 사이 공백"도 사라진다.**

##### 변질되지 않는다는 것을 어떻게 증명하나
LLM 에게 JSON 전체를 주고 "여기에 추가해서 돌려줘"라고 하면 위험하다. 그래서:

- **LLM 은 JSON 을 만지지 않는다.** 변경 명령만 낸다. 기존 JSON 은 주지도 받지도 않는다
- 승인되면 **코드가** 옛 JSON 을 읽어 **그 명령만** 적용한다. 허용 명령에 "기존 항목 수정·삭제"는 아예 없다
- 저장 전에 자동 비교한다

```
옛 버전의 모든 항목 ⊆ 새 버전          (하나라도 빠지거나 바뀌면 거부)
새 버전 − 옛 버전 = 승인한 명령        (명령에 없는 추가도 거부)
"−"(삭제)나 "~"(값 변경) 항목이 있으면  추가형 명령뿐이면 거부
```

적용하는 코드와 검사하는 코드가 **방식이 다르다.** 적용은 명령을 실행하고, 검사는 결과와 옛 것만 보고 차이를 계산한다. 그래서 적용 버그 · 직렬화 사고 · 저장소 직접 수정까지 잡는다. 옛 버전은 덮어쓰지 않고 버전마다 새로 저장하며 해시로 고정한다.

##### 가능 범위

| 변경 | 지금 구조 | 이름을 온톨로지에서 읽는 구조 |
|---|---|---|
| 추가형(어휘 · 동의어 · 선택 속성 · 새 라벨 · 새 관계) | 저장소만 옮기면 관리자 가능 | 관리자 |
| 이름 변경 · 선택 속성 삭제 | 개발자 | **관리자 가능**(확장 → 이전 → 축소) |
| 단순 타입 변환 | 개발자 | 관리자 + 변환 실패 시 멈춤 |
| 의미가 바뀌는 변경(나누기 · 합치기) | 개발자 | **개발자**(판단) |
| 업무 규칙이 닿는 변경(카디널리티) | 개발자 | **개발자**(로직) |
| 키 변경 | 개발자 | **개발자**(정체성) |

9/28 을 예로 들면 어휘 추가는 관리자 영역이고, `MEMBER_OF` 를 겸직 허용으로 바꾼 것만 구조 변경이었다(퇴사 판정 · 속성 합치기를 같이 고쳐야 했다).

##### 라벨 의미 중복 — 진짜 위험
관리자가 라벨을 쉽게 추가하면 `Certification` · `License` · `Qualification` 이 따로 생긴다. 같은 사실이 흩어지고 조회 LLM 이 헷갈린다. 합치기는 "의미 판단 + 키 변경"이라 **개발자가 필요한 구조 변경**이라서, **생긴 뒤 고치는 것보다 추가 시점에 막는 게** 훨씬 싸다.

- 제안서에 **비슷한 기존 항목과 재사용 안 되는 이유**를 필수 칸으로
- 이름 · 한국어 이름 · 동의어가 겹치면 **규칙으로 거부**(정규화 후 비교)
- 설명 · 예시 질문을 임베딩해 **유사도 경고** → 상위 권한자 승인
- 새 라벨보다 **속성이나 어휘 값**을 먼저 권한다
- 라벨 · 관계 추가는 권한을 나누고 분기마다 점검

**규칙은 이름 겹침만 확실히 잡고, 뜻 겹침은 사람 판단이다.**

##### 결론
A(개발자만) · B(추가형만 관리자) · C(라벨·관계까지)를 비교했다. 사용자 말대로 **위험 때문에 A 가 나을 수도 있다.** 절충은 **수정은 개발자만 하고 프론트에는 LLM 초안이 붙은 "변경 요청"만** 두는 것이다. 어휘·동의어 요청이 반복되면 그 종류만 연다.

## 5. 조회 품질을 위해 온톨로지에 더 담을 칸

새 라벨을 추가해도 지금 조회에서는 막힌다 — ① 코드의 라벨 목록에 없어 **LLM 이 존재를 모름** ② "살아 있음" 조건이 `site_status=present` 로 고정이라 **결과가 항상 0건** ③ 1단계가 `name` 속성만 받음 ④ 관계 방향 설명이 없어 방향 실수 ⑤ 자주 묻는 질문을 받쳐 주는 전용 로직이 없음.

①~④는 **온톨로지에 정보가 더 있으면 풀린다.**

| 추가할 칸 | 푸는 문제 | 지금 있는 곳 |
|---|---|---|
| `searchable` | 안 보임 | `SEARCH_LABELS` |
| `alive`(상태 속성과 값) | 결과 0건 | 조회 코드 고정값 |
| `name_property` | 이름으로 못 찾음 | `'name'` 고정 |
| `meaning` · `meaning_reverse` | 방향 실수 | `RELATION_MEANINGS` |
| `exposure`(llm / lookup / hidden) | 개인정보 | `HIDDEN_PROPERTIES` |
| `examples` | 질문 연결 · 회귀 시험 | 없음 |

바뀌는 파일은 `ontology/model.py`(양식) · `declaration.py`(값) · `version.py`, 승격본은 자동 생성, 조회 쪽은 `graph_rag/guided_schema.py` 가 상수 대신 온톨로지를 읽게 하면 된다. **그래프 데이터는 안 바뀐다**(설명서라서). ⑤ 전용 로직은 온톨로지로 대체되지 않는다.

> 개발자 개입은 "변경할 때 승인"이 아니라 **"운영하면서 품질 개선"** 형태가 된다. 라벨별 실패율을 보고, 예시 질문을 회귀 시험으로 쌓아 두는 게 개발자 리뷰를 대신한다.

## 6. 조회 실측에서 나온 것

| 질문 | 결과 |
|---|---|
| 나라원 하위 부서 | `entity_not_found` — 회사 이름 정규화가 `㈜` · `(주)` · `주식회사` · 공백만 떼서 **"나라원" 줄임말은 `나라원시스템` 과 다르다** |
| 나라원시스템 하위 부서 알려줘 | 정상 |

해결안은 A(회사 노드에 별칭 속성, 근거 필요) · B(앞부분 일치, 비슷한 이름이 생기면 위험) · C(정식 이름으로 묻기). 회사가 둘뿐이고 실제로 "나라원" · "아사달"로 부르니 **A 가 맞다**고 본다.

##### 채팅 답이 소속을 지어냈다
한 직원 질문에서 답이 **"소속: ㈜나라원시스템"** 으로 나왔는데, 그래프에서는 `AI1팀 → 웹사업부 → ㈜아사달` 이고 출처도 아사달 명단 하나뿐이다. 겸직자도 아니다. 그래프 조회가 **소속 회사를 안 돌려줘서** 답변 LLM 이 "나라원 챗봇이니 나라원이겠지" 하고 채운 것으로 보인다. 같은 답에 **휴대전화 번호가 그대로 나온 것**도 정책 확인이 필요하다.

→ 조회 쪽에 전달: **직원 질문에 소속 조직·회사를 항상 같이 반환**하고, 그래프가 주지 않은 사실을 답변 LLM 이 채우지 않게 제한.

## 7. 곁가지 — 그래프 화면과 KGreference

##### 시각화 라이브러리

| 안 | 판단 |
|---|---|
| NeoDash | 설치만 하면 되지만 **사용자가 DB 계정으로 로그인**해야 해서 일반 사용자에게는 못 쓴다 |
| NVL(Browser · Bloom 이 쓰는 엔진) | **탈락.** 패키지의 `LICENSE.txt` 를 직접 받아 확인했다 — **Aura 또는 상용 구독 Enterprise 에서만** 사용 가능. 운영은 5.26.30 **Community** 다 |
| **Sigma.js + graphology** | **채택.** 셋 다 MIT, WebGL 이라 수만~십만 규모까지 간다 |

라이브러리보다 중요한 건 **백엔드**다 — 보여줄 라벨·관계·속성을 **서버에서 걸러 보내고**(프론트에서 숨기는 건 소용없다), 응답을 압축 배열 + gzip 으로, `snapshot` 을 데이터 버전 단위로 캐시하고, 규모가 커지면 **좌표를 적재·릴리즈 때 미리 계산**한다. 줌 단계별로 보일 라벨과 클러스터(하위 개수 표시)도 정책으로 정할 수 있고, 묶는 기준은 **조직 계층**이 자연스럽다.

##### KGreference 검토

| 항목 | 결론 |
|---|---|
| 망가진 JSON 복구 | **보류.** 적재에 LLM 후보 생성기가 아직 없고, guided 는 형식을 엄격히 검증한다. **끊긴 응답 살리기는 우리 원칙(추측하지 않고 멈춘다)과 반대** |
| 원문 문장 매칭 | 보류. 쓰더라도 "주어·목적어가 둘 다 있을 때만" 으로 고쳐야 한다 |
| 탐색기 HTML | **보여 줄 사람이 있으면** 진행. 전화번호 제외, 파일은 로컬에만, `SOURCED_FROM`·`Capture`·`removed`·`left` 제외 |
| 추출 프롬프트 · 응답 캐시 | 참고만. 우리 캐시(원천 + 모델 + 프롬프트 버전 해시)가 더 엄격하다 |
| 관계 추론 · 이름 기반 병합 | **가져오지 않는다.** "원천이 말한 것만 넣는다"와 정면으로 충돌 |

LLM 으로 뽑을 자유 텍스트 자체가 적다(보유기술 11 · 사업분야 5 · 연혁 27 · 회사 소개 1). 쓴다면 **LLM 은 후보만 만들고 사람이 확정한 것만 결정론적으로 적재**하는 기존 틀(`resolutions/*.csv`)에 얹는 게 맞다.

## 재사용 가능한 판단

- **적재가 도울 수 있다고 해서 도와야 하는 건 아니다.** 소속은 이미 관계에 있으니 속성으로 한 번 더 적는 것보다 조회가 관계를 타는 게 맞았다
- **쓰는 경로가 둘이 되면 영역부터 나눈다.** 전체 재생성 방식은 "내가 모르는 노드"를 사라진 것으로 본다
- **LLM 은 양식을 해석하고, 값은 코드가 읽는다.** 정확성 · 재현성 · 개인정보 · 비용이 한 번에 해결된다
- **LLM 에게 문서 전체를 고쳐 달라고 하지 않는다.** 변경 명령만 받고 적용은 코드가 한다
- **"기존이 그대로인가"는 사람이 읽어 확인하지 않는다.** 옛 ⊆ 새, 차이 = 승인 명령을 집합 비교로 증명한다
- **적용하는 코드와 검사하는 코드는 방식이 달라야 한다.** 같은 방식이면 같은 실수를 한다
- **구조 변경이 어려운 진짜 이유는 데이터가 아니라 그 이름을 전제로 짠 코드다.** 이름을 온톨로지에서 읽게 할수록 자동화 범위가 넓어진다
- **이름 겹침은 규칙으로, 뜻 겹침은 사람이 막는다.** 뜻이 겹친 뒤 합치는 것은 구조 변경이라 훨씬 비싸다
- **권한을 열 때는 "쉽게"가 아니라 "근거를 대고 어렵게" 연다**
- **라이선스는 패키지 안의 원문을 직접 확인한다.** 무료로 받아진다고 쓸 수 있는 게 아니다
- **화면에 감추는 것은 감춘 게 아니다.** 서버에서 걸러 보내야 한다

## 한계

- **ingress 와 우리 적재의 영역 분리가 안 됐다.** 운영에서 섞어 돌리면 안 된다. A안 설계가 먼저다
- **인원수 질문(⑤)은 다시 시험하지 않았다.** 조회 보강 뒤 운영 재확인이 남았다
- **"나라원" 줄임말과 회사 별칭은 미정이다.** 근거가 될 원문을 찾아야 한다
- **직원 답변이 소속을 지어내는 문제는 전달만 했다.** 어느 서버 버전에서 난 건지도 확정하지 못했다
- **온톨로지 자동화는 전부 설계 단계다.** 저장소 DB 화와 조회의 버전 추종은 조회 담당과 같이 해야 한다
- **시각화는 아직 노드·엣지 수, 공개 속성 범위, 인증 방식이 정해지지 않았다**
- **오늘 코드·커밋은 없다.** 브랜치 `feat/name_normalize` 는 main 과 같은 상태다
- **`.env` 에 PostgreSQL 비밀번호가 커밋된 상태다**
