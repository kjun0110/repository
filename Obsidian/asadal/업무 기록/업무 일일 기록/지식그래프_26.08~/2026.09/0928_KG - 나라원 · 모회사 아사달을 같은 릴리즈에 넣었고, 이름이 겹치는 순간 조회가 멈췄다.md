## 개념

- **겸직** — 두 회사 명단에 같은 직원아이디·이름으로 들어 있는 사람. 오늘 3명
- **`manifest.company`** — 업로드 폴더의 매니페스트에 적는 회사. 폴더 이름과 다르면 적재가 멈춘다. 의미는 파일 이름이 아니라 매니페스트가 정한다(D58)
- **`SUBSIDIARY_OF`** — 자회사 → 모회사 관계. 나라원시스템 → ㈜아사달
- **ground(2단계)** — guided 조회가 질문에서 뽑은 이름으로 DB 노드를 찾는 단계. **정확히 한 개**여야 다음으로 간다. 0개면 `entity_not_found`, 2개 이상이면 `entity_ambiguous`
- **qualifier** — ground 에서 이름과 함께 쓰는 조건. **그 노드의 속성값만** 쓸 수 있고 관계는 못 탄다
- **`name_key`(안)** — 대문자·공백·`㈜` 를 정리한 이름 비교용 값. 아직 없다

## 요약

모회사 아사달 명단을 **같은 DB · 같은 릴리즈**에 넣었다. 오늘이 시작이자 마감이었다.

받은 엑셀 두 개는 **서식이 바뀌어 있었다**(15칸 → 12칸). 그대로면 나라원 명단조차 못 읽어서, 파서를 칸 위치가 아니라 **칸 이름으로** 찾게 고쳤다. 업로드는 `uploads/<회사>/` 로 나누고 회사는 매니페스트가 정한다. 아사달 조직은 사이트가 없어 **명단의 부서·팀에서** 만들었다. 조직 이름(`웹사업부` · `임원`)과 직원 3명이 두 회사에 겹쳐, 아사달 조직 키에만 회사를 넣고 겸직은 **노드 하나 · 소속 둘**로 처리했다.

온톨로지 0.6.2 로 승격하고, main 을 **커밋 없이 시험 머지**해 게이트 6개를 돌린 뒤 되돌려 푸시했다. 운영 적재는 seq 3, 회사 2 · 조직 39 · 직원 239 · 모회사 관계 1 이다. 적재 직후 릴리즈해 공백을 배포 시간만큼으로 줄였다.

**그리고 이름이 겹치는 순간 조회가 멈춰 섰다.** 두 회사에 `웹사업부` 가 있어 ground 에서 2건이 나오고, 조회는 추측하지 않고 `ambiguous` 로 끝낸다. 회사로 좁히려 해도 **조직 노드에 회사 속성이 없다** — 소속은 관계로만 있고 ground 는 관계를 안 탄다. 질문 13개 중 6개 정상 · 1개 모호 · 6개 실패였고, 실패 5건은 0.6.1 스키마로도 재현되는 **기존 조회 문제**임을 확인했다.

## 1. 엑셀 두 개에서 나온 것

##### ① 명단 서식이 바뀌었다
두 파일 서식은 서로 같았고, 운영 중인 9/14 명단과 달랐다.

```
옛 15칸  … 성명 · (빈 칸) · 직원아이디 … 휴대폰번호 · 직장번호 · 근무장소 · 업무분야 · 홈 · 관리
새 12칸  … 성명 · 직원아이디 …          휴대폰번호 ·           근무장소 · 업무분야
```

성명과 직원아이디 사이의 빈 칸이 없어져 뒤가 한 칸씩 당겨졌고, **직장번호 · 홈 · 관리**가 빠졌다. 파서가 칸 위치까지 맞아야 읽게 돼 있어(D29) **나라원 최신 명단도 거부**됐다.

- 검토한 안: 12칸만 받기 — 기각. 옛 명단(9/14)을 읽을 일이 남아 있다
- 택한 안: **머리글에서 칸 이름으로 위치를 찾는다.** 직장번호는 있으면 읽고 없으면 빈 값, 모르는 칸 이름이 나오면 멈춘다. 버전 `hr-roster-v1` → `v2`

직장번호가 비는 사람은 212명이 아니라 **16명**이었다(나머지는 옛 명단에서도 빈칸).

##### ② 아사달 조직은 명단에서 만든다
나라원 조직은 사이트 조직도에서 오지만 아사달은 사이트가 없다.

```
㈜아사달
 ├─ 웹사업부 ─ AI1팀 · AI2팀 · 호스팅팀 · 도메인팀
 └─ 임원    ─ 총무실
```

`임원` 은 나라원과 같은 방식으로 조직을 만들지 않고 **회사 직속**으로 뒀다.

##### ③ 조직 이름이 겹친다
아사달에도 `웹사업부` · `임원` 이 있다. 조직 키가 `hash("unit", 이름 경로)` 라 회사 구분이 없어 그대로 두면 `DUPLICATE` 로 멈춘다. → **아사달 키에만 회사를 넣었다.** 나라원 키는 그대로 둬서 운영 그래프를 흔들지 않는다.

##### ④ 같은 사람이 두 명단에 3명
직원 키가 `hash(아이디, 이름)` 이라 역시 같은 키다. 회장 · 사장 · 부서장으로, **그룹 임원 겸직**이다.

| | 두 명단에서 다른 칸 |
|---|---|
| 회장 | 없음 |
| 사장 | 팀명 · 직급 |
| 부서장 | 팀명 · 근무장소 |

팀명은 한쪽이 `-`, 한쪽이 `no` 라 둘 다 "팀 없음"이다. 소속은 각 회사 직속으로 하나씩 이으면 된다.

## 2. 겸직 값 — 배열을 넣었다가 뺐다

직급 · 근무장소가 회사마다 다른데 노드 속성은 칸이 하나다.

| 안 | 판단 |
|---|---|
| 배열 `["아사달값","나라원값"]` | 사용자 제안으로 한 번 정했다가 **기각.** 칸 타입은 사람마다가 아니라 칸마다 정해져서 **239명 전부가 배열**이 되고, 조회 질의가 `rank = '대리'` 에서 `'대리' IN rank` 로 바뀐다 |
| 회사별 노드 둘 | 기각. 같은 사람이 둘이 되어 중복을 피하려던 목적이 깨진다 |
| 직급을 `MEMBER_OF` 관계에 | 기각(보류). "관계에는 출처 3칸만"이라는 지금 규칙을 풀어야 한다. 정석은 이쪽이고 겸직이 늘면 옮긴다 |
| **노드 하나 · 소속 둘 · 값은 아사달 기준** | **채택.** 칸 타입이 안 바뀌어 나머지 236명은 아무것도 안 바뀐다 |

배열을 뺀 덕에 **칸 타입 변경이 없어져** 버전도 패치로 남았다.

## 5. 시험 머지 — 커밋 없이 합쳐 보고 되돌리기

main 이 또 앞서 있었다(조회 담당의 guided 작업). 변경 범위가 `serving/` · `graph_rag/` 뿐임을 먼저 확인하고 **다 하고 머지**로 갔다.

```
git merge --no-commit --no-ff origin/main     → Automatic merge went well
(이 상태로 게이트 6개 · ruff · 조회 확인)
git merge --abort                              → 924476b 그대로, 작업 트리 깨끗
git push -u origin feat-ontology_asadal
```

`--no-commit` 이면 합친 결과가 파일에만 들어가고 커밋이 안 생겨, `reset --hard` 없이 정확히 되돌아간다. PR 머지 결과와 같은 두 커밋을 합쳐 본 것이라 **여기서 통과하면 PR 머지도 통과**다. 머지 직전에 main 이 또 바뀌면 보증이 깨지므로 `git ls-remote` 로 한 번 본다.

적재 쪽 파일은 main 에서 **하나도 안 바뀌었다.** 그래도 게이트를 돌린 이유는 적재기가 `serving/settings.py` 를 import 하기 때문이다(방향 역전, 0923).

## 6. 운영 적재와 릴리즈

##### 순서 — 적재 먼저

| | 적재 → 릴리즈 | 릴리즈 → 적재 |
|---|---|---|
| 멈추는 시간 | **배포 시간만큼** | 적재 시간만큼(쓰기 · 임베딩 · 검증까지) |
| 적재가 실패하면 | DB 가 0.6.1 그대로, 옛 API 도 정상 — **아무것도 안 깨짐** | 새 API + 옛 DB 로 guided 가 계속 멈춤 |

> **정정.** 오전에 "적재 먼저 하면 공백이 없다"고 했는데 틀렸다. guided 는 DB 버전과 코드 버전이 **정확히 같아야** 답하므로 **어느 순서든 공백이 생긴다.** 할 수 있는 건 공백을 짧게 만드는 것뿐이다.

## 7. 이름이 겹치자 조회가 멈췄다

##### 무슨 일인가
guided 조회는 질문에서 뽑은 이름으로 노드를 찾을 때 **정확히 한 개**여야 진행한다.

```
0.6.1  웹사업부 하나        → 팀 목록 답함
0.6.2  웹사업부 둘(두 회사) → entity_ambiguous, 되물음
```

**틀린 답을 내는 게 아니라 추측하지 않는 동작**이다. 겹치는 이름은 `웹사업부` 하나뿐이다.

##### 왜 "아사달 웹사업부"라고 해도 안 되나
ground 의 조건(qualifier)은 **그 노드의 속성값만** 쓸 수 있다. 조직 노드에는 이름 · 종류 · 순서 · ID 만 있고 **어느 회사인지가 없다.** 회사 소속은 `SUB_ORG_OF` 관계로만 있는데 ground 는 관계를 타지 않는다.

| 축 | 구분되나 | ground 에서 쓸 수 있나 |
|---|---|---|
| `SUB_ORG_OF → Company` | 확실히 됨 | 관계라 못 씀 |
| `MEMBER_OF` | 됨(겸직은 두 회사에 닿음) | 관계라 못 씀 |
| 출처(`SOURCED_FROM`) | 됨 | 관계이고, 파일로 회사를 가르는 건 억지 |
| `unit_id` | 아사달 키에만 회사가 들어감 | 해시라 못 읽음 |
| 노드 속성 | **없음** | 이것만 쓸 수 있는데 값이 없다 |

##### 선택지와 판단

| 안 | 판단 |
|---|---|
| **그대로 두기** | **채택.** 틀린 답이 아니라 되묻는 형태라 안전하다. 오늘이 마감이고 코드도 안 바뀐다 |
| 적재 쪽에서 조직에 `company` 속성 | 보류. 소속이 관계와 속성 두 곳에 들어가고, LLM 이 "아사달"을 조건으로 뽑아 주는지 확인이 안 됐다 |
| 조회 쪽에서 이름이 2건이면 회사로 좁히기 | **구조적으로는 이쪽이 자연스럽다.** 이미 있는 축을 쓰고 데이터를 안 바꾼다. 조회 담당 영역 |

질문에 회사가 없으면(`웹사업부에는 어떤 팀이 있어?`) 사람이 들어도 모르는 질문이라 **되묻는 게 정상**이다. 해결 대상은 회사가 들어간 질문이다.

## 8. 운영 질문 실측 — 13개 중 6개 정상

정상: 웹개발팀 소속 · 웹개발팀 인원 · 사무소 주소 · **모회사** · **아사달 조직** · 총무실 직원. 모호함: 웹사업부(예상대로).

실패 5건은 **0.6.1 스키마로도 4/4 재현**됐다. 1단계는 DB 를 안 보고 질문과 스키마만 보기 때문에 두 스키마로 각각 4번씩 돌려 비교했다.

| 실패 | 원인 |
|---|---|
| 나라원시스템 대표이사는 누구야? | LLM 이 `Company` 에 직원 속성 `position='대표이사'` 를 조건으로 붙임 → 검사에서 탈락. 데이터로는 답할 수 있다(`ceo_name`) |
| 아사달 웹사업부 소속 팀 | 조건에 `name='아사달 웹사업부'` — 이름은 조건으로 못 쓴다 |
| 아사달 총무실에는 누가 있어? | `grounded_entity_binding_required` 2회 반복 후 포기. "총무실 직원 알려줘"는 정상 |
| ○○팀에 몇 명 있어? | `missing_relationship_nodes` |

**이번 적재로 새로 생긴 문제는 웹사업부 이름 겹침 하나뿐이다.**

##### 대소문자와 표기
챗봇 답이 그래프가 아니라 회의록으로 만들어진 건이 있었다. 서버 로그로 확인했다.

```
13:50 이후 /v1/graph/search-by-question 요청이 전부 내 PC IP
→ 그 시각 채팅발 호출은 없었음 (이후 14:44 요청은 실제로 왔고 entity_not_found)
```

| 입력 | DB 값 | 결과 |
|---|---|---|
| AI1팀 | AI1팀 | 찾음 |
| ai1팀 | AI1팀 | 못 찾음 — Cypher `=` 는 대소문자까지 그대로 비교 |
| AI 1팀 · AI개발1팀 | AI1팀 | 못 찾음 |
| 아사달 | ㈜아사달 | 찾음 — **회사에만** `㈜` · `(주)` · 공백을 떼는 재시도가 있다 |

"AI 개발1팀"은 회의록 표기다. 명단에는 `AI1팀` 만 있어 **같은 팀이라는 근거가 데이터에 없다.**

## 9. 조회 담당자 전달과 적재 쪽 보완안

전달 목록 5건을 정리해 페이지로 넘겼다(요청 ID 포함). ① 이름 겹침을 회사로 좁히기 ② 대소문자 · 공백 무시 ③ 스키마에 없는 조건은 버리거나 다시 받기 ④ `grounded_entity_binding_required` ⑤ 인원수 질문. 채팅이 실제로 보낸 문장은 우리 쪽 로그에 없다(`NARA1_TRACE_ENABLED` 꺼짐).

적재 쪽에서 같이 할 수 있는 것:

| 안 | 내용 | 판단 |
|---|---|---|
| **A `name_key`** | 대문자 · 공백 · `㈜` 를 정리한 비교용 이름을 노드에 저장. 조회는 같은 규칙으로 바꿔 비교만. 정규화 규칙은 한 모듈에 두고 양쪽이 공유 | 유력. "AI개발1팀"은 여전히 못 찾음 |
| **B `company` 속성** | 조직에 소속 회사를 적어 기존 qualifier 로 좁히게. 값은 `SUB_ORG_OF` 를 따라 기계적으로 채우고 적재 검증으로 관계와 대조 | 유력. 소속이 두 곳에 들어가는 대가. 겸직 때문에 직원에는 넣지 않음 |
| **C 겹침 보고** | 같은 라벨에서 이름이 겹치면 리포트에 알림 | 싸고 예방 효과 |
| **D 별칭** | `AI1팀` = `AI 개발1팀` | **보류.** 근거 파일이 없다. 모든 값에 출처를 붙이는 원칙과 충돌 |

전부 속성 추가라 **0.6.3(패치)** 이고, guided 가 버전 정확 일치를 요구하므로 **조회 수정과 같은 릴리즈로** 나가야 한다.

## 11. 곁가지 — 업로드·삭제 정책 논의

별도 세션에서 UI 업로드와 삭제를 어떻게 다룰지 정리했다(코드는 안 건드림).

- **삭제도 적재기를 거쳐야 한다.** DB 에 직접 `DELETE` 하면 다음 적재가 그래프 해시 불일치로 전부 멈추고(`PreviousUnavailable`), 파일이 남아 있으면 다시 만들어진다
- 삭제는 셋으로 갈리지만 **반영 경로는 하나**여야 한다 — ① 크롤링 차이(확실성 낮음 → `removed` 유지) ② 파일 업로드 차이(LLM 제안 + 사람 승인) ③ 수동 삭제 버튼. ②와 ③은 결국 같은 것이라 **"사람이 승인한 삭제 결정"** 기록 하나로 모으고 `DELETION_RULES` 에 규칙을 더한다
- 수동 삭제는 한 번 실행하고 끝이 아니라 **계속 유지되는 결정**이어야 한다. 소스에 아직 있으면 다음 수집이 되살린다
- 팀이 없어져도 **팀원 노드는 지우지 않는다.** 노드는 "누구인가", 관계는 "지금 어디 있나"다. 직원 키에 팀이 안 들어가 옮겨도 같은 노드이고, 소속만 다시 맞춰진다
- 중복 방지는 세 층 — 파일 바이트 해시(같은 파일) · **파싱 내용 해시**(엑셀을 열었다 저장만 해도 바이트가 바뀐다) · 그래프 키(같은 대상). 지금은 파일 해시 값만 있고 검사는 없다

##### 동일성 판별 — 파일이 계속 들어와도 노드가 하나이려면

노드 중복은 파일 해시가 아니라 **키**가 막는다. 파일 해시는 "처리할지"만 정하고, 노드가 하나냐 둘이냐는 키가 정한다. 지금 명단은 파일 안 아이디 중복 멈춤(`roster.py`) → `hash(아이디, 성명)` 키 → 배치 안 중복 멈춤 → DB 와 키로 비교해 `MERGE` → 유일 제약(`ddl.py`)까지 다섯 겹이다. 같은 명단을 백 번 올려도 노드는 사람 수만큼이다.

문제는 `아사달` / `(주)아사달` 처럼 **이름으로만 오는 대상**이다. 판별 순서를 이렇게 정리했다.

```
0. 정규화      식별값 형식 통일(123-45-67890 → 1234567890) + 이름 정규화(㈜→(주), 공백 등)
1. 식별값 비교  같으면 확정
2. 이름 비교    정규화된 이름이 같으면 확정
3. 별칭 표      사람이 확정해 둔 별칭에 있으면 확정
4. LLM 판독    제안 → 사람 승인 → 별칭 표에 추가
```

- **식별값** — 사번 · 사업자번호 · 계약번호처럼 원천 시스템이 한 대상에 하나씩 붙인 값. 파일에 있으면 그걸 키로 쓰고 2~4 를 건너뛴다(속성 갱신은 그대로). 회사처럼 **맥락(매니페스트)이 정해 주는 것**도 여기다 — `company_key("asadal")` 은 이름이 아니라 고정 식별자다
- **정규화는 맨 앞 전처리, 판별은 식별값이 이름보다 먼저.** 이름이 같아도 사업자번호가 다르면 다른 회사다. 이름부터 보면 잘못 합친다
- 4번은 발주처에서 이미 돌고 있다 — `resolutions/clients.csv` 에 "Claude 제안 · 근거" + `approved_by`. 한 번 승인하면 다음부터 3번에서 자동으로 풀린다
- **애매하면 합치지 않는다.** 중복은 나중에 합치면 되지만, 잘못 합친 노드는 관계가 섞여 되돌리기 어렵다
- 파일을 **교체**가 아니라 **누적**으로 쓰게 되면, 지금 코드는 두 파일이 같은 노드를 만들 때 "같은 노드가 두 번"으로 멈춘다(`candidates/__init__.py`). 같은 키는 한 노드로 합치고, 속성은 기준일이 늦은 쪽이 이기고, 출처는 둘 다 남기는 규칙이 필요하다

## 재사용 가능한 판단

- **입력 서식은 말없이 바뀐다.** 칸 위치가 아니라 이름으로 읽고, 모르는 칸이 나오면 멈춘다
- **칸 타입은 사람마다가 아니라 칸마다 정해진다.** 예외 3건 때문에 전체를 배열로 바꾸면 조회 질의까지 따라 바뀐다
- **키에 구분 축이 없으면 두 번째 원천이 들어오는 순간 충돌한다.** 새로 들어오는 쪽 키에만 축을 넣으면 기존 그래프를 안 흔든다
- **판정 로직에 "누구 것인가"가 빠져 있으면 두 번째 적재에서 터진다.** 퇴사 판정 · 보관 규칙 · 옛 명단 검사는 전부 회사별이어야 했다
- **커밋 없는 시험 머지가 가장 싸고 정확하다.** `--no-commit --no-ff` 로 합쳐 게이트를 돌리고 `--abort` 로 되돌린다
- **규칙을 느슨하게 하는 변경은 기존 데이터를 깨지 않는다.** 그래서 패치로 둘 수 있다
- **스키마 버전이 바뀌는 배포는 어느 순서든 공백이 생긴다.** 할 수 있는 건 공백을 짧게 만드는 것뿐이고, 실패했을 때 되돌릴 게 없는 쪽(적재 먼저)이 낫다
- **조회가 못 찾을 때 데이터를 의심하기 전에 같은 질문을 옛 스키마로 재현해 본다.** 이번 실패 5건 중 4건이 이번 작업과 무관했다
- **이름은 구분 축이 아니다.** 사람이 봐도 모호한 질문은 되묻는 게 맞고, 구분이 필요하면 구분값이 노드에 있어야 한다
- **민감한 값은 검사로 막기보다 LLM 경로 밖에 둔다.** 검사를 통과하지 못하게 하는 것보다 볼 것이 없게 하는 쪽이 싸고 확실하다
- **로그의 출처 IP 로 "호출이 없었다"를 증명할 수 있다.** 없는 것을 확인하려면 있는 것부터 보인다는 걸 확인한다

## 한계

- **웹사업부 질문은 모호함으로 남는다.** 조회 쪽에서 회사로 좁히거나, 적재에서 `company` 속성을 넣어야 풀린다
- **대소문자 · 표기 차이로 못 찾는다.** `ai1팀` · `AI개발1팀`. `name_key` 는 안으로만 있고 별칭은 근거가 없어 보류했다
- **대표이사 · 인원수 · "아사달 ○○" 질문이 실패한다.** 조회 쪽 문제이고 0.6.1 부터 있었다
- **채팅이 그래프에 실제로 보낸 질문 문장을 모른다.** 서버 trace 가 꺼져 있다
- **사이트(nara1.kr)는 이번에 다시 수집하지 않았다.** 기존 수집본 그대로다
- **전화번호가 조회 LLM 에 열려 있다.** 오늘 숨김이 풀렸고, 사내 정책부터 정해야 한다
- **검사기 우회(맵 투영)가 실제로 통과하는지 확인하지 못했다.** 코드를 읽고 판단만 했다
- **스케줄러(5단계)는 그대로 남아 있다.** 서버 정기 적재도 아직이다
- **업로드 · 삭제 UI 흐름은 논의만 했다.** 철회 기록 형식, 삭제 승인 단위, 보관 기간 모두 미정이다
