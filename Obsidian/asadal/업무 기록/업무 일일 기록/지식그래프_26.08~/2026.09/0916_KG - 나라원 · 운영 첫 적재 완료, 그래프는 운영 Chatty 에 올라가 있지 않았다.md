## 개념

- **릴리즈 보관소** — 적재한 `release.json` 을 `0001-<매니페스트 해시 앞 8자>.json` 이름으로 쌓아 두는 폴더. `index.jsonl`(순번·해시·시각·건수) · `latest.txt`(마지막 파일 이름) 와 함께 둔다. 다음 적재의 "직전 릴리즈"를 여기서 찾는다
- **짝 검사** — DB 의 `ReleaseHead.manifest_sha256` 과 보관소 마지막 릴리즈가 같은지 스키마·데이터를 바꾸기 전에 보는 검사. 빈 DB 는 빈 보관소와만 짝이다
- **드라이런** — `--target` · `--write` 없이 릴리즈 문서까지만 만들고 DB 에 접속하지 않는 실행. 매니페스트 해시로 "섀도우에서 확인한 것과 같은 재료인가"를 본다
- **`--verify`** — DB 에 쓰지 않고 "DB 에 들어 있어야 할 릴리즈"와 되읽은 그래프를 통째로 대조하는 실행
- **BGE-M3 서버** — 사내 GPU 에서 도는 임베딩 서버. OpenAI Embeddings API 와 요청·응답 모양이 같다. 1024차원
- **조회 경로** — 프론트 화면 → Chatty `/ask` → Graph API `/v1/graph/search-by-question` → Neo4j. 오늘 끊긴 곳은 Chatty → Graph API 한 칸이었다
- **Gitea 러너** — 서버 안에 설치돼 워크플로를 서버 로컬에서 실행하는 프로그램. 우리 Graph API 서버의 러너와 Chatty 서버의 러너가 따로 있다

[[0915_KG - 나라원 · 0.4.1 확정까지, 벡터와 생성 문장은 릴리즈 밖에 두어야 적재가 흔들리지 않는다]] 에서 0.4.1 을 확정하고 운영 적재만 남겼다. 오늘 **운영 DB 첫 적재를 마쳤다.** 그 전에 구조가 두 번 바뀌었고, 운영에서 버그 하나가 드러났다.

먼저 삭제(D)를 설계만 따졌다. **지금 데이터에는 노드를 지울 이유가 거의 없고, 지울 상황이 오면 적재가 조용히 틀리지 않고 멈춘다.** 그래서 빈 껍데기 코드도 만들지 않았다. 대신 삭제 판단과 다음 적재의 기준이 되는 `release.json` 을 잃지 않는 장치가 필요했다. "파일 없이 못 하냐"를 끝까지 따진 끝에 **릴리즈 보관소**를 넣었다. 수원 파이프라인을 조사해 보니 릴리즈 개념 자체가 없고, 이전 상태를 덮어쓰는 기준선 파일로만 기억하고 있었다.

오후에는 사내 BGE-M3 임베딩 서버가 이미 떠 있는 것을 확인했다. **운영 DB 가 비어 있는 지금이 가장 싸서** 임베딩을 ada-002(1536)에서 BGE-M3(1024)로 바꾸고 온톨로지 0.4.2 를 확정했다.

운영 DB 에 시험 적재하고 확인하다가 **`--verify` 에 보관소를 붙이면 항상 `verified: false` 가 나오는 버그**를 찾았다. DB 를 비우고, 고치고, 섀도우에서 임베딩까지 다시 돌린 뒤 PC 에서 운영에 정식 적재했다. 노드 584 · 관계 761 · 벡터 220(1024) · `verified: true` 다.

조회를 점검해 보니 **조회 코드는 조직 소속 질문 하나만 답하고, 넣은 벡터를 쓰는 코드는 없다.** `/health/ready` 가 점검 실패에도 `ready: true` 를 내던 버그를 고쳐 배포했다. 배포된 API 에 직접 물으면 답이 나오지만 프론트에서는 그래프가 붙지 않았다. 다른 프로젝트 배포 파일까지 뒤져서 원인을 확정했다. **Chatty 서버의 한 포트는 운영, 다른 포트는 개발이고, 프론트는 운영 Chatty 를 부르는데 그래프 연동은 개발 Chatty 에만 올라가 있었다.** 도메인 이름에 `dev` 가 들어 있어 처음에는 반대로 읽었다.

## 1. 운영 DB 확인 경로와 CRUD 범위 — D 는 만들지 않는다

##### 확인 경로
PC 에서도 서버에서 적재한 것과 같은 DB 를 볼 수 있다. 외부 주소는 PC 용, 내부 주소는 서버용이고 둘 다 같은 Neo4j 를 가리킨다.

```
명령 출력      verified · embedding.verified · release_file
다시 확인      ingestion.load --verify · ingestion.embed --dry-run (todo 비어 있어야 함)
브라우저       운영 Neo4j 브라우저 — .env 계정
쿼리           라벨별 수 · 관계별 수 · ReleaseHead 순번·버전·해시
```

##### CRUD 상태

| | 상태 |
|---|---|
| C | 완료 — 없으면 MERGE |
| U | 완료 — 속성 통째 교체, 임베딩 칸 보존 |
| D | **절반** — 관계는 지움(팀 이동·퇴사·사라진 노드), 노드는 안 지움 |
| R | 다른 담당 — 조직 조회만 있음 |

##### 노드 삭제를 지금 만들지 않는 이유

| 삭제 사유 | 판정 |
|---|---|
| 개인정보 보관 기간 | 유일한 진짜 사유. 인사 방침(퇴사 후 N년)이 정해지면 그 기준으로 만든다 |
| 잘못 적재한 것 되돌리기 | 노드 삭제가 아니라 DB 를 비우고 다시 적재하는 게 맞다 |
| 검색 품질 | 이미 해결. 조회가 `removed` · `left` 를 거르고 임베딩 대상에서도 뺀다 |
| DB 용량 | 해당 없음 (노드 584) |
| "사라진 게 사실이니 없애야 정확" | 반대. 사이트에서 내린 사업도 수행 기록이다 |

빈 `retire.py` 나 호출되지 않는 훅을 "자리 마련"으로 두자는 안도 기각했다. 이 프로젝트에서 이미 두 번 겪은 패턴이다. 계획에 있던 `ledger.py` · `identity.py` · `diff.py` 는 결국 만들 필요가 없었고, 프로토타입에서는 선언이 하지도 않는 일을 한다고 적힌 곳이 5군데 나왔다. **자리는 이미 층으로 나 있다.** `plan.py` 의 `gone = 옛 노드 − 새 노드` 가 곧 삭제 후보이고, 되읽기 대조 · 트랜잭션 롤백 · 지문 검사가 삭제에도 그대로 따라온다.

##### 삭제를 만든다면 — 설계만 남김

```
경로 A  사이트에서 사라짐 (자동)
        사라짐 후보 = 직전 릴리즈 − 이번 후보
        → 마지막으로 본 페이지를 이번 수집 매니페스트에서 찾는다
            못 받음      수집 실패. removed 유지, 삭제 제외
            받았는데 없음 사이트에서 빠짐
        → 라벨별 10% 초과면 멈춤 (파서 회귀)
        → removed 된 지 보존 기간이 지났나 (removed_at 필요 → 버전 올림)
        → release.json 에 retired 목록으로 싣는다
경로 B  잘못 들어간 것 (사람 지정)
        resolutions/retire.csv — 라벨 · 키 · 사유 · approved_by
실행    writers 는 retired 목록에 있는 것만 지운다. 목록에 없는데 DB 에만 있으면 지금처럼 멈춘다
```

**판단을 릴리즈 문서에 적는 것이 핵심이다.** 적재 순간에 판단하면 드라이런으로 미리 볼 수 없고, 기록도 되돌림도 안 된다.

##### 규모가 커지면 먼저 무너지는 곳 (노드·관계 200만 가정)

| 곳 | 지금 | 200만 |
|---|---|---|
| `release.json` | 1.8MB | 약 2.5GB |
| DB 전체 읽기 (적재당 3회) | 0.2초 | 수 GB 메모리, 수십 분 |
| 그래프 해시 | 즉시 | 사실상 불가 |
| 쓰기 한 트랜잭션 | 5초 | 힙 초과 |
| 삭제 후보 | 공짜 | 못 구함 |

이때는 릴리즈를 변경분으로, 지문을 DB 집계(`row_hash` 합)로, 쓰기를 배치+체크포인트로 바꿔야 한다. **"전부 아니면 전무"는 버리고 "다시 돌리면 같은 상태로 수렴"을 보장하게 된다.** `release/`(DB 없음)와 `writers/` 경계, 해시 체인, 결정 표, 10% 멈춤은 규모와 무관하게 남는다.

## 2. 릴리즈 보관소 — 파일 없이 되는가를 끝까지 따짐

##### 문제
`release.json` 은 적재 결과이자 다음 적재의 입력이다. 지금은 `.local/` (깃 밖 임시 폴더) 에 생기고, 다음 적재 때 사람이 `--previous` 로 경로를 적는다. **잃으면 DB 는 멀쩡하지만 다음 적재가 막히고, 이어가려면 DB 를 비우고 처음부터 다시 적재해야 한다.**

##### 파일이 하는 일과 DB 로 대신 되는지

| 쓰임 | DB 로 대신 |
|---|---|
| 순번 · 부모 해시 | 됨 (`ReleaseHead`) |
| 퇴사 · 사라짐 판정 | 됨 (현재 그래프 = 직전 그래프) |
| 사라진 노드의 출처 | 됨 (노드 출처 3칸) |
| **적재 전 지문 검사** | **안 됨** — DB 에서 뽑으면 자기 자신과 비교 |
| 리포트 · 거부 목록 · 결정 이력 | 안 됨 |

`release.json` 1.8MB 를 쪼개 보면 매니페스트 2.2KB · 그래프 1.39MB · 리포트 145B 다. **바깥 기준으로 필요한 것은 매니페스트뿐이고 그래프는 DB 에 이미 있다.**

##### 검토한 안

| 안 | 판정 | 사유 |
|---|---|---|
| **A. 보관소 (전체 문서)** | 채택 | 리포트·이력 보존, 지금 코드 흐름 그대로 |
| B. 매니페스트만 깃에 커밋 | 보류 | 개인정보 없어 커밋 가능, 규모 무관. 대신 두 번째 적재부터 드라이런도 DB 접속 필요 — 흐름 앞부분이 바뀜 |
| C. `ReleaseHead` 에 직전 그래프 해시 각인 | 보류 | 파일이 아예 없어짐. 대신 DB 통째 백업 복원은 못 잡고, 온톨로지 칸 추가로 버전이 올라감 |
| 폴더 없이 복사 두 줄로 운영 | 기각 | 파일을 잃을 위험이 사람에게 달림 |
| 보관소 경로를 `.env` 에 | 기각 | 요청으로 제외 |
| 오래된 릴리즈 정리를 코드에 | 기각 | 운영 판단이라 코드에 박지 않음 |

##### 수원은 어떻게 하나 — 조사 결과 릴리즈가 없음

| | 나라원 | 수원 |
|---|---|---|
| 이전 상태 기준 | 릴리즈 문서 (DB 밖) | DB 각인(`last_seen` · `status` · `content_hash`) + **같은 이름으로 덮어쓰는 기준선 파일** |
| 적재 전 검사 | 지문 대조 → 쓰기 전 거부 | 원천 신선도만. 그래프 대조는 사후 |
| 쓰기 | 달라진 것만 · 한 트랜잭션 · 롤백 | 전량 MERGE (Article 6,297 · 첨부 8,054 를 각각 한 문장), 롤백 없음 |
| 삭제 | 상태만 · 수집본 근거로 판정 예정 | 상태만(`abolished`) · **수집 성공 여부 안 봄** |
| 드리프트 | 10% 사라짐 → 쓰기 전 멈춤 | 10% 줄면 FAIL, 그러나 그래프는 이미 다 써진 뒤 |

수원 코드에 사고 기록이 남아 있다. "스크립트를 따로 돌리면 오늘 안 돌린 노드를 전부 폐지 처리해버린다(실제로 한 번 겪음)", "동명 조직 매칭이 흔들려 실제 사람 22명이 폐지된 채로 이틀". 수원에는 전체 릴리즈 문서보다 **기준선 요약(몇 KB)을 날짜별로 쌓는 것**이 맞다. 그보다 급한 것은 **폐지 판정을 수집이 성공한 원천에만 적용하는 것**이다. 조사만 했고 수원 코드는 고치지 않았다.

##### 구현 — `ingestion/release/store.py` + `load.py --release-store`

```
① 보관소에서 직전 릴리즈 읽기 (자기 검사 통과분만)
② 릴리즈 만들기 · .local 에 먼저 파일로 남김
③ DB 연결 → 짝 검사          ← 새로 넣음. 스키마·데이터 바꾸기 전
④ preflight 지문 → 스키마 → 한 트랜잭션 쓰기 → 되읽기 대조 → verify
⑤ 보관                        ← 새로 넣음. 임베딩 전 (임베딩 실패해도 릴리즈는 남게)
⑥ 임베딩
```

멈추는 경우는 여섯이다. 보관소 훼손(`latest.txt` ↔ `index.jsonl` 불일치, 파일 없음, 내용 변경), 순번 불연속, DB 와 짝 불일치, `--previous` 와 동시 사용, 운영 보관소가 코드 checkout 안, 부모 폴더 없음.

짝이 안 맞을 때는 무엇을 하면 되는지 메시지에 적었다. "다른 곳에서 적재했다면 그 릴리즈 파일 · index.jsonl · latest.txt 를 이 보관소로 옮긴다"는 식이다.

##### 폴더 자동 생성 — 타협안

| 안 | 경로 오타를 언제 잡나 | 평소 |
|---|---|---|
| A. 무조건 자동 생성 | 두 번째 적재 때 (첫 적재는 빈 DB + 빈 보관소라 짝 통과) | mkdir 불필요 |
| B. 없으면 멈춤 | 첫 적재에서 바로 | 처음 한 번 mkdir |
| **타협안 — 부모 폴더가 있을 때만 생성** | 부모 경로 오타는 바로 | mkdir 불필요 |

처음에는 B 로 만들었다가, 요청을 받고 타협안으로 바꿨다. 경로 실수는 마지막 폴더 이름보다 부모 쪽(홈 경로 착각, 다른 위치에서 상대경로 실행)에서 더 자주 난다. 운영 적재에는 절대경로를 쓴다.

##### 결과
오프라인 게이트 25항목, 섀도우 게이트 모두 통과했다. 빈 DB → 순번 1 → 같은 명령으로 순번 2 → 빈 보관소로 적재하면 DB 를 바꾸기 전에 종료 1 → 파일 3개를 옮기니 순번 3 으로 이어졌다.

> **작업 방식 정정.** 보관소 구현을 계획 설명 없이 시작했다가 중단 요청을 받았다. 만든 파일(`store.py`, 게이트 2개)을 지워 커밋 상태로 되돌린 뒤, 계획 → 검토 → 구현 순서로 다시 했다.

## 3. 임베딩을 사내 BGE-M3 로 전환 — 온톨로지 0.4.2

##### 서버 명세 검토
명세 자체는 잘 짜여 있었다. 조용히 망가지는 지점(정규화, base64, index 순서, 정수 배열 입력), `/health` · `/ready` 분리, 429 백프레셔를 짚었다. 보완할 점 8가지를 짚었다.

```
max_length 512 는 문서 임베딩에 짧음 — 청크를 누가 나눌지 명시
모델 revision 노출 — 모델이 바뀌면 벡터 전부 재계산해야 하는데 바뀐 줄 모름
```

## 4. 운영 적재 — 시험 적재에서 `--verify` 버그를 찾음

##### 사전 확인 (PC 에서 읽기만)
Neo4j 5.26.30 community(5.23 이상 충족), 빈 DB · 제약 0 · 인덱스 0, OpenAI 키 200 이었다.

##### 시험 적재 → 확인

```

사이트 노드 전부 present · 직원 전부 active
```

벡터 검색은 "홈페이지 구축 사업" 질문에 0.80 안팎으로 맞게 나왔다. **"인공지능 번역 기술이 있나요"는 사업 인덱스에서 0.72 수준으로 약했다.** 번역은 보유기술 쪽에 있어서, 조회는 두 인덱스를 함께 봐야 한다. 조회 담당에게 넘길 사항이다.

##### 버그 — `--verify` + `--release-store` 는 항상 false
보관소의 최신을 "직전"으로 보고 **다음 릴리즈(순번 2)를 만들어** DB(순번 1)와 비교하고 있었다. 적재(`--write`)에는 영향이 없다. `--verify` 일 때는 보관소 마지막 릴리즈를 "DB 에 들어 있어야 할 것"으로 보고, 그 앞을 직전으로 삼게 고쳤다(`store.parent()`).

##### 순서
운영 DB 비우기(노드·관계·제약·인덱스 전부) → 시험 보관소 폴더 삭제 → 버그 수정 → 오프라인 25 · 섀도우 11 항목 통과 → 섀도우를 비우고 임베딩까지 전체 재실행 → PC 에서 운영 정식 적재 순으로 했다. **DB 를 비우면 보관소도 같이 비워야 한다.** 한쪽만 남으면 짝 검사에서 멈춘다.

## 5. 조회 경로 점검 — 답하는 질문은 조직 소속 하나

##### 조사 결과 (`serving/` · `graph_rag/`)

| 항목 | 상태 |
|---|---|
| 엔드포인트 | `/health/live` · `/health/ready` · `/health/data` · `/v1/graph/search` · `/v1/graph/search-by-question` (뒤 둘 `X-API-Key`) |
| 답하는 질문 | 조직 소속 하나. 고정 Cypher 3개, 문자열 조립 없음, 읽기 전용, 2초 제한 |
| 사업·발주처·보유기술·직원 등 읽는 Cypher | **없음** |
| 벡터 검색 · 질문 임베딩 · `embedding_text` 읽기 | **없음** (요청 스키마에 `embedding` 칸이 있지만 받기만 함) |
| text2cypher · LLM | 없음 (의존성에 LLM SDK 자체가 없음) |
| `removed` 조직 제외 | 조회 Cypher 4곳에 있음 |

##### 버그 — `/health/ready` 가 실패에도 200
`Reader.readiness()` 는 `{"ready": False, "reason": ...}` 딕셔너리를 돌려주는데, API 는 이것을 `bool()` 로 판정한다. **비어 있지 않은 딕셔너리는 참이라 점검이 실패해도 `200 {"ready": true}` 가 나갔다.** 접속·인증 실패는 예외로 503 이 나니, 못 잡는 것은 "붙긴 했는데 쿼리 결과가 실패"인 경우뿐이다. 점검 신호가 거짓을 말하는 종류라 고쳤다(`serving/api.py` 4줄). 응답에 `reason` 을 함께 내고, 정상일 때 응답은 칸 하나만 는다. 도커 healthcheck 와 배포 워크플로는 이 주소를 부르지 않는 것을 확인했다.

##### 배포 뒤 확인 — 질문 규칙

```
ok        웹사업팀은 어디 소속이야?        → 웹사업팀 → 웹사업부 → ㈜나라원시스템
ok        제안실은 어느 조직에 속해?       → 제안실 → ㈜나라원시스템
ok        웹사업부의 상위 조직은?
no_match  우리 회사에서 웹사업팀은 어디 소속이야?   조직명이 맨 앞이 아님
no_match  웹팀은 어디 소속이야?                   완전 일치만
no_match  웹사업팀은 누가 담당해?                 담당·업무 질문은 막아 둠
no_match  나라원시스템 직원이 몇 명이야?  /  홈페이지 구축 사업 한 적 있어?   읽는 코드 없음
```

규칙은 세 가지다. ① 조직명으로 시작, ② 뒤에 조사(은·는·이·가·도·의)나 공백·물음표, ③ `소속` · `상위` · `조직` 중 한 단어.

##### 배포 방식 — SSH 가 쓰이지 않음
Gitea 러너가 서버 안에 설치돼 서버 로컬에서 fetch → checkout → build → up 한다. 운영은 **릴리즈 발행** 시 태그를 checkout(detached HEAD)하고, 개발은 `dev` push 시 별도 checkout 을 `reset --hard` 한다. **워크플로에 적재 명령은 없고, 도커 이미지에 `ingestion/` 도 들어가지 않는다.** 서버에서 적재하려면 SSH 접속 정보가 따로 필요한데, 흔한 SSH 포트가 모두 닫혀 있고 저장소에도 정보가 없다.

## 6. 프론트 연결 — 그래프 연동이 운영 Chatty 에 없음

##### 증상
운영 관리자 화면에서 그래프 모드로 질문하니 "서버의 Graph 진단 응답이 없습니다"가 떴다. 답의 출처는 사이트 조직도 주소가 아니라 Chatty 학습 자료(`나라원 조직도.png`)였다.

##### 경로 — 세 서버가 모두 다름

```
관리자 화면 (나라원 사이트 서버)
  → Chatty /ask (Chatty 서버)                  200 응답 옴
      → Graph API (우리 서버, 운영)             ← 여기가 안 불림
          → Neo4j (DB 서버)                    ready · 질문에 ok
```

화면 HTML 에 채팅 백엔드(채팅 본체 · TTS · STT · `NARA1_GRAPH_CONFIG.askUrl`)가 전부 Chatty 서버의 한 포트로 박혀 있다. **그래프 연동 설정(`NARA1_GRAPH_*`)은 우리 서버가 아니라 Chatty 서버에 들어가야 한다.**

##### 원인 확정 — 프론트는 운영 Chatty, 연동은 개발 Chatty
처음에는 Chatty 도메인 이름에 `dev` 가 있어 프론트가 개발 Chatty 를 본다고 판단했다. **이 판단은 틀렸다.** 다른 프로젝트의 배포 파일과 Chatty 저장소 README 를 확인해 다음을 알아냈다.

| 러너 | 서버 | 배포 대상 |
|---|---|---|
| 우리 서버 러너 | Graph API 서버 | Graph API · AI_Pro_Search · AI_Pro_Trans 등 |
| Chatty 서버 러너 | Chatty 서버 | Chatty 운영 · 개발 둘 다 |

| | 포트 | 배포 방법 |
|---|---|---|
| **운영 Chatty** | 7000 계열 | 태그 push (`v*.*.*-app` 등) |
| **개발 Chatty** | 9000 계열 | `dev` push + 커밋 메시지 `app restart` |

**프론트는 운영 Chatty 를 부르는데, 그래프 연동은 개발 Chatty 에만 올라가 있었다.** 우리 API 문제가 아니다. 해결은 둘 중 하나다. 운영 Chatty 에 연동을 병합하고 설정을 넣거나(운영 반영), 시험용으로 화면의 호출 주소를 개발 Chatty 로 바꾼다. 프론트를 건드리기 어려워 전자가 필요하고, Chatty 담당 영역이다. PC 의 Chatty 저장소 원격 브랜치에서는 `NARA1_GRAPH` 를 찾지 못했다. 원격 정보가 오래됐을 수 있어 어느 브랜치에 들어 있는지는 확인이 필요하다.

##### 결론
**우리 API 에 직접 물으면 정상으로 답한다.** 운영 Chatty 에 연동이 올라가면 조직 질문에 그래프 근거가 붙는다. 연결해도 답하는 질문은 조직 소속 하나다.

## 7. 곁가지 — 사이트 서버 접속과 관리자 AI 화면 요청 경로

##### 사이트 관리자 서버 접속 (MobaXterm)
SFTP 로 시도해 연결이 거부됐다. 포트를 확인하니 **22(SFTP)는 닫혀 있고 21(FTP)만 열려 있었다.** FTP 탭으로 새 세션을 만들고, 목록이 안 뜨면 Passive 모드를 켜라고 안내했다. 세션 폴더 트리 정리 방법(폴더 생성 · 복제 · 번호 접두사)도 정리했다. FTP 는 계정 정보가 평문으로 전송되니 SFTP 지원 여부를 호스팅사에 문의할 것을 남긴다.

##### 관리자 AI 화면 (`admin/ai`, 서버 복제본) 요청 경로
파일 4개(`chatting_graph.htm` · `index2_graph.js` · `graph_ui.js` · `graph_chat.css`)가 요청을 세 층으로 보낸다.

```
외부 AI (하드코딩)   Chatty /ask (그래프·하이브리드) · 에이전트 세션 API · 문서→PDF 뷰어 · 정적 자원 도메인
PHP 변수 기반        ${url1}/ask · /chat/summarize · /chat/keywords/commit · /save/long · /lang_detect · /tts · STT 업로드
                    ($url1 을 정하는 config.php 가 복제본에 없어 실제 도메인은 미확인)
같은 서버 PHP        첨부 업로드 · 사용량 제한 · 도배 방지 · 대화 이력 등
```

브라우저 개발자 도구에서 `ask` 요청에 preflight 가 붙은 것으로 다른 도메인 호출임을 확인했다. 응답 헤더로 `uvicorn` 기반 SSE 스트리밍인 것도 보였다. 응답 헤더에 `access-control-allow-origin: *` 와 `allow-credentials: true` 가 함께 있다. 표준상 같이 쓸 수 없는 조합이고, 아무 사이트에서나 API 를 호출할 수 있다는 뜻이라 Chatty 담당 확인이 필요하다.

## 재사용 가능한 판단

- **삭제는 코드보다 기준이 어렵다.** 기준(보존 기간, 사라짐 판정)이 서기 전에는 빈 껍데기를 만들지 않는다. 지울 상황에서 멈추는 장치가 있으면 미뤄도 안전하다
- **삭제 판단은 적재 순간이 아니라 릴리즈 문서에 싣는다.** 그래야 드라이런으로 미리 보고 기록하고 되돌린다
- **"사라짐"은 셋으로 갈린다 — 사이트에서 빠짐 · 수집 실패 · 파서 회귀.** 수집 매니페스트로 "그 페이지를 실제로 받았나"를 봐야 가른다. 수원에서 이걸 안 봐 22명이 폐지됐다
- **바깥 기준을 DB 에서 뽑으면 검사가 사라진다.** 자기 자신과 비교하게 되기 때문이다
- **짝이 되는 두 상태(DB · 보관소)는 함께 비우고 함께 옮긴다.** 한쪽만 남으면 멈춘다
- **경로 오타는 부모에서 잡는다.** 자동 생성은 부모가 있을 때만
- **바꾸는 비용이 데이터 양에 비례하면 비어 있을 때 바꾼다.** 벡터 차원 전환이 오늘 가장 쌌다
- **`IF NOT EXISTS` DDL 은 정의가 바뀌어도 기존 것을 안 고친다.** 차원 같은 값 변경에는 삭제 후 재생성 단계가 필요하다
- **버전 비교 도구가 무엇을 못 보는지 안다.** `--diff` 는 값 변경을 못 본다
- **시험 적재 뒤 확인 명령을 운영 경로 그대로 돌린다.** `--verify` 버그는 보관소를 붙인 운영 조합에서만 드러났다
- **점검 신호가 거짓을 말하는 버그는 확률이 낮아도 고친다.** 값이 틀린 것보다 "괜찮다는데 안 괜찮은 것"이 위험하다
- **연결이 안 될 때는 층을 끊어서 본다.** API 에 직접 물어 ok 면 우리 쪽이 아니다. 로그에 요청이 찍혔는지로 앞 층을 가른다
- **설정은 호출하는 쪽 서버에 들어간다.** 그래프 연동 설정은 Graph API 가 아니라 Chatty 에 있어야 한다
- **도메인 이름으로 운영·개발을 판단하지 않는다.** `dev` 가 들어간 도메인의 한 포트가 운영이었다. 배포 파일과 서비스 정의를 본다
- **계획을 먼저 말하고 코드를 쓴다.** 오늘 한 번 어겨서 되돌렸다

## 한계

- **운영 적재는 PC 에서 했다.** 보관소(`0001-ffc03472.json` · `index.jsonl` · `latest.txt`)가 PC 에 있다. 다음 적재를 서버에서 하려면 서버 보관소로 옮겨야 한다. 서버에서 적재할 경로(SSH 접속 정보)는 아직 없다
- **PC 적재는 bolt 평문으로 외부 주소를 거쳤다.** 직원 성명·전화번호와 DB 비밀번호가 암호화 없이 전송됐다
- **조회는 조직 소속 질문 하나뿐이다.** 벡터 220개 · 사업 208 · 직원 212 를 읽는 코드가 없다. 사업 인덱스만으로는 보유기술 질문(번역)이 0.72 로 약하다
- **프론트에서 그래프가 붙지 않는다.** 그래프 연동이 운영 Chatty 에 반영돼야 하고, 어느 브랜치에 있는지 확인하지 못했다
- **개발 Graph API 는 떠 있지 않다.** `dev` 브랜치 배포 전이다
- **BGE 서버 인증은 사실상 없다**(`dummy` 통과). GPU 서버 포트가 공인 주소로 직접 응답해 프록시 IP 제한 여부 확인이 필요하다
- **임베딩 모델 이름이 문장 재생성 해시에 섞여 있다.** 모델만 바꿔도 LLM 문장 220건이 다시 생성된다
- **보관소 동시 적재 락이 없다.** 사람 한 명 기준이다
- **`docs/data-load.md` 는 깃 밖이고, `docs/deployment.md` 의 적재 절은 삭제된 옛 명령을 안내한다**
- **노드 삭제 기준(퇴사자 보관 기간)은 인사 쪽에 확인하지 않았다**
- **수원 폐지 판정 문제는 조사만 했고 고치지 않았다**
- **서버·도메인·포트 목록은 일부만 접속해 확인했다.** 나머지는 이름-주소 대응만 봤다
