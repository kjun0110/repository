## 개념

- **`since` 칸 마련** — 선언에 항목을 적되 생긴 버전을 미래(`0.5.0`)로 두어, 현재 버전(`0.4.0`)으로 구우면 빠지게 하는 것. 데이터 없이 칸만 먼저 두는 방법
- **버전 필터 `.at(VERSION)`** — 선언 전체에서 그 버전에 살아 있는 항목만 골라 굽는 것. 없으면 `since` 가 무시되어 미래 칸이 현재 동결본에 섞인다
- **`source_uri`** — 출처 칸의 새 이름. URL(웹 주소)만이 아니라 `db://…` 같은 식별자도 담는다
- **멱등성(추출)** — 같은 원문을 다시 넣으면 같은 후보가 나오는 성질. 적재(MERGE)는 원래 멱등이고, 추출이 비결정적이면 재적재가 멱등이 아니게 된다
- **B 규칙** — 보유기술 소개 추출 규칙. "첫 문단을 소개로 쓰되, 첫 문단보다 하위 h3 가 먼저 나오면 비운다"
- **레코드 단위 대기열** — 후보 하나가 틀리면 배치 전체를 거부하는 대신, 틀린 후보만 빼서 대기시키는 방식. S17 에서 검토

## 요약

[[0911_KG - 나라원 · 선언을 파이썬으로 옮기고, 게시판 HTML은 닫혀 있지 않았다]] 에서 선언을 파이썬으로 옮겼다. 오늘은 **온톨로지를 마무리해 커밋(`7093f4a`)까지 가고, 적재 파이프라인 S7~S12 를 끝냈다.**

오전은 직원 칸이다. 요구받은 칸(성명·직급·직책·역할·입사일·성별·번호·소속)을 `since='0.5.0'` 으로 선언했다. 그 전에 **`build.py` 에 버전 필터가 없어서 미래 칸이 0.4.0 동결본에 경고 없이 섞인다**는 것을 먼저 막았다. 인사 명단(212명)이 도착한 뒤 값을 실측하니 **내가 예로 든 직급·직책 값이 실제와 달랐고, 성별 칸은 원천에 없었다.** 키는 로그인 아이디 재사용을 전제로 `sha256(직원아이디 | 입사일)` 로 정했고, 212명 전원이 선언에 맞았다.

선언 매체는 **YAML 을 권했다가 파이썬 유지로 되돌렸다.** D27 에서 편집기 스키마 방식을 비교에 넣지 않았던 것이 번복의 원인이다. 결론은 "선언을 사람이 편집기로 직접 고치느냐"로 갈리고, 지금은 스크립트로 고치고 곧바로 빌드로 검사하니 파이썬 그대로다. 쓰는 곳이 없는 PyYAML 은 뺐다.

임베딩은 **새 `Chunk` 라벨 없이 기존 라벨 넷에 칸 둘**을 두는 방향만 정하고, 모델 결정은 S19 전으로 미뤘다. 긴 본문이 있는 노드가 16개뿐이라 찾을 대상이 단락이 아니라 문서다.

추출 방식은 "온톨로지와 페이지를 LLM 에 주고 채우게 하는 편이 범용적이지 않냐"는 질문을 따졌다. **반복 크롤링하는 원천에서는 LLM 편차가 매번 변경점이 되어 검토가 반복된다.** 규칙이 뼈대이고 LLM 은 제안만 한다.

오후는 파서다. S7 코드표, S8 엔진, S9 회사·사업분야·사무소, S10 연혁, S11 보유기술, S12 사업실적 게시판을 넣었다. **옛 코드와 전 페이지 대조 차이 0, 게시판 3,018행 + 카드 12 = 3,030 으로 문서 실측과 정확히 일치**했다. 그 과정에서 "첫 h4 앞 문단" 규칙(A)이 멀쩡한 소개 둘을 지운다는 것을 확인하고 B 규칙으로 바꿨다.

## 1. 직원 칸 (0.5.0) — 명단 212명으로 값을 확정

##### 문제
직원 정보를 온톨로지에 넣으라는 요구. 원천은 사이트가 아니라 사내 인사 데이터이고 형식이 정해지지 않았다. 목적은 **칸만 먼저 마련**하는 것이다.

##### 원인 — 선언이 크롤링을 전제로 하고 있었음
모든 노드에 `source_url` 이 필수인데 인사 데이터에는 웹 주소가 없다. 그리고 `build.py` 가 `since` 를 무시하고 선언 전체를 구웠다. `model.py` 는 `since < until` 만 검사해서 **`since='0.5.0'` 을 적어도 0.4.0 동결본에 조용히 섞인다.**

##### 검토한 안과 기각 사유

| 안 | 판정 | 사유 |
|---|---|---|
| `Person` 상위 타입 + `Employee` | 기각 | 사람 종류가 직원 하나뿐. 공통 부모를 묻는 질문이 없음 |
| 출처 칸 이름 유지, `source_url` 에 `db://…` | 기각 | 칸 이름과 내용이 어긋나고, 서빙이 링크로 내보내면 깨진 링크 |
| 키 = `sha256(직원아이디)` | 기각 | 아이디가 재사용되면 새 사람이 퇴사자 노드를 덮어씀. 에러 없이 틀림 |
| 키 = 우리가 매기는 대리키 + 대응 장부 | 기각 | 장부를 잃으면 키가 전부 바뀜. 원천만으로 키를 재생성할 수 없게 됨 |
| 성별 칸 | 삭제 | 명단에 컬럼이 없음 |

##### 택한 안 — `(직원아이디, 입사일)` 해시 + 입사일 정정 탐지
아이디가 재사용되어도 새 사람의 입사일이 달라 키가 갈린다. 약점은 인사팀이 입사일을 정정할 때 한 사람이 둘로 갈리는 것이다. 그래서 적재 시 직전 릴리즈와 비교해 **같은 아이디 · 다른 입사일 · 같은 성명**이면 사람 결정으로 넘긴다.

##### 구현

```
① build.py       declared() (적힌 것 전부) / load(version) (그 버전만) 분리
② 출처 칸         기존 8개 라벨 source_url → source_uri
③ Employee       employee_id · name · rank · position · job_role · contract_type
                 hire_date · mobile_phone · office_phone · work_location · employment_status
                 + 출처 3칸 = 칸 14
   어휘          rank 7 · position 6 · job_role 11 · contract_type 3 · employment_status 2
   MEMBER_OF     팀명이 노드면 팀 → 아니면 부서가 노드면 부서 → 둘 다 없으면 Company 직속
④ --diff         python -m ontology.build --diff 0.4.0 0.5.0
⑤ 문서           D28 (칸 마련) · D29 (실측과 결정)
```

##### 결과 — 명단에서 드러난 것

```
직급      일반직원 · 대리 · 과장 · 차장 · 부장 · 이사 · 대표이사    ← '사원' 없음, 대표이사가 직급
직책      팀원 · 팀장 · 부부서장 · 부서장 · 사장 · 회장              ← 실장 없음
휴대폰    13건이 숫자로 저장돼 앞자리 0 이 빠짐 → 복원
직장번호  빈칸 표시가 세 종류(-- · no-- · -), 실제 번호 16명
입사일    55명이 법인 설립일(2021-10-01) 이전 → 모회사 시절 입사일 승계로 설명 칸에 기록
근무장소  사무소 4곳과 정확히 일치하는 값 0/210 → 관계가 아니라 문자열 속성
팀 없음   '-' 와 'no' 두 표기
```

**내가 제안 단계에서 예로 든 직급·직책 값이 실제와 달랐다.** 어휘를 추측으로 만들지 않고 명단을 받은 뒤 정한 것이 맞았다.

## 3. 선언 매체 — 파이썬 유지, PyYAML 제거 (D32)

##### 문제 — 권고 번복
YAML + 편집기 스키마를 최적으로 권했다. D27 에서 파이썬으로 옮기자고 한 것을 뒤집는 권고였다.

##### 원인 — D27 비교에서 빠진 선택지
D27 에서 파이썬을 고른 결정적 이유는 "오타를 타이핑하는 순간 잡는다"였다. **YAML 도 `model.py` 에서 JSON Schema 를 뽑아 편집기에 연결하면 똑같이 잡힌다는 것을 비교에 넣지 않았다.**

##### 검토한 안

| 형식 | 깊은 중첩 | 설명 적기 | 로직 차단 | 판정 |
|---|---|---|---|---|
| 파이썬 | 보통 | 가능 | 사람이 지킴 | **유지** |
| YAML + 스키마 | 좋음 | 가능 | 형식이 막음 | 선언을 사람이 직접 자주 고칠 때 |
| TOML | 나쁨 — 중첩마다 긴 헤더 | 가능 | 형식이 막음 | 부적합 |
| JSON | 좋음 | 불가 | 형식이 막음 | 부적합 |

##### 택한 안과 이유 — 파이썬 그대로
차이는 오타를 편집 중에 아느냐, 빌드할 때 아느냐뿐이다. 지금은 선언을 스크립트로 고치고 곧바로 빌드·확인 스크립트를 돌린다. 그래서 편집기 검사의 이점이 없고, 한 번 더 바꾸는 번복 비용이 더 크다.

##### PyYAML — 쓰는 곳 0 이라 제거
나중에 만들 `resolutions/*.yaml` 을 읽으려고 남겨 뒀지만 폴더도 읽는 코드도 없다. 그 형식도 YAML 이 아닐 수 있다. **PyYAML 은 따옴표 없는 `no` 를 `False` 로 읽는데, 인사 명단의 "팀 없음" 표기가 실제로 `no` 다.** 사람 결정 파일 형식은 S15 에서 TOML(소수 결정) / CSV(기계가 뼈대를 만드는 표) 중에 정한다.

`uv.lock` 은 마지막 커밋 대비 `pydantic` 두 줄 추가만 남았다. D27 의 "PyYAML 은 안 사라진다" 문장에는 정정 표시를 달았다.

##### 기각 — `declaration.py` → `ontology.py` 이름 변경
`ontology.definition.ontology` 로 경로가 겹친다. 파일 경로로 직접 실행하면 `import ontology` 가 패키지 대신 이 파일을 잡는다. 그리고 `model.py` 의 `Ontology` 클래스와 이름이 어긋난다. 이름은 그대로 두었다.

## 4. 임베딩 — 기존 라벨에 칸 둘, `Chunk` 없음, 모델 결정은 연기 (D31)

##### 처음 권고의 철회 — "그래프 밖 · 온톨로지 밖"
처음에는 텍스트가 약 2만 8천 자라 임베딩을 끄고, 켜더라도 그래프 밖에 두자고 했다. 이 권고는 **임베딩을 보조로 둔다는 전제**였다. 실제 구조는 적재 때 임베딩하고, 벡터 검색을 1순위로, Text2Cypher 를 보조로 쓰는 것이다. 이 구조에서는 적재·DDL·검색·Text2Cypher 네 곳이 같은 사실을 알아야 하므로 **선언에 있어야 한다.**

##### 선언에 둘 것 · 밖에 둘 것

| 선언 | 적재 설정 |
|---|---|
| 임베딩 라벨 · `embedding_text` · `embedding` · 차원 · 유사도 | 모델 이름 · 요약문 틀 · 호출 설정 |

차원은 선언에 둔다. 바뀌면 인덱스와 벡터를 전부 다시 만들어야 하는 스키마 변경이기 때문이다.

##### 대상 라벨

| 라벨 | 임베딩 | 이유 |
|---|---|---|
| Offering (12) | O | 본문 서술, 이름을 모르고 뜻으로 묻는 질문의 주 대상 |
| BusinessArea (4) | O | Offering·BusinessProject 와 같은 검색 안에서 비교돼야 함 |
| BusinessProject (208) | O · 요약문 | 사업명만 넣으면 발주처·연도·분야가 벡터에 안 들어감 |
| HistoryEvent (27) | 선택 | 짧고 적음 |
| Client (82) | X | 이름이 비슷한 다른 기관을 같다고 봄 (nara1graph 실측: 성동구/성북구 0.89) |
| Employee | X | 구조화된 칸 + 개인정보 |
| Company · OrganizationalUnit · Office | X | Cypher·동의어로 정확히 조회됨 |

##### `Chunk` 라벨 — 기각
Neo4j 벡터 인덱스는 노드 하나에 벡터 하나라, 단락마다 벡터를 두려면 조각 노드가 필요하다. 그런데 긴 본문이 있는 노드는 16개(최장 약 7천 자)뿐이다. 검색은 16개 중 어느 문서인지 찾으면 되고, 찾은 뒤 본문을 통째로 넣으면 된다. **판단 기준은 노드 수가 아니라 긴 본문의 양이다.** 도입하게 되면 조각 추가·삭제 때문에 적재에 삭제(D) 구현이 따라온다.

나중을 위한 조각 규칙(소제목 경계, 작은 섹션 합치기, 표는 자르지 않기, 경로 머리말)도 D31 에 남겼다. AI 채팅 페이지 실측으로 섹션 15개가 조각 7개가 된다.

##### 미룬 결정
임베딩 모델(차원·입력 한도), 연혁 포함 여부, 0.4.0 / 0.4.1 여부. **S19 전 결정 권장, 검색 구현 전 필수.** 미결정 표에 Q15 로 추가했다.

## 5. 추출 방식 — 규칙이 뼈대, LLM 은 제안만

##### 문제
두 갈래 질문. ① 오전에 받은 외부 조언(LLM 추출 → 조건 충족 시 적재, 아니면 staging)과 지금 방식 사이의 차이. ② 온톨로지와 페이지를 LLM 에 주고 칸을 채운 뒤 검토하는 방식이 범용적인데 왜 페이지마다 규칙을 잡나.

##### 외부 조언 대조 — 나라원 · 수원 두 파이프라인

| 조언 | 판정 | 사유 |
|---|---|---|
| 타입 계층(멀티 라벨·`extends`) | 보류 | 속성이 다른 하위 타입이 없음. 나라원 `release_writer.py:24` 는 라벨이 하나가 아니면 예외 |
| 스테이징 그래프 → 승격 | 기각 | Neo4j CE 는 인스턴스당 DB 하나. 셰도우를 별도 컨테이너로 두는 현 방식이 CE 의 현실적 형태 |
| `extra` 맵 속성 | 기각 | Neo4j 속성은 맵을 못 담음. JSON 문자열로 넣으면 질의 불가 |
| `Unclassified` · `RELATED_TO {suggested_type}` | 기각 | 추측을 그래프에 들임. 선언에서 `llm_guess` 를 막은 것과 정반대 |
| 흐름 C 검수 결과를 DB 에 바로 반영 | 기각 | 다음 적재의 parity 검사가 "DB 가 예상과 다름"으로 거부. 사람 결정은 `resolutions/` → 릴리즈로 |
| 노드마다 `_onto_version` | 기각 | 한 트랜잭션 원자 적재라 노드마다 다를 수 없음. `ReleaseHead` 한 곳(D15) |
| 집계 리포트 · 드리프트 감지 | 채택 | 규칙 크롤러의 진짜 위험은 사이트 개편 시 에러 없이 건수만 주는 것 |
| 레코드 단위 격리 | 검토 | 납품 후 사이트 한 줄 변경에 전체 적재가 멈추면 고객이 못 고침 → S17 |

수원(`suwon_graph`)에서도 같은 조언을 대조했다. 격리 632건이 있고 `pending.yaml` 질문 49개 중 사람 답변은 0개다. **검수 화면을 만든다고 답이 오지 않으니 질문 수부터 줄여야 한다**는 판정이다.

##### 원인 — 규칙이 맞는 이유
나라원 사이트는 한 번 넣고 끝나는 원천이 아니라 계속 다시 크롤링하는 원천이다.

| | 규칙 | LLM 이 채우고 검토 |
|---|---|---|
| 같은 원문 재실행 | 같은 결과. 달라지면 사이트가 바뀐 것 | 표기·문장이 흔들림. 3,018행이 매번 변경점 |
| 검토 | 규칙을 한 번 | 적재할 때마다 반복 |
| 틀리는 방식 | 멈추거나 빈칸 — 드러남 | 그럴듯한 값 — 검토에서 놓침 |
| 빠짐없음 | 행 수로 확인 | 긴 표에서 행을 건너뛰거나 합침. 세려면 결국 파서가 필요 |
| 키 | 코드로 고정 | 흔들리면 중복 노드 |

**온톨로지 검증은 모양(타입·어휘·필수·방향)만 보고 사실은 보지 않는다.** LLM 이 지어낸 발주처도 어휘가 맞으면 통과한다.

##### 택한 안 — 규칙 뼈대 + LLM 제안 흐름

```
원천 → 규칙 파서 → 확정 후보 → 검증 → 릴리즈 → 그래프
            │
            ├ 규칙이 뽑았지만 확정 못 한 것 ─┐
원천 → 규칙이 못 닿는 내용 ─────────────────┴→ LLM 제안 → 대기 → 사람 승인 → 다음 릴리즈
```

LLM 이 맡을 곳은 잘린 발주처 23종 이름 후보, 기관유형 동률, 조직도에 없는 팀명, 입사일 정정 판정, 비정형 본문·PDF, 빈 description 이다. 적재(MERGE)는 원래 멱등이다. 추출이 비결정적이면 재적재가 멱등이 아니게 되므로, LLM 을 붙일 때는 `(모델, 프롬프트 버전, 원문 sha)` 로 결과를 캐시한다.

미리 넣을 자리는 둘이다. **S15 추출 방법 표시(`rule` / `llm`)**, **S17 레코드 단위 대기열**.

##### 결과
정리 내용을 [[KG_온톨로지 기반 KG 생성 시 고려할 점]] 에 1~4절로 작성하고, 멱등성 비교는 3-1절로 따로 추가했다.

##### S7 — 분류 코드 대응표 (`codes.py`)
스냅샷 4벌에서 게시판 `k`/`v` 를 전수 조사했다. **코드는 짧은 단어가 아니라 문구 전체였다**(`Government of the Republic of Korea` · `a local government` …). 전날 "`a` 같은 모르는 코드"로 본 것은 내 정규식이 공백에서 끊어 잘못 읽은 것이다.

표에 없는 코드 · 표에만 있는 코드             0 · 0

모르는 코드는 예외를 던진다. 사이트가 분류를 바꾸면 여기서 드러난다.

##### S8 — 엔진 (`shapes` · `clean` · `extract` · `run`)

|---|---|---|
| 본문 | 19 | 0 |
| 게시판 | 268 | 0 |

회사개요 이름표-값 쌍, 사무소 h4 구역, 연혁 목록이 같은 모양이라 "구역 목록" 골격 하나로 읽힌다. 게시판 레코드 3,018 + 주요실적 12 = **3,030 으로 문서 실측과 일치**했다. 여러 페이지에 걸친 같은 사업을 묶는 일은 해석기에서 뺐다. 레코드가 원문 한 페이지에 붙어 있어야 출처가 정확하기 때문이며, 묶기는 S15 몫이다.

27 = 자사 8 + 이전 19.

**구분은 연도가 아니라 페이지 구역으로 정한다.** 2021년이 자사(10·11월)와 이전 연혁(1·1·6월) 양쪽에 있어서, 연도로 가르면 5건이 틀린다. 같은 연·월에 여러 건인 곳이 4곳이라 S15 키는 `sha256(연 | 월 | 설명)` 으로 한다. 구분은 키에 넣지 않는다. 사이트가 항목을 다른 구역으로 옮겨도 같은 노드의 구분만 바뀌게 하기 위해서다.

## 7. 보유기술 (S11) — "첫 h4 앞 문단" 규칙은 소개 둘을 지운다

##### 문제
보유기술 12쪽에서 소개(description)를 "본문 첫 문단"으로 뽑으면 **의정정보화 솔루션**의 소개가 틀린다. 이 페이지에는 솔루션 전체 소개가 없고, 첫 문단은 하위 제품(의정자료유통시스템)의 설명이다.

##### 검토한 안과 기각 사유

| 안 | 결과 | 판정 |
|---|---|---|
| 첫 문단 그대로 | 의정정보화 소개가 하위 제품 하나의 설명이 됨 | 기각 |
| A — 첫 h4 보다 앞의 첫 문단 | **17쪽 중 15쪽만 맞음.** 아사프로 CMS 와 사업분야 홈페이지는 h4 `제품개요` 아래에 진짜 소개가 있어 사라짐 | 기각 |
| **B — 첫 문단보다 하위 h3 가 먼저 나오면 비움** | 17쪽 전부 맞음. 사업분야·회사 소개 결과 불변 | 채택 |

의정정보화 페이지의 차이는 h4 가 아니라 h3 에 있었다. 제목 바로 뒤에 하위 제품 제목(h3)이 먼저 나온다.

##### 이름 출처 — 선언 메모가 사실이 아니었음
선언에는 "h3-tit 없으면 서브메뉴 이름, 서브메뉴는 12개를 링크"로 적혀 있었다. 실제로는 좌측 메뉴에 10개만 있고, 이름이 필요한 AI 검색·AI 번역이 거기서 빠진다. 상단 드롭다운(`menuTop2`)은 12쪽 모두에서 같고 두 이름을 갖고 있다. → **h3-tit → 상단 드롭다운 → 둘 다 없으면 멈춤.** AI 번역의 `h3-title` 4개는 화면 문구라 제목으로 인정하지 않는다.

##### 읽기 범위 — 이름으로 지정하면 새 페이지가 조용히 빠짐
12쪽을 이름으로 지정하면 13번째 보유기술이 생겨도 오류 없이 빠진다. `/art/` 아래 전체를 읽고 제외는 명시 목록으로 둔다.

```
index.htm            AI 채팅과 바이트 동일한 복제
homepage_trans.htm   AI 번역 페이지의 탭    ← 문서에 "링크 0개인 고아"로 적은 것은 틀림, 정정
```

대응표에도 제외 목록에도 없는 페이지, 상단 메뉴의 모르는 이름은 멈춘다.

##### body_text — 원문 유지, LLM 요약으로 대체하지 않음
AI 번역 본문은 175줄 중 114줄이 6자 이하의 탭·도움말 문구다. body_text 를 지우고 LLM 요약을 description 에 채우는 안은 기각했다. 기능 목록이나 하위 시스템 넷 같은 내용이 body_text 에만 있고, 생성된 문장이 원문 칸에 섞이면 구분할 수 없으며, 같은 원문이면 같은 결과라는 전제가 깨진다. 잡음은 나중에 검색용 `embedding_text` 에서 처리하고, 빈 description 5곳만 LLM 제안 → 사람 승인으로 채운다(D33).

## 8. 사업실적 게시판 (S12) — 카드 한 장은 제목으로 사업을 정할 수 없다

##### 한 일
게시판 표의 행 하나를 레코드 하나로 뽑는다. 레코드 칸 이름 규칙은 "선언의 속성 이름"에서 "**속성 이름 또는 관계 이름**"으로 넓혔다. 발주처(`ORDERED_BY`)와 분야(`IN_AREA`)가 속성이 아니라 관계라서, 새 이름을 지어내지 않고 선언의 이름을 그대로 쓴다(D34).

```
project_row        268쪽 · 3,018행 · 서로 다른 사업 208
featured_project   카드 12
```

##### 결과

| 확인 | 결과 |
|---|---|
| 기관유형 | 208/208, 사업마다 값 하나 |
| 분야 | 203개 사업 · 256쌍 (분야 없는 사업 5) |
| 연도 탭 ↔ 계약일 연도 | 208/208 일치 |
| 잘린 발주처 | 23종, 원문 그대로 (S13) |
| 멈춤 | 11종 전부 예외 |
| 회귀 | 기존 추출 규칙 8개 건수 · 릴리즈 sha 불변 |

##### 드러난 것 ① — 카드 1장이 게시판 사업 2건과 제목이 같음
카드에는 사업명과 운영 사이트 주소만 있고 날짜·발주처가 없다. "창업기업 확인시스템 유지보수"는 게시판에 계약일 2024-01-02 / 2024-01-11 두 건이 있다. **운영 사이트 주소를 어느 노드에 붙일지 카드만으로는 정할 수 없다.** 문서의 "제목 완전 일치 12/12 라 병합"에 정정 표시를 달았다. S15 에서 사람 결정으로 넘기고, 둘 다 붙이는 안은 둘 중 하나가 틀린 정보라 기각했다.

##### 드러난 것 ② — 같은 발주처의 기관유형이 사업마다 다름
창업진흥원이 한 사업에서는 "재단 및 협회", 다른 사업에서는 "공공기관"이다. 사이트 분류 자체가 일관되지 않다. S13·S15 의 발주처 기관유형 판정 때 다시 본다.

##### 정정 — `cause01/list.htm`
처음에는 "행이 0개인 전체 목록"이라 제외했다. 실제로는 **주요실적 탭**이고 `/cause/index.htm` 과 바이트까지 같은 카드 페이지였다. 제외는 유지하고 사유만 고쳤다.

## 재사용 가능한 판단

- **`since` 를 쓰기 전에 필터부터 만든다.** 미래 버전 칸은 필터가 없으면 에러 없이 현재 동결본에 섞인다
- **어휘는 원천을 받은 뒤 만든다.** 제안 단계의 예시 직급·직책 값이 실제와 달랐다. 먼저 받을 것은 전체 데이터가 아니라 컬럼 정의와 DISTINCT 값이다
- **키는 원천 칸 여러 개의 해시로 만들고, 재사용 전제를 따진다.** 아이디 단독 키는 재사용 시 조용히 덮어쓴다
- **권고를 뒤집을 때는 빠뜨린 선택지를 먼저 적는다.** YAML/파이썬 번복은 편집기 스키마를 비교에 넣지 않은 데서 왔다
- **쓰는 곳이 없는 의존성은 넣지 않는다.** "나중에 쓸 것"이던 PyYAML 은 쓰일 형식조차 정해지지 않았다
- **폴더 경계는 import 규칙과 겹칠 때만 값이 있다.** 밖에서 쓰는 경로가 안 바뀌는 쪽을 옮긴다
- **조각 노드는 노드 수가 아니라 긴 본문의 양으로 판단한다**
- **반복 크롤링하는 구조화 원천에는 규칙, 모양이 제각각이거나 한 번 넣는 원천에는 LLM.** 검증은 모양만 보고 사실은 보지 않는다
- **규칙을 좁히기 전에 그 규칙이 이미 맞히던 페이지를 전부 돌린다.** A 규칙은 문제 페이지는 고쳤지만 멀쩡한 두 곳을 깨뜨렸다
- **대상을 이름으로 나열하지 말고 넓게 읽고 제외를 명시한다.** 나열 방식은 새 페이지를 조용히 놓친다
- **확인 스크립트의 오류를 원문 문제로 보고하지 않는다.** 오늘 두 번(`a` 코드, `<br>` 붙음) 내 스크립트가 원인이었다. 문제를 제기하기 전에 실제 파서 결과로 재현한다
- **원문 칸과 파생 칸을 섞지 않는다.** body_text 는 원문, LLM 결과는 제안이나 검색용 칸에만
- **구분 값은 키에 넣지 않는다.** 사이트가 분류를 옮겨도 같은 노드로 남는다

- **직원 퇴사 판정은 "명단 = 재직자 전원" 가정 위에 있다.** 직전 적재에 있던 사람이 이번 명단에 없으면 `left` 로 본다. 아이디 재사용 여부도 확인이 아니라 가정이다
- **직장번호 규칙은 서울 `02` 9자리 번호를 버린다.** 현재 명단에는 0건
- **명단은 1회 스냅샷이다.** 직원 적재 코드(엑셀 읽기·전화번호 정리·소속 결정·퇴사 판정)는 아직 없다

- **`registry.py` 는 여전히 0.1.0 하드코딩이다.** 새 선언을 런타임이 읽는 것은 S16
