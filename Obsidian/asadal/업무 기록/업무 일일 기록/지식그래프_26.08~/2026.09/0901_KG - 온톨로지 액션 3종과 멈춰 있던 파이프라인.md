## 개념

- **온톨로지 액션** — 적재하는 순간 그래프가 개입해서 하는 일. 게이트·라우팅·검사·추론·계층·전파
- **추론(합성)** — 저장된 적 없는 관계를 원천 관계 두 개 이상을 이어 만들어내는 것
- **요건 검증(D1)** — 클래스별로 "이건 있어야 한다"를 확인하는 것. 미달은 표시만 하고 적재는 한다
- **자기모순 검사(D2)** — LLM이 내린 판정과 LLM이 뽑아낸 내용이 어긋나는지 보는 것
- **일관성 검사(D3)** — 동시에 참일 수 없는 사실을 적재 전에 막는 것
- **`:Entity`** — 벡터 검색 후보를 가리키는 라벨. 이 라벨이 없으면 검색에 섞이지 않는다
- **기준선(baseline)** — 변경 전 결과를 파일로 박아 둔 것. 이후 모든 변경을 여기에 대조한다

## 요약

[[0831_KG - 어휘 경로 신설과 뒤집힌 진단 3건]]에서 검색 품질 병목을 닫고, 남은 것을 적재 쪽으로 옮겼다. 온톨로지 액션 세 가지(추론·검사·계층)를 얹고 게시글을 새 원천으로 넣었다.

```
Issuer 12 · ISSUED_AT 156          발급처 문자열을 관계로 승격
IN_CHARGE_BUREAU 583 · VISIT_FOR 266   저장된 적 없는 답
violations 128 (error 14 / warn 114)   LLM 자기모순이 처음 목록이 됨
Domain 76 · IN_DOMAIN 644          버려지던 breadcrumb 계층 복원
Article 1,060 · POSTED_BY 1,049    게시글 98.9%가 조직에 연결
```

모든 단계에서 **검색 20문항 차이 0건**이고 `:Entity`는 5,910으로 불변이다. 새로 넣은 것 중 벡터 검색에 들어간 것은 없다.

그 과정에서 기존 버그 둘을 밟았다. **`main.py` 전체 실행이 0828 이후 막혀 있었고**, `nodes/14`가 사람을 담당업무 문자열로 식별하고 있었다. 둘 다 파이프라인을 처음부터 돌려서야 드러났다.

## 1. 기준선 — 검증 도구를 먼저 만들고 시작한다

```
data/baseline/
```

## 2. 안전장치 — 제일 큰 라벨이 무방비였다

##### 실측
제약 7개 중 `Place`·`WasteItem`이 빠져 있었다. `Place`는 2,509개로 **제일 많은 라벨**인데 MERGE 키에 유일 제약이 없었다.

```
Place      2,509  place_id   중복 0 · NULL 0
WasteItem    203  item_key   중복 0 · NULL 0
```

##### 결과
제약 7 → 9. 거는 시점에 중복이 없어 실패 없이 걸렸다. 인덱스가 없어 MERGE가 전체 스캔이던 것도 같이 해소된다.

##### 계획에서 뺀 것 — `source` 속성
원래 0단계의 핵심이었으나 **단일 원천이면 값이 하나뿐이라 아무 일도 하지 않는다.** 크롤링만 쓰기로 해서 만들지 않았다. pgvector를 적재하기로 하면 그때 필수다.

##### 정정 — "생애주기 3라벨만 추적"은 틀린 진단이었다
전체의 34%가 방치돼 있다고 봤으나, 실제로는 전략이 넷이다.

| 전략 | 라벨 | 방식 |
|---|---|---|
| 시간축 | OrgUnit · Employee · CivilService | MERGE + `last_seen`/`status`, 이력 보존 |
| 전량 교체 | Place · WasteItem · Issuer · Domain | `DETACH DELETE` 후 재생성 |
| 고아 정리 | Regulation | 부모 관계 없으면 삭제 |
| 부모 종속 | DocumentType · Channel · TargetGroup | 삭제하지 않음 |

`Place`는 추적 밖이 아니라 **매번 통째로 다시 만들어져서** `last_seen`이 필요 없었다. 순수 파생물에는 타당한 설계다.

다만 `DETACH DELETE`가 원천을 가리지 않는다는 점은 남는다. 원천이 둘이 되면 `abolished` 표시가 아니라 **복구 불가능한 삭제**가 된다.

## 3. 발급처 승격 — 대체 관계는 속성이 아니라 구조다

##### 문제
`ontology/documents.py`가 서류명에서 발급처를 판정해 문자열로 남겨 두었다(609종 중 387종). 문자열이라 "이 민원 처리하려면 어디어디 가야 하나"를 물을 수 없었다.

##### 원인 — 값의 성격이 셋으로 갈린다

```
① 진짜 가야 하는 곳   의료기관·은행·세무서 등          106종 (17%)
② 안 떼도 되는 것     접수처 비치·본인 소지·본인 보관   281종 (46%)
③ 모름                (issued_at 없음)                222종 (36%)
```

②를 발급처로 취급하면 "접수처에 비치"까지 가야 할 곳이 되어 정반대 답이 된다. **②가 46%라 무시할 수 없다.**

##### 택한 안
①만 `ISSUED_AT` 관계로, ②는 `no_issue_needed` 플래그로, ③은 아무것도 붙이지 않는다 — "모른다가 정확한 답"이라는 `documents.py`의 방침과 같다.

값을 파싱하지 않고 **표로 적었다.** `issued_at`은 규칙 12개가 만드는 닫힌 목록이라, 구분자로 쪼개는 코드는 규칙이 늘 때 조용히 깨지지만 표는 안 맞는 값이 오면 즉시 멈춘다.

##### 실패 두 번 — 대체 관계를 어디에 붙일 것인가

```
1차  발급처 3개를 그냥 쪼갬
     → "출산 전 지원 = 8곳". 동 행정복지센터·무인민원발급기·정부24를
        셋 다 가라로 읽는다

2차  ISSUED_AT 에 alt_group 속성을 실음
     → '동 행정복지센터'가 두 값에 걸쳐 나와 그룹 2개에 동시에 속하는데
        엣지 하나에 그룹 하나만 실려 덮어써진다

3차  대체 관계가 붙을 자리는 발급처가 아니라 서류
     → issued_at 은 DocumentType 의 단일 속성이므로 한 서류의 ISSUED_AT
        대상들은 언제나 같은 값에서 나온다. 즉 구조적으로 이미 서로 대체다.
        속성을 붙일 필요가 없다
```

**속성으로 표현하려던 것을 구조가 이미 갖고 있었다.**

##### 결과
`Issuer` 12개 / `ISSUED_AT` 156개. 발급처가 여럿인 서류 37종.

## 4. 추론 — 저장된 적 없는 답

##### 만든 것

```
IN_CHARGE_BUREAU  583   HANDLED_BY / PART_OF*    민원 644건 중 583건
VISIT_FOR         266   REQUIRES / ISSUED_AT     민원 88건
```

##### 소관은 가장 가까운 조상 하나만
시장·부시장을 넣으면 모든 민원이 거기로 올라가 답이 되지 못한다(실측: 담당부서에서 거리 3에 시장 562건). 총괄 단위(국·실·사업소·직속기관·구·의회사무국·지방의회) 중 최근접 하나만 남긴다. 담당부서 자신이 이미 총괄인 경우가 있어 거리 0부터 본다.

##### 물질화하지 않은 것
전이 관계(`PART_OF`·`IMPLEMENTS`)는 질의 때 가변 길이로 푼다. 물질화하면 엣지가 폭증하고 조직 개편마다 재계산해야 한다.

##### 계획에서 뺀 것 — 역관계 `HANDLES`
**Neo4j는 관계를 역방향으로 그냥 탈 수 있어서 역관계를 만들면 엣지만 두 배가 된다.** RDF에서는 역속성 선언이 필요하지만 LPG에서는 아니다.

##### 결과

```
5곳  미숙아 및 선천성 이상아 의료비 지원
      의료기관                              출생증명서·진단서·입퇴원확인서·진료비 세부내역서…
      은행                                 지원금 입금계좌통장 사본
      국민건강보험공단                        건강보험료 납부확인서·건강보험증 사본
      대법원… 또는 동 행정복지센터              가족관계증명서
      동 행정복지센터 또는 무인민원발급기 또는 정부24  주민등록등본
```

들를 곳을 셀 때는 발급처가 아니라 **발급처 조합**으로 묶는다. 발급처로 세면 의료기관 서류 6종이 6곳으로 부풀려진다.

## 5. 검사 — LLM의 자기모순이 처음 목록이 됐다

##### 만든 것

```
validate/00_consistency.py   적재 전   D3   원천 JSON 만 보고 판정
validate/01_requirements.py  관계 후   D1·D2
```

D3가 앞인 이유 — 모순은 노드가 생기기 전에 막아야 의미가 있고, 레코드 자체만 봐도 판정된다. D1·D2가 뒤인 이유 — "담당부서가 없다"를 판정하려면 `relationships/03`이 먼저 돌아야 한다.

##### D3 세 규칙 — 전부 위반 0

```
EXTERNAL_ORG_CONFLICT   외부기관 소관인데 수원시 부서 배정      0
UNKNOWN_CONTENT_TYPE    content_type 이 닫힌 어휘 밖           0
DUPLICATE_CIVIL_ID      civil_id 중복                        0
```

파서가 이미 정확히 회피하고 있다. **이 규칙의 값어치는 있는 버그를 찾는 것이 아니라 앞으로 생기지 않게 막는 것이다.** 외부기관 판별은 이 프로젝트에서 이미 한 번 실패해 명시적 목록으로 후퇴한 적이 있다.

##### D1·D2 — 128건

```
!! error  NO_DEPT          7건   담당부서 없음 (external_org 면제)
!! error  PROC_EMPTY       7건   procedure 인데 절차도 서류도 없음
 · warn   PROC_NO_STEPS   44건   procedure 인데 절차 없음
 · warn   PROC_NO_DOCS    70건   procedure 인데 구비서류 없음
```

##### 담당부서 없음이 항상 결함은 아니다
실측 13건 중 6건은 `external_org`가 있다(고용노동부·한국철도공사·경기도·국민신문고). 수원시 소관이 아니라 담당부서가 없는 것이 맞다. 그래서 요건에 면제 조건을 달아 7건만 위반으로 잡는다.

##### 심각도를 갈랐다
`procedure` 51건이 다 같은 결함이 아니다. **절차도 서류도 없는 7건**은 분류 자체가 틀렸을 가능성이 크다(`대형폐기물 인터넷 신고` 195자, `등초본 발급` 254자). 한쪽만 없는 것은 부분 결함이다.

##### 라벨이 아니라 속성으로 표시
`:Violation` 라벨을 검토했으나 `c.violations` 리스트 속성으로 갔다. 라벨은 재실행 때 REMOVE를 빠뜨리면 옛 판정이 남고, 이 프로젝트는 라벨 하나(`:Entity`)가 벡터 검색 입구라 라벨을 늘리는 데 조심할 이유가 있다.

##### 가드가 절대값을 박으면 안 된다
검증에 `:Entity 5909`를 박았다가 걸렸다. 그 수는 `embedding/*`까지 끝난 뒤의 값이고, 검사 지점은 그보다 앞이라 `OrgUnit` 939개가 아직 `:Entity`를 달고 있다(6,658). **"이 스크립트 전후가 같은가"로 바꿨다.**

## 6. 계층 — 깊이는 한 값으로 못 자른다

##### 문제
수집 단계가 breadcrumb을 644건 전부 받아 두고도 `derive_domain()`이 두 번째 조각 하나만 꺼내 `domain` 문자열로 눌렀다. 나머지가 버려진다.

##### 깊이별 실측

| 깊이 | 노드 | 말단 | 민원 1건뿐인 말단 | 말단당 중앙값 | 민원명 충돌 |
|---|---|---|---|---|---|
| 2 | 22 | 20 | 1 (5%) | 21 | 1 |
| 3 | 118 | 97 | 44 (45%) | 3 | 42 |
| 4 | 409 | 333 | 271 (81%) | 1 | 270 |

깊이 4는 사실상 **민원마다 노드를 하나씩 더 만드는 꼴**이라 쓸모가 없다.

##### 원인 — 구역마다 3단계의 뜻이 다르다
깊이 3의 "1건뿐" 44개 중 41개가 `종합민원` 아래였다. 그 구역은 3단계가 곧 민원 페이지 자체다(`종합민원 > 여권민원 > 여권발급 수수료`). 반면 `분야별정보`는 3단계가 진짜 분류다(`복지 > 생애주기별` 92건, `안전 > 3安 도시 수원` 54건).

##### 택한 안 — 구역별 깊이

```
분야별정보 → 3    종합민원 → 2    그 밖 → 2
결과: 노드 76 · 말단 63 · 1건뿐 4개(6%) · 중앙값 6 · 충돌 2개
```

##### 검증식이 틀렸던 것
`domain` 속성과 대조했더니 45건 불일치가 나왔다 — `종합민원` 건수와 정확히 같다. `derive_domain()`이 `분야별정보` 아래에서만 두 번째 조각을 쓰고 그 밖 구역은 최상단 이름을 쓴다. **데이터가 아니라 검증식이 틀렸다.** 1·2단계를 다 후보로 놓게 고쳐 0건.

##### 결과
`Domain` 76 (1단계 2 · 2단계 20 · 3단계 54) / `PARENT_OF` 74 / `IN_DOMAIN` 644. 분야 없는 민원 0건.

```
'복지' 하나로 하위 전부      생애주기별 92 · 생활보장 10 · 장애인 10 · 이주민 10 …
세금 하위 분류              지방세 25 · 세외수입 6 · 납부방법안내 6
```

## 7. 파이프라인이 0828 이후 돌지 않고 있었다

##### 문제
`main.py`를 처음부터 돌리자 두 번째 단계에서 멈췄다.

```
neo4j.exceptions.ConstraintError:
Node(168) already exists with label `OrgUnit` and property `org_id` = '37400690000'
```

##### 원인 — 라벨 조합이 식별자가 되어 있었다

```
embedding/01_build_embeddings.py:56   MATCH (n:OrgUnit) REMOVE n:Entity …
                                      → 0828 롤업 정리로 749개에서 :Entity 제거
nodes/01_org_units.py:38              MERGE (n:OrgUnit:Entity {org_id: …})
                                      → 패턴이 안 맞아 새 노드를 만들려다 유일 제약 위반
```

`:Entity`가 붙은 OrgUnit은 190개뿐인데 MERGE는 939개 전부를 `:OrgUnit:Entity`로 찾는다. 0828에 팀 롤업 임베딩을 제거하면서 생긴 것이고, **그 뒤로 전체 실행을 한 번도 안 해서 드러나지 않았다.**

##### 택한 안
MERGE는 제약이 걸린 `org_id` 하나로만 걸고 `:Entity`는 `SET`으로 붙인다. `nodes/04`도 같은 패턴이라 함께 고쳤다. `Employee`는 이미 단일 라벨로 MERGE하고 있었다 — 같은 사고를 먼저 겪은 흔적이다.

##### 재사용할 판단
**MERGE 패턴에 라벨을 넣으면 라벨 조합이 곧 식별자가 된다.** 다른 스크립트가 라벨을 떼면 조용히 깨진다. 식별은 제약이 걸린 키 하나로만 한다.

## 8. 직원 식별자가 담당업무 문자열이었다

##### 문제

```python
new_id = "live_" + sha1(f"{org}|{pos}|{phone}|{assigned_task}")
```

##### 실측 — 문구가 한 글자만 바뀌면

| 키 | 조직 일치 | 신규 | 폐지 |
|---|---|---|---|
| 업무만 (현행) | 0/934 | 5,076 | 5,052 |

| 전화 우선, 없으면 업무 | 808/934 | 441 | 417 |

##### 이름은 쓸 수 없다
사이트가 직원 이름을 싣지 않아 **5,084명 중 6명(0%)** 에게만 있다.

## 9. 게시글 — 그래프에 넣되 벡터에는 넣지 않는다

##### 규모를 먼저 쟀다
게시판 129개 전수 조사. 사이트 전체를 넣으면 10.8만 건이지만 **최근 1년으로 자르면 연 1,562건**이고, 그중 담당부서 칸이 있어 조직에 연결되는 것만 추리면 더 줄어든다.

##### 왜 벡터에 안 넣나

```
1. 관계가 하나뿐이다(글→담당부서). 민원이 서류·법령·채널·대상층으로
   엮이는 것과 다르다. 그래프의 값어치는 구조 질의에 있다
2. 기존 챗봇이 게시글 본문 벡터를 이미 갖고 있다(12.9만건 중 84%)
3. 주제가 제각각인 글이 후보에 섞이면 민원·조직이 밀린다. 긴 CivilService
   텍스트의 허브 현상(0831)보다 나쁠 수 있다 — 기한 지난 공고가 많은데
   이 그래프에는 시간 감쇠가 없다
```

`Place`·`WasteItem`·`Issuer`·`Domain`과 같은 규칙을 따른다 — `:Entity`를 붙이지 않고 임베딩도 만들지 않는다.

##### 담당부서 매칭 — 두 단계

목록의 담당부서 이름만으로는 동명 조직을 가르지 못한다(`행정민원팀` 44개 동). 상세 페이지에 전화번호가 같이 있다.

```
<th>부서명</th><td>일자리창출팀</td>
<th>전화번호</th><td>031-5191-3273</td>
```

전화로 `Employee → WORKS_AT → OrgUnit`을 타면 조직 하나로 떨어진다. 단 **'이름이 같은 조직 중에서'만** 고른다 — 번호만 보고 고르면 부서가 옮겨간 경우 엉뚱한 조직에 붙는다. 대표번호 `031-5191-2114`는 직원 전화에 없어 오매칭 위험이 없다.

```

미연결 11건 — 동명 5 · 조직 개편 6
```

개편 6건은 전부 2025년 9~10월 글이다(`후생복지팀`·`청소년지원팀`·`교육정책팀`). 과거 글이 과거 조직명을 갖는 것이 맞고, 억지로 붙이면 틀린 사실이 된다.

##### 열은 이름으로 읽어야 한다


## 재사용 가능한 판단

- **MERGE 패턴에 라벨을 넣지 않는다.** 라벨 조합이 식별자가 되어, 다른 스크립트가 라벨을 떼면 조용히 깨진다
- **표를 읽을 때 열은 이름으로 집는다.** 위치로 집으면 표 구조가 조금만 달라도 틀린 칸을 읽는다. 오늘 이 실수를 두 번 했다
- **검증 가드에 절대값을 박지 않는다.** "이 스크립트 전후가 같은가"로 쓴다. 파이프라인 위치마다 정상값이 다르다
- **제약이 붙을 자리를 먼저 묻는다.** 대체 관계를 속성으로 붙이려다 두 번 실패했고, 구조가 이미 그 정보를 갖고 있었다
- **LPG에서 역관계를 만들지 않는다.** 관계를 역방향으로 그냥 탈 수 있어 엣지만 두 배가 된다. RDF의 역속성 선언과 다르다
- **식별자에 자주 바뀌는 값을 넣지 않는다.** 담당업무 문자열이 키에 들어가 있어 문구 수정이 인사이동으로 잡혔다
- **파이프라인은 주기적으로 처음부터 돌린다.** 부분 실행만 하면 단계 간 계약 위반이 쌓인다. 오늘 밟은 버그 둘 다 그래서 숨어 있었다

- **`:Violation` 128건이 검색에 그대로 나온다.** 표시만 하고 걸러내지 않는다
- **선언 파일(TBox)은 만들지 않았다.** 규칙이 파이썬 7곳에 흩어져 있고 전부 정상 작동한다. 새 유형이 들어올 때가 제때다
- **CivilService 임베딩 텍스트가 검색 벡터와 LLM 본문을 겸한다.** 중앙 701자 · 최대 6,000자로 허브 현상의 원인이다. 1,500자 절단이 순위합 -12%로 측정됐지만 1위 적중은 불변이라 미뤘다([[0831_KG - 어휘 경로 신설과 뒤집힌 진단 3건]] 6절)
- **수집 두 건이 진행 중이다.** 게시판 4개 추가(보도자료·시정알림·청렴자료실·해명자료)와 민원사무편람 HWP. 편람은 최신 분기 필터가 제목 형식(`2026년 2분기`)과 안 맞아 398건 전부를 처리하고 있다 — 해롭지 않고 느릴 뿐이다
- **민원사무편람은 수집만 하고 적재하지 않았다.** 판단 근거는 아래 절에 적었다
