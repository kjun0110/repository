## 개념

- **`deletions`** — 릴리즈 매니페스트에 적는 "지워도 되는 것" 목록. 명령이 아니라 **허가**다. 적재기는 `old − new` 중 여기 적힌 것만 지우고, 허가 밖 노드가 DB 에 있으면 쓰지 않고 멈춘다
- **`DELETION_RULES`** — `(판정 함수, 이유)` 표. 지금은 고아 `Capture` 하나뿐이고, 규칙에 걸린 것만 `deletions` 에 담긴다
- **`retention.py`** — 적재가 끝까지 성공한 직후 데이터 폴더를 규칙대로 정리하는 순수 함수. 완주 회차 4개 · 끊긴 회차 7일 · 업로드 kind 당 3개. 저장소는 건드리지 않는다
- **추출 캐시(D63)** — 원문 해시 + 주소 + 규칙 버전을 키로 파싱 결과를 적어 두는 것. 해시 대조는 캐시와 무관하게 늘 한다
- **`readable_shas`** — 적재기가 읽을 수 있는 원문 해시 전부(저장소 첫 수집본 + 데이터 폴더). 캐시 판정에만 쓴다
- **`load_connection`** — 접속 설정만 검사하는 입구. 검색(guided) 설정이 잘못돼 있어도 적재가 멈추지 않게 `load_settings` 에서 갈라냈다
- **guided** — 다른 담당이 넣은 조회 방식(PR #7 · #8). LLM 이 스키마를 보고 Cypher 를 만든다. **DB 의 온톨로지 버전이 코드 버전과 정확히 같아야** 답한다

## 1. 3단계 — 삭제(D)와 보관 정리 (D62)

##### 검토에서 먼저 나온 결함 — 첫 퇴사자에 적재가 멈춘다
퇴사 한 명을 흉내 내 보니 `employees.py` 가 **D56 에서 선언에서 없앤 출처 3칸**(`source_uri` · `source_sha256` · `observed_at`)을 퇴사자에게 찍고 있었다. 출처 관계도 안 달았다.

```
멈춤: 선언 또는 코드 문제라 비율과 상관없이 전부 거부 — UNKNOWN_PROPERTY
```

퇴사자가 아직 없어서 안 드러났을 뿐이다. 사이트 노드(`removed`)는 이미 고쳐져 있었고 직원 쪽만 빠져 있었다. 사라진 노드와 같은 방식으로 **그때의 명단 원문(`Capture`)과 출처 관계를 함께 옮겨** 오게 고쳤다.

##### 택한 안 — 적재기는 스스로 판단하지 않는다
`build_release` 가 "직전 그래프에는 있는데 이번 릴리즈에 없는 노드"를 계산해 규칙 표에 걸린 것만 `deletions` 에 적는다. `write_plan` 은 `old − new` 를 지우되 **허가된 것만** 지운다. 목록이 틀려도 **과삭제가 아니라 멈춤 쪽으로** 틀린다. 삭제 문장은 관계 정리 뒤 맨 마지막이고 같은 트랜잭션이다.

- 온톨로지는 **안 바뀐다**(0.6.1 유지). 매니페스트 칸이 하나 는 것이라 API 재배포도 필요 없다
- 드라이런에서 무엇을 지울지 미리 보인다
- `carry_provenance`(직전 `Capture` 를 전부 옮기던 함수)를 없애고 `removed.py` 의 `Carried` 로 합쳤다. 삭제가 생겼으니 가리키는 것만 옮기면 된다

##### 부작용 점검

| | 판단 |
|---|---|
| 고아를 지우는 적재는 `unchanged` 가 한 번 깨짐 | 정상. 정리 끝나면 다시 `unchanged` |
| 적재가 멈춰 있으면 정리도 안 돎 | 느리게 쌓이고 5단계 알림으로 사람이 안다 |
| 저장소를 지울 위험 | **게이트 항목으로 박았다** — 정리 뒤 저장소 파일 목록이 한 글자도 안 바뀌는지 |
| "회차를 지우면 옛 원문으로 되돌아간다" | 내가 과하게 말했다. 원문은 회차 폴더 밖 `blobs/` 에 있고 최신 회차는 항상 남는다 |
| 수집과 정리 경합 | 5단계 `concurrency` 로 **수집과 적재를 같은 그룹**에 묶는다 |

##### 게이트가 잡은 함정
첫 구현이 `ReleaseHead` 를 "지울 것"으로 넣었다. 매니페스트를 만들 때의 그래프에는 헤드가 아직 없어서다. 그대로 뒀으면 **두 번째 적재부터 무조건 멈췄다.** 비교 전에 헤드를 빼서 고쳤다.

기존 게이트도 손봤다. `gate_056` 8절은 D62 가 **뒤집은 옛 규칙**("옛 수집원문을 쌓아 둔다")을 검사하고 있었다.

## 2. 아키텍처 점검

##### 이미 쓰고 있던 것
CQRS(`ingestion` ↔ `serving`), Plan/Apply, 낙관적 동시성(`expected_before_fingerprint`) + `LOCK_HEAD`, 콘텐츠 주소 저장소(`blobs/<해시>`), 함수형 코어 · 명령형 껍질(⑥단계까지 DB 접속 없음). 일부러 안 쓴 것도 맞았다 — 이벤트 소싱은 `release.json` 에 직원 전화번호가 들어가 **전체 이력 보관이 곧 개인정보 영구 보관**이 된다.

##### 고친 것

| | 문제 | 조치 |
|---|---|---|
| ① | `retention.py` 가 DB 세션을 직접 받아 "세션은 `writers/neo4j.py` 에서만" 규칙을 깼다. 파일 규칙을 시험하려면 Neo4j 가 떠 있어야 했다 | 조회는 `referenced_files(session)` 로 옮기고 `clean` 을 순수 함수로 |
| ② | 정리 실패(`PermissionError` 등)가 **적재 실패로 둔갑** — DB 는 성공했는데 종료코드 1 | `OSError` 를 잡아 사유만 남긴다. 바로 위 임베딩 단계가 이미 쓰던 원칙 |
| ③ | 되돌릴 수 없는 유일한 동작인 삭제가 요약에 안 보임 | `deleted` 칸 추가 |
| ⑤ | `reason` 이 `"orphan_capture"` 하드코딩. 두 번째 규칙이 생기면 영구 기록이 거짓말을 한다 | `DELETION_RULES` 표로. 규칙에 안 걸린 노드는 `deletions` 에 담기지도 않아 이중 방어가 됐다 |
| ⒟ | 거부된 `Capture` 때문에 출처를 잃은 노드를 마지막 재검사가 맨 `ValueError` 로 막아 원인이 안 읽힘 | `ReleaseHalted(report)` 로. 게이트에서 원문 해시를 망가뜨리니 실제로 그 경로를 탔다 |

④ 끊긴 회차 나이를 폴더 mtime 으로 재는 것은 **안 고쳤다.** 서버 폴더를 손으로 만질 일이 없어 mtime 이 흔들릴 이유가 없고, 위험 방향도 "안 지워짐"이다.

##### 알고 미룬 것 — 층 구분
`ingestion/writers/neo4j.py` · `load.py` · `embed.py` 가 `serving/settings.py` 를 import 한다. 쓰기 층이 읽기 층에 의존하는 **방향 역전**이고, 원인은 서빙 이미지가 `serving`·`graph_rag`·`ontology` 만 복사하는 Dockerfile 이다. `config/` 로 옮기려면 `COPY` 한 줄 때문에 **운영 API 재배포**가 필요해 미뤘다(아래 5절에서 이 위험이 실제로 커졌다).

##### 규모가 커졌을 때 — 방향만 확정

| 안 | 판정 |
|---|---|
| (1) 추출 캐시 | **채택.** 무결성 검사는 그대로 두고 파싱만 건너뜀 |
| (2) 라벨별 지문 | **기각.** 아래 3절 |
| (3) 범위 분할(`scope`) | 살아 있음. 한 DB 에 여러 프로젝트가 들어오거나 그래프가 너무 클 때. `deletions` 를 허가 목록으로 만든 게 그대로 맞물린다 |
| (4) 트랜잭션 분할 | 원자성을 잃으므로 마지막 수단 |

측정: 원문 파싱 + 후보 1.02초 · DB 전체 읽기 1.07초(노드 681 · 관계 1,936). **둘을 0으로 만들어도 하루 2초**라, 트리거를 "DB 읽기 10초"로 정하고 상시 계측은 넣지 않았다.

DB 손댐(⒝)은 알림 문구 분리가 대증요법이고 근본은 **Neo4j 읽기 전용 role** 이다. 저장소 코드는 한 줄도 안 바뀌고 `.env` 계정만 가르면 된다. 4단계에서 서버 설정을 만질 때 같이 하기로 했다.

## 3. 라벨별 지문 기각 — 검사는 전부를 만져야 한다

라벨마다 요약 해시를 비교해 DB 전체 읽기를 없애려 했다. 그런데 **운영 · 섀도우 둘 다 순정 Neo4j 5.26.30 이라 APOC 이 없다.** DB 가 서버에서 해시를 못 낸다.

남는 방법은 노드에 `_row_sha` 를 저장하는 것인데, 누가 `name` 만 고치고 `_row_sha` 를 안 고치면 **지문이 그대로라 드리프트를 못 잡는다.** 지금은 이 경우 적재가 큰 소리로 멈추고, 그게 D62 에서 "적재기가 노드를 지워도 된다"고 맡길 수 있었던 근거다. **1초를 위해 그 근거를 내주는 셈**이라 기각했다.

> **검사는 전부를 만져야 검사다.** 파일 해시 대조든 DB 전체 읽기든 캐시로 줄이면 그만큼 보증이 준다. 규모가 커졌을 때 줄일 수 있는 것은 **검사 범위**(부분 릴리즈)이지 검사 자체가 아니다.

APOC 은 그래서 지금 깔지 않는다. 깔려면 운영 DB 재시작이 필요하고, 깔아도 위 문제는 그대로다. 나중에 트랜잭션 분할이 필요해지면 `apoc.periodic.iterate` 때문에 다시 검토한다.

## 4. 추출 캐시 (D63)와 정리

```
<NARA1_DATA_DIR>/cache/extract/<규칙-버전>/<원문 해시>-<주소 해시 16>.json
```

원문이 이미 내용 주소라 **해시가 같으면 결과도 같다.** 해시 대조(`discover`)는 그대로 하고 파싱만 건너뛴다. 데이터 폴더가 없으면 캐시를 쓰지 않아 저장소에 파일이 생기지 않고, `NARA1_EXTRACT_CACHE=0` 으로 끈다. 깨진 캐시는 조용히 다시 계산한다.

```
캐시 없음 1.10초 · 첫 실행 1.46초 · 캐시 적중 0.43초 (원문 292개)
gate_063_cache 15항목 실패 0 — 첫 항목이 "캐시 없이 만든 그래프와 같다"
드라이런 매니페스트 f9281534… 캐시 도입 전과 동일
```

##### `.local` 정리 — 271MB → 1MB
`--output` 산출물 폴더 63개를 지웠다. **그중 `release.json` 92개에 직원 전화번호가 들어 있었다.** 옛 커밋 메시지 · 일회용 진단 스크립트도 정리했다. 못 돌아가는 옛 게이트 2개(`gate_051` · `gate_052`)는 사용자 확인 후 삭제했다.

`docs/data-load.md` 에 "`--output` 폴더는 보고 나면 지운다" 한 줄을 넣자는 내 제안은 **기각됐다.** `docs/` 는 `deployment.md` 말고 전부 깃 밖이라 **읽을 사람이 저장소에 없다.** 진짜 대비는 4단계 워크플로에서 `--output` 을 붙이지 않는 것이다.

## 5. main 머지 — guided 작업과의 충돌 시험

##### 상황
서버 코드가 `v0.1.3-app`(PR #7)이었고, 작업 중 `v0.1.4-app`(PR #8)까지 들어왔다. 둘 다 다른 담당의 조회(guided) 작업이다. **main ← feature 방향**으로 시험 브랜치를 만들어 합쳤다(PR 이 실제로 하는 방향).

```
충돌 0.  main 이 가져온 것은 전부 serving/ · graph_rag/
ingestion/ · ontology/ 는 한 줄도 안 건드림
```

**파일 충돌이 없다고 동작이 맞는 건 아니다.** 우리는 이번에 `capture_id` 를 합치고 `byte_count` 를 뺐다. 그래서 양쪽을 실제로 돌렸다.

| 층 | 확인 |
|---|---|
| 적재 | 게이트 5개 실패 0 · 드라이런 매니페스트 동일 · `load_settings` 호출 정상 |
| 조회 읽기 | 섀도우 실제 그래프에서 guided 읽기 · Chatty 필수 근거 3칸 채워짐 |
| 검색 API | `GuidedEngine.search()` 전체 흐름(LLM 자리만 가짜) — `outcome=ok` |

##### 방향 역전이 실제 위험이 된 지점
PR #8 이 `serving/settings.py` 에 검사를 늘렸다. 적재도 같은 함수를 부르므로 **검색 설정 오타가 적재를 죽인다.** 실제로 터뜨려 확인했다.

```
NARA1_SEARCH_STRATEGY=vector  python -m ingestion.load …
→ ValueError: NARA1_SEARCH_STRATEGY must be guided or template   (DB 근처도 못 감)
```

> **정정.** 처음에 "릴리즈 전에 `.env` 에 guided 키 7개를 넣어야 한다"고 했는데 틀렸다. 전부 코드에 기본값이 있어 `.env` 에 하나도 없어도 통과한다. 위험은 실재하지만 임박한 것은 아니었다.

##### 택한 안 — 파일을 옮기지 말고 함수를 나눈다
사용자 제안대로 `config/` 이동(Dockerfile · 재배포 필요)을 접고 `settings.py` **안에서** 갈랐다.

```python
_environment()  .env · NARA1_ENV · 운영 필수값        공통
_connection()   NEO4J · GRAPH_API_KEY · OPENAI · EMBEDDING
_search()       SEARCH_STRATEGY · GUIDED_*            조회만

load_settings()    이름 · 인자 · 결과 그대로 — 15개 전부 검사
load_connection()  적재용 — 1~9 만 검사
Settings(...)      위치인자 16개 → 키워드
```

검사는 **하나도 지우지 않았다.** 위치인자를 키워드로 바꾼 이유는, 나누다 `guided_timeout` 과 `guided_query_timeout` 이 뒤바뀌어도 타입이 같아 아무도 못 잡기 때문이다. 확인은 **같은 `.env` 로 만든 `Settings` 16칸 전후 대조**(dev · prod 둘 다 동일)로 했다.

## 6. 릴리즈 → 운영 질문 실패 → 적재

##### 증상
`v0.1.5-app` 배포 뒤 챗봇에서 "Graph 검색 연결 실패". API 를 직접 불러 보니:

```json
{"outcome": "unavailable", "reason": "ontology_version_mismatch"}
```

##### 원인
guided 는 **DB 그래프의 온톨로지 버전이 코드 버전과 정확히 같아야** 답한다(`guided_reader.py`). 새 API 는 `nara1-0.6.1`, 운영 DB 는 아직 `nara1-0.6.0` 이었다. 내가 "`SERVING_COMPATIBLE_VERSIONS` 에 둘 다 있으니 안 깨진다"고 했는데, **그 느슨한 규칙은 `/health/data` 에만 적용된다.** 그래서 `ready: true` 인데 질문은 거부됐다.

##### 조치와 결과
PC 에서 운영 DB 에 적재했다(서버 실행은 준비가 더 필요해 질문 복구를 먼저 했다).

```
release_seq 2 · verified true · deleted 96 · embedding generated 0 · verified true
recorded 2026-09-23T06:25:55Z
```

`Capture` 96개 삭제는 D60 에서 해시를 정규화 기준으로 바꿔 전부 새로 생긴 결과다. **임베딩 생성 0** 이라 벡터 220개가 그대로 살아남았다. 조회도 바로 복구됐다(웹개발팀 → 웹사업부 → ㈜나라원시스템).

##### 남길 판단
**온톨로지 버전이 올라가는 릴리즈는 적재를 먼저 하고 릴리즈한다.** 지금까지 순서(릴리즈 → 적재)로는 그 사이에 조회가 막히는 구멍이 생긴다.

## 7. 조회 실측 — 12개 중 10개

조직 상향 · 직원(인원수 포함) · 사업 · 발주처 · 분야 · 보유기술 · 사무소 · 대표자 · 건수는 정상이다. 직원 질문은 출처가 명단 파일로 나온다. 실패한 둘은 **적재도 그래프도 아니라 LLM 이 Cypher 를 잘못 만드는 것**이었다.

| 질문 | 실패 지점 |
|---|---|
| 나라원 연혁 알려줘 | `WITH … ORDER BY …` 뒤에 `collect(...)` 를 이어 붙인 **문법 오류**. 재시도가 1회라 포기 |
| 시스템사업부 밑에 무슨 팀 있어? | 문법은 맞는데 **결과 0건**. `SUB_ORG_OF` 는 아래→위인데 거기서 출발해 화살표를 따라가 상위로 올라갔다 |

고칠 방향은 스키마에 관계 방향을 알려 주기, `NARA1_GUIDED_MAX_REPAIRS` 를 2로, 0건도 피드백하기다. 조회 쪽(PR #7 · #8) 영역이라 **코드는 건드리지 않았다.**

## 8. 4단계 — 서버에서 처음 적재

##### 접속 경로를 찾은 과정
`.62` 22번 포트는 `Connection refused`. 처음 들어간 `dev.chatbaram.com` 은 `110.45.147.56` 으로 **다른 서버**였다(우리 저장소 없음). 확인된 것: 우리 서버는 `aisearch.chatbaram.com`, **SSH 포트 41**, 계정 root, 저장소 주인은 `devuser`, 조회 API 컨테이너가 여기서 돈다. 임베딩 서버는 `.56` 이다.

##### 준비
```bash
mkdir -p /home/chat_bot/nara1-data && chown -R devuser:devuser /home/chat_bot/nara1-data
```
데이터 폴더를 저장소 밖에 두는 이유는 배포가 `git checkout -f <태그>` 로 저장소를 되돌리기 때문이다. 주인을 `devuser` 로, 컨테이너도 `--user devuser` 로 맞춘 이유는 **지금 손으로 하는 실험이 나중 자동 실행과 같은 조건**이 되게 하기 위해서다.

##### 첫 명령이 틀렸다
저장소를 `/app` 에 마운트했더니 이미지의 `/app/.venv` 를 가려 `ModuleNotFoundError: pydantic`. 고친 모양:

```bash
docker run --rm --network host --user devuser \
  -e NARA1_DATA_DIR=/data -e PYTHONPATH=/src \
  -v <저장소>:/src:ro -v <데이터폴더>:/data -w /src \
  ai_pro_neo4j_search-graph-api /app/.venv/bin/python -m ingestion.load --target production --env-file .env [--write]
```

> 4단계를 **추측으로 compose 파일부터 만들지 않고 손으로 먼저** 해 본 이유가 이것이다. 파일에 적었으면 릴리즈를 한 번 더 해야 했다.

##### 결과

| 확인 | |
|---|---|
| 컨테이너에서 Neo4j 내부주소 접속 | OK |
| 이미지에 적재 패키지 | OK(venv 경로만 맞추면) |
| `.env` 읽기 · 저장소 읽기 전용 마운트 · 데이터 폴더 쓰기 | OK |
| **릴리즈 재현성** | `manifest_sha256` 이 **PC 에서 적재한 값과 동일** |
| `--write`(unchanged) | `verified: true` · `embedding.verified: true` · `recorded` 갱신 |

쓰기 경로(`preflight` · MERGE · `DETACH DELETE`)는 `unchanged` 라 안 탔다. 서버에서 재수집을 돌릴 때 확인한다.

## 9. 서버 실행이 처음 드러낸 결함 — 캐시를 매번 버린다

```
"retention": { …, "cache_removed": 195 }     ← 방금 만든 캐시
```

##### 원인
캐시 정리가 **원문 파일(blobs)과 같은 기준**을 썼다.

```
파싱에 쓴 원문   292개   ← 저장소 첫 수집본 전부. 게시판은 연도·쪽마다 파싱해야 한다
그래프의 Capture  97개   ← 페이지당 대표 하나만 (D59, 허브 방지)
남길 기준         97개   ← 저장소는 정리가 일부러 안 보는 영역이라 빠진다
결과             195개 삭제
```

**"쓰는 것만 남긴다"고 해 놓고 쓰는 것을 지웠다.** 매주 292개를 만들고 195개를 버려, 캐시 효과의 3분의 2를 매번 날린다. 동작이나 그래프는 안 깨진다.

##### 조치
`clean()` 에 `readable_shas` 인자를 더해 **캐시 판정에만** 쓰고, `load.py` 가 `manifest_index()`(저장소 + 데이터 폴더의 원문 해시 전부)를 넘긴다. 원문 · 회차 · 업로드 정리 규칙은 그대로다.

게이트가 못 잡은 이유도 고쳤다. **검사에 넘길 해시를 살아 있는 캐시에서 거꾸로 만들어** 넘기고 있었다. 입력을 답에 맞춘 셈이라 무엇을 해도 통과했다. 이제 실제 호출값을 쓰고, "그래프가 몇 개만 가리켜도 파싱에 쓰는 캐시는 남는다"와 회귀 확인 항목을 넣었다.

## 10. 리팩토링과 다음 일감

##### 오늘 한 정리
- **`capture_id` 가 두 가지였다** — `parsers/snapshots.py` 의 내부 키와 `candidates/common.py` 의 그래프 노드 키가 둘 다 `nara1:capture:` 로 시작하는데 값이 달랐다. D62 게이트를 짤 때 실제로 이걸 같다고 봐서 검사가 틀렸다. 키 함수를 `ingestion/keys.py` 로 옮겨 하나로 합쳤다
- 읽는 곳이 없던 `SourceAsset.byte_count` 제거. 사실과 다른 주석 2개 수정
- `collector.py` 802줄 → **494줄**. `collect`(옛 찾기 모드)와 `verify`(적재기가 매번 하는 일)를 걷어냈다. **쪼개기보다 걷어내기가 먼저**다
- `load.py::_run` 115줄 쪼개기는 보류. 소요 시간 계측은 **안 하기로 했다** — 볼 추세가 없다는 사용자 지적이 맞다

##### 아사달 온톨로지 (9/28)
모회사 아사달을 **같은 DB · 같은 릴리즈**에 넣기로 했다. 적재를 따로 두 번 돌리면 서로를 "없어진 노드"로 보고 멈추지만, 한 릴리즈가 그래프 전체를 책임지면 지금 구조 그대로다. 모회사 관계를 이으려면 어차피 같은 릴리즈여야 한다.

입력은 엑셀 하나이고 사이트 수집은 없다. `uploads/` 의 `kind` 로 구분한다(D58). 조회는 guided 스키마가 온톨로지 레지스트리에서 자동 생성되므로 손댈 것이 적다.

**회사를 상수에서 인자로 바꾸는 작업**을 미리 했다. `COMPANY_ID` 가 `"nara1:company:nara1"` 로 박혀 있어, 아사달 직원이 들어오면 **조용히 나라원 소속으로** 붙는다. `contracts.py` 에 `company_id()` · `company_key()` 를 두고 후보 만드는 쪽이 인자로 받게 했다. 회사 판별 로직은 새로 만들지 않는다 — **입력을 읽는 자리가 이미 누구 것인지 안다.** 나라원 키를 넘기면 매니페스트 해시가 그대로다.

## 재사용 가능한 판단

- **새 기능을 붙이기 전에 그 경로를 한 번 흉내 내 본다.** 퇴사자 결함은 삭제 작업이 아니라 그 준비에서 나왔다
- **삭제는 명령이 아니라 허가로 만든다.** 목록이 틀려도 과삭제가 아니라 멈춤 쪽으로 틀린다
- **검사는 전부를 만져야 검사다.** 줄일 수 있는 것은 검사 범위이지 검사 자체가 아니다
- **DB 확인이 끝난 뒤의 곁다리 작업은 적재를 실패시키지 않는다.** 가짜 경보는 진짜 경보를 죽인다
- **되돌릴 수 없는 동작은 요약에 숫자로 보여야 한다**
- **파일 충돌이 없다고 동작이 맞는 건 아니다.** 남의 변경이 같은 영역을 건드렸으면 양쪽을 실제로 돌려 본다
- **구조적 흠을 고치는 것과 실제 위험을 없애는 것은 다르다.** 파일을 옮기면 배포가 흔들리니, 같은 파일 안에서 함수를 갈라 위험만 없앴다
- **같은 이름의 설정이라도 소비자마다 검사 범위가 다르다.** `/health/data` 의 호환 목록과 guided 의 정확 일치를 같은 규칙으로 봤다가 운영 질문이 막혔다
- **스키마를 바꾸는 배포는 적재를 먼저 한다**
- **게이트가 검사값을 검사 대상에서 거꾸로 만들면 무엇을 해도 통과한다.** 실제 호출자가 넘기는 값을 쓴다
- **서버에서 한 번 돌려 봐야 드러나는 것이 있다.** 캐시 결함은 게이트도 PC 적재도 못 잡았다
- **쓰레기를 먼저 버리고 정리한다.** `collector.py` 는 쪼개기 전에 안 쓰는 명령부터 걷어냈다
- **회사·사이트 같은 전제는 상수가 아니라 인자로 받는다.** 전제가 깨지는 순간 조용히 틀린 데이터가 들어간다

## 한계

- **5단계(스케줄)가 남았다.** 스케줄러를 무엇으로 할지 아직 안 정했다(Gitea Actions · cron · systemd timer)
- **서버에서 실제 쓰기 경로를 안 탔다.** `unchanged` 라 MERGE · 삭제 · preflight 는 확인 전이다. 서버 수집(`refresh`)을 돌릴 때 확인한다
- **compose loader 와 실행 방법이 아직 파일로 없다.** 지금은 `docker run` 한 줄을 손으로 친다
- **회사 인자화는 커밋 전이다**(깃은 사용자가 한다). 캐시 수정은 `395d4f8` 로 커밋됐다
- **조직 하향 · 연혁 질문이 실패한다.** LLM 의 Cypher 생성 문제이고 조회 담당 영역이다
- **읽기 전용 Neo4j 계정 분리가 아직이다**
- **층 구분(`ingestion → serving`)은 그대로다.** Dockerfile 을 손댈 때 같이 한다
- **아사달 엑셀은 9/28 에야 받는다.** 그 전에는 온톨로지 선언 · 파서를 설계할 수 없다. 회사가 둘이 되면 "직원 몇 명이야" 같은 질문이 애매해지는 문제도 그때 정한다
