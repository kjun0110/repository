## 1. 법령 계층 — 그리고 그 전에 나온 중복

`IMPLEMENTS`를 얹으려고 보니 **띄어쓰기만 다른 같은 법령이 17쌍/35노드** 있었다.

```
도로교통법시행령(4건)      vs  도로교통법 시행령(1건)
국민기초생활보장법(4건)     vs  국민기초생활 보장법(1건)
도시 및 주거환경정비법(4건) vs 도시 및 주거환경 정비법(1건) vs 도시및주거환경정비법(1건)
```

쪼개져 있으면 "도로교통법에 근거한 민원 전부"가 절반만 반환하고, 계층도 조각난 노드 위에 얹힌다. 대표 표기는 **원문에서 가장 많이 쓰인 것**으로 골랐다 — 어느 쪽이 공식 표기인지 우리가 판단할 근거가 없고, 우세한 표기가 그나마 근거 있는 선택이다.

```
Regulation 210 -> 192    IMPLEMENTS 38건 (시행령·시행규칙 -> 본법)

민방위기본법 근거 민원      3건 -> 4건
식품위생법 근거 민원        3건 -> 4건
도로교통법 시행령 근거 민원  (본법 6건을 반환하던 것) -> 정확히 2건
```

계층은 **아래로만 내려간다** — 본법을 물으면 시행령 근거 민원까지 포함하고, 시행령을 콕 집어 물으면 그것만 나온다.

### 파생 버그 둘

**대표 표기가 어긋나 연결이 끊겼다.** `canonicalize()`가 본법과 시행령의 대표를 각각 독립적으로 고르는 바람에 `자동차손해배상보장법`(본법)과 `자동차손해배상 보장법 시행령`(시행령)의 띄어쓰기가 안 맞아 2건이 안 이어졌다. 계층 매칭을 공백 무시로 바꿔 해결(36 -> 38건).

**대표 표기가 시민 표기와 달라 검색이 깨졌다.** 대표가 `도로교통법시행령`(공백 없음)으로 정해지자 "도로교통법 시행령에 근거한 민원"이 매칭에 실패하고 본법 `도로교통법`만 걸려 6건 전부를 반환했다. 법령명 매칭만 공백 무시(`_longest_match_squashed`)로 바꿨다 — 어느 표기를 대표로 골라도 질의가 맞도록.

## 2. 표 복원 — 버려지던 3,623행

### 무엇이 사라지고 있었나

수집 단계(`_collapse_large_tables`)가 15행 넘는 표를 "머리글 + 예시 3행 + (나머지 생략)"으로 줄인다. 임베딩이 표 노이즈로 뒤덮이는 걸 막으려는 것이라 판단 자체는 옳았지만, 그 대가로 실제 데이터가 사라졌다.

```
표가 있는 페이지  304 / 644     표 634개 / 7,098행
15행 초과 83개 표 -> 버려진 행 3,623행 (51%)
```

사라진 것의 85%는 명부·현황형(상점가 목록, 공중화장실 현황, 중개사무소 명단)이고, 나머지 30개 표 860행이 **시민이 값을 콕 집어 묻는 것들**이었다 — 대형폐기물 스티커 가격표 206행, 무인민원발급기 58행, 민원수수료안내 40행.

### 어디에 담았나

`content`(임베딩 대상)에는 돌려놓지 않았다 — 애초에 압축한 이유가 그거다. 별도 속성 `tables_text`에 담고, 어휘 인덱스에 포함시키고, 답변에는 **질문과 맞는 행만** 골라 넣는다(가장 큰 표가 355행 27,000자라 통째로는 못 넣고, 앞에서 N행만 자르면 92행 가격표 중간의 답을 놓친다).

표는 페이지 하나에 종속된 1:1 데이터라 노드가 아니라 속성이다.

원본 HTML이 `data/raw/civil_service/html/`에 보존돼 있어서 **재수집도 LLM도 필요 없었다** — 그 폴더를 남긴 목적("재수집 없이 파싱 로직만 다시 돌려볼 수 있게")이 그대로 쓰였다.

### 도중에 잡은 문제 셋

**병합 셀(rowspan) 348개가 미처리** — 이게 제일 컸다. 병합된 셀 아래 행이 품명을 통째로 잃고 있었다.

```
전:  냉장고 | 500ℓ 이상 | 8,000
     300ℓ 이상 | 6,000        <- 무엇의 300ℓ인지 모름
후:  냉장고 | 300ℓ 이상 | 6,000
```

두 가지가 동시에 망가져 있었다 — LLM이 그 행을 어느 품목 건지 모르고, `냉장고`가 표에 한 번만 등장해 어휘 검색 점수도 낮았다.

**표 안에서 글자가 띄어져 있었다** — `냉 장 고`, `복 사 기`, 사람 이름 `이 학 보` 등 134개 셀. 표 정렬용 공백인데, 이걸 두면 cjk 바이그램이 '냉장'을 못 만들어 어휘 검색에도 행 매칭에도 안 걸린다.

**행 매칭이 너무 엄격했다** — `토지대장`이 `토지(임야)대장등본`에 안 걸려서 **"무인민원발급기에서 토지대장을 발급받을 수 없습니다"라고 틀리게 답했다.** 괄호 안 부연을 지우고 비교하도록 고쳤다.

### 결과

```
소파 버리려면 스티커 얼마야     -> 1인용 3,000 / 2인용 5,000 / 3인용 7,000 / 4인용 9,000 / 카우치 6,000
장롱 대형폐기물 수수료          -> 폭 120㎝ 이상 8,000 / 미만 6,000 / 60㎝ 이하 4,000 / 받침 2,000
무인민원발급기에서 토지대장     -> 발급 가능, 24시간, 무료
인감증명서 수수료               -> 600원
```

### 표 색인이 제목 검색을 깎아먹은 것 — 그리고 그 이상으로 회복

`tables_text`를 어휘 인덱스에 넣자 4,000자짜리 필드가 생겼고, BM25가 긴 필드에 페널티를 주는 특성 때문에 **표에 우연히 든 낱말이 진짜 제목 일치를 이겼다** — `개요`를 그대로 물으면 제목이 `개요`인 페이지가 밀려나고 본문·표에 '개요'가 든 페이지들이 1~3위를 차지했다(top1 90% -> 88%).

제목에 가중치 5배를 줘서 잡았는데, 부작용 회복을 넘어 **top1 90% -> 92%**로 올라갔다. 제목이 질문과 같다는 건 표 한 칸이 겹치는 것과 비교할 수 없이 강한 근거라, 명시적으로 올려주는 게 맞았다.

## 3. 대상층 축

### 문제

"청년 관련 정책 알려줘"에 벡터검색 top5 중 1건만 상세히 소개하고 끝났다. 이름에 '청년'이 든 민원만 10건인데, 그 10건이 **4개 분야에 흩어져 있어**(교육·청년·청소년 1, 도시 2, 복지 6, 일자리 1) `domain` 축으로도 못 묶였다.

답변 내용 자체는 정확해서 틀린 답처럼 보이지 않는다는 게 오히려 위험했다 — 시민은 "수원시 청년 정책은 이게 다구나" 하고 믿게 된다. 채널이 없어서 "온라인으로 되는 민원 전부"가 한 페이지 목록을 전수인 양 답하던 것과 정확히 같은 구조다.

### 결과

```
(:CivilService)-[:FOR_TARGET]->(:TargetGroup {name})
TargetGroup 12종 / FOR_TARGET 271건 / 대상층 지정 217건

노인 44 · 저소득층 41 · 아동 39 · 장애인 26 · 임산부 23 · 청년 23
한부모 20 · 소상공인·기업 19 · 청소년 14 · 다문화·외국인 14 · 국가유공자 7 · 1인가구 1
```

```
청년 관련 정책 알려줘      -> 청년 대상 민원 총 22건
어르신 지원 사업 전부      -> 노인 대상 44건 (별칭 정규화)
```

### 규칙으로는 못 했다

'지원대상' 절을 정규식으로 훑으면 156건이 잡히는데 정밀도가 나빴다 — `등초본 발급`이 저소득·장애인으로, `인감증명발급`이 장애인으로 잡혔다. 그 단어들이 **수수료 면제 대상 목록**에 있었기 때문이지 그 집단 전용 민원이라서가 아니다.

### 트리거 단어 — `알려줘`를 통째로 넣으면 안 됐다

축을 만들고도 "청년 관련 정책 알려줘"가 안 걸렸다(`알려줘`가 트리거 목록에 없음). 통째로 넣으면 "인감증명 수수료 알려줘" 같은 단일 사실 질문까지 목록으로 답해버린다.

**두 단어로 묶어** 좁게 넣었다(`관련 정책`, `관련 지원`, `지원 사업`, `정책 알려`, `혜택`). 실측으로 목록형 5건은 전부 잡고 단일형 7건("청년 주거 패키지 지원 구비서류 알려줘" 포함)은 하나도 안 걸린다.

## 실패로 끝난 시도 셋 — 다시 하지 말 것

### (a) 교차확증 보존 — 되돌림

"냉장고 버리는 비용"의 정답이 벡터 8위·어휘 7위로 **양쪽 다 상위권인데 어느 쪽에서도 1등이 아니라** 후보에 못 들어왔다. "두 검색이 모두 상위에 올린 후보는 강한 근거"라 보고 보존을 추가했다.

정답을 골라낸 게 아니라 **여러 건을 한꺼번에 넣어 우연히 포함시키는** 방식이었다.

```
[냉장고]   확증 4개 중 정답이 어휘·벡터 양쪽에서 꼴찌  -> 어떤 순위 기준으로도 못 고름
[기초생활] 정답은 이미 어휘 1위인데 노이즈 3건만 추가 -> LLM이 비슷한 후보에 둘러싸여 전부 배제
```

두 번째가 결정적이었다 — 미세먼지 때와 같은 패턴으로 **답이 있는데 "모른다"가 나왔다.** 걷어냈다.

### (b) 대상층 검증 패스 — 걷어냄

구비서류 오추출을 잡았던 처방(추출 후 한 쌍씩 역할 검증)을 그대로 썼는데 **여기서는 안 통했다.** 두 번 조정했고 방향만 반대로 과했다.

```
"애매하면 false" -> 274쌍 중 91건 제거.
                   '임신·출산 진료비 지원'의 임산부, '장애인가정 출산지원금'의 장애인까지 뗌
반대로 조임      -> 이번엔 '한부모가족 지원'의 한부모, '장애인 등록 및 복지카드 신청'의 장애인을 뗌
단독 5건 시험    -> '청년기본소득'을 청년이 아니라고 판정
```

프롬프트가 아니라 **모델 판단 자체가 배치 구성에 따라 흔들린다.** 실측 오분류 7건만 명시적으로 지우는 `TARGET_OVERRIDES`로 갔다(`DOCUMENT_OVERRIDES`와 같은 방식).

### (c) 낱말 빈도 규칙 가드 — 기각

오탐의 패턴이 "해당 낱말이 본문에 0~1회만 스친다"로 보여서 "2회 미만이면 제거"를 재봤다.

```
오탐 6건과 함께 정탐 88건이 죽음
   '미숙아 및 선천성 이상아 의료비 지원'  -> '아동' 0회
   '휠체어 무료 대여서비스'              -> '장애' 0회
   '중·고등학생 교복지원'                -> '아동' 0회
   '긴급복지지원제도'                    -> '저소득' 0회
```

**LLM이 의미로 매핑한 것이 정확히 이 축의 가치**라 그걸 죽이면 안 된다.

### (d) 표 품목명을 임베딩에 넣기 — 측정만 하고 보류

`냉장고`가 임베딩 텍스트에 아예 없어서 벡터 8위에 머무는 게 원인이라 보고, 표의 품목명(150개, 648자)만 임베딩에 추가하는 걸 계산해봤다.

```
냉장고 버리는 비용         8위 -> 1위    개선
세탁기 버리는 값           5위 -> 4위    소폭
300리터 냉장고 폐기 비용  10위 -> 9위    거의 그대로
소파 버리려면 스티커 얼마야 32위 -> 53위  악화
```

**한 질의를 얻고 다른 질의를 잃는 교환**이라 순이득이 불분명했다. "품목명만 넣으면 희석 없이 검색된다"는 가설이 틀렸다 — 150개 품목명 자체가 노이즈다. 1건짜리 문제에 전역 임베딩을 바꿀 이유가 없어 보류.

## 조용히 망가지는 버그 셋

### 캐시 값 별칭 — 데이터 손상

```python
r["target_groups"] = cache[key]   # 같은 리스트 객체를 공유
groups.remove(...)                # 뒤 단계의 제자리 수정이 캐시까지 오염
```

검증 패스를 걷어냈는데도 대상층이 **217건 -> 151건**으로 줄어 있어서 파봤더니 캐시가 이미 손상된 상태였다. 재실행해도 손상된 값이 계속 나왔다. `list(cache[key])`로 복사하고 캐시를 새로 만들었다.

### 배치 하나가 전체를 죽임

644건 중 한 배치에서 LLM이 잘린 JSON을 돌려줘 `JSONDecodeError`로 실행 전체가 중단됐다. 실패 배치만 건너뛰고 캐시에 안 남기게 해서 재실행 시 자동 복구되게 했다(실제로 2배치 10건이 그렇게 채워졌다).

### 문자열 치환의 조용한 실패 — 이번 라운드에만 3회

heredoc으로 코드를 치환하면서 `assert`를 안 걸어 **성공한 줄 알고 넘어간 게 세 번**이었다.

```
FOR_TARGET 절 누락      -> 대상층 축이 629건 전부를 반환
build_text 미적용       -> "품목명을 임베딩에 넣었는데도 안 오른다"는 잘못된 진단으로 이어짐
(이전 세션) BASED_ON 절 -> 지방세법이 629건 전부를 반환
```

두 번은 결과 숫자가 명백히 이상해서 잡혔지만, 세 번째는 **잘못된 결론까지 만들었다.** 앞으로 코드 문자열 치환은 `Edit` 도구를 쓰거나 `assert`를 강제한다.

## 재사용 가능한 판단

- **"두 신호가 모두 상위면 강한 근거"는 순진한 가정이다.** 순위를 합치는 방식은 정답을 골라내는 게 아니라 후보를 늘릴 뿐일 수 있다. 늘어난 후보가 LLM의 배제 로직을 자극하면 답이 있는데도 "모른다"가 나온다.
- **한 곳에서 통한 처방이 다른 곳에서도 통하지는 않는다.** 검증 패스는 구비서류에선 결정적이었지만 대상층에선 두 방향 모두 과했다. 처방을 옮길 때는 그 처방이 통했던 이유가 여기서도 성립하는지 먼저 본다.
- **LLM의 의미 매핑을 규칙으로 대체하려 들지 말 것.** '미숙아 의료비 지원 -> 아동'은 낱말이 하나도 안 겹친다. 그 매핑이 LLM을 쓴 이유인데 낱말 규칙으로 거르면 그걸 죽인다.
- **문자열 치환은 결과를 검증하지 않으면 조용히 실패한다.** 세 번 겪었고, 그중 한 번은 잘못된 원인 진단까지 만들었다.
- **캐시에 담은 가변 객체를 그대로 넘기지 말 것.** 뒤 단계의 제자리 수정이 캐시를 오염시켜, 재실행해도 복구되지 않는 손상이 된다.
- **일괄 처리에서 한 건의 실패가 전체를 죽이면 안 된다.** 실패분만 캐시에서 빼두면 재실행이 곧 재시도가 된다.

**주의**
- 재크롤링은 불필요하지만 **첨부 다운로드는 필요하다** — 지금 보존된 건 HTML 647개뿐이고 파일 자체는 안 받아뒀다. "재크롤링 불필요"라는 요약이 이걸 가릴 수 있다.
- 첨부 링크는 상대경로(`/webcontent/ckeditor/2026/3/25/{UUID}.pdf`)이고 **파일명이 UUID**다. 원래 이름은 링크 텍스트나 표 첫 칸에만 있으므로 다운로드 시 같이 보존해야 한다.
- 기존 챗봇 파서는 `insert_data`(PostgreSQL)·`embed_documents_with_usage`(FAISS)에 묶여 있다. **파싱 부분만 발라내야** 하며, 함수 하나를 부르면 되는 게 아니다.
- 첨부 본문을 `embedding_text`에 넣을지는 측정 후 결정한다 — 위 (d)에서 표 품목명 648자만으로도 다른 질의가 악화됐다. 우선 어휘 인덱스에만 넣는다.

### 그 밖

- **서류 발급처** — "이 서류 어디서 떼요?"에 못 답한다. 다만 `(:CivilService)-[:ISSUES]->(:DocumentType)` 관계로는 **609종 중 7종(REQUIRES 890건 중 44건, 5%)**밖에 못 덮는다 — 많이 요구되는 서류가 대부분 수원시 발급이 아니기 때문이다(통장사본=은행, 진단서=병원, 가족관계증명서=법원, 건강보험료 납부확인서=공단). `DocumentType`에 발급처 속성을 다는 쪽이 커버리지가 넓고, 609종 LLM 분류 한 회면 된다.
- **`FeeTier`(조건부 다단계 수수료 36건)** — 표 복원이 실용적 이득을 대부분 가져가서 우선순위가 내려갔다.
- **`냉장고 버리는 비용`** — 위 (d) 참고. 다른 품목은 전부 답한다.
- **`민방위 교육 안 가면 어떻게 돼`** — 0821에서 이어짐. 96 -> 12위로 올렸으나 top5 진입 실패.
- **온톨로지 `Action`** — 팔란티어 4요소(Object Type / Property / Link Type / Action) 중 Action만 없다. `Graph DB - 구성요소` 노트에서 이미 "RAG는 읽기 작업이라 불필요"로 결론 낸 그대로이고, write-back은 수원시 실제 접수 시스템 연동 문제라 그래프 쪽 일이 아니다. 확장 지점으로만 남겨둔다.
