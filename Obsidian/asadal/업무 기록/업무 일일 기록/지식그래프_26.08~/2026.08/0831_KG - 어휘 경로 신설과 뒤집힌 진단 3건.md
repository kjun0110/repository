## 개념

- **어휘 검색** — 글자가 그대로 겹치는 문서를 찾는 것. 벡터가 뜻으로 찾는 것과 짝
- **cjk 애널라이저** — 한글을 2글자 바이그램으로 쪼개 색인하는 방식. `급수팀장` → `급수`·`수팀`·`팀장`
- **자리 보장** — 어휘가 찾은 후보를 점수 경쟁에 넣지 않고 후보 목록에서 자르지만 않는 것. BM25(30~90)와 코사인(0.7x)은 척도가 달라 섞어 정렬하면 어휘가 무조건 이긴다
- **합의 필터** — 어휘가 고른 조직이 벡터 후보에도 이미 있을 때만 인정하는 것. 새 후보를 주입하지 않으므로 잡음이 늘 수 없다
- **허브** — 아무 질문에나 중간 정도로 가까운 문서. 긴 텍스트일수록 심하다

## 요약

- 어휘 후보 경로를 신설해 직위 조회 1위 적중 **0/12 → 12/12**. `employee_task_index`가 후보를 만드는 데 안 쓰이고 표시용 필터로만 쓰이던 것을 승격
- 두 갈래로 나뉜다. 직위는 `^5` 부스트 + 점수 임계 30, 담당업무는 점수 대신 합의 필터. 업무 쪽 점수는 정답이어도 4~11점이라 절대 임계로 못 가른다
- 미해결 오답 2건 해결. 원인이 서로 달랐다 — `누수 복구 담당`은 점수 뭉침, `수도 계량기 고장나면 어디에`는 긴 민원 텍스트의 허브 현상
- 사이트 대조 미도달 **2.31% → 0.02%**. 남은 1건은 데이터 손실이 아니라 조직 개편 미반영
- 직위를 담당업무 문장의 모양으로 넣고 빼던 규칙을 폐기. 같은 직위가 갈리고 있었다(행정민원팀장 44명 중 43명만)
- LLM 명단의 8칸을 같은 줄이 먹던 문제 해결. 중복 업무 198건에서 서로 다른 업무 +28%, 전화 +21%
- 한글에 영문·숫자가 붙으면 어휘 점수가 반토막 나거나 0이 됨. 어절별 조건부 OR로 해결
- [[0828_KG - 검색 단위 결정과 업무 노드 기각]]의 진단 3건이 측정으로 뒤집혔다

```
사이트 대조 미도달      2.31% → 0.02%
직위 임베딩 반영         845명 → 1,080명
명단 서로 다른 업무      3.30 → 4.23 (중복 업무 198건, 8칸 기준)
```

## 1. 사이트 대조 — 미도달 0.02%, 남은 1건은 조직 개편

##### 문제 — 판정 기준에 따라 숫자가 흔들림

같은 데이터에서 미도달이 8건과 44건으로 갈렸다. 업무를 조각으로 쪼개 세면 분할 규칙이 판정에 섞인다. 업무 노드를 없앤 뒤로 그래프는 담당업무를 통짜 문자열로 갖고 있어 조각 비교의 근거가 사라졌다.

##### 택한 안 — 셀 대 셀, 전화번호로 짝짓기

조직 이름으로 짝지으면 안 된다. 사이트 표 캡션이 시장·의장·부의장 비서실을 전부 `비서실`로만 쓴다. `nodes/14_sync_employees.py`가 같은 이유로 이름 매칭을 안 쓰고 있었다.

기준은 `org_live.json`(08/28 17:04 수집, `<br>` 수정 반영본). 재크롤링하지 않는다 — 그래야 파이프라인 손실만 보이고 사이트 변동이 섞이지 않는다.

##### 결과

```
[이전]  (조직,업무) 쌍 14,303개 중 331 미도달   2.31%
[현재]  직원 5,077명 중 1 미도달              0.02%
```

조직 이름 기준으로 나온 미도달 8건은 **전부 오탐**이었다. 전화번호 4001~4009는 `의장 비서실`·`부의장 비서실`에, 정책실장은 `정책기획과`에 그대로 있다.

전화번호가 없는 410명(8.1%)은 짝을 지을 수 없어 별도로 확인했다. 담당업무 텍스트를 그래프 active 전체와 대조한 결과 **410명 전원 원문 그대로 존재**한다.

##### 남은 1건 — 파이프라인 결함이 아님

```
정책실 / 정책실장 / 031-5191-3861 / "주요 시책·현안 정책결정 보좌"
그래프: 정책기획과 / 정책실장 / status=abolished
```

정책기획과는 없어지지 않았다. 과장은 양쪽 다 있다. 정책실장 자리가 기획조정실 산하 정책기획과에서 떨어져 나와 시장 직속 `정책실`이 됐다(`deptPart=37400650000`, 시장·비서실과 같은 페이지). `14_sync_employees.py`가 조직을 못 찾아 abolished로 표시했고 검색은 `status='active'`만 본다. 조직도 재적재가 필요한 상황이다.

##### `○` 유실 — 3행이 아니라 10행

```
행정민원팀 5810 · 5639 · 7892    동 서무 3행
보육지원팀장 3216 · 7221 · 8341   총괄 3행
돌봄지원팀장 5316 · 7311 · 8863   총괄 3행
위생관리팀 3575
```

내용은 온전하고 `○` 구분기호만 없다. 벡터 이동은 1-cos 0.020~0.035로 이 시스템의 1~10위 점수 폭(0.020~0.055)과 같은 자릿수다. 무시 가능한 크기가 아니다.

다만 `○`를 복원한 판을 만들어 전체 5,075개와 겨루게 하고 14개 질의로 top5를 비교하면 바뀌는 질의가 1개뿐이고(`보육지원팀장이 누구야`의 5위 자리), 정답은 양쪽 다 1위를 유지한다. **영향이 없는 게 아니라 영향이 답까지 도달하지 않는다.** 그대로 둔다.

원인은 문서화된 동작이다. `13_refresh_tasks.py`가 (조직명, 전화)로 1:1 매칭되는 사람만 갱신하고, 전화 공유 416명과 전화 없음 410명은 설계상 갱신 대상 밖이다.

이전 규칙은 `not _MULTI.search(t) and t.endswith("총괄")`이다. **직위는 그 사람이 무슨 일을 하느냐와 독립적인 사실인데, 업무 문장의 생김새로 넣고 뺐다.** 44개 동 중 한 곳만 팀장 신호가 없는 상태였다.

##### 택한 안 — 주무관만 제외

```python
POSITION_STOPWORD = "주무관"
def use_position(position):
    return bool(position) and position.strip() != POSITION_STOPWORD
```

주무관은 3,995명(79%)이라 변별력이 없다. 나머지 624가지 직위는 대부분 조직명을 품고 있어(`급수팀장`·`맑은물정책과장`) 그 자체가 신호다.

##### 결과

주무관 3명은 직위를 잃었다. 담당업무가 우연히 `총괄`로 끝나 이전 규칙에 걸렸던 사람들이다.

##### 위험 점검 — 부팀장 잠식 없음

`부팀장`은 131명으로 주무관 다음으로 흔하다. 흔한 토큰이 서로를 끌어당겨 top5를 먹을 수 있다.

```
'부팀장이 누구야'          top5 중 부팀장 0개
'상수도 특별회계 예산 담당'   0개
```

부팀장 131명은 직위만 같고 조직도 업무도 전부 달라 벡터가 흩어진다. 주무관 3,995명은 직위가 사실상 유일한 공통 토큰이라 뭉친다. 이 차이가 주무관만 빼는 근거다.

`03_employee_embeddings.py` 주석에 기록된 이전 실패(전원에게 붙였더니 "수도 계량기 고장"이 급수팀에서 맑은물정책과로 밀림)는 **재현되지 않았다**. 앞뒤 모두 7위·0.6941로 동일하다. 그때는 업무 노드 11,494개 구성이었다.

## 4. 어휘 후보 경로 — 직위는 임계, 업무는 합의

##### 문제 — 인덱스가 후보를 안 만들고 있었음

`employee_task_index`는 `context.py:51`에서만 쓰였고, 그 쿼리는 `$org_id`로 이미 걸러져 있다. **후보 조직이 정해진 다음 직원을 좁히는 표시용 필터일 뿐 후보를 만드는 데는 쓰이지 않았다.** 후보를 만드는 `lexical_search`는 `civil_text_index`만 조회한다. 조직·직원 질문에는 어휘 후보 경로가 아예 없었다.

##### 갈래 ① 직위 — `^5` 부스트 + 임계 30

```
직위 조회 적중          9/9  (부스트 없으면 8/9, 의사담당관이 법무담당관에 짐)
임계 30에서 양성        39/40
임계 30에서 음성 통과     2/37
```

통과한 음성 2건은 `수원델타플렉스관리운영`→델타플렉스지원팀장(55.8), `수원시 창업지원센터 현황`→창업지원팀장(43.2)으로 사실상 정답이다.

임계가 필요한 이유는 부스트가 잡음도 같이 키우기 때문이다. 무조건 보존하면 일반 질문 12개 중 9개가 쓰레기를 넣었다.

```
'냉장고 버리는 비용'  → 광교박물관팀 "수장고, 유물, 전시 관리"   4.55
'코로나 예방접종'    → 중대산업재해예방팀                    11.14
'전기차 보조금'      → 전기시설팀장                        14.26
```

CivilService 경로가 임계를 못 쓴 것과 갈리는 지점이다. 그쪽은 분포가 겹쳐서(정답 1.20 < 무관 1.32) 점수로 못 가르고 "상위 1건은 자르지 않는다"로만 썼다. 여기서는 겹치지 않는다.

의문사 제거는 필요 없다. `'감사관'`과 `'감사관이 누구야'`가 40.66으로 동일하다.

##### 갈래 ② 담당업무 — 점수 대신 합의 필터

`assigned_task` 필드로만 찾으면 문제의 세 건 모두 정답이 1위다.

```
누수 복구 담당            → 누수보수팀   7.2
누수 신고 어디로          → 누수보수팀   4.3
수도 계량기 고장나면 어디에   → 급수팀     10.8
```

부스트가 없어 점수가 낮고, 임계 10이면 잡음이 38건 중 15건 통과한다. **절대 임계로는 못 가른다.**

그래서 점수 대신 "벡터 후보에도 이미 있는가"로 거른다. 두 방식이 같은 조직을 가리키면 합의고, 어휘 혼자 뽑은 건 버린다. 후보를 새로 주입하지 않으므로 잡음이 늘 수 없다.

##### 기각한 안 — 업무 어휘를 3건까지 승격

직위 조회가 12/12에서 **7/12로 깨졌다**. `감사관이 누구야`에서 감사팀·특정감사팀이 업무 문구로 같이 걸려 감사관 본인을 밀어냈고, `보육지원팀`이 top5에 세 번 나왔다. 직위 일치는 축자 근거가 강하고 업무 일치는 약하다. 강한 쪽이 있으면 약한 쪽은 쓰지 않는 것으로 좁혔다.

##### 구현

```
vector.py     employee_lexical_search()  직위 ^5 · 임계 30
              task_lexical_orgs()        조직 id 만 반환, 합의 필터
pipeline.py   후보 편입 12줄
pipeline.py   중복 접기 seen 에 ("org", name) 등록  ← 없으면 같은 조직이 두 번 나옴
```

##### 결과

```
직위 조회 1위 적중   0/12 → 12/12   (제1부시장은 리더 숏컷이 처리)
일반 질문           18/20 변화, 손실 0
엔드투엔드          오류 0/20
```

일반 질문의 변화는 거의 전부 "담당 조직이 1위로, 민원 페이지가 2위로"다.

```
청소차량 운행 담당    1위 '청소년 상담'(무관)      → 청소팀
전기차 보조금        1위 '한옥건축등보조금'(무관)   → 친환경자동차관리팀
건축 인허가 담당      1위 '국·공유재산 사용허가'(무관) → 건축허가팀
수도 계량기 고장      1위 '상하수도란?'          → 급수팀
```

## 5. 감사관 — 서술 문제가 아니라 검색 문제

```
 1위  0.8322  [감사팀]     감사관 감사팀 서무, 회계, 시민감사관제 운영
 2위  0.8215  [특정감사팀]  감사관 특정감사팀 특정감사팀장 …

18위  0.7663  [감사관]     제1부시장 감사관 감사관 감사관 업무 총괄   ← 본인
```

`감사관`은 조직이면서 감사팀·기술감사팀·조사팀·청렴팀·특정감사팀의 상위 조직이다. 임베딩 텍스트 접두어가 `{상위조직} {조직}`이라 **산하 30여 명이 전부 `감사관`으로 시작한다.** 본인 텍스트는 조직명 반복이라 내용이 없다.

조직 이름과 그 장의 직위명이 같으면서 산하 조직을 가진 곳이 8군데다.

| 조직 | 산하 조직 |
|---|---|
| 제1부시장 | 27 |
| 감사관 | 5 |
| 의사담당관 · 의정담당관 · 홍보기획관 | 4 |
| 공보관 · 법무담당관 | 3 |
| 인권담당관 | 2 |

접두어는 뺄 수 없다. 짧고 흔한 업무가 아무 질문에나 1등이 되는 걸 막는 감쇠 장치이고, 빼면 8/12 → 7/12로 나빠지는 게 0828에 실측돼 있다.

##### 결론

벡터로 풀 문제가 아니다. `employee_task_index`가 `position`을 색인하므로 어휘로 정확히 걸린다. **별도 항목이 아니라 4절의 사례다.**

## 6. 긴 민원 텍스트 — 원인 규명, 두 해법 모두 보류

##### 문제

```
'수도 계량기 고장나면 어디에' 환산 후 상위

 1. [민원] 0.6941  대형폐기물 스티커 판매 가격표   1,302자
 2. [민원] 0.6903  음식물종량제                1,143자
 3. [민원] 0.6892  골목형상점가                5,764자
 4. [민원] 0.6888  수원맛집 100선             1,023자
 5. [민원] 0.6863  공정무역                   1,543자
 7. [조직] 0.6813  급수팀                     ← 정답
```

##### 원인 — 길이와 허브 정도가 단조 증가

서로 무관한 질문 24개에 대한 평균 코사인을 텍스트 길이 구간별로 잰다.

| 길이 | 건수 | 평균 코사인 |
|---|---|---|
| 0~300자 | 81 | 0.2208 |
| 300~800자 | 285 | 0.2290 |
| 800~1500자 | 141 | 0.2352 |
| 1500~3000자 | 99 | 0.2475 |
| 3000~6000자 | 38 | 0.2461 |

차이 0.027은 이 시스템의 1~10위 점수 폭(0.020~0.055)과 같은 자릿수다. **긴 텍스트가 0.68~0.69의 바닥을 만들고, 정답이 그 아래로 내려가는 질문은 잡음에 덮인다.**

##### 기각 ① 허브 보정

노드마다 배경 질문 20개에 대한 평균 코사인을 빼는 방식이다.

```
1위 적중        9 → 9 → 9        (a=0, 0.5, 1.0)
순위합         63 → 57 → 59
기초생활수급자 신청  13 → 16 → 18   악화
```

허브 정도가 질문 방향에 따라 다르게 작용해 스칼라 하나로는 안 풀린다.

##### 기각 ② 텍스트 자르기

644개를 길이별로 재임베딩해 비교한다.

| 방식 | 1위 | 순위합 |
|---|---|---|
| 현행 (최대 6,000자) | 11 | 65 |
| 1,500자 | 11 | 57 |
| 600자 | 11 | 129 |
| 300자 | 11 | 78 |

1,500자만 개선이고 그 아래로는 폭락한다(`기초생활수급자 신청` 13 → 81). 본문 깊숙이 답이 있는 페이지가 죽는다.

##### 결론 — 보류

1,500자 안은 순위합 -12%지만 **1위 적중은 11로 동일**하고 `수도 계량기`도 6위라 top5 밖이다. 어느 질문의 답도 바뀌지 않는다. 4절의 업무 어휘 승격이 이미 엔드투엔드로 1위까지 올려놓았다.

그리고 `embedding_text`가 임베딩 입력이자 LLM에게 보여주는 본문을 겸하고 있어(`synthesize.py`의 `설명:` 줄) 자르려면 두 역할을 분리해야 한다. `RETURN_FIELDS`와 `synthesize.py`까지 손대는 일이라 이득 대비 크다. 규모가 커지면 청킹으로 푸는 게 옳다.

## 7. 토큰화 — 한글에 영문·숫자가 붙으면 어휘가 무너짐

##### 문제

```
'CCTV관제'         3.7   vs  'CCTV 관제'         7.2
'e아동행복지원사업'    2.9   vs  'e 아동행복지원사업'    7.7
'0~5세보육료'       2.4   vs  '0~5세 보육료'       5.1
'제1부시장'         10.4  vs  '제 1 부시장'         16.7
'어디서나FAX민원'      0건   vs  '어디서나 FAX 민원'    11.7
'K-water협약'       0건   vs  'K-water 협약'      2.6
```

데이터에도 흔하다.

| 필드 | 혼합 토큰 | 비율 |
|---|---|---|
| Employee.assigned_task | 639/5,082 | 12.6% |
| Employee.position | 77/5,082 | 1.5% |
| CivilService.name | 14/644 | 2.2% |

4절에서 어휘 경로를 주력으로 만들었으므로 이 경로가 무너지는 질의를 방치할 수 없다.

##### 문서는 안 건드림

띄어쓴 질의로 붙여쓴 문서가 찾힌다. `'어디서나 FAX 민원'` → `어디서나민원(FAX민원)` 9.9점. 재색인이 필요 없다.

##### 기각 ① 무조건 OR

순수 한글 질의가 자기 자신과 OR 되어 점수가 두 배로 뛴다.

```
'감사관'   12.7 → 25.5      '급수팀장'  14.6 → 29.3
```

임계 30 계산이 통째로 깨진다.

##### 기각 ② 치환

붙여쓴 게 정답인 경우에 손해다. `'수원K-뷰티박람회추진TF팀장'` 8.1 → 2.8.

##### 택한 안 — 어절별 조건부 OR

어절마다 경계가 있을 때만 원본과 띄어쓴 판을 OR 한다.

```
"CCTV관제 담당"  →  ((CCTV관제) OR (CCTV 관제)) 담당
"감사관이 누구야"  →  감사관이 누구야                (변화 없음)
```

##### 구현 중 사고 — 부분 이중 계수

처음에는 질의 전체를 OR 했다. 혼합 어절이 하나라도 있으면 **순수 한글 어절까지 양쪽에 들어가 두 번 세어진다.** `담당`이 두 번 세어져 의정담당관이 15.7에서 31.4로 뛰고 임계 30을 넘겼다.

```
CCTV관제 담당        → 의정담당관 31.4
e아동행복지원사업 담당   → 의정담당관 31.4
GIS DB유지관리 담당    → 의정담당관 31.4
```

세 건이 같은 점수인 것이 단서였다. 어절 단위로 바꾸면 15.7로 돌아오면서 혼합 토큰 개선은 그대로 남는다. 4절의 임계 30이 없었으면 조용히 오답으로 나갔다.

##### 결과

```
회귀            직위 조회 0/12 변화 · 일반 질문 0/20 변화 · 엔드투엔드 오류 0/20
어디서나FAX민원    → '어디서나민원(FAX민원)' 1위
수원K-뷰티박람회    → '수원 K-뷰티 박람회 추진 TF팀' 1위, 59.4
CCTV관제 담당     → 영상정보팀 1위
GIS DB유지관리 담당 → 수도기획시설팀 1위
```

## 8. 적재 온톨로지 액션 — 조사

##### 원천 — Chatty `edu/url_edus`가 이미 만드는 것

```
url_normalizer   정규화 URL           → 동일성 판정 키
content_hash     파싱 텍스트 sha256    → 변경 감지
breadcrumb       홈 > 분야 > 하위       → 계층
category         cate_code / parent_cate_code / cate_treecode → 트리
page_classifier  페이지 유형           → 노드 타입 결정
```

##### 온톨로지가 적재 시점에 하는 행동 6가지

| 행동 | 현재 | 필요한 것 |
|---|---|---|
| 게이트 | 스크립트마다 흩어짐, 타입별 규칙 없음 | 타입별 필수 관계표 |
| 라우팅 | `content_type` 2종 | pgvector 유형 → 노드 타입 매핑표 |
| 추론 | 관계 추출은 됨, 계층은 버려짐 | breadcrumb·category → `:Domain` 노드화 |
| 동일성 | URL 기반 MERGE | `content_hash` 도입 → 변경분만 재임베딩 |
| 전파 | 없음 | 파생 노드 6종에 `last_seen`/`status` |
| 보강 | 주소 상속·peer_count | 분야 경로 |

##### 게이트가 타입별이어야 하는 근거

| content_type | 전체 | 담당부서 없음 | 구비서류 없음 | 절차 없음 |
|---|---|---|---|---|
| procedure | 263 | 5 | 77 | 51 |
| reference | 381 | 8 | 372 | 375 |

`reference`는 구비서류·절차가 없는 게 정상이다(381개 중 372·375). `procedure`인데 없는 51개는 결함이다. **타입에 따라 무엇이 필수인지 아는 것이 온톨로지의 일이다.**

##### `source` 없이 pgvector를 넣으면 사고

```cypher
MATCH (c:CivilService)
WHERE c.last_seen <> $batch AND c.status = 'active'
SET c.status = 'abolished'
```

`lifecycle/01_mark_stale.py`에 원천 구분이 없다. pgvector 데이터를 넣은 뒤 웹 크롤링만 돌리면 pgvector에서 온 노드가 전부 abolished 된다. **적재 전에 반드시 `source`를 도입해야 한다.**

##### 생애주기 추적 공백

| 라벨 | 전체 | last_seen | status |
|---|---|---|---|
| OrgUnit · Employee · CivilService | 6,697 | 있음 | 있음 |
| Place | 2,509 | 0 | 0 |
| DocumentType | 609 | 0 | 0 |
| WasteItem | 203 | 0 | 0 |
| Regulation | 192 | 0 | 0 |

Place 2,509개는 민원 페이지의 표에서 뽑은 파생물이다. 페이지가 개편되면 원천에서 사라지는데 그래프엔 남는다. 지금 고아가 0개인 것은 아직 폐지가 일어나지 않았기 때문이다.

`Place.place_id`와 `WasteItem.item_key`는 MERGE 키인데 유일 제약이 없다. 인덱스가 없어 MERGE가 전체 스캔이고, 키가 어긋나도 노드가 하나 더 생길 뿐 아무도 모른다.

##### `domain`이 속성이라 계층을 못 씀

`domain` 12종이 문자열 속성이다. "복지 분야 민원 전부"는 되지만 "복지 > 아동" 하위 분류는 표현할 수 없다. breadcrumb과 `cate_treecode`에 계층이 들어 있는데 버려지고 있다.

## 재사용 가능한 판단

- **판정 기준을 먼저 못박는다.** 같은 데이터에서 미도달이 8건과 44건으로 갈렸다. 기준이 흔들리면 개선 여부를 말할 수 없다
- **그룹을 접는 자료구조가 표본을 왜곡한다.** `{phone: row}` 딕셔너리가 8명 그룹을 1명으로 접어 엉뚱한 비교를 만들었다
- **점수 임계는 신호 종류마다 따로 잡는다.** 직위는 부스트로 40점을 넘지만 업무는 정답이어도 4~11점이다. 한 임계로 둘을 못 가른다
- **점수로 못 가르면 다른 신호의 합의를 쓴다.** 새 후보를 주입하지 않고 기존 후보의 순위만 보장하면 잡음이 늘 수 없다
- **여러 값이 정확히 같은 점수로 나오면 이중 계수를 의심한다.** 세 질의가 전부 31.4였던 것이 단서였다
- **속성의 성질로 판정하고 문장의 모양으로 판정하지 않는다.** 직위는 업무 문장에 쉼표가 있는지와 무관한 사실이다
- **길이는 유사도의 교란 변수다.** 긴 텍스트는 아무 질문에나 중간 점수를 받아 바닥을 만든다. 검색 단위를 정할 때 길이를 봐야 한다
- **한 번에 하나만 바꾼다.** 토큰화와 임계를 같이 바꿨으면 이중 계수 사고의 원인을 못 찾았다
