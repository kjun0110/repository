## 개념

[[0825_KG - 기존 챗봇 연동 하이브리드 RAG 테스트 계획]]대로 연동을 구현한 기록. 그런데 실제 성과는 연동 자체가 아니라 **연동이 드러낸 KG 자체의 버그 4건**이었다.

그래프를 단독으로 쓸 때는 안 보이던 것들이다. 답변을 KG의 LLM이 만들 때는 `synthesize.SYSTEM_PROMPT`가 뒤를 받쳐줬고, 집계 건수는 눈으로 확인할 일이 없었고, 검색 결과를 남에게 넘겨본 적이 없어 URL 중복이 문제가 되지 않았다. **밖으로 내보내니 전부 드러났다.**

| 버그 | 실측 | 처리 |
|---|---|---|
| 집계가 안내 페이지를 민원으로 셈 | 청년 22 → 16, 노인 44 → 24, 도로교통법 6 → 3 | `content_type` 분리 |
| 집계가 이름만 내보냄 | 분야·부서·채널·금액·URL을 전부 버림 | 필드 동반 출력 (377자 → 2,463자) |
| 환각 방지가 통째로 빠짐 | "수원화성 관람료 성인 1,000원" 지어냄 | 근거 블록에 방어 문구 삽입 |
| 같은 원문 URL이면 뒤엣것 폐기 | "등본 떼려면" 정답이 사라짐 | 노드 식별자를 fragment로 부착 |

**최종 상태** — Chatty_Project 수정 0줄. `suwon_graph`에 `api/`·`bridge/` 신규, `search/pipeline.py`·`search/steps/structure.py` 수정.

## 1. 집계가 안내 페이지를 민원으로 세고 있었다

`list_civil_services`가 `RETURN DISTINCT c.name`만 하고 `content_type`을 안 봤다.

수원시 홈페이지에는 신청·처리하는 민원 외에 분류 메뉴·현황표·링크 모음 같은 안내 페이지(`reference`)가 섞여 있다. 그게 전부 민원으로 계산되고 있었다.

```
청년 대상      22건 -> 민원 16 + 안내 7
  안내로 빠진 것: 교육, 사업안내, 주거, 참여·권리, 수원시 창업지원센터 현황,
                청년 행정체험(구 대학생인턴), 청누리
노인 대상      44건 -> 민원 24 + 안내 20
  안내로 빠진 것: 폭염·홍수·호우·가뭄, 대설·한파, 황사, 미세먼지 예·경보제,
                안전관리헌장, 전용차로 등
도로교통법 근거  6건 -> 민원  3 + 안내 3
  안내로 빠진 것: 목적, 법적근거, 전용차로
```

노인은 **절반 가까이가 안내 페이지**였다. 도로교통법은 실제 민원이 의견진술·견인단속·과태료 셋뿐이다.

`synthesize.build_civil_context_block`은 이미 `[민원]`/`[참고자료]`로 나눠 표시하고 있었다 — **개별 답변에서는 구분하는데 집계만 안 하고 있었다.** 같은 그래프를 두 곳에서 다르게 해석한 셈이다.

안내 페이지는 세지 않되 버리지도 않는다. 시민에게 쓸모 있는 것이 섞여 있어서, 건수 밖에 따로 표시한다.

### 파생 — 제목과 본문이 서로 다른 건수를 말했다

브리지가 제목에 붙이는 건수는 `len(hits)`라 안내 페이지까지 셌다. 한 항목 안에서 제목은 "총 23건", 본문은 "민원 16건"이라고 말하는 상태였다.

## 2. 집계가 이름만 내보내고 있었다

그래프에 분야·담당부서·신청경로·지원금액·출처가 다 있는데 집계는 이름만 반환했다.

```
전:  청년 대상 민원은 총 16건입니다:
     마을사랑방 운영, 복지·문화, 원스톱서비스 사전예약, 일자리, ...

후:  - 청년기본소득 [복지 | 교육청년청소년과 | 온라인 신청]
       분기별 지역화폐 25만원 지급(최대 4분기) https://...
     - 취업준비청년 면접정장 무료대여 [복지 | 교육청년청소년과 | 온라인/방문 신청]
       정장 상·하의, 셔츠·블라우스, 넥타이 무료 대여(4일 / 연3회) https://...
```

377자 -> 2,463자. 16건 전부에 URL이 붙는다.

이름 나열로는 **설명과 링크가 붙은 문서 청크와 나란히 놓였을 때 근거로 채택되지 않는다.** 밀도가 낮으면 컨텍스트에 들어가도 무시된다(아래 5절).

`RETURN`에 속성을 늘리면 그룹핑 키가 늘어 같은 이름이 여러 행으로 쪼개진다(같은 이름·다른 URL인 중복 게시물이 실제로 있다). 예전 `DISTINCT c.name`이 해주던 접기를 파이썬 쪽에서 다시 해야 했다.

## 3. 속도 최적화가 환각 방지를 통째로 걷어냈다

기존 챗봇은 외부 검색 결과를 **2초까지만** 기다린다. KG 벡터 경로가 실측 3.5~5.9초라 그대로는 전부 취소된다. 원인은 마지막 답변 합성(`synthesize_answer`, gpt-4o-mini 1회)이었다.

브리지는 근거만 가져가고 답변은 기존 챗봇의 LLM이 만드니, 그 단계를 건너뛰는 스위치(`make_answer=False`)를 넣었다. 0.2~1.0초로 떨어졌다.

**그런데 환각 방지가 거기 들어 있었다.**

```
synthesize.SYSTEM_PROMPT
  "제공된 후보 정보만 근거로 답한다. 후보에 없는 내용은 절대 지어내지 마라"
  "1번을 통과하는 후보가 하나도 없으면 절대 억지로 답을 만들지 말고
   '제공된 정보로는 확실한 답을 찾을 수 없습니다'라고 답해라"
```

원재료만 넘어가고 이 지시는 안 넘어갔다. 실측:

```
질문: 수원화성 관람료 얼마야
KG가 넘긴 후보 5건: 수원화성 헤리티지 콘서트 / 아름답고 착한 작은 결혼식(야외공연장 30,000원)
                  / 수원화성박물관(조직 정보) / 원스톱서비스 사전예약 / 상하수도란?(2021년)
-> 어디에도 관람료가 없는데 "성인 1,000원, 청소년 500원"을 지어냄
```

블록 안에 방어 문구가 아예 없진 않았다("담당부서: 원문에 표기 없음 — 추측하지 말 것", "5년 전 자료 — 금액을 쓰면 단서를 붙일 것"). **"질문한 항목이 후보에 아예 없을 때"만 빠져 있었다.**

근거 블록 앞에 안내를 붙여 복구했다.

```
[지식그래프 후보 — 질문과의 유사도로 뽑은 것이라 질문한 항목이 아예 없을 수 있다.
 아래에 질문이 묻는 값이 그대로 적혀 있을 때만 근거로 써라.
 안 적혀 있으면 이 후보에서 숫자나 사실을 유추해 만들어내지 마라.]
```

수정 후 "구체적인 정보는 제공되지 않았습니다" + 문화예술과 안내로 바뀌었다.

**"모른다고 답해라"가 아니라 "이 후보에서 유추하지 마라"로 좁힌 것이 중요했다.** 전역 거부로 썼으면 혼합 조건에서 기존 RAG가 갖고 있던 정답(2,000원)까지 막혔을 것이다.

## 4. 같은 원문 페이지를 공유하는 민원이 폐기됐다

CivilService 644건의 `source_url`이 643개다. 수원시가 한 페이지에 두 민원을 싣는 경우가 있다.

```
질문: 등본 떼려면 어디로
  주민등록증 발급  .../www01-04-05.jsp
  등초본 발급     .../www01-04-05.jsp   <- 같은 URL. 받는 쪽이 중복으로 보고 버림
```

**정답인 등초본 쪽이 통째로 사라졌다.** 노드 식별자를 fragment로 붙여(`...jsp#3aaaf33d...`) 항목마다 다른 URL이 되게 했다. fragment는 서버로 안 가니 링크가 가리키는 페이지는 그대로다.

37문항 계약 검사를 돌리다 `assert`에 걸려서 찾았다. 눈으로 답변만 봤으면 "등초본이 왜 안 나오지" 수준에서 끝났을 것이다.

## 5. 근거를 넘겨도 답변에 반영되지 않았다 — 원인 규명 4라운드

집계 결과가 컨텍스트에 확실히 들어가는데(`retriever=17`) 답변에는 흔적이 없었다. 원인을 네 번 잘못 짚었다.

```
1차  비율 문제로 봄     -> 밀도 강화(부서·링크 추가)      실패
2차  프롬프트 칸 문제   -> 슬롯 이동, 안내문 추가         그래프만은 개선, 혼합은 그대로
3차  순서 문제 의심     -> 위치 계측: 17건 중 13번째로 밀림  원인 확인
4차  점수 부여로 해결?  -> 등급 자체가 낮아 불가          기각
```

기존 챗봇은 근거 목록을 어휘 일치 수로 다시 줄 세운다. 정렬 키가 `(hit_score, base_score, -idx)`인데 `base_score`는 검색엔진 점수라 **KG 항목에는 그 필드가 없어 0이다.** 동점이면 항상 진다.

게다가 등급 자체가 낮았다.

```
KG 블록   3점 (정책·청년·대상 일치)
RAG 상위  4점 ('청년정책' 복합어까지 일치)
```

점수를 준다고 등급을 넘을 수 없고, 넘기려고 블록에 복합어를 심는 건 점수를 속이는 것이다.

**범주 오류였다.** 재정렬은 같은 코퍼스의 동질적인 문서 청크를 줄 세우는 장치인데, KG 집계 블록은 문서가 아니라 이미 답에 가까운 요약이다.

기존 챗봇 자신도 첨부파일에서 같은 문제를 겪고 같은 방식으로 풀어뒀다.

```
app.py  "첨부 chunk는 일반 검색 결과와 같은 풀에서 경쟁시키지 않는다.
         키워드 재정렬에 밀려 예산에서 잘려나가면 파일 질문의 근거가 사라진다."
```

그 선례대로 KG도 재정렬에서 빼고 선두에 고정했다. 그러자 혼합 답변에 "총 16건입니다"가 나오고 KG 항목과 기존 RAG 항목이 실제로 섞이기 시작했다.

## 6. 연동 구조 — Chatty_Project 무수정

기존 챗봇을 라이브러리처럼 import해서 밖에서 라우트를 얹는다. 소스는 한 줄도 안 바뀐다.

```
전역 python  (neo4j/openai/opik)  -> api/server.py     :9020  KG 검색을 HTTP로
.venv-bridge (기존 챗봇 의존성)      -> bridge/app_kg.py  :9010  기존 챗봇 import + /ask_kg
```

**프로세스를 나눈 이유** — 한 인터프리터에 합치려다 실패했다. `opik -> litellm`이 기존 챗봇의 `openai==1.70.0` 핀과 충돌해 소스 빌드로 backtrack하다 Rust가 없어 죽었다. 브리지는 KG를 HTTP로만 부르므로 neo4j/openai/opik이 필요 없다 — **나누는 편이 실제로 더 간단했다.**

기존 챗봇을 건드리지 않으려고 런타임에서 처리한 것 셋.

| 문제 | 처리 |
|---|---|
| `ai_image.config`이 저장소에 없음 (`.gitignore`의 `config.py`가 하위 디렉터리에도 걸림) | `sys.modules`에 가짜 모듈 등록. 이미지 경로는 채팅이 안 탐 |
| 핀된 `openai==1.70.0`이 `prompt_cache_key`를 모름 (운영은 상위 SDK를 쓰는 듯) | 모델 kwargs 빌더를 감싸 그 인자만 제거. SDK가 지원하면 자동 무력화 |
| 외부 검색 대기 2초 | 환경변수로 10초 |

**주입 지점 2종.** 요청마다 고를 수 있다.

| | quick (`{source}`) | retriever (`{retriever}`) |
|---|---|---|
| 프롬프트 칸 | "학습된 내용 출처" | "학습된 내용" |
| 답변규칙이 지목 | ✗ | ✓ |
| 개수·글자 제한 | 3건 / 1400자 | 없음 (일반 모델) |
| 구현 | 원래 비어 있던 확장 슬롯 | `vector_search` 런타임 교체 |

`retriever` 패치는 요청별 contextvar로 격리한다. 값이 없으면 원본을 그대로 통과시키므로 기존 `/ask` 경로는 구조적으로 영향을 받을 수 없다 — 이 격리가 없으면 토글 OFF 쪽도 오염돼 비교 자체가 무너진다.

**세 조건**을 한 화면에서 순차 실행한다: 기존벡터만 / 그래프만 / 혼합. 그래프만은 private RAG 결과를 버려서 KG 근거만 남긴다.

## 7. 기존 챗봇 학습·색인 구조 (참고)

나중에 다시 조사하지 않으려고 남긴다.

**저장** — `LEARN_LIST` 한 행이 학습 단위 하나. `content`는 본문이 아니라 **원본 URL**이고, `memo1`이 LLM이 만든 요약이다.

```
post   108,200건 (84%)  보도자료·공고
image   10,211건        비전 모델이 img_describe 생성
file     5,802건        hwp/pdf 등 (원본 5,384개로 유일하게 다양)
video    3,097건        전사 + 요약 + segments
url      1,836건        홈페이지 페이지   <- KG가 다루는 영역
text       101건
```

**색인** — 역색인 두 표.

```
SEARCH_TOKEN_LIST       838,267행   단어 사전 (id <-> token_norm)
SEARCH_TOKEN_DOC_MAP 21,820,627행   "이 단어가 몇 번 문서 어느 칸에"
```

한국어라 형태소가 아니라 2~3글자 n-gram으로 자른다(`소파 버리려면` -> 소파, 소파버, 파버, 파버리, 버리). 띄어쓰기와 무관하게 걸리게 하려는 것.

**가중치는 칸 + 매칭 형태**로 정해진다. 문서 1건이 색인 121줄을 만든 예:

```
subject  100   온전한 낱말      대형폐기물, 모바일, 수거, 서비스
subject   90   제목 전체 결합    수원시대형폐기물모바일수거서비스빼기
subject   70   2~3글자 조각     대형, 기물, 물모, 바일, 비스
summary  20~40
keyword  20~40
text_data   10
```

우연한 조각 겹침에는 점수를 덜 주는 구조다. 색인 토큰의 82%가 게시글이고 민원 페이지는 2%다.

**한계 — KG와 갈리는 지점.**

- 점수 순 상위 N개가 전제라 **"전부"를 셀 수 없다**
- 표가 `memo1` 한 문단으로 압축되며 행 데이터가 사라진다 (소파 가격을 "5,000~10,000원 사이"로 지어낸 원인)
- 제목만 맞고 내용은 무관한 문서가 상위로 온다 (예: 대형폐기물 앱 소개 유튜브가 제목 100점인데 요약은 "나쁜 버릇을 버리는 방법"으로 오생성)

---

## 실패로 끝난 시도 — 다시 하지 말 것

**(a) 혼합에서 KG가 묻히는 것을 프롬프트로 풀기 — 4회 실패**

슬롯 이동, 양쪽 동시 주입, 안내문 추가, 밀도 강화. 네 번 다 **그래프만 조건에서는 반응하는데 혼합에서만 안 먹혔다.** 컨텍스트에는 확실히 들어가 있었다(`retriever=17`). 원인은 프롬프트가 아니라 정렬 순서였다(5절).

**(b) `base_score`를 줘서 순위를 올리기 — 측정 후 기각**

동점 타이브레이커라 같은 등급 안에서만 작동한다. KG 3점 / RAG 4점이라 등급을 못 넘는다. **구현 전에 등급을 재본 것이 다행이었다** — 넣었으면 안 먹히는 코드가 남았을 것이다.

**(c) 두 의존성 집합을 한 인터프리터에 합치기**

`opik -> litellm`이 기존 챗봇의 `openai==1.70.0`과 충돌. 프로세스를 나누는 쪽이 더 간단했다.

**(d) `retriever` 슬롯에 quick 크기로 넘기기**

`retriever`는 제한이 없는데 quick 예산(3건/1400자)으로 만들어 보내고 있었다. 집계 목록 16건이 1400자에서 잘렸다. 슬롯마다 예산이 다르다는 걸 코드에 반영해야 했다.

## 재사용 가능한 판단

- **밖으로 내보내면 안 보이던 게 보인다.** 오늘 찾은 KG 버그 4건은 전부 "그래프를 단독으로 쓸 때는 문제가 안 되던 것"이다. 자기 LLM이 뒤를 받쳐주고, 건수를 눈으로 볼 일이 없고, 결과를 남에게 넘긴 적이 없어서였다.
- **속도를 위해 단계를 건너뛸 때, 그 단계가 무엇을 책임지고 있었는지 확인해야 한다.** `make_answer=False`는 3초를 벌었지만 환각 방지를 같이 걷어냈다.
- **같은 데이터를 두 곳에서 다르게 해석하고 있지 않은지 본다.** 개별 답변은 `[민원]`/`[참고자료]`를 구분하는데 집계는 안 했다.
- **남의 정렬 장치에 내 데이터를 태우기 전에, 그 장치가 무엇을 전제하는지 본다.** 어휘 재정렬은 동질적인 문서 청크를 전제한다. 답에 가까운 요약을 같은 자로 재면 항상 진다.
- **선례를 먼저 찾는다.** 첨부파일을 재정렬에서 빼는 처리가 이미 있었고, 주석에 이유까지 적혀 있었다. 같은 문제를 처음부터 풀 뻔했다.
- **구현 전에 가설을 수치로 검증한다.** `base_score` 방안은 등급을 재보니 애초에 성립하지 않았다.
- **계약을 `assert`로 박아두면 눈으로 못 보는 것이 잡힌다.** URL 중복 폐기는 37문항 검사에서 걸렸다.
- **한쪽에만 유리한 지시를 전역으로 쓰지 않는다.** 환각 방지를 "모른다고 답해라"로 썼으면 혼합에서 기존 RAG의 정답까지 막았을 것이다.

## 아직 미해결

- **3조건 전수 측정** — 37문항 x 3조건. 지금은 6문항이고 결론을 낼 수 없는 상태다. 표·집계는 그래프 우위, 그래프 미수록 질의는 기존 벡터 우위까지는 일관되나, 혼합은 질의마다 갈린다(전입신고·청년기본소득은 우위, 노인일자리는 열위). **표본 3개로 "혼합이 이기는 유형"을 정리했다가 네 번째에서 반례가 나왔다** — 전수 측정 전에는 문서에 결론을 남기지 않는다.
- **혼합이 근거 충돌을 못 가린다** — 노인일자리에서 기존 RAG의 "2025년 12월 접수"(지난 회차)와 KG의 "2026년 11~12월"(다음 회차)이 충돌했는데, 둘 다 맞는 값인데도 어느 쪽도 회차를 밝히지 않았다. 프롬프트에 현재 시각과 "일정은 현재 시각 기준으로 답하라"는 규칙이 다 있는데도 그랬다. 컨텍스트를 늘리는 것으로는 안 풀린다.
- **혼합이 상세 조건을 떨어뜨린다** — 같은 질의에서 기존 벡터 단독이 갖고 있던 신청 제외자 조건(생계급여 수급자·직장가입자·장기요양 1~5등급 등)이 혼합에서 사라졌다. 재료가 늘면 요약을 더 세게 하는 것으로 보인다.
- **인용(citation) 동작 미측정** — `retriever` 경로로 넣으면 KG 블록에 각주가 붙는다. 근거 추적 이득인지 노이즈인지 안 봤다.
- **출처 표시 꺼져 있음** — 챗봇 설정이 로컬에서 기본값으로 생성되며 `source_num=0`이라 출처 목록이 표시되지 않는다. 측정 항목 중 "출처가 붙나"를 아직 못 본다.
- **첨부파일 미수집** — 본문 300자 미만 민원 94건 중 상당수가 첨부에만 내용이 있다(서식다운로드 HWP 43개, 공공디자인 진흥계획 PDF 9개 등). 기존 챗봇 `edu/`에 검증된 파서가 있다(pdfplumber+camelot, hwp5txt, openpyxl). 원본 HTML 647개가 보존돼 있어 재수집은 불필요하다.
