## 개념

[[0819_KG - suwon_graph Layer 2 구현 및 디버깅 라운드]]에서 종합민원 44페이지로 검증한 파이프라인을, 분야별정보(deptHome)의 **세금 39페이지 + 복지 151페이지**로 확장한 기록. 데이터가 2.7배 늘면서 기존 설계가 견디지 못한 지점들이 드러났고, 그 과정에서 벡터검색 방식 자체를 바꿨다.

**최종 상태**: CivilService 231 · OrgUnit 939 · Employee 5089 · DocumentType 312 / HANDLED_BY 287 · REQUIRES 515 · PART_OF 937 · WORKS_AT 5089

| 분야 | 건수 | 절차형 | 서류 있음 | 절차 있음 |
|---|---|---|---|---|
| 종합민원 | 45 | 24 | 35% | 31% |
| 세금 | 39 | 12 | 7% | 44% |
| 복지 | 147 | 120 | 64% | 79% |

복지가 압도적으로 알차다 — 지원사업 페이지가 "지원대상 / 지원내용 / 신청방법 / 구비서류 / 문의" 구조를 일관되게 갖고 있어서 스키마와 그대로 맞물렸다.

## 문제 → 수정 → 결과

| 문제 | 수정 | 결과 |
|---|---|---|
| **HNSW 근사검색(ANN)이 진짜 1위 후보를 놓침** — "행정서비스헌장이 뭐야"의 실제 최고점(0.7342)이 top_k=20은 물론 80에서도 안 잡히고 150에서야 나옴. ANN은 미리 만들어둔 이웃 그래프를 따라 일부만 훑기 때문에, **밟히지 않은 노드는 점수 계산 자체가 안 된다**(순위에서 진 게 아니라 후보 명단에 못 오름). 조직도처럼 거의 같은 임베딩이 덩어리로 뭉친 데이터(행정지원과 5개 + 행정관리팀 5개가 0.67~0.70에 밀집)에서 특히 잘 발생 | **전수 스캔 정확검색(exact kNN)**으로 전환 — `vector.similarity.cosine`으로 모든 노드와 비교 | 998노드에서 52ms(ANN 18ms 대비 +34ms) — LLM 호출에 수 초 쓰는 파이프라인에선 무시할 비용. k를 올리는 땜질을 끝냄(이전에도 노드 ~960개일 때 k=5가 정자동 정답을 놓쳐 20으로 올린 전례가 있고, 데이터가 늘면 다른 노드가 밀려나므로 임계값 조정은 근본 해결이 아님) |
| exact kNN 전환 후 지역 답변이 깨짐 — "팔달구 반려동물 등록"의 정답인 팔달구 산업팀은 0.688로 50위권이라 풀(20)에 아예 못 들어옴 | 풀을 60으로 넓히되, region_hit이 폭증하지 않도록 "법정동 관할 행정동"은 전부 보존하고 "구 산하라서 걸린" 후보만 상위 3개로 제한 | 지역 질의 정상 복구. 참고로 이 케이스는 원래 맞는 답이었는데(산업팀 업무에 실제로 "반려동물 등록"이 있음) 중간에 모른다고 하던 상태였다 |
| 이름만 같은 조직이 검색 상위를 독식 — "재산세 세율"에서 재산세팀 3개 + 재산세1·2팀이 top5를 채워 정작 세율표가 있는 민원 페이지가 10위로 밀림 | 지역 미언급 질문에서는 동명 조직을 하나로 접고, 민원 후보가 하나도 없으면 최하위 조직 자리를 최상위 민원에게 양보 | 세율표를 정확히 답변 |
| "구마다 있는 업무"인데 특정 지점을 찍어 안내 | 같은 이름 조직이 몇 개 구/동에 반복되는지 그래프에서 계산해 `peer_count`/`peer_scope`로 심고, 컨텍스트에 "거주지 관할로 안내할 것" 지시 첨부 | "전입신고 → 거주지 관할 구의 종합민원과", "건축 허가 → 거주지 관할 구에서 처리" 등 회귀 전반에서 10종 이상 확인 |
| 위 계산이 보건소 계열을 통째로 누락 — 구/동 산하만 세는 규칙이라 직속기관인 보건소 밑 조직(건강관리과 4개 등)이 안 걸림 | 전역 동명 카운트를 기본으로 하고, 부모가 전부 구/동일 때만 더 구체적인 라벨을 붙이는 순서로 뒤집음 | '기관' 단위 27종/115노드가 새로 포착 |
| 담당자정보 footer가 아예 없는 페이지 29건 — 복지 생애주기별은 본문 "문의" 섹션에만 기관이 적힘 | 3순위 매칭 추가: 문의 섹션에서 OrgUnit 실명과 일치하는 것만 연결(추측 없음). 상위기관+부서가 함께 적힌 줄은 PART_OF로 이어질 때만 하위 부서 사용 | 20건 연결(구별 보건소 4곳 나열 시 4개 다 연결). 외부기관 8건·정보없음 3건은 정확히 제외 |
| 그중 2건은 담당부서가 "문의" 제목이 아니라 본문 중간 문장에 묻혀 있었음(`※ 소재지 구청 가정복지과 문의`, `방문 : 물건소재지 구청 세무과`) | 문의 섹션에서 못 찾으면 본문 전체를 훑는 폴백 추가. 특정 구를 지목하지 않는 표현이라 해당 부서 전부에 연결 | 미매칭 29 → 7건 |
| 담당부서 칸이 비면 LLM이 스스로 채움 — "담당 부서: 여객운임할인(맘편한KTX)"(민원명을 부서로), "상위 소속: 세금"(분야를 조직 경로로), 옆 후보 본문의 "세무과"를 가져옴 | ① 수원시 소관이 아닌 제도는 `external_org` 속성으로 명시 ② 그것도 없으면 "담당부서: 원문에 표기 없음" 문구를 명시 ③ 분야 라벨을 "분야(주제 분류, 조직 아님)"으로 변경 | 지어낸 부서명 0건. "한국철도공사가 담당", "고용노동부에서 담당하는 제도"로 정확히 답변 |
| 복지 구비서류에 서류가 아닌 것이 대량 혼입 — 긴급복지지원제도가 위기사유 22개(사망·가출·화재), 맞춤형 기초생활보장제도가 급여종류 8개를 서류로 추출(147건 중 23건) | 추출 프롬프트에 "급여·수당·사업 이름, 자격/위기 사유, 처리 단계는 서류가 아니다 — 손에 들고 제출하는 것만" 명시 후 재추출 | 해당 레코드 전부 0건으로 정정. 길이 안전망(60자)은 한 번도 발동 안 함 |
| 서류명 부분문자열 오매칭 — "주민등록등본이 필요한 민원"이 1개짜리 `등본`에 걸려 1건만 반환 | 질문에 포함된 이름 중 **가장 긴** 것을 선택(분야·부서에도 동일 적용) | 24건으로 정상화. `여권`이 12개 이상의 긴 서류명에 포함돼 있어 같은 사고가 계속 날 구조였음 |
| 같은 사업이 생애주기별로 중복 게재(일자리센터 운영이 청년·중장년·어르신 3곳) | 본문이 완전히 같은 것만 통합하고 카테고리는 합쳐서 보존 | 234 → 230건. 내용이 실제로 다른 5건은 아래 "미해결" 참고 |
| 페이지 하단 "수정일"을 수집하고도 버림 | `updated` 속성 적재 + 3년 이상 지난 문서엔 코드가 표식을 붙여 기준연도를 밝히게 함 | 2022년 주정차 과태료·2021년 상하수도에 경고, 최신 문서엔 미표시 (5/5 정확) |

## 검증

**구비서류 품질 — 전수 검증했다.** 오류를 두 종류로 나눠서 쟀다.

| 유형 | 방법 | 결과 |
|---|---|---|
| 환각형(원문에 없는 걸 지어냄) | 515건 전부 원문 문자열 대조 | 7건(1.4%). 전부 표의 행+칸 결합("재외국민 주민등록증")이나 패러프레이즈로, 실제 환각 아님 |
| 역할 오인형(원문엔 있으나 서류가 아님) | 313종 전부 LLM 역할 판정 | **0건** |

역할 오인형이 핵심이다 — 원문 대조로는 절대 안 잡히기 때문(`화재`는 원문에 그대로 있었다). 검증기 자체도 시험했다: 이전 추출의 오류 7건(화재→자격사유, 생계급여→급여명, 대상자 선정조사→처리단계)을 전부 적발하고 정상 서류 3건은 통과시켰다.

**고아 노드**: 231개 중 4개(1.7%). OrgUnit·Employee·DocumentType은 0개.

**회귀**: 8개 스크립트 전부 통과, 에러 0건. 남은 "모름" 3건은 의도된 동작(지역 미지정 "동사무소", 스코프 밖 "화재 신고"·"국세청").

## 아직 미해결

- **같은 이름·다른 내용 페이지 5쌍** — `지역공동체 일자리`가 청년 탭은 "18세 이상 / 기업일자리정책과", 중장년 탭은 "19세 이상 / 노동일자리정책과"로 갈린다. 수정일이 둘 다 같아 어느 쪽이 현행인지 판별할 근거가 없고, 임의로 고르면 틀린 자격 조건을 안내하게 된다. 탭마다 별도 관리되는 페이지라 시청에 확인하지 않으면 못 푼다 — 둘 다 유지 중. 집계가 이름 기준 중복 제거라 147건이 141로 표시되는 것도 이 결과.
- **미매칭 7건** — 6건은 고용노동부·한국철도공사·경기도·국민신문고 소관이라 연결하면 안 되는 것들(`external_org`로 표시됨). 1건(`장애아 어린이집 현황`)은 형제 페이지엔 담당과가 있지만 이 페이지엔 없어서, 유추하지 않고 비워뒀다.
- **`content_type` 분류가 형제 페이지끼리 불일치** — 납부방법 7건 중 `가상계좌납부`만 reference, 세목 13건 중 4건이 절차 필드를 가진 채 reference. 절차 정보가 있으면 라벨과 무관하게 컨텍스트에 표시되므로 정보 손실은 없고 헤더 라벨만 어색한 수준.
- **첨부파일·이미지 미반영** — 기존 갭 그대로.

## 재사용 가능한 판단

- **빈칸을 남기면 LLM은 반드시 뭔가로 채운다.** 담당부서 줄을 생략했더니 민원 이름·분야값·옆 후보의 부서를 차례로 가져다 썼다. 비워두는 대신 "없음"이라고 적어주는 것이 해법이었다.
- **날짜 계산 같은 판단은 코드가 하고 LLM에겐 결과만 준다.** 프롬프트에 "3년 이상 지났으면 밝혀라"라고만 썼을 땐 전혀 동작하지 않았다 — LLM은 오늘 날짜를 모른다. 반대로 최신 문서에 없는 경고를 달기도 했다.
- **"OrgUnit에 없으면 외부기관"은 틀린 전제였다.** 수원시 도서관 12곳·복지관·다문화가족지원센터는 조직도에 없지만 수원시 소속이다. 추측 규칙을 버리고 명시적 목록으로 갔다.
- **근사 인덱스는 데이터가 늘 때마다 다른 노드를 놓친다.** 처음엔 top_k=5가 정자동 정답을, 나중엔 top_k=20이 행정서비스헌장을 놓쳤다. 임계값 조정으로는 다음 사고를 막을 수 없다.
- **부분문자열 매칭은 계속 같은 방식으로 실패한다.** unit_level(구/국/과)에서 한 번 겪고 어절 단위 정확일치로 고쳤는데, 서류명(등본⊂주민등록등본)에서 똑같이 재발했다.
