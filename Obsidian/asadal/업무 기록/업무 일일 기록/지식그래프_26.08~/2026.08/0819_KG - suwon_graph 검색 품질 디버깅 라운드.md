## 개념

`suwon_graph` 검색 파이프라인([[0818_KG - suwon_graph 검색 파이프라인 및 Opik 연동]])을 만든 뒤, Opik 트레이스를 직접 들여다보며 실측으로 버그를 찾고 고친 디버깅 세션. 총 9건을 고쳤고, 그중 하나(지역명이 임베딩을 오염시키는 문제)는 "지역+업무" 조합 질문 전반에 영향을 주는 구조적 버그였다.

**핵심 교훈**: 프롬프트를 엄격하게 만들면 오히려 회귀처럼 보이는 현상이 생길 수 있다 — 실제로는 "느슨한 답변이 우연히 맞았던 척했던" 숨은 버그가 드러나는 것이었다(자동차세 사례). 겉보기 성공을 실측 없이 믿으면 안 된다는 걸 다시 확인.

---

## 분류별 정리

### A. 검색 정확도 (retrieval) 버그 — 파급력 제일 큼

| 버그 | 증상 | 원인 | 해결 |
|---|---|---|---|
| **지역명 임베딩 오염** ★가장 중요 | "권선구 세무 관련 문의" → 세무과가 247등(0.64)까지 폭락, 엉뚱한 팀들이 상위권 | 부서 임베딩 텍스트엔 구/동 이름이 아예 없음(그래프 관계로만 소속을 앎). 지역명을 검색어에 남긴 채 임베딩하면 텍스트에 없는 그 단어 쪽으로 의미가 쏠려 정답과 유사도가 떨어짐 | 지역 감지 후 그 지역명을 **임베딩 직전에 검색어에서 제거**(`region.strip_regions`). 지역 일치 판정은 이미 그래프 경로 기준(`region_hit`)으로 별도로 함 — opus의 "지역명은 검색어에서 빼고 일치 여부만 따로 판단" 원칙을 뒤늦게 완전히 구현 |
| top 캡이 지역일치 후보를 자름 | "정자동 전입신고" → 영화동 누락, "매탄동 등본" → 매탄4동 누락 | 법정동 하나를 여러 행정동이 나눠 관할하는데(예: 정자동↔정자1/2/3동+영화동), `top=3`으로 무조건 자름 | `region_hit=True` 후보는 개수 제한 없이 전부 포함, `top`은 지역 무관 일반 후보에만 적용 |
| Neo4j 벡터 인덱스 근사검색(ANN) 손실 | "정자동 전입신고" → 진짜 정답(유사도 0.77)이 안 잡히고 무관한 후보(0.71) | HNSW 근사검색은 `top_k`를 작게 요청하면 탐색 폭이 좁아져 진짜 최근접 이웃을 놓침. `top_k=5`는 깨지고 `top_k=10`부터 정확 | 인덱스에서 **찾아오는 개수**만 20으로 넓힘(안전마진). LLM한테 **보여주는 개수**(top)는 별개로 유지 |
| top=3이 진짜 정답을 컷 | "자동차세 납부" → 정답(차량세무팀, 4등 0.6982)이 3등(0.6983)과 0.0001 차이로 잘림 | `top`이 좁아서 근소한 차이로 진짜 정답이 밀려남. 예전엔 LLM이 느슨해서 3등 안의 오답(자동차등록과)을 그럴듯하게 답해서 "성공"처럼 보였을 뿐 | 실측 근거가 쌓여서 `top` 3→5로 상향 |

### B. 한국어 처리

| 버그 | 원인 | 해결 |
|---|---|---|
| 풀텍스트 검색이 한글 복합어를 못 찾음 ("전입신고" 2건, "주민등록등본" 0건) | Neo4j 풀텍스트 기본 애널라이저(`standard`)가 한글을 통짜 단어로 취급 — 실제 데이터엔 "등초본"/"주민등록증"처럼 다르게 쪼개져 있어 매칭 실패 | Neo4j 내장 **cjk 애널라이저**(한글을 2글자 바이그램으로 인덱싱)로 교체. "전입신고" 2→243건, "주민등록등본" 0→363건으로 개선 |

### C. 라우팅/트리거 버그

| 버그 | 원인 | 해결 |
|---|---|---|
| "시장 연락처"가 리더 숏컷에 안 걸림 | 리더 position 값은 "**수원**시장"인데 시민은 "시장"만 씀 | 별칭 정규식 추가. 단 "시장"은 흔한 글자라 "전통시장"/"시장경제"까지 오매칭될 위험 있어 **단어 경계**(앞뒤에 다른 한글 없음) 조건으로 방어 |
| "장안구 행정복지센터 목록" → 엉뚱하게 구 4개 전체 답변 | "장안**구**"의 "구"가 unit_level '구'로 오매칭 + "행정복지센터"가 "동"의 별칭인 걸 몰랐음 + 구조 라우터에 지역 스코프 기능 자체가 없었음 | 구 이름 먼저 걷어내고 unit_level 매칭 / "행정복지센터"→"동" 별칭 추가 / `list_by_level`에 `gu` 파라미터 추가해 지역 스코프 지원 |
| "주민센터 어디 있나요" → 44개 전체 나열(의도는 1곳 찾기) | `TRIGGER_WORDS`의 "있나요"가 너무 광범위한 트리거였음(원래 "수원시에 어떤 국이 있나요" 잡으려 추가했는데 "어떤"만으로 충분했음) | "있나요"/"있습니까" 제거, "어떤"/"뭐가 있"만 유지 — H01류는 여전히 잡히고 오탐 사라짐 |
| 구조 질의가 트리거 단어를 못 잡는 경우 | 트리거 단어 사전은 결국 유한 | 벡터검색까지 실패("모른다")했을 때만 **LLM에게 "혹시 구조 질의였나?" 재시도**(옵션 C) — 정상 질문엔 추가 비용 없음 |

### D. 별칭 사전

| 이슈 | 내용 |
|---|---|
| opus 사전을 검증 없이 재사용 | `ORG_ALIASES["동사무소"] = ["행정복지센터"]`로 확장했는데, 실제 임베딩 텍스트에 "행정복지센터"가 들어있는 노드 3개가 전부 동(洞)이 아니라 무관한 부서였음 |
| 전수 검증 | 54개 확장어 전부 실제 corpus 매칭 건수 확인 → 52개 정상(숫자 적어도 정확한 부서 가리키는 게 대부분), 2개는 0건이지만 대체어가 커버, **"행정복지센터" 1개만 실제로 유해** |
| 조치 | "행정복지센터" 확장어 제거(별칭 키 자체는 유지 — 시그널로서 의미 있음) |

### E. UX 판단 — 만들었다가 되돌린 것

**지역 되묻기 기능**: "동사무소 전화번호"(지역 없음)처럼 44개 중 어디인지 알 방법이 없는 질문에 "어느 동을 말씀하시는지..."라고 되묻는 기능을 만들었다가 제거했다. 이유: 이 시스템은 대화형 챗봇이 아니라 **질문 1번-답 1번의 검색 형태**라, 되묻고 다음 턴을 기다리는 상호작용 자체가 안 맞는다는 피드백. 지금은 지역 없이 벡터검색으로 그냥 흘려보내고 못 찾으면 정직하게 "모른다"로 끝난다.

## 재발 방지 관점에서 남는 것

- **"성공처럼 보이는 답"을 실측 없이 믿지 말 것** — 자동차세 사례처럼, 느슨한 LLM이 우연히 그럴듯한 오답을 내면 겉으로는 성공으로 보인다.
- **임베딩 텍스트에 없는 단어는 검색어에 넣지 말 것** — 지역명 스트리핑이 이 원칙의 재확인. 앞으로 새 필터/컨텍스트 축(예: Layer 2의 법령/절차)을 추가할 때도 "이 축의 값이 실제로 임베딩 텍스트에 있는가"부터 확인해야 한다.
- **프롬프트 수정 후엔 반드시 회귀 스윕** — 오늘 두 번(단수형 "그 후보가 정답" 표현)이나 프롬프트 문구 하나가 여러 케이스를 동시에 깨뜨렸다.

## 한 눈에 요약

```
A. 검색 정확도  → 지역명 임베딩 오염(★최대), top 캡, ANN top_k, top=3→5
B. 한국어 처리  → 풀텍스트 cjk 애널라이저 (전입신고 2→243건)
C. 라우팅       → 리더 별칭(단어경계), 구조라우터 지역스코프, 트리거 과다매칭 정리, LLM 폴백(옵션C)
D. 별칭 사전    → opus 사전 전수 재검증, 유해 확장어 1건 제거
E. UX          → 지역 되묻기 추가 후 제거 (검색 형태와 안 맞음)

핵심 교훈       → 겉보기 성공을 실측 없이 믿지 말 것 / 임베딩에 없는 단어는 검색어에 넣지 말 것
```
