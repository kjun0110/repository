## 1. 설계 — 노드가 아니라 속성, 방향은 넷

##### 문제 — 시민이 묻는데 답할 축이 없음
민원 644건 중 시간·제재 내용을 본문에 가진 것이 175건(27%)인데 칸은 0개다. 4,000자 `content` 한 덩어리에 묻혀 있었음. `documents` 195 · `channels` 239 · `fee_text` 114와 같은 규모인데 축 자체가 없는 상태.

단일 지표는 `민방위 교육 안 가면 어떻게 돼`로 잡았다. 0821부터 미해결이었고 정답 `불참자 과태료 부과`(본문 168자)가 12위에 머물러 있었음.

##### 노드화 — 기각
판정 두 기준 중 첫 번째부터 통과 못 한다. 취득세의 "60일"과 감리원 신고의 "30일"은 같은 실체가 아니라 같은 종류의 숫자다. 수수료 금액을 노드화하지 않은 것과 같은 판단.

| | 노드가 된 것 | 왜 |
|---|---|---|
| `DocumentType` 609 | 여러 민원이 같은 주민등록등본을 요구 | 실체 공유 ✓ |
| `Channel` 10 | 여러 민원이 같은 정부24를 씀 | 실체 공유 ✓ |
| 기한 | 같은 "60일"이어도 다른 기한 | 실체 공유 ✗ |

##### 배열(kinds/days/froms) — 기각
다른 세션에서 병렬 배열 3종을 제안받았고 데이터로 확인해 반대했다.

기산점이 닫힌 어휘가 아니다. 실제 값은 `상속개시일이 속하는 달의 말일`, `영아 출생 후 만 2년이 되는 날의 전날`, `육아휴직 시작한 날 이후 1개월` 형태다. 닫히지 않으면 `WHERE '취득일' IN c.deadline_froms`가 성립하지 않음. `Channel`을 10개 닫힌 값으로 만든 이유가 이것이다.

days가 정수로 안 떨어진다. `출산예정일 40일 전 ~ 출산일로부터 60일까지`는 둘이고, `매년 8월 16일~31일`은 개념 자체가 없음.

결정적인 것은 숫자만 남기면 오분류를 못 잡는다는 점이다. 여권 재발급의 `1년 이내 2회, 5년 이내 3회`는 분실 횟수를 세는 기간이고 `6개월 이내`는 사진 촬영 시점이다. `[365, 1825, 180]`으로 만들면 신청기한과 구별할 방법이 사라진다.

집합 연산 수요도 확인되지 않았다. `channel` 축은 "온라인 신청 가능한 민원 전부"에 벡터가 페이지 한 장의 목록을 전수인 양 답하는 걸 확인하고 만든 것이다. "신고기한 있는 민원 목록"을 묻는 시민이 있다는 확인은 없음.

##### 택한 안 — `tables_text`와 같은 방식, 줄마다 태그
```
[마감] 취득일로부터 60일 이내
[마감] 상속개시일이 속하는 달의 말일부터 6월이내
[처리] 접수한 날부터 14일
[지급] 매월 25일(토·일요일·공휴일인 경우에는 그 전일에 지급)
[기준] 과세기준일(6월 1일) 현재 재산을 사실상 소유하고 있는 자
```

시간 표현은 방향이 넷이다. 안 나누면 "며칠 안에 해야 돼?"에 "60일 걸립니다"라고 답한다 — `fee_text`/`benefit_text`를 나눠야 했던 것과 같은 문제.

```
시민 → 관청   [마감]   언제까지 해야 하나
관청 → 시민   [처리]   얼마나 걸리나
관청 → 시민   [지급]   언제 받나
방향 없음      [기준]   어느 시점 기준으로 정해지나
```

태그는 코드가 붙인다. LLM은 종류만 답하고 문자열은 코드가 만든다 — 문자열을 맡기면 흘림.

##### 만들지 않은 것 — `deadline_days`, `schedule_year`
숫자 필드는 "30일 이내인 민원 찾아줘"라고 묻는 시민이 없어서 뺐다. `fee_min`/`fee_max`가 있는 이유는 "3만원 이하"가 실제 질의였기 때문이고 기한은 아니다. **fee 스키마를 관성으로 복사할 뻔했음.**

`schedule_year`는 처음 설계에 넣었다가 실측으로 뺐다. 신청기간류 90개 중 절대 연도가 있는 건 23개뿐이고(74%가 상대·반복형), 그 23개도 대부분 2026년이라 "올해니까 유효"로 오판한다. `2026. 1. 19. ~ 1. 30.`은 연도가 맞아도 이미 7개월 전에 끝났음. 시기성은 렌더링 시점에 정규식으로 처리한다.

## 2. 추출 — 원문 대조 가드가 배치 오염 50건 차단

##### 구현 — 4단계
```
1단계  라벨 정규식      "신청기간 :" 형태 → 값·종류 둘 다 확보
2단계  LLM             후보 218건만 (644건 전부 안 넣음)
3단계  결정적 보정      원문 라벨이 LLM 판단보다 믿을 만하다
4단계  원문 대조        추출된 값이 원문에 글자 그대로 있는지
```

644건을 다 넣지 않는 이유는 비용이 아니라 환각이다. 기한이 없는 426건을 넣으면 없는 기한을 만들어낸다 — `03_classify_fee_direction.py`가 `fee_text` 있는 것만 본 것과 같음.

##### 캐시 설계 — 완성품이 아니라 LLM 원본
처음엔 완성품(`schedule_text`)을 캐시했는데 규칙을 한 글자 고칠 때마다 218건 재호출이 필요했다. 원본을 두고 `merge`를 매번 다시 돌리게 바꾸니 이후 규칙 수정 15회가 전부 공짜였다. 이 설계 변경이 이번 라운드에서 가장 값을 했음.

##### 원문 대조 — 이번 라운드 최대 수확
추출된 값이 원문에 공백 무시 부분문자열로 실재하는지 확인하고 없으면 버린다. 50개가 거부됐고 전수 확인 결과 전부 정당한 거부였다. 원인은 배치 오염.

```
부모급여        "아동 출생 후 60일 이내..."     실제로는 '가정양육수당' 페이지 값
기초연금지원제도  "지급일 : 매월 20일 계좌입금"    '장애연금·수당지급' 값
이주민 지원사업   "분만일로부터 6개월 이내"       '출산 후 지원' 값
정보통신설비     "작성하지 아니하거나...300만원"   원문엔 "보존하지...150만원"만 있음
```

**5건씩 묶어 보내면 LLM이 옆 페이지 값을 이 페이지 것으로 답한다.** 가드가 없었으면 50개가 전부 그래프에 들어갔을 것이다.

프롬프트 예시가 형식을 오염시킨 사례도 있다. 불참자 페이지의 `부과금액 - 기준액 10만원`을 예시로 넣었더니 LLM이 주정차 금액에 그 접두사를 씌워 `부과금액 - 기준액 40,000원`을 만들어냈다. 원문엔 `40,000원`만 있어서 걸러졌음.

## 3. 검증 3라운드 — 정밀도만 쟀고 재현율은 안 쟀음

##### 문제 — "완료"라고 보고했으나 틀림
되물어봐 준 덕에 세 번에 걸쳐 더 큰 것이 나왔다. 한 번에 다 안 나왔다는 것 자체가 기록할 가치가 있음.

##### 1차 — `[처리]` 30줄만 보고 "오분류 3.6%"로 보고
덩치인 `[마감]` 168줄을 안 봤다. 전수로 보니 323줄 중 101줄(31%)이 문제였다.

| 문제 | 규모 |
|---|---|
| 중복(같은 값 두 번) | 22 |
| 시간 값이 아님 | 33 |
| 종류 오분류 | 8 |
| 잘림 | 1 |
| `penalty_text`가 지원금·수수료 | 37 |

`penalty_text` 오염 37줄은 내가 만든 것이다. 불참자 페이지에서 금액이 빠지는 걸 고치려고 프롬프트에 "금액이 있으면 반드시 포함해라"를 넣었더니 LLM이 "페이지의 모든 금액"으로 일반화했다. 국소 수정이 전역 부작용을 냈고, 원문 대조는 원문에 있는 값이라 못 막았음.

```
자녀 출산·입양 지원금
   benefit_text  50만원(신설)
   penalty_text  첫째자녀 50만원(신설) / 둘째 100만원 / 셋째 200만원 ...
```

##### 2차 — `[기준]` 9줄 중 3줄만 정답
규칙 8개로 101줄을 정리한 뒤 다시 전수. 나머지는 보험 보장기간 4·시행일 1·자격요건 1이었다.

##### 3차 — 재현율을 안 쟀다는 것이 드러남
그때까지 잰 건 정밀도(들어간 게 맞나)뿐이었다.

```
후보 218건 중 LLM이 아무것도 안 준 건: 66건 (30%)
```

**원문 대조는 잘못 넣는 것만 잡는다. 빠뜨리는 것은 대조할 값 자체가 없어서 못 잡는다.** `이달의 지방세` — 12개월치 납부기한이 든 세금 달력 — 이 통째로 비어 있었음.

## 4. 배치 해체 — 규칙 추가보다 나은 대응

##### 원인 — 배치 구성
`불참자 과태료 부과`가 단독 배치에서는 제대로 뽑혔다는 것이 힌트였다. 원인이 배치 구성이니 규칙을 더 만들 게 아니라 배치를 풀어야 한다.

##### 구현 — 1:1 재질의 두 갈래
```
retry_empty     빈 결과 37건을 1건씩 재질의    → +54줄 (세금 달력 통째로)
retry_partial   부분 누락 14건을 1건씩 보강    → +22줄 (기존 값에 더함, 갈아치우지 않음)
```

`retry_partial`이 갈아치우지 않고 합치는 이유는 1:1 재추출이 같은 페이지에서도 배치와 다른 값을 주기 때문이다. 갈아치우면 이미 전수로 확인한 값이 사라짐.

##### 결과 — 더 나은 형태로의 교체
```
전: 통지를 받은 날부터 30일 이내
후: 과세전 적부심사제도: 통지를 받은 날부터 30일 이내
    심판청구제도: 이의신청 후 결정 통지를 받은 날부터 ... 90일 이내
    감사원 심사청구제도: 납세고지서를 받은 날로부터 90일 ...
```

전엔 4개 기한이 어느 제도 것인지 몰랐다.

## 5. 규칙 설계 — 낱말 목록은 예외 없이 오탐

##### 방법 — 사라진 줄을 전부 출력해 확인
규칙을 하나 적용할 때마다 전수로 봤다. 그러지 않았으면 아래 전부를 놓쳤음.

| 규칙 의도 | 실제로 잡은 것 | 고친 방법 |
|---|---|---|
| 기간류 배제 | `신청기간 : 표시기간 만료 전후 30일` (갱신 마감) | 뒤에 `만료/종료`가 오면 기산점이므로 예외 |
| 맨숫자 배제 | `2026. 2 ~ 11월` 등 청년정책 6줄 | 4자리 연도가 있으면 맥락이 있는 것 |
| 납기 개시일 배제 | `상속개시일이 속하는 달의 말일부터 6월이내` (취득세 핵심 값) | `납기 개시일`로 좁힘 |
| 제재어 요구 | `점검기록을 보존하지 아니한 경우 150만원` | 법령은 '과태료' 없이 위반+금액만 적는다 |
| 시각 배제 | `2026. 1. 19.(월) 09:00 ~ 1. 30.(금) 18:00` | 날짜가 있으면 운영시간이 아니다 |
| 위반어 확대 | 표 헤더·담당부서 목록·자격 요건 대량 유입 | `위반` → `위반한/위반으로/위반 시` |

세 번째가 가장 아찔했다. 취득세의 상속 기한이 `상속개시일`의 '개시일' 때문에 지워질 뻔했음.

##### 같은 실수 3회 — 검증을 경로에 걸었음
```
is_time_value    라벨 경로에만 걸음      → LLM 경로로 "방문접수 : 동 행정복지센터"가 통과
_EXCLUDE         schedule 경로에만 걸음  → penalty 경로로 유효기간이 통과
_PEN_AMOUNT      %만 봄                 → "100분의 3" 가산세 줄들이 통째로 누락
```

**검증은 경로가 아니라 값에 걸어야 한다.**

##### 값만으로 판정 불가 — 원문 문맥을 봄
`[마감] 취득일로부터 60일 이내`만 보면 신청 마감이다. 원문은 `추징요건  취득일로부터 5년 이내에 ... 처분하는 경우 추징함`이다. 시민이 지킬 마감이 아니라 감면이 취소되는 조건이다. 값 단위 규칙으로는 못 가른다.

원문에서 값 바로 앞 24자를 보고 `추징요건|자격요건|유효기간`이 있으면 배제한다. `발급일로부터 3개월 이내`(원문: `각종 증명서의 유효기간 : 발급일로부터 3개월 이내`)도 같은 방식으로 잡았음.

## 6. 인덱스 — `IF NOT EXISTS`가 필드 추가를 조용히 무시

##### 원인 — `IF NOT EXISTS`
```cypher
CREATE FULLTEXT INDEX ... IF NOT EXISTS
```

이미 있는 인덱스는 건드리지 않는다. 코드에는 새 필드가 있는데 색인은 옛 필드 그대로인 상태가 되고, "고쳤는데 검색이 그대로"인 채로 원인을 못 찾게 된다.

##### 구현 — 현재 필드를 읽어 다를 때만 DROP + CREATE
같으면 아무 일도 안 하므로 반복 실행이 공짜다. 이걸 안 잡았으면 이번 작업의 핵심 이득이 통째로 날아갔음.

`tables_text`를 넣을 때도 같은 함정이 있었을 텐데 흔적이 없다 — 그때 어떻게 넘어갔는지 확인이 필요하다.

## 7. 제재 별칭 복원 — 조건이 달라졌기 때문

##### 문제 — 기존 주석이 금지하고 있었음
`search/steps/aliases.py`에 이렇게 적혀 있었다.

> 과태료 같은 강한 단어는 그 뜻이 분명한 말("벌금")에만 붙인다 — "안 가면"처럼 일상 표현에 붙이면 무관한 질문까지 제재 쪽으로 끌려간다.

##### 판단 — 조건이 달라졌는지 따짐
실측 근거가 있는 판단이라 그냥 뒤집지 않았다. 그 판단은 매칭 대상이 `content`(4,000자)뿐일 때 내려진 것이고, `penalty_text`(한두 줄)가 어휘 인덱스에 들어가면 제재어가 제재를 다루는 페이지에만 정확히 물린다.

##### 결과 — 23문항 확인 후 복원
```
"안 가면": ["불참", "과태료"]     ← 과태료 추가
어휘 검색:  불참자 과태료 부과 44.06  vs  민방위 정의 34.36
회귀:      나머지 22문항 변동 0
```

주석이 경고한 부작용이 실제로는 나타나지 않았다.

## 재사용 가능한 판단

- **노드 판정은 첫 기준에서 대부분 끝난다** — "여러 부모가 같은 실체를 참조하나". 두 번째까지 갈 일이 드물다.
- **fee 스키마를 관성으로 복사하지 않는다.** `fee_min`/`fee_max`가 있는 이유는 "3만원 이하"가 실제 질의였기 때문이고, 다른 축에 같은 근거가 있는지는 따로 확인한다.
- **캐시는 완성품이 아니라 LLM 원본을 담는다.** 규칙은 반드시 여러 번 손보게 된다.
- **검증은 경로가 아니라 값에 건다.** 같은 실수를 세 번 했다.
- **낱말 목록 규칙을 넣을 때는 사라진 줄을 전부 출력한다.** 이번에 넣은 낱말 규칙이 예외 없이 오탐을 냈다.
- **국소 수정의 전역 부작용을 의심한다.** 한 페이지를 고치려고 프롬프트에 넣은 한 줄이 37줄을 오염시켰다.
- **배치 오염은 양방향이다.** 잘못 넣는 쪽은 원문 대조가 잡지만 빠뜨리는 쪽은 못 잡는다. 후자는 배치를 풀어서 다시 묻는 수밖에 없다.
- **정밀도와 재현율은 다른 지표다.** "전수 확인했다"가 "다 들어갔다"를 뜻하지 않는다.

## 한계

- 본문 기한 표현 커버율 49% (112개 중 55개). 나머지 절반 중 상당수는 의도적 배제(자격 요건·유효기간·사업기간·운영시간)지만 진짜 누락도 남아 있음 — `주정차위반 과태료란?`은 본문에 마감이 6개인데 일부만 담김
- 회귀 문항 23개는 이번에 만든 것. 이전 세션의 "8개 스위트 / 32문항 광역"이 저장소에 없어 매번 스크래치로 만들고 버렸음. "변동 1건"은 이 23문항 안에서 안 깨졌다는 뜻
- 답변 확인 표본이 유리함. 새 축이 작동하는 걸 보려고 고른 질문이지 무작위가 아니다 — 성능 지표가 아니라 기능 확인으로 읽을 것
- `[마감]` 177줄은 마지막 보강 이후 전수 재판정을 하지 않았음. 새로 들어온 것만 diff로 확인
- 정밀도는 기계 검증이 아님. 기계적으로 보장되는 건 원문 대조 하나뿐이고, `[처리]`인지 `[마감]`인지는 사람 판단
