## 개념

- **TBox / ABox** — 규칙(온톨로지)과 데이터. **설계 검사는 TBox, 데이터 검사는 ABox** 의 일이고, 오늘 시험은 이 둘을 어떤 도구가 맡아야 하는지를 가른 것이다
- **HermiT** — OWL 2 DL 추론기. "이 규칙들이 말이 되는가"를 **판정**한다. 데이터를 고치지 않는다
- **owlrl** — OWL 2 RL 범위만 이해하는 파이썬 추론기. 규칙대로 **새 트리플을 만들어 저장**한다
- **SHACL** — 데이터 검사 규칙 언어. 지금 `validation.py` 가 하는 일을 RDF 표준 방식으로 하는 것
- **열린 세계(Open World)** — OWL 은 "적혀 있지 않다"를 "없다"로 보지 않는다. 그래서 **필수 칸 누락을 오류로 잡지 않는다**
- **UNA(고유 이름 가정)** — "이름이 다르면 다른 대상"이라는 가정. OWL 은 이걸 **하지 않는다**. 그래서 상위 조직이 둘이면 오류로 보는 대신 **두 조직을 같은 것으로 합친다**
- **ROBOT** — 온톨로지 도구 모음. HermiT 가 들어 있는 Docker 이미지가 있어서 **PC 에 Java 를 설치하지 않고** 쓸 수 있다

## 요약

어제까지 조사로만 보던 RDF 추론을 **실제로 돌려 봤다.** `code/test/rdftest` 에 시험 폴더를 만들고, 온톨로지 0.6.2 JSON 에서 OWL 과 SHACL 을 생성해 **섀도우 DB 의 나라원 데이터**를 RDF 로 바꾼 뒤 세 도구에 넣었다.

결론은 예상대로였다. **데이터 검증은 SHACL 만으로 충분하고, HermiT 는 온톨로지 설계가 바뀔 때만 쓸 가치가 있다.** 필수 칸 누락과 상위 조직이 둘인 경우를 OWL 은 오류로 보지 않을 것이라 예상했는데, 실제로 그랬다. 반대로 HermiT 만 잡은 것은 **설계 문제 둘**뿐이었다.

예상과 달랐던 게 세 가지 있다. 하나는 **"상위가 둘"을 HermiT 가 잡는지가 데이터 모양에 따라 달라진다**는 것. 또 하나는 그걸 OWL 로 잡아 보려고 넣은 **"모든 개체가 서로 다르다" 선언이 ×10 규모에서 메모리를 터뜨린다**는 것. 마지막은 **SHACL 을 추론 결과 위에서 돌리면 안 된다**는 것이다 — 추론이 붙인 타입 때문에 틀린 데이터가 통과하고, 합치기 추론까지 번지면 위반 1건이 28~79건으로 불어났다.

> 메모리 부족은 HermiT 가 약해서가 아니다. **SHACL 이 할 일을 HermiT 에게 억지로 시켜서** 터진 것이다. 보통 데이터는 ×50(37만 트리플)에서도 12초에 끝났다.

여기서 세 단계가 깔끔하게 갈렸다 — **① 설계는 DL(HermiT), ② 데이터는 SHACL, ③ 운영 추론은 RL 엔진. 그리고 ②가 ③보다 먼저여야 한다.**

오후에는 **전환 비용**을 코드 기준으로 쟀다. Neo4j 에 묶인 파일이 22개 · 약 3,800줄이고 Cypher 를 쓰는 곳이 45군데다. **Fuseki 로 전면 전환은 96~147인일**, AGE 는 40~60, ArcadeDB 는 20~40이다. ArcadeDB 는 **Bolt 와 openCypher 를 지원**(TCK 97.8% 통과)해서 접속 주소만 바꿔 돌려 볼 수 있다 — 어제 "검증 부족"이라고 한 판단을 공식 문서로 바로잡았다.

그래서 **권장안은 DB 를 두고 표준 도구만 붙이는 것**이다. JSON 에서 OWL · SHACL 을 생성하고, Protégé 로 보고, HermiT 로 검사한다. **1인 3~4주**면 되고, 오늘 시험이 그 방식이 동작한다는 증거다.

마지막으로 어제 못 짚은 구멍 하나를 찾았다. **근거 파일을 지워도 이전 상태로 못 돌아간다.** 지금 코드는 그걸 "철회"가 아니라 "새 자료에서 사라짐"으로 읽어서 **명단은 적재가 멈추고**, 멈추지 않아도 **잘못 올린 파일을 거둔 것이 퇴사자로 바뀐다.**

`nara1-0.6.2.json` → `tbox.ttl`(OWL) + `shapes.ttl`(SHACL). 라벨은 클래스, 관계는 ObjectProperty(domain/range), 속성은 DatatypeProperty 로 옮겼다. 라벨 10개는 서로 전부 배타로 두고, `many_to_one` 은 Functional 로 두었다. SHACL 에는 필수 칸 · 어휘 · 카디널리티 · 도착 라벨을 넣었다.

## 2. 결과 — 누가 무엇을 잡나

| 시나리오 | HermiT | owlrl | SHACL |
|---|---|---|---|
| **실제 데이터** (Capture 포함·제외) | 문제 없음 | 오류 0 | **위반 0** |
| ① 배타 클래스를 동시에 상속하는 클래스 | **잡음** | 놓침 | 놓침 |
| ② 회사이면서 직원인 개체 | 잡음 | 잡음 | 잡음 |
| ③ 상위 조직이 둘 | **놓침** (두 상위를 합침) | 놓침 (조용히 합침) | **잡음** |
| ④ 이름이 빠진 조직 | 놓침 | 놓침 | **잡음** |
| ⑤ 발주처 자리에 회사 | 잡음 | 잡음 | 잡음 |

| SUB_ORG_OF 를 Transitive 로 | 문제 없음 | 상위 관계 **39 → 71** | — |

**열린 세계라서 필수 칸 누락과 카디널리티 위반을 OWL 이 잡지 않을 것**이라는 예상이 맞았다. 그 둘은 SHACL 만 잡았다. **HermiT 만 잡은 건 설계 문제 둘**(①, Transitive + Functional)이고, **데이터 쪽에서 HermiT 만 잡은 건 하나도 없었다.**

`validation.py` 가 통과시킨 현재 데이터를 SHACL 도 위반 0 으로 판정했다. 변환 때문에 손실이 생겼다는 증거는 없었다.

## 3. 예상과 달랐던 것

##### ③ 은 데이터 모양에 따라 결과가 달라진다
두 번째 상위가 **원래 상위의 상위(조부모)** 면 HermiT 도 잡는다. 합치기 추론이 위로 번져 조직과 회사가 같은 개체가 되기 때문인데, **이건 우연이다.** 두 상위가 서로 다르다고 **선언해 주면** HermiT 도 잡는다. 검사기로 쓰기엔 믿을 수 없는 성질이다.

##### "모든 개체가 서로 다르다" 선언은 쓸 수 없다

| 규모 | 보통 | + 모든 개체 "서로 다르다" |
|---|---|---|
| ×1 (개체 714) | 1.8초 | 2.3초 |
| ×10 (개체 7,140) | 3.9초 | **메모리 부족** (6GB 로 올려도 197초 만에 재발) |
| ×50 (개체 35,700 · 37.6만 트리플) | **11.8초, 정상** | 시도 안 함 |

개체 7,140개면 쌍이 **약 2,550만 개**다. 어떤 추론기에 넣어도 무거운 입력이고, 애초에 **SHACL 이 25초에 하는 일을 OWL 로 우회하려던 것**이었다.

##### SHACL 은 추론 전 원본 데이터에 돌려야 한다
추론이 붙인 타입 때문에 **잘못된 도착 라벨이 통과**하고, 합치기 추론까지 번지면 **위반 1건이 28~79건으로 불어난다.**

## 4. 규모별 시간 (초)

| 규모 | HermiT | owlrl | SHACL |
|---|---|---|---|
| ×1 (7.8천 트리플) | 1.8 | 3.1 | 0.5 |
| ×10 (7.5만) | 3.9 | 24 | 4.9 |
| ×50 (37.6만) | **11.8** | **113** | 24.6 |

HermiT 시간에는 Docker · Java 시작(약 0.8초)이 들어 있다. **가장 느린 건 owlrl** 이다. 운영에서 데이터가 커지면 owlrl 보다 Jena 나 GraphDB 가 맞을 수 있는데, 이건 아직 비교하지 않았다.

> HermiT 의 부담은 **데이터 양보다 온톨로지의 복잡도**에 더 좌우된다. 0.6.2 는 배타 선언 · domain/range · Functional 정도라 단순해서 빨랐다. 존재 제약이나 숫자 제약이 늘면 같은 데이터에서도 느려진다.

## 5. 그래서 어떻게 쓰나 — 세 단계

```
1. 온톨로지 작성 →  HermiT (DL)   규칙끼리 모순이 없는가          ← 온톨로지 바뀔 때만, CI
                    RL 범위 검사   그 규칙을 운영 엔진이 알아듣는가
2. 데이터 적재   →  SHACL          들어온 데이터가 규칙에 맞는가    ← 적재할 때마다, 추론 전
3. 운영 추론     →  RL 엔진        통과한 데이터에서 새 사실을 저장  ← 적재 후
```

##### 운영 경로에 HermiT 를 넣지 않는다
검사 대상은 **TBox 뿐**이고 `tbox.ttl` 은 8KB 라 메모리 문제가 생길 수 없다. 데이터를 같이 보고 싶으면 **틀린 예시 몇 개(픽스처)** 만 넣어 "모순으로 잡히는가"를 확인한다. 이건 데이터 검사가 아니라 **배타 선언이 빠지지 않았는지를 데이터로 시험하는 것**이다.

##### HermiT 가 "모순 없음"이라 해도 올바른 건 아니다

| 못 보는 것 | 보완 |
|---|---|
| **규칙이 빠진 것** — 배타 선언을 빠뜨려도 모순이 아니라 통과한다 | 틀린 예시 픽스처 회귀 시험 |
| 운영 엔진이 이해하는 범위인지 | `robot validate-profile --profile RL` |
| OWL 로 표현하지 않은 규칙(필수 칸 · 어휘 · 카디널리티) | SHACL |
| 변환이 맞게 됐는지 | 생성물의 클래스 · 관계 개수를 JSON 과 대조 |

##### RL 범위 밖 표현 8곳
`validate-profile` 로 검사하니 **RL 밖이 8곳**이고 전부 같은 종류 — **"A 또는 B"(합집합)를 domain/range 에 쓴 것**이다. `SUB_ORG_OF` · `MEMBER_OF` 의 도착(조직 또는 회사)과, 여러 라벨이 같은 이름의 속성을 공유해 출발이 합집합이 된 6곳이다.

**HermiT(DL)에서는 정상이지만 owlrl 은 경고 없이 무시한다.** 그래서 "설계 검사는 통과했는데 운영에서 추론이 안 되는" 일이 생긴다. **운영에 RL 엔진을 쓰지 않으면 이 8곳은 문제가 아니다.**

##### 조직 카디널리티는 SHACL 로 막는다
`SUB_ORG_OF` 는 n:1(조직도는 트리), `MEMBER_OF` 는 n:m(겸직 3명). 이건 0.6.2 가 이미 정해 둔 구조다. RDF 로 옮긴다면 **"상위는 하나"를 SHACL(`sh:maxCount 1`)로 막고, OWL 에는 Functional 을 붙이지 않는 쪽**을 권한다. 붙여 두면 SHACL 을 빠뜨렸을 때 **owlrl 이 두 상위 조직을 같은 조직으로 합쳐 써 넣고**, 조직도 질의 결과가 조용히 바뀐다.

## 6. 온톨로지 정본은 JSON 으로 둔다

`.ttl` 은 JSON 에서 **생성한 파일**이다. RDF 로 옮기더라도 당분간 이 방식을 권한다.

| | A. `.ttl` 이 정본 | **B. JSON 이 정본, `.ttl` 은 생성물** |
|---|---|---|
| 장점 | RDF 표준 방식. Protégé 로 바로 편집 | 기존 파이프라인을 그대로 둘 수 있다 |
| 단점 | `validation.py` · DDL 생성 · 버전 관리 · 서빙 코드를 지금 다 고쳐야 한다 | 변환 스크립트를 관리해야 한다 |

이유는 넷이다 — ① 채택이 확정되지도 않은 안을 위해 운영 기반을 먼저 흔들 이유가 없다 ② 생성 방식은 오늘 동작이 확인됐다(변환 약 100줄, SHACL 결과가 `validation.py` 와 일치) ③ 이행 기간에 정본이 둘이면 **반드시 어긋난다** ④ JSON 에만 있는 정보가 많다(`read_by`, 동의어, 비고, 도입 버전, managed 표시).

**생성된 `.ttl` 은 사람이 고치지 않는다.** 고칠 일은 JSON 에서 하고, Protégé 는 보기와 검사에만 쓴다.

Neo4j 에 직접 묶인 파일 **22개 · 약 3,800줄**. 조회에서 Cypher 를 쓰는 곳이 **약 45군데**.

| 약점 | 사용 사례 적음, 개발자 의존 | Cypher 일부 미지원 | 전면 재작성 | 조건 미충족 |
| **공수(1인)** | **20~40인일** | 40~60인일 | **96~147인일** | 0 (+ 라이선스 비용) |

> **정정.** 어제 ArcadeDB 를 "Cypher 호환 불확실, 검증 부족"으로 분류했는데 너무 보수적이었다. 공식 문서 기준 **자체 openCypher 엔진이 있고 TCK 3,897개 중 97.8% 를 통과**하며 **Neo4j Bolt 를 지원**한다. 접속 주소와 계정만 바꿔 지금 코드를 돌려 볼 수 있다. 다만 **벡터 인덱스와 DDL 문법은 따로 확인**해야 한다.

Fuseki 96~147인일은 1인 5~7개월, 2인 3~4개월이다. 처음 쓰는 스택이라 20~30% 여유를 더 잡아야 한다.

##### 권장안 — DB 는 두고 표준 도구만 붙인다
전체를 바꾸지 않아도 Protégé · HermiT · SHACL 의 장점은 거의 다 얻는다.
1. JSON 에서 OWL · SHACL 을 생성한다 (오늘 시험한 방식)
2. Protégé 로 보고, 바뀔 때마다 HermiT 로 검사한다 (CI)
3. SHACL 을 지금 검증기와 대조하는 **두 번째 검증기**로 둔다

**1인 약 3~4주.** 이렇게 쓰다가 클래스 계층이 생기거나 여러 단계 추론이 꼭 필요해질 때 DB 전환을 다시 판단하면 된다. **오늘 시험 결과로 보면 실익이 적다** — 온톨로지에 상속이 없으면 HermiT 가 잡을 게 없고, 데이터 검사는 SHACL 로 충분했다.

## 8. 곁가지 — 근거 파일을 지워도 되돌아가지 않는다

"새 근거로 갱신된 노드를 그 근거 파일을 지워서 되돌릴 수 있나"를 코드로 확인했다. **절반만 된다.**

값은 돌아간다. 적재는 매번 **지금 남은 입력 파일**로 전체를 다시 계산하고, 명단은 회사별로 기준일이 가장 늦은 파일 하나를 쓰기 때문이다. 문제는 지금 코드가 이 상황을 **"철회"가 아니라 "새 자료에서 사라짐"으로 읽는다**는 것이다.

| | 내용 |
|---|---|
| **명단은 적재가 멈춘다** | 직전보다 기준일이 이른 명단이면 "옛 명단"으로 멈추고, **넘기는 옵션이 없다** |
| 멈추지 않아도 뜻이 틀린다 | 새 파일에만 있던 사람이 **퇴사로 바뀐다.** 잘못 올린 파일을 거뒀는데 퇴사자가 생긴다. 10% 를 넘으면 대량 퇴사로 또 멈춘다 |
| 크롤링도 같다 | 지운 수집본에서만 나온 노드는 "사라짐"으로 남거나, 못 받았으면 멈춘다 |
| 철회 기록이 없다 | 지운 파일의 Capture 는 그래프에서 빠지고, **언제 무엇을 철회했는지 남지 않는다** |

##### 원인 — 결과가 "입력의 함수"가 아니라 "지나온 순서의 함수"다
퇴사 · 사라짐 · 근거 · "옛 명단" 검사가 모두 **직전 릴리즈와 비교해서** 정해진다. 그래서 중간 파일 하나를 빼고 다시 돌려도 직전 상태가 그 파일의 흔적을 들고 있다.

##### 고치는 방향 — 입력으로만 재생성(A) + 릴리즈 스냅숏(B)
- **입력을 전부 보존하고 철회는 별도 기록**(`retractions.jsonl`)으로 남긴다. 폴더는 계속 고치지 않는다
- **상태를 직전 릴리즈가 아니라 입력 순서에서 계산한다.** 회사별로 철회되지 않은 명단을 기준일 순으로 모두 읽어, 최신에 있으면 재직 · 이전에만 있으면 퇴사로 정한다. **처음 빠진 명단의 날짜가 곧 퇴사 확인일**이 되어, 10/02 에 필요하다고 한 "상태 변경 날짜" 칸이 자연스럽게 생긴다. "옛 명단" 멈춤도 필요 없어진다
- **직전 릴리즈는 검사에만 쓴다** (10% 경고, 지문 대조)
- **개인정보 기한과 충돌한다.** 명단을 지우면 그 파일에서 나온 이력도 사라지므로, 지우기 전에 **개인정보 없는 요약**(직원 키 · 회사 · 처음 본 날 · 마지막 본 날)으로 접어 두고 그 요약을 입력으로 쓴다
- 공수 **1인 3~4주**

이렇게 되면 철회뿐 아니라 **잘못 올린 파일, 순서가 뒤바뀐 파일, 파서를 고친 뒤 전체 재계산**이 전부 "입력을 고치고 다시 적재" 한 가지 방법으로 해결된다.

> **당장은**, 잘못 올린 명단이 생기면 폴더를 지우지 말고 **올바른 내용으로 기준일이 더 늦은 새 명단을 올리는 것**이 현재 코드로 안전한 방법이다.

## 재사용 가능한 판단

- **열린 세계 가정 때문에 OWL 은 데이터 검사기가 될 수 없다.** 없는 값을 오류로 보지 않고, 이름이 달라도 같은 대상으로 **합쳐 버린다.** 검사기가 데이터를 조용히 고치면 그건 검사기가 아니다
- **도구에 맞지 않는 일을 시키면 성능이 아니라 설계가 터진다.** 메모리 부족은 HermiT 의 한계가 아니라 잘못된 용법의 결과였다
- **검사는 추론보다 먼저다.** 틀린 데이터가 추론에 들어가면 틀린 사실이 불어난다(1건 → 28~79건)
- **두 엔진의 이해 범위가 다르면 "설계는 통과, 운영은 침묵"이 생긴다.** DL 에서 정상인 표현을 RL 엔진은 **경고 없이 무시한다.** 그래서 모순 검사와 범위 검사를 같이 돌려야 한다
- **"모순 없음"은 "올바름"이 아니다.** 규칙을 빠뜨린 실수는 모순이 아니라 통과다. **틀린 예시를 넣어 반드시 걸리는지 확인하는 회귀 시험**이 있어야 한다
- **카디널리티는 검사로 막고, 추론 규칙으로는 선언하지 않는다.** Functional 을 붙여 두면 검사를 빠뜨렸을 때 데이터가 합쳐지고 질의 결과가 조용히 바뀐다
- **정본은 하나여야 한다.** 이행 기간에 정본이 둘이면 반드시 어긋난다. 새 형식은 생성물로 두고, 완전히 넘어갈 때 정본을 옮긴다
- **전환 비용은 저장소가 아니라 재작성 범위가 정한다.** 같은 "DB 교체"인데 20인일과 147인일로 갈린다. 모델이 같은지(속성 그래프), 조회 언어가 같은지, 벡터가 같은 트랜잭션에 있는지가 그 차이다
- **표준의 이점만 따로 떼어 올 수 있는지 먼저 본다.** DB 를 바꾸지 않고 OWL · SHACL 을 생성하는 것만으로 3~4주에 대부분을 얻는다. 전면 전환은 그래도 부족할 때 판단한다
- **보수적으로 적은 판단도 근거가 나오면 바로 고친다.** ArcadeDB 를 "검증 부족"으로 묶어 둔 건 공식 문서를 보기 전이었다
- **"되돌릴 수 있나"는 입력이 결과를 결정하는가의 문제다.** 결과가 지나온 순서에 기대면 중간 하나를 빼도 깨끗하게 돌아가지 않는다
- **실측과 개념은 다른 문서에 둔다.** 수치는 시점과 함께 기록에, 개념은 수치 없이 정리 폴더에

## 한계

- **저장소 코드는 하나도 고치지 않았다.** 시험은 전부 `rdftest` 안에서 했고, CI 연결도 하지 않았다
- **파이프라인으로 이어 돌리지 않았다.** 도구를 각각 따로 실행해 비교한 것이고, 설계 → 검사 → 추론 → 조회가 이어지는 흐름은 만들지 않았다
- **조회(SPARQL)를 한 번도 돌리지 않았다.** Fuseki 를 띄우지 않았다. 추론 결과 위에서 질의가 실제로 단순해지는지, 속도가 괜찮은지 모른다
- **owlrl 추론 결과를 저장하지 않았다.** 메모리에서 계산만 하고 버렸다
- **HermiT 의 추론 결과를 owlrl 과 비교하지 않았다.** 모순 검사만 돌렸다
- **속성 연쇄 규칙은 시험하지 않았다.** Transitive 만 확인했다
- **관계에 붙은 속성(관계 797개)을 변환에서 뺐다.** RDF 로 옮긴다면 RDF-star 나 named graph 중 하나를 정해야 한다
- **Protégé 를 직접 돌려 보지 않았다.** 파일 형식과 일반적인 동작을 근거로 한 판단이다
- **owlrl 외의 운영 추론기(Jena · GraphDB)를 비교하지 않았다.** owlrl 이 가장 느렸다는 것만 안다
- **ArcadeDB · AGE 를 실제로 띄워 보지 않았다.** 공수는 코드 규모에서 뽑은 추정이고, 비교 시험(1~2주)이 있어야 좁혀진다
- **철회 동작은 코드를 읽어 판단한 것**이고 실제로 재현해 보지 않았다
- 생성된 데이터 파일에 **회사 공개 정보(대표자명 등)가 남아 있다**
