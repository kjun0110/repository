## 개념

- **방법 A / 방법 B** — 되돌리기 구현 두 갈래. A 는 **버전 번호를 노드·관계 속성에 붙이고 포인터만 움직이는** 방식, B 는 **변경점을 따로 남겨 두는** 방식
- **미리보기 후 일괄 반영** — Undo/Redo 를 누를 때는 화면에서만 계산해 보여 주고, 저장을 눌렀을 때 한 번만 DB 에 쓰는 패턴
- **릴리즈 = 설계도** — "DB 가 최종적으로 이래야 한다"를 적은 전체 그래프 문서. **DB 에 가는 쓰기는 증분**이고, 그 증분을 계산하는 **기준이 통째**다
- **멀티 테넌시 vs 클러스터링** — 앞은 한 서버 안에서 **데이터를 칸막이 치는 것**, 뒤는 **서버를 여러 대로 늘리는 것**. 전혀 다른 축인데 둘 다 "무료냐"가 걸린다
- **OWL 2 프로파일(EL · QL · RL · DL)** — 표현력이 강할수록 추론이 느려져서 W3C 가 용도별로 기능을 줄여 둔 것. RDF DB 가 실제로 처리하는 범위는 대략 **RL**

## 요약

오늘은 **되돌리기(버전 관리)** 하나를 붙들고 하루 종일 돌았다. 아침에 Neo4j 기준으로 설계를 짜고, 그걸 우리 코드에 대보고, 아예 RDF 스택으로 갈아탔을 때는 어떻게 되는지까지 갔다가, 마지막에 **지금 스택을 유지한다**로 돌아왔다.

설계는 "파일 한 번 적재 = 버전 하나, Undo/Redo 로 오가되 저장할 때만 DB 에 반영"으로 잡혔다. 방법 A(버전 속성 + 포인터)와 방법 B(변경점 보관)를 비교해 **B + 미리보기 + PostgreSQL 보관**으로 정리했다.

그런데 **이 설계를 우리 적재기 위에 그대로 얹으면 충돌이 많다.** 설계가 "파일 하나 = 변경분 하나"를 전제하는데, 우리 적재기는 **매번 원천 전체로 그래프를 다시 만드는 릴리즈 방식**이기 때문이다. 문제가 일곱 가지 나왔고, 그중 셋이 특히 컸다 — **"파일 = 버전"이 성립하지 않는다**, **되돌려도 다음 정기 적재가 다시 덮는다**, **개인정보가 이력에 영원히 남는다.**

대안으로 **버전을 릴리즈 seq 로 통일하고 릴리즈 문서를 버리지 않고 보관하는** 안을 냈다. 실제로 재 보니 현재 그래프 전체가 **1.3MB, 압축하면 190KB** 라서 버전 1,000개를 쌓아도 190MB다.

> 여기서 **"왜 릴리즈가 다 통째냐, 애초에 증분이 목적이었는데"** 라는 지적을 받았다. 설명이 부족했다. **DB 에 가는 쓰기는 지금도 증분**이고, 통째인 것은 그 증분을 계산하는 **기준 문서**다. 통째여야 "무엇이 **사라졌는지**"를 알 수 있고, 틀어져도 다음 적재에서 스스로 맞춰진다.

오후에는 스택 자체를 다시 봤다. **RDF 계열(Fuseki + OWL + 추론)** 을 꽤 깊이 조사했고, **Apache AGE 로 옮기면** 무엇이 그대로 가고 무엇을 다시 짜야 하는지도 코드 기준으로 따졌다. 결론은 **지금 Neo4j 를 유지**다. RDF 로 가면 온톨로지까지 다시 써야 하고 조회(Text2Cypher)를 전부 버려야 한다.

다만 조사에서 **가져올 것 네 가지**는 건졌다. 특히 **벡터로 엔티티를 찾고 그 주변 그래프를 주는 조회 방식**은 지금 Neo4j 에서 그대로 할 수 있고, 조회 실패의 상당수를 줄일 수 있다.

## 1. 되돌리기 설계 — 방법 A 와 B

##### 방법 A: 버전 번호를 데이터에 붙이고 포인터만 움직인다
노드와 관계에 "몇 번 버전에서 생겼나"를 적어 두고, 현재 버전 포인터만 바꾼다.

- 변경이 없는 노드는 **처음 들어온 버전 번호 하나만** 적힌다. 버전마다 복사되지 않는다
- 속성이 바뀌면 **값을 담은 노드(State)가 하나 더 생긴다.** 대상 자체(Entity)는 하나고 관계도 그대로다
- Neo4j 커뮤니티에서 기본 Cypher 와 드라이버만으로 된다(APOC·Enterprise 기능 불필요)

##### 방법 B: 변경점을 따로 남긴다
"무엇을 추가하고 무엇을 삭제했는지"를 밖에 쌓아 두고, 되돌릴 때 반대로 적용한다.

##### 정해진 모양 — 미리보기 후 일괄 반영
Undo/Redo 를 누를 때마다 실제로 DB 를 고치지 말고, **여섯 일곱 번 눌러도 화면에만 반영**했다가 저장할 때 한 번에 쓰는 쪽으로 정했다. 변경 이력은 파일이 아니라 **PostgreSQL** 에 둔다.

```
앱 ──── 변경 이력 읽기 ────▶ PostgreSQL (버전 목록 · 변경 내역 · 현재 포인터)
 │  미리보기는 여기서 계산
 └──── 저장 시 1회 반영 ───▶ Neo4j (현재 버전 데이터만)
```

## 2. 그 설계를 우리 코드에 대보니

##### 이미 맞는 부분
Neo4j 엔 현재 버전만 둔다 · 비즈니스 키로만 참조한다(elementId 안 씀) · upsert 는 전체 속성 · **한 트랜잭션**으로 반영하고 순서를 지킨다 · DB 포인터를 기준으로 삼는다 · Browser 직접 수정 금지 · 동시 실행 차단. 전부 지금 적재기가 하고 있는 것이다.

##### 충돌하는 부분

| | 내용 |
|---|---|
| **1. 버전 체계가 두 개가 된다** | 이미 `ReleaseHead` 에 seq · 매니페스트 해시 · 직전 해시 사슬이 있다. 별도 버전 테이블을 또 두면 같은 일을 두 번 한다 |
| **2. "파일 = 버전"이 성립하지 않는다** (가장 큼) | 적재 한 번은 **크롤링 + 명단 전부**를 합쳐 릴리즈 하나를 만든다. 크롤링을 매일 돌리면 버전이 매일 생기고, **사용자 파일 하나를 되돌리려다 그사이 크롤링 갱신까지 같이 되돌아간다** |
| **3. 되돌려도 다음 적재가 다시 덮는다** | 원천(명단 파일, 사이트)이 그대로라 정기 적재가 원천을 보고 되돌린 내용을 **다시 만든다** |
| **4. 온톨로지 버전이 다른 곳으로는 못 간다** | 조회는 DB 와 코드의 온톨로지 버전이 **정확히 같아야** 답한다. 0.6.2 에서 0.6.1 시절로 되돌리면 조회가 멈춘다 |
| **5. 개인정보가 이력에 영원히 남는다** | undo 백업에 직원 속성이 통째로 들어간다. **"보관 기간 후 반드시 삭제"와 정면으로 충돌**한다. 그래프에서 지워도 PostgreSQL 에 남는다 |
| 6. 빠진 것 | 되살린 노드의 **임베딩**이 없다 · `retention.py` 가 지운 **원문**을 가리키면 출처 검증이 깨진다 · **ingress** 경로도 같은 체계에 들어와야 한다 |
| 7. 백업 | Community 는 `neo4j-admin dump` 에 DB 를 멈춰야 한다. 대신 **릴리즈 문서 자체가 논리 백업**이 된다 |

##### 수정안 — 버전을 릴리즈로 통일한다
```
버전      = 릴리즈 seq (ReleaseHead 와 하나)
저장소    = PG 에 seq · 매니페스트 해시 · 온톨로지 버전 · 출처 목록 · 전체 그래프(jsonb) · 작성자
미리보기  = 현재 릴리즈와 목표 릴리즈의 차이를 앱에서 계산
저장      = 목표 릴리즈 내용을 "새 seq" 로 기존 적재기에 넣음
이력      = 덮어쓰지 않고 늘 앞으로만 (v7 → "v3 내용으로 복원" = v8)
```
`kg_change`, undo 계산, 순변경 합치기, discarded 분기가 **전부 필요 없어진다.** 차이 계산과 쓰기는 이미 있는 부품을 쓴다. 앞으로만 쌓으니 "Redo 불가가 되는 버전" 경고도 없다.

그리고 되돌리기를 둘로 나눈다.

| 종류 | 언제 | 방법 | 지속성 |
|---|---|---|---|
| **출처 철회**(기본) | "이 파일 잘못 올렸다" | 그 업로드를 철회 → 다시 빌드 → 새 릴리즈 | 다음 적재에도 유지 |
| **긴급 복원** | 적재 사고로 그래프가 망가짐 | 마지막 정상 릴리즈 내용으로 새 릴리즈 | 원천을 고칠 때까지 정기 적재를 멈춰야 함 |

**10/02 에 정한 "삭제는 출처 단위" 원칙과 같은 결론**이다.

## 3. 통째와 증분 — 설명이 부족했던 지점

##### 실제로 도는 순서
```
① 릴리즈 문서 만들기 : "DB 가 최종적으로 이래야 한다" — 전체 그래프   ← 통째
② DB 현재 상태 읽기
③ 비교              : ① vs ② → 달라진 것만 골라냄
④ 쓰기              : 달라진 노드·관계만 MERGE/SET, 빠진 관계·지울 노드 삭제  ← 증분
⑤ 확인              : 다시 읽어 ① 과 같은지
```
`plan.py` 에도 "달라진 노드·관계만 MERGE 한다"고 적혀 있다. 바뀐 게 없으면 아예 쓰지 않는다(`unchanged`). **직원 한 명이 바뀌면 그 한 명만 쓴다.**

##### 그런데도 설계도가 통째인 이유
1. **"무엇이 사라졌는지"를 알 수 있다.** 변경분만 받으면 추가·수정은 알아도 빠진 것은 모른다. 9월 명단에 있던 한 직원이 10월 명단에 **없다**는 건 10월 명단 **전체**를 봐야 안다. 퇴사 판단 · 팀 이동 · 사라진 페이지 판단이 전부 이 원리다
2. **어긋나도 스스로 맞춰진다.** 변경분만 쌓으면 한 번 실패할 때 조금씩 틀어진 채로 계속 간다. 매번 최종 상태와 비교하니 누가 DB 를 잘못 건드려도 다음 적재에서 복구된다
3. **같은 입력이면 같은 해시** — PC 와 서버 결과를 비교할 수 있다
4. **쓴 뒤 검증할 기준**이 된다

##### 크기 — 재 봤다
운영 DB 의 현재 릴리즈를 **읽기만** 해서 쟀다.

| 항목 | 값 |
|---|---|
| 노드 | **716** (Capture 포함) |
| 관계 | **2,010** |
| JSON 크기 | **약 1.3MB** |
| gzip | **약 190KB** |
| 임베딩 | 포함 안 됨 (릴리즈 밖에서 관리) |

> 10/01 에 적은 616 · 797 은 **Capture 를 뺀 뷰어 기준**이다. 같은 그래프의 다른 셈이다.

항목 하나당 압축 후 약 70바이트라, **노드·관계 1만 개면 버전 하나가 압축 0.7MB** 다. 게다가 **내용이 바뀌었을 때만 버전이 생기고**, 보관 규칙(최근 30개 전부 → 그보다 오래된 건 월 1개 → 1년 넘으면 삭제)을 두면 수십 개 선에서 유지된다. 수십만 노드가 보이면 그때 **N번째마다 통째 + 사이는 변경분**으로 바꾸면 된다(동영상 키프레임 방식).

## 4. RDF 스택을 끝까지 따라가 봄

##### 표준과 구현물
**RDF 는 데이터를 적는 형식일 뿐이고, 추론은 소프트웨어가 한다.** `:Happy a :Dog` 와 `:Dog rdfs:subClassOf :Animal` 만 있으면 `:Happy a :Animal` 은 **어디에도 없다.** 추론기를 붙여야 도출된다. Jena 는 그 표준을 다루는 Java 프레임워크이고, **Fuseki 하나만 설치하면 SPARQL 엔진 · 저장소 · 추론이 다 들어 있다.**

##### 멀티 테넌시와 클러스터링은 다른 축이다

| | 멀티 테넌시 | 클러스터링 |
|---|---|---|
| 목적 | 데이터를 **나누고 격리** | 같은 데이터를 **여러 서버로**(성능 · 장애 대비) |
| 서버 수 | 한 대로 충분 | 여러 대 |
| 무료로 되나 | 대부분 됨 | **RDF 진영에서는 대부분 유료** |

저장소를 여러 개 두는 것도 **DB 서버를 여러 개 띄우는 게 아니라** 한 프로세스 안에 논리 저장소를 여러 개 만드는 것이다(MySQL 의 `CREATE DATABASE` 와 같다).

##### 제품 비교 — GraphDB Free 가 걸린다

| | **GraphDB Free** | **Jena Fuseki** |
|---|---|---|
| 상업적 사용 | **애매함** — 10.x 문서엔 "commercial & free to use", **11.x 엔 그 문구가 빠지고 "non-commercial" 표현**이 등장 | 자유 (Apache 2.0) |
| 저장소 개수 | **최대 5개** (11.x) → 봇 5개까지 | 제한 없음 |
| 동시 질의 | **2개** | 제한 없음 |
| 클러스터링 | 유료(Enterprise) | **무료** (RDF Delta) |
| 추론 성능 | **강함** (저장 시 미리 계산) | 메모리 기반이라 대용량에 약함 |
| 오픈소스 | 아님 | 맞음 |

추론 품질만 보면 GraphDB 지만, **상업 서비스 + 봇 여러 개**면 Fuseki 가 맞다.

##### 추론기 — 역할이 둘로 갈린다
```
[설계]  온톨로지 작성 → HermiT 로 엄밀하게 검사 (Protégé 또는 스크립트)
[운영]  Fuseki 에 올림 → Jena 추론기로 데이터에 실시간 추론
```
**함정은 HermiT 에서 되던 추론이 Fuseki 에서 안 될 수 있다는 것**이다. 그래서 **운영 온톨로지를 OWL 2 RL 범위로 작성**해야 둘이 일치한다.

| 프로파일 | 용도 | 대표 도구 |
|---|---|---|
| **EL** | 클래스 수십만 개짜리 거대한 분류 체계 | ELK, SNOMED CT |
| **QL** | 기존 관계형 DB 를 온톨로지로 조회 | Ontop |
| **RL** | **RDF DB 에 쌓인 데이터에 실시간 추론** | **Jena**, GraphDB, RDFox |
| **DL** | 전체 표현력. 설계 검사와 모순 탐지 | HermiT, Openllet |

RL 의 한계는 한 줄로 설명된다 — **있는 데이터로 새 사실을 계산하는 건 되지만, 데이터에 없는 개체의 존재를 결론으로 내는 건 안 된다.** 실제 데이터 추론이 목적이면 RL 로 충분하다.

추론기는 **HermiT 하나면 된다**(LGPL — 상업 서비스에 포함해도 내 코드 공개 의무 없음). Openllet 은 SWRL 과 모순 설명이 강하지만 **AGPL** 이라 서버 운영에 넣을 때 주의해야 한다.

##### RDF 쪽 버전 관리도 결국 같다
Fuseki 에도 **undo/redo 는 없다.** 트랜잭션 롤백은 커밋 전까지고, 백업은 통째라 세밀한 되돌리기가 안 된다.

| | 1. 앱에서 직접 기록 | 2. RDF Delta | 3. TerminusDB |
|---|---|---|---|
| 기록 위치 | **내가 고른 DB**(Postgres 등) | Patch Server 디스크 | DB 내부 |
| undo | 반대로 실행 (쉬움) | 역패치 (어려움) | `reset` |
| 추가 운영 | 없음 | Patch Server 하나 더 | DB 교체 |

**원리는 1·2 가 같다 — 이력을 별도 저장소에 쌓아 두고 반대로 적용한다.** 2번은 Postgres 에 못 쌓고, 꺼내서 옮기면 결국 1번이 된다. **1번이 답이고, 이건 Neo4j 든 RDF 든 똑같다.**

## 5. GraphRAG 전략 문서 검토 — 지금 스택을 유지한다

조사 결과를 모아 "Fuseki + HermiT + SHACL + pgvector" 전략 문서를 만들었고, 그걸 **우리 코드 기준으로 다시 검토**했다. 결론은 **권하지 않는다**이다. DB 교체가 아니라 **패러다임 교체**다.

| 부분 | AGE 로 갈 때 | **RDF(Fuseki) 로 갈 때** |
|---|---|---|
| 온톨로지 | 그대로 | **OWL + SHACL 로 다시 작성** |
| 검증 | 그대로 | SHACL 로 다시 (지금 검증기와 중복) |
| 파서 · 후보 | 그대로 | 후보 → 트리플 변환 다시 |
| 출처 | 그대로 | 관계에 붙은 출처 속성을 RDF 로 표현하기 어려움 |
| 조회 | 문법 맞추기 | **Text2Cypher → Text2SPARQL 전면 재작성** |

##### 우리 원칙과 부딪히는 것
- **추론 vs `direct_only`** — 우리는 원천이 말한 사실만 저장한다. OWL 추론은 저장은 안 해도 **조회 결과에 추론된 사실이 섞여 나온다.** 근거에 원천과 추론을 구분해 보여 주지 않으면 출처 추적이 흐려진다. 게다가 우리 도메인(조직 · 직원 · 사업)에는 **클래스 계층이 거의 없다.** 이득이 있는 건 상위 조직 전이 정도인데 이미 가변 길이 경로로 처리한다
- **엔티티 자동 매칭** — 유사도로 자동 병합하자는 것인데, 우리는 **키나 사람이 확정한 CSV 로만** 병합한다. 유사도는 제안까지다
- **URI 를 UUID 로** — 무작위면 같은 원천을 다시 적재할 때 **같은 대상이 같은 ID 로 안 나온다.** 우리는 원천 값에서 만든 **결정적 해시 키**다
- **적재 경로가 LLM 추출 하나뿐** — 우리 주력인 규칙 기반 경로(크롤링 · 명단)가 빠져 있다
- 작은 것 — 벡터 차원 1536은 OpenAI 기준이고 **우리는 BGE-M3 라 1024** 다. "무료 + 상업 사용"이 기준이었는데 **Neo4j Community 도 상업 사용은 무료**다(걸리는 건 멀티 DB 와 클러스터)

##### 가져올 아이디어 넷

| 아이디어 | 지금 적용 |
|---|---|
| **질문 → 벡터로 엔티티 찾기 → 1~2홉 주변 그래프 → LLM** | Text2Cypher 보다 안정적. **Neo4j 에서 그대로 가능.** 이름 표기·줄임말 때문에 생기는 조회 실패를 상당히 줄인다 |
| 문서 조각과 엔티티를 `mentions` 로 연결 | 채팅의 문서 검색과 그래프를 잇는 고리 |
| **임베딩 대상을 온톨로지에 표시** | 우리 온톨로지 칸에 추가하면 된다. 앞서 얘기한 `exposure` · `searchable` 과 같은 결 |
| 모든 쓰기는 백엔드 한 곳으로 | 이미 그렇게 하고 있다 |

## 6. Apache AGE 전환 검토

##### 온톨로지는 그대로 간다
DB 를 만지는 코드를 `writers/` 한 곳에 몰아 둔 덕분이다.

| 그대로 | 바꿔야 함 |
|---|---|
| 온톨로지 선언 · 버전 · 승격 | **DDL 파생** — AGE 는 Cypher 제약이 없어 PostgreSQL 유일 인덱스를 직접 걸어야 함 |
| **검증기** | **쓰기** — psycopg + `cypher()` 호출, openCypher 일부만 지원해서 문장 재작성 |
| 파서 · 후보 생성 | **조회(Text2Cypher)** — 가장 큰 공사. LLM 이 Neo4j 문법에 익숙해 **실패율이 오를 가능성** |
| 릴리즈 만들기 · 정리 규칙 | 벡터 검색 → pgvector, 헬스 체크 · 운영 스크립트 |

##### 얻는 것과 잃는 것
얻는 것은 셋이다 — **그래프와 버전 기록을 한 트랜잭션으로**(지금 Neo4j 와 PG 를 못 묶는 문제가 사라진다), **읽기 전용 계정**(Community 에서 못 하던 것), **온라인 백업**(`pg_dump`). 잃는 것은 Cypher 범위 · 도구 · 긴 경로 탐색 성능이다.

> **AGE 는 표 위에 그래프를 흉내 낸다.** 한 번 건널 때마다 "나가는 관계 행을 찾고 → 끝 노드 행을 찾는" 표 조회가 들어간다. Neo4j 는 노드가 이웃의 위치를 직접 들고 있어 주소를 따라 바로 이동한다. 다만 **지금 규모(노드 약 700)에서는 체감 차이가 없다.** 판단 기준은 성능이 아니라 **Cypher 지원 범위**다.

##### 무료 + 멀티테넌시 + 클러스터 조건으로 거르면

| DB | 무료 멀티테넌시 | 무료 HA | Cypher | 판단 |
|---|---|---|---|---|
| Neo4j Community | 안 됨 | 안 됨 | 완전 | **탈락**(조건 기준) |
| Memgraph Community | 안 됨 | 안 됨 | 거의 완전 | 탈락에 가까움 |
| **Apache AGE** | 됨 | 됨 (PG 복제 + Patroni) | 일부 | **1순위** |
| ArcadeDB | 됨 | 됨 | 범위 확인 필요 | 2순위, **검증 부족** |
| NebulaGraph | 됨 | 됨 (분산 기본) | 약함(nGQL 주력) | **과함** — 서버 3대 권장, 작은 그래프에선 분산 비용만 |

판단 방법은 하나다. **조회가 실제로 쓰는 Cypher 대표 10~20개를 AGE 와 ArcadeDB 에 돌려 보는 것.** 적재는 쓰기 모듈과 DDL 만 바꾸면 되니 결정 기준은 조회 호환성이다.

##### 결론
1. **조회 방식 개선**(벡터 → 엔티티 → 주변 그래프)을 지금 Neo4j 에서 **먼저** 한다. 효과가 가장 빠르다
2. 멀티 테넌시와 HA 가 실제로 필요해지면 **AGE 를 시험**한다. 온톨로지와 적재 파이프라인은 그대로 간다
3. 추론이 꼭 필요한 요구가 생기면 그때 RDF 를 다시 본다

## 7. 곁가지 — 임베딩 현황과 다음 후보

우리도 이미 임베딩을 하고 있고, **어느 라벨을 임베딩할지는 온톨로지 선언이 정한다.** 전략 문서의 `:embeddable` 표시와 같은 역할이다.

| 레이어 | 우리 쪽 | 임베딩 |
|---|---|---|
| 온톨로지(개념) | 온톨로지 선언 | 안 함 — 조회 LLM 에 스키마로 줌 |
| **엔티티** | 회사 · 조직 · 직원 · 사업 · 발주처 · 기술 · 분야 · 사무소 · 연혁 | **사업(약 200) · 기술(12)만** |
| 원문(문서) | Capture + SOURCED_FROM | 안 함 — 본문이 그래프에 없음 |
| 값 | 이름 · 날짜 등 | 엔티티 문장에 섞임 |

임베딩 문장에 **이웃 정보(발주처 · 분야)** 를 넣는 것도 전략 문서의 "이름 + 클래스 + 핵심 관계"와 같은 방식이다.

| 추가 후보 | 판단 |
|---|---|
| **사업분야**(5) · **연혁**(27) | **권함.** 설명이 문장형이라 이름 정확 일치로는 못 찾는 질문에 효과가 크다 |
| 조직 · 발주처 | 애매. 이름이 짧아 벡터보다 **별칭과 정규화**가 낫다 |
| 직원 | **하지 않음.** 개인정보이고 이름 검색에 벡터가 맞지 않는다 |

문서 조각 임베딩은 **채팅 쪽 문서 검색과 역할이 겹친다.** 하게 되면 그쪽과 나누는 것부터 정해야 한다.

## 재사용 가능한 판단

- **증분을 안전하게 하려면 기준이 통째여야 한다.** 변경분만으로는 "무엇이 사라졌는지"를 영원히 알 수 없고, 한 번 틀어지면 계속 틀어진다
- **되돌리기 단위는 "시점"이 아니라 "출처"다.** 여러 원천이 한 릴리즈에 섞이는 구조에서 시점 복원은 엉뚱한 것까지 되돌린다. 그리고 원천이 그대로면 **정기 적재가 다시 덮는다**
- **이력은 되돌리기만 생각하면 안 된다.** 개인정보가 거기 영구 보관된다. 삭제 정책과 이력 설계는 같이 결정해야 한다
- **설계를 받으면 전제부터 확인한다.** "파일 하나 = 변경분 하나"라는 전제가 깨지면 그 아래 설계는 다 흔들린다
- **이미 있는 체계와 같은 일을 하는 설계는 합친다.** 릴리즈 사슬이 이미 버전 체계인데 별도 버전 테이블을 두면 두 체계가 어긋난다
- **DB 를 만지는 코드를 한 곳에 몰아 두면 DB 교체 비용이 그 한 곳으로 수렴한다.** 오늘 AGE 검토에서 파싱 · 후보 · 검증 · 릴리즈가 전부 "그대로"로 나온 이유다
- **스택 교체 비용은 저장소가 아니라 조회에서 나온다.** 적재는 쓰기 모듈 교체로 끝나지만 Text2Cypher 는 통째로 다시다
- **"무료"는 조건을 붙여서 물어야 한다.** 멀티테넌시 · 클러스터 · 동시 질의 · 저장소 개수까지 넣으면 후보가 급격히 줄고, 라이선스 문구는 메이저 버전에서 바뀐다
- **남의 전략 문서는 기각하더라도 가져올 것만 따로 뽑는다.** 패러다임이 안 맞아도 조회 방식 같은 조각은 지금 스택에서 바로 쓸 수 있다
- **벡터를 쓸 곳과 쓰지 말 곳을 레이어로 가른다.** 이름이 짧은 대상은 벡터보다 별칭·정규화가, 설명이 문장형인 대상은 벡터가 낫다

## 한계

- **코드는 하나도 고치지 않았다.** 오늘은 전부 검토와 설계다
- **버전 관리를 어느 안으로 갈지 확정하지 않았다.** 네 가지를 정해야 한다 — 버전을 릴리즈 seq 로 통일할지, 되돌리기를 출처 철회 위주로 할지 시점 복원도 열지, 이력 보관 기간과 개인정보 지우기 규칙, 되돌릴 수 있는 기간(그만큼 원문도 보관)
- **AGE 는 아무것도 시험해 보지 않았다.** Cypher 호환 범위, 지원 PostgreSQL 버전, 프로젝트 성숙도 전부 미확인이고, 조사 내용 일부는 기억에 의존한 것이라 공식 문서 확인이 필요하다
- **RDF 스택도 설치해 보지 않았다.** Fuseki · HermiT · SHACL 은 조사 단계다
- **제안한 조회 방식(벡터 → 엔티티 → 주변 그래프)은 조회 담당자 영역**이다. 제안까지만 했다
- **1만 개 규모 측정은 추정이다.** 현재 2,726개 기준으로 비례 계산한 값이다
- **GraphDB 11.x 의 상업 사용 가능 여부를 확정하지 못했다.** 약관 원문 확인이나 문의가 필요하다
