## 개념

- **파서 / 후보 생성 / 검증** — 적재의 세 단계. 파서는 원문에서 "어느 원문의 어떤 값"(레코드)만 뽑고, **후보 생성이 라벨 · 키 · 관계를 정하고**, 온톨로지는 만드는 데 쓰이지 않고 **만든 결과를 판정**한다
- **릴리즈** — "DB 가 이렇게 돼야 한다"는 완성본 문서. 그래프 전체 + 매니페스트(순번 · 직전 해시 · 온톨로지 버전 · 지울 목록) + 리포트를 해시로 고정한 것. 적재는 이 문서대로만 쓴다
- **전체 현황 출처 vs 사건 출처** — 명단 · 사이트는 그 시점의 **전체 상태**를 말해서 최신 하나로 **교체**되고, 사용자가 올리는 문서는 각자 독립된 사실이라 **쌓인다**. 삭제 기준이 갈리는 지점
- **현재 상태 관계 vs 과거 사실 관계** — 소속 · 상위 조직은 지금 유효해야 참이고, 연혁 · 발주 · 사업 수행은 한 번 일어나면 바뀌지 않는다. 팀이 사라졌을 때 앞은 끊고 뒤는 남긴다
- **Jev** — 2026-09-15 공개된 판단 전용 모델. 문장을 만들지 않고, 주어진 보기 중에서 **타입 있는 값과 확신도**만 돌려준다

## 요약

오늘은 코드를 거의 쓰지 않고 **설명과 정책**을 정리한 날이다.

먼저 **적재 과정을 남에게 설명할 수 있는 형태로** 정리했다. 핵심은 세 가지다 — 라벨은 **주소**로 정하고 관계는 **페이지 구조와 칸의 뜻**으로 정한다는 것, **온톨로지는 만들지 않고 판정만** 한다는 것, **릴리즈와 적재를 나눈 덕분에** 미리 보기 · 서버와 PC 결과 일치 확인 · 다시 읽어 검증이 가능하다는 것이다.

운영 Neo4j 가 어느 서버에 있는지도 처음으로 직접 확인했다. **Docker 컨테이너로 3주째 가동 중**이고, 이미지 태그가 버전으로 고정돼 있지 않은 점과 포트가 외부 전체에 열려 있는 점을 함께 확인했다.

새 모델 **Jev** 를 검토했다. 문장을 생성하지 않고 보기 중에서만 고르는 모델이라, **"온톨로지 밖의 답을 낼 수 없다"** 는 성질이 우리가 지키려던 원칙과 정확히 겹친다. 역할을 **판단은 Jev, 새 정의 생성은 LLM, 적용과 검증은 코드, 최종 승인은 사람**으로 나눌 수 있다.

그다음 **사용자가 주는 파일의 적재 · 수정 · 삭제**를 정했다. 수정은 **최신 파일이 이긴다**로 깔끔하게 끝나는데, 삭제가 어려웠다. 파고들어 보니 "없어졌다"는 신호가 **퇴사 · 사이트 개편 · 잘못 올린 글 정정**을 모두 뜻할 수 있어서, 한 가지로 처리할 수 없었다.

결론은 **자동 판단 범위를 아주 좁히는 것**이다. 원천에서 없어지면 **상태 변경까지만** 자동으로 하고, 실제 삭제는 **기한 · 정정 · 철회** 세 계기에서만 한다. 그 밖의 애매한 경우는 전부 사람에게 간다.

곁가지로 `main` 을 받아 보니 **그래프 조회 API 가 이미 추가돼 있었다.** 어제 "API 는 1만 개 넘을 때"로 미뤘던 그 API 다. 다만 상한이 관계 2,000개라 1만 개 전체는 못 받는다. 받는 방식 네 가지를 비교하고 **상한만 올리는 안**으로 정리했다.

## 1. 적재 과정 정리 — 누가 무엇을 정하나

##### 세 단계로 나뉘어 있다
```
① 파서        원문 → 레코드(종류 + 값)        ← 무엇이 적혀 있나만 뽑음
② 후보 생성    레코드 → 노드 · 관계            ← 라벨 · 키 · 관계를 코드가 직접 정함
③ 검증        노드 · 관계 → 온톨로지와 대조     ← 맞는지 판정만 함
```

**온톨로지는 ②에 쓰이지 않는다.** 그래서 **새 라벨을 온톨로지에 추가해도 ②의 코드가 없으면 적재로는 데이터가 생기지 않는다.** 어제 정리한 "관리자가 바꿀 수 있는 온톨로지 변경" 이야기와 바로 이어지는 지점이다.

##### 라벨은 주소로, 관계는 세 가지 근거로

| 관계의 근거 | 예 |
|---|---|
| **회사 사이트라는 전제** | 회사 → 연혁 · 사무소 · 보유기술 · 사업분야 |
| **페이지 안의 구조** | 조직도 **트리** → 상위 조직, 사업실적 표의 **발주처 칸** → 발주, 목록 **주소의 분류 값** → 분야 |
| **다른 출처와 연결** | 명단의 팀 · 부서 이름으로 사이트 조직도를 찾아 소속 연결, 연혁의 "물적분할 + ㈜아사달" **한 줄**로 모회사 관계 |

모두 사람이 사이트를 보고 미리 코드에 적어 둔 규칙이고, 그때그때 판단하지 않는다. **원천이 직접 말한 관계만 넣는다**(`direct_only`)는 원칙도 그대로다.

##### 예외는 자동 분기가 없다

| 종류 | 처리 |
|---|---|
| 규칙에 안 맞음 | **멈춤** — 모르는 칸, 모회사 근거 줄이 0개나 2개, 옛 명단, 회사별 퇴사 10% 초과 |
| 애매함 | **사람이 결정한 CSV** 를 따름 — 발주처가 같은 곳인지, 기관유형 동률 |
| 값만 이상함 | **비우고 알림** — 전화번호 자릿수, 조직도에 없는 팀 |

##### "모르는 라벨" 검사는 데이터 검사가 아니라 코드 검사다
규칙이 만드는 라벨은 코드에 적힌 것뿐이라, 정상 동작 중에는 생기지 않는다. 그런데도 두는 이유는 **코드와 선언이 어긋나는 사고**를 잡기 위해서다. 그래서 하나만 나와도 전체를 멈춘다.

> 9/23 에 실제로 걸렸다. 퇴사 처리 코드가 이미 온톨로지에서 없앤 속성을 직원 노드에 다시 찍고 있었다. 그대로 운영에 갔다면 **첫 퇴사자가 생기는 날 적재 전체가 멈췄을** 것이다.

데이터 때문에 실제로 자주 걸리는 건 값 문제다 — 어휘(`초급직원`), 날짜 형식, 필수 값, 카디널리티, 출처 불일치.

##### 릴리즈와 적재를 나눈 이유

| | 릴리즈 | 적재 |
|---|---|---|
| 무엇 | 완성본 문서를 만듦 | 문서대로 DB 에 반영 |
| DB | **읽기만** | 씀 |
| 실행 | 항상 | `--write` 일 때만 |

나눈 덕에 가능해진 것 — ① 쓰기 없이 추가 · 변경 · 삭제 **미리 보기** ② 같은 입력이면 같은 해시(**서버와 PC 결과가 일치하는 것을 9/23 에 확인**) ③ 적재는 판단하지 않고 적힌 대로만 쓰며 **다시 읽어 검증** ④ 직전과 같으면 쓰기 건너뜀 ⑤ DB 를 만지는 코드가 한 곳 ⑥ 릴리즈가 사슬로 이어져 이력이 남음.

## 2. 운영 Neo4j 가 있는 서버 확인

그동안 **DB 계정만 있고 서버에 들어가 본 적이 없었다.** DB 비밀번호와 서버 계정은 다른 문이다 — 앞은 금고, 뒤는 건물 출입문이다. 데이터 작업은 DB 계정으로 되지만, 설정 · 재시작 · 백업 · 플러그인은 서버 접속이 필요하다.

확인 결과 운영 Neo4j 는 **Docker 컨테이너로 3주째 가동 중**(상태 검사 통과)이고, **Community 판**이다. 모두 읽기 명령으로만 확인했고 재시작이나 설정 변경은 하지 않았다.

| 눈여겨볼 것 | 내용 |
|---|---|
| **이미지 태그가 버전으로 고정돼 있지 않다** | 누가 이미지를 다시 받고 컨테이너를 만들면 그때의 최신 5.x 로 **의도치 않게 올라간다** |
| **DB 포트가 외부 전체에 열려 있다** | 비밀번호로만 막혀 있다. 우리 PC 와 API 서버만 허용하도록 방화벽을 두는 게 맞다 |

둘 다 인프라 담당자와 상의할 일이다. 어제 뷰어에서 찾은 "관리자 계정이 PHP 에 평문" 과 같은 묶음의 문제다.

## 3. Jev — 판단 전용 모델을 어디에 끼울 수 있나

##### 무엇을 내는 모델인가
문장을 이어 쓰지 않고, **미리 정한 질문에 대한 타입 있는 값**을 낸다.

| 질문 타입 | 출력 | 예 |
|---|---|---|
| 선택 | 보기 중 하나 + 각 보기의 확률 | "이 칸은?" → `rank` 0.93 |
| 예 / 아니오 | 확률 | "두 라벨이 같은 뜻인가?" → 0.81 |
| 점수 | 숫자 | "이 관계의 근거 강도" → 0.67 |

**새 내용을 지어낼 수 없고, 항상 준 보기 안에서만 답한다.** 할루시네이션 대신 "틀린 보기를 고를" 위험만 남고, 그 대신 **확신도**가 같이 온다.

##### 우리 구조와 겹치는 지점
**보기가 온톨로지에서 나온다.** 속성 목록 · 어휘 · 관계 종류가 곧 질문의 보기다. 그래서 **Jev 는 온톨로지 밖의 답을 낼 수가 없다.** 우리가 지키려던 "온톨로지에 없는 건 멈춤"과 같은 성질이다.

| 제안 과정의 일 | Jev |
|---|---|
| 이 파일이 무슨 파일인가 / 이 칸은 어느 속성인가 | **적합** |
| 처음 보는 직급이 기존 어휘 중 무엇인가, 새 값인가 | **적합** |
| 새로 들어온 대상이 기존 노드 중 누구인가, 신규인가 | **적합** — 중복 노드를 막는 핵심 판단 |
| 두 대상 사이 관계가 선언된 관계 중 무엇인가 | **적합** |
| 새 라벨의 이름 · 정의 · 관계 뜻 쓰기 | **불가** → LLM + 사람 |
| 비정형 문서에서 대상 이름 뽑기 | **불가에 가까움** → 규칙이나 LLM |

##### "해당 없음" 은 받을 수 있다
보기에 "해당 없음"을 넣거나, 예/아니오로 먼저 묻거나, **1등 보기의 확률이 낮으면** 없는 것으로 본다. 보기를 주면 모델이 **억지로 가장 비슷한 걸 고르는 경향**이 있을 수 있어서 이 안전장치가 필요하다.

**"해당 없음"이 자주 나오는 영역이 곧 온톨로지를 늘려야 할 곳**이라는 신호가 된다.

##### 역할 분담
```
판단(보기 중 고르기)  → Jev        빠르고 싸고, 답이 온톨로지 안에 갇힘, 확신도 있음
생성(새 문장 · 정의)  → LLM        Jev 로 안 되는 부분만
적용 · 검증           → 코드(규칙)  지금 그대로
최종 승인             → 사람
```
확신도로 **자동 통과 / 사람 검토 / 보류** 셋으로 나누면 사람이 볼 양이 줄고 우선순위도 생긴다. 다만 Jev 가 판단한 데이터도 **바로 넣지 않는다** — 코드 적용 → 온톨로지 검증 → 릴리즈 미리 보기 → 승인 → 적재는 그대로다. **"제안하는 손"이 LLM 에서 Jev 로 바뀌는 것일 뿐**이다.

##### 입력 종류별로 필요한 단계가 다르다

| 입력 | 이름 뽑기 | 판단 |
|---|---|---|
| 정형 파일(아는 양식) | 불필요 — 칸 값이 곧 이름 | 저장된 연결표(규칙) |
| 정형 파일(새 양식) | 불필요 | Jev → 사람 확인 → 양식 저장 |
| 우리 사이트 크롤링 | 불필요 — **구조를 이미 안다** | 규칙 |
| 비정형 문서 · 외부 URL | **LLM 필요** | Jev, 없으면 LLM 제안 |

## 4. 사용자가 주는 파일 — 적재 · 수정 · 삭제

##### 원칙: 출처가 단위다
파일 하나 = 출처 하나. 그 파일에서 나온 노드와 관계에 전부 그 출처가 붙고, 누가 언제 올렸는지도 남긴다. **DB 를 직접 고치지 않는다** — 적재 · 수정 · 삭제 모두 미리 보기 → 승인 → 릴리즈 → 적재 → 다시 읽어 확인을 거친다. 사용자 파일은 **사이트나 명단에서 온 사실을 덮어쓰지 않는다.**

##### 수정은 간단하다
같은 파일의 새 버전이 오면 그 출처의 기여분을 다시 계산해 **추가 / 변경 / 빠짐**을 미리 보여 주고 승인받는다. 명단을 매번 새 파일로 갱신하는 지금 방식과 같은 개념이다. **최신 파일이 이긴다.**

사실 하나만 고칠 때는 DB 를 직접 고치지 않고 **"정정" 기록을 하나의 출처로** 남긴다. 나중에 "이 값은 왜 이렇게 됐나"를 추적할 수 있다.

##### 삭제에서 막혔다
처음엔 "그냥 노드와 주변 관계를 지우면 안 되나"였다. 안 되는 이유가 네 가지였다 — ① 다른 출처가 말하는 사실까지 사라진다 ② 사이트 · 명단에서 온 것은 **다음 적재가 다시 만든다**(또는 지문 불일치로 적재가 **멈춘다**) ③ 노드에 붙은 관계 중 일부는 남의 근거다 ④ 누가 왜 지웠는지 남지 않는다.

그래서 **"근거를 빼고, 근거가 없어진 것만 지운다"** 로 바꿨다. 결과는 "냅다 지우기"와 같지만, 남의 근거가 있는 건 건드리지 않고 지우기 전에 보여 주고 기록이 남는다.

> **그다음 지적이 핵심이었다.** "그렇다고 전부 비활성으로만 두면 삭제 정책이 아예 없는 거라 쌓이기만 하면 언젠가 터진다." 맞다. 그리고 이건 **지금 우리 그래프에도 해당된다** — 사이트에서 사라진 노드와 퇴사자가 비활성으로 계속 쌓이는데, **언제 실제로 지울지 정해 둔 규칙이 없다.**

##### 근거는 쌓이지 않는다 — 출처 종류에 따라 다르다

| 출처 종류 | 근거 | "없음"의 뜻 | 삭제 기준 |
|---|---|---|---|
| **전체 현황**(명단 · 사이트) | **교체**(최신 하나) | 최신에 없으면 "이제 아님" → 퇴사 · 사라짐 | **상태가 된 날 + 기간** |
| 문서의 **과거 사실** | 쌓임 | 해당 없음 | 철회할 때만. **나이로 지우지 않음** |
| 문서의 **현재 상태 주장** | 쌓임 | 오래 재확인 안 됨 | N개월 미확인 → **검토 필요** 표시 |
| 개인정보 | — | — | 보관 기간 경과 시 **반드시** 삭제 · 익명화 |

9월 명단과 10월 명단이 근거로 함께 쌓이는 게 아니다. 10월 명단이 9월 것을 **대체**한다. 실제로 9/28 적재 때 **9/14 명단의 원문이 아무도 안 가리키게 돼서 삭제**됐다("지울 것 Capture 1"이 그거였다).

> **그래서 "최근 5년 내 근거가 없으면 삭제"는 명단에 쓸 수 없다.** 퇴사자의 근거는 **"빠진 것을 확인한 최신 명단"** 으로 계속 갱신되므로, 근거 나이로는 영원히 지워지지 않는다. 기준은 **"그 상태가 된 지 얼마나 됐나"** 여야 한다. 그런데 지금 그래프에는 **"언제부터 그 상태인지"가 기록되지 않는다.** 날짜 칸 추가가 첫 작업이다.

## 5. 관계의 시간성 — 팀이 사라져도 과거는 사실이다

팀이 없어졌을 때, 구성원 소속은 끊어야 하지만 **"그 팀이 2024년에 이 사업을 했다"는 팀이 없어져도 참**이다.

| 관계 종류 | 예 | 팀이 사라지면 |
|---|---|---|
| **현재 상태** | 직원 소속, 팀의 상위 조직, 사무소 | **끊음** — 이제 사실이 아니다 |
| **과거 사실** | 연혁, 발주, 분야, (앞으로) 사업 수행 팀 | **유지** — 여전히 사실이다 |

노드는 **"과거 사실이 가리키는 동안 보존"** 한다.
```
원천에서 사라짐 → 현재 상태 관계 끊기 + 상태 · 날짜 기록
                 → 유예 기간 경과 후: 과거 사실이 가리킨다 → 보존
                                      아무도 안 가리킨다   → 실제 삭제
```
그래서 **쌓이는 건 "과거 기록으로 의미 있는 노드"뿐**이고, 그 양은 실제 역사만큼으로 제한된다. "쌓여서 터지는" 문제를 이렇게 막는다.

**관계마다 어느 종류인지를 온톨로지 선언에 적어 두면**(`temporal: current | historical`) 적재기가 관계 종류만 보고 기계적으로 처리할 수 있다. 사람이 경우마다 판단하지 않아도 된다. 조회도 같이 바뀌어야 한다 — 현재 질문은 활성만, **과거 질문은 과거 사실 관계를 따라 해체된 노드도 허용**해야 한다.

## 6. 그래서 무엇을 지우는가 — 범위는 생각보다 좁다

| 구분 | 대상 | 방식 |
|---|---|---|
| **의무 삭제** | 개인정보(퇴사자 등) | 보관 기간 경과 → 자동 후보 → 승인 |
| **정정 삭제** | 오류, 중복 노드, 잘못 올린 파일 | 사람 요청 → 미리 보기 → 승인 |
| **요청 삭제** | 철회된 파일 | 요청 → 미리 보기 → 승인 |
| **만료 삭제** | 과거 기록에 안 걸린 끝난 현재 상태(해체 조직, 폐쇄 사무소) | 유예 경과 → 자동 후보 → 승인 |
| **자동 정리** | 고아 원문, 추출 캐시, 옛 회차 | 적재 후 자동 — **이미 구현됨** |
| **보존** | 사업실적 · 연혁 · 발주처 · 회사 · 사업분야 | **지우지 않음** |

##### 최종 결론: 자동 판단을 좁힌다
```
원천에서 없어짐  →  자동으로는 "상태 변경"까지만 (퇴사 · 사라짐 · 해체)
실제 삭제        →  ① 기한  ② 정정  ③ 철회  세 계기에서만
그 밖의 애매한 것 →  상태만 바뀐 채 남아 있음 (사람에게)
```
**잘못 지우는 것이 안 지우는 것보다 훨씬 비싸다.** 지운 건 되돌리기 어렵고, 남겨 둔 건 언제든 지울 수 있다.

##### 애매한 경우 하나
사이트 사업실적 게시판에서 **글이 내려갔을 때**. 과거 사실이니 남겨야 할 것 같지만, 내린 이유가 "원래 틀린 글"일 수도 있다. 자동으로 지우지도, 그냥 두지도 말고 **"사라짐(검토 필요)"으로 표시해 사람이 판단**하게 한다.

##### 착수 순서
1. **상태 변경일 기록** — 퇴사 · 사라짐 · 해체에 날짜 칸 추가. 이게 있어야 기한 판단이 된다
2. **개인정보 기한 삭제** — 보관 기간만 정하면 규칙 하나로 끝난다
3. **정정 · 철회 절차** — 요청 → 미리 보기 → 승인 → 지울 목록 → 적재
4. 해체 조직 등 만료 삭제는 **실제로 쌓이는 게 보일 때** 추가한다

**정책으로 정해야 할 값 세 개** — 사라진 노드 유예 기간, 퇴사자 개인정보 보관 기간(법무 확인), 철회 시 원본 파일 보관 여부. 기술이 아니라 정책이다.

## 7. 곁가지 — 조회 API 가 이미 들어와 있었다

##### 정정
`main` 을 받기 전 로컬 코드만 보고 **"조회 API 는 없다"고 답했는데 틀렸다.** 최신 `main` 에는 PR #21 에서 **그래프 조회 API 가 추가**돼 있었다. 어제 "API 는 1만 개 넘을 때로 미루자"고 했던 그 자리를 다른 분이 이미 만들어 둔 것이다. 응답 형식도 지금 뷰어가 쓰는 PHP 와 같다.

| 항목 | 내용 |
|---|---|
| 상한 | **관계 기준 기본 300, 최대 2,000** — 넘으면 `truncated: true` |
| 인증 | API 키 필요, 키가 없으면 503 |
| 타임아웃 | 10초 (PHP 는 25초) |
| **속성** | **거르지 않는다** — 직원 전화번호와 임베딩이 그대로 나간다 |
| 뷰어 | 아직 이 API 를 쓰지 않고 기존 PHP 를 호출한다 |

함께 들어온 변경은 ① 질의응답 정확도 보완(Qwen 모델 지원, 동명이인 구분, 회사 소속 조건, 같은 이름 조직 구분, 상위 회사 경로 8단계) ② **신규 자료 적재 전 검토 · 교정 · 승인 전 검증**(ingress) ③ 시험 · 개발 폴더를 Git 에서 제외.

##### 1만 개를 받는 방법 비교
지금 상한으로는 1만 개 전체를 받을 수 없다. 관계 2,000개면 노드는 많아야 4,000개이고, **정렬이 없어서 잘릴 때 어느 2,000개가 올지 정해져 있지 않으며**, 나머지를 이어 받는 방법도 없다.

| 방법 | 판단 |
|---|---|
| **A. PHP 그대로** | 코드 변경 없음. 속성 거르기와 계정 노출 문제는 그대로 |
| **B. 상한만 올리기** | **1만 개까지는 이걸로 충분할 가능성이 높다.** PHP 가 이미 같은 방식이다 |
| C. 커서로 나눠 받기 | 총 시간은 줄지 않는다. 이득은 **안정성**(한 번 호출이 타임아웃을 안 넘김)뿐 |
| D. 일부만 보여주고 펼치기 | 화면을 어떻게 보여줄지의 문제라 **프론트에서 정할 일** |

> **정정.** 처음에 C 의 장점을 "응답이 가볍고 타임아웃 위험이 적다"고만 적어 더 빠른 것처럼 읽히게 썼다. **총 시간은 B 와 비슷하거나 조금 더 길다** — 호출마다 왕복이 붙고, 정렬 때문에 **매 호출이 전체를 다시 훑는다.** C 를 권한 건 과했다.

병렬로 받는 것도 따져 봤다. 커서 방식은 다음 시작점을 앞 묶음이 알려주므로 **병렬이 불가능**하다. 번호(SKIP)로 나누면 **요청마다 전체를 훑고 정렬**해서 DB 가 같은 일을 N번 한다. 그나마 자연스러운 건 **관계 타입별로 나누는 것**이다(서로 겹치지 않는다). 다만 1만 개에서 오래 걸리는 건 조회가 아니라 **배치(10~13초)** 라서, 조회를 병렬로 해서 1초를 줄여도 체감은 거의 같다.

##### 시간을 줄이는 순서
```
1. 응답 작게 — 속성 허용 목록(전화번호 · 임베딩 제외), gzip 압축     ← 가장 쉽고 확실
2. 반복하지 않기 — 릴리즈 버전 기준 서버 · 브라우저 캐시
3. 그래도 크면 — 배치 결과 좌표 저장, 또는 펼치기 방식
```
"전체를 보낸다"는 전제라면 **데이터가 커질수록 시간이 늘어나는 건 피할 수 없다.** 근본적으로 안 늘게 하려면 전체를 보내지 않는 것뿐이다.

##### 점진적 로딩은 배치를 먼저 바꿔야 한다
"중심 노드부터 보내고, 나머지가 오는 동안 앞부분을 계산하면 빨라 보이지 않나" — 방향은 맞다. 다만 **지금 배치와는 맞지 않는다.** 지금 배치는 중심 선택 · 가지 각도 · 꽃 크기를 **전체를 다 본 뒤에** 정하므로, 나머지가 들어오면 **이미 그린 화면이 크게 흔들린다.** 필요한 것은 ① **이미 그린 노드를 고정하는 덧붙이기 배치** ② 백엔드가 중심부터 단계별로 보내기 ③ 가지 크기를 미리 알려 자리를 비워 두기. 어제 만든 꽃 · 부채꼴 규칙은 그대로 쓸 수 있다.

##### 다른 사람이 만지고 있는 뷰어
어제 올린 뷰어 파일 위에 **다른 분의 미커밋 변경**이 있었다. 상단 메뉴에서 "지식 그래프"를 빼고 화면 안에 **"그래프 조회 / 지식 추가" 탭**을 만드는 작업이다(`htm` + `css`). 배치 코드(`js`)는 **바뀌지 않았다.**

> 확인이 필요한 점 하나 — **"지식 추가" 탭이 가리키는 파일이 아직 로컬에 없다.** 그대로 올리면 404 가 난다. (처음에 "탭 스타일도 없다"고 했는데, 내가 확인한 직후에 추가돼서 틀린 말이 됐다.)

##### 보안 한 건
`.env` 가 원격 저장소에 추적되고 있고, 이번 PR 에서 모델 설정 세 줄이 추가됐다. **API 키가 저장소 이력에 남는다는 뜻이다.** 값은 확인만 하고 옮기지 않았다. 키 교체와 추적 해제를 권했다.

## 재사용 가능한 판단

- **만드는 쪽과 판정하는 쪽을 분리하면 사고를 잡는다.** 온톨로지가 후보를 만들지 않고 결과만 판정하므로, 코드와 선언이 어긋나면 데이터가 들어가지 않고 멈춘다
- **"생길 수 없는 오류"를 검사하는 이유는 데이터가 아니라 코드를 의심하기 위해서다.** 모르는 라벨은 버그 탐지기, 어휘·날짜·필수는 데이터 이상 탐지기다
- **설계도와 공사를 나누면 미리 보기 · 재현 확인 · 사후 검증이 전부 가능해진다.** 쓰기 코드는 판단하지 않아야 한다
- **"없어졌다"는 신호는 한 가지 뜻이 아니다.** 퇴사일 수도, 사이트 개편일 수도, 잘못 올린 글의 정정일 수도 있다. 한 규칙으로 처리하려 하면 반드시 틀린다
- **잘못 지우는 것이 안 지우는 것보다 비싸다.** 자동 판단은 상태 변경까지만, 실제 삭제는 정해진 계기에서만
- **삭제 기준은 "근거의 나이"가 아니라 "그 상태가 된 날"이다.** 전체 현황 출처는 근거가 계속 갱신되므로 나이로는 영원히 안 지워진다
- **관계에는 "지금 참"과 "한 번 참이면 영원히 참"이 섞여 있다.** 이 구분을 온톨로지에 적어 두면 적재기가 기계적으로 처리할 수 있다
- **비활성 표시는 삭제 정책이 아니다.** 유예 기간으로만 쓰고 기한이 지나면 반드시 지워야 쌓이지 않는다
- **이력은 그래프가 아니라 릴리즈 기록에 남긴다.** 그래프에 과거를 쌓으면 조회가 매번 걸러야 한다
- **보기 안에서만 답하는 모델은 온톨로지 기반 작업과 잘 맞는다.** 선택지를 온톨로지에서 만들면 모델이 선언 밖으로 나갈 수 없다
- **"해당 없음"이 많이 나오는 자리가 온톨로지를 늘려야 할 자리다.** 모델의 실패를 설계 신호로 쓸 수 있다
- **내 저장소 로컬 상태만 보고 "없다"고 답하면 틀린다.** 다른 사람이 같은 자리를 이미 만들어 뒀을 수 있다

## 한계

- **코드는 하나도 고치지 않았다.** 오늘 정한 삭제 정책은 전부 문서 단계다
- **상태 변경일 칸이 아직 없다.** 기한 기반 삭제는 이 칸이 생기기 전까지 불가능하다
- **정책 값 세 개가 비어 있다** — 유예 기간, 개인정보 보관 기간, 원본 보관 여부. 법무 · 회사 정책 확인이 필요하다
- **Jev 는 공개 자료로만 파악했다.** 한국어 성능, "해당 없음" 정확도, 사내 운영 가능 여부, 가격, 얼리 액세스 접근 가능 여부를 전혀 모른다. 성능 수치도 회사 발표다
- **명단은 개인정보라 외부 판단 API 로 보내는 것 자체가 검토 대상이다.** 머리행과 가린 샘플만 보내는 방식이어야 할 수 있다
- **온톨로지에 사업 → 팀 관계가 없다.** "어느 팀이 수행했나"는 아직 그래프에 없고, 과거 사실 관계 설계는 그 관계가 생길 때를 가정한 것이다
- **새 조회 API 의 실제 조회 시간을 재지 않았다.** 1만 개에서 1~2초라는 건 추정이다
- **API 상한 2,000의 의도를 만든 분에게 확인하지 않았다.** 풀기 전에 물어봐야 한다
- **운영 서버 조치는 아무것도 하지 않았다.** 이미지 태그 고정과 포트 제한은 인프라 담당자 일이다
