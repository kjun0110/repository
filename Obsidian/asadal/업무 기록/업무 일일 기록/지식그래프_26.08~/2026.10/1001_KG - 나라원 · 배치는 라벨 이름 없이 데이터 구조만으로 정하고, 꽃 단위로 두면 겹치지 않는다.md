## 개념

- **그래프 뷰어** — 관리자 화면(`admin/ai/`)의 읽기 전용 그래프 화면. `graph_viewer.htm` · `js/graph_viewer.js` · `css/graph_viewer.css` · `graph_viewer_api.php` 네 파일이고, **브라우저 → PHP → Neo4j** 세 단계로 파이썬을 거치지 않는다
- **꽃(폐포)** — 연결이 하나뿐인 잎 노드를 3개 이상 거느린 허브와 그 잎들. 팀과 직원, 회사와 연혁이 이에 해당한다. 배치의 단위를 노드가 아니라 이 꽃으로 바꾼 것이 이번 핵심이다
- **나무 가지** — 가지 안에서만 연결되고 밖으로 나가는 선이 거의 없는 묶음(부서 → 팀 → 직원). 물리 배치에 맡기지 않고 통째로 계산해 놓는다
- **공유 노드** — 한 단계 위 이웃이 둘 이상인 노드(두 사업분야에 걸친 사업 등). 두 부모 목표 위치의 중간을 목표로 삼는다
- **근접 중심성** — 다른 모든 노드까지의 평균 거리. 이 값이 가장 짧은 노드를 중앙에 둔다. 라벨 이름을 쓰지 않고 중심을 고르는 기준
- **`deptList.do`** — 수원시 챗봇 API. 담당업무 · 행정전화 · 부서명 · **부서 전체경로** 4칸을 준다

## 요약

그래프 뷰어 화면을 Neo4j 브라우저 수준으로 정돈했다. **임시 폴더의 복사본에서 끝까지 맞춘 뒤 마지막에 원본에 적용하고 운영 서버에 올렸다.**

API부터 다시 봤다. 처음에 30만 개 규모를 전제로 `search` · `expand` · `schema` 3~4개와 상한을 설계했는데, 사용자 지적대로 **지금 규모(노드 616 · 관계 797)에서는 전체를 한 번에 주고 그리는 쪽에서 조절하는 게 맞다.** 그리고 **PHP API 가 이미 전체를 주고 있었다.** 그래서 새 API 는 1만 개를 넘을 때로 미뤘다.

엉킴의 원인은 백엔드가 아니라 프론트였다. 배치(`cose`)와 **축소 상태에서 616개 이름과 797개 관계명을 전부 그리는 것**이 회색 노이즈를 만들고 있었다.

배치는 `fcose` → d3-force → 방사형 트리 → **꽃 단위 배치**로 열 번 넘게 고쳐 가며 맞췄다. 최종 규칙은 **라벨 이름 · 노드 이름 · 난수를 하나도 쓰지 않는다.** 중심은 근접 중심성으로 고르고, 가지는 같은 라벨끼리 묶어 하위 수로 정렬하고, 꽃은 부채꼴로 펼친다. 같은 데이터면 항상 같은 그림이 나온다.

성능도 쟀다. v21 은 616개에서도 배치에 3.4초, 9천 개에서는 8분이 넘어 중단됐다. 계산 방식만 고친 v22 는 **그림이 완전히 같으면서 1.2초 · 40초**다. 여기에 반복 횟수와 힘 적용 빈도를 조정하면 **1만 개가 13.6초**이고 품질은 떨어지지 않는다.

별도로 수원시 API 의 부서 경로만으로 조직도를 만들 수 있는지 재 봤다. **만들 수 있지만**(크롤링 940개 중 931개 일치) 조직 코드 · 시장 단계 · 부서 속성이 없어 크롤링을 대체하지 못한다.

## 1. 뷰어 구조와 보안

##### 구조
```
브라우저 (graph_viewer.js) → graph_viewer_api.php → Neo4j HTTP Query API
```
PHP 가 사이트 로그인 쿠키를 확인하고, Capture 를 뺀 노드와 관계를 한 번에 조회해 `{nodes, edges}` 로 내려준다. 파이썬 서버를 거치지 않아 **파이썬이 꺼져 있어도 동작한다.** 그리기는 **Cytoscape 3.30.4**(CDN)이고, 앞서 검토했던 sigma.js · graphology 는 쓰지 않는다(폴더 전체 검색으로 확인).

##### 눈여겨볼 것

| | 내용 |
|---|---|
| **Neo4j 관리자 계정 비밀번호가 PHP 에 평문** | 정상 동작 중에는 브라우저로 노출되지 않지만, PHP 가 실행되지 않는 설정 사고 · 백업 파일 · 복제본 · 공유로 한 번만 새면 피해가 크다. `accessMode: Read` 는 그 요청만 읽기이고 **계정 권한을 제한하지 않는다** |
| Neo4j 가 공개 도메인 · http | 방화벽이 없으면 비밀번호만으로 외부에서 붙을 수 있고, 인증 정보가 암호화되지 않은 채 오간다 |
| 조회에 LIMIT 없음 | 데이터가 늘면 PHP 25초 · JS 30초 타임아웃에 걸린다 |
| 쿠키 검사 | `unserialize` 결과에 `id` 가 있으면 로그인으로 본다. PHP 8 이면 객체 주입은 막히지만, **사이트가 쿠키에 서명하지 않는다면 위조 가능**하다. 쿠키를 만드는 파일은 이 폴더에 없어 확인하지 못했다 |

권하는 순서: ① 비밀번호 교체(이미 복제본과 대화에 노출) ② 읽기 전용 계정 분리 ③ 포트 접근 제한 ④ 비밀번호를 웹 루트 밖으로. ①③은 코드를 고치지 않고 할 수 있다.

## 2. API — 전체를 주는 게 맞았다

##### 처음 설계와 뒤집힌 지점
30만 개를 전제로 1단계(검색 + 펼치기)와 2단계(지도형)를 나누고, API 4개와 상한 · 커서를 설계했다. 사용자가 **"API 자체는 전체를 줘도 되는 거 아니냐"**, **"그릴 때 적당히 그리면 되는 거 아니냐"** 고 물었고, 따져 보니 맞다.

| 기준 | 전체 제공 | 나눠 제공 |
|---|---|---|
| 응답 · 로딩 | 1만 개면 압축 후 0.3~1MB, 0.5~1.5초(캐시 시 0.5초 미만) | 항상 가볍다 |
| 받은 뒤 검색 · 펼치기 | 서버 호출 없이 즉시 | 매번 호출 |
| DB 부하 | 호출마다 전체 조회 → **캐시 필수** | 작다 |
| 보안 | 한 번에 전부 가져갈 수 있다 | 범위가 작다 |

**지금 규모(616 · 797)에서는 전체 제공이 단순하고 맞다.** 엉킴은 그리는 양을 줄여서 해결하는 것이고, 전체를 받아 두는 것과 충돌하지 않는다. 그리고 확인해 보니 PHP API 가 이미 전체를 주고 있었다(`truncated: false`).

##### 그래서 보류한 것
새 파이썬 조회 API(`schema` · `search` · `expand`)와 풀텍스트 인덱스 · 허브 상한 · 속성 허용 목록 · 스키마 요약 화면은 **1만 개를 넘을 때** 다시 꺼낸다. 30만 개 규모의 2단계(서버에서 좌표 미리 계산 + 묶음 펼치기 + sigma.js)도 "전체 조망이 꼭 필요하다"가 확인되면 한다.

> 다만 이번에 만든 배치 규칙은 **서버 계산으로 그대로 옮길 수 있다.** 2단계로 가도 버려지지 않는다.

## 3. 엉킴의 원인

| | 내용 |
|---|---|
| 배치 | 기본 `cose` + `randomize: true`. 허브-잎 구조에서 꼬이고, 조회할 때마다 모양이 달라진다 |
| **글자** | **축소해도 이름 616개와 관계명 797개를 전부 그린다.** 읽을 수 없는 크기로 겹쳐 회색 노이즈가 된다. Neo4j 브라우저가 깔끔한 건 축소하면 색 점만 그리기 때문이다 |
| `nodeDimensionsIncludeLabels` | 글자 크기까지 노드 크기로 계산해 배치가 벌어진다 |
| 관계명 기본 켜짐 · 전체 곡선 | 줌·이동이 무거워진다 |
| 색 | 라벨을 이름순으로 정렬해 팔레트를 돌려 쓰면서 고정색과 겹쳤다. **사업 ↔ 조직이 둘 다 주황, 발주처 ↔ 직원이 둘 다 초록** |

##### 시험 데이터
`.env` 계정으로 운영 Neo4j 를 **읽기 전용 조회**해 임시 폴더에 받았다. 노드 616 · 관계 797 로 브라우저 화면과 일치한다. 5.9MB 인데 **임베딩을 빼면 0.79MB** 다(적재 단계에서 빼기로 한 그 값). 직원 전화번호가 들어 있어 임시 폴더에서만 쓰고 작업 후 폴더째 지운다.

## 4. 배치 — 열 번 넘게 고쳐 잡은 규칙

##### 경과

| 단계 | 결과 |
|---|---|
| `cose`(현재) | 배치 10.0초. 넓게 퍼지고 뭉친다 |
| `fcose` A(기존 보정 유지) / **B(고정값)** | 1.1초 / **1.0초.** 예상과 달리 **보정 없는 B 가 더 정돈됐다** — fcose 가 허브를 알아서 처리한다 |
| v2 축소 시 글자 숨김 | 회색 덩어리가 사라졌다. 체감 변화가 가장 컸다 |
| v4~v6b (d3-force) | 꽃잎이 바깥으로 뻗고, 뭉치 사이에 여백이 생겼다 |
| v7~v9 (방사형 트리) | 중심에서 가지별로 방향을 나눠 뻗게 했다 |
| v9e~v9q | 중심 자동 선택, 가지 정렬 규칙, 공유 노드 중간 배치, 고정 시드 |
| **v17 → v19** | 배치 단위를 **꽃**으로 바꾸고 나무 가지를 통째로 배치. **꽃을 가로지르는 선 11 → 0** |
| v20 | 회사 주변 부채꼴 · 잎 이름 자르기 → **사용자가 이전이 낫다고 해 폐기** |
| **v21** | 팀 꽃을 부채꼴로(상위 조직 반대쪽으로 펼침) |
| **v22** | 계산만 줄여 같은 그림에 3~6배 빠르게 |

##### 최종 규칙 (라벨 이름 없음)
1. **중앙** — 근접 중심성이 가장 높은 노드. 실측에서 ㈜나라원시스템(평균 2.49단계)이 자동 선택됐다. **연결 수 기준으로 고르면 사업분야 허브가 중앙에 와서 틀린다**
2. **가지** — 중앙에서 트리를 만들어 1단계 노드를 가지로 본다
3. **정렬** — 같은 라벨의 가지끼리 붙이고, 하위 노드가 많은 라벨 묶음부터, 같은 라벨 안에서는 작은 가지부터
4. **방향** — 가장 큰 묶음을 오른쪽에, 나머지는 반시계
5. **각도** — 가지마다 `√하위 수`, 잎 하나는 아주 작게
6. **꽃** — 잎 3개 이상인 허브는 꽃 크기의 원으로 취급해 **겹칠 수 없게** 하고, 잎은 물리 계산에서 빼고 둘레에 직접 놓는다. 선이 한두 개인 허브는 **부채꼴**(들어오는 쪽 약 110° 비움)
7. **나무 가지** — 밖으로 나가는 선이 가지 크기의 1/12 이하인 묶음은 중심 둘레에 직접 배치하고, 자식이 5개 이상이면 두 겹으로 엇갈려 바깥 꽃으로 가는 선이 안쪽 꽃 **사이 틈**을 지나게 한다
8. **공유 노드** — 두 부모의 중간을 목표로 하고 어느 뭉치에도 넣지 않는다
9. **마무리** — 위 위치를 목표로 물리 시뮬레이션으로 다듬는다

##### 하드코딩 점검
배치 · 색상 코드에 라벨 이름 · 관계 타입 이름 · 노드 이름 · `Math.random` 이 **하나도 없다**(파일 전체 검색). 라벨은 "같은 라벨인지"만 비교한다. 색도 라벨 이름 해시로 배정해 목록이 필요 없다. 트리 방문 순서를 연결 수 기준으로 정렬하고 난수를 고정 시드로 바꿔 **두 번 그려 좌표 합이 같은 것**을 확인했다.

원본에 남은 것은 **제목 속성 목록**(`name` → `title` → … → `description`)과 안내 문구의 "Capture" 뿐이고, 배치와 무관하다. 제목 규칙에 `description` 을 더해 연혁 27개가 `elementId` 대신 내용으로 보이게 했다.

## 5. 성능 — 그림을 바꾸지 않고 줄였다

실제 데이터를 복제해 5배(3,072) · 15배(9,212) 시험 데이터를 만들어 쟀다.

| 규모 | v21 | **v22** |
|---|---|---|
| 616 | 3.4초 | **1.2초** |
| 3,072 | 51초 | **8초** |
| 9,212 | 8분 넘어 중단 | **40초** |

v22 에서 고친 것은 **계산량뿐**이다 — 물리 힘 두 가지가 거의 모든 노드를 비교하던 것을 가까운 노드만 보게, 나무 가지 판별을 선 한 번 훑기로, 중심 탐색에서 잎 제외, 꽃의 줄 수 상한(40줄) 제거. 616개에서 지표와 좌표가 v21 과 같다.

##### 1만 개를 10초대로 — 안을 만들어 재 봄

| 조합 | 9,212개 총 시간 | 품질 |
|---|---|---|
| v22 | 40~46초 | 기준 |
| A 강하게(반복 수 반비례 감소) | 14.5초 | 교차 +11% |
| **A 약하게 + B** | **13.6초** | **교차 −5%**(기준보다 좋음) |
| A 강하게 + B | 10.3초 | 기준과 비슷 |

> **정정.** B 를 "비싼 힘을 후반 1/3 에만 적용"으로 제안했는데 틀렸다. 그 힘들은 후반으로 갈수록 약해지도록 돼 있어 효과가 없다. **"3번에 한 번만, 대신 3배 세게"**(총 힘은 같고 계산은 1/3)로 바꾸니 시간도 품질도 좋아졌다.

C(뼈대 먼저 배치하는 2단계)는 **필요 없다.** A+B 로 목표에 들었고 C 는 그림이 달라질 위험이 있다. 두 안 모두 **시뮬레이션 대상 1,000개 이하면 지금과 같은 계산**을 해서 현재 화면은 바뀌지 않는다. 추가 코드는 10줄 남짓이다.

##### 성능과 별개로 드러난 것
1만 개에서 전체 보기를 하면 그래프 폭이 약 26,000px 이라 **노드가 2px 도 안 돼 사실상 안 보인다.** 그 규모에서는 축소 시 최소 크기로 그리거나 묶어서 보여줘야 한다. 배치 속도와는 다른 문제다.

| `graph_viewer.htm` | d3 모듈 `<script>` 4줄 추가(ISC, 버전 고정). 실험용 fcose 3줄은 제거 |
| `css/graph_viewer.css` · `graph_viewer_api.php` | 변경 없음 |

순서대로 ① 조정값을 상수로 모으고 **d3 를 못 불러오면 기존 `cose` 로 그리는 대비책**을 넣고 ② 정리 전후 좌표가 같은지 확인한 뒤 ③ 원본에 적용하고 ④ **FTP 로 운영 서버에 올렸다.** 커밋은 하지 않았다(별도 저장소). 전화번호가 든 시험 데이터 폴더도 지웠다.

달라지는 동작은 다섯 가지다 — 배치, 색상 자동 배정, 제목에 `description`, 축소 시 글자 숨김, **항상 같은 배치**. 1만 개 대응(A+B)도 함께 들어가 있고, 1,000개 이하에서는 계산이 예전과 같아 현재 화면은 그대로다.

## 7. 곁가지 — 수원시 API 로 조직도를 만들 수 있나

`deptPathNm`(`수원시.권선구.종합민원과.가족관계등록팀`)을 점으로 자르고 **접두사마다 노드를 만들고 앞 접두사를 부모로** 걸면 조직도가 된다. 같은 이름이라도 경로가 다르면 다른 노드다(행정민원팀 44곳 · 맞춤형복지팀 28곳이 전부 구분됨).

```
경로 5,105 → 고유 938 → 노드 948 · 상하 946        크롤링 940 중 931 일치
레코드가 직접 가리킨 조직 938 · 접두사로만 생긴 조직 10
```

"수원시"만 있는 레코드는 0건인데 **접두사로 자동 생긴다.** 사용자 지적대로 이름 속 점 때문에 생긴 가짜 조직 4~5개는 **경로 끝을 `deptNm` 으로 되돌려 붙이면** 8건이 풀려 노드가 943개가 된다. 못 푼 2건은 경로와 부서명 표기가 다른 경우다(`제1부시장실` vs `제1부시장`).

업무는 조직 · 전화 · 담당업무 조합으로 **4,610개**(중복 495 제외)다. 전화 없음 425줄, 한 번호를 최대 26줄이 공유하고 이름 · 직위가 없어 **"직원"이 아니라 "업무 한 줄"** 로 봐야 한다.

| | API 만으로 |
|---|---|
| 조직 계층 · 담당업무 · 전화 | 된다 |
| 조직 코드 · 직위 · 부서 위치 · 팩스 · 시장 단계 | **없다** |
| 직원 0명인 조직 | 경로에 안 나온다 |

**크롤링을 유지하고 API 는 교차 확인용으로 둔다** — 9/22 결론과 같다.

## 재사용 가능한 판단

- **규모를 가정하고 설계하기 전에 지금 규모를 본다.** 30만 개 기준으로 API 를 네 개로 쪼갰는데, 현재는 616개이고 전체를 주는 쪽이 단순하고 빠르다
- **백엔드가 풀 문제와 프론트가 풀 문제를 가른다.** 엉킴은 양과 배치·글자 문제이고 API 구조로는 해결되지 않는다
- **체감을 가장 크게 바꾸는 것이 가장 사소할 수 있다.** 축소 시 글자 숨김 한 줄이 배치 알고리즘 교체보다 효과가 컸다
- **추측보다 그려 보고 고른다.** "허브가 있으니 보정 함수가 나을 것"이라는 예상이 실제 렌더링에서 뒤집혔다
- **배치 단위를 노드에서 꽃으로 올리면 겹침이 구조적으로 사라진다.** 잎까지 물리 힘에 맡기면 빈 공간으로 흘러들어 남의 선 위에 올라간다
- **라벨 이름을 쓰지 않으면 데이터가 바뀌어도 규칙이 산다.** 중심은 근접 중심성, 순서는 하위 개수, 색은 이름 해시로 정한다
- **"같은 데이터면 같은 그림"을 보증하면 비교와 검증이 가능해진다.** 난수와 조회 순서 의존을 없애는 것이 먼저다
- **성능 개선은 결과를 바꾸지 않는 것부터 한다.** 계산량만 줄인 v22 는 좌표가 동일하다
- **임시 폴더의 복사본으로 다 맞춘 뒤 마지막에 원본에 한 번 적용한다.** 되돌릴 일이 없고, 적용은 파일 교체 한 번으로 끝난다
- **경로 문자열은 식별자가 아니다.** 이름에 구분자가 들어가면 조용히 가짜 노드가 생긴다

## 한계

- **운영 화면을 내가 직접 보지는 못했다.** 로그인과 PHP 가 필요해 내 PC 에서는 띄울 수 없고, 올린 뒤 확인은 눈으로만 했다
- **CDN 에서 d3 를 받는다.** 막히면 기존 `cose` 로 떨어지게 해 뒀지만, 그때 화면은 예전 모양이 된다
- **1만 개 규모는 눈으로 확인하지 못했다.** 전체 보기에서 노드가 2px 미만이라 스크린샷이 빈 화면처럼 나온다
- **사업·발주처 덩어리는 여전히 빽빽하다.** 사업 208건이 사업분야 2곳에 함께 묶인 구조에서 나오고, 교차 대부분이 여기다
- **전화번호가 속성 패널에 그대로 나오고, PHP 에 관리자 계정이 들어 있다.** 이번 범위에 넣지 않았다
- **임베딩 때문에 응답이 5.9MB 다.** 적재 단계에서 빼기 전까지는 그대로다
- **미리보기 서버가 10분마다 꺼져** 확인이 자주 끊겼다. 직접 띄우는 명령으로 우회했다
- **수원 API 로 기존 그래프를 대체할 수 없다.** 조직 코드와 부서 속성이 없다
