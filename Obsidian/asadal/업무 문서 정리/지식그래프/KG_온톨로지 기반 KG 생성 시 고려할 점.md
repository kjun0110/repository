## 개념

- **선언** — 무엇이 존재하고(라벨), 어떤 속성을 갖고, 어떻게 관계되며, 어떤 제약을 따르는지 적은 파일. 온톨로지 본체다
- **동결본** — 선언을 검사한 뒤 구운 JSON. 런타임과 적재는 이것만 읽는다. 원본 선언의 형식은 "사람이 편집할 때의 경험" 문제일 뿐이다
- **배관 / 고유 정보** — 라벨 하나를 추가할 때 하는 일의 두 종류. 고유 정보("몇 번째 칸이 무슨 속성")는 줄일 수 없고, 배관(파일 열기 · 행 순회 · 정제 · 출처 붙이기)은 라벨마다 똑같다
- **골격(shape)** — "이 순서로 읽으면 된다" 의 이름표. 표 행 · h4 구역 · 평면 목록 · 본문 · 이름표-값 쌍. HTML 모양만 가리키고 내용은 모른다
- **대기열(staging)** — 검증을 통과하지 못했거나 사람 승인이 필요한 후보를 그래프 밖에 모아 두는 자리
- **조각(Chunk)** — 긴 본문을 단락 단위로 나눠 조각마다 벡터를 두는 노드

## 요약

나라원 사이트 온톨로지(라벨 9 · 관계 7 · 노드 372)를 설계하고 적재 파이프라인을 계획하면서, 네 가지 선택에서 판단이 여러 번 뒤집혔다. 뒤집힌 이유는 대부분 **비교에서 한 가지 방법을 빠뜨렸거나, 조건을 빼고 일반론으로 답했기 때문**이었다. 이 문서는 최종 판단과 함께 **어떤 조건에서 판단이 바뀌는지**를 남긴다.

```
온톨로지 선언      파이썬 — 단, 여러 사람이 직접 고치면 YAML + 편집기 스키마
추출 방식          테이블 주도 해석기(파이썬) — 구조화된 페이지 기준
적재 파이프라인    규칙이 뼈대, LLM 은 제안만 — 승인된 것만 다음 릴리즈로
임베딩             기존 라벨에 칸 둘 — 조각 노드는 긴 본문이 많아질 때
```

## 1. 온톨로지 선언 — YAML 방식과 파이썬 방식

##### 먼저 — 무엇을 비교하나

선언 파일은 **라벨 → 속성 → 속성 규칙**으로 깊게 중첩되고, 라벨·속성마다 근거 설명이 길다. 모양은 `pydantic` 모델이 강제하고, 런타임은 구운 JSON 만 읽는다.

##### 비교

| | 파이썬 | YAML + 편집기 스키마 | TOML | JSON |
|---|---|---|---|---|
| 깊은 중첩 | 보통 | **좋음** | **나쁨** — 인라인 표는 한 줄, 중첩마다 긴 헤더 | 좋음 |
| 설명 · 주석 | 가능 | **가능** (블록 문자열) | 가능 | **불가** |
| 순수 데이터 보장 | **사람이 지켜야 함** | 형식이 막아 줌 | 형식이 막아 줌 | 형식이 막아 줌 |
| 편집 중 오타 검출 | 편집기가 기본으로 | **스키마를 연결하면** | 스키마를 연결하면 | 스키마를 연결하면 |
| 타입 함정 | 없음 | `no` → 거짓, `1.0` → 실수 | 거의 없음 | 없음 |
| 의존성 | 없음 | PyYAML | 없음 (3.11+ 표준) | 없음 |

##### 편집기 스키마

`pydantic` 모델에서 JSON Schema 를 뽑아(`model_json_schema()`) 편집기(VS Code YAML 확장 등)에 연결하면, YAML 을 고치는 **도중에** 빨간 줄과 자동완성이 뜬다.

```yaml
# yaml-language-server: $schema=./ontology.schema.json
nodes:
  Company:
    kye: company_id        ← "허용되지 않는 칸"
    cardinality: N:1       ← "one_to_one · one_to_many … 중 하나"
```

**판단이 한 번 뒤집힌 지점이 여기다.** 처음에 파이썬을 고른 결정적 이유가 "오타를 타이핑하는 순간 잡는다" 였는데, YAML 도 스키마를 연결하면 같다는 것을 비교에서 빠뜨렸다.

##### YAML 의 타입 함정은 선언 파일에서는 조용히 틀리지 않는다

`no` 가 거짓으로, `1.0` 이 실수로 바뀌어도 **모델이 문자열 칸에서 거부해 빌드가 멈춘다.** 반면 사람 결정 파일처럼 값을 느슨하게 받는 파일은 조용히 틀린다 — 인사 명단의 "팀 없음" 표기가 실제로 `no` 였다.

##### 결론 — 누가 선언을 고치느냐로 정한다

```
차이는 "틀린 걸 고치는 도중에 아느냐, 빌드를 돌려서 아느냐" 하나뿐이다
어느 쪽이든 빌드와 확인 스크립트가 틀린 선언은 막는다
```

| 선언을 고치는 방식 | 선택 |
|---|---|
| 스크립트로 고치고 곧바로 빌드 · 확인 | **파이썬** — 편집 중 검사의 이득이 거의 없고, 설정도 필요 없음 |
| 여러 사람이 파일을 직접 열어 자주 고침 | **YAML + 편집기 스키마** — 설명이 많은 선언을 읽고 고치기 쉽고 로직이 끼어들 수 없음 |

**파이썬을 고르면 "선언에는 로직을 쓰지 않는다"(전개 · 함수 호출 · 반복문 금지)를 파일 머리에 명시한다.** 옮기는 것은 기계 변환이고, 구운 바이트가 같은지로 증명할 수 있어 나중에 바꾸는 비용이 작다.

##### 사람 결정 파일은 선언 파일과 따로 고른다

잘린 기관명 확정, 동률 판정처럼 **인스턴스에 대한 사람의 판단**을 담는 파일이다.

```
사람이 처음부터 적는 소수 결정 + 근거     TOML   의존성 없음 · 문자열 따옴표 필수라 타입 함정 없음
기계가 후보를 뽑고 사람이 칸만 채우는 표   CSV    표준 라이브러리로 읽고 쓰기 · 엑셀로 편집
파이썬은 쓰지 않음                        승인이 코드 변경이 되어버린다
```

**쓰는 코드가 생기기 전에 파서 의존성(PyYAML 등)을 넣지 않는다.**

## 2. 추출 방식 — 파서 파일과 해석기

##### 세 가지

| | 방식 | 모양 |
|---|---|---|
| A | 파서 파일 | 페이지마다 파이썬 파일 하나에 읽는 절차를 전부 씀 |
| A' | **테이블 주도 해석기 (파이썬)** | 추출 규칙을 파이썬 표로 적고 해석기 하나가 돎 |
| B | 선언 해석기 (YAML) | 규칙을 YAML 로 적고 해석기가 읽음 (nara1graph 방식) |

##### 같은 골격이면 11단계 중 10단계가 같다

공지사항 표 `[No, 제목, 등록일]` 과 사업 게시판 표 `[No, 사업명, 계약일, 발주처]` 는 내용이 전혀 다르지만 읽는 절차가 같다.

```
 1. 파일 찾기   2. <table> 찾기   3. <tr> 순회   4. 머리글·빈 행 거르기   5. <td> 배열
 6. 칸 번호 → 이름            ← 여기만 다르다
 7. 정제   8. 형변환   9. 묶기   10. 출처 3칸   11. 레코드 만들기
```

배관(1~5 · 7~11)을 몇 단계까지 공유하느냐가 방식의 차이다. **배관을 끝까지 뽑아내면 그게 해석기다.**

##### 라벨이 늘수록 해석기가 유리한 기전

```
         첫 번째 라벨   같은 골격 두 번째부터
A 파서       42줄          42줄      ← 파일 · 함수 · 등록이 매번 반복
B YAML       55줄           5줄      ← 첫 골격에서 실행기를 만들고 이후 급락
```

nara1graph 실측 — `board.cause04` 26줄(table-rows 첫 사용) → `board.notice` 5줄(재사용), `highlight` 20줄 → `board.companyphoto` 5줄. **가장 싼 두 추출기가 정확히 기존 골격을 재사용한 둘이다.**

##### 그런데 새 골격이 나오면 양쪽 다 코드를 쓴다

nara1graph 의 shape 10종 중 **7종이 딱 한 번씩만 쓰였다.** 추출기 14개 중 절반은 골격을 새로 발명했고, 그때마다 실행기와 `elif` 가지가 붙었다. "라벨이 늘면 YAML 만 늘고 코드는 그대로" 는 **골격이 포화된 뒤에만** 참이다.

##### YAML 해석기의 비용은 대부분 "YAML 은 함수를 담을 수 없다" 에서 나온다

```
CLEANERS 레지스트리      "nbsp_strip" 글자 → 함수
transforms 레지스트리    "normalize_org_name" 글자 → 함수
shape → run_* elif 사슬  "table-rows" 글자 → 함수
metaschema.py 294줄      키 오타 검사기
```

파이썬 표면 함수를 직접 넣으니 전부 사라진다.

```python
"notice": Extract(
    shape=parse_table_rows,                       # 함수 그 자체
    keep=lambda r: r[0].strip().isdigit(),        # 문법 설계 없음
    fields={"title": Field(1, (nbsp_strip, collapse_ws, strip))},
    label="Notice"),
```

##### 시제품으로 확인한 것

```
해석기             38줄로 라벨 3종 · 골격 2종 처리 (YAML 판 약 500줄)
가장 어려운 연혁    한 페이지에 구조가 둘 — 훅 7줄로 27건(자사 8 · 이전 19) 정확히 일치
</tr> 누락 버그     게시판이 <tr> 14 : </tr> 2. 골격 함수 한 곳 수정으로 사업 게시판 · 공지 동시 해결
```

마지막 줄이 배관 공유의 값어치를 추측이 아니라 **실제로 일어난 일**로 보여 줬다. 파서 파일이었으면 두 곳에 같은 처리가 있었다.

##### 결론

| 조건 | 선택 |
|---|---|
| 구조화된 페이지, 규칙에 로직(훅)이 필요 | **A' 테이블 주도 (파이썬)** |
| 훅이 30줄을 넘는 블록이 여럿 | 그 블록만 **A 파서 파일**로 뺌 — 파이썬이라 섞어 쓸 수 있음 |
| 규칙을 개발자가 아닌 사람이 코드 배포 없이 고쳐야 함 | B — 그 이점이 필요할 때만 |

**셀렉터 문자열만 모은 파일은 만들지 않는다.** 표준 `html.parser` 상태 기계에서 사이트에 묶인 것은 문자열 한 줄이고, 개편 때 고칠 것은 문자열이 아니라 진입 조건이다.

## 3. 적재 파이프라인 — 규칙 기반 + LLM 사용법

##### 두 방식의 차이는 "후보를 누가 만드나" 하나다

```
              후보 만들기                 검증             결과
규칙 기반      파서가 칸에서 뽑음        →  온톨로지 검사  →  통과하면 릴리즈로 적재
LLM 기반      LLM 이 원문+온톨로지 보고  →  온톨로지 검사  →  통과하면 적재 / 실패하면 대기열
```

##### 구조화된 원천에는 규칙이 맞다

- **원문이 이미 칸으로 나뉘어 있다** — 게시판 표, 조직도 트리, 연혁 한 줄씩. LLM 이 해석할 여지가 없다
- **건수가 많으면 작은 오류율도 여러 건이다** — 208건에서 1% 면 2건. 규칙은 전부 맞거나 같은 방식으로 틀려서 금방 드러난다
- **LLM 은 도와주려고 채워 넣는다** — 화면에서 잘린 기관명 `과학기술정보통신부 ..` 을 그럴듯하게 복원한다. 없는 정보를 추정하지 않는다는 원칙과 부딪힌다
- **재현성** — 같은 스냅샷에서 같은 그래프가 나와야 바이트 게이트 · manifest 체인 · 적재 후 대조가 성립한다

##### 검증은 모양을 볼 뿐 사실을 보지 않는다

```
LLM 이 지어낸 값  "발주처: 서울특별시교육청"   → 어휘 · 타입 전부 맞음 → 검증 통과
```

그래서 **"조건 충족 시 자동 적재" 는 LLM 후보에 쓰면 위험하다.**

##### 최종 구조 — 규칙이 뼈대, LLM 은 제안만

```
원천 ──► 규칙 파서 ──► 확정된 후보 ──► 검증 ──► 릴리즈 ──► 그래프
              │
              ├─ 규칙이 뽑았지만 확정 못 한 것 ─┐
              │                              ├─► LLM 제안 ──► 대기열 ──► 사람 승인 ──► 다음 릴리즈
원천 ──► 규칙이 못 닿는 내용 ───────────────────┘
```

**LLM 은 그래프에 직접 쓰지 않는다.** 승인된 것만 다음 릴리즈에 들어가므로 릴리즈 체인과 대조가 그대로 유지된다.

| LLM 이 맡는 자리 | 예 |
|---|---|
| 규칙이 뽑았지만 확정 못 한 것 | 잘린 기관명 후보 · 기관유형 동률 판정 · 조직도에 없는 팀명 · 입사일 정정 여부 |
| 규칙이 못 닿는 내용 | 서술 본문 속 기능 · 게시판 본문 · 공지 · PDF |
| 사이트 개편 | 드리프트(건수 급감)가 감지되면 새 셀렉터 · 매핑 제안 → 개발자 반영 |

| LLM 이 하지 않는 것 |
|---|
| 규칙이 이미 확정적으로 뽑는 값을 대신 뽑기 |
| 검증에 실패한 레코드를 자동으로 고쳐 넣기 |
| 승인 없이 그래프에 쓰기 |
| 원문에 없는 값 채우기 — **제안에는 원문 인용이 붙고, 원문에 없으면 제안도 버린다** |

##### 나중에 LLM 을 붙이려면 규칙 파이프라인에 미리 넣을 것

| 필요한 것 | 이유 |
|---|---|
| **레코드 단위 대기열** | 후보 하나만 틀려도 배치 전체를 거부하면, 납품 후 사이트가 한 줄 바뀌어도 적재가 멈춘다. 틀린 후보만 빼고 리포트 — 단 추출기별 거부율이 기준을 넘으면 전체 거부 |
| **추출 방법 표시** (`rule` · `llm`) | 서빙이 LLM 추출값을 구분할 수 있게 |
| **LLM 결과 캐시** (모델 · 프롬프트 버전 · 원문 sha) | 같은 릴리즈가 다시 나오게 |

##### 순서 — 규칙이 먼저

규칙으로 만든 그래프가 **LLM 추출 정확도를 재는 정답지**가 된다. 같은 페이지에서 LLM 이 뽑은 결과를 규칙 결과와 대조하면 오류율이 숫자로 나온다.

##### 삭제(D)는 미뤄도 되지만, 수정(U)은 먼저 손본다

- 적재 후 대조가 DB 전체를 읽으므로, 삭제가 필요한 상황이 오면 **잘못 들어가지 않고 적재가 거부된다**
- 그러나 속성을 통째로 교체하면 **사람이 확정한 값이 다음 적재에서 원문값으로 되돌아간다** — 후보 생성 단계에 사람 결정 우선 규칙이 필요하다
- 사라진 것이 ① 진짜 없어졌나 ② 크롤이 못 받았나 ③ 파서가 놓쳤나를 구분해야 삭제할 수 있다 — 스냅샷이 그 페이지를 실제로 받았을 때만 삭제 후보로 본다

## 3-1. 원천을 LLM 에 주고 칸을 채우게 하면 안 되나 — 멱등성

##### 먼저 — 무엇을 묻나

온톨로지와 페이지를 LLM 에 주고 값을 채우게 한 뒤 검토해서 넣는 방식은 **범용성은 더 높다.** 새 사이트 · 새 페이지 모양이 나와도 코드를 쓰지 않는다. 그래도 반복 크롤링하는 구조화 원천에는 규칙을 쓴다.

```
적재(MERGE)는 멱등이다      같은 후보를 두 번 넣어도 그래프가 같다
추출은 결정적이어야 한다    같은 원문에서 매번 다른 후보가 나오면 재적재가 멱등이 아니다
```

##### 비교

| | 규칙 | LLM 채우기 + 검토 |
|---|---|---|
| 같은 원문 → 같은 결과 | **예** | 아니오 — "아사프로 CMS" / "아사프로CMS", 설명 문장이 매번 다름 |
| 검토 | 규칙을 **한 번** | 적재할 **때마다** — 게시판 3,018행의 변경점 대부분이 사이트 변경이 아니라 LLM 편차 |
| 변경점의 뜻 | 결과가 달라지면 **사이트가 바뀐 것** | 사이트 변경과 LLM 편차가 섞임 |
| 틀리는 방식 | 이상한 구조에서 멈추거나 빈칸 — **드러난다** | 그럴듯하게 채움 — **숨는다** |
| 빠짐없음 | 행 수를 센다 | 긴 표에서 행을 건너뛰거나 합침. 세려면 결국 파서가 필요 |
| 키 | 코드로 고정 | 이름 표기가 흔들리면 같은 대상이 다른 노드로 MERGE |

##### 실제 사례 — 의정정보화 솔루션

"첫 문단 = 설명" 규칙이 17쪽(보유기술 12 · 사업분야 4 · 회사개요 1) 중 `/art/solution/index.htm` 한 곳에서만 틀렸다. 첫 문단이 솔루션 전체가 아니라 하위 제품의 개요였다.

```
의정정보화 솔루션        ← 페이지 제목 (h3-tit)
  의정자료유통시스템     ← 하위 제품 (h3)
    개요: "의정활동에 필요한 의원요구자료…"   ← 첫 문단
  의정포털시스템 …
```

- 규칙을 **"첫 문단보다 하위 h3 가 먼저 나오면 설명을 비운다"** 로 좁혀 17/17 — 틀려도 빈칸 쪽으로 틀린다
- 처음 제안한 "첫 h4 보다 앞의 문단" 은 아사프로 CMS · 사업분야 홈페이지에서 진짜 소개를 지웠다 — **규칙은 문제 페이지 하나가 아니라 같은 골격의 전체 페이지로 검사한다**
- LLM 이었다면 그럴듯한 설명을 채웠을 가능성이 크고, 맞았는지 알려면 사람이 원문을 다시 봐야 한다

##### "페이지마다 규칙" 은 생각보다 적다

규칙은 페이지가 아니라 **골격마다** 하나다 — 골격 5개로 약 300쪽, 게시판 268쪽은 규칙 하나. 페이지별로 남는 것은 slug 대응표 같은 **"이 대상을 어떤 키로 부를지" 의 결정**인데, LLM 방식에서도 누군가 해야 하고 프롬프트 안에 숨을 뿐이다.

대응표는 조용히 빠지는 곳을 만들지 않게 둔다 — 읽는 범위는 넓게(`/art/` 전체), 제외는 명시 목록으로, 둘 다에 없는 페이지가 나오면 멈춘다.

##### 원천 성격으로 고른다

| 원천 | 선택 |
|---|---|
| 템플릿이 적고 반복 크롤링 (홈페이지 · 인사 DB) | **규칙** |
| 모양이 제각각 (제안서 · PDF · 외부 기관 사이트 여러 곳) | **LLM 추출 → 대기열 → 승인** |
| 문장 속 관계 · 비어 있는 설명 | **LLM 제안** |
| 한 번 넣고 끝나는 원천 | LLM — 재적재가 없어 편차 비용이 없다 |

"온톨로지 기반" 은 LLM 을 뜻하지 않는다. 온톨로지는 **채울 칸의 정의**이고, 규칙과 LLM 은 둘 다 그 칸을 채우는 수단이다. 레코드 칸 이름을 선언의 속성 이름에 맞춰 두면 나중에 LLM 추출기를 붙여도 같은 칸으로 들어간다.

##### 원문 칸과 LLM 파생 칸을 나눈다

| 칸 | 채우는 것 | LLM |
|---|---|---|
| `body_text` | 원문 본문 그대로 (버튼 · 탭 글자 포함) | 덮어쓰지 않고 지우지 않는다 — 요약에서 빠진 내용은 되살릴 수 없다 |
| `description` | 원문 첫 문단. 없으면 빈칸 | 빈칸만 **제안 → 승인**, 추출 방법 `llm` 표시 |
| `embedding_text` | 검색용 요약 또는 이름 + 설명 + 본문 조합 | 요약 가능 — **찾는 데만 쓰고 답변 근거로는 원문을 보여 준다**. 원본 sha 를 같이 적어 본문이 바뀐 노드만 다시 만든다 |

body_text 를 지우고 LLM 요약으로 description 만 남기는 안은 쓰지 않는다 — "주요기능이 뭐야" 같은 질문의 근거가 본문에만 있고, 요약이 틀려도 대조할 원문이 사라진다. 본문은 12개를 합쳐도 2만 자가 안 돼 지워서 얻는 것이 없다.

##### 섞어 쓰는 자리

- **LLM 이 규칙 초안을 쓴다** — 사람은 코드를 한 번 검토한다. 새 골격을 만드는 비용이 준다
- **LLM 추출을 교차검증에 쓴다** — 규칙 결과와 다른 곳만 사람이 본다. 의정정보화 같은 사례를 자동으로 찾는다
- **LLM 결과를 캐시한다** (모델 · 프롬프트 버전 · 원문 sha) — LLM 을 쓰더라도 같은 원문이면 같은 후보가 나오게 해서 멱등성을 되찾는다

##### 정리

- **재적재가 멱등이려면 추출이 결정적이어야 한다.** MERGE 가 멱등이어도 같은 원문에서 다른 후보가 나오면 진짜 변경이 편차에 묻힌다 — 반복 크롤링 원천은 규칙, 한 번 넣는 비정형 원천은 LLM
- **규칙은 문제 페이지 하나가 아니라 같은 골격의 전체 페이지로 검사한다.** 한 곳을 고친 규칙이 다른 두 곳의 진짜 값을 지웠다
- **원문 칸은 LLM 이 덮어쓰지 않는다.** LLM 결과는 빈칸 제안이나 검색용 파생 칸(`embedding_text`)에만 둔다

## 4. 임베딩 — 조각(Chunk) 노드를 쓸 것인가

##### 먼저 — 그래프 RAG 에 임베딩이 필수는 아니다

nara1graph 는 같은 사이트에서 임베딩을 끄고 `Text2Cypher → 본문 통째 주입 → 임베딩` 순으로 두었다. 전체 텍스트가 약 52,000자라 검색 단계가 오차만 늘린다는 판단이었다. 우리 텍스트는 약 2만 8천 자다.

그래프 RAG 의 핵심은 **그래프를 따라가는 조회**다. 임베딩은 "뜻으로 찾는 질문" 을 맡는 한 경로다.

##### 벡터를 그래프에 저장하면 선언에 있어야 한다

같은 사실을 네 곳이 알아야 한다 — 적재(무엇을 임베딩하나) · DDL(벡터 인덱스) · 검색(어느 인덱스) · Text2Cypher(스키마). 벡터 인덱스는 `indexed` 처럼 DDL 로 실제로 생기는 인덱스라 같은 부류다.

| 선언 (무엇이 있나) | 적재 설정 (어떻게 만드나) |
|---|---|
| 임베딩하는 라벨 · 텍스트 칸 · 벡터 칸 · **차원** · 유사도 | 모델 이름 · 요약문 틀 · 호출 설정 |

차원이 바뀌면 인덱스를 새로 만들고 전부 다시 계산해야 하므로 선언에 둔다.

##### 어떤 노드를 임베딩하나 — 뜻으로 찾는 서술만

| 기준 | 질문 |
|---|---|
| 서술 | 의미를 담은 문장이 있나 |
| 의미 질문 | 정확한 이름 · 값을 모른 채 뜻으로 묻나 |
| 정확 조회로 안 풀리나 | Cypher · 동의어 · 전문 검색으로 더 정확히 풀리면 임베딩은 오답 원인 |
| 해가 없나 | 개인정보가 섞이거나 비슷한 이름끼리 헷갈리지 않나 |

| 임베딩 | 라벨 | 텍스트 |
|---|---|---|
| O | 보유기술 · 사업분야 | 이름 + 설명 + 본문 |
| O | 사업실적 | **요약문** — 사업명 + 연도 + 발주처 + 유형 + 분야 (이름만 넣으면 발주처가 벡터에 없다) |
| 선택 | 연혁 | 연월 + 설명 |
| X | 회사 | 자본금 · 대표자는 칸에 있다. 임베딩 경로가 "자본금 확인되지 않습니다" 오답을 냈다 |
| X | 조직 · 사무소 | 서술이 없다 |
| X | **발주처(기관)** | 비슷한 이름끼리 벡터가 가깝다 — 실측 **성동구 · 성북구 0.89** |
| X | **직원** | 구조화 칸 + 유사도 검색에 개인정보가 딸려 나올 수 있다 |

##### 조각 노드는 지금 필요 없다 — 기준은 노드 수가 아니라 긴 본문의 양

Neo4j 벡터 인덱스는 **노드 하나에 벡터 하나**다. 긴 본문을 조각마다 벡터로 두려면 조각마다 노드가 필요해 `Chunk` 가 생긴다.

그러나 서술 본문이 있는 노드가 16개(최장 약 7천 자)뿐이고, 검색이 할 일은 **어느 문서인지 찾는 것**이다. 찾은 뒤 본문을 통째로 답에 넣으면 되므로 단락을 골라낼 필요가 없다.

| 경우 | 예 | 조각 노드 |
|---|---|---|
| 짧은 노드가 많음 | 사업실적 208 · 직원 212 | 불필요 — 노드 하나가 이미 조각 하나 크기 |
| 긴 문서가 적음 | 보유기술 12 · 사업분야 4 | 불필요 |
| 긴 문서가 많음 | 게시판 본문 수백 건 · 첨부 PDF | 유리 |

##### 조각 노드가 필요해지는 때

```
① 본문이 모델 입력 한도를 넘는 문서가 많아짐     뒷부분이 벡터에서 사라짐
② 문서가 커서 통째로 넣을 수 없음               단락을 골라야 하고, 단락마다 벡터 · 노드가 필요
③ 문서 수가 늘어 통째 주입 비용이 커짐           관련 단락만 넣어 줄임
```

긴 문서가 많아지면 문서당 벡터 하나는 여러 주제의 평균이라, 후보가 수백 개일 때 그 주제를 짧게 다룬 다른 문서가 앞질러 올라온다.

**비용도 따라온다** — 노드 · 관계가 늘고, 소제목이 추가 · 삭제되면 조각이 생기고 사라져 **삭제(D) 구현이 필요**하며, 구조가 바뀌면 조각 벡터를 다시 계산한다.

##### 조각을 만든다면 — 규칙

```
자르는 경계     소제목(h3 · h4) — 의미 단위를 먼저 따른다
합치는 것       같은 부모 소제목 아래의 작은 섹션 · 본문 0자인 소제목 + 그 아래 섹션
합치지 않는 것   다른 문서끼리 · 부모 소제목이 다른 섹션끼리
쪼개는 것       크기 상한을 넘는 섹션만, 문단 단위로. 표는 자르지 않는다
머리말          "[보유기술 > AI 채팅 > 고급 기능 > 검색범위 설정]" + 본문  ← 없으면 무엇에 관한 조각인지 사라진다
키             sha256(부모 키 | 섹션 경로) — 본문 해시로 만들면 문구 수정마다 새 노드가 생긴다
```

실측 — 보유기술 "AI 채팅" 은 소제목 기준 섹션 15개(6,727자)가 규칙대로 합치면 **조각 7개**가 된다.

##### 이렇게 두면 모든 내용을 가져올 수 있나

**닿을 수는 있지만 한 번에 전부 가져오지는 않는다.**

```
목록 · 개수 · 조건    "몇 건" · "전부" · "2023년"       → Text2Cypher (전수)
설명 · 가능 여부      "챗봇 돼?" · "어떤 기능"           → 벡터 상위 k + 부모 · 관계 확장
이름                 "서울시교육청 사업"                → 전문 검색 → Cypher
```

벡터 검색은 상위 몇 개만 돌려주므로 "전부 · 몇 건" 질문은 풀 수 없다. 못 가져오는 것은 그래프에 없는 내용(이미지로만 있는 인증서 · 매출 차트 · 고객 로고)뿐이고, 그것은 검색이 아니라 적재 범위의 문제다.

##### 릴리즈 체인과 맞추기

- 벡터는 **릴리즈 그래프 안에서 같이** 들어가야 한다. 적재 뒤에 노드에 따로 쓰면 다음 릴리즈가 "DB 가 예상과 다름" 으로 거부된다
- (모델, sha256(임베딩 텍스트)) → 벡터 **캐시**로 같은 릴리즈가 다시 나오게 한다. 텍스트가 바뀐 노드만 새로 계산한다
- 모델 이름은 노드마다가 아니라 릴리즈 마커 한 곳에

## 재사용 가능한 판단

- **비교표에 방법이 빠지면 결론이 뒤집힌다.** 선언 형식에서 "편집기 스키마" 를, 추출 방식에서 "파이썬 테이블" 을 빠뜨려 두 번 번복했다. 추천 전에 중간 선택지부터 찾는다
- **"라벨이 늘면 유리하다" 는 회수 구간을 세어야 한다.** 해석기의 이득은 골격이 포화된 뒤에만 나온다 — 실측 shape 10종 중 7종이 한 번만 쓰였다
- **매체의 장점과 모델의 장점을 가른다.** 선언에 설명 · 예시를 적을 수 있었던 건 YAML 덕이 아니라 모델에 그 칸이 있어서였다
- **버그가 한 곳에서 고쳐지는지가 공유 구조의 값어치다**
- **검증은 모양을 보고 사실을 보지 않는다.** LLM 후보는 검증 통과만으로 적재하지 않는다
- **LLM 은 제안하고 사람이 승인한다.** 제안에는 원문 인용을 붙이고, 원문에 없으면 버린다
- **규칙 결과가 LLM 의 정답지다.** 규칙 파이프라인을 먼저 세운다
- **조각 노드의 기준은 노드 수가 아니라 긴 본문의 양이다**
- **벡터 검색은 "전부" 를 가져오지 않는다.** 목록 · 개수는 Text2Cypher 가 맡는다
- **쓰는 코드가 생기기 전에 의존성을 넣지 않는다**
- **데이터를 보기 전에 어휘를 박지 않는다.** 직급 · 직책 예시 값이 실제 명단과 달랐다('사원' 이 아니라 '일반직원', 대표이사는 직책이 아니라 직급)

## 한계

- **추출 방식 비교의 줄 수는 추정이 섞여 있다.** 해석기 38줄 · 훅 7줄은 시제품 실측이고, 라벨 20 · 30종일 때의 총량은 계산이다
- **LLM 제안 흐름은 설계만 있다.** 근거 대조 방식 · 대기열 저장 위치 · 승인 화면은 정해지지 않았다
- **임베딩 모델이 정해지지 않았다.** 차원과 입력 한도가 모델에 달려 있어 긴 본문이 잘리는지 아직 모른다
- **nara1graph 대조는 한 구현과의 비교다.** shape 재사용률 · 기관명 유사도 0.89 는 그 구현의 데이터에서 나온 값이다
