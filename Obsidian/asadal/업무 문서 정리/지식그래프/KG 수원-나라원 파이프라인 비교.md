## 개념

- **온톨로지 구동(ontology-driven)** — 선언이 파싱·검증·적재·추론·라우팅을 *만든다*. 선언 한 줄을 고치면 코드를 안 건드려도 검사 수·제약 수·질의 모양이 바뀐다
- **온톨로지 추론(ontology-reasoning)** — 규칙을 고정점까지 스스로 적용하는 엔진. OWL 추론기가 하는 일. **둘 다 아니다**
- **규칙 적용기** — 선언한 규칙을 한 바퀴 돌리는 것. 두 프로젝트가 지금 하는 것
- **물질화(materialize)** — 파생 사실을 간선으로 저장할지, 질의 때 풀지
- **조용한 실패** — 실패했는데 결과가 멀쩡해 보이는 것. 검증기가 못 잡는다

---

## 요약

두 프로젝트가 **같은 철학, 다른 구조**로 수렴했다.

철학은 같다 — 선언이 구동하고, 사람 결정에 승인이 붙고, 파생 간선에 출처가 있고, 어긋나면 멈춘다.

구조는 다르다 — 나라원은 **단계마다 파일이 남는** 8단계, 수원은 **DB로 곧장 흐르는** 33단계다. 나라원은 *단계 격리*를 샀고 수원은 *배치 일관성*을 샀다.

그리고 **서로 다른 것을 검증했다.** 나라원은 규칙 종류를 넓게(집계·포섭·연쇄) 갖췄지만 계층이 한 단계뿐이라 가변 깊이를 시험할 데이터가 없다. 수원은 종류가 하나(연쇄)뿐이지만 `PART_OF` 938개 위에서 가변 깊이·정지 조건·동점 처리를 실제로 돌린다.

## 1. 파이프라인 단계

```
나라원   crawler → parse → resolve → infer → validate → embed → load → serve
            ↓        ↓        ↓        ↓
        nara1data/ graph/ resolved/ inferred/        단계마다 파일이 남는다

수원     scraping → [순서·코드 검사] → schema → nodes → relationships → infer
                  → [요건·스키마 검사] → lifecycle → embedding → [품질 게이트] → serve
            ↓                                     ↓
        data/raw/                              Neo4j 에 바로 쓴다
```

##### 중간 산출물 — 수원엔 없다

수원의 설계 결정이다. `main.py` docstring 에 이유가 적혀 있다.

> 한 프로세스 안에서 실행되므로 `BATCH_ID` 가 전 단계에 걸쳐 동일하게 유지된다. 스크립트를 따로 돌리면 `lifecycle` 이 "오늘 이 스크립트를 안 돌린 노드"를 전부 폐지 처리해버린다 — 실제로 겪었다.

```
나라원이 산 것   단계 격리 · "적재만 다시" 가능 · 중간 상태를 따로 검사
수원이 산 것     배치 일관성 · MERGE 멱등 · 한 번에 전부
```

지금 수원은 전체가 20분이라 안 아프다. 데이터가 10배가 되면 아파진다.

##### `resolve` 단계 — 수원엔 없다

```
나라원   parse → [resolve: 결정 덧씌우기] → infer      결정 적용이 별도 단계
수원     결정이 14개 파일에서 필요할 때 읽힌다          nodes/09 · ontology/classify · search/steps/structure …
```

나라원은 "결정을 조용히 건너뛰면 사람은 병합된 줄 알고 그래프는 멀쩡하니 검증기도 못 잡는다"를 **입력 검사**로 막는다.
수원은 같은 문제를 **`validate/06` 의 결정 대상 존재 검사**로 막는다 — 대상이 그래프에 없으면 "조용히 아무 일도 안 한다"고 알린다.

##### `stage: source / invariant` — 수원엔 없다

나라원은 계약을 둘로 가른다. 실측치(사이트를 센 값)는 결정을 반영하면 달라지는 게 정상이라, 섞으면 결정 이후를 검사할 수 없다.

**수원엔 그 구분이 없다. 필요가 없어서다** — `resolve` 단계가 없으니 "결정 전후"라는 것이 없다.

| 항목 | 나라원 | 수원 |
|---|---|---|
| 클래스 | 라벨 16 · 설명 16/16 · 한글명 16/16 | 라벨 14 · 설명 14/14 · 한글명 14/14 |
| 속성 | 77 · 타입 · 필수 · 데이터없음 5 | 87 · 타입 · 필수 55 · **커버리지 32** |
| 관계 | 17 · domain/range 17/17 · 카디널리티 17/17 | 18 · 18/18 · 18/18 |
| 닫힌 어휘 | 11종 · 동의어 51 · 원본표기 9 | 11종 68값 · **검색 별칭 165** |
| 계층(포섭) | 7쌍 · **observed 로 관측/선언 구분** | 전이 3종 · **materialize 선언** |
| 규칙 | **3종** (aggregate·transitive·chain) | 2개 · **chain 1종** (depth·where·nearest·tie_break) |

##### 커버리지가 수원에만 있는 이유

`required` 만으로는 "비어 있는 것이 정상인가"를 못 가린다.

```
Employee.name             0%    사이트가 직원 이름을 안 싣는다 (5,084명 중 6명은 기관장)
CivilService.external_org 0%    수원시 소관이면 비는 게 맞다 (644 중 6)
OrgUnit.address          94%    상속받은 주소를 포함한 값
```

조사해서 알아낸 사실이 선언에 숫자로 남는다.

## 3. 추론 — 같은 결론, 다른 증거

##### 나라원이 "수원에서 필요해진다"고 예측한 것

> chain 규칙 미검증 — 구현했지만 꺼뒀습니다. PART_OF 같은 **가변 깊이(via 의 depth)는 아직 없습니다. 수원의 IN_CHARGE_BUREAU 가 그 모양이라 거기서 필요해집니다.**

정확히 그랬다. 그리고 **수원이 먼저 만들었다.**

```yaml
# 나라원 제안 (미구현)
via:
  - {edge: HANDLED_BY, direction: out}
  - {edge: PART_OF, direction: out, depth: "1..", stop_at: {class: 총괄기관}}

# 수원 현재 (동작 중 · 583간선)
via:
  - rel: HANDLED_BY
  - rel: PART_OF
    depth: "0..5"                        가변 깊이
    where: { unit_level: bureau_levels }  정지 조건
    nearest: true
    tie_break: org_id                     ← 나라원 목록에 없던 것
```

##### `tie_break` 는 실데이터에서만 드러난다

선언으로 옮기니 손으로 쓴 Cypher 와 **18건에서 다른 답**이 나왔다. 원인은 구현이 아니라 규칙이었다.

```
난임부부 시술비 지원   4개 구보건소가 전부 거리 0 · 전부 직속기관
                     "가장 가까운 것 하나" 로는 답이 안 정해진다 (동점 21건)
```

나라원 제안에 `tie_break` 가 없는 이유는 **나라원 계층이 한 단계라 동점이 안 생겨서**다.

`stop_at` 과 `where + nearest` 는 트리에서 답이 같지만, **동점이 있으면 `stop_at` 은 순회 순서에 답이 달린다.**

##### 물질화 — 양쪽 다 "안 한다"

```
나라원   BROADER 를 저장 안 하는 건 Cypher 가 *0.. 을 네이티브로 하기 때문
수원     PART_OF 한 칸 938개인데 2홉 이상 경로가 2,070개. 저장하면 3배
```

수원은 여기에 **검사까지 붙였다** — `materialize: false` 인데 폐포가 저장돼 있으면 FAIL. 지름길 간선을 하나 만들어 잡히는 걸 확인했다.

##### 고정점 반복 — 양쪽 다 소비자가 없다

```
IN_CHARGE_BUREAU  ←  HANDLED_BY + PART_OF      둘 다 원천
VISIT_FOR         ←  REQUIRES + ISSUED_AT      둘 다 원천

규칙이 만든 것을 읽는 규칙이 없다 → 한 바퀴나 백 바퀴나 결과가 같다
```

나라원도 "만들어도 아무 일도 안 일어난다"고 적었다.

##### 그래서

```
온톨로지 구동 KG      양쪽 다 ✅
온톨로지 추론 KG      양쪽 다 ❌  — 규칙 적용기지 추론기가 아니다
```

**나라원은 종류가 넓고 깊이가 얕다. 수원은 종류가 좁고 깊이가 있다.**

## 4. 조용한 실패 — 같은 부류를 양쪽에서 만났다

나라원이 하루에 네 번 만났다고 적은 그 부류를 수원도 만났다.

| 나라원 | 수원 |
|---|---|
| `resolve` — same_as 대상 없으면 조용히 병합 안 함 | 결정 대상이 그래프에 없으면 조용히 아무 일도 안 함 |
| `serve` — Cypher 0건을 버려 '없다'의 근거가 사라짐 | 후보가 없어도 5개를 채워 "빈자리"를 못 알아봄 |
| `load` — group_edges 가 간선 속성을 통째로 버림 | `--full` 이 첫 인자면 죽음 (주석엔 된다고 적혀 있었다) |
| `infer` — 모르는 코드면 조용히 간선 안 만듦 | 창을 넓혔는데 조기 종료가 막아 안 들어옴 |

**공통 결론** — 검증기는 *없는 것*을 검사하지 못한다. 대신 **선언과 실제를 대조**하면 잡힌다.

## 5. 수원에만 있는 검사 둘

##### `validate/07` — 산출물 순서

나라원의 freshness 와 같은 것. 선언이 산출물보다 새로우면 FAIL.

##### `validate/08` — 선언과 **코드** 대조

**나라원에 없는 것이다.** `validate/06` 은 선언과 *그래프*를 대조하므로, 같은 사실이 선언과 코드에 두 벌 있어도 통과한다.

```
schema.yaml       org_classes → unit_level 17개
structure.py      UNIT_LEVELS = [...같은 17개...]
```

여기서 하나만 고치면 **적재는 잘 되고 검색만 조용히 틀린다.** 데이터가 멀쩡하니 그래프 검사로는 영원히 안 잡힌다.

이 검사가 만들어지자마자 `_SCHED_LABEL` 의 키 4개가 `schedule_kind` 어휘와 같은 것을 잡았다 — 어휘에 종류를 추가하면 라벨이 없어 답변에서 누락되는 상태였다.

## 6. 리팩토링이 찾아낸 결함 (수원, 2026-09-07)

전부 **"데이터는 멀쩡하고 답만 틀리는"** 부류라 그래프를 보는 검사로는 안 잡혔을 것들이다.

```
WORKS_AT 식별자가 조직 이름 사용     카디널리티 검사    두 구의 세무과가 한 사람으로
제약·키가 선언과 코드에 두 벌        레지스트리 신설
UNIT_LEVELS 17개가 두 벌           손으로 → validate/08 이 이제 잡는다
_SCHED_LABEL 이 어휘 키와 중복      선언·코드 대조     어휘 늘면 답변 누락
IN_CHARGE_BUREAU 동점 21건 미정의   추론 선언화
YAML 이 no 를 false 로 읽음        속성 선언         검사기가 자기 선언의 오류를 잡음
```

## 재사용 가능한 판단

- **선언이 검사를 만들면, 선언을 고칠 때 검사 수가 변한다.** 그게 "온톨로지 구동"의 증거다. 말이 아니라 숫자로 확인할 수 있다
- **규칙을 코드에서 선언으로 옮기면 규칙의 빈틈이 드러난다.** 동점 처리가 없다는 걸 옮기기 전에는 아무도 몰랐다
- **`materialize: false` 는 "안 한다"가 아니라 "일부러 안 한다"는 선언이다.** 없으면 다음 사람이 다시 만든다
- **커버리지는 required 가 못 하는 말을 한다** — "비어 있는 것이 정상인가"
- **기준선을 자동 갱신하면 검사가 무너진다.** `code_constants.json` 은 사람이 손으로 더한다. `quality.json` 과 반대 방침이고, 이유는 "새로 생긴 것이 조용히 기준이 되면 안 되기 때문"이다
- **쓸 데가 확인 안 된 규칙 종류는 만들지 않는다.** 만들어도 검증할 방법이 없다

## 한계

- **수원의 중간 산출물 없음** — "적재만 다시"가 안 된다. 지금 전체 20분이라 안 아프지만 데이터가 10배가 되면 아파진다
- **`stage: source/invariant` 없음** — `resolve` 단계가 생기면 그때 필요해진다
- **`observed` 구분 없음** — 계층이 관측된 것인지 사람이 정한 것인지 구분이 없다
- **규칙 종류 1개** — 제안요청서의 "추론 기반 검색" 요구 수준을 모르는 상태다. 문구를 보고 판단해야 한다
- **도메인 하나** — 두 프로젝트 다 "코드에 도메인 지식이 없다"를 증명하지 못했다. 수원은 `scraping/` 5,230줄에 사이트 구조가 그대로 박혀 있고, 선언으로 덜어낸 건 게시판 쪽뿐이다
