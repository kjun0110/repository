수원시 지식그래프를 **자동으로 최신화되게** 만들고, 나아가 **다른 기관에도 붙일 수 있게** 하는 계획. 2026-09-02 작성.

## 목표

```
Chatty(벡터)  ─┐
                ├─ 브리지(hybrid) ─▶ 시민 답변
KG(관계·구조) ─┘
      ↑
   여기가 자동으로 최신화돼야 한다
```

**KG 가 사이트 전체를 삼키는 것이 목표가 아니다.** 그것은 Chatty 가 이미 하고 있고(게시글 10.8만 건 포함), 둘을 합치는 것은 브리지가 한다.

```
벡터가 잘하는 것      본문을 읽고 답하기
KG 만 할 수 있는 것   관계를 타는 것
                    "인감증명 담당 부서는? 그 부서는 무슨 국 소관?"
                    "주민등록등본 필요한 민원 전부"
                    "냉장고 버리는 비용"          표 한 행
                    "청년 대상 민원 몇 건"        집계
                    "이 서식 어디서 받아"         파일 다운로드
```

실측이 그 차이를 보여준다.

```
"민방위 교육 안 가면"
  벡터   "과태료가 부과될 수 있습니다"                      일반론
  KG     "기준액 10만원, 50% 경감/가중, 거주지 관할 구 민방위팀"   구체
```

**KG 의 값은 커버리지가 아니라 관계 밀도다.** 그러므로 자동화의 목표도 "모든 페이지를 담는 것"이 아니라 **"관계를 만들 수 있는 페이지를 놓치지 않는 것"** 이다.

## 1단계 — 수원시가 스스로 최신화되게

### ⑨ 품질 게이트 (간단)

```
지금   적재 -> validate/03 기준선 갱신
문제   나빠져도 그것이 새 기준이 되어 굳어진다

후     적재 -> validate/04(1위 적중) -> 통과해야 기준선 갱신
                                  -> 떨어지면 알림 + 기준선 안 건드림
```

**이것이 없어서 실제로 일이 났다.** 2026-09-02 이전에 `여권 신청 어디서 해` 가 `어디서나민원(FAX민원)` 을 1위로 내놓고 있었는데, 회귀는 "어제와 같은가"만 봐서 20/20 통과였다. **안정적으로 틀린 것을 통과라고 부르고 있었다.**

### ⑩ 알림 (간단)

```
새 페이지 발견 · 검사 실패 · 품질 하락 · 파이프라인 중단
-> 로그 파일 + (필요하면) 메일·슬랙
```

지금은 눈을 감고 도는 셈이다.

### ① 발견 (반나절)

수원시 사이트는 **모든 페이지에 전체 메뉴가 박혀 있다.** 그것이 곧 페이지 목록이다.

```
1. 아무 페이지 한 장을 받는다                        HTTP 1회
2. <a href="*.jsp"> 를 전부 뽑는다                   698개
3. URL 패턴으로 민원 구역만 고른다
       /deptHome/dep_*/   분야별정보   받는다
       /www01/            종합민원     받는다
       /www02/ /www03/ /www05/         안 받는다 (신고센터·정보공개·시정소식)
4. PAGES 와 대조한다
       메뉴에 있는데 PAGES 에 없다  ->  새 페이지
       PAGES 에 있는데 메뉴에 없다  ->  사라진 페이지
```

**LLM 도 재귀 크롤링도 필요 없다.** 그리고 이 판정은 확실하다 — `content_type` 을 URL 로 맞히면 73%지만, **"민원 구역인가"는 사이트 구조가 그대로 말해 준다.**

현재 실측:

```
메뉴에 있는 jsp   698개
우리가 가진 것    647개
빠진 것          96개
   분야별정보(민원)   12개   <- 진짜 놓친 것
   www02 신고센터    24개
   www03 정보공개    30개
   www05 시정소식    28개
```

**발견만 하고 자동으로 넣지 않는다.** 사람이 보고 목록에 추가하는 것으로 시작한다 — 잘못 넣으면 "시민이 신청할 수 있는 것"이라는 노드 정의가 깨진다.

URL 패턴은 `sites/suwon.yaml` 로 뺀다. 2단계의 씨앗이다.

```yaml
# sites/suwon.yaml
base: https://www.suwon.go.kr
menu_probe: /sw-www/www01/www01-04/www01-04-01.jsp
accept: ["/sw-www/deptHome/dep_", "/sw-www/www01/"]
reject: ["/sw-www/www02/", "/sw-www/www03/", "/sw-www/www05/"]
content_selector: "#contents"
meta: { dept: {th: "담당부서"}, phone: {th: "전화번호"} }
breadcrumb_selector: ".path"
```

### ⑪ 실패 안전성 (하루) — 무인 운영의 전제

**롤백이 없다.** `graph_client` 에 명시적 트랜잭션이 없어 단계마다 자동 커밋되고, **멈춘 자리까지가 확정된다.**

중단 지점 둘의 성격이 다르다.

```

                   가장 확실하지만 그래프가 커지면 느리고 백업 관리가 붙는다
```

## 새 유형이 들어오면 — 판정·라벨·승격

자동화의 가장 어려운 부분이다. **기존 그래프에 없는 종류의 정보가 왔을 때** 무엇으로 만들지를 누가 어떻게 정하는가.

### 지금은 "모르는 것"이 못 들어온다

```python
"content_type": {
    "enum": ["procedure", "reference"]    # 둘 중 하나. 탈출구 없음
}
```

그리고 `validate/00` 이 이 목록 밖의 값이면 **파이프라인을 멈춘다.**

**지금은 이것이 강점이다** — 그래프에 무엇이 있는지 확정적이다. 그런데 자동화하면 **약점이 된다.** FAQ 페이지가 하나 생기면 LLM 이 억지로 `procedure` 나 `reference` 를 찍고, 아무도 모르게 잘못 들어간다.

### 온톨로지가 판정하는 것이 아니다

여기가 핵심이다.

```
LLM 이 판정한다                       본문을 읽고 유형을 정한다
온톨로지는 그 판정이 허용되는가를 본다     닫힌 어휘 안에 있는가
```

`ontology/schema.yaml` 의 `vocabulary` 절이 그것이고, `validate/00` 이 읽어서 목록 밖이면 멈춘다.

```yaml
vocabulary:
  content_type: [procedure, reference]
```

**닫힌 어휘의 진짜 값은 "모르는 것이 들어오면 알려 주는 것"이다.** 분류를 잘하게 만드는 장치가 아니라, **분류할 수 없는 것이 왔을 때 조용히 넘어가지 않게** 하는 장치다.

### 자동화되면 멈추는 대신 격리한다

```
지금    목록 밖 -> sys.exit             사람이 와서 봐야 한다
후      목록 밖 -> unknown -> (:Page)   파이프라인은 계속 돌고
                            -> 리포트    사람이 나중에 본다
```

### 만들어야 할 자리 셋

**자리 1 — 게이트에 `unknown` 을 준다**

```python
"content_type": {
    "enum": ["procedure", "reference", "unknown"]
}
```

`unknown` 은 실패가 아니라 정직한 답이다. LLM 에게 "확신 없으면 unknown" 이라고 명시하면 억지 판정을 안 한다.

**단 도피처가 될 위험이 있다.** 애매하면 다 `unknown` 으로 던지면 아무것도 분류가 안 된다. 감시가 붙어야 한다.

```
unknown 비율이 5% 넘으면 알림
   -> 프롬프트가 나빠졌거나, 진짜 새 유형이 늘고 있거나
```

**자리 2 — 대기실 `(:Page)`**

```
아는 유형     기존 클래스 (:CivilService 등)  ->  :Entity     ->  검색된다
unknown      (:Page) 노드 + 속성            ->  :Entity 없음  ->  검색에 안 섞인다
```

버리지도 않고 오염시키지도 않는다. 속성으로만 담아 둔다 — [[KG - 온톨로지 선언 파일 (TBox)]] 의 원칙 그대로다.

```
관계 타입    닫힘   질의가 이름을 알아야 쓸 수 있다
노드 라벨    닫힘   :Entity 를 붙일지·임베딩할지 사람이 정해야 한다
속성         열림   모르는 값이 와도 담아둘 수 있다
```

**자리 3 — 승격 리포트**

```
매 수집 후
  (:Page) 신규 12건 · 누적 47건
  묶어보니 3종
    "부서 소개" 계열     7건   <- 승격 안 함. 조직 노드가 이미 있다
    "FAQ" 계열          4건   <- 후보. 20건 되면 다시 보자
    "채용공고"           1건   <- 보류
```

### 승격은 무엇을 보고 결정하나 — 기준은 하나다

```
여러 개체가 같은 값을 가리키고 그것으로 묶어 묻고 싶다   ->  노드
개체 하나에만 붙고 조건 검색만 한다                     ->  속성
```

실제 선례가 그 기준을 보여 준다.

```
신분증           수백 개 민원이 공유           ->  (:DocumentType) 노드
인감증명법        여러 민원이 참조              ->  (:Regulation) 노드
"제19조"         그 연결에만 붙음              ->  BASED_ON 관계 속성
"1. 신청서 작성"  그 민원만의 것                ->  속성
content_type     분류인데 질의가 이름으로 안 씀   ->  속성 (라벨이 아니다)
```

`content_type` 이 좋은 예다. 클래스 구분인데 라벨을 안 만들었다 — `WHERE c.content_type = 'procedure'` 로 충분하고, 라벨은 재실행 때 `REMOVE` 를 빠뜨리면 옛 판정이 남는다. 2026-09-02 에 `:총괄기관`·`:실무조직` 을 걷어낸 것과 같은 판단이다.

### 3단계 승격

```
1단계  속성으로 받는다        새 정보는 일단 문자열
         ↓ 값이 쌓이고 반복되면
2단계  닫힌 어휘인지 확인한다   값 종류가 몇 개인지 센다
         ↓ 공유되면
3단계  노드·관계로 승격한다    선언 추가 + 마이그레이션
```

### 관계는 자동으로 못 늘린다

가장 중요한 제약이다.

> `:SUPPORTS_FOR` 같은 관계가 자동으로 생겨도 `search/` 가 그 이름을 모르면 조회할 코드가 없다 — **노드는 늘고 답은 그대로다.**

그리고 어휘가 갈라진다.

```
HANDLED_BY · MANAGED_BY · IN_CHARGE_OF · RESPONSIBLE_FOR
   -> 같은 뜻인데 LLM 이 페이지마다 다르게 짓는다
```

**어휘가 갈라지면 그래프가 조회 불가능해진다.** 그래서 관계와 라벨은 닫혀 있고, 사람이 선언을 추가해야만 늘어난다.

### 전체 흐름

```
새 페이지
   │
   ├─ ① URL 패턴(신호 1층)으로 구역 판정
   │       /deptHome/dep_*  ·  /www01     ->  받는다
   │       /www02 · /www03 · /www05       ->  안 받는다
   ▼
   ② 본문 추출 (사이트별 셀렉터. sites/*.yaml)
   │
   ├─ ③ LLM 이 content_type 판정 (신호 3층)
   │       procedure  |  reference  |  unknown
   ▼
   ④ validate/00 — 온톨로지 어휘 대조
   │
   ├─ 어휘 안 ──▶ (:CivilService)  ──▶ :Entity ──▶ 벡터 검색에 편입
   │                  │
   │                  └─▶ 관계 적재 ──▶ 추론 ──▶ 답변에 관계가 붙는다
   │
   └─ unknown ─▶ (:Page) 속성만   ──▶ :Entity 없음 ──▶ 격리
                      │
                      └─▶ 승격 리포트 ──▶ 사람이 판단
                                            │
                                            ├─ 값이 공유됨
                                            │     -> 선언 추가 + 마이그레이션
                                            │     -> 노드·관계로 승격
                                            │
                                            └─ 안 됨
                                                  -> 속성으로 둔다
```

### 지금 있는 것과 없는 것

```
있음    닫힌 어휘 + validate/00 이 목록 밖을 잡는 것
        3단계 승격 원칙 (TBox 노트)
        "값이 공유되는가" 판단 기준
        content_type 을 라벨이 아니라 속성으로 둔 선례

없음    unknown 값
        (:Page) 대기실
        승격 리포트
        마이그레이션 절차
        unknown 비율 감시
```

**`(:Page)` 가 쌓이기만 하고 아무도 안 보면 쓰레기통이 된다.** 승격 리포트가 실제로 굴러가야 의미가 있다.

## 2단계 — 두 번째 지자체로 재사용을 증명

### 왜 고양시인가 — 실측 근거

```
              본문 셀렉터    담당부서 th/td   breadcrumb   URL 체계
수원          #contents      O              .path        /sw-www/www01/www01-04/www01-04-06.jsp
고양          #content       X (전화번호만)   없음         /www/www02/www02_1/www02_1_3.jsp
화성          못 찾음         X              없음         /www/minwon/minwonGnrlzInfo/mcrtfFee.jsp
성남          다른 체계        —              —            /city/1000226/30001/bbsList.do
```

**URL 체계는 놀랍게 비슷하다** — 수원 `www01/www01-04/www01-04-06.jsp`, 고양 `www02/www02_1/www02_1_3.jsp`. 같은 업체 솔루션이고 메뉴 번호로 계층을 표현하는 방식이 같다.

**그런데 파싱은 하나도 안 맞는다.** `#contents` vs `#content` 한 글자 차이로 셀렉터가 다르고, 고양은 담당부서 `th/td` 가 아예 없으며 breadcrumb 클래스도 없다.

### 무엇을 증명하려는가

```
층                    지자체 간 공통성    재사용?   2단계에서 확인
────────────────────────────────────────────────────────────
① HTML 파싱           거의 0            X        yaml 로 빼면 되나
② 도메인 규칙          높음              △        "○○과 -> 과", 발급처 12종이 그대로 먹나
③ 온톨로지 선언         매우 높음          O        bureau_levels · content_type 이 그대로 도나
④ 적재·검증·추론        완전              O        28단계가 코드 수정 없이 도나
⑤ 검색                완전              O        그대로 도나
```

**지금은 "재사용될 것 같다"지 "재사용된다"가 아니다.** 위 표도 실측이 아니라 코드를 읽고 추정한 것이다. 한 번 붙여 봐야 진짜 갈림선이 나온다.

코드 규모로 보면 이렇다.

```
수집       ~2,000줄    사이트마다 다시 (PAGES 700 + 파싱 364 + LLM 패스)
적재·검증   ~3,000줄    그대로
검색       ~2,500줄    그대로
온톨로지    ~800줄      거의 그대로
```

### 왜 도메인 규칙은 재사용될 것 같은가

한국 지자체는 **조직 체계가 법으로 정해져 있다.**

```
실/국/과/팀/구/동     지방자치법. 전국 동일
"○○과" -> 과         이름 규칙도 동일
주민등록등본 발급처     어느 시든 동 행정복지센터·무인민원발급기·정부24
```

`classify.py` 의 접미사 규칙과 `documents.py` 의 발급처 어휘는 거의 그대로 먹을 것이다. 예외 25건(도서관·박물관 같은 것)만 시마다 다르다.

## 3단계 — 2단계 결과에 따라 갈린다

```
2단계가 쉬웠다면    sites/*.yaml 을 늘리는 것으로 끝. LLM 불필요
2단계가 어려웠다면   LLM 이 site.yaml 을 써 주게 한다
```

### LLM 을 파싱에 넣지 않고 설정 생성에 쓴다

```
새 사이트 표본 3~5장  ->  LLM  ->  site.yaml 초안
                                    ↓
                             검증(본문 길이 · 제목 포함 여부 · 표본 전부에서 되나)
                                    ↓
                             사람이 확인하고 확정
```

**사이트당 LLM 5회.** 페이지마다 부르는 것이 아니라 한 번 설정을 뽑는다. 실행은 여전히 규칙이라 그래프가 흔들리지 않는다.

**얻는 것은 구조지 의미가 아니다.**

```
자동으로 됨    본문이 어디 있나 · 담당부서가 어느 칸인가
안 되는 것     "이 기관에서 주민등록등본은 어디서 떼나"
              "이 기관의 조직 체계는 어떤가"
```


## 안 할 것 — 이유와 함께

##### LLM 이 HTML 을 통째로 읽게 하기

```
장점   사이트를 안 가린다. 바로 붙는다
단점   HTML 이 페이지당 38만 자. 토큰이 수십 배
       표 구조가 평탄화돼 WasteItem·Place 가 안 나온다
       실행마다 흔들려 그래프가 안 굳는다
```

지금 그래프 밀도(`HANDLED_BY` 700 · `REQUIRES` 890 · `ISSUED_AT` 156)를 포기하는 것이다.

##### 스키마를 느슨하게 — `(:Thing)-[:REL {type}]->(:Thing)`

**제약이 곧 검증이다.** `documenttype_name_unique` 가 있어서 `주민등록등본` 이 두 개 생기면 즉시 터진다. 범용 스키마면 `Thing` 두 개가 생기고 아무도 모른다.

`DEPT_NOT_BODY` 도 마찬가지다. `HANDLED_BY` 가 별도 타입이라 "이 관계의 대상은 실무조직이어야 한다"를 물을 수 있다. `REL {type:"..."}` 이면 그 질문 자체가 성립하지 않는다.

##### 표준 어휘(schema.org / CPSV)로 갈아타기

```
얻는 것   상호운용성. 그런데 지금 우리 그래프를 읽을 다른 시스템이 없다
잃는 것   issued_at 의 12종 닫힌 어휘. "접수처에 비치 — 미리 떼 올 필요 없음"
         같은 값은 표준에 없는데 281종(46%)을 차지한다
그대로    표준을 써도 "담당부서가 국이면 안 된다"는 여전히 우리가 짜야 한다
```

##### B 신호 1·2층으로 `content_type` 판정하기

644건 실측으로 기각했다.

```
URL 구역 다수파       467/644 = 73%
breadcrumb 다수파    530/644 = 82%     (항상 reference 로 찍어도 59%)
확실한 구간           8건 이상 순수 6종 77건 = 12%
```

**breadcrumb 은 주제를 나타내지 행동 여부를 나타내지 않는다.** 같은 `복지 > 생애주기별 > 영유아` 21건에 procedure 18 · reference 3 이 섞여 있다.

그리고 캐시가 이미 있어 재실행 비용이 0 이다. 1층으로 아끼는 것은 첫 수집의 12%뿐인데 오판하면 `validate/01` 규칙과 답변이 직접 깨진다.

**단, 규모가 커지면 역할이 뒤바뀐다.** 게시판 본문(10만 건 × 5패스 = 50만 호출)이 들어오면 "전부 LLM 에 보낸다"가 불가능해지고, 1층의 일이 판정이 아니라 **걸러내기**가 된다. 버리는 것은 틀려도 회복 가능하지만 판정을 틀리는 것과는 위험이 다르다.

## 순서

```
1  ⑨ 품질 게이트 + ⑩ 알림     간단     지금 눈감고 도는 것을 막는다
2  ① 발견                    반나절   지금 놓친 12개를 잡는다
3  ⑪ 실패 안전성 (C안)         하루     무인 운영의 전제
4  ⑬ unknown + (:Page) 대기실  하루    새 유형이 와도 안 멈추고 격리된다
5  ⑭ 승격 리포트              반나절   (:Page) 가 쓰레기통이 되지 않게
6  ⑫ 스케줄                   간단
────────────────────────────────────
7  2단계 — 고양시로 재사용 증명   2~3일

```

**1·2 를 먼저 하는 것이 맞다.** 3이 없어도 사람이 보고 돌리면 되지만, **품질 게이트가 없으면 나빠진 것을 모른 채 굳어진다** — 실제로 일어났던 일이다.
