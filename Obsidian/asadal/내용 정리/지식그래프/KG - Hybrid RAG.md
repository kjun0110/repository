
### 아키텍쳐 A(매핑방식): 벡터DB(별도) + 그래프DB(별도), 둘을 연동
그래프DB엔 임베딩 필요 없고, 벡터DB에 매핑 테이블이 필요하다

```
사용자 질문
   │
   ├─① 벡터DB(Pinecone, Weaviate 등)에서 임베딩 유사도로 진입점 노드 ID를 찾음
   │
   └─② 그 ID를 가지고 그래프DB(Neo4j)에 가서 관계 확장(N홉 탐색)
   │
   ▼
결과 합쳐서 LLM에 전달
```


### 아키텍처 B(라우팅방식): Neo4j 하나에 벡터 인덱스까지 통합
그래프 DB에 임베딩이 필요함
대부분의 경우 청킹이 필요 없지만 청킹이 필요한경우 나눠서 노드로 만들고 has chunk로 관계 지어서 만들면 됨 

```
사용자: "주민등록 관련 민원 다 보여줘" (카테고리성 질문)
   ↓
① 벡터 검색: "주민등록"이라는 Type 노드와 유사도 매칭 (이때는 Type 노드 임베딩이 유용함)
   ↓
② Type 노드를 찾은 뒤, INSTANCE_OF 역방향으로 그 타입에 속한 실제 민원들을 다 가져옴
   MATCH (m)-[:INSTANCE_OF]->(:Type)-[:SUBCLASS_OF*0..]->(:Type {name:"주민등록"})
   RETURN m.name  // 전입신고, 전출신고 등 다 나옴
```


### 어느 쪽이 맞는지 — 규모에 따라 갈림

|상황|추천 아키텍처|
|---|---|
|데이터 규모가 크지 않음 (수만~수십만 노드)|**B (Neo4j 통합)** — 운영 단순함이 이점|
|임베딩 대상이 수백만~수천만 건, 초저지연 필요|**A (벡터DB 분리)** — 전문 벡터DB의 최적화 성능 필요|
|이미 조직에 벡터DB가 구축돼 있음|A (기존 인프라 재사용)|


### 아키텍처 c(퓨전방식) 
- 벡터DB(Postgres/pgvector) + 그래프DB(Neo4j)를 동시에 활용하는 검색 아키텍처
- 질문이 들어오면 Postgres와 Neo4j 양쪽에 동시에 검색을 걸고, 두 결과를 하나의 순위로 재정렬(재랭킹)해서 LLM에 넘긴다.
- 질문 → Postgres 검색도 하고 Neo4j 검색도 동시에 함 → 두 결과를 합쳐서 하나의 컨텍스트로 → LLM

#### 스코어를 합치는 표준 기법: RRF (Reciprocal Rank Fusion)

두 검색 시스템의 점수 체계가 다를 수 있어서(Postgres 코사인 유사도 vs Neo4j 코사인 유사도가 살짝 다른 스케일일 수 있음), 순위 기반으로 공정하게 합치는 기법이 실무에서 많이 쓰여요:

### 하이브리드 RAG 구조 (A + B 병행)

**역할 분담**

- **pgvector**: 전체 원문 커버, 의미 유사도 기반 검색 (dense retrieval)
- **그래프DB**: 관계가 질의에 의미 있는 개체들의 부분집합만 온톨로지화 (타입 체계 + 관계 의미 + 도메인 제약을 갖춘 진짜 구조)

### 검색 흐름

**A 방식 (기본 골격) — 순차형**

1. pgvector에서 벡터 검색으로 관련 청크 top-k 확보
2. 청크 ↔ 그래프 노드 매핑 테이블로 연결된 노드(엔티티) 시드 확보
3. 그래프에서 1~2홉 확장 → 관계/구조 정보 획득
4. 청크 원문 + 그래프 확장 결과를 합쳐 LLM 컨텍스트 구성

**B 방식 (보조 보강) — 병렬형**

- 그래프 노드 자체에도 임베딩을 붙여 독립적으로 벡터 검색
- A가 놓친 엔티티를 보완, RRF 등으로 A 결과와 fusion
- 단, 청크 임베딩과 노드 임베딩은 텍스트 단위/모델이 달라 스코어 직접 비교는 주의 필요

### 필수 연결 구조

|요소|내용|
|---|---|
|매핑 테이블|`chunk_id ↔ node_id` (N:M 관계이므로 별도 테이블 권장)|
|노드 메타데이터|`source_doc_id`, `source_offset` — 나중에 청크와 소급 매칭 가능하도록|
|정합성 관리|문서 갱신 시 청크 재임베딩 + 엔티티 재추출이 같은 파이프라인/트랜잭션에서 함께 처리되도록 설계|

### 지금 상황(그래프DB만 담당, pgvector 접근 불가)에 맞춘 순서

1. **지금**: 원본 소스에서 직접 텍스트 인입 → 엔티티/관계 추출 → 노드 타입·엣지 타입 스키마 설계 → 노드에 자체 임베딩 부여(B 단독 완결)
2. **동시에 반드시**: `source_doc_id`, `source_offset` 등을 노드/엣지에 심어둠 (나중 매칭용)
3. **나중(pgvector 접근 열리면)**: 오프셋 매칭으로 `chunk_id ↔ node_id` 매핑 테이블 소급 생성 → A 파이프라인 연결 → 이후 A+B 병행 하이브리드 완성
