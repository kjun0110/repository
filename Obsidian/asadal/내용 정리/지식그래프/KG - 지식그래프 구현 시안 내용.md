## 개요

수원시 조직도를 그래프DB로 구현하는 두 가지 방식 — **라벨 방식**(`suwon_label`)과 **온톨로지 방식**(`suwon_ontology`) — 의 구현 내용과 비교 정리.

---

## 1. 라벨 방식 (suwon_label)

수원시청 공식 조직도를 Neo4j 그래프DB로 구축. 시장 → 부시장 → 실/국/사업소/구청 → 과/팀 → 직원까지 전체 위계구조를 그래프로 연결.

- 수원 조직도 및 상세페이지를 스크래핑·파싱해 라벨 생성
- 이름 접미사 규칙(`~과`→"과", `~국`→"국" 등) + `MANUAL_LABEL_OVERRIDES` 딕셔너리(접미사로 안 잡히는 예외 26개, 보건소·사업소·전문위원 등)로 "이 이름이 무슨 종류냐"를 문자열로 반환 → 이 문자열이 그대로 Neo4j **라벨**이 됨
- 구조 관계는 `PART_OF`로 매칭

---

## 2. 온톨로지 방식 (suwon_ontology)

같은 데이터를 **TBox(개념 계층)와 ABox(실제 데이터)로 분리**해서 구현.

- **TBox**: `:Class` 노드 + `SUBCLASS_OF` 관계로 개념 계층을 그래프 안에 직접 저장 (`조직`/`구성원` 루트 아래 `시장`/`부시장`/`실`/`국`/`과` 등 17개 하위 클래스)
- **ABox**: 실제 조직·직원 데이터는 라벨 없이 전부 `:Instance` 하나로 통일하고, `TYPE_OF` 관계로 해당 `:Class`와 연결
- 구조 관계는 라벨 방식과 동일하게 `PART_OF` 사용

```cypher
(:Instance {id:"37403020000", name:"행정지원과"})-[:TYPE_OF]->(:Class {name:"과"})
(:Class {name:"과"})-[:SUBCLASS_OF]->(:Class {name:"조직"})
```

핵심 차이: "이게 무슨 종류냐"라는 정보가 라벨 방식에서는 **문자열 태그**(Neo4j 라벨)로 존재하고, 온톨로지 방식에서는 **그래프 안의 노드**(`:Class`)로 존재한다.

---

## 3. 두 방식 비교

| 항목 | 라벨 방식 | 온톨로지 방식 |
|---|---|---|
| 타입 표현 | Neo4j 네이티브 라벨(문자열 태그) | `:Class` 노드 + `TYPE_OF` 관계 |
| 노드 / 관계 수 (측정 시점 기준) | 6,046 / 12,069 | 6,027 / 6,025 |
| 타입 필터링(`MATCH (n:과)`) | **빠름** — 라벨이 노드에 직접 붙어있어 1단계 확인 | 느림 — `TYPE_OF` 관계를 한 홉 더 타야 함 |
| 벡터 검색 | 느림 — 라벨마다 인덱스가 분산돼 scatter-gather 필요 | **빠름** — 인덱스가 `:Instance` 하나로 통합됨 (실측 3.17배, [[그래프DB 라벨 vs 온톨로지 구조 벡터검색 비교정리 (Graph DB Label vs Ontology Vector Search Comparison)]] 참고) |
| 스키마 확장 | 코드 수정 필요 | 데이터만 추가하면 됨 |

> [!note] 노드/관계 수는 측정 당시 스냅샷 기준으로, 이후 데이터 수정(고아 노드 정리 등)으로 현재 값과 다를 수 있음 — 재확인 필요.

> [!warning] "온톨로지가 항상 느리다"는 연산 종류에 따라 다름
> 초안에는 "속도: 온톨로지가 항상 같거나 느림"이라고 적혀 있었으나, 이는 **타입 필터링 연산에만 해당**한다. 벡터 검색은 반대로 온톨로지 쪽이 더 빠르다 — 인덱스가 `:Instance` 하나로 통합돼 있어 왕복 횟수가 줄기 때문. 자세한 원인 분석은 [[그래프DB 라벨 vs 온톨로지 구조 벡터검색 비교정리 (Graph DB Label vs Ontology Vector Search Comparison)]] 참고.

## 4. 온톨로지 방식의 이점

**1) 코드 안 고치고 스키마 확장 가능 (제일 실질적인 이점)**

`suwon_label`은 새 조직 종류가 생기면 `classify()` 함수, `ALL_LABELS` 리스트, `MANUAL_LABEL_OVERRIDES` 딕셔너리까지 Python 코드를 열어서 고쳐야 한다. `suwon_ontology`는 그래프에 `:Class` 노드 하나 + `SUBCLASS_OF` 관계 하나만 추가하면 끝 — 배포·코드수정 없이 데이터로 스키마를 확장할 수 있다.

**2) "개념 목록/계층"을 코드가 아니라 쿼리로 조회 가능**

```cypher
MATCH (c:Class)-[:SUBCLASS_OF*0..]->(:Class {name:"조직"}) RETURN c.name
```

`suwon_label`로 똑같은 걸 하려면 `ALL_LABELS = [...]`처럼 사람이 직접 나열해둔 Python 리스트를 코드에서 열어봐야 안다. 온톨로지 쪽은 그래프 자체가 스스로 "나는 이런 개념들로 이뤄져 있다"고 답할 수 있다 — **self-describing** 구조의 핵심 이점.

**3) 개념 자체에 정보를 붙일 수 있음**

`:Class` 노드는 이름표가 아니라 진짜 노드라서 속성을 가질 수 있다. 예를 들어 "과"라는 개념에 `설명: "실·국 산하 최소 행정단위"`, `근거법령: "지방자치법 ~조"` 같은 메타정보를 그 `Class` 노드에 그대로 `SET`하면 된다. `suwon_label`의 라벨은 문자열 태그일 뿐이라 라벨 자체엔 아무것도 못 붙인다 (Python 코드 주석에 적는 게 전부).

**4) 다른 시스템과의 매핑/통합이 쉬움**

나중에 "수원시 '과'"를 "전국 표준 행정조직 온톨로지의 'Department'"와 연결하고 싶다면:

```cypher
(:Class {name:"과"})-[:EQUIVALENT_TO]->(:Class {name:"Department", source:"국가표준"})
```

처럼 개념과 개념을 관계로 바로 이을 수 있다. 라벨 방식은 이런 매핑을 하려면 Python 딕셔너리로 별도 변환 테이블을 만들어야 한다.

---

## 5. 트레이드오프 (공짜는 아님)

- 타입 필터링 쿼리가 라벨 방식보다 느림 (`TYPE_OF` 한 단계 더 거쳐야 함)
- 노드/관계 수가 더 적지만(`:Class`/`TYPE_OF` 오버헤드는 있음), 벡터 검색 인덱스는 오히려 통합돼 유리
- 구조가 한 단계 더 복잡해서 처음 보는 사람은 이해하기 어려움

---

## 6. 결론

조직 종류가 자주 안 바뀌고 **타입 필터링·빠른 단순 조회**가 중요하면 `suwon_label`이 유리하고, 스키마가 계속 진화하거나 **벡터 검색·다른 시스템과의 개념 매핑**이 중요하면 `suwon_ontology`가 유리하다.
