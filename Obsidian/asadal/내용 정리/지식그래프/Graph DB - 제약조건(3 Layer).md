### 제약조건(Constraint) 정리 - 결국 규칙 그 자체는 db 내에 존재하는건 아니고 명시하는것

#### 핵심 원칙

**정의(Specification)와 강제(Enforcement)는 별개다.**

- 정의 = "어떤 규칙이 있어야 하는가"를 명시하는 것 → **온톨로지의 역할**
- 강제 = 그 규칙을 실제로 지키게 만드는 메커니즘 → **레이어마다 위치가 다름**

#### 레이어 1 — DB 엔진 네이티브 제약 - 쿼리문 작성
존재 제약, 유일성 제약, 타입 제약. Neo4j가 기본 문법으로 지원.
cypher
```cypher
CREATE CONSTRAINT person_name_exists
FOR (p:Person) REQUIRE p.name IS NOT NULL;

CREATE CONSTRAINT contract_id_unique
FOR (c:Contract) REQUIRE c.contract_id IS UNIQUE;
```
→ DB 엔진이 알아서 강제해줌. 별도 구현 불필요.

#### 레이어 2 — 카디널리티/관계 규칙
예: "REPORTS_TO는 1인당 상사가 최대 1명."
Neo4j는 관계형DB의 FK처럼 이런 카디널리티 제약을 기본 지원하지 않음 → 직접 구현 필요:
- **APOC(또는 Neo4j 5.13+ 내장) 트리거**: DB 레벨에서 쓰기 시 자동 검증(db.triggers 관련 프로시저 대체해야할 수 도) - (쿼리문으로 제약조건 명시)
- **애플리케이션 코드**: 쓰기 요청 전에 먼저 조회해서 체크 - (python으로 제약조건 명시)
- (Neo4j 대신 GraphDB, Stardog 같은 RDF+SHACL 기반이면 선언적으로 엔진이 지원)

#### 레이어 3 — 비즈니스 규칙 / Action precondition
예: "활성 고객만 계약 갱신 가능."
DB가 알 수 없는 순수 비즈니스 맥락이므로, Action을 실행하는 애플리케이션 코드 안에서 반드시 체크. 이것도 온톨로지 밖이 아니라 **Action Type 정의의 일부**로 다뤄야 함(precondition으로 명시).
### APOC 트리거
**장점**
- 어떤 경로로 쓰기가 들어오든(직접 Cypher 콘솔에서 치든, 다른 앱에서 API 호출하든) 무조건 걸러짐 — 우회 불가능
- 규칙이 DB 안에 한 곳에 모여 있어서 관리 포인트가 하나

**단점**
- Neo4j 5.13+ 부터는 APOC 트리거가 아예 deprecated 되고 **Neo4j 자체 내장 트리거 기능(`db.triggers`)**로 이전되는 중이라, 버전 확인 필요 — 오래된 문서 보고 따라하면 동작 안 할 수 있음
- 복잡한 비즈니스 로직(여러 조건 분기, 외부 API 조회 등)을 Cypher로 표현하기 번거로움
- 디버깅이 애플리케이션 코드보다 어려움 (에러가 DB 레이어에서 터짐)
- 트리거가 많아지면 쓰기 성능에 영향
#### 요약

| 레이어 | 정의 주체 | 강제 주체 |
|---|---|---|
| 1. 존재/유일성/타입 | 온톨로지 | Neo4j 엔진(네이티브) |
| 2. 카디널리티/관계 | 온톨로지 | 트리거 또는 애플리케이션 |
| 3. 비즈니스 규칙 | 온톨로지 (Action 정의) | 애플리케이션(Action 실행 로직) |


### 애플리케이션 레벨 체크 — 코드에서 체크
**장점**
- 일반 프로그래밍 언어로 짜므로 복잡한 로직, 외부 시스템 연동, 상세한 에러 메시지 처리가 쉬움
- 디버깅/테스트가 익숙한 방식으로 가능 (유닛 테스트 등)
- 팀이 이미 익숙한 언어/프레임워크로 작업

**단점**
- 이 검증 로직을 거치지 않고 **다른 경로로 직접 Cypher를 날리면 뚫림** (예: 나중에 다른 서비스나 스크립트가 그래프에 직접 접근하면 규칙이 무시됨)
- 여러 서비스가 같은 그래프에 쓰기를 한다면, 그 검증 로직을 모든 서비스에 각각 구현/동기화해야 함 → 중복 및 누락 위험

## APOC 트리거 vs 애플리케이션 체크

| | 트리거 | 애플리케이션 체크 |
|---|---|---|
| 장점 | 우회 불가능, 규칙이 한 곳에 집중 | 복잡한 로직 짜기 쉬움, 테스트/디버깅 익숙 |
| 단점 | 5.13+부터 deprecated 진행 중, 복잡한 로직 표현 번거로움 | 다른 쓰기 경로로 뚫릴 수 있음, 여러 서비스면 중복 관리 필요 |
| 적합 상황 | 여러 서비스가 그래프에 직접 쓰기 접근 | 쓰기 경로가 단일 서비스로 통제됨 |
