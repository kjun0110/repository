RDF 스택에서 추론기 · 검사기가 **어느 단계에서 무슨 일을 하는지**를 예시 하나로 처음부터 끝까지 따라가며 정리한다. 추론기 후보 조사와 라이선스는 [[RDF - 스택 구성과 버전 관리, 추론기 선택]]에 있다.

---

## 한 줄 요약

> 온톨로지 하나를 OWL 로 쓰고, **DL 엔진(HermiT)은 "이 규칙이 말이 되나"를 판정**하고, **SHACL 은 "들어온 데이터가 규칙에 맞나"를 검사**하고, **RL 엔진은 "이 규칙대로 데이터에 사실을 채워 넣는"** 일을 한다. 두 엔진이 같은 결론을 내게 하려고 운영 규칙은 RL 범위 안에서 쓴다.

| 순서 | 단계 | 도구 | 하는 일 |
|---|---|---|---|
| 1 | 온톨로지 작성 | **HermiT (DL)** | 규칙끼리 모순이 없는지 검사 (+ RL 범위 검사) |
| 2 | 데이터 적재 | **SHACL** | 들어온 데이터가 규칙에 맞는지 검사 — 쓰지 않고 검사만. 문지기 |
| 3 | 운영 추론 | **RL 엔진** (owlrl · Jena · GraphDB 등) | 검사를 통과한 데이터에서 새 사실을 뽑아 저장 |
| 4 | 조회 | SPARQL | 추론 결과까지 한 줄 질의로 |

## 용어 정리 — 언어 · 범위 · 엔진

| 이름 | 정체 | 비유 |
|---|---|---|
| **온톨로지** | 내용 — 개념 · 관계 · 규칙 | 계약서 내용 |
| **OWL** | 온톨로지를 적는 W3C 표준 언어 | 계약서를 쓰는 언어 |
| **OWL 2 DL** | OWL 의 넓은 범위(프로필) | — |
| **OWL 2 RL** | DL 의 일부인 좁은 범위. "A 이고 B 이면 C" 규칙으로 바꿀 수 있는 것만 | — |
| **HermiT** | DL 범위를 계산하는 엔진 (Java) | DB 엔진 |
| **owlrl** | RL 범위를 계산하는 파이썬 엔진. 이름이 범위 이름과 같아 헷갈린다 | DB 엔진 |
| **SHACL** | 데이터 검사 규칙 언어 (W3C). OWL 과 별개 | 입력 폼 유효성 검사 |

- **OWL 은 언어, HermiT 는 엔진**이다. SQL 과 MySQL 관계. HermiT 는 OWL 로 적힌 규칙이 없으면 할 일이 없다
- **RL 범위는 내가 정하는 게 아니다.** W3C 표준(OWL 2 Profiles)이 경계를 고정하고, 나는 그 안에서 쓸지만 고른다
- 범위는 포함 관계 — `OWL 2 Full ⊃ DL ⊃ RL (· EL · QL)`
- 표준 문서: OWL 2 프로필 https://www.w3.org/TR/owl2-profiles/ (RL 은 4.3절), DL 제약 https://www.w3.org/TR/owl2-syntax/ (11절), SHACL https://www.w3.org/TR/shacl/

| | OWL 2 DL | OWL 2 RL |
|---|---|---|
| 역할 | **설계 검사**, 정밀한 판단 | **운영 추론** |
| 엔진 | HermiT | owlrl, Jena, GraphDB, RDFox |
| 추론 방식 | 논리적으로 따져 봄 | 규칙 반복 적용 |
| 결과 | "모순이다 / 반드시 그렇다" 판단 | 새 트리플 저장 → SPARQL 조회 |
| 강점 | 표현력, 정확함 | 속도, 대량 데이터 |

# 예시로 따라가기

## 0. 예시: 작은 회사 조직도

**데이터** (실제로 저장된 사실)
```
직원E1  MEMBER_OF   팀T
팀T     SUB_ORG_OF  부서D
부서D   SUB_ORG_OF  본부H
```

**온톨로지 규칙** (OWL 로 작성)

| 번호 | 규칙 | 뜻 |
|---|---|---|
| R1 | 팀 ⊂ 조직단위, 부서 ⊂ 조직단위 | 팀과 부서는 조직단위의 한 종류 |
| R2 | 조직단위 ⊥ 회사 | 조직단위이면서 회사일 수는 없다 (배타) |
| R3 | SUB_ORG_OF 는 Transitive | 팀→부서, 부서→본부면 팀→본부 |
| R4 | MEMBER_OF ∘ SUB_ORG_OF → MEMBER_OF | 팀 소속이면 그 팀이 속한 상위 조직 소속이기도 하다 (속성 연쇄) |

---

## 1단계: 설계 검사 (OWL 2 DL 엔진 = HermiT)

**목적:** 규칙끼리 모순이 없는지 **데이터를 보기 전에** 확인한다.

누가 실수로 규칙을 하나 추가했다고 하자.
```
R5 (실수):  부서 ⊂ 회사
```

**HermiT 가 따져 보는 방식**
1. "부서인 개체가 하나 있다고 가정해 보자."
2. R1 에 따라 그 개체는 **조직단위**여야 한다.
3. R5 에 따라 그 개체는 **회사**여야 한다.
4. R2 에 따라 조직단위이면서 회사일 수는 없다. → **모순**
5. 결론: **"부서"라는 클래스는 존재할 수 없다** (성립 불가능한 클래스)

데이터가 하나도 없어도 이 오류를 찾는다. 규칙만 보고 "이 규칙대로라면 부서는 존재할 수 없다"를 증명하는 것이다.

**여러 온톨로지를 합칠 때 특히 중요한 이유**
- A 온톨로지: "고객사 ⊥ 회사"
- B 온톨로지: "고객사 ⊂ 회사"

각각은 멀쩡한데 **합치는 순간 모순**이다. 사람이 두 파일을 같이 보기 전에는 알아채기 어렵고, HermiT 는 바로 잡는다. 온톨로지를 여러 개 만들고 서로 import · 연결할수록 이 검사의 가치가 커진다.

**HermiT 가 주는 결과물:** 데이터를 바꾸지 않는다. "모순 있음/없음", "이 클래스는 성립 불가", 원인 공리 목록 같은 **판정**만 준다.

**HermiT 가 못 보는 것:** 규칙이 **빠진** 것. 배타 선언을 깜빡해도 모순이 아니라 통과한다. 그래서 "이건 반드시 모순이어야 한다"는 틀린 예시(픽스처)를 같이 돌려 보완한다.

---

## 2단계: 데이터 검사 (SHACL)

추론 전에 원본 데이터가 규칙에 맞는지 본다. 필수 칸, 어휘, "상위 조직은 하나" 같은 것이다.

**추론보다 먼저 하는 이유:** 틀린 데이터가 추론에 들어가면 틀린 사실이 **불어난다.** 또 추론이 타입을 붙여 주면(예: range 추론으로 "발주처 자리에 온 회사"가 발주처 타입을 얻음) 잘못된 도착 라벨이 검사를 통과해 버린다.

---

## 3단계: 운영 추론 (OWL 2 RL 엔진 = owlrl, Jena, GraphDB 등)

**목적:** 규칙으로 도출되는 사실을 **데이터에 실제로 써 넣어서** 조회할 수 있게 한다.

**RL 엔진의 방식: 규칙을 돌리고, 새 사실이 안 나올 때까지 반복**

| 회차 | 적용한 규칙 | 새로 생긴 사실 |
|---|---|---|
| 1회차 | R3 (팀T→부서D, 부서D→본부H) | `팀T SUB_ORG_OF 본부H` |
| 1회차 | R4 (E1→팀T, 팀T→부서D) | `직원E1 MEMBER_OF 부서D` |
| 2회차 | R4 (E1→부서D, 부서D→본부H) | `직원E1 MEMBER_OF 본부H` |
| 3회차 | — | 새 사실 없음 → **종료** |

결과적으로 저장소에는 이렇게 남는다.
```
직원E1  MEMBER_OF   팀T      (원래 있던 사실)
직원E1  MEMBER_OF   부서D    ← 추론
직원E1  MEMBER_OF   본부H    ← 추론
팀T     SUB_ORG_OF  본부H    ← 추론
```

---

## 4단계: 조회 (SPARQL)

"본부H 에 속한 직원 전부"를 찾고 싶다면:

| | 질의 |
|---|---|
| 추론 없이 | 조직 계층을 거슬러 올라가는 경로 질의를 직접 써야 한다. 질의마다 계층 규칙을 반복해서 넣어야 한다 |
| 추론 후 | `?직원 MEMBER_OF 본부H` 한 줄이면 된다 |

**규칙이 질의가 아니라 온톨로지에 한 번만 있다**는 게 핵심이다. 질의하는 사람(또는 LLM)이 계층 구조를 몰라도 된다.

---

## 5단계: 왜 "운영 규칙은 RL 범위로" 써야 하나

규칙을 이렇게 바꿨다고 하자.
```
R6: MEMBER_OF 의 도착은 "팀 또는 회사"   (합집합)
데이터: 직원E2 MEMBER_OF X,  X 는 회사가 아님
```

| 엔진 | 결론 |
|---|---|
| HermiT (DL) | X 는 팀 아니면 회사인데 회사가 아니니 → **X 는 팀** |
| owlrl (RL) | "또는"을 규칙 반복으로 처리할 수 없어서 → **결론 없음, 경고도 없음** |

그러면 이런 일이 생긴다.
1. 설계 검사(HermiT)는 **통과**한다.
2. 개발자는 "X 는 팀으로 추론되겠지"라고 기대한다.
3. 운영(owlrl)에서는 X 에 팀 타입이 **붙지 않는다.**
4. "모든 팀 목록" 조회에서 X 가 **조용히 빠진다.**

그래서 CI 에 **RL 범위 검사**(`robot validate-profile --profile RL`)를 같이 둔다.

**RL 범위에서 안 되는 주요 표현과 대안**

| RL 에서 안 되는 표현 | 대안 |
|---|---|
| domain/range 에 "A 또는 B" | 공통 상위 클래스를 만든다 (A, B ⊂ 조직) → range 는 "조직" 하나. "또는" 검사는 SHACL `sh:or` |
| "모든 팀은 팀장이 **최소 1명** 있다" | 데이터 검사이므로 SHACL `minCount` 로 넘긴다 |
| "최대 2개" 같은 숫자 제약 | SHACL `maxCount` 로 넘긴다 |

---

## 전체 흐름

```
① 온톨로지 작성 (OWL)
      │
      ├─ [CI] HermiT 설계 검사 ──── 모순·성립 불가 클래스 → PR 실패 + 원인 표시
      ├─ [CI] RL 범위 검사 ──────── RL 밖 표현 → 운영에서 무시될 규칙 경고
      ▼
② 데이터 적재
      │
      ├─ SHACL 데이터 검사 ──────── 필수 칸·어휘·카디널리티 위반 → 적재 중단
      ▼
③ RL 엔진 운영 추론 ─────────────── 추론된 트리플을 저장소에 기록
      ▼
④ SPARQL 조회 ──────────────────── 추론 결과까지 한 줄 질의로
```

| 단계 | 도구 | 언제 | 대상 | 결과 |
|---|---|---|---|---|
| 설계 검사 | HermiT (DL) | 온톨로지 수정 시 | 규칙 | 판정 (모순 여부, 원인) |
| RL 범위 검사 | ROBOT | 온톨로지 수정 시 | 규칙 | RL 밖 표현 목록 |
| 데이터 검사 | SHACL | 적재할 때마다 (추론 전) | 데이터 | 위반 목록 |
| 운영 추론 | RL 엔진 | 적재 후 | 규칙 + 데이터 | 새 트리플 |

# OWL 이 데이터 검사에 맞지 않는 이유

## 열린 세계 — "없는 값"은 오류가 아니다

OWL 은 **열린 세계 가정**을 쓴다. 데이터에 이름이 없으면 "이름이 없다"가 아니라 "이름을 아직 모른다"로 본다. 그래서 필수 칸 누락 · 어휘 위반을 오류로 잡지 않는다. 이건 SHACL 몫이다.

## 이름이 달라도 같은 대상일 수 있다 — 합치기

**OWL 은 "이름이 다르면 다른 대상"이라고 가정하지 않는다.** 같은 대상을 이름 둘로 부르는 것일 수도 있다고 본다.

1. 규칙: "상위 조직은 하나뿐" (Functional)
2. 데이터: 조직X 의 상위가 `조직A` 이기도 하고 `조직B` 이기도 하다
3. 사람의 결론: 오류
4. OWL 엔진의 결론: 하나뿐이라 했으니 **A 와 B 는 같은 조직**. 모순 없음

- 합치기는 **"하나뿐" 규칙 + 그 자리에 다른 이름 둘**일 때만 생긴다. 직원이 여러 팀에 소속되는 것(MEMBER_OF, n:m)으로는 안 생긴다 — 같은 클래스에 속하거나 각자 다른 팀에 있다는 것만으로 합치지 않는다
- 두 상위가 "서로 다르다"고 선언되어 있으면 그때서야 모순으로 잡는다. 그렇다고 **모든 개체 쌍에 "서로 다르다"를 선언**하면 쌍 수가 개체 수의 제곱으로 늘어 추론기 메모리가 버티지 못한다 — 쓸 수 없는 우회로다
- RL 엔진은 "A 와 B 는 같다"(sameAs)를 **데이터에 실제로 써 넣는다** → 한 부서의 팀 목록에 다른 부서 팀이 섞이는 식으로 질의 결과가 바뀐다

그래서 **"하나뿐"은 OWL Functional 이 아니라 SHACL maxCount 로** 지킨다. 틀린 데이터를 합치는 대신 오류로 막는다.

## 조직도 설계 — 조직은 n:1, 소속은 n:m

| 관계 | 규칙 | 뜻 |
|---|---|---|
| MEMBER_OF (직원 → 팀) | n:m | 직원은 두 팀 이상 소속 가능 (겸직) |
| SUB_ORG_OF (팀 → 상위 조직) | n:1 | 상위는 하나뿐. 조직도는 트리 |

- 현실에 매트릭스 조직 · 공동 운영 TF 가 있어도 SUB_ORG_OF 를 n:m 으로 풀지 않는다. 트리가 깨지면 "최상위 부서"가 둘이 되고 인원 집계가 중복된다
- 이중 소속은 사람 단위(MEMBER_OF)로 표현하고, 조직 간 협력이 정말 필요하면 별도 관계(예: `CO_MANAGED_BY`)를 추가한다
- SHACL 로 같이 걸 것: 상위 하나(`maxCount 1`), 상위 없는 조직 금지(`minCount 1`), 순환 금지(SHACL-SPARQL — 기본 SHACL 로는 표현이 어렵다)

# 선택과 이유

| 결정 | 택한 것 | 이유 |
|---|---|---|
| 설계 검사 | **HermiT** (ROBOT Docker, CI) | 설계 모순을 데이터 없이 증명하고 원인 공리까지 준다. 온톨로지가 여러 개로 늘수록 가치가 커진다 |
| 데이터 검사 | **SHACL** | 데이터 오류는 대부분 필수 칸 · 어휘 · 카디널리티이고 이건 SHACL 만 잡는다. 개체 · 칸 · 규칙별 목록을 준다 |
| 운영 추론 | **RL 엔진** (Jena · owlrl 등) | 추론 결과를 저장해 SPARQL 로 조회. 운영 규칙은 RL 범위로 쓴다 |
| HermiT 실행 방식 | **Docker 일회성 컨테이너** (`--network none`) | PC · CI 에 Java 설치 없이 돈다. 서버가 아니라 실행 후 종료하는 도구 |
| 온톨로지 정본 | **JSON 유지, OWL · SHACL 은 생성** | Neo4j 와 병행하는 동안 정본을 하나로 둔다. 생성 OWL 은 손으로 고치지 않는다. RDF 로 완전히 넘어가면 `.ttl` 정본 전환을 다시 본다 |
| Protégé | **로컬 보기 · 검사 전용** | 데스크톱판은 zip 에 Java 포함, 설치 불필요. 서버형(WebProtégé)은 MongoDB 까지 필요하고 편집 협업용이라 "평소에 보기"엔 과하다. 평소 보기는 pyLODE 같은 정적 HTML 생성이 가볍다 |

## CI 에 둘 것 (온톨로지가 바뀔 때)
