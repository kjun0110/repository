## 개념

지식그래프에서 관계를 **몇 홉까지 순회할지는 전역 상수 하나로 정할 게 아니라, 관계의 의미(사실형/계층형/체인형)에 따라 다르게 정해야 한다.** 홉 수 자체보다 "몇 홉이든 얼마나 잘 걸러서 LLM에 주느냐"가 답변 품질을 더 좌우한다.

---

## 관계 유형별 홉 정책

### 1. 사실형 관계 — 1홉 고정

대상 하나에 사실 하나가 매달린 원자적(atomic) 관계 (예: 소속, 담당자, 근거). 1홉을 넘어가면 관련 없는 잡음(그 대상의 상위 개체, 그 값을 공유하는 다른 개체 등)이 컨텍스트에 섞여 들어가 정답률이 오히려 떨어진다. 이런 관계는 **의도적으로** 1홉 고정이어야 한다.

### 2. 계층형 관계 — 가변 길이 + 상한

조직도·분류 체계처럼 깊이가 있는 관계. 상한은 임의로 정하지 않고 **실제 계층 깊이**(도메인마다 다르지만 보통 3~5단계)에 맞춰 잡는다. 무제한 순회는 데이터에 순환 참조 같은 이상치가 있을 때 쿼리가 폭주할 위험이 있어 피한다.

### 3. 체인형 관계 — 기본 2홉 + 제어 장치

선행/후행, 다음 단계처럼 순서가 있는 관계. 1홉만 순회하면 "다음 단계가 뭐야?" 같은 질문엔 답할 수 있어도 "전체 절차가 뭐야?" 같은 질문엔 실패한다 — 두 번째 이후 단계가 애초에 조회 범위 밖이기 때문.

**방향**: 무작정 홉 수를 키우는 게 정답은 아니다. 대부분의 절차형 체인은 실제 길이가 짧기 때문에 **기본값 2홉**만으로도 대부분 커버되고, 더 긴 체인이 필요한 경우엔 반드시 제어 장치를 같이 걸어야 한다.

- **홉 수 상한**: 실측 최대 단계 수보다 여유 있게 캡을 둔다. 무제한 순회는 이상치에서 쿼리 폭주 위험이 있음
- **관계 타입 필터링**: 순회 중 해당 체인 관계만 따라가고 다른 관계로 새지 않도록 고정
- **경로당 노드 수 상한**: 체인이 예외적으로 길어지는 경우를 대비해 각 경로에서 가져오는 노드 수를 top-k로 자름
- **동적 홉 결정(query routing)**: 질의를 먼저 "1홉이면 충분한 질문"과 "체인 전체가 필요한 질문"으로 분류해서 홉 수를 질의마다 다르게 주는 게, 모든 질의에 정적으로 N홉을 열어두는 것보다 낫다

## 관계 타입 분류는 그래프 데이터가 아니라 설계 규칙

관계 "이름"은 자유롭게 지어도 되지만, 그 관계가 사실형/계층형/체인형 중 어디에 속하는지는 정확히 분류돼야 한다. 잘못 분류하면 바로 문제가 생긴다.

- 체인형인데 사실형으로 착각 → 1홉만 파서 절차 후반부가 통째로 누락
- 사실형인데 계층형/체인형으로 착각 → 불필요하게 깊이 파고들어 노이즈 유입, 홉 폭발 위험

**이 분류를 그래프 안에 타입 노드로 만들 필요는 없다.** 이유는 노드 타입 계층(클래스+서브클래스)을 그래프에 넣는 이유와 정반대다.

- 노드 타입 계층을 그래프 데이터로 두는 이유: 새 종류가 운영 중에 계속 늘어나야 하고, 코드 수정 없이 데이터만 추가해 확장하기 위해서다.
- 관계 타입 분류는 성격이 다르다: 관계 타입 개수는 스키마를 설계할 때 정해지고, 운영 중에 데이터가 늘어난다고 관계 타입 자체가 늘어나진 않는다 (새 인스턴스만 늘어남).
- 그래프DB는 애초에 관계 "타입"에 공용 메타데이터를 붙이는 기능이 구조적으로 없다. 이를 억지로 노드화(reification)하려면 관계마다 별도의 타입 노드를 만들고 실제 관계와 다시 연결해야 하는데, 이건 조회할 때마다 홉이 하나 더 늘어나는 대가를 치르는 것이라 "불필요한 홉은 줄인다"는 원칙과 정면으로 배치된다.

**그래서 실무적으로는** 관계 이름 → 카테고리 매핑은 코드(설계 계층)에 고정된 정책 테이블로 관리하는 걸로 충분하다:

```
사실형 관계 (예: 소속, 담당자, 근거)   →  1홉 고정
계층형 관계 (예: 상하위 분류)          →  가변 길이 + 상한
체인형 관계 (예: 선행/후행, 절차 순서)  →  가변 길이, 끝까지
```

"조직 종류(클래스)는 데이터로 확장, 관계 정책은 설계 규칙"이라는 구분과 같은 원칙이다.

## 복합조건/추론형 질의는 홉 수 하나로 안 끝남

"전체 절차와 각 단계별 필요조건을 다 알려줘" 같은 복합조건 질의는 홉 수를 늘리는 문제가 아니라 **두 패턴을 합성하는 문제**다.

1. 체인 관계를 가변 길이로 먼저 끝까지 펼치고
2. 그 체인 위의 **각 노드마다** 사실형 관계(1홉)를 다시 붙인다

즉 "체인 순회(가변 길이) + 체인 각 지점에서 사실 확장(1홉)"의 조합이지, "전부 N홉으로 확장"이 아니다. 시작 노드 하나에서만 1홉을 뽑는 방식으로는 체인 중간/끝 노드에 딸린 정보는 원천적으로 조회 범위 밖에 남는다.

## 실무 홉 수 기준 (일반론)

보통 **1~2홉이 실무 기본값**이고, 3홉 이상은 특별한 이유가 있을 때만 쓴다.

### 왜 1~2홉이 기본인가

**노드 수가 홉마다 기하급수적으로 늘어난다.** 시드 노드 하나가 평균 연결도(degree) 10인 그래프라면:

```
1홉: 노드 10개
2홉: 최대 100개
3홉: 최대 1000개
```

실제 그래프는 이렇게 딱 떨어지진 않지만, **허브 노드**(연결이 아주 많은 노드 — 예: 범용 개체)를 한 번 거치면 3홉째에 사실상 그래프 전체가 딸려오는 **"홉 폭발(hop explosion)"** 현상이 흔하다.

**LLM 컨텍스트 윈도우 한계.** 홉이 늘어날수록 딸려오는 관계/노드 텍스트가 늘어나서, 정작 질문과 무관한 정보까지 채워 넣게 된다 → **"lost in the middle"**(컨텍스트 중간에 묻힌 정보를 LLM이 놓치는 현상)로 답변 품질이 오히려 떨어진다.

### 홉 수별 용도

| 홉 수 | 용도 |
|---|---|
| 1홉 | 단순 사실 질의 ("A의 소속은?", "B의 담당자는?") — 대부분의 질의가 여기서 커버됨 |
| 2홉 | 관계형 추론 필요 ("A와 B는 어떻게 연결돼 있나?", "A의 상사의 소속 부서는?") — 하이브리드 RAG 기본값으로 가장 많이 씀 |
| 3홉 이상 | 명시적 multi-hop 추론이 필요할 때만 (예: 공급망 추적, 조직도 다단계 탐색) — 반드시 아래 제어 장치를 같이 걸어야 함 |

### 3홉 이상 갈 때 반드시 같이 거는 제어

- **연결도 상한(degree cap)**: 허브 노드는 확장 대상에서 제외하거나 상위 N개 관계만 채택
- **관계 타입 필터링**: 질의와 관련 없는 관계 타입은 애초에 순회 대상에서 제외 (예: A 관계만 필요한데 B 관계까지 따라가지 않도록)
- **경로당 노드 수 상한**: 각 확장 경로에서 가져오는 최종 노드 수를 top-k로 자름 (예: 관련도 스코어 기준 상위 20개)
- **동적 홉 결정(query routing)**: 질의 유형을 먼저 분류해서("이건 1홉이면 충분", "이건 multi-hop 필요") 홉 수를 질의마다 다르게 주는 방식이 정적으로 고정하는 것보다 낫다

### 결론

기본값은 **2홉**으로 잡고, 확장된 노드/관계를 그대로 다 넣지 말고 **관련도 기준 top-k 필터링**을 거쳐 LLM에 넘기는 게 실무 표준이다. 홉 수 자체보다 **"몇 홉이든 얼마나 잘 걸러서 주느냐"**가 실제 답변 품질을 더 좌우한다.

## 비교표

| 관계 유형 | 정의 | 홉 정책 | 이유 |
|---|---|---|---|
| 사실형 | 대상 하나에 매달린 원자적 사실 | 1홉 고정 | 넘으면 잡음 유입 |
| 계층형 | 상하위 구조가 있는 분류 관계 | 가변 길이 + 상한 | 실제 계층 깊이만큼만 필요 |
| 체인형 | 순서(선행/후행)가 있는 관계 | 기본 2홉, 필요시 가변 길이 + 제어 장치 | 체인 전체를 물을 수도 있지만 무제한은 위험 |

## 한 눈에 요약

```
사실형 관계 (담당조직/서류/법령)  →  1홉 고정 (넘으면 노이즈)
계층형 관계 (조직도/클래스 계층)  →  가변 길이 + 상한 (실측 깊이 기준 4~5)
체인형 관계 (절차 순서 PRECEDES) →  현재 1홉(한계) → 기본 2홉 + 제어 장치 필요 (미적용, 검토 예정)

복합조건 질의        →  체인 순회(가변) + 각 노드 1홉 사실 확장의 "조합"
실무 홉 수 기준         →  1~2홉이 기본값, 3홉 이상은 이유 있을 때만 + 반드시 제어 장치
홉 폭발(hop explosion)  →  허브 노드 경유 시 3홉째부터 그래프 전체가 딸려올 수 있음
컨텍스트 품질          →  홉 수보다 "얼마나 잘 걸러서(top-k) LLM에 주느냐"가 더 중요
관계 타입 분류 위치      →  그래프 데이터(노드) 아님, 코드/설계 계층의 정책 테이블로 충분
```
