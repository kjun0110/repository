## 개념

- **적재 액션(ingest action)** — 데이터를 그래프에 넣는 순간 온톨로지가 개입해서 하는 일. 넣기 전에 따져 묻고, 넣으면서 없던 사실을 만들어낸다
- **TBox** — 클래스·관계·규칙의 선언. "무엇이 무엇인가". 데이터가 아니라 스키마 쪽 ([[Ontology - T-BOX]])
- **ABox** — 실제 노드·관계 인스턴스. "이 노드가 그 무엇이다"
- **신호 3층** — 페이지가 무슨 개체인지 판정할 때 쓰는 근거의 층. 1층 사이트 자체 분류 / 2층 HTML 구조 / 3층 문장 의미. 위층일수록 싸고 확실하다
- **게이트(gate)** — 조건을 못 채운 데이터를 적재 단계에서 걸러내는 행동
- **일관성(consistency)** — 서로 동시에 참일 수 없는 사실이 함께 들어오는 것을 막는 행동
- **자기모순 검사** — LLM이 내린 판정과 LLM이 뽑아낸 내용이 서로 어긋나는지 보는 것
- **보류함(quarantine)** — 판정 실패를 어느 한쪽으로 밀어 넣지 않고 "판정 못 함" 그대로 남기는 자리
- **물질화(materialize)** — 추론으로 얻은 관계를 질의 때마다 계산하지 않고 적재 시점에 실제 엣지로 써 두는 것

##### 이 문서가 다루는 범위

적재가 **어떻게 도는가**만 담는다. 갈라져 나간 두 문서가 있다.

- [[KG - 온톨로지 선언 파일 (TBox)]] — 규칙을 선언 파일로 빼는 방식, 새 클래스를 언제 늘리는지
- [[KG - 원천별 적재 (크롤링 vs pgvector)]] — 원천을 크롤링으로 할지 pgvector로 할지

## 핵심 한 줄

**온톨로지는 LLM을 대체하는 것이 아니라 LLM의 답을 검사한다.**

문장을 읽어야만 아는 판정은 LLM이 해야 하고 뺄 수 없다. 온톨로지가 하는 일은 두 가지다 — 위층 신호로 LLM 호출을 줄이는 것, 그리고 LLM이 낸 답이 자기모순인지 확인하는 것.

## 지금 상태 — 선언 하나 + 파서 여섯

```
ontology/
  schema.yaml      ★ 선언 파일(TBox). 2026-09-02 신설
  schema.py        그 로더. 선언이 어긋나면 로딩 시점에 멈춘다
  classify.py      조직 이름 → unit_level   (override 25건 + 접미사 규칙)
  aliases.py       unit_level별 시민 통칭 별칭
  documents.py     서류명 정규화 + 발급처 판정
  fees.py          "3만원" → fee_min/fee_max
  regulations.py   법령명·조항 파싱
  inquiry.py       본문 "문의" 섹션 파싱
```

파서 여섯은 **문자열을 값으로 바꾸는 일**을 한다. 실측으로 다듬어진 좋은 코드지만, 온톨로지가 하는 일 — 무엇이 무엇인지 선언하고 그로부터 따져 묻는 것 — 은 여기 없었다.

**2026-09-02 에 `schema.yaml` 을 신설해 그 자리를 만들었다.** 코드 여러 곳에 리스트로 박혀 있던 것을 한 곳에 모았다.

```
org_classes             조직 부류 (총괄기관 7종 / 실무조직 10종)
bureau_levels           IN_CHARGE_BUREAU 가 가리킬 수 있는 레벨 7종
body_fallback_levels    본문에서 조직명을 찾을 때 후보로 삼을 레벨 6종
vocabulary              content_type · inquiry_labels · inquiry_end
classes                 Procedure/Reference 는 HANDLED_BY 가 있어야 한다
hierarchy.domain_depth  구역별 분야 계층 깊이
```

##### 선언과 그것이 만드는 라벨은 다르다

처음에 `org_classes` 선언이 `:총괄기관`·`:실무조직` **라벨까지** 만들게 했다가 라벨만 걷어냈다.

```
라벨을 읽는 곳   없음. 검색·라우터·검증 어디에서도 (o:실무조직) 을 안 씀
unit_level      같은 답을 내면서 "국만"·"구만"도 물을 수 있다. 인덱스도 있다
```

라벨은 7종을 하나로 뭉갠 **정보를 잃은 파생 뷰**였다. 게다가 적재기가 `SET` 만 하고 `REMOVE` 를 안 해서, 개편으로 과가 국이 되면 두 라벨이 함께 남는다 — **선언은 disjoint 를 강제하는데 적재가 그걸 안 지켰다.**

**선언 자체는 계속 일한다.** `schema.py:47` 이 그것을 unit_level 닫힌 어휘 대장으로 써서 `bureau_levels` 오타를 잡는다. 선언을 남기고 라벨만 없애는 것이 맞았다.

##### 그래도 남은 것

규칙이 "조심해서 지키는 것"인 자리가 아직 있다. `inquiry.py` 주석이 그 예다.

> 다른 행정주체(고용노동부·한국철도공사·경기도)는 연결하면 안 된다. "수원시가 담당한다"는 틀린 사실이 되기 때문.

`validate/00` 이 적재 전에 이걸 검사하게 만들어서 **조심하지 않아도 막히게** 했지만, Neo4j Community 는 Domain/Range·Disjoint 를 강제하지 못하므로 여전히 **적재기가 온톨로지를 집행하는 자리**다.

## A. 수용

##### A1. 원천 읽기
지금은 `scraping/00~01`이 직접 긁어 JSON으로 떨어뜨린다. pgvector로 가면 이 자리만 바뀌고 아래는 그대로다.

##### A2. 수용 게이트 — 받을지 말지

```
수원시 도메인인가              아니면 거부
title / text 가 있나          비었으면 거부
page_type이 매핑표에 있나      없으면 거부 + 로그
```

중요한 것은 마지막이다. **모르는 유형은 넣지 않는다.** 지금은 크롤러가 가져온 것을 전부 넣어서, 새 페이지 유형이 생기면 정체불명 노드가 조용히 쌓인다.

거부는 버리는 것이 아니라 **사유와 함께 기록**한다. "왜 이 페이지가 그래프에 없나"에 답할 수 있어야 한다.

##### A3. 동일성 — 있던 놈인가

```
정규화 URL로 조회
  ├ 없음               → new
  ├ 있음 + hash 같음   → unchanged   ★ 여기서 종료. B~F 전부 건너뜀
  └ 있음 + hash 다름   → changed
```

LLM이 C2에만 있으므로 unchanged면 LLM 비용이 0이다. 지금은 매번 전부 다시 추출한다. `content_hash`는 pgvector가 이미 만들어 둔 값이라 가져다 쓰기만 하면 된다.

## B. 판정 — 신호 3층

페이지가 무슨 개체가 되는지 판정할 때 근거가 세 층이다. **위층부터 써서 아래층 호출을 줄이는 것이 설계 원칙이다.**

##### 1층 — 사이트가 이미 붙여 놓은 분류 (규칙)

```
URL 경로         www01-04/*  → 민원안내 구역
                 deptHome/*  → 부서별 안내
breadcrumb       홈 > 복지 > 아동
cate_treecode    사이트 자체 트리
page_classifier  pgvector가 이미 돌린 분류기
```

내용 해석이 아니라 그냥 읽는 것이라 예외가 거의 없다.

##### 2층 — 구조만 보면 아는 것 (규칙)

```
담당자 footer 유무             복지 '생애주기별' 27건은 footer 없음(실측)
"구비서류"·"신청방법" 섹션 헤더 유무
표 유무 / 목록 유무
본문이 제목뿐인가              실측 37건
```

여기서 클래스가 확정되면 B2를 부르지 않는다.

##### 3층 — 문장을 읽어야만 아는 것 (LLM)

`procedure` / `reference` 구분이 정확히 여기다. 지금도 `scraping/02_extract_llm.py`의 추출 스키마 안에서 **LLM이 판정하고 있다.**

> 시민이 직접 신청/신고/납부하는 방법을 안내하면 procedure, 제도·용어·세율만 설명하거나 링크 모음이면 reference. 애매하면 본문에 민원인이 따라 할 동작이 있는지로 판단해라.

"따라 할 동작이 있느냐"는 규칙으로 못 잡는다. **LLM이 하는 것이 맞고 여기서 뺄 수 없다.**

##### B3. 판정 근거 기록

```
classified_by: "rule:url"        1층으로 갈림
               "rule:structure"  2층으로 갈림
               "llm"             LLM이 판정
               "override"        손으로 박음
```

나중에 "이 판정을 믿을 만한가"를 물을 수 있다. `llm`으로 판정된 것만 골라 검수하는 것도 가능해진다.

## D. 검사 — 온톨로지의 본진

##### D1. 요건 검증 — 클래스별 필수 항목

| content_type | 전체 | 담당부서 없음 | 구비서류 없음 | 절차 없음 |
|---|---|---|---|---|
| procedure | 263 | 5 | 77 | 51 |
| reference | 381 | 8 | 372 | 375 |

`reference`가 구비서류·절차 없는 것은 **정상**이다(381개 중 372·375). 클래스별로 필수 항목이 다르다는 것을 아는 것이 온톨로지의 일이다.

미달이면 **`:Violation` 마커만 붙이고 적재는 한다.** 버리면 "왜 이게 검색에 안 나오나"를 추적할 수 없다.

##### D2. 자기모순 검사 — LLM이 자기 말과 어긋났나

```
LLM: procedure다   →  절차 없음  →  모순. 강등하거나 재질의
LLM: reference다   →  절차 없음  →  정상
```

실측 `procedure` 263건 중 **51건이 절차가 없다.** LLM이 "이건 절차 안내다"라고 판정해 놓고 절차를 못 뽑은 것이다. 지금은 그냥 통과한다. 온톨로지가 있으면 **LLM의 자기모순이 자동으로 목록이 된다.**

이것이 D1과 다른 점: D1은 "데이터가 불완전한가", D2는 "판정과 내용이 어긋나는가"다.

##### D3. 일관성 검사 — 동시에 참일 수 없는 것

```
external_org가 있는데 수원시 OrgUnit에 HANDLED_BY 연결됨   → 거부
Procedure와 Reference가 동시에 붙음                       → 거부
```

D1·D2와 다른 점: **D1·D2는 불완전(마커만 붙임), D3는 틀림(적재 안 함).**

##### D4. 관계 Range·방향 — 2026-09-02 추가

D1~D3 은 노드 하나를 본다. 관계가 **어디를 가리키는가**는 안 봤다.

```
DEPT_NOT_BODY       민원의 담당부서는 실무조직이어야 한다      마커
                    도입 시점 위반 0/700
                    (과 608 · 단 46 · 팀 18 · 직속기관 12 · 시설 9 · 관 6 · 사업소 1)

PART_OF_DIRECTION   총괄기관은 실무조직 밑에 오지 않는다       중단
                    도입 시점 위반 0/938
```

깨지면 무엇이 나쁜가.

```
Range     "출생신고 어디서 해?" -> "시민복지국이 담당합니다"
          국은 결재 라인이지 창구가 아니라서 답이 되지 못한다

방향      IN_CHARGE_BUREAU 는 PART_OF*0..5 로 가장 가까운 총괄 조상을 찾는다.
          나무가 한 군데 뒤집히면 583건이 한꺼번에 엉뚱한 국을 가리키는데
          답이 그럴듯해서 아무도 알아채지 못한다
```

**0건일 때 넣는 것이 요점이다.** 나중에 넣으면 이미 쌓인 위반이 무더기로 떠서 진짜 새 위반이 그 안에 묻힌다.

방향 규칙만 중단인 이유는 이것이 데이터 품질이 아니라 **구조 파손**이기 때문이다. `main.py` 순서상 `validate/01`(76) → `relationships/05`(77) → `embedding/01`(79) 이라 **추론과 임베딩 전에 멈춘다.**

##### 한 번도 안 걸려 본 규칙은 일부러 깨뜨려 봐야 한다

위반 0인 규칙은 쿼리가 틀렸어도 0을 낸다. 이 프로젝트는 도메인 검증 쿼리가 틀렸던 적이 이미 있다. 시험용 노드를 매달아 보니(국을 과 밑에) 둘 다 잡혔고, 치우니 0으로 복귀했다.

## E. 적재

##### E1. MERGE
클래스별 identity 키로. 지금 `Place.place_id`·`WasteItem.item_key`는 유일 제약이 없어서 키가 어긋나면 노드가 하나 더 생기고 아무도 모른다.

```
source: 'pgvector' | 'crawl:org' | 'crawl:civil'
last_seen: batch_id
```
F5의 전제다.

## F. 파생 — 적재가 다 끝난 뒤

##### F1. 추론 물질화 — 2026-09-01 구현됨

```
IN_CHARGE_BUREAU : HANDLED_BY / PART_OF*     583개   민원 644건 중 583건
VISIT_FOR        : REQUIRES / ISSUED_AT      266개   민원 88건
```

E 다음이어야 한다. 원천 관계가 다 있어야 합성이 된다. 전이 관계(`PART_OF`, `IMPLEMENTS`)는 물질화하지 말고 질의 때 가변 길이로 푸는 것이 낫다 — 물질화하면 엣지가 폭증하고 조직 개편마다 재계산해야 한다. 홉 정책은 [[KG - 홉 탐색 전략 (Hop Depth Strategy)]]의 분류를 그대로 따른다.

소관은 시장·부시장을 제외한 총괄 단위 중 **가장 가까운 조상 하나**만 남긴다. 넣으면 모든 민원이 거기로 올라가 답이 되지 못한다(실측: 거리 3에서 시장 562건).

##### 역관계는 만들지 않는다

계획에는 `HANDLES`(= `HANDLED_BY`의 역)가 있었으나 취소했다. **Neo4j는 관계를 역방향으로 그냥 탈 수 있어서 역관계를 만들면 엣지만 두 배가 된다.** RDF에서는 역속성 선언이 필요하지만 LPG에서는 아니다 ([[Graph DB - 2가지 비교 (RDF, LPG)]]).

##### 대체(alternative) 관계는 속성이 아니라 구조다 — 실패 두 번

`VISIT_FOR`를 만들면서 "이 중 아무 데나"를 어디에 표현할지 세 번 시도했다.

```
1차  발급처를 그냥 쪼갬
     → "출산 전 지원 = 8곳". 동 행정복지센터·무인민원발급기·정부24를
        셋 다 가라로 읽는다

2차  ISSUED_AT 에 alt_group 속성을 실음
     → '동 행정복지센터'가 두 값에 걸쳐 나와 그룹 2개에 동시에 속하는데
        엣지 하나에 그룹 하나만 실려 덮어써진다

3차  대체 관계가 붙을 자리는 발급처가 아니라 서류
     → issued_at 은 DocumentType 의 단일 속성이므로 한 서류의 ISSUED_AT
        대상들은 언제나 같은 값에서 나온다. 즉 구조적으로 이미 서로 대체다.
        속성을 붙일 필요가 없다
```

**속성으로 표현하려던 것을 구조가 이미 갖고 있었다.** 추론 관계를 설계할 때 "이 제약이 붙을 자리가 정말 여기인가"를 먼저 물어야 한다.

##### F2. 계층 구축

```
"홈 > 복지 > 아동·청소년 > 보육"
  → (:Domain{복지})-[:PARENT_OF]->(:Domain{아동·청소년})-[:PARENT_OF]->(:Domain{보육})
```

지금 `domain` 12종이 문자열 속성이라 "복지 분야 전부"는 되지만 "복지 > 아동" 하위 분류는 표현할 수 없다. breadcrumb과 `cate_treecode`에 계층이 들어 있는데 적재 때 버려진다.

##### F3. 속성 상속
주소 상속·`peer_count` — 이미 `nodes/09_org_address.py`가 한다.

##### F4. 임베딩
A3에서 걸러진 **변경분만.**

##### F5. 생애주기 — 전략이 하나가 아니라 넷이다

"추적하는 라벨이 3종뿐이고 나머지 34%는 방치"라고 봤으나 **틀린 진단이었다**(2026-09-01 실측).

| 전략 | 라벨 | 방식 |
|---|---|---|
| 시간축 | OrgUnit · Employee · CivilService | MERGE + `last_seen`/`status`, 이력 보존 |
| 전량 교체 | Place · WasteItem · Issuer | `DETACH DELETE` 후 재생성 |
| 고아 정리 | Regulation | 부모 관계 없으면 삭제 |
| 부모 종속 | DocumentType · Channel · TargetGroup | 삭제하지 않음 |

Place 2,509개는 추적 밖이 아니라 매번 통째로 다시 만들어져서 `last_seen`이 필요 없었다. **순수 파생물에는 타당한 설계다.**

##### `source`는 단일 원천이면 아무 일도 하지 않는다

```cypher
WHERE c.source = $source AND c.last_seen <> $batch AND c.status = 'active'
```

크롤링만 쓰기로 하면 값이 하나뿐이라 만들 이유가 없다. 그래서 넣지 않았다(2026-09-01 결정).

pgvector 적재를 결정하면 **넣기 전에 반드시 필요하다.** 조건이 없으면 pgvector 데이터를 넣은 뒤 크롤링만 돌렸을 때 pgvector 노드가 전부 폐지된다. 더 나쁜 것은 `DETACH DELETE`를 쓰는 라벨들로, 그쪽은 표시가 아니라 **복구 불가능한 삭제**다.

## 페이지 하나가 가질 수 있는 상태

```
rejected       A2에서 거부. 사유 기록
unchanged      A3. 아무것도 안 함
quarantined    B에서 판정 못 함. 보류함
violation      D1·D2 미달. 적재는 됨, 마커 붙음
inconsistent   D3 모순. 적재 안 함
loaded         정상
```

**적재 리포트가 이 6개 숫자다.** 그것이 곧 데이터 품질 대시보드이고, 데모에서 "온톨로지가 무엇을 잡아냈나"를 보여줄 화면이다.

## 데모 시나리오 3장면

##### 1. 선언 한 줄로 새 소스 붙이기
새 `page_type` 하나를 routing 표에 추가 → 코드 수정 0줄로 적재.

##### 2. 온톨로지가 잡아낸 것
적재 리포트의 6개 상태 숫자. "procedure인데 절차 없음 51건 / 외부소관 모순 N건". 사람이 검수한 목록이 아니라 **선언에서 자동으로 나온 목록.**

##### 3. 아무도 안 넣은 답
"확정일자 받으려면 어디어디 가야 해?" → 민원 → 서류 → 발급처 합성 추론. 그 관계는 저장된 적이 없다.

## 아직 안 정한 것

- **pgvector에 실제로 무엇이 들어 있는지 안 봤다** — 코드(`edu/url_edus`)만 봤다. 건수, 필드 값, breadcrumb이 실제로 채워져 있는지 미확인. A2·B·F2는 이것을 봐야 설계할 수 있다
- **pgvector 임베딩을 재사용할 수 있나** — 거기는 페이지 청크 단위, 여기는 직원·민원 단위 `embedding_text`. 모델·차원도 다를 수 있다. 못 쓰면 F4는 지금처럼 새로 계산
- **조직도·직원이 pgvector에 있나, 있어도 표 구조가 살아 있나** — 페이지를 텍스트로 평탄화해 저장했다면 담당업무 칸 구조가 이미 날아간 상태다(`<br>` 유실 사고와 같은 기제). 그러면 조직도만큼은 직접 크롤링해야 한다
- **선언 형식** — YAML인지 OWL/Protégé인지. OWL로 가면 추론기를 그대로 쓸 수 있지만 Neo4j로 옮길 때 손실이 있다 ([[RDF - 트리플과 추론, Neo4j 이관 시 손실]])
- **`:Violation` 노드가 검색에 섞이지 않게 하는 법** — 지금 벡터 인덱스가 `:Entity` 라벨 전체를 본다
- **`직속기관`을 총괄기관으로 볼지 실무조직으로 볼지**
