## 개념

- **온톨로지 액션** — 데이터가 그래프로 들어갈 때 그래프가 개입해서 하는 일. 게이트·라우팅·검사·추론·계층·전파 여섯
- **선언(TBox)** — "무엇이 무엇인가"를 적어 둔 것. `ontology/schema.yaml` 한 곳
- **집행** — 그 선언을 읽어 실제로 막거나 만드는 것. 각 파이썬 단계가 한다
- **`:Entity`** — 벡터 검색 후보를 가리키는 라벨. 이게 없으면 검색에 안 섞인다
- **자리 보장** — 점수 경쟁에 넣지 않고 후보 한 자리를 확보해 주는 것. 척도가 다른 검색을 섞을 때 쓴다
- **신호 3층** — 사이트 자체 분류(URL·breadcrumb) / HTML 구조 / 문장 의미(LLM)

##### 이 문서가 다루는 범위

2026-09-04 기준 **실제로 돌아가는 것**만 적는다. 설계안·계획은 [[KG - 온톨로지 데이터 투입 액션]]에 있고, 여기는 "지금 이렇게 돈다"의 기록이다.

## 핵심 한 줄

**비싸고 실행마다 흔들리는 판단(LLM)은 적재 때 한 번만 하고, 검색은 그 결과를 읽기만 한다.**

그래야 질문마다 비용이 안 붙고, 돌릴 때마다 그래프 모양이 달라지지 않는다.

```
LLM 을 쓰는 곳    수집 5회 (배치, 644건에 한 번)
                답변 합성 1회 (질문당)
LLM 을 안 쓰는 곳  적재 30단계 · 검증 6종 · 구조 라우터
```

##### 1-1. HTML 긁기 — LLM 없음

구조가 확실한 것만 규칙으로 뽑는다.

```
<th>담당부서</th><td>혁신민원과</td>       -> dept
<th>전화번호</th><td>031-5191-2000</td>   -> phone
<div id="contents"> … </div>             -> content (본문 통째)
HOME > 종합민원 > 민원안내 > 인감증명발급    -> breadcrumb
```

구비서류·절차·법령은 여기서 안 뽑는다. 페이지마다 `<h4>+<ul>`, `<li>+<table>` 로 표현이 갈려서 **정규식으로 안 된다**(20페이지 안에서만 최소 2가지 패턴).

원본 HTML 은 `data/raw/civil_service/html/` 에 보존한다. 재수집 없이 파싱만 다시 돌려볼 수 있게, 그리고 사이트가 바뀌었을 때 비교 근거로.

##### 1-2. 게시판은 성격이 다르다 — LLM 0회

열을 **위치가 아니라 이름(`thead th`)으로** 읽는다. 게시판마다 열 구성이 달라서 위치로 읽으면 틀린 칸을 집는다(실제로 두 번 틀렸다).

```
1042 시정소식    번호·제목·작성자명·담당부서·등록일·조회
1275 옥외광고물   번호·제목·첨부파일·담당부서·조회        <- 등록일이 없다
```

기준일도 게시판마다 다르다.

```
소식류 (1042·1043·1044·1254·1279)   1년치    작년 행사 공지는 답이 안 된다
서식류 (1026·1298·1275)             전량     서식은 2018년 것도 지금 쓰는 서식
```

이 성격을 `Board.timeless` 로 노드에 싣는다. **한때 검색의 기간 제한이 이 값을 읽었는데, 09-04 에 `article_type` 으로 축을 바꿨다**(2-4·3-7) — 서식 게시판을 빼야 하는 이유가 "오래돼서"가 아니라 "첨부 블록이 이미 그 자리를 담당해서"였기 때문이다. `timeless` 는 최근 소식 조회(`recent_news` 의 180일 제한)에서 계속 쓴다.

##### 1-2b. 본문을 받는다 (2026-09-03 에 뒤집힘)

**09-02 까지는 본문을 아예 안 받았다.** 근거는 이랬다 — 게시글은 관계가 `(글)-(담당부서)` 하나뿐이라 벡터에 넣으면 주제가 제각각인 글이 후보에 섞여 민원·조직을 밀어낸다. 그래서 그래프만 할 수 있는 것(부서별·기간별 구조 질의, 첨부 파일명)만 가져왔다.

**밀어내는 현상 자체는 사실이었다.** 전량을 넣어 재 보니 후보 자리를 서식 게시판이 11자리 먹고 정답을 0건 냈다. 그런데 그것은 **본문을 안 받을 이유가 아니라 자리 수를 제한할 이유**였다.

```
받는다        ARTICLE_CAP 3 으로 잠식 폭을 묶는다 (4-10)
              유형으로 검색 대상을 거른다 (3-7)
안 받는다      "축제 언제 해" · "채용 공고 났어" 류에 아예 답을 못 한다
```

`scraping/12` 가 셀렉터 하나로 본문을 뽑는다.

```
.bbs__view td.p-table__content          본문만
(.bbs__view 전체를 긁으면 제목·작성자·부서·전화·첨부목록·이전글/다음글이 딸려 온다
 실측 788자 중 본문은 401자)
```

파싱 실패 0건. 현재 4,988건 중 4,948건이 본문을 갖고 있다(나머지는 원래 빈 글).

##### 1-2c. 선언이 크롤링을 지시한다 — `sites/suwon.yaml` (2026-09-04)

09-02 까지 이 파일은 robots 예외를 적어 둔 **메모**였다. 접속 주소·셀렉터·게시판 목록은 `scraping/12` 안에 상수로 박혀 있었다. 지금은 코드가 이 파일을 읽는다.

```yaml
endpoints:   board_list · board_view
selectors:   9종   body · body_fallback_rows · meta_th · file_href · file_size ·
                   file_icon_prefix · list_head · list_body · list_row_link
crawl:       5종   user_agent · delay_sec 0.6 · default_days 365 ·
                   refetch_days 30 · seen_stop_pages 2
robots:      deny 6경로 + allow_despite_robots (사유 포함)
boards:      128개   take:true 20 / take:false 108
```

**`take:false` 108개에 전부 `why` 를 적게 한 것이 요점이다.** "안 긁는다"만 남으면 나중에 누구도 다시 판단할 수 없다. 가장 큰 덩어리는 업무추진비 4종(11,032건)이고 사유는 "행정 공개 의무 자료 — 시민 질문의 답이 아니다"다.

수집 루프는 이렇다.

```
게시판마다:
  목록 페이지를 넘기며 글 목록을 읽는다
  "이미 본 글만"인 페이지가 2번 연속 -> 이 게시판 끝            조기 종료
  각 글:
    캐시에 있고 30일보다 오래됨  -> 건너뜀
    캐시에 있고 30일 이내       -> 다시 받아 content_hash 비교   변경 감지
    없음                      -> 받는다
  50건마다 _detail_cache.json 저장                             중간 저장
이전 articles.json 과 병합하되 게시판별 1년 창 밖은 버린다        in_window
```

`content_hash` 는 본문 sha256 앞 16자다. **이 사이트는 캐시 헤더를 하나도 안 주므로(1-10) 받아 봐야만 바뀐 것을 안다.** 사흘째에 진짜 수정 3건을 잡았다.

```
장애인 특별공급 안내      "○ 수정내용 : 84F 삭제, 84D 배정세대 변경" 이 추가됨
청소년 음악 경연대회      행사명 "2026 음악" -> "2026 전국 청소년 음악" 정정
새빛시민 도시정비학교     문자 몇 개 정정
```

**첫 번째가 정확히 잡아야 하는 것이다** — 배정세대가 바뀐 공고를 옛 본문으로 답하면 시민이 헛걸음한다.

조기 종료로 수집 시간이 **18분 → 11분**, 데이터 손실 0. 다만 병합이 1년 창을 깰 뻔했다 — 이전 `articles.json` 을 그대로 합치니 창 밖 글까지 되살아났다(3,747 → 3,736 으로 11건이 줄어드는 것을 보고 알았다. 전부 2025-09-03 자).

**아직 민원 쪽은 선언이 아니다.** `#contents` 셀렉터·`th/td` 메타 파싱·`PAGES` 644 목록은 코드에 남아 있다(1-8).

##### 1-3. LLM 에게 본문을 읽히기 — `02_extract_llm.py`

"분류해 줘"라고 시키지 않는다. **채울 칸을 스키마로 정하고 그 형식으로만 답하게 강제한다.**

```python
tools=[EXTRACT_TOOL],
tool_choice={"type":"function", "function":{"name":"extract_civil_service_fields"}}
```

`EXTRACT_TOOL` 은 같은 파일 292행의 JSON Schema 다.

```
documents        [문자열]                    제출해야 하는 서류 이름
procedure_text   문자열 or null              절차 (본문에 없으면 반드시 null)
regulation_text  문자열 or null              법령 근거
content_type     "procedure" | "reference"   <- enum. 다른 값을 못 낸다
```

`tool_choice` 를 지정하면 **LLM 이 문장으로 답할 수가 없다.** 항상 이 JSON 모양으로 나온다.

`content_type` 이 라우팅 액션이다.

```
시민이 신청·신고·납부 같은 '행동'을 하는 방법을 안내   -> procedure
제도·용어·세율·기준 설명, 참고 링크 모음            -> reference
애매하면 따라 할 동작이 있는지로 판단 — 없으면 reference
```

**마지막 줄이 중요하다.** 애매할 때 기울 쪽을 정해 주지 않으면 실행마다 흔들린다.

`documents` 의 설명이 유난히 긴데 전부 **실제로 틀렸던 것을 막는 문장**이다.

```
주의1  카탈로그 목록은 제출서류가 아니다 (무인민원발급기가 '발급해 주는' 증명서 목록)
주의2  표 헤더('본인'·'대리인')와 수수료는 서류가 아니다
주의3  대상자 목록·위기사유·면제대상은 서류가 아니다
주의4  법령 조문은 documents 가 아니라 regulation_text 로
```

##### 1-5. 보조 패스 넷 — `02` 를 안 고치고 따로 붙인 이유

`02` 를 만들어 써 보니 빠진 것이 나왔다. 스키마에 칸을 추가하면 캐시가 통째로 날아가고, 여러 번 손봐 안정된 구비서류 추출이 LLM 편차로 다시 흔들린다.

```
03  금액이 '내는 돈'인가 '받는 돈'인가   난임부부 30만원이 수수료로 적재돼 있었다
04  신청 채널 + 지원금액              02 스키마에 지원금 칸이 아예 없었다
```

`07` 이 왜 필요했는지가 좋은 예다. `불참자 과태료 부과` 는 본문이 168자뿐인 정답 페이지인데 `"민방위 교육 안 가면 어떻게 돼"` 에서 12위였다. `content` 4,000자를 매칭 대상으로 삼으니 별칭 `"안 가면"->"불참"` 이 희석됐다. **짧은 칸이 있어야 물린다.**

`03` 의 독스트링이 왜 LLM 이 필요한지를 밝힌다 — `ontology/fees.is_benefit()` 이 '지원/지급/보조금' 표현으로 22건을 걸러내지만(오제외 0건), "1인당 최대 300만원"처럼 **방향 신호가 문자열 안에 아예 없는** 경우가 남는다. 방향은 금액 문자열이 아니라 그 페이지가 무엇에 관한 것인지에 달려 있어서 민원 이름·분야를 같이 봐야 한다.

(그 `is_benefit()` 자체는 수집이 아니라 적재 단계 `nodes/04` 에서 돈다. 수집 단계에서 `ontology` 를 직접 import 하는 것은 `04_extract_channel_benefit.py` 하나뿐이다.)

##### 1-6. LLM 은 뽑기만 하고 온톨로지가 다듬는다

```
LLM      "주민등록 등본" / "주민등록등본" / "등본"
  ↓  ontology/documents.py  canonicalize()
정규화    "주민등록등본"                          같은 서류로 합침
  ↓  issued_at()
발급처    "동 행정복지센터·무인민원발급기·정부24"     12종 닫힌 어휘
```

**LLM 은 "어디서 떼는지"를 모르고, 알아도 실행마다 달라진다.** 규칙에 박아 뒀고 목록에 없는 값이 나오면 `check_vocabulary()` 가 멈춘다.

**`ontology/` 안에서도 성격이 둘로 갈린다**

```
선언 (schema.yaml + schema.py)     "무엇이 무엇인가"
   org_classes · bureau_levels · body_fallback_levels
   vocabulary · classes · hierarchy.domain_depth
   -> 수집은 안 읽는다. 적재·검증 단계가 읽는다

파서 (6모듈)                       "문자열을 값으로"
   classify.py     조직 이름 -> unit_level
   aliases.py      unit_level -> 시민 통칭
   documents.py    서류명 정규화 + 발급처 판정
   fees.py         "3만원" -> fee_min/fee_max, 내는 돈/받는 돈
   regulations.py  법령명·조항 분리
   inquiry.py      본문 "문의" 섹션 파싱
   -> 수집이 쓰는 것은 여기뿐이고, 그마저 04 하나다
```

**수집 단계는 선언을 안 읽는다.** 선언이 하는 일(닫힌 어휘 검사·관계 Range·계층 깊이)은 전부 그래프에 넣을 때 따지는 것이라 적재·검증 쪽에 있다. 수집은 LLM 출력을 `enum` 으로 강제하는 것까지만 하고, 그 값이 **정말 허용된 어휘인지는 `validate/00` 이 적재 직전에 다시 본다** — 스키마를 나중에 고치거나 다른 경로로 값이 들어오면 `enum` 만으로는 뚫리기 때문이다.

**LLM 의 흔들림을 인정하고 넣은 장치**

`temperature=0` 인데도 재실행하면 결과가 달라진다. 주석에 실측이 남아 있다.


##### 1-7. 왜 민원만 LLM 을 타나

원천 셋 중 민원만 LLM 5회를 쓰고 조직도·게시판은 0회다. **구조가 답을 알려주느냐 아니냐**의 차이다.

```
조직도    HTML 중첩이 곧 소속 관계다
          <li>기획조정실<ul><li>정책기획과<ul><li>정책기획팀
          PART_OF 를 그대로 읽으면 된다. 물어볼 것이 없다
          unit_level 도 이름 끝 한 글자로 끝난다 ("○○과" -> 과, 예외 25건은 목록)

게시판    칸이 이미 나뉘어 있다
          번호 | 제목 | 담당부서 | 등록일 | 조회
          제목이 어디고 부서가 어디인지 물을 필요가 없다
          게다가 본문을 안 받으므로 LLM 이 읽을 대상 자체가 없다

민원      구조가 답을 안 알려준다
          "인감증명 발급 / 발급기관 : … / 발급신청 구비서류 / 대상자 및 항목 /
           신분확인방법 / 비 고 / 내국인 / 본인 / 주민등록증,운전면허증,…"
          주민등록증은 서류지만 '내국인'·'본인'은 표의 행 이름이고
          '대상자 및 항목'은 칸 제목이고 '600원'은 수수료다
          이걸 가르려면 문장의 뜻을 알아야 한다
```

신호 3층으로 보면 이렇다.

```
1층  사이트가 붙여 놓은 분류   URL 경로 · breadcrumb      조직도·게시판이 여기서 끝난다
2층  HTML 구조              th/td · 표 · 태그 중첩       여기서도 끝난다
3층  문장의 뜻               LLM                        민원만 여기까지 내려온다
```

**위층에서 답이 나오면 아래로 안 내려간다.** 3층은 비싸고 실행마다 흔들린다.

민원 안에서도 전부 LLM 에게 맡기지 않는다.

```
담당부서·전화번호   th/td            1·2층에서 끝
breadcrumb       상단 경로          1층에서 끝
표 원문           <table>          2층에서 끝
대형폐기물 품목     표의 행           2층에서 끝 -> WasteItem 노드
장소 목록         표의 행           2층에서 끝 -> Place 노드
────────────────────────────────────────────
구비서류·절차·법령                    3층
content_type                       3층
금액 방향(03)                       규칙이 22건을 가르고 애매한 것만 3층
```

##### 1-9. A2 게이트 · B 1·2층은 언제 필요한가 (2026-09-02 실측)

설계에는 있는데 구현이 없는 두 가지다. **지금 필요 없는 이유와 나중에 필요한 이유가 다르다.**

```
(항상 reference 로 찍어도)              59%
```

같은 메뉴 안에 신청하는 것과 현황 안내가 섞여 있다.

그리고 **캐시(`content_key` = 본문+프롬프트 해시)가 이미 있어서 재실행 비용이 0** 이다. 1층으로 아끼는 것은 첫 수집의 12%뿐인데, 오판하면 `validate/01` 규칙과 답변이 직접 깨진다. 게다가 지금 "순수한" 분류가 앞으로도 순수하리란 보장이 없다 — `임신·출산` 20건이 지금 전부 procedure 인데 그 메뉴에 현황 페이지가 하나 추가되면 1층이 그것을 자신 있게 오판한다.

**"이득 12% vs 조용한 오판 위험"이 나쁜 거래**라는 것이지, 원리적으로 틀렸다는 뜻은 아니다.

**규모가 커지면 역할이 뒤바뀐다.**

```
규모 질문    1층이 LLM 을 부를 것을 얼마나 줄이나?   -> 이것이 핵심이 된다
```

```

게시판 본문 추가   10만 건 × 5패스 = 50만 호출. 비용도 문제지만 벽시계 시간이 며칠
```

**여기서는 "전부 LLM 에 보낸다"가 불가능하다.** 1층의 일이 판정이 아니라 **걸러내기**가 된다 — 버리는 것은 틀려도 회복 가능하지만(다시 넣으면 된다) 판정을 틀리는 것과는 위험이 다르다.

**A2 게이트가 더 급하다.** 지금은 `PAGES` 644개를 사람이 골라 놔서 게이트가 판정할 대상 자체가 없다. 실제로 하려면 순서가 이렇다.

```
① 사이트맵/재귀 크롤링으로 페이지를 발견
② 그중 무엇을 받을지 판정        <- A2 게이트. 지금 없다
③ 받은 것을 분류                <- B 1·2·3층
```

**②가 없으면 ①을 못 한다.** 재귀로 훑으면 신고센터·정보공개·시정소식이 다 딸려 들어와 "시민이 신청할 수 있는 것"이라는 노드 정의가 깨진다.

**아직 안 재본 쓸모 하나** — 1층을 라우팅이 아니라 **검사**로 쓰는 것. breadcrumb 이 100% procedure 인 구간인데 LLM 이 reference 라고 했다면 표시해서 사람이 본다. 검사는 틀려도 마커만 붙고 적재는 되므로 손해가 없다. `validate/01` 의 D1/D2 와 같은 자리다.

**그것만으로 범용이 되지는 않는다.** A2·B 1·2층은 범용성의 필요조건이지 충분조건이 아니다 — 만들어도 새 사이트를 붙이려면 셀렉터(`#contents`)와 메타 파싱(`th/td`), 조직명 규칙, 발급처 어휘를 다시 짜야 한다.

**아직 정하지 않았다.**

##### 1-10. 무엇이 바뀌었는가 — `content_hash` (2026-09-02)

각 레코드에 본문 지문을 싣고, 이전 배치와 대조해 리포트를 낸다.

```
이전 배치 대비: 신규 3 · 변경 12 · 그대로 629
  [변경] 인감증명발급
  [변경] 여권발급 수수료
```

**재수집을 줄이지는 못한다.** 이 사이트는 캐시 헤더를 하나도 안 준다(실측).

```
ETag             없음
Last-Modified    없음
Cache-Control    없음
```

조건부 요청(`If-None-Match` / `If-Modified-Since`)이 불가능해서 **받아 봐야만 바뀐 것을 안다.**

**LLM 추출은 이미 증분이었다.** 처음에 "본문이 그대로여도 다시 뽑는다"고 봤는데 틀렸다 — `content_key()` 가 `sha1(content + prompt)` 라 다섯 패스 전부 내용 기반 캐시다.

```
content_key(record)
    prompt = json.dumps(EXTRACT_TOOL, sort_keys=True)
    raw = (record.get("content") or "") + "\x00" + prompt
    return sha1(raw)
```

그래서 `content_hash` 의 값은 절감이 아니라 **검증**이다. 재수집하면 뒤이어 도는 `02`~`07` 이 바뀐 페이지만 LLM 에 보낼 텐데, **그 수가 이 리포트와 맞아야 정상**이다. 지금까지는 그것을 대조할 방법이 없었다.

그래프에도 싣는다(`CivilService.content_hash`) — 원천과 적재 결과를 대조할 수 있게.

##### 2-0. 실행 방식

```python
for step in STEPS:
```

한 프로세스인 이유는 `BATCH_ID` 를 전 단계가 공유하기 위해서다. 모든 노드에 `last_seen = BATCH_ID` 를 찍고, 마지막에 `lifecycle` 이 **이번 배치에 안 찍힌 노드를 폐지**시킨다. 나눠 돌리면 안 돌린 쪽이 통째로 폐지된다.

##### 3-0. 무엇을 임베딩하는가

##### 3-1. `:Entity` 가 검색의 입구다

이 라벨이 있으면 벡터 검색에 잡히고 없으면 안 잡힌다. 인덱스가 `FOR (n:Entity) ON (n.embedding)` 이라 라벨 하나로 후보 집합이 정해진다.

```
붙이는 것    OrgUnit · CivilService · Employee · Article
안 붙이는 것  Attachment · Place · WasteItem · Domain · Issuer · Board
```

**Article 은 09-03 에 넘어왔다.** 그전 판단("게시글이 후보에 섞이면 민원·조직을 밀어낸다")은 관측 자체는 맞았지만 처방이 과했다 — 자리 수로 묶으면 되는 일이었다(4-10).

**안 붙이는 쪽은 여전히 일부러다.** 특히 Attachment 5,985개가 후보에 섞이면 파일명이 화면을 뒤덮는다. 그것들은 **구조 질의(이름 정확 일치·관계 순회)로만 닿는다** — 첨부는 별도 블록으로, 장소는 `places_for` 로, 폐기물 품목은 구조 라우터로.

폐지된 노드도 `:Entity` 를 떼서 후보에서 빠진다(`lifecycle/01`).

##### 3-2. OrgUnit 은 940개 중 190개만 넣는다

조직이 **자기 이름으로 내건 '주요업무'가 있는 것**만 대상이다. `행정민원팀` 44개가 전부 후보로 뜨면 검색이 그것으로 뒤덮인다.

이 동작이 `nodes/01` 의 `MERGE` 설계를 강제한다 — 749개에서 라벨을 떼므로, `MERGE` 패턴에 `:Entity` 를 넣으면 다음 실행에서 패턴이 안 맞는다.

##### 3-3. CivilService 임베딩 텍스트의 구성

```
이름 + 별칭 + 본문 + 표 품목명(800자 상한)
MAX_CHARS = 6000            text-embedding-3-small 한도가 8192 토큰
평균 1,061자 · 중앙 701자 · 최대 6,000자
```

**별칭을 넣는 이유.** 별칭은 "시민이 공식 명칭과 다른 말로 부른다"를 다루는 값인데, 컨텍스트 블록에만 쓰고 임베딩에서 빠뜨리면 정작 검색 단계에서 못 쓴다. 실측 사고가 있었다 — 교통 데이터를 넣자 "등본 관련해서 어디에 문의"가 자동차 `등록증재교부`(0.7831)·`등록원부발급`(0.7697)에 밀려 정답인 `등초본 발급` 이 25위 밖으로 사라졌다. 별칭 "등본"이 임베딩 텍스트에 있으면 정답 쪽이 직접 매칭된다.

**표는 원문이 아니라 이름만 넣는다.** 가장 큰 표가 355행 27,000자다. 통째로 넣으면 임베딩이 숫자·규격으로 뒤덮인다. 각 행의 첫 '이름 같은' 칸만 모으고 숫자만 있는 칸은 건너뛴다.

##### 3-4. 증분 임베딩 (2026-09-02)

한때 매 실행마다 전량을 다시 보냈다. 지금은 **텍스트와 모델이 그대로면 건너뛴다.**

```
평상시     0/190 · 0/644 · 0/5077     OpenAI 호출 0회
바뀌면     1/644                      정확히 그것만
--all      비교를 건너뛰고 전량 재생성
```

**별도 해시 속성을 안 만들었다.** 세 스크립트가 이미 `embedding_text` 를 노드에 저장하고 있고 그것이 곧 `build_text()` 의 출력이라 그대로 비교하면 된다. 해시를 따로 두면 텍스트와 해시가 어긋날 자리가 하나 더 생긴다.

**모델 이름은 새로 넣었다**(`embedding_model`). 같은 텍스트라도 모델이 갱신되면 다른 벡터가 나오는데, 그 판단을 사람 기억에 맡길 수 없다.

**롤업 정리 의미는 유지했다.** 전부 지우고 다시 만드는 대신 **대상이 아닌 것만** 지운다. `01` 이 749개에서 `:Entity` 를 떼는 동작은 그대로고, 그것이 `nodes/01` 의 `MERGE` 가 `org_id` 로만 걸려야 하는 이유다.

왜 이것이 중요한가 — 전량 재생성이면 `main.py` 전체 실행이 부담스러워지고, 그래서 안 돌리게 되고, **전체를 돌려야만 드러나는 버그가 잠복한다.** 실제로 `nodes/01` 의 `MERGE` 라벨 문제가 0828부터 몇 주 동안 안 드러났다.

##### 3-5. 표를 빼는 안은 실측으로 기각했다

표를 가진 민원 70건을 표 없이 재임베딩해 순위 변화를 봤다(그래프는 안 건드리는 오프라인 시뮬레이션).

```
좋아짐 0 · 나빠짐 1 · 그대로 11
나빠진 것: "기초생활수급자 지원" 1위가 맞춤형 기초생활보장제도 -> 청년기본소득
```

이유는 애초에 희석이 안 될 만큼 작아서다 — 표 원문 평균 3,937자인데 임베딩 기여분은 최대 800자이고, 표를 가진 민원이 70/644(11%)뿐이다.

##### 3-6. 임베딩이 긴 것들은 표 때문이 아니다

상위 12개 중 10개가 표 0자다.

```
복지·문화              6,000자(본문 10,387)   표 없음   ← 유일한 묶음 페이지, 제도 58개
보험 및 신청 안내        6,000자              표 없음
대설, 한파             6,000자              표 없음
태풍, 강풍             5,475자              표 없음
경보에 따른 행동요령      5,403자              표 없음
중고차 허위매물 체크리스트  4,820자              표 없음
수원 국가유산 허용기준     6,000자              표 19자
수질 및 수생태계 환경기준   4,561자              표 205자
```

**본문이 원래 긴 안내문**이다. 재난 행동요령·체크리스트·현황은 한 페이지가 곧 한 주제라 쪼갤 근거가 없다. 여러 사업이 뭉친 것은 `복지·문화` 하나뿐이고(597줄, 청년기본소득이 별도 노드로도 있는데 여기 또 들어 있다), 644건 중 1건이라 지금 손댈 값어치가 없다고 판단했다.

##### 3-7. 게시글 임베딩 — 범위를 유형으로 정한다 (`embedding/04`)

```python
SEARCHABLE_TYPES = ["공고", "결과발표", "안내", "소식"]
# 제외: 자료실 · 현황공개 · 홍보
MAX_CHARS = 6000
```

임베딩 텍스트는 **제목 + 게시판 + 담당부서 + 본문**이다. **날짜는 넣지 않는다** — 날짜는 정렬에 쓰는 값이지 의미가 아니라서, 임베딩에 넣으면 숫자가 유사도를 흔든다.

##### 범위 판정은 후보 세 개가 전부 빗나갔다

세운 후보는 `all / timeless / recent` 였다. 후보로 들어온 게시글의 출처를 세어 보니 정반대였다.

```
민원서식자료실 timeless=True   후보 11자리 차지 · 정답 0건
시정소식      timeless=False   5자리 · 정답 1
보도자료      timeless=False   3자리 · 정답 1
```

**서식 게시글은 첨부 블록이 이미 담당하는 자리다.** 첨부 적중이 4/4 로 나가고 있는데 같은 것이 후보 자리를 또 먹으며 관련 후보를 밀어냈다.

처음엔 `news`(= NOT timeless)로 갈랐고, `article_type` 이 생긴 뒤 그것으로 바꿨다. **`timeless` 는 "오래돼도 유효한가"이고 `article_type` 은 "무엇인가"인데, 빼야 할 이유가 오래돼서가 아니었으므로 유형이 맞는 축이다.**

##### 범위 밖은 `:Entity` 만 떼고 벡터는 남긴다

그래서 범위를 바꿔 보는 실험이 공짜다 — 임베딩을 다시 만들지 않는다. 현재 4,988건 중 4,292건이 `:Entity` 다.

##### 4-1. 구조 라우터가 가로채는 것 셋

**대형폐기물 요금** — 표 한 행이 곧 답이라 유사도로는 못 찾는다. 실측: "냉장고 처리 얼마"는 벡터 1~10위 점수 폭이 0.013 이라 사실상 무작위였고, 어휘는 파이프라인이 1위 하나만 받는데 그 자리를 "공유냉장고"가 세 번 나오는 무관한 표가 가져갔다. **이름 정확 일치로 조회한다.**

**조직 목록** — "국 목록", "장안구 동 목록" 같은 질의. `unit_level` 인덱스로 푼다.

**민원 집계·필터** — 축이 넷이다.

```
domain              분야
dept                담당부서
has_regulation      법령근거 있는 것만
requires_document   특정 서류가 필요한 것만
fee_min / fee_max   수수료 범위
benefit_min/max     지원금 범위       ← 수수료와 반대 필드를 본다
```

같은 금액 조건이라도 "수수료 3만원 이상"과 "지원금 3만원 이상"은 보는 필드가 반대다.

**두 라우터가 동시에 걸릴 수 있다.** 실측: "동 행정복지센터에서 처리하는 민원 목록"이 토큰 '동'에 걸려 조직 목록으로 가는 바람에 민원이 아니라 44개 동 이름을 반환했다. 그래서 "민원을 나열해달라는 질문인가"(`asks_for_civil`)를 보고 조직 라우터를 끈다.

##### 4-2. 척도가 셋 섞여 있다

```
코사인      0.7x        벡터
BM25       14~80       어휘 (풀텍스트)
구조 결과   점수 없음     라우터
```

섞어 정렬하면 BM25 가 무조건 이긴다. 그래서 **점수로 겨루게 하지 않고 자리만 보장한다.**

실측하면 1위가 5위보다 점수가 낮은 질문이 나온다(`전입신고 어떻게 해` 0.7470 < 0.7489). 설계상 그런 것이고, **그래서 이 필드로는 "점수 뭉침"을 잴 수 없다** — 벡터 경로만 따로 봐야 한다.

**자리 보장은 절반만 푼다.** 후보를 살려낼 뿐 자리 안의 순서를 정하지 못해서, 2~5위가 코사인 하나로만 줄을 섰다. 나머지 절반을 09-03 에 RRF 로 풀었다(4-8).

##### 4-3. BM25 를 다섯 가지로 다르게 쓴다

같은 어휘 검색인데 자리마다 쓰는 법이 다르다.

```
민원 제목      자리 보장 1건      LEXICAL_KEEP=1. 점수 경쟁에 안 넣는다
직위          절대 임계 30       EMP_LEXICAL_MIN. 짧은 칸이라 임계가 높다
```

##### 4-6. 지역 처리

지역명은 **임베딩용 텍스트에서만 뺀다.** 부서 임베딩에는 구·동 이름이 아예 없어서(소속을 그래프 관계로만 안다), 지역명을 남겨두면 임베딩이 그쪽으로 쏠린다 — 실측: "권선구 세무 관련 문의"에서 세무과가 3등(0.72)에서 247등(0.64)으로 폭락했다.

지역 일치 판정은 그래프 경로로 따로 한다. 그리고 지역을 안 물었는데 구·동마다 있는 동명 조직이 상위를 채우면(실측: "재산세 세율"에서 재산세팀 3개가 top5 를 차지) **같은 이름은 최고점 하나만 남기고 `peer_count` 로 "N개 구에 각각 있다"를 따로 전달한다.** 그래야 답변이 특정 지점을 찍는 대신 거주지 관할로 안내할 수 있다.

##### 4-6b. 지역명 자체는 답이 아니다 — 한 원칙, 세 자리 (2026-09-03)

`권선구 세무 관련 문의` 의 1위가 **'권선구'(구 자체)** 로 나왔다. 원인이 셋이었고 **전부 같은 뿌리** 였다 — "시민이 구 이름을 댄 것은 그 구 안의 무언가를 묻는 것이지 구청 자체를 묻는 게 아니다"를 세 장치가 각각 몰랐다.

```
① 이름 승격      $q CONTAINS o.name 에 '권선구'(3글자)가 걸려 무조건 1위로
② 어휘 자리보장   (:CivilService{권선구}) 를 물었다 — 공인중개사무소 목록 표 페이지
③ 직위 검색      직위 '권선구청장' 이 34.4점으로 걸려 (:OrgUnit{권선구}) 를 주입
```

세 곳에 같은 규칙을 넣었다 — **이름이 지역명 "그 자체"일 때만 뺀다.**

```python
region_names = [reg["gu"]] + [d["name"] for d in reg["dongs"]]
# 어휘 자리보장:  h.get("name") not in region_names
# 직위 검색:      [h for h in emp_ranked if h["name"] not in region_names]
# 이름 승격:      AND NOT o.name IN $region_names
```

`장안구보건소` 는 이름이 `장안구` 와 달라서 안 걸린다 — **이름 승격 규칙이 실제로 순위를 바꾼 유일한 사례가 그것이라 반드시 살아남아야 했다.**

**기각한 대안**: "어휘 검색도 지역명 뺀 텍스트를 쓴다". 실측하니 `장안구보건소장이 누구야` 가 깨진다(원문이라야 장안구보건소 86.7 로 1위, 지역을 빼면 보건행정과만 남는다). `권선구청장이 누구야` 는 `detect_leader` 가 앞에서 이미 답하므로 제외해도 잃는 것이 없다.

```
+ 권선구 세무 관련 문의   0/5 -> 3/5
+ 팔달구 반려동물 등록    2/5 -> 3/5     같은 원인이었다
```

**팔달구가 같이 고쳐진 것이 중요하다** — 한 질문에만 맞춘 땜질이 아니라는 뜻이다.

##### 4-7. 현재 품질 (2026-09-04)

```
1위 적중     17/17       gold 47문항 중 top1 을 지정한 17문항
후보 정밀도   86/222 = 39%
첨부 적중     4/4
장소 적중     3/3          표에 실린 장소를 질문 지역으로 좁히는가 (09-04 신설)
속도         평균 0.30s
```

가는 길은 이랬다.

```
09-02   16/16   41/118 = 35%   gold 26   RRF 없음, 코사인 정렬
09-03   17/17   59/163 = 36%   gold 35   RRF · 게시글 본문
09-04   17/17   86/222 = 39%   gold 47   게시판 라우팅 · 유형 필터 · 장소
```

**후보 정밀도는 여전히 "올리는 것"이 목표가 아니다.** 09-02 에 여덟 가지를 시도해 전부 실패했고 그 판단은 유효하다 — 잡음은 LLM 이 걸러 내고, **답이 깨지는 것은 정밀도가 0/5일 때뿐이다.** RRF·라우팅으로 오른 것은 잡음을 줄여서가 아니라 **관련 후보를 더 넣어서**다.

**그리고 지표를 통과해도 답은 깨질 수 있다**(7-7).

##### 4-8. RRF — 척도가 안 섞이는 문제를 순위로 푼다 (2026-09-03)

```
score(d) = SUM  w / (k + rank_L(d))        w = 1.0, k = 60
           L
```

`search/steps/rrf.py`. 점수를 버리고 순위만 쓴다. 표는 다섯이다.

```
vector · lexical · employee · task_org · article
```

`other_hits` 정렬만 바꿨다. 자리 보장·별칭·지역·이름 일치는 안 건드렸다 — 효과를 이 변경에만 귀속시키려면 한 번에 하나만 바꿔야 한다. 코사인은 **2차 키**로 남긴다(어느 검색기에도 안 든 후보끼리는 여전히 유사도로 서야 한다).

`k=60` 은 관례값이고 우리 데이터로 튜닝하지 않았다. 26문항에 맞춰 고르면 그 26문항에만 맞는 값이 된다.

##### 자리 보장을 RRF 가 대체하지 못한다 (기각)

없애도 되는지 실제로 빼 보고 쟀다.

```
자리보장 유지 + RRF     1위 16/16   정밀도 45/118 = 38%    채택
자리보장 제거 + RRF     1위 15/16   정밀도 41/118 = 35%    기각
(RRF 없음, 코사인 정렬)  1위 16/16   정밀도 41/118 = 35%
```

이유는 `k=60` 의 성질 그 자체다. 어휘 1위와 벡터 1위가 둘 다 `1/61` 로 비기고, 어휘가 주입한 후보는 코사인이 0.0 이라 동점에서 진다. **평활화가 합의를 우대하는 대신 단독 강한 표를 누른다.**

```
자리 보장    후보를 살려낸다        "이건 자르지 마라"
RRF         살아남은 것을 줄 세운다  "이 순서로 보여라"
```

##### RRF 의 커버리지 편향 — 09-03 에 가장 중요한 발견

게시글을 넣었는데 뉴스 질문이 거의 안 잡혔다. 그런데 벡터 검색은 완벽했다(새빛청년존 2위 0.757 · 일자리두드림 1위 0.803 · 연화장 1위 0.817).

```
벡터 1위 게시글          {vector: 1}                0.01639  ->  RRF 8위
벡터 54위 CivilService   {vector: 54, lexical: 1}   0.02517  ->  RRF 2위
```

원인은 **어휘 인덱스가 Article 을 안 덮어서**였다.

```
CivilService   벡터 + 어휘              2개
OrgUnit        벡터 + 직위어휘 + 업무어휘  3개
Article        벡터                    1개   <- 구조적으로 영구히 불리
```

`article_text_index`(title^5 · content, cjk)를 만들어 2개로 맞췄다. 제목에 `^5` 를 주는 이유는 게시글 제목이 고유명사인 경우가 많아서다('일자리두드림'·'새빛청년존'·'연화장').

**교훈: RRF 를 쓸 때는 검색기별 커버리지가 라벨마다 같은지 봐야 한다.**

##### 4-9. 게시판 단위 라우팅 (2026-09-04)

`수원시 공무원 채용 공고` 를 물으면 **지난 공고**가 최신보다 위에 왔다. 시간 감쇠가 없어서라고 보고 세 번 고치려다 전부 실패했다.

```
① NOTICE_POOL 5 -> 25    날짜 경쟁 창을 넓힌다      변화 0건 · 정밀도 -2   기각
② 어휘 게시글을 풀에 주입   후보에 넣어 준다          변화 0건               기각
③ 어휘 1위를 자리 보장     확실한 것부터 고정한다     어휘 1위도 오답        기각
```

**세 번 다 진단이 틀렸다.** 어휘 검색은 정답을 이미 찾고 있었다(1048 게시판 글 25건 중 14건). 그런데 **어휘 1위부터가 '공무원 사칭' 보도자료**였다 — '공무원'이라는 낱말이 그 기사에 물려 벡터·어휘가 둘 다 그것을 위로 낸다. **관련성 단계에서 이미 진 것을 순위 조정으로 되살릴 수 없다.**

네 번째로 게시판을 신호로 썼다.

```python
BOARD_ROUTE_TYPES = {"공고"}
BOARD_ROUTE_MIN   = 0.4
BOARD_ROUTE_KEEP  = 2

# 어휘 게시글 결과가 어느 게시판에서 왔는지 센다
# 한 게시판이 40% 이상이고 그 게시판이 공고 유형이면 -> 최신 2건 자리 보장
```

**신호를 지어내지 않았다.** 어휘 검색은 이미 돌고 있고 게시판 소속도 이미 그래프에 있다. 세는 것만 추가했다.

```
정밀도       81/222  ->  86/222
최신성(3문항)  2/15  ->  6/15
좋아짐 3 · 나빠짐 0 · 오발동 0 (47문항 전수)
```

발동한 5개 질문의 게시판 비중은 56·56·100·100·100% 였다. **`0.4` 문턱은 현재 데이터에서 한 번도 갈라내지 않는다** — 지금은 사실상 비활성이고 게시판이 늘었을 때를 위한 안전장치다.

##### 지표의 함정 하나

`BOARD_ROUTE_KEEP` 을 4로 늘리니 `91/224` 로 더 좋아 보였다.

```
KEEP 2   86/222   후보 5개
KEEP 3   88/222   후보 5개
KEEP 4   91/224   후보 6개   <- 착시
```

자리 보장이 `top`(=5)을 넘어서면 `hits` 가 6개가 되어 **분자와 분모가 같이 는다.** 지표가 "후보를 더 보여주는 것"에 보상을 준다. **후보 수를 고정하고 비교해야 한다.**

##### 4-10. 자리 상한 셋

한 종류가 5자리를 다 먹는 것을 막는다. **전부 "점수로 겨루게 하지 않고 자리 수로 묶는다"는 같은 장치다.**

```
REGION_GU_CAP  3   구 산하 후보. 풀을 60으로 넓히니 28개까지 늘었다
ARTICLE_CAP    3   게시글. 관련성 상위 5건(ARTICLE_POOL)으로 좁힌 뒤 최신 3건
중복 접기           이름이 같은 것. 조직은 peer_count>1 일 때,
                   민원은 **분야까지 같을 때만** ('인터넷납부' 가 세금·교통에 각각 있다)
```

게시글의 순서가 미묘하다. **관련성으로 먼저 좁히고 그 안에서 최신을 고른다.** 뒤집으면 무관한 어제 글이 이긴다. 그리고 뽑힌 뒤엔 원래 RRF 자리에 그대로 둔다 — 최신이라고 앞으로 끌어올리는 것은 관련성보다 시점을 우선하는 다른 판단이다.

`ARTICLE_CAP` 은 09-03 에 1이었다가 09-04 에 3이 됐다. **근거가 바뀐 것이 아니라 들어오는 게시글의 성격이 바뀌었다** — 1로 정할 때는 게시글 "전량"이었고 서식 게시판이 후보 11자리를 먹던 때다. 유형으로 거르니 다르다.

```
gold 41문항:  1 -> 65/188 · 2 -> 70/190 · 3 -> 75/192 · 4 -> 76/193 · 5 -> 76/193
```

4에서 평평해지지만 3으로 뒀다 — 게시글이 5자리 중 4를 먹으면 민원·조직 답이 설 자리가 없고, 3→4 의 이득은 1건뿐이다.

##### 4-11. 목록 라우터를 결과 수로 판정한다 (2026-09-03)

`중장년 1인가구 지원사업 신청하려면` 의 후보가 1건뿐이었다. 원인은 "'중장년'이 무시됐다"가 아니었다.

```
'중장년'    TARGET_ALIASES 에 아예 없다. 무시된 게 아니라 모르는 말
'지원사업'   TRIGGER_WORDS 에 있어서 목록 라우터가 발동
결과        target_group='1인가구' -> 1건
```

**목록 라우터의 값은 "전수를 보여주는 것"인데 1건이면 그 값이 없다.** 게다가 그 경로는 `hits` 에 `civil_id` 를 안 실어서 절차·구비서류·담당부서·첨부가 통째로 빠진다.

```python
CIVIL_FILTER_MIN = 2
if len(names) < CIVIL_FILTER_MIN:
    civil_filters = None      # 벡터 경로로 흘려보낸다
```

**트리거 어휘를 좁히는 방법은 안 골랐다**("지원사업"을 빼는 식) — 그러면 진짜 목록 질문을 잃는다. **결과 수로 판정하는 편이 어휘를 지어내지 않는다.**

##### 5-0. 후보 하나가 블록 하나가 된다

```
부서 블록    이름 · 별칭 · unit_level · 소관 국 · 주소(자기 것인지 표시) ·

            + 최근 소식 + **표에 실린 장소**(5-5)
게시글 블록   날짜 · 제목 · 담당부서 · 본문 1,200자 · 출처              09-03
```

**게시글 블록은 조립할 것이 없다** — 관계가 담당부서 하나뿐이라 본문과 날짜가 곧 답이다. 그래서 지시문을 하나 붙인다.

```

```

`OrgUnit` 분기로 흘려보내면 `employees_for(h["org_id"])` 가 `None` 을 받아 깨지므로 분기를 따로 뒀다.

##### 5-1. 구비서류를 발급처별로 묶는다

그냥 나열하면 24줄이 된다. 발급처 조합이 같은 것끼리 묶으면 6줄이다.

```
stops           진짜 가야 하는 곳. 발급처 조합으로 묶음
no_issue_docs   접수처 비치·본인 소지 — 안 떼도 되는 것
unknown_docs    발급처를 모르는 것
```

발급처를 이름만 주면 LLM 이 "어디서 떼느냐"를 컨텍스트의 다른 주소로 메운다(실측: 통장사본 -> 동 행정복지센터). 그래서 서류명과 발급처를 짝으로 넘긴다.

##### 5-2. 첨부 블록은 네 장치가 함께 필요했다

```
트리거 게이트   질문에 서식·양식·신청서·청구서·신고서 같은 말이 없으면
              조회 자체를 안 한다. 기준선 20문항 오탐 4 -> 0

자식 1칸 순회   (o)<-[:PART_OF*0..1]-(:OrgUnit)<-[:POSTED_BY]-(:Article)
              시민이 아는 이름은 '과', 글 올리는 건 그 밑 '팀'

임계 5        6점 이상은 전부 정답, 4점 이하는 전부 오답이었다.
              4점 이하가 오답인 이유는 그 질문에 맞는 파일이 아예 없어서다 —
              후보가 비면 BM25 는 남은 것 중 제일 나은 쓰레기를 준다.
              임계는 "없으면 없다고 답하게" 만드는 장치다

전역 15점      파일명이 질문어를 통째로 담으면 관계 없이도 정답이다.
              트리거를 통과하지만 첨부가 답이 아닌 질문 10건의 전역 1위
              최고점이 9.0 이라 그 위에 선을 그었다
```

관계 경로와 전역 경로를 **합쳐서** 점수로 세운다. "관계가 못 찾았을 때만 전역"으로 했더니 관계가 문 10.6짜리 때문에 전역의 20.4짜리 정답이 영영 안 나왔다 — **관계가 뭔가 찾았다는 것이 그것이 최선이라는 뜻은 아니다.**

같은 파일명은 최신 하나만 남긴다. `file_id` 가 다운로드 uuid 라 글에 다시 올릴 때마다 새 노드가 생기고, 서식은 개정되므로 최신이 맞다.

##### 5-3. 지시문이 앞 단계와 중복되면 안 된다

블록 지시문이 "질문이 서식·양식을 찾는 것일 때만 안내하라"였다. 트리거 게이트가 없던 시절 LLM 이 게이트 노릇을 하던 흔적인데, 그대로 두니 **답을 손에 쥐고도 안 줬다.**

```
"출생신고 서류 뭐 필요해"
  받은 후보  출생신고서(1).hwp  10.9
  실제 답변  "출생신고에 대한 구체적인 서류 목록이 포함되어 있지 않습니다"
```

판정 기준을 '질문의 종류'에서 **'파일이 질문 내용과 맞는가'** 로 옮겼다. 걸러야 할 것은 질문 종류가 아니라 딸려온 홍보물이다.

교체 후 각 질문 3회 반복 실측: **18/18 의도대로**(정답 4종 전부 3/3 등장, 홍보물 2종 전부 0/3).

##### 5-4. 환각 방지는 프롬프트가 담당한다

`synthesize.SYSTEM_PROMPT` 에 "1번을 통과하는 후보가 하나도 없으면 절대 억지로 답을 만들지 마라"가 있다. 후보 정밀도가 35%인 상태에서 이것이 실질적 방어선이다.

브리지 경로(`make_answer=False`)는 이 단계를 건너뛰므로 방어가 통째로 빠진다 — 실측: "수원화성 관람료"에서 후보 5건에 관람료가 한 줄도 없는데 LLM 이 "성인 1,000원"을 지어냈다. 그래서 브리지 쪽에 `VECTOR_GUARD` 를 따로 붙였다.

##### 5-5. 표에 실린 장소를 지역으로 좁힌다 — `places_for` (2026-09-04)

`권선동 공중화장실 어디 있어` 를 물으면 민원 페이지 전체가 나온다. 그 안에 수원시 **전역**의 화장실 표가 들어 있고, 본문 요약이 "118개 행 중 3개만"으로 자르기 때문에 지역 질문에 답이 안 나갔다.

```cypher
MATCH (p:Place)-[:LISTED_IN]->(c:CivilService {civil_id: $civil_id})
WHERE any(w IN $names WHERE p.address CONTAINS w)
RETURN p.name, p.address, p.phone  ORDER BY p.name  LIMIT 8
```

`$names` 는 질문에서 잡힌 **구 + 행정동 + 법정동** 이름 전부다. `권선동` 이면 8건이 나오고, 이름·주소·전화로 민원 블록 끝에 붙는다.

**`LISTED_IN` 2,509개의 첫 사용처다.** 09-02 에 "관계 18종 중 4종이 죽어 있다"고 적었던 것 중 하나가 여기서 살았다.

##### 기각 — Place 를 `:Entity` 로 올리기

"장소도 검색되게 하면 되지 않나"를 실측했다. 안 된다.

```
Place 노드가 후보 자리를 먹고 관련 민원을 밀어낸다
장소는 "무엇을 하는 곳인가" 없이 이름·주소뿐이라 질문과 안 맞는다
```

**장소는 검색 대상이 아니라 답을 좁히는 재료다.** 앵커(CivilService)를 먼저 찾고 그 안에서 거르는 구조가 맞다.

##### 기각 — 죽은 관계 되살리기

`VISIT_FOR`(266개)를 검색에 붙여 봤다. **88건 중 88건이 이미 `visit_stops()` 가 내는 것과 같았다.** 관계는 있는데 정보가 중복이다. 지우지는 않고 검색에 안 쓰기로 했다.

## 6. 외부 연결

##### 6-0. 프로세스 둘

```
KG API   api/server.py     :9020   전역 python        POST /kg/search
브리지    bridge/app_kg.py  :9010   .venv-bridge      /ask_kg?mode=rag|kg|hybrid
```

인터프리터를 나눈 이유는 의존성 충돌이다 — `opik -> litellm` 이 Chatty 의 `openai==1.70.0` 핀과 충돌한다. 브리지는 KG 를 HTTP 로만 부르므로 neo4j·openai·opik 이 필요 없다.

##### 6-1. `make_answer=False` 가 기본이다

Chatty 는 KG 결과를 기다리는 예산이 짧고(기본 2초, 브리지가 10초로 늘림), 답변은 Chatty 의 LLM 이 만든다. KG 가 자기 답을 또 만들면 3~6초가 붙어 통째로 버려진다.

그래서 KG 는 **근거(`context_blocks`)만 반환**한다.

##### 6-2. Chatty 소스는 안 건드린다

함수를 감싸서 KG 항목을 앞으로 옮긴다. Chatty 의 키워드 재정렬에 KG 블록을 그냥 태우면 밀린다 — 실측: 맨 앞에 넣은 KG 집계가 17건 중 13번째로 밀려 LLM 이 사실상 무시했다.

**애초에 범주가 다르다.** 재정렬은 같은 코퍼스의 동질적인 문서 청크를 줄 세우는 장치인데, KG 블록은 문서가 아니라 이미 답에 가까운 요약이다.

첨부 블록도 같은 이유로 경쟁에서 뺀다. Chatty 자신이 첨부에서 같은 문제를 같은 방식으로 풀었다 — `app.py:3104` "첨부 chunk는 일반 검색 결과와 같은 풀에서 경쟁시키지 않는다."

##### 6-3. Chatty 가 받는 쪽의 제약

```
url 이 없으면 통째로 버려진다              app.py 2655/2955
title 이 겹치면 버려진다                   2650
항목마다 1400자로 잘린다                   3166
답변 컨텍스트에는 상위 3건만 들어간다        3193
```

집계 질의가 이 제약에 정면으로 걸린다. 그래프가 센 22건은 hits 에 이름만 있고 url 이 없어 하나도 안 들어가고, url 을 붙여도 항목을 쪼개면 3건만 남아 "22건 중 3건"이 정답인 양 나간다. **그래서 집계·구조 경로는 완성된 목록을 통째로 항목 하나에 담는다.**

##### 6-4. `make_answer` 두 경로를 따로 재야 한다

로컬에서 18/18 로 확인한 첨부가 브리지를 통과하면 하나도 안 나왔다. 로컬 시험은 `make_answer=True`(KG 자체 LLM)였고 브리지는 `False` 인데 **그 경로를 한 번도 안 쟀다.**

원인은 브리지가 `context_blocks` 와 `hits` 를 1:1 순서로 소비하는데 첨부 블록만 짝이 없어서, 엉뚱한 이름이 달리고 `max_items` 컷에 먼저 잘린 것이었다. 별도 필드(`attachment_block`)로 내고 맨 앞자리를 보장하게 고쳤다.

**09-04 에 같은 부류가 또 나왔다** — `_hit_url` 이 게시글을 몰라 출처가 전부 부서 홈으로 떨어졌다(7-7). `article_url` 갈래를 추가해 고쳤다.

```python
def _hit_url(hit):
    url = (hit.get("source_url") or "").strip()      # 민원
    if url: return url
    art = (hit.get("article_url") or "").strip()     # 게시글  <- 09-04 추가
    if art: return art
    org_id = hit.get("org_id")                       # 조직
    if org_id: return f"{BASE_DEPT}#{org_id}"
    return BASE_DEPT
```

**두 번 다 "로컬에서 통과한 것이 브리지에서 죽었다"이다.** 경로가 둘이면 둘 다 재야 한다.

##### 6-5. 3조건 비교

브라우저에서 같은 질문을 세 조건으로 돌려 본다.

## 7. 검증 — `validate/00`~`05`

##### 7-0. 여섯 개가 각각 다른 것을 본다

```
00  적재 전 모순      원천 JSON      위반이면 중단
01  적재 후 결함      그래프         마커 128건 / 구조 파손은 중단
02  게시글 사전 검사   원천 JSON      id 중복 · 필수 필드 · 날짜 형식 · file_id 충돌
03  기준선 생성       그래프 + 검색   라벨·관계·제약·status·원천 해시·임베딩 수·
                                 violations·unit_levels + 검색 20문항
                                 09-03 부터 **기본 보기 전용**. 덮어쓰려면 --write
04  검색 품질        검색           gold 47문항. 1위·정밀도·첨부·장소
05  품질 게이트       03+04 대조     나빠지면 exit 1, 기준선을 갱신하지 않는다   09-03
```

**`05` 만 `main.py` STEPS 에 들어 있다.** 30단계의 마지막이고, **여기서만 파이프라인이 "검색 결과"를 근거로 멈춘다** — `00` 은 원천의 모순을, `01` 은 적재된 그래프의 모순을 보는데 **둘 다 통과해도 답은 나빠질 수 있다**(관계는 멀쩡한데 순위가 밀리는 경우).

##### 7-1. `03` 과 `04` 는 목적이 다르다

```
03 (search20)  "어제와 같은가"      변화 유무만 본다
04 (gold)      "정답이 1위인가"     품질을 본다
```

**03만으로는 안정적으로 틀린 것을 통과라고 부른다.** 실제로 회귀 20/20 을 통과하면서 `여권 신청 어디서 해` 가 `어디서나민원(FAX민원)` 을 1위로 내놓고 있었고, `출생신고 서류 뭐 필요해` 는 후보 5건이 전부 무관했다.

`04` 를 만들고 재니 1위 적중이 14/16 이었고, 원인 셋을 고쳐 16/16 이 됐다.

##### 7-1b. 품질 게이트 — 기록과 판정을 갈랐다 (2026-09-03)

`03` 은 대조 없이 기준선을 덮어썼다. **나빠진 채로 돌려도 그 결과가 새 기준이 되고, 다음부터는 "어제와 같다"로 통과한다.**

**실제로 그 사고를 냈다** — RRF 를 붙이면서 대조 없이 `03` 을 돌려 이전 `search20.json` 을 날렸다. 그때는 `04` 를 손으로 전후에 찍어 뒀지만, 자동으로 돌면 아무도 손으로 안 찍는다.

```
1. 정답 라벨 실행
2. 그래프 상태 측정
3. 저장된 기준(data/baseline/quality.json)과 대조
4. 통과면 세 파일 갱신 / 실패면 아무것도 안 쓰고 exit 1
```

**실패했을 때 기준선을 그대로 두는 것이 핵심이다.** 다음 실행이 고쳐졌는지 비교할 대상이 남아야 한다.

```
1위 적중 감소        FAIL   정답이 1위에서 밀렸다. 후보에 있어도 답이 안 나온다
첨부 적중 감소        FAIL   4문항뿐이라 1건만 빠져도 크다
장소 적중 감소        FAIL   3문항 (09-04 신설)
정밀도 3건 초과 하락   FAIL
노드/관계 10% 감소    FAIL   수집 실패·적재 사고. 검색 지표보다 먼저 잡힌다
violations 50% 증가  WARN   규칙을 새로 넣어도 늘어서 막지 않는다
```

문턱을 감으로 안 정했다 — 같은 코드로 3회 연속 돌려 세 번 다 똑같이 나왔다. 그래서 1위·첨부는 여유 0이고, 정밀도 여유 3은 지금 관측된 잡음이 아니라 **앞으로 생길 잡음**(HNSW·데이터 증가) 몫이다.

**`gold_sha`** 를 `quality.json` 에 넣었다. 라벨이 바뀌면 비교를 건너뛴다 — 질문을 9개 더하면 `45/118` 이 `52/159` 가 되는데 그건 개선이 아니다.

**고장 주입으로 확인했다.** 어휘 자리 보장을 일부러 빼고 돌리니 `exit 1` 이 나고 `md5sum -c` 로 기준선 두 파일이 안 덮인 것을 확인했다.

##### 7-2. 정답 라벨의 형식

```json

  "top1": "급수팀",
  "relevant": ["급수팀", "수도요금팀", "상하수도란?"],
  "note": "고장 접수는 급수팀. 요금 관련이면 수도요금팀도 답이 된다."

```

```

relevant   후보로 들어와도 좋은 것 전부. 정밀도를 잰다
```

##### 7-3. 라벨 자체를 검산한다

`gold.json` 의 이름이 그래프에 없으면 멈춘다. 첫 실행에서 바로 일했다 — `냉장고` 를 "그래프에 없다"고 판정했는데, 대형폐기물 요금은 `WasteItem` 노드에 있고 검산 쿼리가 `CivilService`·`OrgUnit` 만 보고 있었다. **도구가 맞고 쿼리가 좁았다.**

라벨을 사람이 적는 이상 라벨도 틀린다. 실제로 두 번 틀렸다.

```
부서 답을 오답으로 셌다     전입신고·민방위·전기차는 민원과 부서 둘 다 1위로 타당
품목 노드를 놓쳤다         대형폐기물은 가격표 페이지가 아니라 WasteItem 이 답
```

1위 적중이 13/19 -> 14/16 이 된 것은 **채점 기준이 틀렸던 것이지 검색이 좋아진 게 아니다.**

##### 그 뒤로 세 번 더 틀렸다 (09-03 · 09-04)

```
수원 발레축제       "기사에만 있다"고 적었는데 CivilService 본문에 '기 간 : 2026. 9. 12.(토)'
새빛청년존         관련 3건인데 1건만 적었다
명절에 문 여는 병원  '문 여는' 으로 찾았는데 사이트 표기는 '문**을** 여는' 이었다
```

**세 번 다 "내가 만든 조사 쿼리가 곧 라벨이 됐다."** 규칙으로 못 박았다 — **0/5 가 나오면 검색이 아니라 라벨부터 열어본다.**

반대 방향으로도 한 번 틀렸다. `수원도시공사 직원 채용` 의 라벨을 1153 게시판 전체로 넓혔더니 수원문화재단 채용까지 정답이 됐다. 되돌렸다 — **질문이 좁으면 라벨도 좁아야 한다.**

##### 7-4. 경로를 갈라서 센다

`hits` 의 `score` 는 단일 척도가 아니므로, 어느 경로가 그 후보를 만들었는지를 표식으로 본다.

```
어휘 42 · 벡터 96 · 지역 3      (26문항, 후보 141건)
```

벡터가 대부분이고 어휘는 자리보장이라 대체로 맞는다.

##### 7-5. 0건일 때 규칙을 넣어야 한다

`DEPT_NOT_BODY`·`PART_OF_DIRECTION` 은 도입 시점 위반이 각각 0/700, 0/938 이었다. 나중에 넣으면 이미 쌓인 위반이 무더기로 떠서 **진짜 새 위반이 그 안에 묻힌다.**

그리고 **한 번도 안 걸려 본 규칙은 일부러 깨뜨려 봐야 한다** — 쿼리가 틀렸어도 0을 낸다. 시험용 노드를 매달아(국을 과 밑에) 둘 다 잡히는 것을 확인하고 치웠다.

##### 7-6. 기준선은 재현 가능해야 한다

`validate/03` 은 스크립트다. 손으로 뜨면 무엇을 어떻게 셌는지가 안 남는다 — 인덱스 DDL 을 `schema/01` 한 곳에 모은 것과 같은 이유다.

**기준선 자체도 검산해야 한다.** 옛 기준선은 조직을 이름으로 키 잡아 232개가 192개로 접힌 채 한동안 회귀를 통과시켰고, `org_live.records` 가 0 이었다(리스트가 아니라 `{"orgs": […]}` 라서 `len()` 이 키 개수를 셌다). **0은 "없음"과 "안 셌음"이 구별되지 않는다.**

##### 7-7. 지표를 통과해도 답은 깨질 수 있다 (2026-09-04)

게이트가 `1위 17/17 · 정밀도 86/222 · 첨부 4/4 · 장소 3/3` 으로 전부 통과한 상태에서, 실제 답변을 브리지까지 태워 눈으로 봤다. 둘이 나왔다.

**(1) 브리지의 게시글 URL 이 전부 틀렸다.** `bridge/_hit_url` 이 `source_url`(민원)·`org_id`(조직)만 알고 `article_url` 을 몰라 전부 부서 홈 루트로 떨어졌다. 거기에 `_dedup_url` 이 `#3`·`#4` 를 붙여서, 시민이 출처를 눌러도 그 공고로 안 갔다. 09-03 에 Article 을 `:Entity` 로 올리면서 생긴 구멍이다.

**gold 로는 절대 안 잡힌다** — gold 는 후보 이름만 세고 브리지를 안 탄다.

**(2) `출생신고 서류 뭐 필요해` 가 확신 있게 틀린 답을 낸다.** 답변이 출생신고가 아니라 **출산 지원금** 서류를 답한다("관할 보건소", "분만일로부터 6개월", "여성정책과"). 그리고 첨부 `출생신고서(1).hwp` 를 **찾아 놓고 3/3 회 답변에 안 쓴다**(효도수당 3/3 · 지방소득세 3/3 은 잘 쓴다).

원인은 프롬프트가 아니다. **출생신고는 대법원 소관이라 수원시 CivilService 에 아예 없다.** 그래서 후보 5개가 전부 출산 지원이고 LLM 이 그것으로 답을 만든다.

```
gold 는 이 문제를 절반만 본다
  후보 정밀도 0/5      O   잡는다
  첨부를 찾고도 안 쓴다   X   못 잡는다
```

같은 부류가 적재 로그에도 찍힌다.

```
[참고] 담당 OrgUnit 을 안 붙인 13건 — 고용노동부·경기도 등 수원시 소관이 아니라 정상
[참고] 법령명을 특정할 수 없어 연결하지 않은 3건
```

**적재는 "수원시 소관이 아니다"를 이미 알아보는데 검색·답변 쪽에는 그 축이 없다.** 고치려면 `external_org` 를 답변까지 태워야 한다.

```
지표는 "어제보다 나빠졌는가"를 본다
지표는 "애초에 맞는가"를 못 본다
주기적으로 실제 답변을 눈으로 보는 것이 지표만 보는 것보다 값지다
```

## 아직 1차 구현인 것

- **수집이 파이프라인 밖이다** — `scraping/*` 이 `STEPS` 에 없어서 손으로 돌린다. "자동으로 수집·적재"의 앞 절반이 비어 있다. LLM 을 쓰는 `01`·`02` 는 멱등하지 않아 못 넣지만, `00`(조직도)·`12`(게시판)는 LLM 0회라 넣을 수 있다
- **"수원시 소관이 아니다"를 말할 수 없다** — 적재는 이미 알아본다(외부기관 13건에 담당부서를 안 붙인다). 그런데 검색·답변에 그 축이 없어서 `출생신고 서류 뭐 필요해` 가 출산 지원금으로 답한다(7-7). **확신 있게 틀린 답은 무응답보다 나쁘다**
- **`unknown` 이 0 이다** — 격리·승격 장치가 한 번도 안 돌았다. 20개 게시판을 사람이 미리 분류해 놨기 때문이다. **게시판을 더 열어야 그 장치가 처음 일한다**(2-4)
- **A2 수용 게이트 · B 신호 1·2층** — 설계만 있고 구현이 없다. **지금 안 하는 것이 맞다는 09-02 판정은 아직 유효하다**(1-9): 1층 정확도 73~82%, 확실한 구간 12%, 캐시가 있어 재실행 절감 0.
  09-03 에 게시판 본문 4,948건이 들어왔지만 **LLM 패스를 안 태웠으므로** "10만 건 × 5패스 = 50만 호출"이라는 조건은 아직 안 왔다. 게시글은 본문을 그대로 임베딩하고 유형은 게시판 선언에서 물려받는다
- **1층을 검사로 쓰는 안** — 라우팅이 아니라 "breadcrumb 이 100% procedure 인데 LLM 이 reference 라고 했다"를 표시하는 용도. 손해가 없는 쪽인데 아직 안 재봤다
- **⑤ `IN_DOMAIN` 집계 라우터** — Domain 트리 76개를 적재해 놓고 검색이 안 탄다
- **민원 쪽 사이트 구조가 코드에 박혀 있다** — 게시판은 선언으로 나왔지만(1-2c) `#contents` 셀렉터·`th/td` 메타 파싱·`PAGES` 644 목록·조직명 규칙·발급처 어휘는 그대로다
- **서브도메인 12개** — `council` 은 본문 셀렉터가 `#content`(www 는 `#contents`), `jangan`·`health` 는 JS 렌더링이라 정적 HTML 로 못 읽는다. **"수원시 확장"이 아니라 "사이트 12개 통합"이다**
- **주기 분할** — 매일 게시판 / 주1 조직·민원 / 월1 법령·서류. 조기 종료(1-2c)로 긴급도는 낮아졌다

##### 2026-09-02 에 닫힌 것

- **증분 임베딩** — 완료. 텍스트·모델이 그대로면 건너뛴다(3-4)
- **A3 동일성** — `content_hash` 를 넣어 "무엇이 바뀌었는가"를 리포트한다(1-10). 다만 **LLM 추출은 원래부터 증분이었다** — `content_key()` 가 본문을 키에 넣고 있었다. 재수집 자체는 사이트가 캐시 헤더를 안 줘서 못 줄인다

##### 2026-09-03 에 닫힌 것

- **`main.py` 클린 실행** — 30단계 완주, exit 0, 게이트 통과. **하루에 두 번 "전체를 돌려야만 드러나는 버그"가 나왔다**(f-string 중괄호 · `nodes/16` 낡은 가드). `EXPLAIN` 파싱이나 단독 실행으로는 절대 안 잡히는 부류다

- **게시글 본문** — 안 받던 것을 받는다(1-2b). 파싱 실패 0건
- **정답 라벨 26 -> 35문항** — 추가하자마자 회귀 2건과 내 라벨 오류 1건을 잡았다

##### 2026-09-04 에 닫힌 것

- **선언이 실제로 크롤링을 지시한다** — `sites/suwon.yaml` 이 메모에서 지시서가 됐다(1-2c)
- **수집 증분** — `content_hash` + `REFETCH_DAYS 30`. 사흘째에 진짜 수정 3건을 잡았다
- **게시판 라우팅** — 세 번 실패한 뒤 네 번째에 풀렸다(4-9). 정밀도 81 -> 86, 최신성 2/15 -> 6/15
- **`LISTED_IN` 이 살았다** — `places_for`(5-5). 죽은 관계 4종 중 하나
- **`article_type` 어휘** — `unknown` 을 어휘 안에 두고 유형으로 검색 대상을 정한다(2-4·3-7)
- **정답 라벨 35 -> 47문항** — 장소·최신성·소관 축 신설
