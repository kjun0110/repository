## 개념

- **온톨로지 액션** — 데이터가 그래프로 들어갈 때 그래프가 개입해서 하는 일. 게이트·라우팅·검사·추론·계층·전파 여섯
- **선언(TBox)** — "무엇이 무엇인가"를 적어 둔 것. `ontology/schema.yaml` 한 곳
- **집행** — 그 선언을 읽어 실제로 막거나 만드는 것. 각 파이썬 단계가 한다
- **`:Entity`** — 벡터 검색 후보를 가리키는 라벨. 이게 없으면 검색에 안 섞인다
- **자리 보장** — 점수 경쟁에 넣지 않고 후보 한 자리를 확보해 주는 것. 척도가 다른 검색을 섞을 때 쓴다
- **신호 3층** — 사이트 자체 분류(URL·breadcrumb) / HTML 구조 / 문장 의미(LLM)

##### 이 문서가 다루는 범위

2026-09-02 기준 **실제로 돌아가는 것**만 적는다. 설계안·계획은 [[KG - 온톨로지 데이터 투입 액션]]에 있고, 여기는 "지금 이렇게 돈다"의 기록이다.

## 핵심 한 줄

**비싸고 실행마다 흔들리는 판단(LLM)은 적재 때 한 번만 하고, 검색은 그 결과를 읽기만 한다.**

그래야 질문마다 비용이 안 붙고, 돌릴 때마다 그래프 모양이 달라지지 않는다.

```
LLM 을 쓰는 곳    수집 5회 (배치, 644건에 한 번)
                답변 합성 1회 (질문당)
LLM 을 안 쓰는 곳  적재 28단계 · 검증 5종 · 구조 라우터
```


## 1. 수집 — `scraping/`

```
00  조직도            org_chart.json        232건
01  민원 안내 페이지    civil_service.json    644건    사이트 메뉴 커버리지 96%
02  LLM 구조화 추출    content_type 판정 등            ★ 라우팅 액션
03~11  보조 추출      수수료·채널·표·대상층·기한·위치·품목·장소
12  게시판 글         articles.json       3,750건    게시판 8개
13  민원사무편람       358건 수집, 미적재
```

##### 1-1. HTML 긁기 — LLM 없음

구조가 확실한 것만 규칙으로 뽑는다.

```
<th>담당부서</th><td>혁신민원과</td>       -> dept
<th>전화번호</th><td>031-5191-2000</td>   -> phone
<div id="contents"> … </div>             -> content (본문 통째)
HOME > 종합민원 > 민원안내 > 인감증명발급    -> breadcrumb
```

구비서류·절차·법령은 여기서 안 뽑는다. 페이지마다 `<h4>+<ul>`, `<li>+<table>` 로 표현이 갈려서 **정규식으로 안 된다**(20페이지 안에서만 최소 2가지 패턴).

원본 HTML 은 `data/raw/civil_service/html/` 에 보존한다. 재수집 없이 파싱만 다시 돌려볼 수 있게, 그리고 사이트가 바뀌었을 때 비교 근거로.

##### 1-2. 게시판은 성격이 다르다 — LLM 0회

**본문을 아예 안 받는다.** 게시글은 관계가 `(글)-(담당부서)` 하나뿐이라 벡터에 넣으면 주제가 제각각인 글이 후보에 섞여 민원·조직을 밀어낸다. 대신 그래프만 할 수 있는 것을 가져온다 — 부서별·기간별 구조 질의, 그리고 첨부 파일명.

열을 **위치가 아니라 이름(`thead th`)으로** 읽는다. 게시판마다 열 구성이 달라서 위치로 읽으면 틀린 칸을 집는다(실제로 두 번 틀렸다).

```
1042 시정소식    번호·제목·작성자명·담당부서·등록일·조회
1275 옥외광고물   번호·제목·첨부파일·담당부서·조회        <- 등록일이 없다
```

기준일도 게시판마다 다르다.

```
소식류 (1042·1043·1044·1254·1279)   1년치    작년 행사 공지는 답이 안 된다
서식류 (1026·1298·1275)             전량     서식은 2018년 것도 지금 쓰는 서식
```

이 성격을 `Board.timeless` 로 노드에 실어서 **검색의 기간 제한이 그 값을 읽는다.** 두 곳에 따로 적으면 한쪽만 고쳐진다.

##### 1-3. LLM 에게 본문을 읽히기 — `02_extract_llm.py`

"분류해 줘"라고 시키지 않는다. **채울 칸을 스키마로 정하고 그 형식으로만 답하게 강제한다.**

```python
tools=[EXTRACT_TOOL],
tool_choice={"type":"function", "function":{"name":"extract_civil_service_fields"}}
```

`EXTRACT_TOOL` 은 같은 파일 292행의 JSON Schema 다.

```
documents        [문자열]                    제출해야 하는 서류 이름
procedure_text   문자열 or null              절차 (본문에 없으면 반드시 null)
regulation_text  문자열 or null              법령 근거
content_type     "procedure" | "reference"   <- enum. 다른 값을 못 낸다
```

`tool_choice` 를 지정하면 **LLM 이 문장으로 답할 수가 없다.** 항상 이 JSON 모양으로 나온다.

`content_type` 이 라우팅 액션이다.

```
시민이 신청·신고·납부 같은 '행동'을 하는 방법을 안내   -> procedure
제도·용어·세율·기준 설명, 참고 링크 모음            -> reference
애매하면 따라 할 동작이 있는지로 판단 — 없으면 reference
```

**마지막 줄이 중요하다.** 애매할 때 기울 쪽을 정해 주지 않으면 실행마다 흔들린다.

`documents` 의 설명이 유난히 긴데 전부 **실제로 틀렸던 것을 막는 문장**이다.

```
주의1  카탈로그 목록은 제출서류가 아니다 (무인민원발급기가 '발급해 주는' 증명서 목록)
주의2  표 헤더('본인'·'대리인')와 수수료는 서류가 아니다
주의3  대상자 목록·위기사유·면제대상은 서류가 아니다
주의4  법령 조문은 documents 가 아니라 regulation_text 로
```

##### 1-4. 캐시가 스키마 해시다

```python
prompt = json.dumps(EXTRACT_TOOL, ensure_ascii=False, sort_keys=True)
```

스키마를 통째로 직렬화한 해시가 캐시 키다. **`description` 한 글자만 바꿔도 644건이 전부 다시 돈다.**

##### 1-5. 보조 패스 넷 — `02` 를 안 고치고 따로 붙인 이유

`02` 를 만들어 써 보니 빠진 것이 나왔다. 스키마에 칸을 추가하면 캐시가 통째로 날아가고, 여러 번 손봐 안정된 구비서류 추출이 LLM 편차로 다시 흔들린다.

```
03  금액이 '내는 돈'인가 '받는 돈'인가   난임부부 30만원이 수수료로 적재돼 있었다
04  신청 채널 + 지원금액              02 스키마에 지원금 칸이 아예 없었다
06  대상층                         "청년 정책" 물으면 10건 중 1건만 답하던 문제
07  기한 + 제재                     본문 4,000자에 묻혀 별칭이 희석되던 문제
```

`07` 이 왜 필요했는지가 좋은 예다. `불참자 과태료 부과` 는 본문이 168자뿐인 정답 페이지인데 `"민방위 교육 안 가면 어떻게 돼"` 에서 12위였다. `content` 4,000자를 매칭 대상으로 삼으니 별칭 `"안 가면"->"불참"` 이 희석됐다. **짧은 칸이 있어야 물린다.**

`03` 의 독스트링이 왜 LLM 이 필요한지를 밝힌다 — `ontology/fees.is_benefit()` 이 '지원/지급/보조금' 표현으로 22건을 걸러내지만(오제외 0건), "1인당 최대 300만원"처럼 **방향 신호가 문자열 안에 아예 없는** 경우가 남는다. 방향은 금액 문자열이 아니라 그 페이지가 무엇에 관한 것인지에 달려 있어서 민원 이름·분야를 같이 봐야 한다.

(그 `is_benefit()` 자체는 수집이 아니라 적재 단계 `nodes/04` 에서 돈다. 수집 단계에서 `ontology` 를 직접 import 하는 것은 `04_extract_channel_benefit.py` 하나뿐이다.)

##### 1-6. LLM 은 뽑기만 하고 온톨로지가 다듬는다

```
LLM      "주민등록 등본" / "주민등록등본" / "등본"
  ↓  ontology/documents.py  canonicalize()
정규화    "주민등록등본"                          같은 서류로 합침
  ↓  issued_at()
발급처    "동 행정복지센터·무인민원발급기·정부24"     12종 닫힌 어휘
```

**LLM 은 "어디서 떼는지"를 모르고, 알아도 실행마다 달라진다.** 규칙에 박아 뒀고 목록에 없는 값이 나오면 `check_vocabulary()` 가 멈춘다.

**`ontology/` 안에서도 성격이 둘로 갈린다**

```
선언 (schema.yaml + schema.py)     "무엇이 무엇인가"
   org_classes · bureau_levels · body_fallback_levels
   vocabulary · classes · hierarchy.domain_depth
   -> 수집은 안 읽는다. 적재·검증 단계가 읽는다

파서 (6모듈)                       "문자열을 값으로"
   classify.py     조직 이름 -> unit_level
   aliases.py      unit_level -> 시민 통칭
   documents.py    서류명 정규화 + 발급처 판정
   fees.py         "3만원" -> fee_min/fee_max, 내는 돈/받는 돈
   regulations.py  법령명·조항 분리
   inquiry.py      본문 "문의" 섹션 파싱
   -> 수집이 쓰는 것은 여기뿐이고, 그마저 04 하나다
```

**수집 단계는 선언을 안 읽는다.** 선언이 하는 일(닫힌 어휘 검사·관계 Range·계층 깊이)은 전부 그래프에 넣을 때 따지는 것이라 적재·검증 쪽에 있다. 수집은 LLM 출력을 `enum` 으로 강제하는 것까지만 하고, 그 값이 **정말 허용된 어휘인지는 `validate/00` 이 적재 직전에 다시 본다** — 스키마를 나중에 고치거나 다른 경로로 값이 들어오면 `enum` 만으로는 뚫리기 때문이다.

**LLM 의 흔들림을 인정하고 넣은 장치**

`temperature=0` 인데도 재실행하면 결과가 달라진다. 주석에 실측이 남아 있다.

```
02  "temperature=0이어도 실행마다 이 목록을 documents 로 넣었다 뺐다 함"
    "면제대상 6개가 재실행마다 달라짐"
07  "배치 구성이 바뀌면 같은 페이지에서도 결과가 달라진다"
```

그래서 캐시 / 검증 패스(`verify_documents`) / 닫힌 어휘 셋을 함께 쓴다.

##### 1-7. 왜 민원만 LLM 을 타나

원천 셋 중 민원만 LLM 5회를 쓰고 조직도·게시판은 0회다. **구조가 답을 알려주느냐 아니냐**의 차이다.

```
조직도    HTML 중첩이 곧 소속 관계다
          <li>기획조정실<ul><li>정책기획과<ul><li>정책기획팀
          PART_OF 를 그대로 읽으면 된다. 물어볼 것이 없다
          unit_level 도 이름 끝 한 글자로 끝난다 ("○○과" -> 과, 예외 25건은 목록)

게시판    칸이 이미 나뉘어 있다
          번호 | 제목 | 담당부서 | 등록일 | 조회
          제목이 어디고 부서가 어디인지 물을 필요가 없다
          게다가 본문을 안 받으므로 LLM 이 읽을 대상 자체가 없다

민원      구조가 답을 안 알려준다
          "인감증명 발급 / 발급기관 : … / 발급신청 구비서류 / 대상자 및 항목 /
           신분확인방법 / 비 고 / 내국인 / 본인 / 주민등록증,운전면허증,…"
          주민등록증은 서류지만 '내국인'·'본인'은 표의 행 이름이고
          '대상자 및 항목'은 칸 제목이고 '600원'은 수수료다
          이걸 가르려면 문장의 뜻을 알아야 한다
```

신호 3층으로 보면 이렇다.

```
1층  사이트가 붙여 놓은 분류   URL 경로 · breadcrumb      조직도·게시판이 여기서 끝난다
2층  HTML 구조              th/td · 표 · 태그 중첩       여기서도 끝난다
3층  문장의 뜻               LLM                        민원만 여기까지 내려온다
```

**위층에서 답이 나오면 아래로 안 내려간다.** 3층은 비싸고 실행마다 흔들린다.

민원 안에서도 전부 LLM 에게 맡기지 않는다.

```
담당부서·전화번호   th/td            1·2층에서 끝
breadcrumb       상단 경로          1층에서 끝
표 원문           <table>          2층에서 끝
대형폐기물 품목     표의 행           2층에서 끝 -> WasteItem 노드
장소 목록         표의 행           2층에서 끝 -> Place 노드
────────────────────────────────────────────
구비서류·절차·법령                    3층
content_type                       3층
금액 방향(03)                       규칙이 22건을 가르고 애매한 것만 3층
```

##### 1-8. 이 수집은 수원시 전용이다

여기까지의 설명은 **수원시 홈페이지 하나를 분석해서 손으로 깎은 것**이다. 다른 사이트를 넣으면 대응이 안 된다. 그것이 이 구현의 성격이므로 명시해 둔다.

**어디까지가 이 사이트에 묶여 있나**

```
PAGES 644개          URL 을 손으로 박았다. 사이트맵도 재귀도 안 쓴다
<th>담당부서</th>      이 사이트의 footer 구조
#contents            이 사이트의 본문 div id
"○○과" -> 과          한국 지자체 조직명 규칙 + 예외 25건 목록
issued_at 12종        수원시 서류에서 관찰된 발급처
content_type 2종      이 사이트 페이지가 두 종류더라
표 15행 임계          이 사이트 표 크기 분포를 보고 정했다
게시판 열 이름         thead th 로 읽지만 "담당부서"라는 이름을 안다는 전제
```

**새 사이트에서는 이 중 하나도 안 맞는다.**

**아이러니**

신호 3층 중 **사이트에 안 묶인 층은 3층(LLM)뿐인데, 우리는 그걸 제일 적게 쓴다.**

```
1층 사이트 자체 분류   사이트마다 다름. 통째로 다시 짜야 한다
2층 HTML 구조        사이트마다 다름. 통째로 다시 짜야 한다
3층 문장 의미(LLM)    유일하게 사이트에 안 묶인 층
```

##### 1-9. A2 게이트 · B 1·2층은 언제 필요한가 (2026-09-02 실측)

설계에는 있는데 구현이 없는 두 가지다. **지금 필요 없는 이유와 나중에 필요한 이유가 다르다.**

**지금은 이득이 없다.** 1층(URL·breadcrumb)이 `content_type` 을 얼마나 맞히는지 재 봤다 — 644건의 LLM 판정을 정답으로 놓고 대조했다.

```
URL 구역 다수파로 맞히기        467/644 = 73%
breadcrumb 다수파로 맞히기      530/644 = 82%
(항상 reference 로 찍어도)              59%

한쪽으로만 몰린 breadcrumb 분류
  8건 이상 기준    6종 · 77건 · 12%
  5건 이상 기준   15종 · 127건 · 20%
  3건 이상 기준   38종 · 206건 · 32%
```

이유는 **breadcrumb 이 주제를 나타내지 행동 여부를 나타내지 않아서**다.

```
21건  proc 18 / ref  3   분야별정보 > 복지 > 생애주기별 > 영유아

```

같은 메뉴 안에 신청하는 것과 현황 안내가 섞여 있다.

그리고 **캐시(`content_key` = 본문+프롬프트 해시)가 이미 있어서 재실행 비용이 0** 이다. 1층으로 아끼는 것은 첫 수집의 12%뿐인데, 오판하면 `validate/01` 규칙과 답변이 직접 깨진다. 게다가 지금 "순수한" 분류가 앞으로도 순수하리란 보장이 없다 — `임신·출산` 20건이 지금 전부 procedure 인데 그 메뉴에 현황 페이지가 하나 추가되면 1층이 그것을 자신 있게 오판한다.

**"이득 12% vs 조용한 오판 위험"이 나쁜 거래**라는 것이지, 원리적으로 틀렸다는 뜻은 아니다.

**규모가 커지면 역할이 뒤바뀐다.**

```
지금 질문    1층이 LLM 만큼 정확한가?              -> 아니오 (73%)
규모 질문    1층이 LLM 을 부를 것을 얼마나 줄이나?   -> 이것이 핵심이 된다
```

```
지금            644 페이지 × 5패스 = 3,220 호출. 캐시 있어 재실행 0
게시판 본문 추가   10만 건 × 5패스 = 50만 호출. 비용도 문제지만 벽시계 시간이 며칠
```

**여기서는 "전부 LLM 에 보낸다"가 불가능하다.** 1층의 일이 판정이 아니라 **걸러내기**가 된다 — 버리는 것은 틀려도 회복 가능하지만(다시 넣으면 된다) 판정을 틀리는 것과는 위험이 다르다.

**A2 게이트가 더 급하다.** 지금은 `PAGES` 644개를 사람이 골라 놔서 게이트가 판정할 대상 자체가 없다. 실제로 하려면 순서가 이렇다.

```
① 사이트맵/재귀 크롤링으로 페이지를 발견
② 그중 무엇을 받을지 판정        <- A2 게이트. 지금 없다
③ 받은 것을 분류                <- B 1·2·3층
```

**②가 없으면 ①을 못 한다.** 재귀로 훑으면 신고센터·정보공개·시정소식이 다 딸려 들어와 "시민이 신청할 수 있는 것"이라는 노드 정의가 깨진다.

**아직 안 재본 쓸모 하나** — 1층을 라우팅이 아니라 **검사**로 쓰는 것. breadcrumb 이 100% procedure 인 구간인데 LLM 이 reference 라고 했다면 표시해서 사람이 본다. 검사는 틀려도 마커만 붙고 적재는 되므로 손해가 없다. `validate/01` 의 D1/D2 와 같은 자리다.

**그것만으로 범용이 되지는 않는다.** A2·B 1·2층은 범용성의 필요조건이지 충분조건이 아니다 — 만들어도 새 사이트를 붙이려면 셀렉터(`#contents`)와 메타 파싱(`th/td`), 조직명 규칙, 발급처 어휘를 다시 짜야 한다.

**아직 정하지 않았다.**

##### 1-10. 무엇이 바뀌었는가 — `content_hash` (2026-09-02)

각 레코드에 본문 지문을 싣고, 이전 배치와 대조해 리포트를 낸다.

```
이전 배치 대비: 신규 3 · 변경 12 · 그대로 629
  [변경] 인감증명발급
  [변경] 여권발급 수수료
```

**재수집을 줄이지는 못한다.** 이 사이트는 캐시 헤더를 하나도 안 준다(실측).

```
ETag             없음
Last-Modified    없음
Cache-Control    없음
```

조건부 요청(`If-None-Match` / `If-Modified-Since`)이 불가능해서 **받아 봐야만 바뀐 것을 안다.**

**LLM 추출은 이미 증분이었다.** 처음에 "본문이 그대로여도 다시 뽑는다"고 봤는데 틀렸다 — `content_key()` 가 `sha1(content + prompt)` 라 다섯 패스 전부 내용 기반 캐시다.

```
content_key(record)
    prompt = json.dumps(EXTRACT_TOOL, sort_keys=True)
    raw = (record.get("content") or "") + "\x00" + prompt
    return sha1(raw)
```

그래서 `content_hash` 의 값은 절감이 아니라 **검증**이다. 재수집하면 뒤이어 도는 `02`~`07` 이 바뀐 페이지만 LLM 에 보낼 텐데, **그 수가 이 리포트와 맞아야 정상**이다. 지금까지는 그것을 대조할 방법이 없었다.

그래프에도 싣는다(`CivilService.content_hash`) — 원천과 적재 결과를 대조할 수 있게.

```
  -> ISSUED_AT 3개
```

값을 파싱하지 않고 **표로 적는다.** `issued_at` 은 규칙 12개가 만드는 닫힌 목록이라, 구분자로 쪼개는 코드는 규칙이 늘 때 조용히 깨지지만 표는 안 맞는 값이 오면 즉시 멈춘다(`check_vocabulary()`).

값의 성격이 셋으로 갈린다.

```
① 진짜 가야 하는 곳   의료기관·은행·세무서         106종 (17%)  -> ISSUED_AT
② 안 떼도 되는 것     접수처 비치·본인 소지        281종 (46%)  -> 플래그만
③ 모름                                       222종 (36%)  -> 아무것도 안 붙임
```

대체 관계("이 중 아무 데나")는 별도 표현이 없다. `issued_at` 이 서류 하나의 단일 속성이라 한 서류의 `ISSUED_AT` 대상들은 언제나 같은 값에서 나온다 — **구조적으로 이미 서로 대체다.**

##### 2-8. 적재 후 검사 — `validate/01_requirements.py`

완성된 그래프를 보고 검사한다. **위반을 표시하되 지우지 않는다.**

```
NO_DEPT             error   담당부서 없음 (external_org 면제)
PROC_EMPTY          error   procedure 인데 절차도 서류도 없음
PROC_NO_STEPS       warn    procedure 인데 절차 없음
PROC_NO_DOCS        warn    procedure 인데 구비서류 없음
DEPT_NOT_BODY       error   담당부서가 실무조직이 아님
```

현재 128건 (error 14 / warn 114).

**클래스별로 필수가 다르다는 것이 요점이다.**

```
              전체   담당부서없음   구비서류없음   절차없음
procedure     263        5           77          51
reference     381        8          372         375
```

`reference` 가 구비서류·절차 없는 것은 정상이다(381 중 372·375). 같은 빈칸이 클래스에 따라 결함이기도 하고 정상이기도 하다.

**라벨이 아니라 `violations` 속성**으로 표시한다. 라벨은 재실행 때 `REMOVE` 를 빠뜨리면 옛 판정이 남고, `:Entity` 가 벡터 검색 입구라 라벨을 늘리는 데 조심할 이유가 있다.

조직 나무 검사는 별도이고 **중단**이다.

```
PART_OF_DIRECTION   총괄기관이 실무조직 밑에 붙으면 sys.exit    현재 0/938
```

마커가 아닌 이유는 이것이 데이터 품질이 아니라 **구조 파손**이라서다. `main.py` 순서상 `validate/01`(76) -> `relationships/05`(77) -> `embedding/01`(79) 이라 추론과 임베딩 전에 멈춘다.

##### 2-9. 추론 — `relationships/05_inferred.py`

★ **추론 액션.** 저장된 적 없는 관계를 원천 관계에서 합성한다.

```
IN_CHARGE_BUREAU   HANDLED_BY / PART_OF*0..5    583   민원 -> 소관 국
VISIT_FOR          REQUIRES / ISSUED_AT         266   민원 -> 서류 -> 발급처
```

소관은 **가장 가까운 조상 하나만** 남긴다. 대상 레벨은 `schema.bureau_levels()` 7종이고 시장·부시장은 빠진다 — 모든 민원이 거기로 올라가 답이 되지 못한다.

**역관계는 만들지 않는다.** LPG 는 관계를 역방향으로 그냥 타므로 엣지만 두 배가 된다. **전이 관계도 물질화하지 않는다** — 질의 때 가변 길이로 푼다.

##### 2-10. 생애주기 — `lifecycle/01_mark_stale.py`

`last_seen != BATCH_ID` 인 노드를 `abolished` 로 바꾸고 `:Entity` 를 뗀다.

전략이 하나가 아니라 넷이다.

```
시간축      OrgUnit · Employee · CivilService     MERGE + last_seen
전량 교체    Article 등                           DETACH DELETE 후 재적재
고아 정리    DocumentType · Regulation            참조 0이 되면 삭제
부모 종속    Attachment                           글이 지워지면 같이
```

서류를 시간축으로 관리하면 안 되는 이유: 민원 하나가 사라진 것이 서류가 없어진 것은 아니다. **참조가 0일 때 지우는 것이 맞다.**

현재 `last_seen` 을 쓰는 것은 3라벨뿐이라 Place·DocumentType·WasteItem·Regulation·Article 이 추적 밖이다.

##### 2-11. 온톨로지가 적재에서 하는 일

적재 28단계 중 **11곳**이 `ontology/` 를 읽는다. 두 종류로 갈린다.

**선언(`schema.yaml` + `schema.py`) — "무엇이 무엇인가"**

```
nodes/01      org_class_of()            unit_level 이 선언된 어휘인지 확인
nodes/12      domain_depth()            구역별 계층 깊이 (분야별정보 3 / 종합민원 2)
rel/03        body_fallback_levels()    본문에서 조직명 찾을 후보 레벨 6종
rel/05        bureau_levels()           소관으로 답할 수 있는 레벨 7종
validate/00   vocab("content_type")     닫힌 어휘 검사 -> 위반이면 중단
validate/01   org_classes()             HANDLED_BY Range · PART_OF 방향
```

**파서(6모듈) — "문자열을 값으로"**

```
nodes/01      classify.py      조직 이름 -> unit_level
              aliases.py       unit_level -> 시민 통칭 별칭
nodes/04      fees.py          금액 파싱 · 내는 돈/받는 돈 방향
              inquiry.py       외부기관 명시 목록
nodes/05,15   documents.py     서류명 정규화 + 발급처 판정
nodes/06      regulations.py   법령명·조항 분리
rel/03        inquiry.py       본문 "문의" 섹션 파싱
```

수집이 `ontology` 를 직접 쓰는 곳은 `scraping/04` 하나뿐이다. **선언은 수집이 안 읽는다** — 선언이 하는 일(닫힌 어휘 검사·관계 Range·계층 깊이)은 전부 그래프에 넣을 때 따지는 것이라 적재·검증 쪽에 있다.

##### 2-12. 선언과 그 선언이 만드는 라벨은 다르다

`org_classes` 로 `:총괄기관`·`:실무조직` 라벨까지 만들었다가 **라벨만 걷어냈다**(2026-09-02).

```
라벨을 읽는 곳   없음. 검색·라우터·검증 어디에서도 (o:실무조직) 을 안 썼다
unit_level      같은 답을 내면서 "국만"·"구만"도 물을 수 있다. 인덱스도 있다
disjoint        선언은 강제하는데 적재기가 SET 만 하고 REMOVE 를 안 했다
```

**선언은 계속 일한다.** `schema.py` 가 그것을 unit_level 닫힌 어휘 대장으로 써서 `bureau_levels` 오타를 잡는다. `content_type` 이 라벨이 아니라 속성인 것도 같은 판단이다.

##### 2-13. LLM 출력이 셋으로 갈린다

```
documents[]       ->  (:DocumentType) 노드 609개 + REQUIRES
regulation_text   ->  (:Regulation) 노드 192개 + BASED_ON {article:"제19조"}
procedure_text    ->  CivilService.procedure_text   속성
content_type      ->  CivilService.content_type     속성 (라벨 아님)
```

**노드로 만드는 기준은 "여러 민원이 공유하는가"다.**

```
신분증        수백 개 민원이 공유   -> 노드. "신분증 필요한 민원 전부"를 물을 수 있다
인감증명법     여러 민원이 참조      -> 노드
"1. 신청서 작성 …"  그 민원만의 것  -> 속성. 노드로 만들면 609개 쓰레기 노드
```

##### 2-14. 적재의 설계 원칙 넷

```
LLM 을 안 쓴다        판단이 결정적이어야 한다. 쓰면 실행마다 그래프가 달라진다

```

## 3. 임베딩 — `embedding/01`~`03`

##### 3-0. 무엇을 임베딩하는가

```
embedding/01  OrgUnit       940 -> 190      롤업 정리로 749개에서 :Entity 를 뗀다
embedding/02  CivilService  644
embedding/03  Employee    5,077
                          ─────
:Entity                   5,911            벡터 검색 후보 전부
```

모델은 `text-embedding-3-small`, 1536차원, 코사인.

##### 3-1. `:Entity` 가 검색의 입구다

이 라벨이 있으면 벡터 검색에 잡히고 없으면 안 잡힌다. 인덱스가 `FOR (n:Entity) ON (n.embedding)` 이라 라벨 하나로 후보 집합이 정해진다.

```
붙이는 것    OrgUnit · CivilService · Employee
안 붙이는 것  Article · Attachment · Place · WasteItem · Domain · Issuer · Board
```

**안 붙이는 쪽은 일부러다.** 게시글 3,771건이 후보에 섞이면 주제가 제각각인 글이 민원·조직을 밀어낸다. 그것들은 **구조 질의(이름 정확 일치·관계 순회)로만 닿는다.**

폐지된 노드도 `:Entity` 를 떼서 후보에서 빠진다(`lifecycle/01`).

##### 3-2. OrgUnit 은 940개 중 190개만 넣는다

조직이 **자기 이름으로 내건 '주요업무'가 있는 것**만 대상이다. `행정민원팀` 44개가 전부 후보로 뜨면 검색이 그것으로 뒤덮인다.

이 동작이 `nodes/01` 의 `MERGE` 설계를 강제한다 — 749개에서 라벨을 떼므로, `MERGE` 패턴에 `:Entity` 를 넣으면 다음 실행에서 패턴이 안 맞는다.

##### 3-3. CivilService 임베딩 텍스트의 구성

```
이름 + 별칭 + 본문 + 표 품목명(800자 상한)
MAX_CHARS = 6000            text-embedding-3-small 한도가 8192 토큰
평균 1,061자 · 중앙 701자 · 최대 6,000자
```

**별칭을 넣는 이유.** 별칭은 "시민이 공식 명칭과 다른 말로 부른다"를 다루는 값인데, 컨텍스트 블록에만 쓰고 임베딩에서 빠뜨리면 정작 검색 단계에서 못 쓴다. 실측 사고가 있었다 — 교통 데이터를 넣자 "등본 관련해서 어디에 문의"가 자동차 `등록증재교부`(0.7831)·`등록원부발급`(0.7697)에 밀려 정답인 `등초본 발급` 이 25위 밖으로 사라졌다. 별칭 "등본"이 임베딩 텍스트에 있으면 정답 쪽이 직접 매칭된다.

**표는 원문이 아니라 이름만 넣는다.** 가장 큰 표가 355행 27,000자다. 통째로 넣으면 임베딩이 숫자·규격으로 뒤덮인다. 각 행의 첫 '이름 같은' 칸만 모으고 숫자만 있는 칸은 건너뛴다.

##### 3-4. 증분 임베딩 (2026-09-02)

한때 매 실행마다 전량을 다시 보냈다. 지금은 **텍스트와 모델이 그대로면 건너뛴다.**

```
평상시     0/190 · 0/644 · 0/5077     OpenAI 호출 0회
바뀌면     1/644                      정확히 그것만
--all      비교를 건너뛰고 전량 재생성
```

**별도 해시 속성을 안 만들었다.** 세 스크립트가 이미 `embedding_text` 를 노드에 저장하고 있고 그것이 곧 `build_text()` 의 출력이라 그대로 비교하면 된다. 해시를 따로 두면 텍스트와 해시가 어긋날 자리가 하나 더 생긴다.

**모델 이름은 새로 넣었다**(`embedding_model`). 같은 텍스트라도 모델이 갱신되면 다른 벡터가 나오는데, 그 판단을 사람 기억에 맡길 수 없다.

**롤업 정리 의미는 유지했다.** 전부 지우고 다시 만드는 대신 **대상이 아닌 것만** 지운다. `01` 이 749개에서 `:Entity` 를 떼는 동작은 그대로고, 그것이 `nodes/01` 의 `MERGE` 가 `org_id` 로만 걸려야 하는 이유다.

왜 이것이 중요한가 — 전량 재생성이면 `main.py` 전체 실행이 부담스러워지고, 그래서 안 돌리게 되고, **전체를 돌려야만 드러나는 버그가 잠복한다.** 실제로 `nodes/01` 의 `MERGE` 라벨 문제가 0828부터 몇 주 동안 안 드러났다.

##### 3-5. 표를 빼는 안은 실측으로 기각했다

표를 가진 민원 70건을 표 없이 재임베딩해 순위 변화를 봤다(그래프는 안 건드리는 오프라인 시뮬레이션).

```
좋아짐 0 · 나빠짐 1 · 그대로 11
나빠진 것: "기초생활수급자 지원" 1위가 맞춤형 기초생활보장제도 -> 청년기본소득
```

이유는 애초에 희석이 안 될 만큼 작아서다 — 표 원문 평균 3,937자인데 임베딩 기여분은 최대 800자이고, 표를 가진 민원이 70/644(11%)뿐이다.

##### 3-6. 임베딩이 긴 것들은 표 때문이 아니다

상위 12개 중 10개가 표 0자다.

```
복지·문화              6,000자(본문 10,387)   표 없음   ← 유일한 묶음 페이지, 제도 58개
보험 및 신청 안내        6,000자              표 없음
대설, 한파             6,000자              표 없음
태풍, 강풍             5,475자              표 없음
경보에 따른 행동요령      5,403자              표 없음
중고차 허위매물 체크리스트  4,820자              표 없음
수원 국가유산 허용기준     6,000자              표 19자
수질 및 수생태계 환경기준   4,561자              표 205자
```

**본문이 원래 긴 안내문**이다. 재난 행동요령·체크리스트·현황은 한 페이지가 곧 한 주제라 쪼갤 근거가 없다. 여러 사업이 뭉친 것은 `복지·문화` 하나뿐이고(597줄, 청년기본소득이 별도 노드로도 있는데 여기 또 들어 있다), 644건 중 1건이라 지금 손댈 값어치가 없다고 판단했다.

## 4. 검색 — `search/pipeline.py`

##### 4-0. 단계 전체

```
(0)   리더 숏컷        "시장이 누구야" -> Employee 직행            LLM 안 탐
(1)   구조 라우터       대형폐기물 요금 / 조직 목록 / 민원 집계        LLM 안 탐
(1.7) 별칭 확장        "안 가면" -> "불참"                        68개 사전
(2)   벡터 검색        풀 60건
(2b)  어휘 자리보장     BM25 1건, 임계 14 이상만
      의문사 제거       "어디서" 같은 어절을 통째로 뺀다
(2c)  직원 어휘        직위를 그대로 물은 질문. 절대 임계 30
(2.5) 지역 감지        구·동 언급 시 재랭킹
      조직명 완전일치    이름이 통째로 들어 있으면 1위 승격
(3)   컨텍스트 조립     후보 5건 -> 블록 5개 (+ 첨부 블록)
(4)   LLM 답변 합성                                            LLM 1회
```

**앞쪽 두 단계는 LLM 을 안 탄다.** 구조 질의는 그래프 집합 연산으로 정확한 답이 나오므로 유사도로 겨룰 이유가 없고, 비용도 0이다.

##### 4-1. 구조 라우터가 가로채는 것 셋

**대형폐기물 요금** — 표 한 행이 곧 답이라 유사도로는 못 찾는다. 실측: "냉장고 처리 얼마"는 벡터 1~10위 점수 폭이 0.013 이라 사실상 무작위였고, 어휘는 파이프라인이 1위 하나만 받는데 그 자리를 "공유냉장고"가 세 번 나오는 무관한 표가 가져갔다. **이름 정확 일치로 조회한다.**

**조직 목록** — "국 목록", "장안구 동 목록" 같은 질의. `unit_level` 인덱스로 푼다.

**민원 집계·필터** — 축이 넷이다.

```
domain              분야
dept                담당부서
has_regulation      법령근거 있는 것만
requires_document   특정 서류가 필요한 것만
fee_min / fee_max   수수료 범위
benefit_min/max     지원금 범위       ← 수수료와 반대 필드를 본다
```

같은 금액 조건이라도 "수수료 3만원 이상"과 "지원금 3만원 이상"은 보는 필드가 반대다.

**두 라우터가 동시에 걸릴 수 있다.** 실측: "동 행정복지센터에서 처리하는 민원 목록"이 토큰 '동'에 걸려 조직 목록으로 가는 바람에 민원이 아니라 44개 동 이름을 반환했다. 그래서 "민원을 나열해달라는 질문인가"(`asks_for_civil`)를 보고 조직 라우터를 끈다.

##### 4-2. 척도가 셋 섞여 있다

```
코사인      0.7x        벡터
BM25       14~80       어휘 (풀텍스트)
구조 결과   점수 없음     라우터
```

섞어 정렬하면 BM25 가 무조건 이긴다. 그래서 **점수로 겨루게 하지 않고 자리만 보장한다.**

실측하면 1위가 5위보다 점수가 낮은 질문이 나온다(`전입신고 어떻게 해` 0.7470 < 0.7489). 설계상 그런 것이고, **그래서 이 필드로는 "점수 뭉침"을 잴 수 없다** — 벡터 경로만 따로 봐야 한다.

##### 4-3. BM25 를 네 가지로 다르게 쓴다

같은 어휘 검색인데 자리마다 쓰는 법이 다르다.

```
민원 제목      자리 보장 1건      LEXICAL_KEEP=1. 점수 경쟁에 안 넣는다
직위          절대 임계 30       EMP_LEXICAL_MIN. 짧은 칸이라 임계가 높다
담당업무       합의 필터         벡터 후보에 이미 있는가로 거른다
직원 좁히기    범위 안 순위       조직이 정해진 뒤 그 안에서 8명
```

##### 4-4. 풀 60은 LLM 에 안 간다

```
벡터 풀     60건    지역·동명 조직이 아래쪽에 있어 넓게 잡는다
최종 후보    5건     평균 6,340자 ≈ 3,200 토큰
```

풀을 넓게 잡는 이유는 실측이다 — "팔달구 반려동물 등록"의 정답인 팔달구 산업팀은 0.688 로 50위권이라 20으로는 아예 안 들어오고, 시 전체 담당인 반려동물센터 0.794 만 남아 지역 답변이 사라졌다.

정답의 위치는 이렇다.

```
1위       13/25
5위 안    23/25
60위 안   25/25
```

##### 4-5. 어휘 경로의 세 장치 (2026-09-02)

```
임계 14         BM25 는 후보가 없어도 남은 것 중 제일 나은 것을 내놓는다.
                검증 없이 1번 자리에 앉히면 오답이 정답을 밀어낸다.
                gold 26문항 실측: 자리보장이 구해낸 것 1 · 중복 12 · 해로운 것 13.
                임계 14 아래 4건은 전부 오답이고 정답 손실 0

의문사 제거      "여권 신청 어디서 해"의 '어디서'가 '어디서나민원'과 물려 32.4점
                1위를 먹었다. 어절 전체가 일치할 때만 뺀다 — 부분 문자열로
                지우면 "어디서나FAX민원이 뭐야"가 깨진다.
                서술어("있어"·"해")까지 넣었다가 "청년 관련 정책 뭐가 있어"의
                1위가 오답으로 바뀌어 되돌렸다

조직명 완전일치   시민이 이름을 그대로 불렀으면 유사도로 겨룰 일이 아니다.
                "장안구보건소 어디에 있어"의 1위가 '보건소 취약계층 건강 지원'
                (어휘 47.8)이었고 주소를 가진 장안구보건소는 2위였다.
                긴 이름 우선(장안구보건소 > 장안구), 3글자 미만 제외
```

##### 4-6. 지역 처리

지역명은 **임베딩용 텍스트에서만 뺀다.** 부서 임베딩에는 구·동 이름이 아예 없어서(소속을 그래프 관계로만 안다), 지역명을 남겨두면 임베딩이 그쪽으로 쏠린다 — 실측: "권선구 세무 관련 문의"에서 세무과가 3등(0.72)에서 247등(0.64)으로 폭락했다.

지역 일치 판정은 그래프 경로로 따로 한다. 그리고 지역을 안 물었는데 구·동마다 있는 동명 조직이 상위를 채우면(실측: "재산세 세율"에서 재산세팀 3개가 top5 를 차지) **같은 이름은 최고점 하나만 남기고 `peer_count` 로 "N개 구에 각각 있다"를 따로 전달한다.** 그래야 답변이 특정 지점을 찍는 대신 거주지 관할로 안내할 수 있다.

##### 4-7. 현재 품질

```
1위 적중     16/16       gold 26문항 중 top1 을 지정한 16문항
후보 정밀도   35%          후보 5건 중 관련 있는 것
첨부 적중     4/4
속도         평균 0.30s · 최대 0.95s
```

**후보 정밀도 35%는 올릴 대상이 아니라고 판단했다.** 여덟 가지를 시도해 전부 실패했다 — 후보를 2건으로 줄이면 정답을 통째로 잃는 질문이 8건이고, 블록 길이 상한은 정답 블록도 똑같이 깎는다(정답 평균 1,300자 vs 오답 1,396자). 그리고 잡음은 LLM 이 걸러 낸다 — 수도계량기 2/5, 민방위 3/5인데 답변은 정확했다. **답이 깨지는 것은 정밀도가 0/5일 때뿐이다.**

개선은 "잡음 줄이기"가 아니라 **"틀린 1위 찾아 고치기"** 로 간다.

## 5. 답변 조립 — `context.py` -> `synthesize.py`

##### 5-0. 후보 하나가 블록 하나가 된다

```
부서 블록    이름 · 별칭 · unit_level · 소관 국 · 주소(자기 것인지 표시) ·
            직원 목록 · 최근 소식(180일, 서식 게시판 제외)
민원 블록    본문 · 구비서류(발급처별로 묶음) · 채널 · 기한 · 제재 · 담당부서
첨부 블록    질문에 서식·신청서 같은 말이 있을 때만. 후보와 별도로 붙는다
```

##### 5-1. 구비서류를 발급처별로 묶는다

그냥 나열하면 24줄이 된다. 발급처 조합이 같은 것끼리 묶으면 6줄이다.

```
stops           진짜 가야 하는 곳. 발급처 조합으로 묶음
no_issue_docs   접수처 비치·본인 소지 — 안 떼도 되는 것
unknown_docs    발급처를 모르는 것
```

발급처를 이름만 주면 LLM 이 "어디서 떼느냐"를 컨텍스트의 다른 주소로 메운다(실측: 통장사본 -> 동 행정복지센터). 그래서 서류명과 발급처를 짝으로 넘긴다.

##### 5-2. 첨부 블록은 네 장치가 함께 필요했다

```
트리거 게이트   질문에 서식·양식·신청서·청구서·신고서 같은 말이 없으면
              조회 자체를 안 한다. 기준선 20문항 오탐 4 -> 0

자식 1칸 순회   (o)<-[:PART_OF*0..1]-(:OrgUnit)<-[:POSTED_BY]-(:Article)
              시민이 아는 이름은 '과', 글 올리는 건 그 밑 '팀'

임계 5        6점 이상은 전부 정답, 4점 이하는 전부 오답이었다.
              4점 이하가 오답인 이유는 그 질문에 맞는 파일이 아예 없어서다 —
              후보가 비면 BM25 는 남은 것 중 제일 나은 쓰레기를 준다.
              임계는 "없으면 없다고 답하게" 만드는 장치다

전역 15점      파일명이 질문어를 통째로 담으면 관계 없이도 정답이다.
              트리거를 통과하지만 첨부가 답이 아닌 질문 10건의 전역 1위
              최고점이 9.0 이라 그 위에 선을 그었다
```

관계 경로와 전역 경로를 **합쳐서** 점수로 세운다. "관계가 못 찾았을 때만 전역"으로 했더니 관계가 문 10.6짜리 때문에 전역의 20.4짜리 정답이 영영 안 나왔다 — **관계가 뭔가 찾았다는 것이 그것이 최선이라는 뜻은 아니다.**

같은 파일명은 최신 하나만 남긴다. `file_id` 가 다운로드 uuid 라 글에 다시 올릴 때마다 새 노드가 생기고, 서식은 개정되므로 최신이 맞다.

##### 5-3. 지시문이 앞 단계와 중복되면 안 된다

블록 지시문이 "질문이 서식·양식을 찾는 것일 때만 안내하라"였다. 트리거 게이트가 없던 시절 LLM 이 게이트 노릇을 하던 흔적인데, 그대로 두니 **답을 손에 쥐고도 안 줬다.**

```
"출생신고 서류 뭐 필요해"
  받은 후보  출생신고서(1).hwp  10.9
  실제 답변  "출생신고에 대한 구체적인 서류 목록이 포함되어 있지 않습니다"
```

판정 기준을 '질문의 종류'에서 **'파일이 질문 내용과 맞는가'** 로 옮겼다. 걸러야 할 것은 질문 종류가 아니라 딸려온 홍보물이다.

교체 후 각 질문 3회 반복 실측: **18/18 의도대로**(정답 4종 전부 3/3 등장, 홍보물 2종 전부 0/3).

##### 5-4. 환각 방지는 프롬프트가 담당한다

`synthesize.SYSTEM_PROMPT` 에 "1번을 통과하는 후보가 하나도 없으면 절대 억지로 답을 만들지 마라"가 있다. 후보 정밀도가 35%인 상태에서 이것이 실질적 방어선이다.

브리지 경로(`make_answer=False`)는 이 단계를 건너뛰므로 방어가 통째로 빠진다 — 실측: "수원화성 관람료"에서 후보 5건에 관람료가 한 줄도 없는데 LLM 이 "성인 1,000원"을 지어냈다. 그래서 브리지 쪽에 `VECTOR_GUARD` 를 따로 붙였다.

## 6. 외부 연결

##### 6-0. 프로세스 둘

```
KG API   api/server.py     :9020   전역 python        POST /kg/search
브리지    bridge/app_kg.py  :9010   .venv-bridge      /ask_kg?mode=rag|kg|hybrid
```

인터프리터를 나눈 이유는 의존성 충돌이다 — `opik -> litellm` 이 Chatty 의 `openai==1.70.0` 핀과 충돌한다. 브리지는 KG 를 HTTP 로만 부르므로 neo4j·openai·opik 이 필요 없다.

##### 6-1. `make_answer=False` 가 기본이다

Chatty 는 KG 결과를 기다리는 예산이 짧고(기본 2초, 브리지가 10초로 늘림), 답변은 Chatty 의 LLM 이 만든다. KG 가 자기 답을 또 만들면 3~6초가 붙어 통째로 버려진다.

그래서 KG 는 **근거(`context_blocks`)만 반환**한다.

##### 6-2. Chatty 소스는 안 건드린다

함수를 감싸서 KG 항목을 앞으로 옮긴다. Chatty 의 키워드 재정렬에 KG 블록을 그냥 태우면 밀린다 — 실측: 맨 앞에 넣은 KG 집계가 17건 중 13번째로 밀려 LLM 이 사실상 무시했다.

**애초에 범주가 다르다.** 재정렬은 같은 코퍼스의 동질적인 문서 청크를 줄 세우는 장치인데, KG 블록은 문서가 아니라 이미 답에 가까운 요약이다.

첨부 블록도 같은 이유로 경쟁에서 뺀다. Chatty 자신이 첨부에서 같은 문제를 같은 방식으로 풀었다 — `app.py:3104` "첨부 chunk는 일반 검색 결과와 같은 풀에서 경쟁시키지 않는다."

##### 6-3. Chatty 가 받는 쪽의 제약

```
url 이 없으면 통째로 버려진다              app.py 2655/2955
title 이 겹치면 버려진다                   2650
항목마다 1400자로 잘린다                   3166
답변 컨텍스트에는 상위 3건만 들어간다        3193
```

집계 질의가 이 제약에 정면으로 걸린다. 그래프가 센 22건은 hits 에 이름만 있고 url 이 없어 하나도 안 들어가고, url 을 붙여도 항목을 쪼개면 3건만 남아 "22건 중 3건"이 정답인 양 나간다. **그래서 집계·구조 경로는 완성된 목록을 통째로 항목 하나에 담는다.**

##### 6-4. `make_answer` 두 경로를 따로 재야 한다

로컬에서 18/18 로 확인한 첨부가 브리지를 통과하면 하나도 안 나왔다. 로컬 시험은 `make_answer=True`(KG 자체 LLM)였고 브리지는 `False` 인데 **그 경로를 한 번도 안 쟀다.**

원인은 브리지가 `context_blocks` 와 `hits` 를 1:1 순서로 소비하는데 첨부 블록만 짝이 없어서, 엉뚱한 이름이 달리고 `max_items` 컷에 먼저 잘린 것이었다. 별도 필드(`attachment_block`)로 내고 맨 앞자리를 보장하게 고쳤다.

##### 6-5. 3조건 비교

브라우저에서 같은 질문을 세 조건으로 돌려 본다.

```
① rag      기존 벡터만
② kg       그래프만
③ hybrid   둘 다
```

관측된 것(3문항):

```
             ① rag        ② kg       ③ hybrid
수도계량기     24.0s        7.3s       11.6s
민방위        19.0s        7.2s       23.4s
FAX민원       —           양호        양호
```

②가 답변 밀도·속도 모두 좋다. ③은 부서 대표번호처럼 벡터 쪽에만 있는 정보가 필요할 때만 이득이 있는데 2배 느리다. **어느 쪽을 기본으로 할지는 20문항으로 세야 정해진다.**

## 7. 검증 — `validate/00`~`04`

##### 7-0. 다섯 개가 각각 다른 것을 본다

```
00  적재 전 모순      원천 JSON      위반이면 중단
01  적재 후 결함      그래프         마커 128건 / 구조 파손은 중단
02  게시글 사전 검사   원천 JSON      id 중복 · 필수 필드 · 날짜 형식 · file_id 충돌
03  기준선 생성       그래프 + 검색   라벨·관계·제약·status·원천 해시·임베딩 수·
                                 violations·unit_levels + 검색 20문항
04  검색 품질        검색           gold 26문항. 1위 적중 · 후보 정밀도 · 첨부 적중
```

##### 7-1. `03` 과 `04` 는 목적이 다르다

```
03 (search20)  "어제와 같은가"      변화 유무만 본다
04 (gold)      "정답이 1위인가"     품질을 본다
```

**03만으로는 안정적으로 틀린 것을 통과라고 부른다.** 실제로 회귀 20/20 을 통과하면서 `여권 신청 어디서 해` 가 `어디서나민원(FAX민원)` 을 1위로 내놓고 있었고, `출생신고 서류 뭐 필요해` 는 후보 5건이 전부 무관했다.

`04` 를 만들고 재니 1위 적중이 14/16 이었고, 원인 셋을 고쳐 16/16 이 됐다.

##### 7-2. 정답 라벨의 형식

```json
"수도 계량기 고장나면 어디에 연락해야 해": {
  "top1": "급수팀",
  "relevant": ["급수팀", "수도요금팀", "상하수도란?"],
  "note": "고장 접수는 급수팀. 요금 관련이면 수도요금팀도 답이 된다."
}
```

```
top1       1위여야 하는 것 하나. 여럿이 타당하면 null 로 두고 채점하지 않는다
relevant   후보로 들어와도 좋은 것 전부. 정밀도를 잰다
attach     서식 첨부가 답의 일부인 질문
aggregate  집계 질문. 목록 전체가 답이라 정밀도 계산에서 뺀다
note       판정 근거. 애매한 판정은 반드시 남긴다
```

##### 7-3. 라벨 자체를 검산한다

`gold.json` 의 이름이 그래프에 없으면 멈춘다. 첫 실행에서 바로 일했다 — `냉장고` 를 "그래프에 없다"고 판정했는데, 대형폐기물 요금은 `WasteItem` 노드에 있고 검산 쿼리가 `CivilService`·`OrgUnit` 만 보고 있었다. **도구가 맞고 쿼리가 좁았다.**

라벨을 사람이 적는 이상 라벨도 틀린다. 실제로 두 번 틀렸다.

```
부서 답을 오답으로 셌다     전입신고·민방위·전기차는 민원과 부서 둘 다 1위로 타당
품목 노드를 놓쳤다         대형폐기물은 가격표 페이지가 아니라 WasteItem 이 답
```

1위 적중이 13/19 -> 14/16 이 된 것은 **채점 기준이 틀렸던 것이지 검색이 좋아진 게 아니다.**

##### 7-4. 경로를 갈라서 센다

`hits` 의 `score` 는 단일 척도가 아니므로, 어느 경로가 그 후보를 만들었는지를 표식으로 본다.

```
어휘 42 · 벡터 96 · 지역 3      (26문항, 후보 141건)
```

벡터가 대부분이고 어휘는 자리보장이라 대체로 맞는다.

##### 7-5. 0건일 때 규칙을 넣어야 한다

`DEPT_NOT_BODY`·`PART_OF_DIRECTION` 은 도입 시점 위반이 각각 0/700, 0/938 이었다. 나중에 넣으면 이미 쌓인 위반이 무더기로 떠서 **진짜 새 위반이 그 안에 묻힌다.**

그리고 **한 번도 안 걸려 본 규칙은 일부러 깨뜨려 봐야 한다** — 쿼리가 틀렸어도 0을 낸다. 시험용 노드를 매달아(국을 과 밑에) 둘 다 잡히는 것을 확인하고 치웠다.

##### 7-6. 기준선은 재현 가능해야 한다

`validate/03` 은 스크립트다. 손으로 뜨면 무엇을 어떻게 셌는지가 안 남는다 — 인덱스 DDL 을 `schema/01` 한 곳에 모은 것과 같은 이유다.

**기준선 자체도 검산해야 한다.** 옛 기준선은 조직을 이름으로 키 잡아 232개가 192개로 접힌 채 한동안 회귀를 통과시켰고, `org_live.records` 가 0 이었다(리스트가 아니라 `{"orgs": […]}` 라서 `len()` 이 키 개수를 셌다). **0은 "없음"과 "안 셌음"이 구별되지 않는다.**

## 아직 1차 구현인 것

- **`main.py` 클린 실행 미검증** — 28단계가 순서대로 도는 것을 아직 못 봤다. Cypher 129개는 `EXPLAIN` 으로 전수 파싱했고, 증분 임베딩이 생겨 이제 전체 실행이 싸다
- **A2 수용 게이트 · B 신호 1·2층** — 설계만 있고 구현이 없다. **지금 안 하는 것이 맞다고 실측으로 판정했다**(1-9): 1층 정확도 73~82%, 확실한 구간 12%, 캐시가 있어 재실행 절감 0. 게시판 본문(10만 건)이나 재귀 크롤링이 들어오면 그때 필요해진다
- **1층을 검사로 쓰는 안** — 라우팅이 아니라 "breadcrumb 이 100% procedure 인데 LLM 이 reference 라고 했다"를 표시하는 용도. 손해가 없는 쪽인데 아직 안 재봤다
- **⑤ `IN_DOMAIN` 집계 라우터** — Domain 트리 76개를 적재해 놓고 검색이 안 탄다
- **사이트 구조가 코드에 박혀 있다** — `#contents` 셀렉터, `th/td` 메타 파싱, 조직명 규칙, 발급처 어휘. A2·B 를 만들어도 이것들을 선언으로 빼야 새 사이트가 붙는다

##### 2026-09-02 에 닫힌 것

- **증분 임베딩** — 완료. 텍스트·모델이 그대로면 건너뛴다(3-4)
- **A3 동일성** — `content_hash` 를 넣어 "무엇이 바뀌었는가"를 리포트한다(1-10). 다만 **LLM 추출은 원래부터 증분이었다** — `content_key()` 가 본문을 키에 넣고 있었다. 재수집 자체는 사이트가 캐시 헤더를 안 줘서 못 줄인다
