## 개념

벡터 검색에서 "가장 비슷한 것"을 찾는 방식은 두 가지입니다.
**정확 최근접(Exact kNN)**은 모든 벡터와 비교해 진짜 1등을 반드시 찾고, **근사 최근접(ANN, Approximate Nearest Neighbor)**은 일부만 훑어 빠르게 찾되 **놓칠 수 있습니다**.

둘 다 똑같이 코사인 유사도를 계산하는 벡터 검색입니다. 차이는 "벡터냐 아니냐"가 아니라 **전부 비교하느냐, 일부만 비교하느냐**입니다.

---

## HNSW 동작 원리

가장 널리 쓰이는 ANN 색인이 **HNSW(Hierarchical Navigable Small World)**입니다. Neo4j·Pinecone·pgvector 등이 이걸 씁니다.

색인을 만들 때 벡터들을 **"비슷한 것끼리 이웃"으로 연결한 그래프**를 만들어 둡니다. 검색은 그 그래프 위를 걸어다니는 방식입니다.

```
1. 아무 노드에서 출발
2. 지금 노드의 "이웃"들만 점수를 계산
3. 그중 질문과 가장 가까운 쪽으로 한 발 이동
4. 더 좋아지는 이웃이 없거나 탐색 예산(ef)이 끝나면 종료
```

**핵심**: 걸어가며 **밟은 노드만 점수가 계산**됩니다. 안 밟은 노드는 유사도가 아무리 높아도 **점수 자체가 존재하지 않습니다** — 순위 경쟁에서 진 게 아니라 후보 명단에 오르지 못한 것입니다.

---

## ANN이 정답을 놓치는 경우

방향은 유사도가 높은 쪽이 맞습니다. 문제는 **갈 수 있는 길이 색인 생성 시점에 미리 정해져 있다**는 점입니다.

```
[빽빽한 무리]  ←── 검색이 여기로 진입
  0.70 ┐
  0.69 │  거의 같은 임베딩 10여 개가 뭉쳐 있음
  0.69 │  → 어디로 가도 고만고만해서 개선 방향이 안 보임
  0.68 ┘  → 탐색 예산이 여기서 다 소모됨

[외딴 노드]  0.73  ←── 진짜 1등이지만 무리의 이웃 목록에 없어
                        길이 없어서 도달 불가
```

**동일 임베딩 덩어리가 많은 데이터에서 특히 잘 발생합니다.**
예: 조직도에서 같은 이름 부서가 구마다·동마다 반복되는 경우(행정민원팀 44개, 종합민원과 4개 등).

## 실측 사례 (suwon_graph)

노드 998개 규모, 질문 `"행정서비스헌장이 뭐야"`

| 탐색 폭(k) | 인덱스가 찾은 1등 | 결과 |
|---|---|---|
| 20 (당시 설정) | 행정지원과 0.7057 | 정답 누락 |
| 80 | 행정지원과 0.7057 | 정답 누락 |
| 150 | **행정서비스헌장 0.7342** | 정답 발견 |

정답 노드의 임베딩을 직접 꺼내 계산하면 0.7342로 명백한 1등인데, 인덱스는 k=150이 되어서야 후보에 올렸습니다. 상위권을 보면 원인이 드러납니다.

```
 1위  0.7341  행정서비스헌장   ← 혼자 떨어져 있음
 2위  0.7059  행정지원과   ┐
 3위  0.6964  행정지원과   │  행정지원과 5개 + 행정관리팀 5개가
 4위  0.6906  행정지원과   │  0.67~0.70 구간에 밀집
 5위  0.6885  행정관리팀   ┘
```

**k를 올리는 대응의 한계**: 같은 프로젝트에서 이전에도 노드 ~960개일 때 k=5가 다른 정답을 놓쳐 20으로 올린 적이 있습니다. 노드가 추가되면 HNSW가 이웃 연결을 다시 구성하는데, **어느 노드가 탐색 경로에서 밀려날지 미리 알 수 없습니다.** 임계값 조정은 이번 사고만 막고 다음 사고는 못 막습니다.

## 비교

| | 정확 검색(Exact kNN) | 근사 검색(ANN/HNSW) |
|---|---|---|
| 방식 | 전체 벡터와 비교 | 그래프를 따라 일부만 비교 |
| 정확도 | 항상 진짜 1등 | 놓칠 수 있음(확률적) |
| 속도(998노드 실측) | 52ms | 18ms |
| 복잡도 | O(n) | 대략 O(log n) |
| 유리한 규모 | 수천~수만 건 | 수십만 건 이상 |
| 튜닝 | 없음 | ef/M/k 조정 필요, 데이터 변경 시 재검토 |

## 선택 기준

**데이터 규모와 지연 예산으로 판단합니다.**

- 전체 응답 시간에서 벡터 검색이 차지하는 비중이 작으면 정확 검색이 유리합니다. RAG 파이프라인은 보통 LLM 호출에 2~5초를 쓰므로, 수십 ms 차이는 체감되지 않습니다.
- 수십만 건 이상이거나 벡터 검색 자체가 병목이면 ANN이 필요합니다. 이때는 ef/M 파라미터를 넉넉히 잡고 **정답 누락률(recall)을 실측**해야 합니다.
- 애매하면 정확 검색으로 시작하는 편이 안전합니다. 나중에 ANN으로 바꾸긴 쉽지만, ANN이 조용히 놓치는 정답은 **버그로 인지되지도 않습니다**.

```cypher
// Neo4j 정확 검색 (5.18+)
MATCH (n:Entity) WHERE n.embedding IS NOT NULL
WITH n, vector.similarity.cosine(n.embedding, $vector) AS score
RETURN n ORDER BY score DESC LIMIT $k

// Neo4j ANN (HNSW 인덱스)
CALL db.index.vector.queryNodes('index_name', $k, $vector)
YIELD node, score
```

## 한 눈에 요약

```
정확 검색(Exact kNN)  →  전부 비교, 반드시 1등을 찾음, O(n)
근사 검색(ANN/HNSW)   →  그래프 따라 일부만 비교, 빠르지만 놓칠 수 있음

놓치는 이유           →  점수가 낮아서가 아니라, 밟히지 않아 점수 계산 자체가 안 됨
잘 놓치는 데이터       →  거의 같은 임베딩이 덩어리로 뭉쳐 있는 경우
k 조정의 한계         →  데이터가 바뀌면 다른 노드가 밀려남, 근본 해결 아님
판단 기준             →  벡터 검색이 전체 지연에서 차지하는 비중이 작으면 정확 검색
```
