## 개념

동일한 데이터(수원시 조직도)를 **라벨 하드코딩 방식**과 **온톨로지(TBox/ABox) 방식**으로 각각 구축한 그래프DB에서, 벡터 검색 성능을 실측 비교한 정리입니다. 일반적으로 알려진 "라벨 매칭이 온톨로지보다 빠르다"는 원칙이 **벡터 검색에서는 역전**되는 현상과 그 원인을 다룹니다.

---

## 구조 차이

Neo4j 벡터 인덱스는 **"인덱스 1개 = 라벨 1개"**로 고정되어 있어, 여러 라벨을 한 인덱스로 묶어 검색할 수 없습니다.

| 항목 | 라벨 (suwon_label) | 온톨로지 (suwon_ontology) |
|---|---|---|
| 벡터 인덱스 개수 | 9개 (라벨마다 1개) | 1개 (Instance 전체) |
| 검색 방식 | scatter-gather (9개 인덱스 순회 후 병합) | 단일 쿼리 |
| 검색 시 DB 왕복 횟수 | 9회 | 1회 |

```
라벨 방식 (suwon_label)
├── 임베딩 대상이 9개 라벨(과/관/단/동/사업소/실/비서실/전문위원/팀)에 분산
├── 벡터 인덱스 9개 (라벨마다 1개)
└── 검색 시 scatter-gather 필요
    ① scatter: 9개 인덱스에 각각 따로 질의
    ② gather : 9번 결과를 합쳐서 점수순 재정렬

온톨로지 방식 (suwon_ontology)
├── 모든 타입이 :Instance 라벨 하나 아래 존재 (TYPE_OF로 Class 구분)
├── 벡터 인덱스 1개 (Instance 전체)
└── 검색 시 단일 쿼리로 끝남 (scatter-gather 불필요)
```

**scatter-gather가 필요한 이유**: 검색 전에는 정답이 어느 라벨에 있을지 알 수 없음 → 라벨을 하나라도 빼면 정답을 놓칠 위험 → 임베딩된 모든 라벨을 빠짐없이 검색해야 함.

---

## 예시 — 검색 쿼리 비교

```cypher
// 라벨 방식: 인덱스 개수만큼 반복 (9회)
CALL db.index.vector.queryNodes('팀_embedding', 20, $vec) YIELD node, score ...
CALL db.index.vector.queryNodes('과_embedding', 20, $vec) YIELD node, score ...
// ... 7개 더 반복 후 파이썬에서 병합/재정렬

// 온톨로지 방식: 단일 쿼리 (1회), 타입 표시는 같은 쿼리에 TYPE_OF 홉만 추가
CALL db.index.vector.queryNodes('instance_embedding', 20, $vec) YIELD node, score
MATCH (node)-[:TYPE_OF]->(c:Class)
RETURN node.id, c.name AS type, score
```

## 실측 결과

동일 조건(pool_size=20, 20회 반복 평균, 순수 DB 왕복 시간만 측정)으로 비교:

| 항목 | 라벨 방식 | 온톨로지 방식 |
|---|---|---|
| 벡터 인덱스 개수 | 9개 | 1개 |
| DB 왕복 횟수 | 9회 | 1회 |
| 평균 응답 시간 | 48.4ms | 15.3ms |
| 배수 | - | **약 3.17배 빠름** |

---

## 왜 역전이 생기는가

벡터 유사도 계산(HNSW) 자체는 두 방식 모두 동일 기술이고, 계산량 차이도 거의 없습니다 (HNSW는 **로그 스케일(log N)**로 동작하므로 914개를 1묶음으로 보든 9묶음으로 쪼개 보든 순수 계산 시간은 무시할 수준). 실제 병목은 **요청 1회당 발생하는 고정 오버헤드**(네트워크 왕복, Cypher 파싱, 트랜잭션 처리)입니다. 이 고정비가 라벨 방식은 9번, 온톨로지 방식은 1번 발생하는 게 속도 차이의 실질적 원인입니다.

> 일반적인 그래프 탐색(`MATCH (n:과)` 등 단순 라벨 매칭)에서는 여전히 라벨 방식이 유리합니다 — 네이티브 라벨 인덱스로 즉시 찾아지는 반면, 온톨로지는 매번 TYPE_OF 관계를 한 홉 더 타야 하기 때문입니다. 벡터 검색만 예외적으로 역전되는 건 "벡터 인덱스가 라벨을 넘나들 수 없다"는 Neo4j 자체의 구조적 제약 때문입니다.

---

## 종합 비교 — 연산 종류별 승자

"온톨로지가 다 이긴다"가 아니라 **연산 종류에 따라 승자가 갈립니다.** 오늘 실측한 건 벡터 검색 하나뿐이고, 그 외 연산에서는 라벨 쪽이 유리하거나 무승부입니다.

| 연산 종류 | 승자 | 이유 |
|---|---|---|
| 벡터 검색 | **온톨로지** (3.17배 빠름) | 인덱스 1개 vs 9개 — 왕복 횟수 차이 |
| id로 특정 노드 조회/경로 탐색 (`{id: $id}`) | 거의 동일 | id가 전역 유니크라 라벨 지정 여부와 무관하게 바로 찾음 |
| 타입으로 전체를 걸러내는 조회 (`MATCH (n:과)` 등) | **라벨** | 아래 설명 참고 |
| 검색 스크립트 코드 복잡도 | 온톨로지 (근소) | scatter-gather 로직 자체가 없어지고, label 인자가 함수 시그니처에서 사라짐 |
| 스키마 유연성 (새 조직 타입 추가 등) | 온톨로지 | Class 노드 하나만 추가하면 됨, 라벨 방식은 코드(ORG_LABELS 목록 등) 수정 필요 |

### 왜 타입 필터링은 라벨이 더 빠른가

**라벨 매칭** (`MATCH (n:과)`): Neo4j는 각 노드가 가진 라벨 정보를 노드 자체에 직접 저장해두고(토큰 인덱스), "이 노드가 과 라벨을 가졌는가"를 노드 하나만 보고 즉시 확인합니다. 다른 노드나 관계를 거칠 필요가 없는 **1단계짜리 확인**입니다.

**TYPE_OF 매칭** (`MATCH (n:Instance)-[:TYPE_OF]->(c:Class {name:'과'})`): 최소 **2단계**가 필요합니다 — ① `Class` 노드 중 이름이 "과"인 걸 먼저 찾고, ② 거기서 `TYPE_OF` 관계를 타고 들어오는 `Instance` 노드를 하나씩 방문. Neo4j의 index-free adjacency(관계를 포인터로 바로 따라가는 방식) 덕분에 각 홉 자체는 빠르지만(그래프 크기와 무관하게 O(1)), **"포인터를 한 번 더 따라가야 한다"는 사실 자체가 라벨 매칭보다 한 단계 많은 작업**이라 그만큼 느립니다.

즉 벡터 검색에서 온톨로지가 이긴 이유(왕복 횟수 감소)와 타입 필터링에서 라벨이 이기는 이유(관계 홉 생략)는 **같은 원리의 양면**입니다 — "정보가 노드 자체에 붙어있는가(라벨), 아니면 관계를 타고 가야 얻어지는가(TYPE_OF)"의 차이.

## 인덱스 개념 정리 — 왜 파티셔닝이 손해였는가

### 인덱스란 무엇인가

**"인덱스 하나"는 값 하나가 아니라, 특정 컬럼(또는 라벨)의 모든 값을 빠르게 찾을 수 있게 만들어둔 자료구조 전체**입니다. 책 뒤에 있는 색인(찾아보기)과 같은 개념 — 색인은 단어 하나가 아니라 그 책에 나오는 모든 단어+페이지 목록을 정리해둔 표 전체를 가리킴.

```
"인덱스 1개" = 컬럼 안의 값 1, 2, 3, ..., N 전부를 담아 빠르게 찾게 해주는 구조 하나

온톨로지: instance_embedding 인덱스 1개 안에 914개 벡터가 전부 들어있음
라벨:     팀_embedding(707개) / 과_embedding(124개) / ... 로 같은 914개를 9개 구조로 쪼갠 것
```

### 나눠도 되는 경우 vs 나누면 손해인 경우

일반적으로 "인덱스를 나누면(파티셔닝) 항상 나쁘다"는 법칙은 아닙니다. 핵심은 **검색 전에 "어느 조각을 봐야 할지" 미리 알 수 있는가**입니다.

- **나눠도/나누는 게 유리한 경우**: 어느 파티션에 답이 있는지 미리 알아서, 나머지 파티션을 아예 건너뛸 수 있는 경우(partition pruning). 이땐 작은 인덱스 여러 개가 오히려 유리할 수 있음.
- **나누면 손해인 경우**: 어느 파티션에 답이 있을지 검색 전엔 알 수 없어서, **매번 전부 다 봐야 하는 경우**. 이땐 건너뛰기의 이점 없이 왕복 비용만 늘어남.

오늘 사례가 후자입니다 — "여권 재발급"의 답이 팀/과/관 중 어디 있을지 미리 모르니 9개 라벨(파티션)을 하나도 건너뛸 수 없음. 정확히는 **HNSW 자체가 각 인덱스 안에서 모든 벡터를 일일이 스캔하는 게 아니라**(그건 브루트포스), **"9개 파티션 중 단 하나도 스킵할 수 없다"**는 게 핵심 — 파티션 자체를 건너뛸 방법이 없으니, 굳이 나눌 이유가 없었던 것.

### pgvector와의 비교

pgvector에서 인덱스가 보통 1개인 이유는, 데이터를 처음부터 **한 테이블(=한 라벨)로 통합 관리**하기 때문입니다. "인덱스를 하나로 만들자"고 별도로 정한 게 아니라, 데이터 모델 자체를 통합했기 때문에 인덱스도 자연스럽게 하나가 된 것 — 이게 정확히 온톨로지(`:Instance` 하나에 통합) 구조와 같은 패턴입니다. 반대로 pgvector에서도 타입마다 테이블을 9개로 쪼개서 관리했다면 인덱스도 9개가 되고, 똑같은 파티셔닝 손해를 겪었을 것입니다.

### Neo4j는 HNSW만 지원

Neo4j 5의 벡터 인덱스는 **HNSW 알고리즘 하나만 지원**하며, IVFFlat 등 다른 대안은 없습니다. 다만 이 프로젝트 규모(임베딩 914개)에서는 어떤 알고리즘을 쓰든 체감 속도 차이가 거의 없습니다 — HNSW의 진짜 장점(브루트포스 대비 로그 스케일 우위)은 수십만~수백만 개 규모에서 나타나기 때문입니다. 오늘 측정한 속도 차이(48.4ms vs 15.3ms)는 **알고리즘(HNSW) 성능 차이가 아니라, 파티션을 몇 번 왕복하느냐의 차이**였습니다.

## 검토 — "검색 전에 어느 라벨에서 찾을지 미리 선별하면 안 되나?"

기술적으로는 가능하지만 채택하지 않는 이유:

1. **정확도 리스크**: 질문을 보고 "이건 팀 라벨에만 있을 것 같다"고 미리 판단해 해당 인덱스만 검색했는데 그 판단이 틀리면, 정답이 있는 인덱스를 아예 안 뒤지게 되어 **답을 통째로 놓침**. scatter-gather는 느려도 전부 뒤지므로 누락 위험이 없다는 게 핵심 장점인데, 선별을 넣으면 이 보장이 깨짐.
2. **선별 자체가 공짜가 아님**: "어느 라벨일지" 판단하는 것도 그 자체로 분류 작업(LLM 등)이 필요하고, 벡터 검색 자체보다 더 느리고 비쌀 수 있음.

**"데이터가 쌓이면 라벨 방식이 유리해지지 않나?"**: 아니라고 판단. HNSW는 로그 스케일이라 데이터가 늘어도 개별 인덱스 검색 시간은 거의 늘지 않음. 반면 왕복 1회당 고정 오버헤드는 데이터 양과 무관하게 항상 동일. 즉 격차의 원인이 "계산량"이 아니라 "왕복 횟수"이므로, 데이터가 아무리 쌓여도 이 배수 차이는 줄어들지 않고 유지됨.

**참고 — 정석적 해법**: 인덱스는 1개로 두고 그 안에서 타입을 필터 조건으로 거는 **filtered ANN search** 방식이 있음 (pgvector의 WHERE절 결합 인덱스 검색 등). 다만 지금 쓰는 Neo4j 벡터 인덱스는 "인덱스 1개 = 라벨 1개" 구조가 고정이라 이 방식 자체가 적용 불가능함. 온톨로지 구조는 애초에 라벨이 하나뿐이라 이 제약을 만나지 않음.

## 한 눈에 요약

```
벡터 인덱스 제약     →  Neo4j: 인덱스 1개 = 라벨 1개 (라벨 넘나드는 검색 불가)

라벨 방식            →  임베딩 대상이 9개 라벨에 분산 → 인덱스 9개
                     →  scatter-gather 필요 (9회 왕복 후 병합)
온톨로지 방식         →  모든 타입이 :Instance 하나 → 인덱스 1개
                     →  단일 쿼리로 끝남 (1회 왕복)

실측                 →  라벨 48.4ms vs 온톨로지 15.3ms (약 3.2배)
역전 원인            →  HNSW 계산량 차이 아님 (log N이라 무시할 수준)
                     →  요청 1회당 고정 오버헤드(네트워크/파싱/트랜잭션)가
                        9번 vs 1번 반복되는 게 진짜 병목

일반 그래프 탐색      →  라벨 방식이 여전히 유리 (네이티브 인덱스, TYPE_OF 홉 불필요)
벡터 검색만 예외      →  라벨 분산 → 인덱스 분산 → 왕복 배수 증가로 역전

사전 선별 미채택 이유 →  ① 오판 시 정답 인덱스 자체를 놓침 (recall 손실)
                        ② 선별 판단 자체도 비용 (LLM 분류 등)
스케일 논쟁          →  데이터 늘어도 격차 안 줄어듦 (병목이 계산량이 아니라 왕복 횟수라서)
정석 해법            →  filtered ANN search (단일 인덱스 + 타입 필터), 단 Neo4j 현재 버전 미지원
```
