## 개념

**온톨로지 레이어(Layer)**는 지식그래프에 담기는 지식의 종류를 층위별로 나눈 것이다. 하나의 그래프 안에 스키마(어떤 개념이 있는가), 실제 데이터(누가/무엇이 있는가), 업무 지식(무엇을 어떻게 처리하는가), 검색 계층(질문을 어떻게 찾아가는가)이 서로 다른 층으로 쌓인다. 각 층은 서로 다른 종류의 질문에 답하기 위해 존재하며, 하나가 다른 하나를 대체하지 않는다.

---

## 구조 — Layer 0~3

| Layer | 정의 | 답할 수 있는 질문 |
|---|---|---|
| **Layer 0** | 스키마(TBox) — 어떤 종류의 개념(Class)이 존재하는가, 그 개념들의 상하위(is-a) 관계 | "이 조직은 어떤 유형인가?" |
| **Layer 1** | 실제 데이터(ABox) — Layer 0 개념의 구체적 인스턴스와 소속/포함 관계 | "이 부서는 어디 소속인가?" |
| **Layer 2** | 업무·서비스 지식 — 조직이 실제로 처리하는 일의 구조화된 사실(서류, 기한, 법령, 절차) | "이 민원을 처리하려면 뭐가 필요한가?" |
| **Layer 3** | 임베딩/벡터 검색 — 자연어 질의를 그래프의 특정 노드에 의미적으로 매칭 | "이 애매한 질문은 어느 노드와 관련 있는가?" |

```
Layer 0 (스키마)     조직, 구성원, 서비스, 서류, 법령 ... 이런 "종류"가 있다
   ↓ 정의
Layer 1 (실제 데이터)  행정민원팀, 김OO 주무관 ... 실제 개체와 소속 관계
   ↓ 그 위에
Layer 2 (업무 지식)   전입신고 → 신분증 필요, 14일 이내, 주민등록법 16조
   ↓ 검색을 위해
Layer 3 (임베딩)      "이사했는데 신고해야 하나요?" → 위 어느 노드와 매칭되는가
```

Layer 0·1은 "무엇이 존재하는가"를 다루고, Layer 2는 "그것이 무엇을 하는가"를 다루며, Layer 3는 "어떻게 찾아가는가"를 다룬다. **층이 다르므로 하나를 잘 만든다고 다른 층의 부재가 채워지지 않는다.**

---

## Layer 2가 필요한 이유

### Layer 1만으로는 부족한 지점

조직도 데이터에는 보통 "이 팀이 어떤 업무를 담당한다"는 정보가 사람이 적어놓은 짧은 서술형 텍스트로만 존재한다 (예: "통합민원(전입, 주민등록)"). 이 텍스트가 실제로 알려주는 건 "누가 담당인지" 뿐이다. 다음 정보는 여기에 애초에 존재하지 않는다.

- 그 업무를 처리하려면 어떤 서류가 필요한가
- 처리 기한과 수수료는 얼마인가
- 법적 근거 조항은 무엇인가
- 처리 후 이어지는 다음 절차는 무엇인가

원본 데이터 수집 단계에서 애초에 수집되지 않은 정보이기 때문에, 텍스트를 아무리 정교하게 분석해도 나오지 않는다.

### Layer 3(임베딩)로도 못 푸는 이유

**임베딩**은 의미가 비슷한 노드를 찾아주는 기술이지, 없는 사실을 만들어내는 기술이 아니다. "전입신고"로 검색하면 벡터 유사도로 담당 부서까지는 찾아줄 수 있지만, 거기서 "신분증이 필요하다"는 사실 자체가 그래프 어디에도 적혀있지 않으면 검색 기술이 아무리 좋아도 답을 끄집어낼 수 없다. 검색 방식의 문제가 아니라 데이터 자체가 없는 문제이므로, 이건 검색 개선이 아니라 **없는 지식을 새로 구조화해서 채워 넣는 작업**이다.

---

## Layer 2의 구조 — 새 노드와 관계

기존 조직 노드는 건드리지 않고, 그 위에 새로운 노드 종류를 얹어 화살표로 연결하는 방식이다.

```
(Service {name: "전입신고", 기한: "14일 이내", 수수료: "무료"})
     -[:HANDLED_BY]-> (기존 조직 노드)             ← 담당 조직 연결
     -[:REQUIRES]-> (Document {name: "신분증"})     ← 필요 서류
     -[:REQUIRES]-> (Document {name: "임대차계약서"})
     -[:BASED_ON]-> (Law {name: "주민등록법", 조항: "제16조"})
     -[:PRECEDES]-> (Service {name: "확정일자 신고"})  ← 다음 절차
```

`Document`(서류)·`Law`(법령)를 별도 노드로 분리하는 이유는 **재사용성**이다. "신분증"이 여러 민원에 공통으로 필요하다면, 텍스트로 매번 중복 기술하는 대신 노드 하나를 만들고 여러 관계로 연결하면 요건이 바뀔 때 한 곳만 고치면 되고, "이 서류가 필요한 민원 전부"도 역방향으로 즉시 조회할 수 있다.

`PRECEDES`(절차 순서)는 서로 다른 조직에 걸친 처리 순서(전입신고 → 확정일자 신고)까지 표현하는데, 이는 개인/팀의 업무 서술 텍스트로는 담을 수 없는 **여러 조직에 걸친 프로세스 지식**이다.

### 넣기 전 / 넣은 후

| 질문 | Layer 2 없음 | Layer 2 있음 |
|---|---|---|
| "이 부서가 뭐 하는 곳이에요?" | 업무 텍스트 유사도로 대충 답변 가능 | 동일 |
| "필요 서류가 뭐예요?" | ❌ 그래프에 이 정보 자체가 없음 | ✅ `REQUIRES` 따라가서 정확히 답 |
| "하고 나서 뭐 해야 해요?" | ❌ | ✅ `PRECEDES` 따라가서 다음 절차 안내 |
| "법적 근거가 뭐예요?" | ❌ | ✅ `BASED_ON` 따라가서 조항까지 인용 |

## 연결 단위 — 조직 O, 개인 X

Layer 2의 `HANDLED_BY`는 팀/과 같은 조직 단위에 연결해야 하며, 개별 직원 노드에 연결하면 안 된다.

| 이유 | 설명 |
|---|---|
| **안정성** | 담당 조직은 인사이동과 무관하게 유지되지만, 특정 개인은 발령 한 번으로 바뀜. 개인 단위 연결은 인사이동마다 관계를 다시 걸어야 하는 유지보수 부담 발생 |
| **다대다 문제** | 하나의 업무를 여러 명이 나눠 맡는 경우가 흔한데, 그중 한 명만 특정해서 연결할 근거가 없음. 조직 단위로 묶으면 자연스럽게 해소 |
| **개인 식별 정보 한계** | 원본 데이터가 개인정보 보호로 이름 없이 직책·업무·전화번호만 있는 경우가 많아, 개인을 안정적인 연결 대상으로 삼기 어려움 |

담당자 연락처가 필요하면, 서비스 → 조직까지 연결한 뒤 조직에 이미 있는 소속 관계를 한 번 더 타서 **파생**시키면 된다. 별도로 중복 저장할 필요가 없다 — 인사이동이 생겨도 조직-직원 소속 관계만 갱신하면 서비스-조직 연결은 그대로 유효하다.

```cypher
MATCH (svc:Service {name:"전입신고"})-[:HANDLED_BY]->(team)
MATCH (team)<-[:PART_OF]-(staff)
RETURN staff.position, staff.phone   // 저장 안 해도 항상 최신 담당자가 파생됨
```

## 검색 흐름 — Graph RAG 패턴

1. **벡터 검색**(Layer 3)으로 질문과 의미적으로 가장 가까운 노드를 찾는다 (앵커 확정)
2. **관계 타입을 미리 지정**해서 1~2홉만 선택적으로 확장한다 (`REQUIRES`, `BASED_ON`, `HANDLED_BY`, `PART_OF`역방향 등)
3. 끌어온 사실(서류·법령·연락처)을 언어모델 컨텍스트로 제공 → 모델이 종합해 답변 생성

```cypher
MATCH (team:Instance {name:"행정민원팀"})
OPTIONAL MATCH (svc:Service)-[:HANDLED_BY]->(team) WHERE svc.name CONTAINS "전입"
OPTIONAL MATCH (svc)-[:REQUIRES]->(doc:Document)
OPTIONAL MATCH (svc)-[:BASED_ON]->(law:Law)
OPTIONAL MATCH (team)<-[:PART_OF]-(staff) WHERE staff.duty CONTAINS "전입"
RETURN svc, collect(DISTINCT doc.name), collect(DISTINCT law.name), collect(DISTINCT staff.phone)
```

관계 타입을 가리지 않고 무제한으로 확장하면 안 된다. 조직 위계를 타고 최상위까지 딸려오거나(예: 팀 → ... → 시청) 널리 공유되는 서류 노드를 거쳐 전혀 관계없는 다른 민원까지 섞여 들어올 수 있다. 필요한 관계 타입과 방향을 명시적으로 지정해 **1~2홉으로 제한**해야 노이즈 없이 정확한 컨텍스트가 만들어진다.

## 임베딩 확장 필요성

기존 임베딩은 보통 조직(팀) 단위로, 소속 인원들의 업무 텍스트를 하나로 뭉쳐서 벡터화한다. 이 방식은 한 조직이 여러 종류의 업무를 처리할 때 모든 업무가 비슷한 하나의 벡터로 **뭉뚱그려지는 한계**가 있다 — 서로 다른 민원 질문이 전부 같은 조직 벡터에 걸려버려서, 그 조직이 처리하는 여러 업무 중 정확히 무엇을 사용자가 원하는지 벡터만으로는 구분되지 않는다.

Layer 2에서 만든 `Service` 노드를 개별적으로 임베딩하면, 각 서비스마다 고유하고 정밀한 벡터가 생겨 질문 의도와 훨씬 정확하게 매칭된다. 이렇게 되면 검색 진입점도 자연스럽게 바뀐다.

| 검색 진입점 | Layer 2 이전 | Layer 2 이후 |
|---|---|---|
| 1차 검색 대상 | 조직(팀) | 서비스(Service) |
| 홉 방향 | 조직 → (관계로 서비스 탐색) | 서비스 → `HANDLED_BY` 역방향으로 조직/연락처 |

**임베딩 우선순위**: `Service`(정밀도 이득 큼) > 기존 조직(이미 존재) > `Document`/`Law`(사용자가 직접 검색어로 쓸 일이 적어 우선순위 낮음, 항상 Service를 거쳐 도달하는 값이므로).

## 한 눈에 요약

```
Layer 0   →  스키마(TBox)     →  "어떤 개념이 있는가"
Layer 1   →  실제 데이터(ABox) →  "실제로 뭐가 있고 어디 소속인가"
Layer 2   →  업무 지식        →  "그게 실제로 뭘 하는가" (서류/기한/법령/절차)
Layer 3   →  임베딩/벡터검색   →  "애매한 질문을 어느 노드로 연결할까"

Layer 2가 필요한 이유
  →  기존 업무 서술 텍스트는 "담당자"만 알려줄 뿐 서류/기한/법령/절차는 없음
  →  임베딩은 있는 걸 "찾아줄" 뿐 없는 사실을 "만들어내지" 못함

Layer 2 구조
  →  Service -[:HANDLED_BY]-> 기존 조직 노드 (조직 자체는 안 건드림)
  →  Service -[:REQUIRES]-> Document / -[:BASED_ON]-> Law (재사용 가능한 별도 노드)
  →  Service -[:PRECEDES]-> Service (조직을 넘나드는 절차 순서)

연결 단위       →  조직(팀/과) O, 개인 X (안정성 · 다대다 · 개인 비식별 문제)
담당자 연락처    →  저장 안 하고 조직-직원 소속 관계에서 파생

검색 흐름(Graph RAG)
  →  ① 벡터 검색으로 앵커 확정
  →  ② 관계 타입 화이트리스트로 1~2홉만 선택적 확장
  →  ③ 끌어온 사실을 LLM 컨텍스트로 제공
  →  주의: 무제한 홉 확장은 노이즈·무관한 정보 혼입 위험

임베딩 확장
  →  조직 단위 임베딩은 여러 업무가 뭉뚱그려져 정밀도 낮음
  →  Service 단위 임베딩 추가 시 검색 정밀도 상승, 진입점이 조직→Service로 이동
  →  우선순위: Service > 기존 조직 > Document/Law
```
