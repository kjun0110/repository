# KG_나라원 운영 전환 점검

작성 2026-09-09 · 대상 `nara1graph` · 비교 대상 수원시 구현

---

## 요약

나라원 KG 는 **설계 검증용 프로토타입으로는 목표를 달성**했다. 선언 한 벌로 검사·적재·추론·질의를 생성하는 구조가 실제로 동작하고, 데이터 정합성 장치는 수원 구현보다 나은 부분이 있다.

다만 **운영 서비스 기준으로는 출시할 수 없다.** 인증·권한·제한·트랜잭션·배포가 통째로 비어 있다. 이는 온톨로지 설계와 무관한, 어떤 API 든 갖춰야 하는 영역이다.

| | 나라원 | 수원 |
|---|---|---|
| 데이터 정합성 | **강함** | 강함 |
| 쓰기 경로 안전성 | 약함 | **강함** |
| 서빙 범위 | **15개 라벨** | 조직 질의 1개 |
| 서빙 안전성 | 약함 | **강함** |
| 운영 골격 | 없음 | **있음** |

**결론** — 수원 과업에는 *수원의 운영 골격 + 나라원의 선언 방식* 조합이 맞다.

## 2. 출시를 막는 것 — 5

### ① 인증이 사실상 없다 (최우선)

```python
api_key = get("SERVE_API_KEY") or ""
def auth(x_api_key = Header(default="")):
    if api_key and x_api_key != api_key:   # api_key 가 빈 문자열이면 통째로 안 탄다
        raise HTTPException(401)
```

환경변수가 빠지면 **인증이 조용히 꺼진다.** 호출마다 OpenAI 비용이 나가는 API 가 무방비로 열린다.

**조치** — 키 미설정 시 서버 기동 자체를 거부.

### ② 읽기 전용 세션이 아니다

LLM 이 생성한 Cypher 를 쓰기 권한 세션에서 실행한다. 가드는 정규식 금지목록 하나뿐이라 방향이 거꾸로다.

```
차단   MATCH (n) DETACH DELETE n
차단   CALL apoc.load.json(...)
통과   CALL dbms.components()      ← 서버 정보 노출
통과   CALL db.labels()            ← 스키마 열람
```

**조치** — `session(default_access_mode=READ_ACCESS)` + 서빙 전용 읽기 계정 분리.

### ③ 쿼리 타임아웃·행수 제한 없음

생성된 Cypher 가 전체 스캔을 돌면 그대로 대기한다. 수원 규모(노드 2.4만)에서는 한 질문이 서버를 수 초간 점유한다.

**조치** — 타임아웃 2초 + 행수 상한(초과 시 명시적 거절).

### ④ 적재가 트랜잭션이 아니다

```python
s.run("노드 넣기")   # 성공
s.run("간선 넣기")   # 여기서 중단되면
```

노드만 있고 간선이 없는 그래프로 응답하게 된다. 롤백 경로가 없다.

**조치** — 단일 트랜잭션 + 적재 후 건수 대조 + 불일치 시 롤백.

### ⑤ 레이트리밋·CORS 없음

공공 홈페이지에 연결되는 API 에 호출 제한이 없다.

## 3. 구조라 나중에 못 바꾸는 것 — 3

### ⑥ 이름이 같으면 즉시 병합한다

```yaml
Organization: "org:{slug(org_name)}"
```

문자열 일치만으로 동일 개체로 판단한다. 수원 기준으로는 **같은 이름의 과가 여러 국에 존재**할 수 있다. 조직도는 `path` 기반 키로 해결했으나, 발주처·담당자 등은 여전히 이름 기준이다.

수원 구현은 관측 단위로 노드를 분리하고(`identity_status="review_required"`) 사람 검토 후 병합한다. **이 방식이 옳다.**

> 착수 시점에 정해야 한다. 나중에 바꾸면 전체 재적재.

### ⑦ 그래프에 온톨로지 버전이 없다

```yaml
meta:
  version: 1        # 적혀 있으나 어디서도 읽지 않음
```

노드 속성에 `ontology_version` 이 없어, 스키마 변경 후 부분 재적재하면 구·신 버전이 섞여도 감지되지 않는다. 실제로 라벨 변경 시 옛 산출물이 섞이는 사고가 발생했고 검증기가 우연히 잡았다.

**조치** — semver 로 전환 + 적재 시 전 노드에 각인 + 서빙 기동 시 대조.

### ⑧ 개인정보 정책 미검토

수원 조직도에는 담당자 성명·직통번호가 포함된다. 그래프 적재 시:

- 챗봇 답변에 개인 성명 노출
- 벡터 임베딩에 포함되어 유사도 검색으로 노출
- 질의 로그에 함께 기록

**적재 여부와 마스킹 방침을 선언 단계에서 확정해야 한다.** 현 구조에 `status: unavailable` 로 "수집하지 않음"을 선언하는 자리가 이미 있다.

## 4. 온톨로지 선언 자체의 갭

### 카디널리티 6종이 선언만 되고 검사되지 않음

```
선언   N:1 7 · 1:N 5 · N:M 4 · 1:1 1
검사   N:1 만
```

미검사 관계: `PERFORMED` `HOMEPAGE` `HAS_OFFICE` `HAS_HISTORY` `HOLDS` `OFFERS`

`HOMEPAGE` 가 `1:1` 로 선언돼 있으나 한 기관에 둘이 붙어도 잡히지 않는다. **선언이 사실과 다른 상태.**

### 추론 허용 정책이 없음

수원 구현은 관계별로 `inference_policy: direct_only | deterministic` 를 선언하고, 위반 시 거절한다. 나라원은 `derived: true` 표식만 있고 **"이 관계는 추론으로 만들면 안 된다"는 선언이 없다.**

### 동결본 대조가 없음

수원은 적재 시 릴리스 선언과 동결 아티팩트를 바이트 단위로 대조한다. 나라원은 메타스키마가 문법만 검사하며, **선언을 수정하고 적재만 돌려도 통과한다.**

### 값 제약이 enum 뿐

범위·정규식·길이·날짜 구간 제약이 없다. `contract_date` 에 미래 날짜가 들어와도 통과한다. `span: [2021-10-01, 2024-12-26]` 이 선언에 있으나 검사로 이어지지 않는다.

## 5. 운영 골격 — 전부 없음

```
배포        Docker · CI · DEV/PROD 분리 · 롤백
모니터링    응답시간 · 오답률 · 에러율
request_id  로그와 응답을 잇는 식별자
재현성      같은 입력 → 같은 그래프 증명
릴리스      상태 전이 기록 (previous → expected_before → after)
```

질의 로그는 파일로 쌓이나 **특정 응답을 역추적할 수단이 없다.**

### 응답 계약 비교

```
나라원   answer · found · route · sources · elapsed_ms
수원     contract_version · ontology_version · request_id ·
         outcome · reason · items · elapsed_ms
         outcome ∈ {ok, no_match, ambiguous, unauthorized,
                    timeout, unavailable, ontology_version_mismatch}
```

`ambiguous` 부재가 특히 크다. 수원은 경로가 복수면 추측하지 않고 반환한다. 나라원은 LLM 이 하나를 선택한다.

## 6. 나라원이 더 나은 것 (수원에 이관 권장)

### 선언에서 검사 자동 생성

```
선언 18줄 → 검사 118건
```

관계 선언 3줄이 검사 4개 + MERGE 문 + 규칙 경로 + LLM 스키마 카드 한 줄로 전개된다. 수원의 3계층 검증은 강력하나 **파이썬으로 직접 작성**하므로 라벨 추가 시 검사도 함께 늘려야 한다.

### 변화량 기준 검증 (drift)

```yaml
- {check: node_count, label: Project, drift: true}
drift: {shrink: block, grow: warn, jump: 0.2}
```

기대치를 사람이 적지 않는다. 직전 실행 측정값과 대조한다.

```
+1건       경고, 통과          사람 개입 0
-1건       차단 + 사라진 id 특정
절반 유실   차단 (51% 변화)
80건 급증   차단 (39% 변화, 증가여도 차단)
```

**게시물이 매일 증가하는 수원 환경에 필수.** 고정 기대치는 매 수집마다 사람이 숫자를 갱신해야 하고, 그런 검사는 곧 비활성화된다.

### 선언 문법 검증 (metaschema)

```
✘ edges.ORDERED_BY.cardinalty 를 엔진이 읽지 않는다
✘ extract...into 의 Project.nam 속성이 선언에 없다
✘ validate.blocking[0].check 가 node_conut 다 (node_count 오타인가?)
```

선언 오타로 검사가 조용히 사라지는 것을 로드 시점에 차단한다.

### 계층 일반화

부서/팀을 단일 라벨 + `level` 속성 + 자기참조 간선으로 통합. **층이 늘어도 라벨·간선·검사가 늘지 않는다.** 수원 조직도(국·과·팀 3~4단)에 그대로 적용 가능하며 3단 트리 검증 완료.

### caveats → 스키마 카드

37건의 주의사항이 LLM 프롬프트에 직접 반영된다.

```
"한 사업이 분야 2~3개에 걸칠 수 있다. 분야로 세면 합이 206을 넘는다"
"기관유형은 Organization 이 아니라 Project 에 붙는다"
"계약금액은 원본에 없다. 물어보면 데이터 없음으로 답해야 한다"
```

속성 목록만 제공하면 LLM 이 그럴듯하게 틀린 질의를 생성한다. Neo4j 는 없는 속성 조회 시 오류가 아닌 **빈 결과**를 반환하므로 조용히 오답이 된다.

## 7. 우선순위

### 1주차 — 미조치 시 서비스 불가 (약 1일)

| | 항목 | 소요 |
|---|---|---|
| ① | 키 미설정 시 기동 거부 | 30분 |
| ② | READ_ACCESS + 읽기 전용 DB 계정 | 1시간 |
| ③ | 쿼리 타임아웃 + 행수 상한 | 1시간 |
| ④ | 적재 트랜잭션 + 롤백 | 3시간 |
| ⑤ | 레이트리밋 | 2시간 |

### 2~3주차 — 구조 확정 (나중에 변경 불가)

- ⑥ 관측 단위 동일성 정책
- ⑦ `ontology_version` 각인 + 서빙 대조
- ⑧ 개인정보 방침 → 선언 반영
- 응답 계약 확장 (`outcome` · `request_id` · `ambiguous`)
- 카디널리티 6종 검사 보완

### 이후

- 배포 파이프라인 · 릴리스 체인 · replay · 모니터링

## 8. 수원시 착수 시 반영 사항

| 항목 | 근거 |
|---|---|
| 식별자는 사이트가 제공하는 안정 키 사용 | 이름 기반 키는 표기 변경 시 노드 분리 |
| 관측 단위와 실체를 분리 | 동명 조직 병합 방지. 사후 변경 불가 |
| 건수 검증은 변화량 기준 | 게시물 일일 증가. 고정값은 검사 비활성화로 이어짐 |
| 계층은 단일 라벨 + level | 3~4단 구조에서 라벨 증식 방지 |
| 개인정보 수집 범위 사전 확정 | 담당자 성명·연락처 |
| 온톨로지 버전 데이터 각인 | 부분 재적재 시 혼입 감지 |
